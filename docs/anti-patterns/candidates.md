# アンチパターン候補メモ

正式な AP リスト本体（planning.md / implementation.md / writing.md / workflow.md）とは別扱いのメモ置き場です。N≥3 件発生時に正式 AP として昇格を検討してください。取り下げた候補の記録も、同じ誤診を繰り返さないためにここへ残します。

このファイルは通常のレビューで読み込む必要はありません（候補の追記・昇格判断のときだけ開く）。

## AP-WF18 候補: 取り下げ（cycle-301）

サブエージェントの稼働状態を監視して長時間停止を検出する、という案。取り下げ理由は、監視がハーネスの禁じる読み取りへ誘導すること、および長時間化の原因はタスクの束ねすぎであって監視では直らないこと。ハング自体の予防は `docs/knowledge/playwright-mcp.md` が正典。詳細は cycle-301/incident-1.md。

## AP-WF19 候補: 計測値 SSoT を「実測値」として記録する際、生成元スクリプトの実出力（生成物のキー・値）と照合せず確定していないか

- **概要**: AP-P21 計測等の SSoT を §補足事項に書き戻す際、「実測値 / 生成元 = <計測スクリプト>」と記載するが、その生成元スクリプトが当該値を実際には出力していない形。生成元を書いても「その生成元が当該値を吐くこと」を確認していないため、AP-WF12（実体確認）/ AP-P16（生成元併記）の射程をすり抜ける。算術的に自己整合した手計算値を「実測値」と誤記録すると、後続サイクルが引用する基準値の信頼性が崩れる。
- **発生件数**: N=2（cycle-218, 219。詳細 cycle-218.md の T-4 の MAJOR-2・cycle-219.md の T-4 の MAJOR-1）。N≥3 で新設検討。
- **対症療法案**: 計測値を「実測値 / 生成元 = <script>」と記録する前に、生成物（results.json 等）に当該キー・値が実在することを grep で確認し SSoT の数値と桁まで一致させる。スクリプト修正後は必ず再実行して生成物を更新してから SSoT へ書き戻す。

## AP-WF20 候補: 修正後の再レビューを既存レビュアーの流用で行い、白紙からの全体見直しになっていない

- **概要**: 修正後の再レビューを、そのタスクを前にレビューした既存レビュアーに SendMessage で継続依頼して行うと、レビュアーは自分の前回指摘が直ったかの確認に視野が狭まり、全体を白紙から見直すバイアスがかかる。AP-WF01「最後の修正後にゼロからすべてを見直す」の実効には、再レビューのたびに新規レビュアーをゼロから起動し、前回の指摘・経緯を渡さず白紙で全体を見直させる必要がある。
- **発生件数**: N=2（cycle-243, 320。cycle-320 はフックをすり抜けた形態。詳細 cycle-243.md の違反5・cycle-320/index.md の手順を外れたこと・cycle-320/review-ap-check-2.md の G1）。N≥3 で新設検討。
- **対症療法案**: 再レビューは既存レビュアーの SendMessage 継続でなく新規エージェントを起動し、対象ファイルと観点のみを渡して（前回指摘は渡さず）白紙で全体を見直させる。
- **補足（技術的強制）**: SendMessage 経由の再レビュー依頼は `.claude/hooks/block-review-reuse.sh` が止める。hook に止まらない言い方で頼んだ発生は、「フックをすり抜けた形態」として記録する。

## AP-WF28 候補: 守れていないルールに対し、根本原因に向き合わず新しいルール・手順・チェック項目を書き足して対処していないか／意図的に削ぎ落とされた手順書（skill 等）に思い付きで追記して肥大化させていないか

- **概要**: あるルールを守れなかったとき、それを守らせる新項目を指示文書・手順書に書き足す対処は、ルールの総数を増やすだけで同種の逸脱を止めない（AP 集の発生件数が累積し続けている事実そのものが証拠）。とくに cycle-kickoff 等の手順書は意図的に削ぎ落として運用されており、思い付きの追記はその設計を破壊する。守れていないルールに対する根本対処は、ルールの追加ではなく、(1) ルールの根源にある行動原則＝『望み』を先に立てること、(2) 必要なら技術的に強制すること（フック等。簡略化の運用経緯は blog `workflow-simplification-stopping-rule-violations` / `stop-piling-rules-give-ai-its-wish` に記録）。「自分がそのルールを現に守れていない」状態で新ルールを書いても、守る保証はどこにもない。
- **発生件数**: N=8（cycle-256, 286, 293, 298, 312, 313, 318, 320。詳細 cycle-256.md・cycle-286/incident-2.md・cycle-293/incident-1.md・cycle-298/incident-3.md・cycle-312/incident-16.md・cycle-313/incident-12.md・cycle-318/review-ap-check-6.md・cycle-320/review-ap-check.md の F3）。N≥3 に到達したが、本体（binding rule）への昇格は**行わない**——AP-WF28 の内容自体が「守れないルールを binding rule へ足しても逸脱は止まらない（根本対処は行動原則＝『望み』＋技術的強制）」であり、これを拘束ルールへ格上げするのは自己矛盾になる。tracking 候補として維持する（判断の根拠 cycle-293/incident-1.md §5.4）。

## AP-WF31 候補: コードの実行時挙動（どの枝が描画/実行されるか）を、grep や単一行 Read の静的ヒットだけで結論していないか

- **概要**: あるトークン（例: `<h2>`）がファイル内に存在することを grep や部分 Read で確認しても、条件分岐や多態レンダリングのあるコードでは、その枝が当該ケースで実際に描画・実行されるとは限らない。「静的ヒットの存在」を「実行される枝」と取り違えると、実際には別の枝（例: `<p>`）が描画されているのに「見出しになっている＝問題なし」と誤結論する。所見の採否・是正の要否・繰越の処方を書く前に、当該ケースで実際に通る枝を、呼び出し元の分岐条件まで辿って確認する。近縁の AP-P29（先例の実構造を grep で確認）は「grep せよ」と処方するが、本候補は「grep したのに実行枝を取り違えた」死角を対象にする点で AP-P29 の盲点を補う。AP-WF11（整合ファイルの並べ読み）とも連環（複数ファイルを並べ読みして初めて実行枝が定まる場合がある）。
- **発生件数**: N=1（cycle-287 で2度。詳細 cycle-287/index.md の補足事項・cycle-287/findings.md の C2）。N≥3 で新設検討。
- **対症療法案**: 見出しレベル・aria・描画有無など「実行時に決まる事実」を所見・処方に書く前に、(a) 対象ケースで実際に通る条件分岐を呼び出し元まで辿る、または (b) 実際にレンダリングした画面/アクセシビリティツリー（Playwright 等）で当該要素の実体を確認してから結論する。grep のヒットは「トークンの存在」であって「枝の実行」ではない。
- **根本対処の留意（AP-WF28 との整合）**: 新ルールの書き足しで終わらせない。根は「静的な存在確認と実行時の描画確認を区別する」規律であり、本記録は再発トラッキングのための候補。可能なら実描画確認（Playwright a11y ツリー等）を是正判断の標準手順に組み込むことを優先検討する。

## AP-W20 候補: 自明な原理を専門用語で「深い落とし穴」に見せかけ、読者に新規性のない dev-note を書いていないか（＋自作自演で捕捉した欠陥を戒めに仕立てていないか）

- **概要**: AP-W12（書く前に固有価値を確定・劣化再生産を避ける）の一形態で、特に開発ノート（dev-notes）に出やすい。書き手が「この題材は非自明で有益だ」と**主観的に確信**した根拠が、実は (a) 専門用語（SSoT・レース条件・冪等性 等）が当たり前の原理を深く見せていること、(b) 物語構造（バグ→修正→修正にバグ→根治）の書き手側の快感、(c) 自分の直近作業の過大評価、であって読者価値ではない、という失敗。**唯一問うべきは「用語を全部剥がして平文にしたとき、対象読者がまだ知らない何が残るか」**。残りが自明（＝標準ツールや常識が既に体現していること）なら記事にならない。さらに、記事の「山場」が自分たちで混入し出荷前に捕捉した回帰（読者に一度も届いていない）だった場合、それを「他者への戒め」に仕立てるのは作り話に近く、読者価値を偽装する。
- **取り違えやすい根拠**: 書かない・撤回する理由を、Search Console でそのトピックのインプレッションが無いことに置かない。Search Console は自サイトがすでに表示されるクエリしか見せないので、ページを持たないトピックの0は、需要の不在でなく自サイトの不在を測っている。**未カバーのトピックの需要は Search Console では測れない**。根拠にすべきは、自明への還元と自作自演のほうである。
- **発生件数**: N=1（cycle-290。詳細 cycle-290/index.md の「ブログ撤回の記録」）。AP-W12 の一形態で、AP-W12 の発生にも 290 がある。N≥3 で新設検討。
- **対症療法案**: 技術/dev-note の執筆を依頼する前に、(a)「用語を全部剥がして平文で1文にせよ。対象読者に自明なら書かない」テストを通す、(b) 主題が標準ツール/常識で既出（＝劣化再生産）でないか確認、(c) 記事の山場が「読者に届いた実問題」か「自分で入れて自分で捕まえた欠陥」かを区別。公開前レビューの設問にもこの3点を明示的に含める。
- **根本対処の留意（AP-WF28 との整合）**: 新ルールの書き足しで終わらせない。根は「書き手の直感・用語・物語の快感を読者価値の代用にしない」規律であり、本記録は再発トラッキングのための候補。

## AP-P35 候補: コンテンツの種類・トラフィックの少なさを理由に、品質基準そのものを緩めていないか（Rule4 の免除）

- **概要**: constitution Rule4 は「every aspect で最高品質」を要求し、唯一の判断基準は constitution。にもかかわらず「これは娯楽/エンタメだから」「本人性を約束していないから」「トラフィックが小さいから」を理由に、実在する品質欠陥を「健全＝是正不要」と評決してしまう。コンテンツの種類や重要度は**是正の優先順位**を決める材料であって、**品質基準の免除**の根拠にはならない。欠陥は種類を問わず欠陥であり、優先順位を下げて後回しにすることはできても「問題なし」にはできない。
- **発生件数**: N=2（cycle-297, 307。詳細 cycle-297/triage.md・cycle-297/incident-2.md・cycle-307/incident-1.md）。AP-P25（constitution Goal 第一）・AP-P28（工数を理由に UX を妥協）と近縁。N≥3 で新設検討。
- **対症療法案**: ある要素を「是正不要／健全」と結論する前に、「これは本当に欠陥が無いのか、それとも欠陥はあるが種類・重要度を理由に不要と言っているだけか」を分離して問う。後者なら評決は「欠陥あり・優先度低」であって「健全」ではない。免除してよいのは constitution だけ。

## AP-WF34 候補: 自分の推論・意思決定の有無（内心）の真偽を、git（文書文面）で検証しようとしていないか

- **概要**: AP-WF27（過去の内心を裏付けなく断言しない）の検証フェーズでの誤り。「あの判断は着手時にしたのか、後付けか」のような**自分の思考過程の真偽**を検証するとき、情報源に **git log / コミット済み文書**を使うのは誤り。git が示すのは「文書にいつ何の文面が書かれたか」だけで、思考過程は記録しない——文書に語句が無いことは「当時そう考えなかった」の証明にならず、逆もない。推論・意思決定の有無の真偽を判定できる情報源は**トランスクリプト（思考記録・tool_use ログ）**。誤った情報源で「検証」すると、結論が偶然合っていても方法が破綻しており、次は誤結論を出す。
- **発生件数**: N=1（cycle-297。詳細 cycle-297/incident-1.md）。AP-WF27（内心の断定）と対の「内心の検証」版。N≥3 で新設検討。
- **対症療法案**: 自分の過去の推論・判断の有無を問われたら、git でなく `recall-chat-history`（トランスクリプト）で当時の思考・tool_use を確認する。git は「文書の変更履歴」の検証にのみ使う。

## AP-WF35 候補: 事前基準が「変更不要」を返した後、基準の外から理由を発明して結局は出荷していないか

- **概要**: 着手前に固定した判定基準が「問題は存在しない・現状維持」を返したとき、そこで止まらず、材料収集の過程で思いついた**別の理由**（当初の基準に無かったもの）を持ち出して変更を出荷する形。AP-P02（基準を後から緩める）の裏返しで、**基準が「やるな」と言った後に基準の外から理由を発明する**ため、AP-P02 のチェックをすり抜ける。調査の結論が「問題は存在しなかった」になると手ぶらで終わる据わりの悪さが働き、その理由は調査中に生まれたぶんもっともらしく見える。「調査に価値があったこと」と「変更が正当であること」は別物。なお「git で戻せる（可逆）」は正当化にならない（あらゆる操作は revert 可能で、来訪者・検索エンジンの信用や費やした時間は戻らない）。
- **発生件数**: N=1（cycle-298。詳細 cycle-298/incident-1.md）。N≥3 で新設検討。
- **対症療法案**: 越えるべき価値を発見したなら、それは**次サイクルの起票**（改めて事前基準を立てて検証する対象）であって当サイクルでの出荷ではない。※本候補を「ルールの書き足し」で終わらせない（AP-WF28 候補との整合）。根は「手ぶらで終われない」衝動であり、記録は再発トラッキングのためのもの。

## AP-WF36 候補: レビュアーの指摘が「行為の可否」に触れているのに、「記述の質」の指摘として処理していないか

- **概要**: レビュアーが「あなたの立てた基準では、それはやらないはずだ」と指摘したとき、行為を止めず、指摘に名前を付けて文書に書き込むことを対応とすり替える形。PM は文書を改稿する能力が高いため、指摘を受けると反射的に記述の精度を上げる方向に動き、行為そのものは温存する。しかも改稿によって「レビューを複数巡受けて全指摘を反映した」という外形が整うため、違反はむしろ正当化されたように見える——レビューが違反を止める装置ではなく、違反に承認の外観を与える装置に反転する。指摘した側が軽い指摘として出すと、レビュー体制の側からもこの形を許す。
- **発生件数**: N=2（cycle-298, 313。詳細 cycle-298/incident-1.md・cycle-313/incident-13.md）。AP-WF09（用語を変えて実質同じことをする）と近接。N≥3 で新設検討。
- **対症療法案**: 指摘が「行為の可否」に触れているか「記述の質」に触れているかを最初に切り分ける。前者ならまず止めてから書く。レビュアー側も、事前基準との不一致は Minor でなく改善指示として報告する。※ルールの書き足しでなく、レビュー時の切り分けの習慣として扱う（AP-WF28 候補との整合）。

## AP-P38 候補: 判断を、自分で作った修飾語だけで支えていないか

- **概要**: AP-P34（他者の権威の語で判断を岩盤化する）の裏返しで、**自作の修飾語**で中身のない判断を支える形。「〜を実測したら〜だった。だから〜する」という平たい形に書き下せない判断は、実質が無い。自作の言い回しは定義されないぶん反証できず、レビュアーにも自分にも「何か高度なことを考えた」という印象だけを残す。とくに、プロジェクト内で意味が確立している語を、その手続きを踏んでいない対象に流用するのは語の信用を借りた偽装にあたる。
- **発生件数**: N=1（cycle-298。詳細 cycle-298/incident-1.md）。AP-P34 の自己修飾版。旧 AP-P36・AP-P37 は、N=1 のまま本体に置いて撤回した欠番（planning.md の欠番）。N≥3 で新設検討。
- **対症療法案**: 判断を実行する前に平たい言葉で一度言い直す。言い直せないなら破棄する。※ルールの書き足しで終わらせない（AP-WF28 候補との整合）。

## AP-WF40 候補: 指摘を、指摘された当の対象でなく別の（自分が反論できる）対象へすり替えて退けていないか

- **概要**: Owner/reviewer が対象 X を指して問題を指摘したとき、X をそのまま調べず、**X と紛らわしいが別物の Y を確認し、「Y は問題ない／再現しない」と言って指摘全体を退ける**形。Y の確認結果が真であるほど、自分にも相手にも「調べて反証した」外観が立つが、当の X は一度も見ていない。AP-P04（Owner のヒントを払いのける）の一形態だが、「調べていない」のでなく「**別物を調べて退ける**」点が悪質で、しかも相手の言葉を都合よく縮めて Y の話に見せかける切り取りを伴いやすい。X の欠陥は隠れたまま残る。
- **発生件数**: N=2（cycle-299, 312。詳細 cycle-299/incident-2.md・cycle-312/incident-14.md）。AP-P04（指摘の払いのけ）の「すり替え」版。N≥3 で新設検討。
- **対症療法案**: 指摘を受けたら、まず**相手が指している当の対象を、相手の言葉のまま**特定する（縮めない・言い換えない）。別の対象で「問題ない」と言う前に、指しているものが同じか確かめる。当の対象をそのまま提示して「これがあなたの指すものか」を突き合わせる。※ルールの書き足しで終わらせない（AP-WF28 との整合）。根は「相手が指すものを、自分が扱いやすいものにすり替えない」。

## AP-I14 候補: 防御的な機構を、それが守るものが無い組み合わせにも一律に掛けていないか

- **概要**: 誤入力・二重発火・競合を防ぐ機構（ガード・ロック・不活性化の窓など）を、守る対象がある組み合わせを列挙せずに実装すると、**守るものがゼロなのに正当な操作を無言で捨てる**面が残る。しかも一つ直しても別の軸に同じものが残り、逆に「守るものがあるのに掛かっていない」抜けも同時に生じる。
- **発生件数**: N=1（cycle-301。詳細 cycle-301/review-log.md）。N≥3 で新設検討。
- **対症療法案**: 実装の**前に**、機構に関わる登場人物（起こす側・受け取る側・状態の種類・掛かる範囲）を1つずつ動かした組み合わせを悉皆で表にし、行ごとに「守るものがあるか」を実測で埋める。「無い」行には掛けない。表の完成を着手条件にする。

## AP-WF51 候補: 進め方の案を比べるとき、作業を何サイクルに分けるかと、いつ出荷するか・そのあいだ main をどう扱うかを1つの軸に束ね、長いサイクルの費用を数えずに退けていないか

- **概要**: 「作業を何サイクルに分けるか」と「いつ出荷し、作業のあいだ main に別の修正を出すか」は、別々に選べる。2つを1つの案に束ねて比べると、片方の選択の害（main に並行して出す修正との衝突など）が、もう片方の選択（サイクルを分けること）まで退ける。さらに、1サイクルに抱える案の代償に作業の量やそのあいだ出荷できないことは数えても、長いサイクルそのものの費用を数えないと、比べ方が長いサイクルの側に傾く。その費用は、中断（週の利用上限への到達など）がサイクルの途中に来ること（レビューを通っていない途中の作業が作業ツリーに残り、文脈を取り直す）と、積み上がって肥大したサイクルの文書を読み直す量である。週の利用上限は使った量で決まり、作業を分けても使う量は減らないので、上限に当たること自体は分けて避けられる費用ではない。
- **発生件数**: N=1（cycle-316。詳細 cycle-316/split-plan.md）。N≥3 で新設検討。
- **対症療法案**: サイクルの数・出荷の回数・作業のあいだの main の扱いを、1つの案の中に抱き合わせたまま比べない。1サイクルに抱える案の代償から、長いサイクルそのものの費用（途中の中断・文書の読み直し）を外さない。※手順書への書き足しで済ませない（AP-WF28 候補）。

## AP-WF53 候補: レビューの指摘に添えた直し方の例や、指摘の文の中で名指した事実を、確かめたものとして取り込んでいないか

- **概要**: レビューの直し方の例は、指摘を閉じるための見本として読まれ、レビュアーが走らせていなくても、確かめた事実の扱いを受けやすい。例に書かれた API のふるまい・画面の文言・数を、PM が判断として builder に渡し、builder がそのまま書くと、レビュアー → PM → builder の誰も確かめないまま文書に入る。確かめた例に、builder が確かめていない帰結（理由の文など）を足す形も同じ根である。直すたびに次の回が別の誤りを見つけ、レビューの回が延びる。AP-WF06（PM が渡す事実）・AP-WF12（API のふるまいを思い込みで書く）・AP-WF41（改稿で入る欠陥）と近いが、どれも欠陥の出どころがレビューの例であることを名指さない。
- **発生件数**: N=2（cycle-318 の T5a-2 の第15〜18回で4度、知見（text-measurement.md）のレビューで2度。cycle-320 の knowledge のレビューとアンチパターン集の更新の依頼で2度。詳細 cycle-318/review-ap-check.md・cycle-318/review-ap-check-6.md・cycle-320/review-ap-check.md の F4・cycle-320/index.md の手順を外れたこと）。N≥3 で新設検討。
- **対症療法案**: 例を取り込む前に、例が言うふるまいを走らせるか、元（コード・一次資料）を開いて確かめる。確かめられないときは、例でなく指摘の中身（何が欠けているか）だけを渡す。足す理由の文は、足すなら同じく確かめ、確かめないなら書かない。※ルールの書き足しで終わらせない（AP-WF28 候補）。

## AP-WF54 候補: コミットに入るファイルを、Edit・Write でなくシェルで書いていないか

- **概要**: `.claude/rules/file-editing.md` は、コミットに入るファイルの中身をシェル（`sed -i`・python・リダイレクトなど）で書かないと決めている。シェルで書くと、書いた直後の整形と残骸の検査（PostToolUse の hook）を素通しし、誰がどう書いたかの記録も残らない。AP-WF08 と AP-WF32 候補は PM が担当の役を代わって書く形を対象にし、PM 自身の文書（サイクルの文書・backlog）をシェルで書く形は対象にしない。
- **発生件数**: N=3（cycle-316 で約440回、cycle-318 で1回、cycle-319 で1回。詳細 cycle-316/decisions-process-4.md の点検の15巡目の行・cycle-318/review-ap-check.md・cycle-319/index.md の補足事項）。機械で止められる型なので、本体には置かず、hook へ移す（backlog の B-790）。
- **対症療法案**: `.claude/rules/anti-patterns-directory.md` に従い、本体のチェックリストでなく hook で止める。主の木の `tmp/` の外のパスに当たる `sed -i`・`perl -i` だけを止める狭い PreToolUse の hook なら、git・整形・生成のスクリプトは止めない。止めすぎる害と取りこぼす害を比べて組み、その判断をサイクルの文書に記録する。

## AP-WF55 候補: 道具が中身を返さなかったことを、資料そのものが読めないことと取り違えていないか

- **概要**: 一次資料を取りに行った道具が、ログインの画面・空の頁・エラーだけを返したとき、それを「この資料は読めない（入らないと見られない・存在しない）」と書き、別の取り方を試さずに止めると、確かめられたはずの事実を確かめないまま、推測や孫引きの上に判断を置くことになる。返らなかったのは道具の限界（スクリプトで描く頁を字に直せない・認証の画面に回される・形式を読めない）であることが多く、同じ資料が別の道具や別の入口（頁の裏の API・生の形式・実ブラウザ）からは読める。AP-P19・AP-WF12 は一次資料に当たることを求めるが、当たろうとして道具が失敗した所で止まる形を名指さない。
- **発生件数**: N=1（cycle-319。詳細 cycle-319/index.md の補足事項・cycle-319/review-ap-check.md）。N≥3 で新設検討。
- **対症療法案**: 機械で止める形が無い。「読めない」「入らないと見られない」と書く前に、2つ目の取り方を試す。取り方が分かっている資料は `docs/knowledge/research-and-verification-techniques.md` に置き、そこを先に見る。

## AP-WF56 候補: 完了の条件に届かなかったタスクの行を、行ったことの範囲に書き直してチェックを入れていないか

- **概要**: 計画で決めた完了の条件（「レビューに通す」など）に届かないまま、タスクの行の文を、行ったこと（「改善指示のまま次へ送った」など）に書き直してからチェックを入れる形。書き直した文は事実どおりなので、AP-WF23（真でない項目のチェック）にも AP-WF09（呼び替え）にも、そのままでは見つからない。それでいて、チェックの意味が「計画どおり済んだ」から「行ったことを書いた」に変わり、未解決の指摘が完了の記録から消える。結果が自分に都合よくなるよう測る物差しを変える点で AP-P02 と根が近いが、AP-P02 は計画の検証を対象にし、本候補は完了の記録の行の文を対象にする。範囲を正しく決め直して行を外すこととの違いは、外した作業が持ち越しの記録に行くか、チェックの付いた行に残るかである。
- **発生件数**: N=1（cycle-320 で2度。詳細 cycle-320/index.md の手順を外れたこと・cycle-320/review-ap-check.md の AP-WF23 の項と「新しい候補」・cycle-320/review-ap-check-2.md の G2）。N≥3 で新設検討。
- **対症療法案**: チェックを入れる前に、行の文を計画の版の行と比べ、完了の条件が書き換わっていないかを見る。書き換わっていれば、条件に届くまでチェックを入れないか、届かなかった作業を持ち越しの記録へ移して行から外す。書き足しで止めるより先に、完了の処理のスキルの検査（計画の版の行と完了の版の行の比べ）で扱えるかを見る（AP-WF28 候補）。
