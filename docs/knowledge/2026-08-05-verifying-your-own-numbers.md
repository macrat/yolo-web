# 自分が書いた数を検算する方法（cycle-302 で 11 回失敗して得た知見）

cycle-302 は、**同じ形の失敗を11回繰り返した**。毎回「実測した」と書き、毎回それが実測になっていなかった。決意や注意では止まらなかったので、**何が起きていたか**と、**唯一効いた手順**を残す。

## 11回の内訳——「確かめる動作」は毎回している

| 回  | 「実測した」と書いたものの実体                                                                  |
| --- | ----------------------------------------------------------------------------------------------- |
| 1   | 対策を「宣言」で書いた（「実寸で判定する」は cycle-299 も宣言していた）                         |
| 2   | 別の欠陥を見て、別の条件を校正したと記録した                                                    |
| 3   | 測れば否定される主張を、測らずに「下がりようがない」と書いた                                    |
| 4   | 中間ファイルを測って、出荷ファイルを測らなかった                                                |
| 5   | 「機械の歯止めを入れた」——そのテストはリポジトリに存在しなかった（`.gitignore` に食われていた） |
| 6   | 「緩めたら落ちる」——落ちたのは較正テストではなく別のテストだった                                |
| 7   | 「帯を実測した」——両端しか測らず、間を推論で埋めた                                              |
| 8   | 帯の中央を計算せずに「中央に置いた」と書いた                                                    |
| 9   | 断片の数を数えずに「3つ」と書いた（実測は4つ）                                                  |
| 10  | 一部のファイルだけ直して「訂正した」と記録した                                                  |
| 11  | **他人の報告を、数え方を確かめずに転送した**（別の定義で数えた数だった）                        |

**共通しているのは「確かめなかった」ことではない。** 毎回、何かは確かめている。**足りなかったものが毎回ちがう**ので、「ちゃんと確かめる」という決意では止まらない。

## 唯一効いた手順——公開した規則を、機械的に全数へ当てる

11回目のあと、ブログ記事の書き手が**公開されている定義（有彩色・図・可視・地の各定義）を機械的に全数へ当てて総当たり**したところ、**それまで6巡のレビューが見逃していた誤りがもう1件出た**。

```
本文が主張しているすべての数について、
  その数を出した規則が文書に書かれているか？
  書かれている規則で計算し直すと、同じ数になるか？
```

これで見つかったのは「202は紙色のタイル・墨6」——公開している図の定義を当てると **199 ＋ 9（うち墨の芯6・線の縁のAA 3）** で、3画素をタイル側に寄せたのが 202 の正体だった。**目視でも、指摘への逐次対応でも、6巡のレビューでも出なかった。**

## 具体的な手順

1. **数を出した規則を、必ず文書に書く。** 書けないなら、その数は使わない。
2. **書いた規則で全数を再計算するコードを書き、実行する。** 「〜個」「〜画素」「〜だけ」「〜のうち」と書いた箇所を全部。
3. **範囲（帯・区間）を書くときは、両端の外側1つずつを含めて連続で測る。** 飛ばした点を推論で埋めない。
4. **他人（レビュアー・サブエージェント）の報告を転送する前に、その数がどの規則で数えられたかを確かめる。** 数字が実在しても、規則が違えば別の数である。
5. **一部を直したら、同じ数が他のファイルに無いか横断で grep する。** 「訂正した」は全箇所を直してから書く。

## サブエージェントへ渡すときの注意

**渡すのは数字ではなく数え方である。** cycle-302 の11回目は、レビュアーが「朱系（R−B > 40）＝11画素」と報告し、それをそのまま書き手へ渡した。記事が公開している定義は max−min > 20 で、その規則では **14** だった。**11 も 14 も実在する数**だが、記事のコードを走らせた読者が得るのは 14 のほうである。

## なぜ「気をつける」で止まらないか

このサイクルは、失敗のたびに手当てを書いた。「宣言は対策にならない」「入れた機械が動くことを環境の外で確かめる」「渡す前に測る」——**どれも正しく、どれも次の回を止めなかった**。手当てが**そのときの失敗の形にだけ効く**もので、次はちがう形で出たからである。

機械的な全数検算だけが、**形を問わずに効いた**。
