# 自分が書いた数を検算する方法（cycle-302 で 15 回失敗して得た知見）

cycle-302 は、**同じ形の失敗を15回繰り返した**。毎回「実測した」と書き、毎回それが実測になっていなかった。決意や注意では止まらなかったので、**何が起きていたか**と、**唯一効いた手順**を残す。

## 11回の内訳——「確かめる動作」は毎回している

| 回  | 「実測した」と書いたものの実体                                                                  |
| --- | ----------------------------------------------------------------------------------------------- |
| 1   | 対策を「宣言」で書いた（「実寸で判定する」は cycle-299 も宣言していた）                         |
| 2   | 別の欠陥を見て、別の条件を校正したと記録した                                                    |
| 3   | 測れば否定される主張を、測らずに「下がりようがない」と書いた                                    |
| 4   | 中間ファイルを測って、出荷ファイルを測らなかった                                                |
| 5   | 「機械の歯止めを入れた」——そのテストはリポジトリに存在しなかった（`.gitignore` に食われていた） |
| 6   | 「緩めたら落ちる」——落ちたのは較正テストではなく別のテストだった                                |
| 7   | 「帯を実測した」——両端しか測らず、間を推論で埋めた                                              |
| 8   | 帯の中央を計算せずに「中央に置いた」と書いた                                                    |
| 9   | 断片の数を数えずに「3つ」と書いた（実測は4つ）                                                  |
| 10  | 一部のファイルだけ直して「訂正した」と記録した                                                  |
| 11  | **他人の報告を、数え方を確かめずに転送した**（別の定義で数えた数だった）                        |

**共通しているのは「確かめなかった」ことではない。** 毎回、何かは確かめている。**足りなかったものが毎回ちがう**ので、「ちゃんと確かめる」という決意では止まらない。

## 唯一効いた手順——公開した規則を、機械的に全数へ当てる

11回目のあと、ブログ記事の書き手が**公開されている定義（有彩色・図・可視・地の各定義）を機械的に全数へ当てて総当たり**したところ、**それまで6巡のレビューが見逃していた誤りがもう1件出た**。

```
本文が主張しているすべての数について、
  その数を出した規則が文書に書かれているか？
  書かれている規則で計算し直すと、同じ数になるか？
```

これで見つかったのは「202は紙色のタイル・墨6」——公開している図の定義を当てると **199 ＋ 9（うち墨の芯6・線の縁のAA 3）** で、3画素をタイル側に寄せたのが 202 の正体だった。**目視でも、指摘への逐次対応でも、6巡のレビューでも出なかった。**

## 具体的な手順

1. **数を出した規則を、必ず文書に書く。** 書けないなら、その数は使わない。
2. **書いた規則で全数を再計算するコードを書き、実行する。** 「〜個」「〜画素」「〜だけ」「〜のうち」と書いた箇所を全部。
3. **範囲（帯・区間）を書くときは、両端の外側1つずつを含めて連続で測る。** 飛ばした点を推論で埋めない。
4. **他人（レビュアー・サブエージェント）の報告を転送する前に、その数がどの規則で数えられたかを確かめる。** 数字が実在しても、規則が違えば別の数である。
5. **一部を直したら、同じ数が他のファイルに無いか横断で grep する。** 「訂正した」は全箇所を直してから書く。

## 13回目——**測る相手が、測りたい相手だと確かめる**

11回目のあと、PM 自身が2回やった。どちらも**同じ機序**である。

`next start -p 3001` を起動して e2e を走らせたところ、18通り中18件が FAIL し、別の e2e も「シェアボタンが 22px 高で WCAG のタッチ目標を満たしていない」と出た。**両方とも報告した。** 実際は 18/18 PASS・108×44px で、どちらも欠陥ではなかった。

起きていたのは、`next start` が **EADDRINUSE で起動に失敗していた**（ログに `errno: -98`）のに、`curl` でのヘルスチェックが**そのポートに居座っていた何時間も前の別ビルド**に対して成功していたこと。**「サーバが応答した」を「自分が起動したサーバが応答した」と読んだ。**

```
起動したコマンドが成功したことを確かめたか？
  （プロセスが生きているか・ログにエラーが無いか）
測っている相手が、いま自分がビルドしたものだと確かめたか？
  （応答が返ることは、正しい相手が応答したことを意味しない）
```

**この形は「数を検算する」では止まらない。** 数え方は正しく、計算も正しく、ただ**対象が別物**だった。したがって手順に「対象の同定」を独立の段として置く。

**歯止め**: `.claude/hooks/pre-push-check.sh` の e2e は**空きポートを探してから起動**し、確保できなければ失敗する。ポートを固定してはいけない。

## サブエージェントへ渡すときの注意

**渡すのは数字ではなく数え方である。** cycle-302 の11回目は、レビュアーが「朱系（R−B > 40）＝11画素」と報告し、それをそのまま書き手へ渡した。記事が公開している定義は max−min > 20 で、その規則では **14** だった。**11 も 14 も実在する数**だが、記事のコードを走らせた読者が得るのは 14 のほうである。

## なぜ「気をつける」で止まらないか

このサイクルは、失敗のたびに手当てを書いた。「宣言は対策にならない」「入れた機械が動くことを環境の外で確かめる」「渡す前に測る」——**どれも正しく、どれも次の回を止めなかった**。手当てが**そのときの失敗の形にだけ効く**もので、次はちがう形で出たからである。

機械的な全数検算だけが、**形を問わずに効いた**。

## 15回目——**「まだ現れていない」と「起きない」は別物**

push 後に GitHub Actions の run 一覧を引き、**最新が6日前だった**ことから「デプロイが起動していない」と結論した。実際は**push から run 登録まで11分かかっていた**だけで、run は後から現れて成功した。見ていたのは、その手前のスナップショットである。

**悪いのは誤りそのものより、その上に説明を積み上げたことだった。** 「events API に PushEvent が無い」「PAT に workflow スコープが無い」「Actions の設定 API が 403」——**個々は事実だが、どれも結論を支えていない**。結論を先に決めて、周りの事実を集めた形である。その結果、Owner に不要な対応を求めた。

```
観測が「無い」を示したとき、
  それは「まだ無い」のか「これからも無い」のか？
  待てば現れるものを、待たずに測っていないか？
非同期に登録されるもの（CI の run・キャッシュの反映・インデックス）は、
  「一度見て無かった」を根拠にしてはいけない。
```

**歯止め**: `scripts/wait-for-ci.sh` は本体のワークフローが見つからないうちは**待つ**（即座に赤を返さない）。タイムアウトのメッセージも「まず時間を置いて再実行し、それでも現れない場合にだけ設定を疑う」と書いてある。
