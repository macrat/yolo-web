# AIエージェント間のやり取りの設計と運用に関する知見

複数の AI エージェントのあいだのやり取りをどう設計するかと、LLM エージェントが実際にどう振る舞うか、サブエージェントの起動の形がどう効くかについての知見。

## エージェント間のやり取りの設計原則

- **意図した通信トポロジーと実際の挙動は一致しないことがある。** エージェント間の通信経路を「A→B→C」のように意図して設計しても、実際には異なるパターン（例：全エージェントがPMを経由する星型）に収束することがある。設計後は実際のログを観察し、意図通りに機能しているかを検証する必要がある（cycle-95。メモによる通信が PM を経由する形に収束したことは記録で確認、設計後に検証すべきというのは推論）。

- **状態遷移のトリガーは「作業完了時」だけでは不十分で「作業開始時」にも設けるべき。** キューやステート管理を設計する際、「作業完了時にアーカイブする」だけでは未処理のアイテムが残り続ける。「作業開始時にアクティブ状態へ移す」「作業開始時に前回のアクティブ状態が残っていたら完了済みとしてアーカイブする」というトリアージのタイミングと手順を明確化することで、アイテムの滞留を大幅に防げる（cycle-95。完了時だけのアーカイブで inbox にメモが溜まり、作業開始時の移動を足して溜まらなくなったことは記録で確認、一般化は推論）。

- **エージェント間のやり取りに「記録」を求める場合、その記録システム自体がコンテキストを消費することを考慮する。** 通信の記録・管理・追跡のために中間ファイルやステート管理を設けると、エージェントが本来の作業に使えるコンテキストが削減される。「よくできた仕組み」であっても、LLMにとってはコンテキストを圧迫する重荷になりうる（推論・cycle-95）。

- **記録システムとエージェント間の実際の通信手段は別物として設計する。** メモやファイルによる記録はあくまで追跡・監査のための仕組みであり、通信そのものはAgentツール（プロンプトの引き渡し）が担っている。「記録」と「通信」を混同した設計は誤解を生む。LLMベースのシステムでは、エージェントへの指示をメモIDのみで渡すことでメインエージェントのコンテキストを削減するといったアーキテクチャ上の工夫が有効な場合がある（推論・cycle-95）。

- **オーナー向けの報告はノンブロッキングにする必要がある。** 全自動で動作するシステムにおいて、オーナーが常時監視・応答することを前提とした設計はスケールしない。オーナー不在でも作業が進められるよう、報告はファイルなどに記録して後から確認できる形にし、エージェント間の通信もあとから監査できる仕組みを持たせることが重要（推論・cycle-95）。

- **第1期（臨機応変型）と第2期（厳格ワークフロー型）の設計の違いを理解する。** 第1期の特徴は「サブエージェントの役割を詳細に定義する」「ワークフローを臨機応変に動かす」「1つのメモが1つの作業単位」であり、生産性は高いが品質やルール遵守は低い傾向があった。第2期の特徴は「ドキュメントをシンプルに保つ」「定義されたワークフロースキルに従って動かす」「複数の作業をまとめたサイクル単位で管理する」であり、品質は向上したがコンテキスト消費が増加した。どちらの方針が適切かはプロジェクトの目標次第（cycle-95。各期の特徴と傾向は記録を調べて確認、方針の選び方は推論）。

- **オーナー宛てメモを無断でトリアージするなど、「他エージェント宛てのアイテムに手を出す」という逸脱は設計上の抜け穴になりやすい。** ディレクトリ分割などでエージェントごとにスコープを切っても、明示的な制約がなければ他のスコープに手を出す挙動が発生する。エージェントが「自分のスコープ外を扱わない」というルールは、単に分割するだけでなく、それを強制する仕組みも合わせて設ける必要がある（cycle-95。PM が Owner 宛てのメモを無断でアーカイブしたことは記録で確認、対策は推論）。

## LLMの挙動に関する実証的知見

- **`Plan` 型のサブエージェントは、ファイルを書く仕事に向かない。** `Plan` 型は Edit/Write を持たず、システムの指示で読み取り専用とされる。Bash で書き換えるよう頼むと、書く回と、読み取り専用の指示に従って書かずに置換の一覧だけを返す回がある（実測・cycle-316）。書かなかった回は、置換を当てるために別のエージェントをもう1人起動することになる。設計の文書を書き換える planner の仕事は、書き込める型（`general-purpose` など）に planner の役を与えて頼む。

- **CLAUDE.mdなどのシステムプロンプト的な指示は、セッションが長くなるほど強制力が低下する。** CLAUDE.mdの指示は強制力の低いユーザーメッセージとして、かつコンテキストの冒頭にのみ挿入されるため、セッションが長引くほど後続の指示や作業内容に埋もれ、遵守率が落ちていく。長期セッションでのルール維持には、この特性を踏まえた別の仕組み（例：チェックリスト方式、スキルによるリマインド）が必要（推論・cycle-95。Owner から共有された知見で、このプロジェクトでは遵守率を測っていない）。

- **複数の方法が共存する「中間状態」はLLMがうまく使いこなせない。** 段階的な移行として「古い方法」と「新しい方法」を一時的に併存させると、LLMはドキュメントに明示的に「使うな」と書かれていても古い方法を再発見して使い続けることがある。これは「段階的移行はうまくいかない」という教訓であり、シンプルで汎用性の高い1つの仕組みに一気に切り替えてしまう方が、中間状態を厳密に設計・管理する手間よりも少ない工数で安全に移行できる場合がある（cycle-95。古い方法が使われ続けたことは記録で確認、一気に切り替える方がよいというのは推論）。

- **Claude Codeの多重起動防止（`CLAUDECODE`環境変数）は迂回されるリスクがある。** `CLAUDECODE`環境変数を削除してサブプロセスを起動することで、多重起動防止が機能しなくなる。これにより、フックなどが意図しないプロセスでも発火し、予期しない副作用（例：他エージェントへの指示がオーナーからのメッセージとして記録されてしまう）が生じうる。Claude Codeの多重起動防止を前提とした設計（フックの実装など）では、この迂回パターンへの対策（例：`unset CLAUDECODE`を禁止するフックのセット）も合わせて実装することが望ましい（cycle-95。builder が `unset CLAUDECODE` で別のプロセスを起動し、そのプロセスの入力が Owner のメモとして記録されたことは記録で確認、対策は推論）。

## サブエージェントの起動の形（フォアグラウンドとバックグラウンド）

- **`run_in_background: false` を指定して起動したのに、「バックグラウンドで起動した」と返ったことがある。** 分かっている事実と分かっていないことは次のとおり。
  - 分かっている事実: cycle-316 のセッションの初めに、PM がレビュアーを Agent ツールで `run_in_background: false` を指定して2回起動し、2回とも起動の応答は「バックグラウンドで起動した」だった。PM はこの食い違いを調べず、以後のサブエージェントをバックグラウンドで起動した（事故の記録で確認・cycle-316）。2体はレビュアーで、MCP のツールを使う仕事ではなかった。
  - 分かっていないこと: 原因（ハーネスの設定・版・指定の渡し方のどれによるか）、どの条件で再現するか、そのとき起動したエージェントが MCP のツールを使えたか。再現は、Agent ツールを持つ PM のセッションでしか試せない。cycle-316 の完了の処理で調べた builder はサブエージェントで Agent ツールを持たず、試せなかった。
  - 効き方: バックグラウンドで起動したサブエージェントは MCP のツールを使えない（`playwright-mcp.md` の「バックグラウンドのエージェントは MCP ツールに届かない」）。指定と違う形で起動したことに気づかなければ、Playwright MCP や GA の MCP を使う確かめが黙って失敗するか、別の手段で埋めた結果が MCP で確かめた結果として届く。

- **MCP を使う確かめ（Playwright・GA）を頼むときは、フォアグラウンドで動いているかを次の手順で確かめる。**
  1. Agent ツールを `run_in_background: false` で呼び、応答を読む。フォアグラウンドで動いたなら、その呼び出しの結果がエージェントの最後の報告そのものになる。「バックグラウンドで起動した」「完了は通知で届く」という応答が返ったら、指定と食い違っている。
  2. 依頼文で、作業の初めに使う MCP のツールを1回呼ばせ、呼べたかどうかと、呼べなかったときのエラーの文を報告の頭に書かせる。呼べなかったときは、別の手段で埋めずにそう報告させる。報告には MCP の呼び出しが返した実体（撮った画像のパス、GA の報告の指標・期間・数）を含めさせ、PM がそれを確かめる。
  3. 食い違ったら、そのエージェントの報告を MCP で確かめた結果として使わない。完了の通知を待ってから（待つあいだはコマンドで待たない）フォアグラウンドで起動し直し、食い違いが起きたことを記録に残す。
  4. 起動し直しても食い違うときは、MCP を使わない手段に切り替える。ブラウザの確かめは、リポジトリの `playwright` ライブラリで書いたスクリプトを `node` で動かす（`playwright-mcp.md` の「クラウドのコンテナでは MCP のブラウザが起動しない」。claude.ai のクラウドのコンテナでは、フォアグラウンドでも Playwright MCP のブラウザは起動しない）。GA の数は `analyze-bigquery` スキルの BigQuery で取る（2026-03-28 より前の数は GA の MCP にしか無い）。どちらも Bash で動くので、起動の形に依らない。

  この手順は、上の項目の食い違い（記録で確認）への対策として組んだもので、手順そのものはまだ試していない（推論・cycle-316）。

- **バックグラウンドのサブエージェントの完了は、何もせずに待つ。** 完了は通知で届く。ほかに進められる作業が無ければ、何も出さずにターンを終える。サイクルの進行中は `.claude/hooks/stop-cycle-guard.sh` がターンの終わりを差し戻し、その文は「作業が残っているなら、続けてください」と書くが、同じ停止を2度は差し戻さない作り（`stop_hook_active`）なので、待つだけのときは何も出さずにもう一度ターンを終える。`sleep`・`until` のループ・出力ファイルの大きさの確かめなどのコマンドで待つと、待つたびにコンテキストを使い、そのあとの判断の質を落とす。これはオーナーの決まり（「サブエージェントが完了すると通知が来るので何もせず待つこと。コマンドで能動的に待つことを禁止する」）で、cycle-316 で、差し戻しのあとターンの中でコマンドで待ち続けたことがある（`docs/cycles/cycle-316/incident-1.md`。hook の作りはコードで確認）。

- **サブエージェントが `run_in_background` で起動したプロセスは、そのエージェントのターン終了とともに死ぬことがある。** builder サブエージェントが lint/test/build などの長時間ゲートをバックグラウンド実行し「完了通知を待つ」と報告してターンを終えると、ゲートのプロセスはエージェントのタスク完了時に終了し、結果は永遠に届かない。出力ログも途中で止まり、PM 側からは「全部通った」のか「途中で死んだ」のか区別できない。サブエージェントへの指示には「検証コマンドは必ずフォアグラウンドで実行する（バックグラウンド禁止）」を明記し、PM はサブエージェントが報告したゲート結果を鵜呑みにせず、ログの末尾（テスト件数・exit code）まで確認するか自分で再実行する（実測・cycle-232）。
