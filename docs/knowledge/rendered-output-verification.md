# 描画結果を実測するときの落とし穴

「実測した」と書ける条件は、**測定器が測りたいものを測っている**ことである。
以下はいずれも、測定器が黙って別のものを測り、出力そのものは正常に返ってくる形で、
値だけを見ても誤りに気づけない（測定日 2026-09-14 / Playwright + Chromium / Next.js 16.3.0）。

## `<noscript>` の中身は Playwright のテキストエンジンに一致しない

JS を無効にしたコンテキスト（`javaScriptEnabled: false`）で `<noscript>` の中身は実際に描画されるのに、
`getByText(...)` / `locator("text=...")` / `filter({ hasText: ... })` はいずれも **0 件**を返す。
同じページの `<noscript>` の外にある同じ文字列は1件で一致するので、
セレクタの書き間違いにも見えない。「JS 無効時のメッセージが出ていない」と誤って結論づけることになる。

読めるのは要素経由である。

| 取り方                              | JS 無効            | JS 有効                      |
| ----------------------------------- | ------------------ | ---------------------------- |
| `getByText` / `text=` / `hasText`   | 0 件               | 0 件                         |
| `locator("noscript").textContent()` | 中身のテキスト     | 中身の**マークアップ文字列** |
| `locator("noscript").innerHTML()`   | 中身のマークアップ | 同左                         |
| `locator("noscript").boundingBox()` | 箱が返る           | `null`                       |

JS 有効時に `textContent()` がマークアップ文字列を返すのは、
**スクリプトが有効なときの HTML パーサが `<noscript>` の中身を DOM ではなく生テキストとして扱う**ためである。
JS 無効時だけ中身が本物の要素になる。

## `<noscript>` は JS 有効時にレイアウトへ関与しない

JS 有効時、`<noscript>` は箱を持たない。`boundingBox()` は `null`、`getClientRects().length` は 0、
`checkVisibility()` は `false` で、**直後の要素の座標も動かない**（前後に 10px の要素を置いた実測で、
後続要素の `y` は JS 有効 10 / JS 無効 28）。

ただし **`getComputedStyle(...).display` は `none` ではなく `inline` を返す。**
描画の抑止は計算値の `display` ではなく、その手前で効いている。
**`display: none` を期待する検査を書くと落ちる**ので、箱の有無（`boundingBox()` / `getClientRects()`）で判定する。

この性質のおかげで、`<noscript>` は「JS が無いときだけ見せたいもの」を
**レイアウトシフトを作らずに置ける唯一の場所**になる。JS 有効時は高さ 0 として存在し、
ハイドレーション後に取り除いても周りは動かない。

## `fill()` は対象を画面内へ自動スクロールする

Playwright の `fill()`（MCP の `browser_type` も同様）は操作前に対象を画面内へスクロールする。
画面外の入力欄に打つと、`window.scrollY` は 0 から数百〜千数百 px 動く（実測: 2000px 下の入力欄で 0 → 1418）。
同じページで入力欄が画面内にあるときは 0 → 0 で動かない。

したがって「入力してもスクロール位置が動かないこと」を**画面外の入力欄で測ると、アプリが正しくても動いて見える**。
スクロール挙動を測るときは、対象を先に画面内へ入れてから操作する。

## `next start` の孤児プロセスが古いビルドを配り続ける

`next start` を起動すると、実際に HTTP を待ち受けるプロセスの argv は **`next-server (vX.Y.Z)`** になり、
文字列 `next start` を含まない。含むのはその親（`npm exec next start` と `sh -c next start`）だけである。
結果として:

- **`pkill -f "next start"` は待ち受けプロセスを殺さない。** 親だけが死に、待ち受けプロセスは PID 1 に
  引き取られて動き続ける（実測: 親を殺した後も同じポートが 200 を返す）。
- 残ったプロセスは**起動時のビルド成果物を配り続ける**。その後に `npm run build` をしても反映されず、
  `localhost` を見ている人は自分の変更が入っていない画面を測ることになる。
- さらに `pkill -f "next start"` は**それを実行したシェル自身のコマンドラインにも一致する**ので、
  自分を殺しかねない。

検証の前に `ps -eo pid,args | grep next-server` で待ち受けプロセスの有無を確認し、
残っていれば止めてから起動する。ポートが応答することは「新しいビルドが配られている」ことを意味しない。
