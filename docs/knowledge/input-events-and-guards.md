# 入力イベントと二重発火ガードの知見

cycle-301（B-620: 診断の二重発火で設問が飛び結果が変わる欠陥）で確定した、再利用できる事実。原則として実ブラウザ（本番ビルド・Chromium・touch 有効）での実測に接地しており、**仕様からの演繹にとどまる記述はその都度「演繹・未実測」と明示する**（AP-WF27: 演繹と実測を書き分ける）。

## 1. 実タップの2打目は「別の task」で届く。マウント単位の ref では原理的に止められない

同一の React コミット内で起きる二重発火（同一 tick）と、指の二度打ちは**別の現象**である。

- **同一 tick の二重発火**: 1回のイベント配送の中でハンドラが2回走る。子コンポーネントの `useRef` による同期ロックで確実に止まる。
- **実タップの2打目**: 2つの入力イベントは常に別の task で配送される。1打目で状態が変わりコンポーネントが再マウントされると、2打目は**新しいマウントの fresh な ref** に受け付けられる。**マウント単位のロックは原理的に効かない。**

実測（375px・同一座標を2回タップ）: マウント単位の ref だけを入れた状態では、**0/20/40/60/80/120/175/250/350/500ms のすべての間隔で**設問が1問飛んだ。「短い間隔なら吸収される窓がある」という直感は誤り。

**したがって**: 「二重タップを塞いだ」と言うには、(a) 状態更新そのものを冪等にする（どの経路から何回呼ばれても壊れない不変条件を持たせる）、(b) それでも塞げない「別 task の2打目が次の画面の要素に落ちる」経路に別の手当てをする、の2層が要る。

## 2. jsdom の `act` では実タップの2打目を再現できない

上記1の帰結。jsdom のテストは同一 tick の二重呼び出しは再現できるが、**別 task の2回の実入力は再現できない**。この層の検証は Playwright の実ブラウザ（本番ビルド）でしか担保できない（AP-I07 の具体例）。

**検査が空振りでないことを示す対**を必ず用意する。たとえば「0〜500ms で飛ばないこと」だけを測ると、機能そのものが壊れていても合格する。「**600ms 以上では正常に +2 進むこと**」を同じ表に並べて初めて、その検査が差を検出できると言える。

## 3. `pointer-events: none` はヒットテストを経る入力だけを止める

- **止まるもの**: マウス／タッチのクリック（座標からのヒットテストを経るもの）。
- **止まらないもの**: **キーボード操作**（Tab でフォーカスして Enter）、**プログラム的な `element.click()`**。

実測で、`pointer-events: none` の窓の最中でも Tab によるフォーカス移動・Enter によるリンク遷移・プログラム的 click による「もう一度挑戦する」の作動がいずれも通った。**ページのスクロールも妨げない**——`body` に掛けた状態で実タッチのスワイプを CDP（`Input.dispatchTouchEvent`）から送っても、通常時と同じだけスクロールした（通常時 263px・`body` に掛けた状態 262px）。ヒットテストは `body` を素通りして `html`（＝ビューポートのスクローラ）に落ちる（`document.elementFromPoint` が `HTML` を返す）。

**スクリーンリーダの起動（TalkBack / VoiceOver のダブルタップ）も `element.click()` と同じ合成 click として届くはずだが、これは HTML の activation behavior からの演繹であって未実測**（両者を実行できる環境が無い）。演繹が外れて支援技術の起動がヒットテストを経る入力として届く場合、この窓は支援技術の利用者も止めてしまう。**倒れる向きが「保護を失う」ではなく「摩擦が残る」側であることを確認したうえで採ること。**

**したがって**: 「誤タップから来訪者を守る短い窓」を `pointer-events` で作っても、**キーボードの利用者を締め出さない**（支援技術については上記の留保つき）。逆に言えば、キーボード経路を止めたい場合はこの手段では止まらない。

### 窓を「どこに」掛けるかは、2打目が落ちる先を測って決める

`pointer-events: none` は掛けた要素より外には効かない。落ちる先は構造からは推測できず（同じ経路でも共通フッタのときも、コンポーネント内の関連リンクのときもあった）、**capture phase の click リスナで実測**して初めて確定する。

**ただし「どこに掛けるか」を考える前に、「そもそも掛ける必要があるか」を疑うこと**——次項。

## 3.5. 「2打目が変な所に落ちる」の前に、**1打目の後に来訪者が何を見ているか**を測る

cycle-301 は、画面の入れ替わりでページが縮む経路（結果画面 → intro）で 2打目が共通フッタのナビに落ちて `/about` へ離脱する現象に対し、`body` 全体へ `pointer-events: none` を掛ける窓を入れた。**これは症状に蓋をしただけだった。**

真の原因は、その入れ替わりに**「入れ替わった先の領域へのスクロールとフォーカス移動」が無かった**ことである。ページが縮んでもスクロール位置は縮んだ高さにクランプされるだけなので、視界は縮む前と同じ位置——このケースでは共通フッタ——のままになる。

**測定条件**（下の表の数値に共通）: ビューポート 375×667・本番ビルドの実ブラウザ（Chromium・touch 有効）・15本のクイズ。各本を最後まで解いて結果画面に到達し、**「もう一度挑戦する」ボタンの中心座標を控えてから同じ座標を2回タップ**する（1打目で retry が起き、2打目は入れ替わった先の画面でその座標に来た要素へ落ちる）。スクロール位置は「結果まで解いた直後の位置」をそのまま使い、人為的には動かさない。離脱の判定は2打目のあとにページが遷移したか（URL が変わったか）。

**各行がどの条件の対照かを明示する**（混ぜると独立に再現できない）:

| 観測項目                                                  | 条件A: リビールなし（是正前）                | 条件B: リビールあり（是正後）  |
| --------------------------------------------------------- | -------------------------------------------- | ------------------------------ |
| 主要操作（「はじめる」）が画面内                          | **3/15**（窓の有無に依らない）               | **15/15**                      |
| `document.activeElement`                                  | **15/15 が `<body>`**（窓の有無に依らない）  | 15/15 が入れ替わり先の領域     |
| 2打目による離脱（15本 × 6間隔）／**窓なし**               | **離脱が再現する**（一次測定 61/90・下記注） | —                              |
| 2打目による離脱（15本 × 6間隔）／**窓あり**（当時の本番） | 前巡レビュアーの抜き取りで 1/6               | **0/90**（窓を撤去したうえで） |

上2行は**窓の有無に依らない**（スクロール位置とフォーカスの話なので `pointer-events` は関係しない）。3行目の「窓なし・リビールなし」は**実際には一度も存在しなかった状態の対照**であって、本番や前巡にあったのは4行目の「窓あり・リビールなし」のほうである——**61/90 を「以前の実害率」と読んではいけない。**

**数値そのものは harness 依存なので信用しすぎない。** 同じ条件で別のハーネスが測り直すと **11/90**（700ms は 3/15）しか再現しなかった。タップ座標の決め方・スクロール位置の作り方・2打目までの実時間のわずかな違いで着弾先が変わるためである。

> **【重要な訂正・2026-07-31】** ここに当初「**恒久的に受け取ってよいのは方向だけ**——対照（リビールなし）では離脱が再現し、**是正後（リビールあり）は 0/90**」と書いた。**この「0/90」は後の実測で反証された。**
>
> **リビールを入れても、窓が無ければ離脱は再現する。** 別のレビュアーが retry ボタンの**画面内の位置を変えて**測ると、リビールありでも **12/30 が離脱**した。着弾先は intro の関連リンクで、これは 15/15 本のクイズ定義に存在し、リビールが intro を画面先頭へ移す以上**必ず fold 内に来る**。
>
> **脆弱帯の上端はハーネスによって割れており、一方を正としてはいけない**——独立した2つの測定で **y≈145–190**（190 で 3/3 離脱・205 で消失）と **y≈145–215** に分かれ、割れる原因は特定できていない。**測り直すときは最低でも y=120〜215 を掃くこと。** 下端も 140 で切ってはいけない（**y≈120–140 では2打目が「はじめる」を叩き、意図しないプレイ開始が起きる**）。初報は 140–185 で、それだけを測ると実在する帯を取りこぼす——この行自身がその履歴を持っている。
>
> **なぜ 0/90 が出たか**: その測定は「結果を読み進めずに retry を押す」1つのスクロール位置に固定されていた。振られていた次元は間隔と本数で、**1打目のタップ座標は固定されていた**。だから「守るものが無い」の証明にならない。
>
> **この節から持ち帰るべきなのは、下の §3.5 のチェックリスト（1打目の後に来訪者が何を見ているかを測れ）であって、「リビールを入れれば窓が要らなくなる」ではない。** cycle-301 では実際に、リビール（根本是正）と**領域限定の窓**（上乗せ）の**両方**が必要だった。

つまり来訪者から見て「押したのに何も起きていない」状態で、しかもその時点で視界にある唯一の操作要素がフッタのナビだった。**2打目は事故ではなく、無反応に見えたから押した合理的な反応**である。だから時間の窓では原理的に防ぎきれない——条件A（リビールなし・窓なし）では **700ms でも離脱が残った**（一次測定 10/15、別ハーネスの測り直しでは 3/15）。600ms の窓の外側なので窓を広げるしかなく、広げれば今度は意図的なタップまで弾く。

**チェックリスト**: 画面を入れ替えた直後に 2打目が悪さをする現象を見たら、窓を検討する前に次を実測する。

1. 入れ替わり直後の `scrollY` / `document.documentElement.scrollHeight`（ページが縮んだか）
2. 入れ替わった先の**主要操作要素の `getBoundingClientRect().top`** と画面内かどうか
3. `document.activeElement`（`<body>` に落ちていないか）

いずれかが壊れているなら、それが原因である。まずそれを直す。

**ただし「直せば窓が不要になる」と結論を急がないこと。** cycle-301 では、根本是正（スクロール＋フォーカス）を入れた時点で「守るものが無くなった」と判断して窓を撤去したが、**それは1つのスクロール位置でしか測っていなかった**。位置を変えると離脱は再現し、結局**根本是正と領域限定の窓の両方**が必要だった。

正しい順序は「**根本を直す → そのうえで、2打目が落ちうる先をスクロール位置を振って測り直す → まだ操作要素に当たるなら窓を上乗せする**」。撤去できたのは `body` 全体に掛ける粗い機構であって、**領域限定の窓ではない**（cycle-301 の実際: `body` 機構は撤去・intro 領域と結果領域の窓は保持）。

### スクロールの見え方（smooth / 即時）は距離と目的で決める

同じ「領域へスクロール + フォーカス」でも、**数画面ぶん飛ぶ移動を `behavior: "smooth"` にしてはいけない**。移動が続く時間は **約 800ms** だった。

**測り方**: `requestAnimationFrame` で毎フレーム `scrollY` を記録し、**起点は click**（`scrollIntoView` を呼んだハンドラの入口ではなく、来訪者が押した瞬間）として、値が動き始めてから静止するまでを取る。2,922px＝ビューポート 4.4 画面ぶんの移動で、click から **90ms〜890ms**（別ハーネスの測り直しでは 23ms〜820ms）。**どちらも「動いている時間 約 800ms」で一致する**——開始の遅れ（rAF の初回コールバックまで）はハーネスで揺れるので、受け取るのは差のほう。

この約 800ms は座標が毎フレーム変わる不安定な時間で、2打目はそこへ落ちる——即時なら 15本×8間隔で 0/120 だった離脱が、smooth では 3本×4間隔の探索のうち 90ms/200ms の 3 試行で再発した。

- **下に現れた続きへ注意を誘導する短い移動** → smooth（`prefers-reduced-motion: reduce` で即時に落とす）
- **別の画面へ置き換わる長い移動**（戻る・やり直す） → 即時。ページ遷移と同じ扱いにする

## 4. 時間ベースのガードは3つの軸で適用対象を絞る

二重タップを防ぐための時間ガードを、一律に掛けると**正当な入力を無言で捨てる**。cycle-301 では絞り込みの軸が**3つ**あり、1つずつ別々の巡で指摘された。すべて同じ問いの言い換えである——「**この組み合わせに、守るものはあるか**」。

### 軸1: どの遷移が基準時刻を更新するか（＝結果の差で判定する）

経路（どの action か）ではなく**遷移の前後の結果の差**（表示中の画面が実際に変わったか）で判定する。画面が変わらない遷移では2打目が落ちる先も変わらないので守るものが無い。経路で判定すると、経路が増えるたびに手当てが要り、守るものが無い経路にも摩擦が乗る。

実測: 画面が変わらない「回答→次へ」にも基準時刻を更新していたため、79/170/321/469/559ms の「次へ」が無視され 660ms で初めて通った。

### 軸2: ガードを**受け取る**入力の種類

キーボードには「1つのジェスチャが2回届く」経路が存在しない——`Enter` は keydown で click を1回発火し、遷移後にフォーカスが click ハンドラを持たない要素へ移るならオートリピートも何も叩かない。**守るものがゼロなのに摩擦だけが残る。**

実測（キーボードのみ・Tab→Enter）: 一律の 600ms ガードでは 50/150/300/500ms の高速回答が**すべて拒否**された。

### 軸3: ガードを **arm する**（＝その遷移を起こした）入力の種類

軸2 を直しても残る。**非ポインタが起こした遷移の後には「1つのジェスチャの2打目」が原理的に存在しない**——次に届くポインタ入力は必ず別のジェスチャの1打目である。それを弾くのは正当な入力を捨てるだけで、守るものはゼロ。

実測（キーボードで回答 → 指でタップ）: 140/300/550ms が**無言で拒否**され、700ms で受理された（＝拒否はガードによるもので空振りではない）。同じ理屈で `pointer-events` の窓も、非ポインタが起こした入れ替わりでは開けてはならない（キーボードだけで完走した直後の結果領域が 600ms 不活性になっていた）。

**判別の手がかり**: キーボード起因の click は `MouseEvent.detail === 0`／`PointerEvent.pointerType === ""` になる。採用する際は一次資料に当たって確かめること。**恒久のコメントにブラウザのバージョン番号を固定して書かない**——次に読む人がその番号では再現できない事実になる。代わりに取得方法（`click` の capture リスナで `detail` / `pointerType` を記録し、タッチ・マウス・Tab+Enter で比べる）を残す。

## 5. `Date.now()` は単調でない

端末の時刻が後ろへ跳ぶと `now - lastAt` が負になり、`< 閾値` の判定が恒真になって、**跳んだ幅のあいだ UI が完全に無反応**になる。素朴な差分ガードには `if (now < lastAt) return false;` の1行が要る。

`performance.now()` は単調だが、テストで時計を制御する設計（React の scheduler も `performance.now` を見るため干渉する）とは衝突しうる。どちらを採るかは、テスト容易性とのトレードオフで決める。

## 6. 画面が入れ替わる瞬間の誤タップは、座標が動くことが原因ではない

結果画面が現れる瞬間に2打目が別の要素を叩いて離脱する、という現象について、`prefers-reduced-motion: reduce`（＝`scrollIntoView` が即時になり座標が動かない）で対照を取ると、離脱は **4/4** と通常の 3/4 より**むしろ多かった**。

原因は座標の移動ではなく、**同じ座標にある要素が入れ替わること**である。したがってスクロールの挙動を変えても解決しない。

**§3.5 と矛盾しない**: ここで測ったのは「下に現れた結果へ向かう短い移動」で、移動の有無は結果を変えなかった。§3.5 が問題にしているのは「数画面ぶんの長い移動」で、そこでは**動いている時間そのもの（実測 約 800ms・測り方は §3.5）**が不安定な窓になる。効くのは「動くかどうか」ではなく「**入れ替わった先の画面が、来訪者が次に触るまでに静止して視界に入っているか**」である。
