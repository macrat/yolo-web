# 入力イベントと二重発火ガードの知見

cycle-301（B-620: 診断の二重発火で設問が飛び結果が変わる欠陥）で確定した、再利用できる事実。原則として実ブラウザ（本番ビルド・Chromium・touch 有効）での実測に接地しており、**仕様からの演繹にとどまる記述はその都度「演繹・未実測」と明示する**（AP-WF27: 演繹と実測を書き分ける）。

## 1. 実タップの2打目は「別の task」で届く。マウント単位の ref では原理的に止められない

同一の React コミット内で起きる二重発火（同一 tick）と、指の二度打ちは**別の現象**である。

- **同一 tick の二重発火**: 1回のイベント配送の中でハンドラが2回走る。子コンポーネントの `useRef` による同期ロックで確実に止まる。
- **実タップの2打目**: 2つの入力イベントは常に別の task で配送される。1打目で状態が変わりコンポーネントが再マウントされると、2打目は**新しいマウントの fresh な ref** に受け付けられる。**マウント単位のロックは原理的に効かない。**

実測（375px・同一座標を2回タップ）: マウント単位の ref だけを入れた状態では、**0/20/40/60/80/120/175/250/350/500ms のすべての間隔で**設問が1問飛んだ。「短い間隔なら吸収される窓がある」という直感は誤り。

**したがって**: 「二重タップを塞いだ」と言うには、(a) 状態更新そのものを冪等にする（どの経路から何回呼ばれても壊れない不変条件を持たせる）、(b) それでも塞げない「別 task の2打目が次の画面の要素に落ちる」経路に別の手当てをする、の2層が要る。

## 2. jsdom の `act` では実タップの2打目を再現できない

上記1の帰結。jsdom のテストは同一 tick の二重呼び出しは再現できるが、**別 task の2回の実入力は再現できない**。この層の検証は Playwright の実ブラウザ（本番ビルド）でしか担保できない（AP-I07 の具体例）。

**検査が空振りでないことを示す対**を必ず用意する。たとえば「0〜500ms で飛ばないこと」だけを測ると、機能そのものが壊れていても合格する。「**600ms 以上では正常に +2 進むこと**」を同じ表に並べて初めて、その検査が差を検出できると言える。

## 3. `pointer-events: none` はヒットテストを経る入力だけを止める

- **止まるもの**: マウス／タッチのクリック（座標からのヒットテストを経るもの）。
- **止まらないもの**: **キーボード操作**（Tab でフォーカスして Enter）、**プログラム的な `element.click()`**。

実測で、`pointer-events: none` の窓の最中でも Tab によるフォーカス移動・Enter によるリンク遷移・プログラム的 click による「もう一度挑戦する」の作動がいずれも通った。**ページのスクロールも妨げない**——`body` に掛けた状態で実タッチのスワイプを CDP（`Input.dispatchTouchEvent`）から送っても、通常時と同じだけスクロールした（通常時 263px・`body` に掛けた状態 262px）。ヒットテストは `body` を素通りして `html`（＝ビューポートのスクローラ）に落ちる（`document.elementFromPoint` が `HTML` を返す）。

**スクリーンリーダの起動（TalkBack / VoiceOver のダブルタップ）も `element.click()` と同じ合成 click として届くはずだが、これは HTML の activation behavior からの演繹であって未実測**（両者を実行できる環境が無い）。演繹が外れて支援技術の起動がヒットテストを経る入力として届く場合、この窓は支援技術の利用者も止めてしまう。**倒れる向きが「保護を失う」ではなく「摩擦が残る」側であることを確認したうえで採ること。**

**したがって**: 「誤タップから来訪者を守る短い窓」を `pointer-events` で作っても、**キーボードの利用者を締め出さない**（支援技術については上記の留保つき）。逆に言えば、キーボード経路を止めたい場合はこの手段では止まらない。

### 窓を「どこに」掛けるかは、2打目が落ちる先を測って決める

`pointer-events: none` は掛けた要素より外には効かない。cycle-301 では、画面の入れ替わりで**ページが縮む**経路（結果画面 → intro）で、2打目が**その機能のコンポーネントの外**——サイト共通フッタのナビ——に落ちて `/about` へ離脱した。領域単位の窓では届かず、`body` に掛ける必要があった。落ちる先はクイズによって変わり（共通フッタのときも、intro 内の関連リンクのときもあった）、**構造から推測せず capture phase の click リスナで実測**して初めて確定した。

## 4. 時間ベースのガードは3つの軸で適用対象を絞る

二重タップを防ぐための時間ガードを、一律に掛けると**正当な入力を無言で捨てる**。cycle-301 では絞り込みの軸が**3つ**あり、1つずつ別々の巡で指摘された。すべて同じ問いの言い換えである——「**この組み合わせに、守るものはあるか**」。

### 軸1: どの遷移が基準時刻を更新するか（＝結果の差で判定する）

経路（どの action か）ではなく**遷移の前後の結果の差**（表示中の画面が実際に変わったか）で判定する。画面が変わらない遷移では2打目が落ちる先も変わらないので守るものが無い。経路で判定すると、経路が増えるたびに手当てが要り、守るものが無い経路にも摩擦が乗る。

実測: 画面が変わらない「回答→次へ」にも基準時刻を更新していたため、79/170/321/469/559ms の「次へ」が無視され 660ms で初めて通った。

### 軸2: ガードを**受け取る**入力の種類

キーボードには「1つのジェスチャが2回届く」経路が存在しない——`Enter` は keydown で click を1回発火し、遷移後にフォーカスが click ハンドラを持たない要素へ移るならオートリピートも何も叩かない。**守るものがゼロなのに摩擦だけが残る。**

実測（キーボードのみ・Tab→Enter）: 一律の 600ms ガードでは 50/150/300/500ms の高速回答が**すべて拒否**された。

### 軸3: ガードを **arm する**（＝その遷移を起こした）入力の種類

軸2 を直しても残る。**非ポインタが起こした遷移の後には「1つのジェスチャの2打目」が原理的に存在しない**——次に届くポインタ入力は必ず別のジェスチャの1打目である。それを弾くのは正当な入力を捨てるだけで、守るものはゼロ。

実測（キーボードで回答 → 指でタップ）: 140/300/550ms が**無言で拒否**され、700ms で受理された（＝拒否はガードによるもので空振りではない）。同じ理屈で `pointer-events` の窓も、非ポインタが起こした入れ替わりでは開けてはならない（キーボードだけで完走した直後の結果領域が 600ms 不活性になっていた）。

**判別の手がかり**: キーボード起因の click は `MouseEvent.detail === 0`／`PointerEvent.pointerType === ""` になる。採用する際は一次資料に当たって確かめること。**恒久のコメントにブラウザのバージョン番号を固定して書かない**——次に読む人がその番号では再現できない事実になる。代わりに取得方法（`click` の capture リスナで `detail` / `pointerType` を記録し、タッチ・マウス・Tab+Enter で比べる）を残す。

## 5. `Date.now()` は単調でない

端末の時刻が後ろへ跳ぶと `now - lastAt` が負になり、`< 閾値` の判定が恒真になって、**跳んだ幅のあいだ UI が完全に無反応**になる。素朴な差分ガードには `if (now < lastAt) return false;` の1行が要る。

`performance.now()` は単調だが、テストで時計を制御する設計（React の scheduler も `performance.now` を見るため干渉する）とは衝突しうる。どちらを採るかは、テスト容易性とのトレードオフで決める。

## 6. 画面が入れ替わる瞬間の誤タップは、座標が動くことが原因ではない

結果画面が現れる瞬間に2打目が別の要素を叩いて離脱する、という現象について、`prefers-reduced-motion: reduce`（＝`scrollIntoView` が即時になり座標が動かない）で対照を取ると、離脱は **4/4** と通常の 3/4 より**むしろ多かった**。

原因は座標の移動ではなく、**同じ座標にある要素が入れ替わること**である。したがってスクロールの挙動を変えても解決しない。
