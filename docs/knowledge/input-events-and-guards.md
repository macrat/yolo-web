# 入力イベントと二重発火ガードの知見

cycle-301（B-620: 診断の二重発火で設問が飛び結果が変わる欠陥）で確定した、再利用できる事実。すべて実ブラウザ（本番ビルド・Chromium・touch 有効）での実測に接地している。

## 1. 実タップの2打目は「別の task」で届く。マウント単位の ref では原理的に止められない

同一の React コミット内で起きる二重発火（同一 tick）と、指の二度打ちは**別の現象**である。

- **同一 tick の二重発火**: 1回のイベント配送の中でハンドラが2回走る。子コンポーネントの `useRef` による同期ロックで確実に止まる。
- **実タップの2打目**: 2つの入力イベントは常に別の task で配送される。1打目で状態が変わりコンポーネントが再マウントされると、2打目は**新しいマウントの fresh な ref** に受け付けられる。**マウント単位のロックは原理的に効かない。**

実測（375px・同一座標を2回タップ）: マウント単位の ref だけを入れた状態では、**0/20/40/60/80/120/175/250/350/500ms のすべての間隔で**設問が1問飛んだ。「短い間隔なら吸収される窓がある」という直感は誤り。

**したがって**: 「二重タップを塞いだ」と言うには、(a) 状態更新そのものを冪等にする（どの経路から何回呼ばれても壊れない不変条件を持たせる）、(b) それでも塞げない「別 task の2打目が次の画面の要素に落ちる」経路に別の手当てをする、の2層が要る。

## 2. jsdom の `act` では実タップの2打目を再現できない

上記1の帰結。jsdom のテストは同一 tick の二重呼び出しは再現できるが、**別 task の2回の実入力は再現できない**。この層の検証は Playwright の実ブラウザ（本番ビルド）でしか担保できない（AP-I07 の具体例）。

**検査が空振りでないことを示す対**を必ず用意する。たとえば「0〜500ms で飛ばないこと」だけを測ると、機能そのものが壊れていても合格する。「**600ms 以上では正常に +2 進むこと**」を同じ表に並べて初めて、その検査が差を検出できると言える。

## 3. `pointer-events: none` はヒットテストを経る入力だけを止める

- **止まるもの**: マウス／タッチのクリック（座標からのヒットテストを経るもの）。
- **止まらないもの**: **キーボード操作**（Tab でフォーカスして Enter）、**プログラム的な `element.click()`**（スクリーンリーダの起動＝TalkBack/VoiceOver のダブルタップはこれに相当する）。

実測で、`pointer-events: none` の窓の最中でも Tab によるフォーカス移動・Enter によるリンク遷移・プログラム的 click による「もう一度挑戦する」の作動がいずれも通った。

**したがって**: 「誤タップから来訪者を守る短い窓」を `pointer-events` で作っても、**キーボードと支援技術の利用者を締め出さない**。逆に言えば、キーボード経路を止めたい場合はこの手段では止まらない。

## 4. 時間ベースのガードは「入力の種類」で適用対象を絞る

二重タップを防ぐための時間ガードを、入力の種類を見ずに一律に掛けると、**キーボード／支援技術の利用者の正当な入力を無言で捨てる**。

キーボードには「1つのジェスチャが2回届く」経路が存在しない——`Enter` は keydown で click を1回発火し、遷移後にフォーカスが click ハンドラを持たない要素へ移るならオートリピートも何も叩かない。**守るものがゼロなのに摩擦だけが残る。**

実測（キーボードのみ・Tab→Enter）: 一律の 600ms ガードでは 50/150/300/500ms の高速回答が**すべて拒否**された。

**判別の手がかり**: キーボード起因の click は `MouseEvent.detail === 0`／`PointerEvent.pointerType === ""` になる。採用する際は一次資料に当たって確かめること。

**あわせて**: ガードの「基準時刻を更新する条件」も、経路ではなく**結果の差**（表示中の画面が実際に変わったか）で判定する。経路で判定すると、経路が増えるたびに手当てが要り、守るものが無い経路にも摩擦が乗る。

## 5. `Date.now()` は単調でない

端末の時刻が後ろへ跳ぶと `now - lastAt` が負になり、`< 閾値` の判定が恒真になって、**跳んだ幅のあいだ UI が完全に無反応**になる。素朴な差分ガードには `if (now < lastAt) return false;` の1行が要る。

`performance.now()` は単調だが、テストで時計を制御する設計（React の scheduler も `performance.now` を見るため干渉する）とは衝突しうる。どちらを採るかは、テスト容易性とのトレードオフで決める。

## 6. 「原因は座標が動くことではない」——推測で対処を選ばない

結果画面が現れる瞬間に2打目が別の要素を叩いて離脱する、という欠陥に対し、「スクロールで座標が動くのが原因だから、スクロールを即時にすれば直る」という筋は**実測で否定された**。`prefers-reduced-motion: reduce`（＝スクロール即時）の対照では離脱が **4/4** と、通常の 3/4 より**むしろ悪化**した。

原因は座標の移動ではなく**画面の中身が入れ替わること**だった。対処の選択は、機序の推測ではなく対照実験で決める。

## 7. 「一律に掛ける」は同じ形で何度も再発する

cycle-301 では、時間ガードの適用範囲について**2巡続けて同型の指摘**が出た。

1. 3巡目: 経路の軸——守るものが無い経路（knowledge の「回答→次へ」）にも掛かっていた。
2. 4巡目: 入力の種類の軸——守るものが無い入力（キーボード）にも掛かっていた。

1つ目を直したとき、**同じ原則を別の軸に適用していなかった**。防御的な機構を入れるときは「この機構が守るものが**無い**のに掛かってしまう組み合わせ」を、軸を変えて列挙すること。
