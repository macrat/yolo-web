# フロントエンド実装の技術ノート

DESIGN.md（デザインの原則の正典）が「何を・なぜ」を定め、本ノートは「どう実装するか」の手段を補う。原則と手段を分けることで DESIGN.md を規範文書として安定させる（DESIGN.md §11）。

## stretched-link で行全体をクリック可能にする

DESIGN.md §4「クリック標的＝視覚単位の全体」の実装手段。一覧の行/カードで、品名テキストだけでなく行全体をクリック/タップ標的にしたいときに使う。

### 原則と方式の対応

一覧のクリック領域には3つのイディオムがありうる:

1. **タイトルのみリンク**（品名テキストだけが `<a>`）: 標的が狭く「押せない」摩擦を生む＝DESIGN.md §4 違反。使わない。
2. **行全体を単一 `<a>` で包む**（`display:block` のリンクが行の全内容を子に持つ）: 標的は行全体で §4 準拠。ただしアクセシブル名が「品名＋よみ＋説明＋値札」の連結になり、スクリーンリーダーが冗長に読み上げる。**行内に副リンクを持てない**（`<a>` の入れ子は不正 HTML）・見出し要素を内包すると意味構造を崩す。副リンク・見出しの無い単純な行に限り許容。
3. **stretched-link**（主リンクの擬似要素でクリック標的だけを拡張）: 標的は行全体・アクセシブル名は主リンク名のみ・副リンク（タグ等）を独立に押せる。**推奨**。

### stretched-link の実装

主リンク（品名）は `<a>` のまま残し、その擬似要素 `::after` を絶対配置で行全体に広げる:

```css
.row {
  position: relative; /* ::after の位置基準 */
}
.name::after {
  content: "";
  position: absolute;
  inset: 0; /* 行（.row）全体をクリック標的に */
}
```

- **DOM は不変**なのでアクセシブル名は品名のみに保たれる（SR 良好・既存テストも保全）。
- **hover は要素自身の `:hover` を使う**（`.name:hover`）。`::after` が行を覆うため行のどこをホバーしても発火する。`.row:hover .name` のような子孫セレクタは不要。
- **focus**: キーボード focus は主リンクに出る（WCAG 準拠。フォーカス可能要素にリングが出ていれば足りる）。`:focus-within` で行全体を光らせる必要はない（副リンク focus でも行が光る副作用を避ける）。

### 行内に副リンク（タグ等）がある場合

副リンクを `::after`（z-index auto=0）より前面に出す:

```css
.tagRow {
  position: relative;
  z-index: 1;
}
```

- `.row` に `z-index` を付けない（スタッキングコンテキストを作らないので、`z-index:1` の副リンクが `::after` の前面に立つ）。
- 副リンクをホバーすると、最前面は副リンクなので主リンクの `::after` にヒットせず、`.name:hover` は発火しない＝**副リンク上では主リンクの hover 表現が出ない**（意図どおり）。
- **副リンク行のデッドゾーンと是正**: block 級の副リンク行（例: タグの `<ul>`）を全幅で前面に上げると、副リンクの右側の空き帯も `::after` の前面に乗り、そこをクリックしても主リンクに遷移しない「デッドゾーン」ができる。**是正は副リンク行に `width: fit-content; max-width: 100%` を当てる**——幅を内容ぶんに絞ることで右側の空きが主リンクの `::after` に戻り（＝主リンクへ遷移する）、`fit-content = min(max-content, available)` の性質で狭幅では利用幅で頭打ちになるため flex-wrap の折り返しは保たれ overflow しない。cycle-281 で BlogList のタグ帯に適用し、デスクトップでデッドゾーン解消・モバイル（375）でタグ12個強制でも3行折り返し＋overflow ゼロを実機で検証した（設計時に懸念した「fit-content が折り返しを壊す」は実測で否定された）。

### 副作用（許容の判断）

- `::after` が覆う領域のテキストは選択・コピーできなくなる。一覧のナビ行（遷移が目的・全文は遷移先にある）では許容。読ませる散文が主目的の面には使わない。

### 適用実績

- cycle-281: `Shinagaki`（RelatedArticles 内包）・`BlogList`（TagList の独立クリックを z-index で両立）をイディオム1→3へ是正。フェーズR移行で生じたクリック領域劣化の是正。
- イディオム2の実例: `DictionaryEntryList`・`PlayRecommendBlock`（標的は行全体で §4 準拠だが、アクセシブル名の浄化は将来 stretched-link 化の候補＝B-573 系）。

## 溢れる表を横スクロール面に載せる

記事本文の表は `width: 100%` で読む幅に収まろうとする。表の自動レイアウトは各列を
「内容の最小幅」まで潰してでも収めるので、**日本語はどこでも改行できる＝最小幅が1文字**
になり、狭い列では「ラ／イ／ト／の／タ／ブ／地」と1文字ずつ縦に折れる。cycle-302 の実測では
360px で1行の高さが 217px、4行の表が縦 725px を占めていた
（`rss-feed-and-pagination` の3番目の表）。

### 効いた組み合わせ

1. **セルに最小幅の床**（`th, td { min-width: 6.8em }`）。これで列は潰れなくなるが、
   合計幅が読む列を超える。
2. **超えた分の逃がし先**（ラッパーに `overflow-x: auto`）。逃がし先が無いと、はみ出しは
   `html, body { overflow-x: clip }` に食われて**到達できない**（読者が読めない領域になる）。
3. **溢れていることの告知**。横スクロールは、切れていること自体が見えないと「表を最後まで
   読んだ」と誤解させる。

### 落とし穴

- **床の要否は画面幅では決まらない。** 「読む幅が `--measure` で頭打ちだから広い画面には床が
  要らない」は誤り。要否は「列の min-content の合計が読む幅を超えるか」で決まり、これは幅が
  固定されても解消しない。幅でブレークポイントを切ると、境界の1px 差で症状が出たり消えたりする。
- **`min-width` は box-sizing の影響を受ける。** `border-box` 環境では左右パディングと罫を
  引いた残りが内容領域なので、`6.8em` は「6.8字ぶん」ではない。さらに
  `border-collapse: collapse` では隣り合うセルが罫を分け合うため、セルが持つ罫は左右 0.5px ずつ
  （合わせて 1px）で、罫を「1px×2」で引くと 1px ずれる。15px 字・8px パディングなら
  102 − 1 − 16 = 85px ＝ 5.67字（実測 `clientWidth` 101px）。
- **床の値で「あと数px だけ溢れる表」は消せない。** 値を下げると別の表が境界に乗ってくる
  （6.8em で4個 → 6.6em で8個）。溢れ量ではなく「文字が隠れたか」で判定する。表の右端で切れるのは
  最後のセルの右パディングと右罫なので、その合計までは文字に届かない。
- **告知は表の「前」に置く。** 後ろに置くと背の高い表（実測で最大 2337px）では読み終えるまで
  目に入らない。
- **スクロール面をフォーカス可能にするのは、溢れた表だけ。** 全部に `tabindex="0"` を焼き込むと、
  矢印キーで何も起きないタブ停止が増える（表が最も多い記事で11個）。フォーカスできる領域には
  役割と名前が要るので `role="region"` + `aria-label` を伴わせる。溢れているかは実行時にしか
  分からないので、静的 HTML ではなくクライアント側で `ResizeObserver` を使って付け外しする。
- 影・グラデーションでのフェード表現は §8 の禁止リストに当たる。告知は**言葉**で行う。

### 床は「列ごと」に、その列が要る幅で頭打ちにする

床を全列一律（`th, td { min-width: 6.8em }`）にすると、**セルが1〜2文字しかない表**
——カレンダーのような——まで幅が数倍に膨らみ、折り返しゼロで収まっていたものが
横スクロールに落ちる。

そこで床を列ごとに `min(6.8em, その列が折り返さずに要る幅)` にする。ビルド時に
markdown のトークンから列ごとの幅を見積もり、`--table-col-1` … `--table-col-7` として
包みに載せ、CSS がパディングと罫を足して 6.8em と比べる:

```css
.prose th:nth-child(1),
.prose td:nth-child(1) {
  min-width: min(6.8em, var(--table-col-1, 6.8em) + var(--table-cell-extra));
}
/* …列数ぶん繰り返す */
```

**要点は「列の自然幅で頭打ちにする」こと。** 床の合計がその表の自然幅とほぼ同じところに
収まるので、「表全体が収まるか」を判定する必要が無くなり、`100cqw`・`clamp()`・
`container-type` への依存もまとめて消える。

ただし**「原理的に超えない」わけではない**。見積もりには丸めと列ごとの遊びが乗るので、
床の合計が自然幅を上回りうる。実測（列ごとの床を合計して、床を外した max-content と
比べた値）では 280〜720px で3個 / 1280px で1個が超過し、最大 +42px。境界に近い表も
実在する（「読む列 − 自然幅」で見て、375px の伝統色辞典は4px、360px の
`sns-optimization-guide` は3px）。

見積もりが数px 外れても、効くのは1列の床が数px ずれるところまでで、表全体の見え方が
反転することはない。**判定を持っていた頃**（表ごとに床を付けるか外すかを決めていた頃）は、
見積もりが数px 外れるだけで表全体の床が付いたり外れたりし、280px のカレンダーは
5px 足りないだけで 237px → 714px（溢れ483px）に膨らんでいた。

見積もりは「多めに倒す」のではなく実描画に寄せる。装飾記号（`**`・`[]()`）を落とし、
字種ごとに測った送り幅で数え、インラインコードは等幅＋座布団（実測 8.925px）で別に数え、
見出し行は `font-weight: 600` のぶんラテンだけ広げる（小文字1.097倍）。
**字種平均のずれを吸収する遊びを列ごとに 0.2em 足す**——遊びが無いと `Q04`（実描画
28.36px）に対し床が 26.8px にしかならず `Q0` と `4` に割れた（`Q` の実幅 11.67px を
大文字平均 10.2px で数えるため）。床は 6.8em で頭打ちなので、遊びが効くのは
自然幅が 6.8em に届かない短い列だけ。

**見積もりは px ではなく em で出す。** CSS 側のキャップが `6.8em` なので、px で出すと
字が大きくなったときにキャップだけが伸び、床が文字に対して小さくなる。
`html { font-size: 20px }` を注入して測ると、px 版は 360px・全203表で 2文字/行以下の
セルが74個（24px 相当で128個）に戻り、em 版は0個（24px 相当で10個）だった。

**ただしこの不具合に読者が到達する経路は、いまのところ無い。** `globals.css` が
`html, body { font-size: 16px }` と px で固定しているので、ブラウザの既定フォントサイズ
設定は効かない（CDP の `Page.setFontSizes` でも `--blink-settings` でも `html` は 16px の
まま）。著者CSSを上書きできる「最小フォントサイズ」設定のほうは `em` も追随しない
（em は指定 font-size で解決される）ので、em でも救えない。em 化は**防御的な措置**で、
来訪者に届く不具合を直したわけではない——コストが無く、`font-size: 16px` の固定が
外れたときに効くから採っている。**`html` の px 固定そのものは別件**（拡大の効かない
サイトになっている）で、起票の対象。

**送り幅は測った環境のもので、実ユーザーの環境とは一致しない。** `--font-gothic` は
Hiragino → Yu Gothic → Noto Sans JP の順に解決されるが、CI コンテナにはどれも入っておらず、
ラテン部分は DejaVu/Liberation（Arial 相当）にフォールバックする。全角＝1em は日本語フォント
共通なので大崩れはしないが、ラテンの送り幅は環境ごとに数%変わる。**列ごとの床は、その差を
1列ぶんの数pxに閉じ込める設計**になっている。

#### 実測（全203表・60記事）

数え方（これが無いと検算できない）:

- **2文字/行以下のセル**: セル単位。インラインコードを含むセルと3字未満のセルは除く。
  行数は Range の矩形を top（6px 以内は同一行）でまとめて数え、文字数 ÷ 行数 ≤ 2 を1つと数える。
  文字数は `textContent` を trim した長さで、途中の空白も1字に数える（ここを除くと数が変わる）。
- **横スクロールになる表**: `scrollWidth - clientWidth > 0px` の `.table-scroll` の数。
- **真の変更前**: 表まわりの新しい指定をすべて外し、パディングを `8px 16px`・
  `overflow-wrap` を `normal`・`vertical-align` を `middle` に戻した状態。
  **「床だけ外した対照」とは別物**で、数が食い違って見えるのは正しい
  （280px の溢れは前者120・後者22）。

2文字/行以下のセル数 ／ 横スクロールになる表の数:

| 幅     | 真の変更前 | 床だけ外す | 一律 6.8em | 列ごと（現行） |
| ------ | ---------- | ---------- | ---------- | -------------- |
| 280px  | 931 / 120  | – / 22     | 0 / 158    | **0 / 158**    |
| 320px  | 778 / 77   | – / 12     | 0 / 157    | **0 / 150**    |
| 360px  | 561 / 48   | – / 9      | 0 / 75     | **0 / 72**     |
| 375px  | 495 / 43   | – / 8      | 0 / 63     | **0 / 60**     |
| 390px  | 462 / 38   | – / 6      | 0 / 59     | **0 / 54**     |
| 720px  | 49 / 1     | – / 0      | 0 / 4      | **0 / 2**      |
| 1280px | 51 / 1     | – / 1      | 0 / 4      | **0 / 2**      |

列ごとの床は、一律の床と同じく1文字折れを全幅で消したうえで、横スクロールになる表を
280px を除く6幅で減らす（280px は 158 で同数）。

**損なった側も残す。** 「真の変更前は詰まりゼロで収まっていたのに、いま溢れる」表
（溢れ > 0px で数えた）は 280px:3個 / 320px:6個 / 360px:2個 / 375px:1個 / 390px:0個 /
720px:1個 / 1280px:1個。多くは横スクロールと引き換えに背が縮んでいる（320px の
`sns-optimization-guide` の1つ目は 559px → 303px）。横にも縦にも悪くなるのは2つで、
`nextjs-directory-architecture` の4つ目（720px で 0 → +43px・610px → 639px、1280px で
0 → +64px・610px → 724px）と `redos-defense-web-worker-terminate` の2つ目
（320px で 0 → +23px・354px → 383px）。前者は7列すべての自然幅が 6.8em を超えるため、
床の合計（714px）が読む列（660px）を上回るのが理由。キャップ 6.8em が列数を見ない
単一定数なので、列数を見たキャップ（読む列 ÷ 列数）にすれば 720px では溢れが減る
（実測済み）が、狭い画面では下限が要り、4.5em に置くと 360px で2文字/行が32個戻る。
下限の置き方は未検証なので解いていない（B-633）。

#### 採らなかった案

- **`max-content` に判定を委ねる**（`table { width: max-content; min-width: 100%;
max-width: calc(var(--table-cols) * 6.8em) }`）。見積もりが要らなくなるので魅力的だが、
  **表が読む列に収まるときの列配分を auto レイアウトに委ねることになり、長い列と短い列が
  同居する表で短い列が潰れる**。全203表の実測で、2文字/行以下のセルが
  **280px で247・360px で219・375px で218・390px で183** 残った（上と同じ数え方）。棄却。
- **文字数の閾値で「短い表」を判定する**: 同じ文字数でも列数と字幅で必要な幅が変わる。
  外したい表の一方は最長2文字、もう一方は最長11文字（`components/`）で、1つの閾値では
  両方を捉えられない。
- **表ごとに床を付ける／外すを判定する**（`clamp()` と `100cqw` で比較）: 見積もりが数px
  外れると表全体の床が反転し、280px で幅が3倍になる崖ができた。列ごとの床に置き換えて廃止。
- **クライアントで測って床を外す**: 外した瞬間にレイアウトシフトが出る。床は既定で敷き、
  外す向きの動的変更はしない。
- **媒体クエリで幅ごとに床を出し分ける**: 表ごとの事情を見られない。719px で切っていたときは、
  719px と 720px で症状が出たり消えたりした。
- **端のフェードでスクロールを示唆する**: DESIGN.md §4「影は原則使わない」に反する。言葉で知らせる。
