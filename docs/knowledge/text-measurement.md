# 日本語テキストをシェルと道具で数える・切る・探すときの注意事項

シェルのコマンドと Claude Code の道具で日本語テキストを数える・切る・探すときの落とし穴。多くは、C ロケールのコマンドが文字ではなくバイトを単位にして動くことから起きるが、UTF-8 でも起きるもの（`String.length` と字の数・語の切れ目・道具の探す範囲・分けた字）がある。どれもエラーを出さずに誤った結果を返す。

## 作業環境のロケール

このリポジトリの作業環境は C ロケール（`LC_ALL` / `LANG` が空で、`locale` は `POSIX` を返し、`locale charmap` は `ANSI_X3.4-1968` を返す）である。UTF-8 のロケールも入っており、`locale -a` は `C`・`C.utf8`・`POSIX` を返す。コマンドの前に `LC_ALL=C.UTF-8` を付けると、そのコマンドだけ UTF-8 で動く（`LC_ALL=C.UTF-8 locale charmap` は `UTF-8` を返す）。

UTF-8 の日本語は1文字3バイトなので、C ロケールのコマンドは日本語の1文字を3つの別々の文字として扱う。

## 数える: awk / wc

`awk` や `wc` で日本語テキストの文字数を測ると、バイト長が返る。

```sh
# 誤り: どれもバイト長を返す
echo "いらっしゃる" | awk '{ print length($0) }'  # → 18 (6文字×3バイト)
echo -n "いらっしゃる" | wc -c                    # → 18 (バイト数)
echo -n "いらっしゃる" | wc -m                    # → 18 (C ロケールでは wc -m もバイト長)
```

`LC_ALL=C.UTF-8` を付けると `wc -m` は 6 を返す。`awk` の実体は mawk で、`LC_ALL=C.UTF-8` を付けても `length()` はバイト長（18）を返す。

UI の実装（JavaScript/TypeScript）が文字数の上限や見積もりに使うのは **`String.length`**（UTF-16 コードユニット数）なので、UI の実装と同じ値を測るときは `node -e` または `npx tsx` で `String.length` を使う。

```sh
node -e "console.log('いらっしゃる'.length)"    # → 6
npx tsx -e "console.log('いらっしゃる'.length)" # → 6
```

`String.length` は字の数と同じとは限らない。かなとふつうの漢字は基本多言語面（BMP）にあり1字が 1 だが、BMP の外の字（常用漢字の「𠮟」U+20B9F、人名の「𠮷」U+20BB7、「𩸽」U+29E3D など）は1字が 2 になる（`'𠮟'.length` → 2）。字の数が要るときは `[...s].length`（`[...'𠮟'].length` → 1）で数える。どちらも全角と半角を同じ 1 と数える（`'ＡＢ'.length` も `'AB'.length` も 2）ので、表示の幅そのものではない。

根拠: 実測（cycle-216・cycle-316）。cycle-216 で keigo-reference の尊敬語の最長値を awk `length()` で測ると「81」になったが、これはバイト長で、`String.length` では「27」（`いらっしゃる・おいでになる・お見えになる・お越しになる`）だった（81 バイト ÷ 3 = 27 文字）。cycle-316 にこの節の各コマンドを現在の作業環境で実行し、記載どおりの値を確かめた。cycle-318 に、BMP の外の字と全角・半角の `String.length` と `[...s].length` を `node -e` で確かめた。

## 切る: cut -c / head -c

`cut -c` と `head -c`（`--bytes`）はバイト単位で切る。日本語の行は字の途中で切れ、長い行を先頭だけ出して読んだつもりでも、思ったより短い範囲しか読めていない。

```sh
echo -n "あいう。" | cut -c1-4   # → 「あ」と壊れた字（4バイト = 1文字と1バイト）と改行
echo -n "あいう。" | head -c 4   # → 「あ」と壊れた字（改行なし）
echo -n "あいう。" | head -c 6   # → あい（6バイト = 2文字）
```

この環境の GNU coreutils 9.4 では、`cut -c` は `-b` の別名で、`LC_ALL=C.UTF-8` を付けてもバイトで切る（`cut -c1-4` の結果は同じ）。GNU coreutils 9.11（2026年4月20日）からは `cut` がマルチバイトの入力を扱い、`-c` が `-b` の別名でなくなった（[coreutils-9.11 の告知](https://lists.gnu.org/archive/html/info-gnu/2026-04/msg00006.html)、2026-10-05 に確かめた）ので、環境の版が上がると UTF-8 のロケールでの `cut -c` の結果が変わる。版は `cut --version` で確かめる。`head -c` は版によらずバイトで数える。

文字の数で切るなら `node -e "console.log('あいう。'.slice(0, 2))"`（→ あい）か `LC_ALL=C.UTF-8 grep -o '^.\{0,2\}'`（→ あい）を使う。長い行を全文読むときは、切らずにファイルへ書き出して、そのファイルを読む。

根拠: 実測（cycle-318、GNU coreutils 9.4）。上の各コマンドを実行し、`od -An -tx1` で `cut -c1-4` の出力が `LC_ALL=C.UTF-8` の有無によらず `e3 81 82 e3 0a`（切った4バイトと改行）であることを確かめた。

## 探す

日本語のテキストを探すときの決まりは次の3つである。偽の「無い」はそのまま不在の主張になるので、「この字・この言い回しはどこにも無い」を確かめるときは特に守る。

- 日本語を含む型で探すときと「無い」を確かめるときは、Claude Code の Grep の道具（ripgrep）か、`LC_ALL=C.UTF-8` を付けた `grep` だけを使う。`git grep`・`sed`・`awk` など、ほかの道具では探さない（C ロケールの `git grep`・`sed` と、ロケールによらず `awk`（mawk）は、日本語の型で一致を見落とす）。
- `-w`・`\b`・`\<`・`\>`（語の切れ目）は、日本語にはどのロケール・どの道具でも使わない。
- `.gitignore` に載るファイルと NUL を含むファイルまで含めて「無い」を言うときは、`LC_ALL=C.UTF-8 grep -ra` を使う。

### C ロケールの grep の外れ方

C ロケールの `grep` は日本語の1文字を3つの文字と見るので、文字を単位にする書き方や選択肢が、型によって違う外れ方をする。どれもエラーは出さない。

```sh
# 角括弧が「その字を作る3バイトのどれか」になり、一致する行を見落とす（偽の「無い」）
echo "あいう。" | grep -c "あ[^。]*。"                # → 0, 終了の値 1
echo "あいう。" | LC_ALL=C.UTF-8 grep -c "あ[^。]*。" # → 1

# . が1バイトに一致し、一致する行を見落とす（偽の「無い」）
echo "あいう。" | grep -c "あ.う"                     # → 0, 終了の値 1
echo "あいう。" | LC_ALL=C.UTF-8 grep -c "あ.う"      # → 1

# -i が ASCII の外の大文字と小文字を同じに見ず、全角の英字を見落とす（偽の「無い」）
echo "Ａ" | grep -ci "ａ"                             # → 0, 終了の値 1
echo "Ａ" | LC_ALL=C.UTF-8 grep -ci "ａ"              # → 1
```

`[^。]` が「い」に一致しないのは、「い」（E3 81 84）と「。」（E3 80 82）が先頭のバイト E3 を共有するためである。ひらがな・カタカナと、句読点・かぎ括弧・中黒・長音符などの和文の記号（U+3000〜U+30FF）は先頭のバイトがどれも E3 なので、この取りこぼしは珍しくない（全角の（・！・？は U+FF00 台で、EF BC で始まる）。外れる書き方はこの3つに限らず、`grep -F` で固定の文字列を探すときも `-i` を付ければ外れるので、C ロケールのまま使ってよい型を覚えて頼るより、決まりどおり `LC_ALL=C.UTF-8` を付ける。

根拠: 実測（cycle-318、GNU grep 3.11）。角括弧に日本語を入れた `grep` が一致する行を見落としたことから、上の各コマンドを実行し、記載どおりの出力と終了の値を確かめた。バイトの値は、`printf %s "あい。、" | od -An -tx1` が `e3 81 82 e3 81 84 e3 80 82 e3 80 81`、`printf %s "（！？・ー、「" | od -An -tx1` が `ef bc 88 ef bc 81 ef bc 9f e3 83 bb e3 83 bc e3 80 81 e3 80 8c` を返した。ほかの道具は、「あいう。」と「東京に行く」の2行を追跡するファイルで、`git grep -c "あ[^。]*。"`・`git grep -P -c "あ.う"`・`sed -n "/あ.う/p"`・`awk "/あ[^。]*。/"`・`LC_ALL=C.UTF-8 awk "/あ.う/"` が何も出さず、`LC_ALL=C.UTF-8 git grep -cw 東京` が 1（`LC_ALL=C.UTF-8 grep -cw 東京` は 0）を返した（git 2.43.0）。

### 語の切れ目

`-w`・`\b`・`\<`・`\>` は、どのロケールでも日本語の語を正しく切り出せない。C ロケールでは日本語の字の各バイトを語の外の字と見て、字の並びの途中を切れ目にする。UTF-8 ではかなと漢字をどれも語の字と見るので、分かち書きしない日本語の文は句読点までが1語になる。

```sh
echo "東京に行く" | grep -cw "東京"                   # → 1（C ロケールでは、たまたま一致する）
echo "東京に行く" | LC_ALL=C.UTF-8 grep -cw "東京"    # → 0, 終了の値 1（偽の「無い」）
echo "東京に行く" | LC_ALL=C.UTF-8 grep -c "\<東京\>" # → 0, 終了の値 1
echo "東京に行く" | rg -cw "東京"                     # → 何も出さず、終了の値 1
```

Grep の道具で `\b東京\b` を探しても、「東京に行く」の行には一致しない。

根拠: 実測（cycle-318、GNU grep 3.11・ripgrep 14.1.0）。上の各コマンドと Grep の道具を実行し、記載どおりの結果を確かめた。`echo "東京に行く。次へ" | LC_ALL=C.UTF-8 grep -ow "東京に行く"` は「東京に行く」を返し、句読点の前までが1語になった。

### 探す範囲と、NUL・壊れた UTF-8 を含むファイル

Grep の道具は、ロケールによらず UTF-8 の文字を単位に一致を取る（C ロケールのままで、`あ[^。]*。` は「あいう。」の行に一致する）。ただし、ディレクトリを探すときは次のファイルを探しきらず、知らせも出さない。

- `.gitignore` に載るファイルは探さない（隠しファイルは探す。Bash の `rg` は隠しファイルも探さない）。
- NUL を含むファイルは、NUL に出会ったところで探すのをやめる。NUL が先頭近くにあるとファイルごと飛び、後ろにあると NUL より後の一致が抜ける。ファイルの一覧（files_with_matches）にそのファイルが出ても、全部を探したとは限らない。

`LC_ALL=C.UTF-8` を付けた `grep -r` はどのファイルも終わりまで探すが、`-a` を付けないと一致行の一部を出さない。NUL を含むファイルでは NUL より後の一致行を、壊れた UTF-8 を含むファイルでは壊れたバイトのある一致行を出さず、代わりにファイルごとに1度、最後に標準エラーへ `grep: <ファイル名>: binary file matches` を出す（終了の値は 0。`2>/dev/null` を付けると抜けたことに気づけない）。`-a` を付けると、どちらのファイルでも一致行をすべて出す。

根拠: 実測（cycle-318、GNU grep 3.11・ripgrep 14.1.0）。試しの git の木で次を確かめた。

- `.gitignore` に載るディレクトリと隠しディレクトリに「あいう。」を置くと、Grep の道具は隠しディレクトリのほうだけを、`rg -c "あいう" .` はどちらも見つけなかった。
- `printf '\0x\nあいう。1\nあいう。2\n'` のファイルは、Grep の道具と `rg -c "あいう" .` の結果に出ず、`LC_ALL=C.UTF-8 grep -n` は一致行を出さずに `binary file matches` だけを出し（`-c` は 2）、`-an` は2行を出した。
- 「あいう。1」〜「あいう。100000」のあとに NUL と「あいう。end」を置いた約1.8MB のファイルは、Grep の道具の files_with_matches には出たが、「あいう。end」は Grep の道具でも `rg -c "あいう。end" .` でも見つからなかった（`rg` の終了の値 1）。`LC_ALL=C.UTF-8 grep -n "あいう"` は 98921 行目まで出して `binary file matches` を出し、`LC_ALL=C.UTF-8 grep -ra "あいう。end" .` は `./huge.txt:あいう。end` を出した。
- 5行のうち2行目と4行目の末尾に `\377` を置いたファイルで、`LC_ALL=C.UTF-8 grep -n` は 1・3・5 行目と標準エラーの1行を出し、`-c` は 5、`-a` は5行を出した。

### 合成済みの字と分けた字

合成済みの「が」（U+304C）と、「か」に結合用の濁点（U+3099）を続けた「が」は、別のバイトの並びなので、ロケールにも道具にもよらず互いに一致しない。

根拠: 実測（cycle-318）。「か」と U+3099 を書いたファイルを、`LC_ALL=C.UTF-8 grep -c "が"`・`grep -c "が"`・`rg -c "が"` で探し、どれも一致しなかった（終了の値 1）。
