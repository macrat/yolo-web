# C ロケールで日本語テキストを扱うときの注意事項

シェルコマンドで日本語テキストを数える・切る・探すときの落とし穴。どれも、コマンドが文字ではなくバイトを単位にして動き、エラーを出さずに誤った結果を返す。知見は cycle-216（数える）と cycle-318（切る・探す）の実測に基づき、数えるほうは cycle-316 に現在の作業環境で測り直して同じ結果を得た。

## 作業環境のロケール

このリポジトリの作業環境は C ロケール（`LC_ALL` / `LANG` が空で、`locale` は `POSIX` を返し、`locale charmap` は `ANSI_X3.4-1968` を返す）である。UTF-8 のロケールも入っており、`locale -a` は `C`・`C.utf8`・`POSIX` を返す。コマンドの前に `LC_ALL=C.UTF-8` を付けると、そのコマンドだけ UTF-8 で動く（`LC_ALL=C.UTF-8 locale charmap` は `UTF-8` を返す）。

UTF-8 の日本語は1文字3バイトなので、C ロケールのコマンドは日本語の1文字を3つの別々の文字として扱う。

## 数える: awk / wc

`awk` や `wc` で日本語テキストの文字数を測ると、バイト長が返る。

```sh
# 誤り: どれもバイト長を返す
echo "いらっしゃる" | awk '{ print length($0) }'  # → 18 (6文字×3バイト)
echo -n "いらっしゃる" | wc -c                    # → 18 (バイト数)
echo -n "いらっしゃる" | wc -m                    # → 18 (C ロケールでは wc -m もバイト長)
```

`LC_ALL=C.UTF-8` を付けると `wc -m` は 6 を返す。`awk` の実体は mawk で、`LC_ALL=C.UTF-8` を付けても `length()` はバイト長（18）を返す。

UI の実装（JavaScript/TypeScript）が参照するのは **`String.length`**（UTF-16 コードユニット数）。日本語は基本多言語面（BMP）内のため、`String.length` = 文字数と一致する（サロゲートペア外）。文字数の計測（特に UI の表示幅・折り返し見積もり）は `node -e` または `npx tsx` で `String.length` を使う。

```sh
node -e "console.log('いらっしゃる'.length)"    # → 6
npx tsx -e "console.log('いらっしゃる'.length)" # → 6
```

## 切る: cut -c / head -c

`cut -c` と `head -c` はバイト単位で切る。日本語の行は字の途中で切れ、長い行を先頭だけ出して読んだつもりでも、思ったより短い範囲しか読めていない。

```sh
echo -n "あいう。" | cut -c1-4   # → 「あ」と壊れた字（4バイト = 1文字と1バイト）
echo -n "あいう。" | head -c 4   # → 同じ
echo -n "あいう。" | head -c 6   # → あい（6バイト = 2文字）
```

GNU coreutils 9.4 の `cut -c` は `LC_ALL=C.UTF-8` を付けてもバイトで切る（`cut -c1-4` の結果は同じ）。`head -c` は名前どおりいつもバイトで数える。

文字の数で切るなら `node -e "console.log('あいう。'.slice(0, 2))"`（→ あい）か `LC_ALL=C.UTF-8 grep -o '^.\{0,2\}'`（→ あい）を使う。長い行を全文読むときは、切らずにファイルへ書き出して、そのファイルを読む。

## 探す: grep の角括弧

`grep` の角括弧（`[^。]`・`[あ]` など）に日本語の字を入れると、C ロケールでは角括弧が「その字を作る3バイトのどれか」という集合になる。結果は、一致するはずの行が一致しない（偽の「無い」）か、一致しないはずの行が一致する（偽の「有る」）かのどちらかで、エラーは出ない。

```sh
# 偽の「無い」: 一致する行があるのに空を返し、終了の値は 1
echo "あいう。" | grep -o "あ[^。]*。"                  # → (空), 終了の値 1
echo "あいう。" | grep -c "あ[^。]*。"                  # → 0, 終了の値 1
echo "あいう。" | LC_ALL=C.UTF-8 grep -o "あ[^。]*。"   # → あいう。, 終了の値 0

# 偽の「有る」: 「い」は「あ」を含まないのに一致する
echo "い" | grep -c "[あ]"                              # → 1, 終了の値 0
echo "い" | LC_ALL=C.UTF-8 grep -c "[あ]"               # → 0, 終了の値 1
```

`[^。]` が「い」に一致しないのは、「い」（E3 81 84）と「。」（E3 80 82）が先頭のバイト E3 を共有するためで、`[^、]` でも同じことが起きる。ひらがな・カタカナ・多くの記号は先頭のバイトが同じなので、この取りこぼしは珍しくない。角括弧を使わない形（`grep -F "あいう"`・`grep -o "あ.*。"` など）は C ロケールでも正しく一致する。

「この字・この言い回しはどこにも無い」を `grep` で確かめるときは、偽の「無い」がそのまま不在の主張になる。日本語を含む型で探すときは `LC_ALL=C.UTF-8` を付けるか、角括弧を使わない形にする。

根拠: 実測（cycle-216・cycle-316・cycle-318）。cycle-216 で keigo-reference の尊敬語の最長値を awk `length()` で測ると「81」になったが、これはバイト長で、`String.length` では「27」（`いらっしゃる・おいでになる・お見えになる・お越しになる`）だった（81 バイト ÷ 3 = 27 文字）。cycle-316 に「数える」の各コマンドを現在の作業環境で実行し、記載どおりの値を確かめた。cycle-318 に、角括弧に日本語を入れた `grep` が一致する行を見落として偽の「無い」を返したことから、「切る」「探す」の各コマンドを GNU grep 3.11・GNU coreutils 9.4 で実行し、記載どおりの結果を確かめた。
