# ブラウザの組みと送りの挙動

ブラウザが要素をどう組み、フォーカスやページ内の移動でページをどう送るかについて、このサイトで確かめた非自明な挙動と対処。各項の末尾の「根拠」に、実測・確認・推論の別と、根拠になったサイクルを書く。測ったブラウザも根拠に書く。このリポジトリの作業の環境にある Playwright の Chromium は 141（141.0.7390.37、Playwright の chromium-1194）で、来訪者の使う安定版の Chrome より古い。この環境で測った挙動は、Chromium 141 の挙動である。

---

## 1. ルートの `scroll-padding-top` は、上端に留めた要素そのものへのフォーカスでもページを送らせる

画面の上端に留める要素（`position: sticky; top: 0`）の下に本文が隠れないよう、ルートに `scroll-padding-top`（留めた要素の高さ + あき）を掛けると、ページ内の移動と本文の要素へのフォーカスは、留めた要素の下に見えるよう送られる。ところが、留めた要素の中の要素（開閉の行など）へフォーカスが移ったときも、その要素は上の余白の中にあるので、ページが送られる。留めた要素は画面の上端にいるままなので、来訪者には読んでいた所が数百 px 動いたとしか見えない。Shift+Tab で留めた要素へ戻ったとき、スクリプトで `focus()` したとき（`preventScroll` を付けないとき）に起きる。マウスで押しただけでは起きない。

留めた要素の中に、中で縦に送る一覧（開いた目次の項目の並び）があるときは、打ち消しの向きがさらに問題になる。一覧の中の項目へフォーカスが移ると、一覧の箱とページの両方が、項目の `scroll-margin-top` と上の余白で見せる位置を計算する。

**対処**:

- 留めた要素の中で、閉じた形のときにフォーカスを受ける要素（開閉の行）には、上の余白を打ち消す負の `scroll-margin-top` を掛ける。量は幾何で決まる。開閉の行の上端は、留めた要素の上の線と内側の余白の分だけ要素の上端から下にあるので、要素が画面の上端に留まっているとき、画面の上端から「線 + 内側の余白」の所にある。そこが上の余白の下端とみなされるよう、「線 + 内側の余白 − 上の余白」にする。
- 中で送る一覧を開いているあいだは、ルートの `scroll-padding-top` と打ち消しの `scroll-margin-top` をどちらも外す。一覧を開くときに留めた要素を画面の上端まで送っておけば、開いているあいだ本文を隠すのは開いた一覧のほうで、上の余白は要らない。閉じると余白が戻るので、項目を選んで移った先や、外へ出たフォーカスは、留めた要素の下に見える。
- スクリプトで留めた要素の中へフォーカスを戻すとき（Escape で開閉の行へ戻すなど）は、`focus({ preventScroll: true })` にする。

```css
@media (min-height: 500px) {
  .toc {
    position: sticky;
    top: 0;
  }

  html:has(.toc > details:not([open])) {
    scroll-padding-top: calc(var(--toc-height) + var(--space-16));
  }

  .toc > details:not([open]) > summary {
    scroll-margin-top: calc(
      var(--rule-w) + var(--box-padding) - var(--toc-height) - var(--space-16)
    );
  }
}
```

使えない形:

- 打ち消しを留めた要素の中のすべての要素（`.toc, .toc *`）に掛ける形。一覧が中で送れる長さのとき、Tab で最後の項目へ進むとページが 300px 余り下へ動き、Shift+Tab で戻ると項目が一覧の上端より上に出て見えなくなる。
- 一覧の中の要素だけ打ち消しを 0 にする形。項目は一覧の中に見えるが、ページが 8〜150px 動く。
- 打ち消しを `-9999px` のような大きな負の値にする形。スクリプトで `focus()` したとき、ページが1万〜5万 px 下へ飛ぶ。
- 打ち消しを「上の余白」や「留めた要素の高さ」だけにする形。開閉の行へのフォーカスで、ページが数 px〜約 300px 動く。

**根拠**: 実測（cycle-316 の T5-15。ブログの記事の目次。Chromium 141.0.7390.37（Playwright の chromium-1194）で、375×667・1280×800・375×667 の文字サイズ 200% を測った。WebKit と Firefox では測っていない）。

- 打ち消しの無いとき、留まった目次の開閉の行へ Shift+Tab で戻ると、ページは上へ 341px（375）・408px（1280）・288px（200%）送られた。
- 打ち消しを「−上の余白」にすると下へ 11px（375）・19px（1280）、「−留めた要素の高さ」にすると上へ 297px（375）・下へ 3px（1280）送られた。`-9999px` では、Escape で `focus()` したとき 1万〜5万 px 下へ飛んだ。
- 打ち消しを `.toc, .toc *` に掛けた形では、21項目の一覧で Tab で最後の項目へ進むとページが 309px（375）・368px（1280）下へ動き、Shift+Tab で戻ると項目が一覧の外に出て見えなかった（2回目のレビューの測り）。一覧の中の要素だけ 0 にした形では、ページが 8〜150px 動いた（同じレビューの測り）。
- 上の CSS の形では、2記事（11項目で一覧が中で送れない長さと送れる長さ、21項目で送れる長さ）× 3つの大きさ × 留まる前と後で開き、Tab で最後の項目まで進んで Shift+Tab で開閉の行まで戻るあいだ、どの項目も一覧の中に見え、ページの位置は変わらなかった。Escape で閉じたあともページは同じ位置で、フォーカスは開閉の行にあった。閉じた目次の開閉の行へ Shift+Tab で戻るとき・マウスで開くときも、ページは動かなかった。項目を選んで移った先の見出しは、閉じた目次の下端の 16px 下にあった。

**推論**: ルートの `scroll-padding` の中にある要素へのフォーカスでページを送るのは、CSSOM View の scroll into view が `scroll-padding` を差し引いた範囲に要素を見せる決まりどおりの動きに見える。そうならほかのエンジンでも同じことが起きるが、確かめていない。打ち消しの量が幾何どおりに効くことも、測ったのは Chromium だけである。

## 2. 本文に重なる層の上の送りは、`overscroll-behavior` と入力ごとの受け手では止めきれない。層が出ているあいだはページの送りを止める

本文の上に重なる層（開いた目次の一覧など）の上で送ったとき、ページが送られると、来訪者は層に隠れて気づかないまま読んでいた所を失う。層に `overflow-y: auto; overscroll-behavior: contain` を掛けても、次の送りはページへ漏れる。

- 中身が収まって送れない層の上のホイールと指の送り（Chromium 143 以前・Firefox 149 以前。仕様では止まり、Chromium は 144、Firefox は 150 で仕様に合わせた。Safari は確かめていない）。
- キーの送り（↑↓・PageUp・PageDown・Space・Home・End）。Chromium 143 以前は、中で送れる層でもキーの送りを `overscroll-behavior` で止めず、層の端を越えた送りをページへ渡す（Chromium は 144 の別の変更で従うようにした）。
- 層を開く行（`summary`）など、層の外の要素にフォーカスがあるときのキーの送り。マウスや指で開いても、フォーカスは開く行に残る。
- 修飾キーを伴う送り（Shift+Space・Ctrl+Home・Ctrl+End・Alt+↑↓。Mac では Cmd+↑↓・Option+↑↓ も既定の送り）。

`wheel`・`touchmove`・`keydown` の受け手で送りを1つずつ止め、層だけを送る形は、入力の道（フォーカスの場所・修飾キー・続けて押したときの滑らかな送りの続き）ごとに漏れが残った。

**対処**: 層が出ているあいだは、ページ全体の送りを止める。

- ルートに `overflow: hidden` を掛ける。掛けるのは、層が出ていて、かつ層が画面に留まって本文に重なる条件（目次では留める規則と同じ `@media (min-height: 500px)`）のときだけにし、どちらも CSS で決める（`html:has(<層> [open])` を留める規則と同じメディアクエリの中に置く）。ホイール・指・キー（層の外にフォーカスがあるときや、修飾キーとの組み合わせを含む）のどの送りもページを動かさない。層は自分の `overflow-y: auto` で中を送れる。
- 層が留まらない条件（低い画面）では止めない。層はページとともに動くので、ページを送っても層に隠れたまま本文だけが動くことはない。止めると、開いたまま拡大・窓の変更・回転で留める条件を外れたとき、層が記事の元の位置（画面の外）へ戻ったままページを送れなくなる。
- 開いたまま画面が留める条件をまたいだら（`matchMedia` の `change`）、層を閉じずに、開くときと同じく層の上端が画面の上端に来るまで即時に送る。送らないと、留まらなくなった層は画面の外へ消え、留まるようになった層は一覧の下が画面の外にはみ出す。スクリプトの送りは `overflow: hidden` のルートでも効く。条件をまたがない大きさの変わり（スマホのツールバーの出し入れなど）では送らない。送ると、低い画面で開いたままページを送った来訪者を層へ引き戻す。
- 層を持つページのルートに、いつも `scrollbar-gutter: stable` を掛ける。`overflow: hidden` でページのスクロールバーが消えても、その場所が残り、開閉で本文の幅と折り返しが変わらない。スクロールバーが場所を取らない端末（重ねて出すスマホなど）では何も変わらない。
- 層の中の項目を選んでページの中を移るときは、層を閉じて止めを外してから移る（項目の `click` で閉じれば、リンクの既定の移動は閉じたあとに起きる）。
- 層の端まで送ったあとの指の送りを、ページの引っ張り（更新）や跳ね返りに渡さないよう、層の `overscroll-behavior: contain` は残す。
- 入力ごとの受け手（`wheel`・`touchmove`・`keydown`）は置かない。ブラウザの拡大（Ctrl+ホイール・つまみ）もそのまま効く。
- 止めているあいだは、層の外に見える本文も送れない。層を閉じれば送れる。低い画面では止めないので送れる。

**根拠**: 実測（cycle-316 の T5-15。Chromium 141 で、ヘッドレスの 375×667・1280×800・375×667 の文字サイズ 200% と、`Xvfb` の上の画面ありの 1280 幅の窓を測った。Chrome 144 以降・WebKit・Firefox では測っていない）。

- ページの送りを止める形で、2記事（11項目の一覧と21項目の一覧）× 3つの大きさ × 留まる前と後の12通りを測った。フォーカスを開く行・最初の項目・最後の項目に置き、↓・↑・PageDown・PageUp・Home・End・Space・Shift+Space・Ctrl+Home・Ctrl+End・Alt+↓・Alt+↑・Meta+↓・Meta+↑ を2回ずつ押しても、層の上と層の外の本文の上でホイールと指で送っても、ページは1度も動かなかった。中で送れる一覧は、ホイール・指・キー（最初の項目から End、最後の項目から Home）で両端（387・241・671・1497）まで送れた。
- 画面ありの Chromium（1280 幅の窓、スクロールバーあり）で開閉すると、`documentElement.clientWidth` は 1265→1280→1265 と変わるが、`main` の位置と幅（152.5+960）と本文の幅は変わらず、開閉のあいだの layout-shift は0件だった（2記事 × 留まる前と後）。対照として `scrollbar-gutter` を外すと、開いたとき `main` の左端が 152.5→160 へ動き、layout-shift が1件出た。
- 同じ窓（1280×900、100% で `innerHeight` 761）で、2記事を y=4000 で開き、一覧の上で本物の X の Ctrl+ホイールを1回ずつ送って 200% まで拡大した。150%（`innerHeight` 507）までは目次は上端（0）に留まり、止めも掛かったまま。175%（435）で留める条件を外れると、目次は上端（0）へ送られ（ページ 4000→518）、止めは外れた（ルートの `overflow` が `visible`）。200%（380）では目次の上端が −100・−59 になった（条件をまたがない拡大なので送らない）が、一覧の下端（280・322）は画面の中にあり、最後の項目を押せた。200% の本文の上の本物のホイールで、ページは 519→699 と送られた。開いたまま Ctrl+0 で 100% に戻すと、目次は上端（0）に留まり、止めがまた掛かり、最後の項目を押せた。止めを留める条件に結びつける前の形では、同じ手順の 175% で目次が記事の頭の元の位置（画面の上端から −3482px）へ戻り、止めが掛かったままで、200% でホイールを5回送ってもページは 4000 のままだった（10回目のレビュー（review-t5-15-10.md）の測り）。
- 同じ窓で、本物の X の入力（`Xvfb` の上で `libXtst` の `XTestFakeKeyEvent`・`XTestFakeButtonEvent`）で、開いた一覧の上に Ctrl+ホイール（上へ3回）を送ると、拡大が 100%→150%（`innerWidth` 1280→853）になり、`wheel` 3件はどれも取り消されず、ページは 4000 のままだった。ふつうのホイールは、一覧の上では一覧だけを送り（0→280）、一覧の外の本文の上ではページを送らなかった（4000 のまま）。
- 入力ごとの受け手の形の漏れ（止める形を採る前の測り）:
  - 受け手の無い形で、中で送れない11項目の一覧の上のホイールと指で、ページが 543→3743・4000→7200・4000→7682（375）・4000→8561（1280）まで送られた。キーでは、最後の項目から ↓2回 4000→4080、End 4000→11170（1280）・14574（375）（8回目のレビュー（review-t5-15-8.md）の測り）。
  - 層がまだ送れるときだけキーをブラウザに任せる形で、21項目の一覧の上端から ↓ を 40ms おきに30回押すと、一覧が端へ着いたあと、ページが 4000→4120（375）・4080（1280）へ送られた。
  - 項目の上のキーだけを止める形で、開く行にフォーカスがあると End でページが 54505 へ、Home で 0 へ送られ、修飾キーの Shift+Space・Ctrl+Home・Ctrl+End・Alt+↓（4000→4700）もページを送った（9回目のレビュー（review-t5-15-9.md）の測り）。
- 記事の上に、`position: fixed; max-height: 400px; overflow-y: auto; overscroll-behavior: contain` の箱を置き、その上で 400px のホイールを6回送った。中身が1段落で送れない箱では、ページが 3000 から 5089（375）・5076（1280）へ送られた。中身が60段落で送れる箱では、箱の中が 1486 まで送られ、ページは 3000 のままだった。
- 測り方の落とし穴:
  - Playwright のヘッドレスの Chromium はスクロールバーを描かない（`--hide-scrollbars`）が、`scrollbar-gutter: stable` はその場所を取る。375 の画面で `main` の幅が 343→328 になり、ヘッドレスで測った位置が画面ありやスマホと合わなくなる。スマホの形（`isMobile`）では 343 のまま、画面ありの Chromium ではスクロールバーがもとから同じ場所を取るので 328 のままで、どちらも `scrollbar-gutter` の有無で変わらない。幅に関わる値は、画面ありとスマホの形で測る。
  - CDP の `Input.dispatchMouseEvent`（`modifiers: 2`）で送る Ctrl+ホイールは、ヘッドレスでも画面ありでも、ブラウザの拡大の処理を通らない。拡大は起きず、取り消されなければページが送られる（本文の上で、画面ありで上へ 120 を3回送ると 4000→3640、ヘッドレスで上へ 120 を1回送ると 4000→3880）。CDP の `Input.synthesizePinchGesture` も拡大しなかった。拡大は、`Xvfb` の上の画面ありの Chromium に XTest で本物の入力を送り、拡大する対照と取り消す陰性の対照を置いて測る（6回目のレビュー（review-t5-15-6.md）の測りで、すべての `wheel` を取り消す陰性の対照では拡大しなかった）。拡大を戻すのも X の Ctrl+0 で送る。
  - キーの送りは既定で滑らかに動くので、押した直後に位置を読むと、送りの途中の値になる（End・Home のあと 150ms で読むと 0→0・632→18、1秒後には端にあった）。

**確認**:

- 仕様（CSS Overscroll Behavior Module Level 1、https://www.w3.org/TR/css-overscroll-1/#propdef-overscroll-behavior）は、`overscroll-behavior` を、中身があふれているか・来訪者が送れるかに関わらず、すべてのスクロールコンテナに当てる。
- Chrome は 144（安定版 2026-01-13）で、中で送れない箱でも `overscroll-behavior` が送りの引き継ぎを止めるようにした（Chrome 144 のリリースノート https://developer.chrome.com/release-notes/144 の「Respect `overscroll-behavior` on non-scrollable scroll containers」、chromestatus 5129635997941760、blink-dev の Intent to Ship https://groups.google.com/a/chromium.org/g/blink-dev/c/OSq1yVSSdDE/m/fq8a7frQAAAJ）。同じ 144 の別の変更で、キーの送りも `overscroll-behavior` に従うようにした（同じリリースノートの「Respect `overscroll-behavior` for keyboard scrolls」、chromestatus 5099117340655616、Chromium の issue 41378182）。
- Firefox は 150（2026-04-21）で、中身があふれていないスクロールコンテナにも `overscroll-behavior` を当てるようにした（MDN の Firefox 150 の開発者向けリリースノート https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/150、Bugzilla 1837436 https://bugzilla.mozilla.org/show_bug.cgi?id=1837436）。149 以前は、送れる幅の無い `overflow: auto` の箱では従わなかった（Bugzilla 1724358 https://bugzilla.mozilla.org/show_bug.cgi?id=1724358 の議論）。
- Chromium は Ctrl+ホイールとトラックパッドのつまみを、`ctrlKey` の付いた `wheel` の既定の動きとして拡大し、ページがその `wheel` を取り消すと拡大しない（Chromium の blink-dev での変更の告知 https://groups.google.com/a/chromium.org/g/blink-dev/c/BW4hshtMsmo と Chromium の issue 40332613）。

どれも cycle-316 の T5-15 のレビュー（5回目・7回目・8回目・9回目、review-t5-15-5.md・review-t5-15-7.md・review-t5-15-8.md・review-t5-15-9.md）が出典を読んで確かめた。Firefox 150 の変更と、Chrome 144 のキーの送りの変更は、9回目が確かめた。

**確認**（iOS の Safari で止めが漏れる、知られた場合。10回目のレビュー（review-t5-15-10.md）が WebKit の bug の記録を読んで確かめた）:

- ツールバーが縮んでいるとき、ルートの `overflow: hidden` があってもページが指で送れる（WebKit Bugzilla 240859 https://bugs.webkit.org/show_bug.cgi?id=240859「`<body>` with overflow: hidden CSS is scrollable on iOS when Safari's UI is collapsed」）。設定の変更（bug 301667）で直り、Safari 26.4（2026年4月）でその設定の既定が切り替わった。それより前の iOS では漏れ、26.4 以降にも残る場合を bug 317941 https://bugs.webkit.org/show_bug.cgi?id=317941 が追う。記事を読み進めた来訪者は、ツールバーが縮んだ状態で層を開くことが多い。
- 画面をつまんで拡大しているとき（visual viewport が layout viewport より小さいとき）、ページ全体が送れる（WebKit Bugzilla 240860 https://bugs.webkit.org/show_bug.cgi?id=240860。直っていない）。

**推論**: 上の iOS の Safari の漏れは、この環境では確かめられず、測っていない（T9 で、ツールバーが縮んだ状態と出ている状態、つまんで拡大したあと、iOS の版を記録して実機で確かめる）。つまむ拡大とトラックパッドのつまみが止めているあいだも効くかも、測っていない。Mac の Cmd+↑↓・Option+↑↓ が止まることも測っていないが、ページの送りそのものを止めるので、ほかのキーと同じく止まると考える。

## 3. スマホの形で画面を回すと、Chromium は画面の上の真ん中の要素を拠り所に送る。上端に留めた要素が拠り所になり、読んでいた所を失う

スマホの形（ビューポートの meta を持つページを、画面の幅が変わる形で回すとき）で、Chromium は回す前に画面の上の真ん中（画面の幅の 0.5・高さの 0 の点）にあった要素を拠り所にし、回したあとも同じ要素が画面の上に来るようにページを送る。縦の画面で上端に留めた要素（閉じた目次）はちょうどその点にあるので、拠り所になる。横の画面で画面が低くなって要素が留まらなくなると、要素は記事の頭の元の位置へ戻り、Chromium はそこへページを送る。来訪者は読んでいた所から記事の頭へ引き戻される。CSS の送りの拠り所（scroll anchoring）とは別の仕組みで、`overflow-anchor: none` では止まらない。

**対処**: 留めた要素が閉じているあいだ、読み始めの線（留めた要素が上端に留まっていればその下端、でなければ画面の上端）のすぐ下の本文の要素と、その要素のどこが線に掛かっているか（線の下から始まるなら線からの距離、線をまたぐなら線より上に出た部分の割合）を、送るたびに覚えておく。画面の大きさが変わって留める条件をまたいだら、その要素を線に対して同じ所へ即時に送る。

- 覚えるのは、画面の大きさが変わる前の値にする。回したときの `resize` と `scroll` の出来事は、Chromium が拠り所に合わせて送ったあとに届く（`resize` の時点で、ページはもう記事の頭へ送られている）。覚えたときと画面の大きさが違う `scroll` では覚え直さない。
- 大きさが変わったあとの数フレームは、本文の表の組み直し（ResizeObserver）とブラウザの送りの拠り所がまだ本文を動かすので、すぐに戻したうえで、次の2フレームでも同じ所へ戻し直す。
- 覚える要素は、線の少し下を順に調べて、画面の高さより低い要素にする。調べる点が段落のあいだのあきに当たると本文全体を包む要素が返り、それは幅が変わると組み直されて読んでいた所を指さない。
- 線をまたぐ長い段落は、割合で覚える。幅が変わって段落の行数が変わっても、同じあたりの行を線に合わせられる。
- 留める条件をまたがない大きさの変わり（スマホのツールバーの出し入れなど）では送らず、ブラウザの送りに任せて覚え直す。
- 留めた要素が開いているあいだは、2の項のとおり、条件をまたいだら要素を画面の上端へ送る。

**根拠**: 実測（cycle-316 の T5-15。Chromium 141 の、Playwright のスマホの形（`isMobile`・`hasTouch`、`deviceScaleFactor: 2`）で、`setViewportSize` で幅と高さを入れ替えて回した。iOS の Safari と Android の Chrome の実機では測っていない）。

- 直す前（目次を留めて、覚えて戻す処理の無い形）: 2記事 × 375×667・390×844・412×915 で y=5000 から縦→横に回すと、ページが 415〜474（記事の頭）へ送られた。横→縦に戻しても元の所へは戻らなかった。ルートや目次に `overflow-anchor: none` を掛けても同じだった。目次を留めない対照では、読んでいた段落の近く（3103〜4016）に残った（12回目のレビュー（review-t5-15-12.md）の測り）。
- 回したときの出来事の順: y=2500 から回すと、`resize` の時点で `scrollY` はもう 418 で、そのあと `scroll`、留める条件の `change` の順に届いた。
- 覚えて戻す形: 2記事 × 3つの大きさ × 深さ 900・2500・5000・8000 の24通りで、回す前に読み始めの線の上にあった字（`caretRangeFromPoint` で取った字を Range で追った）は、横の画面で線から回す前と最大 31px 違う所（1行ほど）にあり、縦に戻すと最大 18px 違う所にあった。目次を留めない対照では、それぞれ最大 25px と 2px だった。
- デスクトップの形（1280×800→1280×450→1280×800、1280×800→1280×480→1280×800）で y=5000 から高さを変えても、読んでいた行は線から同じ所（14・−1）に残った。タブレット（768×1024→1024×768→768×1024。どちらも留める）でも同じ所（−4・5）に残った。
- 開いたまま回すと、目次は画面の上端（0・1）に来て開いたままで、縦に戻すと上端に留まり、ページの送りの止めも戻った（375×667・390×844・412×915）。

**確認**: Chromium の `RotationViewportAnchor`（`third_party/blink/renderer/core/frame/rotation_viewport_anchor.cc`）は、画面の中の点で当たりを取った要素を拠り所にし、回したあとにその要素の位置からページの送りを決め直す。その点は `web_view_impl.cc` の `viewportAnchorCoordX = 0.5f`・`viewportAnchorCoordY = 0`（画面の上の真ん中）で、メインフレームの幅が変わる回転のときに `ResizeWithBrowserControls` が使う（Chromium の main のソースを読んで確かめた。cycle-316 の T5-15）。

**推論**: Android の Chrome は同じ Blink の仕組みで回すので、実機でも同じことが起き、同じ対処が効くと考える。iOS の Safari が回すときにどの要素を拠り所にするかは分からず、測っていない（T9 で、閉じた目次のまま本文の途中で縦から横に回し、読んでいた所が保たれるかを実機で確かめる）。
