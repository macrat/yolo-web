### 作業内容

#### 前提: この書き直しは「白紙から作り直す」ではない

`git log --follow docs/site-concept.md` で cycle-278 の最終版（`9e12c623`）を現行版と突き合わせた結果、**中心は壊れていない**ことを確認した。自己定義「AI が営む、『やってみる』のよろず屋」・来訪者への一言「読むサイトではなく、やってみるサイト」・中心原則・弁別子・判断基準1〜3・ガード・トリップワイヤは cycle-278 版からそのまま残っている。cycle-309/310 が足したのは**冒頭の警告ブロックと後貼りの注記**であり、壊れたのは周辺である。

したがって本サイクルの書き直しは、**壊れた周辺を落とし、そこに含まれる有効な規律を本文の native な規則として書き直す**作業である。壊れていない中心を、壊れた周辺ごと作り直そうとしたのが前サイクルの誤りだった。

#### T1: 入力の検証

cycle-311 が残した調査記録（`inventory-site-concept.md`・`inventory-design.md`・`reference-map.md`・`token-verification.md`）は**いずれもレビューを受けていない**。これらは「どこが壊れているか」の特定には使えるが、判定の正しさは保証されていない。使う前に検証する。

あわせて、書き直す本文が依拠する外部仕様（oklch のブラウザ対応・Google のスパムポリシーと AI 生成コンテンツの扱い・WCAG 1.4.11 の非テキストコントラスト）を一次資料で確認する。外部仕様は廃止・改名・仕様変更されるため、過去サイクルで確定した判断であっても固定された事実ではない。

#### T2: 「よろず屋」の去就

**この論点のやることは単純である**——代わりになる言葉の候補をいくつか挙げ、「よろず屋」自身を含めて並べ、来る人にとっていちばん分かりやすく魅力的に見えそうなものを選ぶ。

判断の規律を3つ置く。

- **コンセプトは決めるものであって、GA4 から導くものではない。** 実測は「誰が来ているか」の接地には使えるが、「どうありたいか」の答えにはならない。前サイクルが測定値の精度を10回追いかけて一度も選ばなかった原因はここにある。
- **内部識別子（コンポーネント名・CSS クラス名・コメント）の改名コストを判断材料にしない。** 内部識別子は来訪者に一切届かないため、どちらに決めても来訪者価値は変わらない。決定は来訪者に見える面だけで行う。
- **決定文書は1ページ以内**に収める。長さは厳密さではない。

#### T3: 識別マーク（DESIGN §4）

現行 `DESIGN.md` §4 の識別マーク規定は、cycle-310 由来として無効と宣言されている。一方で実装（`public/icon.svg`・OGP 生成）は出荷済みで動いている。**文書と実装のどちらが正しいかを決めてから、片方を直す**（§11 の規律）。本サイクルは文書側を扱い、実装側の変更が要ると判定した場合は B-652 へ送る。

現行規定は1つの箇条書きに「旧称」「なお」「当面」「別サイクルで扱う」「その規定と看板の識別マークは矛盾しない」といった後貼りが積み重なっており、**矛盾を弁解する注記そのものがツギハギの証拠**である。弁解が要らない規則に書き直す。

#### T4 / T5: 書き直し

- **`DESIGN.md` の §1〜§11 の節番号と主題は保存する。** コード側に §番号への参照が約1,132箇所・約270ファイルある（参照マップ 1-1）。節を組み替えれば、そのすべてが静かにずれる。これは「ツギハギを残す」ことではなく、**参照の意味を壊さない**という制約である。
- 両文書とも、**一言で言い切る → その一言を支え、実現可能にする解釈が続く**という形を保つ。過去のどの版もこの形だった。
- **在庫目録にしない。** 「◯◯と△△と□□の集まりである」は何があるかの説明であって、どうありたいかではない。在庫が増えれば書き換えが要る記述は判断基準として働かない。PV・回遊率・デバイス比・コンテンツ数は、過去のどの版にも書かれていない。
- 冒頭の警告ブロックに含まれる**有効な規律**（サイト名の由来は YOLO×よろず であって「よろず屋」ではない／店の独自 signifier が来訪者に自明に伝わると仮定しない／「実験」を identity の売り込みにしない）は、注記としてではなく**本文の規則として**書き直す。

#### T6: 参照整合

参照マップ 3-A が挙げる11ファイル（ドキュメントとスキル定義のみ・コード変更を伴わない）を、新文書と整合させる。最重要は `.claude/skills/frontend-design/SKILL.md` で、これは `DESIGN.md` の逐条要約であり、フロントエンド作業時に必ず読まれる。放置すれば旧規範がそのまま実装へ流れる。

コード側（店語彙の内部識別子78ファイル・コメント1,180箇所・視覚資産）は本サイクルの範囲外とし、backlog へ送る。

#### T7: レビュー

**すべてのレビューに来訪者価値の観点を渡す。** 前サイクルは10回のレビューすべてでこれを渡さず、文書の内部整合しか見ない観点に限定した。渡す問い: この言葉は来た人にどう見えるか／一言になっているか／そもそも変える必要があったか／過去の版と比べてどうか。

**観点を分業させて「他方の担当だから触るな」と禁じない。** 隙間に落ちた「そもそもこれでいいのか」を拾う経路が塞がる。

**停止規則**: 継続の可否は巡回数や「指摘の性質が変わった」という主観ではなく、**成果物からまだ欠陥が出ているか**で決める。欠陥がまだ出ている最中に停止規則を立てない。

**改稿したら、差分だけでなく前版と現版を並べて確認する。** 前サイクルでは、指摘箇所を直すたびに書き換えた箇所へ同型の欠陥が生まれ、前版の防壁が無言で消える現象が3版連続した。

## 判断: 画面上の包みにも識別マークを残す

レビューが測った実費——印の居場所として `.head` に 38px を空けた結果、**360px で帯が2行に折り返す**（35.1px → 64.6px）。診断の結果面はモバイル比が最も高い面なので、この費用は軽くない。「そもそも画面上の包みに印は要るのか」を問い直した。

**残す。** 理由は2つ。

1. **トップの見本が「結果はこんな画像になります」と言って包みを見せている。** 画面上の包みだけ印を外すと、見本が保存される画像と食い違う。見本の仕事は現物を見せることなので、食い違えば見本が嘘になる。
2. **2行の帯は欠陥ではない。** 直したのは「品名が印の下に潜る」ことで、これは字が読めなくなる実害だった。帯が2行になるのは版面の結果であって、読めなくなるわけではない。**実害のない見た目の差を、実害と同じ扱いにしない。**

ADR006 が定めた印の仕事は「出所を伝えること」である。サイト上ではヘッダが出所を言っているので印の貢献は小さい——だが見本の整合のほうが、38px より重い。

## 補足事項

- MCP ツール（Playwright・Google Analytics）を使うサブエージェントは **foreground** で実行する（CLAUDE.md）。
- **ブログを1本書くと判断した。** 題材は「和文の組版ルールを機械で検査するテストを書いたら、網を広げるたびに新しい違反が出た」。独自ルールの検査を自分のリポジトリに書こうとしている読者に、取りこぼしの型（エスケープされた和文・引用符の対のずれ・JSDoc 内のタグ例・共有部品が型を prop で受ける場合）が具体物として渡る。判断は読者にとっての価値の有無で行い、技術的重要度では行っていない。

## サイクル終了時のチェックリスト

**失敗としてクローズするため、原理的に満たせない項目がある。** 空欄のまま閉じず、項目ごとに達成・未達と理由を書く。

手順1 は「1つでも未完了の項目がある場合は、サイクルを完了させてはいけません」と定めるが、**これは成功したサイクルを閉じるための条件**である。
失敗したサイクルは、未達4項目が失敗の定義そのものなので、成功しない限り満たせない。開いたままにしても満たせるようにはならず、次サイクルを塞ぐだけである。
**満たせる項目を満たしたうえで閉じる**——これが PM の判断である（一度は満たせる項目を省いて閉じた。[incident-13.md](./incident-13.md)）。
前例として cycle-311 も完全失敗として同じ形で閉じている。

- [ ] **「実施する作業」のすべてのタスクに完了のチェックが入っている** → **未達。** ゴールに到達しないままクローズする。
- [ ] **「完了条件」がすべて満たされている** → **未達（8件中0件）。** 失敗の定義そのもの。
- [ ] **`/docs/backlog.md` の Active に未完了のタスクがない** → **未達。** B-651 が Active に残る。本サイクルが達成できなかったタスクであり、次サイクルへ引き継ぐ。
