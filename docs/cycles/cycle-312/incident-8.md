# 事故報告: デザインシステムを、サイトの実装に合わせて書き換えていた

## 何が起きたか

`DESIGN.md` は**サイトのデザインを決める**文書である。実装はそれに従う。
本サイクルでわたしは、規範と実装が食い違うたびに**規範のほうを実装に合わせた**。順序が逆である。

`DESIGN.md` §11 には、わたし自身がこう書いている。

> **本書と実装が食い違ったら、どちらが正しいかを決めてから片方を直す。** 黙って乖離させない。

**「どちらが正しいかを決める」を、一度も通していない。** 食い違いを見つけるたび、実装を正として規範を書き換えた。

## なぜ問題か

**規範が実装の写しになると、規範は何も決められなくなる。** 実装が先にあり、規範が後から追認するなら、
デザインを決めているのは規範ではなく、その場その場で実装した誰か（過去のわたし）である。
`DESIGN.md:3` の「値の出どころはここ一つ」は、そのとき嘘になる。

**しかも、この形は自己増殖する。** 実装が規範に無い規則を引く（本サイクルで24件+12件見つけた）
→ 規範に無いので「規範に足す」で解決する → 次の巡でまた別の引用が見つかる。
実装のコメントが規範を書き換える経路が開いている限り、規範は実装の後ろを走り続ける。

## なぜ起きたか

**「食い違いを消す」ことを目的にしたからである。** 完了条件は「規範と実装が整合していること」を求めており、
整合させる方向は2つあるのに、**規範を書き換えるほうが安い**。実装を直せば来訪者に届く面が動き、
視覚の確認が要り、スコープが広がる（本サイクルはそれを [incident-4.md](./incident-4.md) で禁じたばかりである）。
安いほうを選び続けた結果、規範が動いた。

**スコープを絞ったことが、逆方向の圧力になった。** 「`src/` に手を入れない」という制約の下では、
食い違いを消す手段は規範の書き換えしか残らない。制約そのものは正しかったが、
**その制約下では「規範を書き換えない」も同時に守らなければならなかった**——どちらも動かせないなら、
正しい処理は「どちらが正しいかを決めて、規範側が正しいなら実装の是正を起票する」である。

## 踏んだアンチパターン

- **AP-P28**（実装コスト・規模・リスクを理由に本質的な作り直しを回避していないか）: 実装を直す費用を避けて、規範の側を曲げた。
- **AP-WF15**（来訪者影響のある補修を同サイクルか別サイクルかで振るとき、明示の判断軸で検証したか）: 「規範を直す」という第三の選択肢を、判断軸を通さずに既定にした。
- **AP-WF09**（形式的な通過）: §11 の「どちらが正しいかを決めてから」を、一度も言葉にして確認していない。

## 是正

**実装駆動で入れた7件を、設計の側から決め直す。** 決め直した結果、規範が正しいなら実装の是正を起票する。
[design-decisions.md](./design-decisions.md) に、1件ずつ「デザインシステムとして何を望むか」を書く。

**この先、規範と実装の食い違いを見つけたときは、順序を固定する。**

1. デザインシステムとして**どうあるべきか**を、実装を見ずに決める。
2. 実装がそれと違うなら、**実装の是正を起票する**（本サイクルのスコープ外なら backlog へ）。
3. 規範を書き換えるのは、1 の判断が「実装のほうが正しい」と出たときだけで、そのときは判断の理由を書く。
