# 事故報告 2: PM が確かめずに書いた前提（5回）

## 何が起きたか

本サイクルで PM は、計画や指示文に書いた前提を5回間違えた。いずれもサブエージェント・レビュアーの実測で発覚した。

| #   | PM が書いたこと                                           | 実際                                                                           | 発覚元   |
| --- | --------------------------------------------------------- | ------------------------------------------------------------------------------ | -------- |
| 1   | frontmatter の残骸ブロックは23記事                        | 25記事                                                                         | T1 担当  |
| 2   | `related_tool_slugs` は記事ページの関連ツールリンクに効く | 逆引き専用。効くのは道具・ゲーム側の「関連記事」欄                             | T1 担当  |
| 3   | 残骸を残すと連載の順序が壊れる                            | `series_order` を読むコードは無い。順序は `published_at` 昇順                  | T4 担当  |
| 4   | テーマトグルは静的シェルでは視覚的に消えている            | 箱（52×28px）は残る。`disabled` ＋ `aria-hidden` ＋ `tabIndex={-1}` の空ボタン | T8b 担当 |

## 誤りの型

4件とも同じ型である——**確かめずに書いた**。ただし内訳は2種類ある。

- **#1・#2・#3**: PM 自身が作った検出器やコードの読みが甘かった。#1 は検出器が `[` の単独行しか数えず、1行に収まった残骸を取りこぼした。#2・#3 は消費側のコードを最後まで追わずに「そうなっているはず」で書いた。
- **#4**: **サブエージェントの報告の記述を、検証せずに別のサブエージェントへ事実として転記した。** T8 担当が「テーマトグルは JS 無効時に視覚的に消えている」と書いたのを、実装を読まずに T8b の指示文へ持ち込んだ。

## 既存のアンチパターンに当たるか

**当たる。** `docs/anti-patterns/workflow.md` の AP-WF06 がそのものである。

> サブエージェントに渡す事実情報（数値・日付・コンテンツ内容等）をファイルやコマンドで事前に確認したか？推測や記憶で伝えていないか？
> → （…）**調査レポート由来の数値であっても、指示文に転記する前に実体確認しなければ同じ伝播が起きる。**

#4 は「調査レポート由来」の条項に正面から該当する。AP-WF12（PM 自身が参照する事実の確認）も #1〜#3 を覆っている。

## なぜチェックが働かなかったか

**「サブエージェントが実測して報告したこと」を「検証済みの事実」と同一視していた。**

T8 担当は実際に JS 無効のスクリーンショットを撮っており、その画面でトグルが見えないのは本当である。だが「見えない」の理由は箱が消えたからではなく、中身のアイコンが無いからだった。**観察は正しく、そこから導いた説明が誤っていた。** PM はその説明のほうを引き写した。

報告の中で「観察した事実」と「その説明」は別物であり、後者は検証を経ていない。この区別を付けずに転記したことが原因である。

## 結果として何が起きたか

#4 では、誤った前提が指示文に入ったまま T8b 担当へ渡った。PM は「テーマトグルと同じく静的シェルでは出さない」を選択肢(b)として提示していた。

**担当は指示を鵜呑みにせず実装を読み、前提の誤りを指摘したうえで正しい案（箱は据え置き・`disabled`）を採った。** 誤った前提は成果物に入らなかったが、それは担当の判断に救われたのであって、PM の手続きが機能したからではない。

## 手続きの是正（第一版）

指示文に他のサブエージェントの報告を引く場合、**その報告が「観察」か「説明」かを分け、説明のほうは PM が一次資料（コード・コマンドの出力）で裏を取ってから書く。**
裏が取れないものは「担当の報告によれば」と出典を明示し、事実として断定しない。

## その是正は効かなかった

**上の是正を書いた直後に、5件目と5'件目が出た。** どちらも他人の報告の転記ではない。PM 自身が
「実測した」と書いて記録した数値である。第一版の是正は #4 の型（他者の報告の転記）しか見ておらず、
**より多い型を取り逃していた。**

5件のうち #1・#3・#5・#5' の4件は同じ型である——**PM が使い捨ての検出器を書き、その出力を検証せずに事実として記録した。**

| #   | 検出器の盲点                                                                                                                                    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `[` が単独で1行を占める形しか数えず、1行に収まった残骸を取りこぼした                                                                            |
| 3   | 消費側のコードを最後まで追わずに「そうなっているはず」で書いた                                                                                  |
| 5   | `git log -- <path>` を使い、`--follow` を付けなかった。記事が `src/content/blog/` から移動する前の履歴を丸ごと見落とした                        |
| 5'  | `grep` で `.tags` を拾って「消費箇所」としたが、同名プロパティの別物（遊びコンテンツの値札）を混ぜ、逆に `tags` を props で受け渡す面を落とした |

**「実測した」と書けるのは、検出器が正しい場合に限る。** 検出器そのものは検証されていない。
そして PM は毎回、検出器の出力を「実測値」として文書に記録していた。

## 手続きの是正（第二版）

検出器を書いて数値を出したら、**記録する前に次の2つを実行する。**

1. **反例を1つ手で確かめる。** 検出器が「該当しない」と判定した対象から1つ選び、目で見て本当に該当しないかを確認する。
   #1 はこれで捕まった（25件中2件が「該当しない」側に紛れていた）。
2. **検出器が見ていない範囲を言葉にする。** 「この検出器は◯◯を見ていない」を1行書く。書けないなら、検出器の射程を理解していない。
   #5 は「ファイルの移動前の履歴を見ていない」と書けていれば防げた。

数値を文書に書くときは、**どう測ったか（コマンド・スクリプトの要点）を併記する。** 測り方が書けない数値は書かない。
