# サイクル-313

記事に書かれているタグが、来訪者に届いていない。

`src/blog/content/` の8記事は frontmatter に5つずつタグを書いているのに、サイトはそれを空配列として読む。
その結果、その記事はタグ一覧ページに載らず、関連記事のスコア計算（共有タグ数）からも外れる。
別の4記事は `related_tool_slugs` を同じ理由で失っており、道具・ゲームのページから記事への導線が消えている。

原因は `src/lib/markdown.ts` の手書き YAML パーサである。値が次の行へ折り返された配列を読めず、
黙って `null` を返す。`src/blog/_lib/blog.ts` が `Array.isArray(...) ? ... : []` で受けるため、
型の上は正常値になり、ビルドもテストも通る。**壊れていることを誰も知らせない。**

本サイクルでこれを直す。ついでではなく、根から直す——記事の残骸を除き、パーサを既存の `js-yaml` に一本化し、
「frontmatter に書かれた値がパース結果に現れる」ことを全記事で検査する回帰テストを置く。

## 作業計画

### 目的

**記事に書かれているタグと関連ツールを、来訪者に届くようにする。**

実測した実害は次のとおり（2026-09-14・`git merge-base main HEAD` の `fe94f907` 時点）。

| 失われているもの     | 記事数 | 件数            |
| -------------------- | ------ | --------------- |
| `tags`               | 8      | 40（5本×8記事） |
| `related_tool_slugs` | 4      | 52              |

最も古いもので **7か月**（2026-02-14 起点）のあいだ、書かれた値が読者に渡らないまま記事が並んでいた。
**12記事すべてが、その値を frontmatter に書いた最初のリビジョンから読まれていない。**
例外は1度だけで、うち4記事が 2026-03-27 の **2時間27分38秒**（10:56:46〜13:24:24 JST）だけ読める状態にあった。
値の側を書き戻して直した窓が、Prettier の整形で閉じたものである（[measurements.md §4](./measurements.md#4-値の側を直したら2時間27分38秒で戻った)）。

失われたタグは、**タグ一覧ページへの掲載・記事ページと一覧カードのタグ表示・タグページの生成可否・
`sitemap.xml` のタグURL・関連記事のスコア・一覧の人気タグ・キーワード検索・フィード・
`<meta name="keywords">` の10の面**に同時に効いている。
とりわけ「ワークフロー連載」は掲載数が4→11となり `MIN_POSTS_FOR_TAG_INDEX`（5件）を跨ぐため、
`noindex` から `index` へ変わる。連載を探している読者が検索から直接たどり着ける面が1つ増える。

面の一覧は [measurements.md §5](./measurements.md#5-tags-が効いている面)、タグごとの掲載数の増減は
[§2](./measurements.md#2-失われたタグが痩せさせていたタグ一覧ページ)、起点の内訳は
[§3](./measurements.md#3-いつから届いていなかったか) に置く。

**そして、確かめに行って別の欠陥が出た。** 本番の `https://yolos.net/blog` が返す HTML には、
記事へのリンクが**1本も入っていない**（実測: `<a>` は25個・すべてヘッダとフッタ）。
記事一覧はハイドレーション後にクライアントで描かれている。`/blog/category/*`・`/blog/tag/*` も同じである。

つまり、JavaScript が動くまで一覧は空白で、動かない環境では最後まで空白のままになる。
タグを復元しても、その行き先のページが最初の描画で空なら、来訪者の道は繋がらない。
本サイクルの検証手順（生成された HTML でタグ一覧への掲載を確認する）も、このままでは成立しない。
**同じ道の同じ区間の話なので、本サイクルで両方を直す。**

### 作業内容

#### T1: 残骸ブロックの除去（25記事）

frontmatter に、キーを持たない ID 配列が残っている。廃止されたメモ系統（`docs/cycles/` 記載・
記事 `2026-03-16-memo-system-rise-and-fall` が廃止を述べている）の残骸である。2つの形がある。

```yaml
series_order: 1
  [
  "19c5663375f",
  ...
  ]
related_tool_slugs: ["kanji-kanaru", "yoji-kimeru"]
```

```yaml
series: null
  - "19c8e142237"
  - "19c94cc9cb6"
```

**この除去を T2 より先に行う必然がある。** 手書きパーサはこれらの行を読み飛ばすので実害が無いが、
**厳格な YAML はこれを直前のキーの平文スカラーの継続として吸収する**（実測）。
`series: null` は文字列 `"null - \"19c8e142237\" - ..."` に、`series_order: 5` は文字列 `"5 - ..."` になる。

残骸25記事のうち、親キーが `series: null` の12記事は**連載の所属**が壊れる。
`series` は `SeriesNav` とシリーズ内の記事一覧に効くので、これは来訪者に見える実害になる。
残る13記事は親キーが `series_order` で、文字列化するのはその値だけである——
`series_order` を読むコードはリポジトリに存在せず、連載の並びは `getSeriesPosts` が `published_at` の昇順で決めている。
つまり実害は12記事だが、**残骸を残したままパーサを替えれば必ずそこが壊れる**ので、T1 を T2 より先に置く。

```yaml
tags:
  - "ワークフロー"
  - "AIエージェント"
```

#### T4: パーサの一本化

**欠落が誰にも知らされなかった理由は、パーサの振る舞いそのものにある。** 読めない形に出会ったとき、
手書きパーサは例外を投げずに `null` を返す。受け側の `Array.isArray(data.tags) ? … : []` が `null` を `[]` に変える。
`[]` は下流のどの消費者にとっても型として正しい値なので、TypeScript も vitest も `next build` も何も言わない。
**標準フォーマットの部分自作パーサは、仕様のどこを落としているか誰も把握できない。**

`js-yaml` は既に本番依存であり（`package.json` の `dependencies`）、
`scripts/validate-blog-frontmatter.ts` もこれで frontmatter を読んでいる。
つまりリポジトリには読み取り経路が2本ある。これは別の危うさで、
2本ある限り「どちらが正しいか」を突き合わせる者がいない状態が続く。

このスクリプトが承認していたのは日時2キーだけで、`tags` は検査対象に無い——
経路が2本あることと、検証が壊れた値を通していたことは別の問題である
（[measurements.md §11](./measurements.md#11-frontmatter-の検証スクリプトが見ていたもの)）。

手書きパーサ（`parseYamlBlock` / `parseYamlScalar`・約100行）を削除し、`parseFrontmatter` を `js-yaml` に委ねる。

日付の扱いに注意が要る。`js-yaml` は引用符の無い日付を `Date` として解釈する
（`scripts/validate-blog-frontmatter.ts` の既存コメントが述べている）。
現行の記事はすべて引用符付きだが、`parseFrontmatter` の型境界で文字列を期待している箇所が
壊れないことを実測で確かめる。

#### T4b: 書式の統一

T2 で12記事をブロック配列形にした結果、**87記事のうち12記事だけが違う書き方**になっている。
どの記事に手を入れたかが書式から見分けられる状態で、これはツギハギである（CLAUDE.md「ツギハギ禁止」）。

全87記事の `tags` / `related_tool_slugs` をブロック配列形へ揃える。値は変えない。
T4 でパーサを `js-yaml` にすればインライン形でも実害は無くなるが、**揃えておけば
「`prettier` が折り返す」という状態そのものが二度と発生しない。** パーサの正しさに頼らずに済む。

#### T5: 回帰テストの新設

`src/blog/__tests__/blog-frontmatter-validation.test.ts` は
`published_at` / `updated_at` / `category` / `series` / `slug` しか見ておらず、
`tags` と `related_tool_slugs` を検査しない。ここが今回の見逃しの穴である。

**「サイトの読み取り結果 == 厳格な YAML」という形の検査は置けない。** T4 でサイトが `js-yaml` を使う以上、
それは `js-yaml` を `js-yaml` と比べるだけの、常に通るテストになる。

置くべき検査は、**frontmatter に書かれた文字が、パース結果に現れているか**である。
パーサの実装が何であっても成立し、黙った欠落を捕まえる。全87記事に対して次を検査する。

1. **書かれ方とパース結果が一致する**——パース結果の各値を frontmatter の書式へ書き戻し、
   それがファイルに立っている文字列と一致することを求める。文字列は引用符付き、`null`・数値・真偽値は裸、
   要素のある配列はブロック配列形が正典である。**全キーが対象**で、配列の取りこぼしも、
   引用符を落としたスカラーも、ここで落ちる。
2. **frontmatter に宙に浮いた行が無い**——`---` に挟まれた各行は、キー行・そのキーに属する値の行・
   空行・コメントのいずれかである。どのキーにも属さない行があれば失敗させる（今回の残骸ブロックがこれに当たる）。
3. **キーの型が期待どおり**——`tags` / `related_tool_slugs` は文字列の配列、
   `published_at` / `updated_at` は文字列、`draft` は真偽値、`series_order` は数値または不在。

   日付を文字列として検査する理由は「引用符を落とすと `Date` になるから」だが、**この条件は一様ではない**（実測）。
   `js-yaml` がタイムスタンプとして解釈するのは `2026-07-16` / `...+09:00` / `...Z` / `2026-07-16 12:00:00` の形で、
   **コロンの無いオフセット `+0900` は引用符が無くても文字列のまま**である。
   だから型の検査だけでは足りず、検査1が要る。

4つの壊し方を作業用コピーで再現し、どの検査が落ちるかを確かめた（[measurements.md §7](./measurements.md#7-回帰テストが何を捕まえるか)）。
検査1と検査2は網の張り方が違う——検査1は「書かれた値がそのまま読めているか」を、
検査2は「そもそも読み手に届かない行が無いか」を見る。**両方が要る。**

なお、既存の `blog-frontmatter-validation.test.ts` の中に**もう一つの手書き YAML スカラー抽出器**が入っていた。
本サイクルが `markdown.ts` から削除したのと同じ性質の部分実装である。
ファイル全体をサイト本体の `parseFrontmatter` に一本化して解消した。

#### T7: ブログ一覧を静的HTMLに載せる

> **この節の判断は撤回した（[incident-10.md](./incident-10.md)）。**
> fallback 無しの `<Suspense>` は「一覧は JS で描く」という設計判断であり、欠陥ではなかった。
> 静的HTMLに載せ直したことで、全来訪者が一覧の中身を2回受け取るようになっていた

> 実測で1%未満である。以下は当時の記述をそのまま残す。

`src/blog/_components/BlogListView.tsx` は、記事一覧まるごとを `<Suspense>` で包んでいる。**fallback を渡していない。**
その中身の `BlogFilterableList` は `"use client"` で `useSearchParams` を呼ぶ。

Next.js の仕様はこうである。

> If a route is prerendered, calling `useSearchParams` will cause the Client Component tree up to the closest `Suspense` boundary to be client-side rendered.

> Place the `<Suspense>` boundary as close to the hook call as possible. Wrapping a large subtree forces the entire subtree into the fallback and loses prerendered content.

境界が一覧全体を包み、fallback が空なので、静的HTMLには**何も入らない**。実測と一致する。

是正は、フックの読み取りを必要な葉まで下ろし、記事リストそのものは静的シェルに載せることである。
キーワード検索（`?q=`）が無い状態の一覧は、サーバ側で確定できる——`posts` は既にページネーション済みで
Server Component から渡っている。`?q=` が付いたときだけクライアントが差し替えればよい。

fallback の形は最終的な描画と一致させる（Next.js 公式がレイアウトシフトの回避として求めている）。
`calculateNewSlugs` は `Date.now()` を使うが、これは既に Server Component 側で計算して props で渡しており、
fallback を非決定的にしない。

**完了条件は測れる形にする**——`npm run build` の生成物で、`/blog`・`/blog/category/*`・`/blog/tag/*` の
各 HTML に記事への `<a href="/blog/<slug>">` が含まれていること。

**検索欄を1つ足したことで、一覧そのものがHTMLから消えていた。** 4か月と1週間、誰も気づかなかった。

#### T8b: 静的シェルの検索欄

> **この節の判断は T7 とともに撤回した（[incident-10.md](./incident-10.md)）。**
> 静的シェルに検索欄が出ること自体が T7 の産物なので、戻した現在は欄も一文も存在しない。
> 以下は当時の記述をそのまま残す。

T8 の実機確認で、**本サイクルの変更が作った副作用**が出た。

静的シェルの検索欄は `readOnly` だけが付いた状態で、JS 無効の実機では
**有効時とまったく同じアクセントカラーのフォーカスリングが出て、キャレットも立ち、打った文字は黙って捨てられる**。
スクリーンショットは JS 有効時と完全に同一で、来訪者には区別がつかない。

前提として、**JS 無しの検索は原理的に作れない**。ページは静的に prerender されており、`?q=` を付けて開いても
同じ静的HTMLが返る（絞り込みはクライアントで行われる）。サーバーで `searchParams` を読めば可能だが、
それはルートを動的にするので採れない。`<form method="GET">` にしても同じ理由で機能しない。
**「機能させる」選択肢は無く、「どう見せないか」の判断になる。**

**このサイトに、倣うべきパターンは無い。** 同じ「JS 無しでは機能しないコントロール」に対して、
テーマトグル・ハンバーガー・検索欄の3通りの扱いが同居している。
扱いの内訳と、この面で満たすべき3条件・却下した解は
[measurements.md §12](./measurements.md#12-js-無しで機能しないコントロールの扱い) に置いた。

**採った解**は、検索欄を `readOnly` から `disabled` へ変え、
JavaScript が動かない環境でだけ現れる一文を入力欄の直下に添えることである（`ee0486b`・`2a22097d`）。

`disabled` が担うのは操作と読み上げの側である。打った文字が捨てられることはなくなり、欄はタブ順から外れ、
支援技術には無効として伝わる。`Input` の `:disabled` が変えるのは `background` / `color` / `cursor` の3つだけで、
箱の寸法に効く宣言を1つも持たないため、静的シェルとハイドレーション後でレイアウトは動かない。

**見た目は伝えていない。** `:disabled` の地 `--paper-2` と通常時の地 `--paper` のコントラスト比は
ライト **1.061:1**・ダーク **1.080:1**（`globals.css` のトークン値から WCAG の式で算出）で、隣に並べても差が見えない。
文字色も、静的シェルの時点で検索欄は空であり、見えているプレースホルダは通常時から `--ink-2` なので変わらない。
枠線（`--rule-strong`）も変わらない。**「いま使えない」ことを伝えているのは、入力欄の直下に出る一文である。**
入力欄そのものの見分けにくさはサイト全体の課題なので、`readOnly` の側を B-694、
無効状態の見分けにくさを B-708 として起票した。ハンバーガーの扱いは B-695 である。
**3件とも本サイクル内に中止した**——入力欄の見た目はデザインシステムが決めるもので、
B-651 の作り直しで消える（[キャリーオーバー](#キャリーオーバー)）。

（[measurements.md §14](./measurements.md#14-タグページを持たないタグが読者から隠れていた)）。

**なぜ本サイクルで扱うのか。** 本サイクルの目的は「記事に書かれたタグを読者に届ける」ことで、
パーサを直しても `TagList` のフィルタが、書かれたタグを別の理由で消す。いちばん重いのは YAML の記事で、
書かれた5つのタグのうち3つが読者に出ていなかった。**同じ道の同じ区間である**（T7 と同じ理由）。

**設計はサイクルの途中で変わっている。** 最初に実装したのは「ページを持たないタグも見せ、リンクにしない」で、
罫の線種（実線＝リンク／破線＝ラベル）で区別した（`6a6eb561`）。3巡目の実機レビューがこれを否決した。
実効コントラストは実線 1.52:1 / 破線 1.27:1（ライト）・1.62:1 / 1.36:1（ダーク）で、
識別情報に求められる 3:1 の半分以下である。さらにラベルは `min-height: 44px`——操作要素のタップターゲット寸法——で
組まれており、同じ画面に出る値札（実線の罫を持つ非リンク）が「実線＝押せる」を既に否定していた。

**採ったのは、区別する符号を作り直すことではなく、区別する必要を無くすことである**（`f9526235`）。
サイトはページの存在（`MIN_POSTS_FOR_TAG_PAGE = 3`）と索引（`MIN_POSTS_FOR_TAG_INDEX = 5`）を別々の閾値で決めており、
掲載3〜4本のタグは既に「ページはあるが `noindex`」で運用されていた。存在の閾値だけを撤廃し、
`getAllTags` が返すすべてのタグにページを作る。リンクにならないタグも、新しい符号も、`linkableTags` の引き回しも、
4ファイルに重複していた定数も同時に消えた。索引の挙動は変えていない——新たにページを得た8タグはいずれも掲載2本以下で、
`noindex, follow` のまま `sitemap.xml` のタグURLは23件で前後不変である（§14）。
タグの種類が37のまま増減しないことは読み取りの是正と同じで、
[§2](./measurements.md#2-失われたタグが痩せさせていたタグ一覧ページ) に前後の掲載数がある。

T12（`TODO(cycle-184/B-389)` の削除）は、削除時点の12箇所すべてが T11 で触る5ファイル
（`blog/[slug]/page.tsx`・`BlogList.tsx`・`BlogListPanel.tsx`・`BlogListView.tsx`・`TagList.tsx`）に載っていたため、
最初の実装（`6a6eb561`）で同時に処理した。待ち先のタグUI撤去案は cycle-184 で中止済みで、残す理由が無い。
削除後の `src/` の該当箇所は0である（実測）。

### 検討した他の選択肢と判断理由

**(a) 手書きパーサに折り返し配列の読み取りを足す。** 採らない。
今回の欠陥は「折り返し配列」という一形態ではなく、**YAML の部分実装が仕様のどこを落としているか誰も把握していない**
ことに由来する。一形態を足しても、次の形態で同じ黙った欠落が起きる。
`js-yaml` が本番依存として既に入っている以上、部分実装を維持する理由が無い。

**(b) 12記事の frontmatter だけを直す（B-685 の起票時のスコープ）。** 採らない。
それでは手書きパーサが残り、`prettier` が次に折り返した瞬間に同じことが起きる。
**この道は既に一度歩かれている。** 2026-03-27、同じ欠陥が診断され、折り返した `tags` をインライン配列へ
書き戻して5記事が読めるようになった。その **2時間27分38秒後**、frontmatter を書き換える別のコミットで
Prettier が走り、うち4記事が元の折り返しへ戻った（[measurements.md §4](./measurements.md#4-値の側を直したら2時間27分38秒で戻った)）。
cycle-312 の事故19も同型である。

**(c) `prettier` の整形結果に合わせて書き方を固定する。** 採らない。
`prettier` 公式ドキュメントは markdown の frontmatter の整形について何も規定していない。
規定の無い挙動に設計を依存させると、`prettier` の更新で黙って壊れる。
パーサ側を正しくして、**整形結果に依存しない状態**にするのが正しい。

**(d) B-651（サイトコンセプト・デザインシステムの整理・P0）を本サイクルで扱う。** 採らない。
cycle-310・311・312 の3サイクルが連続で B-651 に失敗し、来訪者には1件も届いていない。
やり方を変えずに4回目を始めるのは、同じ失敗の再演になる。
B-651 は Queued に残し、本サイクルは**来訪者に実際に届く小さな1件**に絞る。

**(e) T7 で `export const instant = false` を使って一覧をリクエスト毎の描画にする。** 採らない。
Next.js 公式が「For a client-hook error this is rarely the right answer」と述べており、
ナビゲーションが即時でなくなる代償を払う。一覧の中身はキーワードが無ければサーバで確定できるので、
境界を葉へ下ろすほうが正しい。

**(f) T7 を別サイクルへ回す。** 採らない。
本サイクルの検証手順（生成HTMLでタグ一覧への掲載を確認する）がこの欠陥に依存しており、
直さないと本サイクルの成果が確かめられない。また、タグを復元する目的は
「読者が次の1本にたどり着けるようにする」ことで、行き先が最初の描画で空ならその目的は達成されない。
**同じ道の同じ区間である。**

**(g) T7 が作った B-696（ハイドレーション時にフォーカスが body へ落ちる）を本サイクルで根治する。** 採らない。
根治の形は `useSearchParams` をやめ、マウント後に `location.search` を読むことである。
フォーカスの喪失も一覧 DOM の差し替えも消えるが、`useSearchParams` が担っている
**戻る/進むで `?q=` が変わったときの追従**を、`popstate` の購読として自前で書き直すことになる。
戻る/進むが壊れるほうが、ハイドレーションまでの短い窓でフォーカスが外れるより、遭遇する来訪者も影響も大きい。
そして本サイクル自体が、標準フォーマット（YAML）の読み取りを手書きしたために欠落が7か月間
誰にも知らされなかった事例である（[measurements.md §3](./measurements.md#3-いつから届いていなかったか)）。
**フレームワークが提供する標準の挙動を手書きで置き換える賭けは、同じ形をしている。**
フォーカスの喪失は既知の劣化として受け入れ、当時は B-696 として追跡することにした。
**その B-696 も本サイクル内に中止した**（B-651 に畳む・[キャリーオーバー](#キャリーオーバー)）ので、
追跡先は残っていない。根治へ進む条件は変わらない——`popstate` による追従を安全に書き直せる根拠
（テストを含む）が揃ったときである。

## 出荷について
