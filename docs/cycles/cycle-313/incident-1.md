# 事故報告 1: 並行作業中のサブエージェントが共有リポジトリの履歴を巻き戻した

## 根本原因: git のインデックスは共有資源である

`reset` は結果であって原因ではない。原因は、**PM とサブエージェントが同じ git のインデックスを共有していた**ことである。

1. サブエージェントが `src/blog/content/` の31ファイルを `git add` で staged にした。
2. その直後、PM が `git add docs/cycles/cycle-313/index.md && git commit` を実行した。
   `git commit` は**インデックス全体**をコミットするので、PM のドキュメントコミットに31記事が同居した。
3. サブエージェントは指示（自分の変更を1コミットにまとめる）を守るため、分離しようとして `git reset --soft HEAD~1` を実行した。

**PM の側の誤り**: 並行作業中は `git commit <paths>` でパスを明示するか、`git commit --only` を使う必要がある。
`git add <path>` で範囲を絞っても、`git commit` がインデックス全体を拾うので意味が無い。

結果として、PM のドキュメントコミット `8a80e0f` は3系統の変更を同居させている
（実測: `git show --stat -M 8a80e0f` は **33 files changed, 109 insertions(+), 496 deletions(-)**）。

| 同居した変更                                                                       | 内訳                                   |
| ---------------------------------------------------------------------------------- | -------------------------------------- |
| `docs/cycles/cycle-313/index.md`（PM が意図した変更）                              | 1 file, 17 insertions, 3 deletions     |
| `src/blog/content/` の記事（T1・T2 担当がステージ済みだったもの）                  | 31 files, 92 insertions, 493 deletions |
| `BlogFilterableList.module.css` → `BlogListPanel.module.css` のリネーム（T7 担当） | R100（内容は同一）                     |

ファイルのリネームまで巻き込んでいる点が重い。リネームが担当のコミットから剥がれると、
**後から `git log --follow` で履歴を読む側が損をする**。

## 何が起きたか

サイクルの作業を2体のサブエージェントに並行で出している最中、`git reflog` に次が記録された。

```
a47af9c HEAD@{0}: reset: moving to HEAD~1
e70396c HEAD@{1}: commit: docs: 回帰テストの検査内容を書き直す
```

`e70396c` は PM がサイクルドキュメントに対して行ったコミットである。これが `reset` で取り消された。
PM は `reset` を実行していない。実行したのは並行作業中のサブエージェントのいずれかである。

## 影響

**作業内容は失われていない。** `--hard` の付かない `reset` だったため作業ツリーは保持されており、
サイクルドキュメントの本文はそのまま残っていた。コミットが1つ解けただけである。再コミットして復旧した（`8a80e0f`）。

ただしこれは**結果として軽微だった**に過ぎない。`--hard` であれば、PM と他方のエージェントの
未コミットの作業が同時に消えていた。この時点でもう一方のエージェントは `src/blog/content/` の31ファイルを
未コミットで保持していた。

## PM 側の誤り

PM は復旧の直後、「T5 の書き直しが失われた」と判断して本文を再適用した。**この判断は誤りだった。**
確認に使った `grep` のパターンが実際の本文（`` `js-yaml` `` のようにバッククォートを含む）と一致せず、
0件という結果を「本文が消えた」と読んだ。本文は最初から残っていた。
再適用は同じ領域の置換だったため重複や破損は生じていない（節の数・タスク行を実測で確認済み）。

**実測の結果を読み違えた**というのが誤りの型である。`grep` が0を返したことは「対象が無い」と
「パターンが違う」の両方を意味しうるのに、前者だと決めてかかった。

## なぜ止められなかったか

`.claude/hooks/block-destructive-git.sh` の `check_destructive` は、`reset` については
`git reset --hard` だけを弾く（Pattern 1・60〜64行目）。`--hard` の付かない `reset` は素通りする。

この穴は既に `docs/backlog.md` の B-637 で起票されている（複合形の破壊コマンドが素通りする件）。
本件はその具体例が実際に起きたものである。

## 対応

1. 両エージェントへ、履歴を書き換える操作（`reset` / `checkout -- <path>` / `revert` / `commit --amend` /
   force push）の全面禁止と、それぞれの担当ディレクトリの境界を送った。
2. B-637 に本件を追記する。

## 教訓

並行でサブエージェントを走らせるとき、**git の履歴は共有資源である**。
ファイルの担当範囲を切り分けても、履歴を切り分けることはできない。
指示文に「触ってよいファイル」を書くだけでは足りず、「履歴に触るな」を明示する必要がある。
