## 指摘

### 指摘1（高）: 診断のページでの道具の押しは、半辺 12.5px でなく半辺 10px の面で調整される

t5a-measure.md 0章の「タッチの調整」「届くかどうか」「D5 の数の意味」「試しの走りで見えたこと」、report.mjs の頭の注釈（「道具の押しは半辺 12.5px の面で調整され」）は、道具の押しを半辺 12.5px の面での調整としている。もとは knowledge §8 と review-knowledge-2.md の実測（素のページで dy 12 まで寄り 13 で寄らない）である。ところが、ページに `touchstart` か `pointerdown` の受け手があると、面は一辺 25 dip に広がらず、半辺 10px になる。

- 小さなページ（800×600、`hasTouch`、左上 (300,100)・100×40 のボタン、下の縁から dy 離して `Input.dispatchTouchEvent` で押す。`btn3.mjs`・`btn.mjs`）: 受け手が無いページと `click` の受け手だけのページでは、dy 9.5・11.5 とも寄った（review-knowledge-2.md と同じ）。`window` に passive の `touchstart`、`document` に `touchstart`、`document` に `pointerdown` の受け手を置くと、どれも dy 9.5 は寄って 11.5 は寄らなかった。`pointerdown` の受け手のページで渡さない押しを測ると、dy 9.5 は寄り、10.5・11.5・12・13 は寄らない（境は 10px）。`radiusX/Y` 12 では dy 11.5 まで寄り、12 で寄らない（境は 12px）。寄せた座標も半辺 10px の面の交わりの中心と合う（dy 9.5 の点 149.5 → 面 [139.5, 159.5] とボタン [100, 140] の交わりの中心 139.75 → 139）。
- 診断のページ（変更後の版の science-thinking、375×550、`hasTouch`、道具の受け手は置かない。`edge.mjs`）: 1問目の最後の選択肢の行（`li`）の下端から押すと、行の下端から 8.05px（押せる範囲の下端からは 9.05px。指摘2）は寄って、9.05px（同じく 10.05px）は寄らなかった。`radiusX/Y` 16 では押せる範囲から 15.05px まで寄り、16.05px で寄らない。寄せた y も、どの点でも半辺 10px の面と押せる範囲の交わりの中心と合い、半辺 12.5px の面とは合わない（例: 行の下端から 0.05px の点 392 は 386 に寄った。半辺 10px なら交わり [382, 390.95] の中心 386.5、半辺 12.5px なら 385.2）。
- 試しの走りの★の16本も同じである。375×550 の contrarian-fortune（点 308、選択肢までの dy 0.3）は 302 に、impossible-advice（点 350、dy 0.8）は 344 に、1280×800 の10本（点 356、dy 0.9）は 350 に寄った。半辺 10px の面なら 302・344・350、半辺 12.5px の面なら 301・343・349 になる（押せる範囲の下端は指摘2 のとおり記録の下端の 1px 上）。React はルートに `touchstart`・`pointerdown` の受け手を置き、道具の `pageProbe` も `window` に `touchstart` の受け手を置くので、道具がこのサイトで押すときはいつも半辺 10px になる。
- PM の問いの dy 11.8・12 の回が寄らなかった件は丸めによるものではない。面は半辺 10px で、押せる範囲は記録の矩形より 1px 内側にある（指摘2）ので、実際の隔たりは 12.8・13px で、どちらの理由でも届かない。

受け手で面が変わる仕組みは、ソースでは確かめていない（推論: 受け手があると押しが描画の側で受けられてから gesture に組まれ、Aura の 25 dip に広げる段を通らない）。ただ、このサイトで道具の押しが半辺 10px の面で調整されることは、上の実測で決まる。

このことから、次が変わる。

- 道具の押しは Android のいちばん小さい面（半辺 10px）と同じ幅で調整される。plan-t5a7.md 3 の両向きの数え直しのうち「道具では寄ったが max(dx, dy) が 10px 以上の件」は、つくりの上で 0 になる（指摘3 の測る時がずれていなければ）。数えるのは「道具では寄らなかったが 16px より小さい件」の一つの向きになる。
- D5 の数は「ずれ＋半辺 10px の面での調整」の値になる。
- 10-1 の「Android のいちばん小さい面の半辺 10px よりずっと内側」は正しいままだが、0章の「道具の押しの面の半辺（12.5px）の中にも」は直す。

直し方: 0章の「タッチの調整」以下を、「このサイトの診断のページには `touchstart`・`pointerdown` の受け手があり（React のルートと道具の受け手）、道具の `Input.dispatchTouchEvent` の面は一辺 2×max(radiusX, radiusY) を Blink が 20〜32 dip に収めたもので、渡さない押しは一辺 20 dip（半辺 10px）」という形で、初めからそう書いたように書き直す。report.mjs の注釈と README の要約の `n` の読み方も合わせる。knowledge §8（「このコンテナの Chromium では…25〜32 dip」「渡さない押し…は一辺 25 dip」と根拠の行）と、plan-t5a7.md 3 の「タッチの調整の距離」（「試しの走りの数は半辺 12.5px の面での調整にあたる」）は担当の書ける所ではないので、PM が直させる（受け手の有無で面が変わることと、上の実測を根拠に足す）。

### 指摘2（中）: 問の選択肢の押せる範囲を、行の罫線を含めた矩形で測っている

`nearFrom` と着地の記録の `reach` は、`data-hit-area="after"` の要素の押せる範囲を、位置を決めた祖先（`li`）の `getBoundingClientRect()`（罫線を含む箱）で取る。押せる範囲を広げている `.choiceButton::after` は `position: absolute; inset: 0` で、絶対位置の基準になる `li` の内側の箱（padding box）を覆い、`li` の `border-bottom: var(--rule-w-hair)`（1px）は覆わない。診断のページで `document.elementFromPoint(65, 行の下端 − 0.5)` は `LI`、`行の下端 − 1.5` は `BUTTON` を返し、罫線の 1px は押せない。上の指摘1 の寄せた座標も、押せる範囲の下端を記録の下端の 1px 上に置くと合う。

このため、選択肢が点の上にあるとき、記録の dy は実際の隔たりより 1px 小さい（★の件の dy 0〜0.9 は実際は 1〜1.9、字に落ちた5本の 11.8〜12.7 は 12.8〜13.7）。数え直しの境（10px・16px）で1px ずれるので、`mayFall16` を多めに数える。

直し方: 道具では、`data-hit-area="after"` の要素の押せる範囲を、祖先の矩形から罫線の幅（`getComputedStyle` の `border-*-width`）を引いた内側の箱で取り、README の `n`・`l` の文と 0章の「記録」の文にそう書く。着地の記録の `farFirst`・`farBoth` も同じ箱で数える（関数の `chooseLanding` の引数の矩形は関数が渡したままなので、道具の側で直すか、直さないなら 1px の差を README に書く）。PM へ: 変更後の版の `pressableRectOf`（reveal.ts）も同じ箱で数え、注釈は「要素の箱で数えると、行の区切りの罫線…を『押せるものが無い』と取り違える」と書くが、下の罫線は実際には押せない。着地の作りを決め直すときの材料として渡す。

### 指摘3（中）: 隔たりを着地のあとの最初のフレームで取るので、2打目を調整する時の組みと違うことがある

Chromium は2打目の tap を受けた時の組みで寄せる。道具は、2打目が受けた画面の着地のあとの最初のフレーム（`requestAnimationFrame`）で `near` を取る。そのあと2打目までに組みが動けば、記録の隔たりは寄せに使われた隔たりと違う。

- 基準の版: 問のカード（`.card`）と解説に `fadeIn 0.3s`（`translateY(8px)` から 0）があり、最初のフレームの矩形は 8px 近く下にずれている。試しの走りの基準の版では、記録の隔たりが 10px を超えるのに次の問の選択肢に寄った押しが 15 あった（答えの走査の 300ms で 14.1・15.1・15.1・10.5、90ms で 9.5、200% の「はじめる」で 11.9、D5「はじめる」の (0, +20) の 300ms で 11.1〜11.7 の9本。`scan.mjs`）。面が半辺 10px（指摘1）なら、2打目の時には選択肢がもっと近くにあったことになり、動きのずれで説明がつく。
- 変更後の版: `QuizContainer.tsx` は、Web フォントの `loadingdone` で問の高さが変われば、来訪者が送っていなければ同じ決め方で送り直す。どの回も字を読み込んでいない新しい文脈から始めるので、300・500ms の回では、最初のフレームと2打目のあいだに組みと送りが変わりうる。試しの走りの押しごとの記録（判断に要る押しだけ）では着地の呼び出しはどれも1押しに2つ以下で、送り直しは見えなかったが、`near` はフレームの切り替わりでしか取らないので、送り直しがあっても取り直さない。

直し方: 2打目の `touchstart` の受け手（`pageProbe` の捕捉の段階）で、その時の組みで `nearFrom(points[0])`・`nearFrom(points[1])` を取り、要約の `n`・`n2` はこれにする（2打目の押し下げと tap の調整のあいだに組みは変わらない）。最初のフレームの値も残すなら別の欄にする。0章の「記録」の文と README の `n` の文もそう直す。

### 指摘4（中）: report.mjs と記録から、plan-t5a7.md 3 の合否の数（落ちうる件のうち避けられた件）が出せない

plan-t5a7.md 3 は、「避けられたのに落ちた件」の合否を「max(dx, dy) が 16px より小さい件を落ちうる件として判定する」と定める。数えるには、回（走査は押し）ごとに「落ちたか max(dx, dy) が 16px より小さい」と「着地の範囲の中に避ける送りがあった」の両方が要る。

- report.mjs の `avoidable` は実際に落ちた回だけを数え、`mayFall16` は着地の記録（`l`）と組み合わせていない。
- 答えの走査（`answers`）の要約の `n` は隔たりだけを持ち、着地の記録を持たない。押しごとの記録を置くのは落ちた押しなどだけなので、落ちなかったが 16px より近い押しが、範囲の中に避ける送りを持っていたかは、どこにも残らない。条件7 の答え・「次へ」と D5 の答えの走査で、この件を数えられない。

直し方: 答えの走査の `n` の各押しに、その押しの着地の記録（`l` と同じ4つ）を足す。report.mjs は、`avoidable` に加えて、落ちたか 16px より近い件のうち `clearOf` が立つ件（組ごと）を出し、あわせて範囲の中で 16px 以上離せた件（`farFirst`・`farBoth` ≥ 16）も出す。どれを合否に使うかは plan-t5a7.md 5 の判断で、PM が決める。

`null` は別に数え、走査の `n` の各押しに落ちた先の組（`s` と同じ字）を持たせて、押しごとの記録に頼らずに数える。

### 指摘9（低）: 道具の「押せるもの」が Chromium の候補より狭いことが書かれていない

Chromium のタッチの調整の候補は、knowledge §8 のとおり、マウスでフォーカスできる要素（`tabindex` を持つもの）と `:hover`・`:active` で見た目が変わる要素を含む。道具の `PRESSABLE` は `a[href]`・`button`・`summary`・入力・`[role]` だけで、問の見出し（`h2[tabindex="-1"]`）と結果のボックス（`section[tabindex="-1"]`）を含まない。これらが選択肢より点に近ければ、Chromium はそちらへ寄せうる（推論。来訪者の答えは変わらない向き）。0章か README の `n` の文に、道具の候補が着地の関数の候補と同じで、Chromium の候補より狭いことを書く。
