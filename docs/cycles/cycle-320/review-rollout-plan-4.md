## A. 出荷の可否か来訪者が受け取るものを変えるもの

### A-1. 「はじめる」の二度押しに、本番との比べと、通ったと言える線が無い【重】

タスク2の3つ目の項は、2打目が1問目の選択肢に落ちるかを design-rollout だけで確かめている。落ちるなら「スクロールしない（本番と同じふるまい）」に直し、同じ組で確かめ直す。しかし、本番そのものがどうなるかを測る手順が無い。

- 本番の `QuizContainer`（origin/main）は、「はじめる」で `setPhase("playing")` するだけで送らない。開始の画面は同じ入れ物の中で問の画面に入れ替わる。そのため本番でも、「はじめる」の真下に1問目の選択肢が来る画面では、2打目が選択肢に落ちうる。
- cycle-316 の t5a-measure.md 5-1 では、T5a の前の design-rollout の版（送らない版）で、2打目が6画面すべてで1問目の選択肢に落ちている。この版は本番のふるまいに近い。
- そうだとすると、「スクロールしない」に直しても同じ組で落ちる件は0にならない。「確かめ直す」が何を満たせば終わるのかが決まっていないので、直しても終われず、cycle-320 と同じく直しと測りを繰り返すおそれがある。
- 逆に、本番でも同じだけ落ちるなら、決め方の上では直す対象にならない。その場合、送りを外す直しは要らず、B-614 の直し（選択肢がすべて見えること）も保てる。

**直し**: 同じ小さなスクリプトで、同じ組を本番の版（origin/main のビルド）にも当てる。線は「本番で落ちない組では design-rollout でも落ちない」とする。直すのは、その線を外れた組があるときだけにする。直したあとも同じ線で確かめる。あわせて、「200% の12本」の画面を「375×550 の 200%」と書く。index.md が出どころとして示す t5a-measure.md 10章は、36be6b9a で消えている。

### A-2. cycle-320 を閉じる方法が無く、次のサイクルが新しい計画に入れない【重】

次のサイクルは、`cycle-kickoff` の手順1で「前回のサイクルが完了していない場合は、まずはそちらを完了させてください」と求められる。しかし cycle-320 は、いまの文書のままでは完了の処理を通れない。

- cycle-320 の index.md は `completed_at: null` で、`pause-cycle` の印が残っている。
- 「実施する作業」には、未チェックの T5a の作業が7行ある（26〜32行。着地の直しの害・測りの分け方・T5a-7a-2・外れた件の判断・T5a-8・B-623・申し送り）。
- 一方で、サイクル終了時のチェックリスト（128行）は、一度載った項目を外すこと、次へ送ること、狭めることを禁じている。`cycle-completion` の手順1も、未完了があれば完了させない。
- そのため、次のサイクルの PM が手順のとおりに進めると、cycle-320 の T5a の作業を終えようとするか、そこで止まる。どちらになっても、計画の「出荷まではこの計画のタスクだけ」と矛盾する。

main 側にも穴がある。セッションは main から始まる。

- main の `docs/backlog.md` の B-754 の行は、いまも「分け方はそのブランチのcycle-316/split-plan.md」を指している。
- main の `cycle-kickoff` には、オーナーが残した「サイトの価値に寄与しない修正だけが3回以上続いたら止める」の1文が無い（`git show origin/main:.claude/skills/cycle-kickoff/SKILL.md` に無い）。
- `cycle-completion` の手順7は、統合のブランチの途中のサイクルが2つのスキルを変えたら、main へ手順のコミットを作るよう定めている。cycle-320 を閉じるときにそれをしないと、次のセッションは古い指し先と古いキックオフで始まる。

**直し**: cycle-320 の閉じ方を決めて書き、出荷のサイクルを始める前にそのとおりに閉じる。書くのは、carryover.md、または PM がいま閉じるならその記録である。書くことは次のとおり。

- 未チェックの7行の扱い。オーナーの失敗の認定（incident-2.md）で取りやめたこと、行き先の B-795 を書く。
- `pause-cycle` の印を外す根拠（オーナーの許可）。
- `completed_at` の記入。
- main への手順のコミット。B-754 の行を rollout-plan.md を指す形にし、`cycle-kickoff`・`cycle-completion` を同じ中身にする。

### A-3. テーマの切替の記事が、出荷すると無いボタンを案内する【中】

`src/blog/content/2026-02-21-dark-mode-toggle.md` は、「ヘッダー右側に、新しいボタンが増えていることにお気づきでしょうか」と来訪者にボタンを案内している。design-rollout では `ThemeToggle`・`ThemeProvider` が無い（T1 で置かないと決めた。B-597）。出荷すると、記事が画面と食い違って来訪者を誤らせる。計画がゲームの記事2本を出荷の前に直す理由と同じことが、この記事にも当てはまる。

サイトには先例もある。撤去した検索機能の記事（`2026-02-21-site-search-feature.md`）には、冒頭に「追記: この機能は現在は撤去済み」の1文が置かれている。同じ形の追記なら1文で済む。

**直し**: タスク2に、この記事の冒頭への追記を加える。`2026-05-30-playwright-dark-mode-screenshot-next-themes.md` も、「このサイトは next-themes を…使っている」と現在形で書いている。開発の記録なので、同じ追記で足りるかを一緒に決める。

### A-4. 知識クイズの最後の「次へ」の2打目が、結果を読ませずにほかのページへ移る件を確かめていない【中】

cycle-320 の index.md の補足事項（118行）と t5a-measure.md 5-3 には、次の記録がある。

- 375×800 の kanji-level・kotowaza-level・yoji-level で、最後の「次へ」の2打目が、結果の画面のおすすめのリンクに落ちた。来訪者は結果を読まないまま別のページへ移った。
- 回数は、T5a の前の版で 32/150、cycle-320 の変更後の版で 24 走査のうち2走査である。
- いまの HEAD の着地（`revealLanding` で結果のボックスへ送る）で起きている件で、本番より悪いかどうかは測られていない。

起きれば「結果の画面を受け取れない」という害なので、決め方の上で確かめる対象になる。A-1 の同じスクリプトに組を足すだけで、手間は小さい。

**直し**: 375×800 のこの3本の最後の「次へ」の二度押し（タッチ 90ms・300ms）を、A-1 と同じく本番と比べる。本番より悪い組があれば、結果への送りを本番と同じ `scrollIntoView` の形に戻すことを退き方とする。

### A-5. 出荷のサイクルでブログを書くかが決まっていない【中】

`cycle-completion` の手順2は、来訪者が興味を持ちそうな変更をしたなら、完了の前に記事があることを確かめるよう求めている。サイト全体のデザインの刷新は、これに当たりうる。この計画では、完了の処理が出荷そのものなので、ここで記事の執筆とレビューを始めると、その分だけ出荷が遅れる。

**直し**: 計画に、ブログをどう扱うかを1行で決めて書く。例: 出荷の前には書かず、出荷のあとに B-797 か新しい行で、読者に届いた変化とあわせて判断する。

## B. それ以外（軽いもの）

1. **DESIGN.md との食い違い**: タスク2で直すかもしれないものが2つある。1つは、選択肢の字をブラウザの既定の改行に戻すこと。DESIGN.md §4 は、ボタンの面の字を「見出しと同じ規則で折る」と定めている。もう1つは、「はじめる」のあとに送らないこと。§8 は「「はじめる」を押したとき…問のまとまりを見せる」と定めている。直したら、当たる節を実装と同じ中身に直すことを、計画に書く。直さないままだと、正本と実装が食い違ったまま出荷される。また B-795 の担当とレビューが、古い正本を見て元へ戻しうる。直したことは、B-795・B-614 の行にも書く。
2. **index.md の古い指し先**（前回の 4-2-2 の残り）:
   - 32行「次のサイクルへの申し送りを書く（T5a-7 の残り…）」

   これらは、15行・carryover.md の「次のサイクルは rollout-plan.md だけ」と食い違う。A-2 の閉じ方とあわせて直す。

3. **ADR009**（前回の 4-2-4 の残り）:
   - 20・23行が、無くなった「T10」を、22行が「T9」を指している。B-801・B-799 に直す。
   - ADR009 のディレクトリの日付は 2026-10-23 のままである。出荷のサイクルのキックオフ（手順2）では、延ばす記録が1つ要る。

4. **B-754 を Done にする時**: backlog は「出荷し本番で確かめたらDone」としている。計画は「完了のコミットで…Done にする」で、本番の確かめより前になる。どちらかにそろえる。
5. **戻したあとの出し直しの順**: 計画は「ロールバックを解いて（promote）から、直したものを main へ push」としている。この順では、promote する版を選ぶ段で、壊れた版を出し直すか、意味の無い promote が1つ挟まる。Vercel の文書では、戻しのあいだも main への push はデプロイを作り、本番に上がらないだけである。直したものを先に push し、そのデプロイを確かめてから promote する順に書き直す。
6. **本番の確かめの記録の置き場**: 確かめた結果をどこに書き、いつ main へ push するかが書かれていない。確かめのあとに記録のコミットを push する、と1文で書く（前回 2-1 の末尾）。
7. **Lighthouse の入れ方**（前回 2-8 の残り）: `./tmp/` に版を決めて入れ、2つの版を同じものとブラウザで測る、と書く。
