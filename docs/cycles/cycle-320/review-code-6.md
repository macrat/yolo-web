## 指摘

### 指摘1（来訪者に届くもの・中）: 番号で結べない `click`（WebKit の形・番号を持たない形）では、同じ点に残った互換の事象を出さないタップに起点が移り、「はじめる」の二度押しの2打目が1問目に答えを入れる

`compatPairOf` は、番号で結べない `click` を、32px の中の押しのうち受ける押しのいちばん古いものに結ぶ。互換の事象を出さないタップ（決めごとが見込む iOS の Safari の押せない字へのタップ）が、離してから 1 秒のうちに同じ点に残っていると、その次の「はじめる」の押しの `click` はそのタップに結ばれる。すると守りの起点が、「はじめる」の押しでなく、それより前のタップになる。

再現（`tmp/review320c6/mut/src/play/quiz/__tests__/probe6.test.ts`。`createPressGuard` を、「はじめる」の click で `open("start", lastAcceptedClick().press)` を呼ぶ形で付けた）:

1. 押せない字に (100, 500) でタップ（0〜50、互換の事象なし）。
2. 同じ点の「はじめる」をタップ（900〜950。`mousedown`・`click` は番号を持たない形か WebKit の形）。`click` は 1 のタップに結ばれ、起点の押し下げは 0 になる。
3. 「はじめる」の押しから 250ms の2打目（1150〜1200、(100, 520)、1問目の選択肢の上）。起点から 1150ms なので窓の外とされ、`click` は止まらない（2つの形のどちらでも、期待した `clickPrevented: true` が false）。

起点が `g` ms 前に移ると、窓は「はじめる」の押しから 700 − `g` ms で閉じる（推論。2のあと並びに残った「はじめる」の押しは、守りを開く時に `g` < 700 なら受けない押しになり、`g` ≥ 700 なら受ける押しのまま残る。2打目の押し下げが起点から 700ms 以上なら2打目は受ける押しで、受ける押しを先に選ぶので、2打目の `click` は、前者では2打目に、後者では残った「はじめる」の押しに結ばれ、どちらでも通る。再現の 3 は後者）。指の二度押しの間合いを 100〜250ms とすると、同じ点のタップから「はじめる」までが 450〜600ms を超えれば守りが効かない。

来訪者への影響: 守りが塞ぐはずの「まだ読んでいない1問目に答えが入る」がそのまま起きる。当たるのは番号で結べない形の `click` を出すブラウザで、決めごとが見込むのは iOS の Safari（WebKit Bug 282988 の形と、それより前の番号を持たない形）である。字を触ってから（たとえば送りの惰性を止めるタップのあと）1 秒のうちに、その 32px の中の「はじめる」を二度押しした来訪者に起きる。起きる回は多くないが、iPhone の来訪者は多い。knowledge §9 のとおり、iOS の Safari が押せない字へのタップに互換の事象を出さないかはいまの版で確かめていないので、起きるかの最後の判断はその確かめに掛かる。それでも決めごとは、そうしたタップがあるとみなして点の絞りと「受ける押しを先に選ぶ」を置いており、その見込みの中でこの経路は塞がっていない。

決めごとの「同じ点に残ったその押しとは点でも見分けられないので、受ける押しを先に選び、迷ったら来訪者の押しを止めない側に倒す」は、迷った `click` そのものを止めないことの理由としては正しい。ただ、迷って結んだ押しが守りの起点になると、起点が前に移り、そのあとの二度押しの2打目を通す。止めない側に倒したつもりが、来訪者を読んでいない問へ連れていく側に倒れる。決めごとはこの帰結を扱っていない。

直し方の案（どれも、確かめてから選ぶこと）:

- 離したあとに互換の事象を出す押し（タッチと hover を持たないペン）で、互換の事象を待ち続ける長さを、離してから次の押しの押し下げまでで絞る。knowledge §9 の Chromium の実測では、速い二度押しでも1打目の互換の事象は2打目の押し下げのすぐあとに届く。互換の事象を受けないまま次の押しの押し下げまで長く空いた押し（たとえば `TOUCH_CONSECUTIVE_MS` 以上）は、もう互換の事象を受けないものとして外す。iOS の Safari の互換の事象の遅れは確かめられていないので、その幅の見込みを文書に書く。
- 結んだ押しが、並びのもっと新しい押しより前に離した押しで、その互換の事象の時刻が自分の離しから長く空いている（新しい押しの離しには近い）ときは、新しい押しに結ぶ。
- 起点を選ぶときに、結んだ押しでなく、`click` の点の近くで離したいちばん新しい押しを使う（起点が後ろへ移る誤りは、窓を少し長くする向きにしか倒れない）。

どれを採るにしても、上の再現を試験に入れ、番号で結べない2つの形で落ちて直したら通ることを確かめること。決めごとを変えるので、decision-landing.md 1「押しの単位」、t5a-design.md 4-9 と 5章の写し、SKILL.md の「押しと `mousedown`・`click` の結び方」、knowledge §9 の「`click` を受けない押し」と、pressGuard.ts の `compatPairOf` と `hasStoppedWaiting` のコメントも同じ中身に直すこと。

## 指摘にしないが書いておくこと

- 押し直しを数えるとき、受けた側の押せるものは押し下げの的から取り（`noteAccepted` の `accepted.target`）、止めた側は止めた事象の的から取る。タッチの調整で押し下げの的が `click` の的と違えば、押し直しを数え損なう。ただ、上の実ブラウザの試しでは、Chromium は `pointerdown` の的もボタンに寄せた。WebKit では確かめていない。指摘1 を直すついでに、受けた側も `click` の的から取る形にそろえると、両側が同じ決まりになり、ブラウザの寄せ方に頼らない（来訪者の目に見えるふるまいは変わらない）。
- 変異 5c（`click` の番号を `pointerType` を見ずに使う）は、試験を消しても落ちない。型の違う同じ番号の押しが並びにあるのは、マウスを押し下げたまま画面に触れるような組み合わせだけで、ブラウザの実際の事象の順では組めない。試験を足すことは求めない。
- `chooseTouchClearLanding` の基準が送らない枝の `isClear(0) ? 0 : nearestClear` は、前回書いたとおり `nearestClear` と同じ値になる。ふるまいは変わらない（軽いもの）。
- 着地の送りの量は、A″ のとおり前より大きくなることがある（試験の 375 相当の組で、−21 から +85 へ）。決めごとの範囲の中で、来訪者の目に「送りが大きくなった」と出る所なので、T5a-7 の測りで操作ごとの量を見ること（決めごとどおりで、指摘にはしない）。
