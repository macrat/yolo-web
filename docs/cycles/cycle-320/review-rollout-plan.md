## 結論

**改善指示（要修正）**。骨組み（CI・本番との並べ比べ・速さ・基線・出荷）は正しく、大きく削った方針も妥当である。ただし、記録にすでにある「出荷すると本番より悪くなる所」が計画に名前で入っておらず、タスク2のふつうの通し操作では見つからないものがある。また、「出荷のあとに回したもの」に出荷の前に要るものが3つ紛れている。どれも小さい作業で、出荷を大きく遅らせずに足せる。

## 2. 抜けているもの（無いと本番より悪くなる、または出荷できない）

### A. 診断のプレイ面（閲覧の約8割）について記録にある悪化が、タスク2に名前で入っていない【重要】

`design-rollout` は cycle-319 が終わったときの状態にある（36be6b9a が cycle-320 の T5a-4・`pressGuard.ts`・区切りの直しを戻した）。cycle-319 のキャリーオーバーには、その状態の悪化が2つ書いてある。

1. **選択肢の字の折れ**: 選択肢の字が区切られずに `Button` に渡り、文全体が1つの文節として `keep-all` と `overflow-wrap: anywhere` で組まれる。そのため、375・320 で1字の行（「描／く」）と、行頭の閉じ括弧（「」を思い返し」）が出る。本番の `QuestionCard.module.css` は折り方を変えていないので、ブラウザの既定の禁則で組まれ、行頭の閉じ括弧は出ない。character-personality の回答画面で、本番より字の組みが悪くなる。
2. **「はじめる」の二度押し**: 375×550 で「はじめる」の2打目が1問目の選択肢に落ち、読んでいない問に答えが入る。これが起きるのは character-personality・word-sense-personality・music-personality・character-fortune の4本で、どれも 90ms と 300ms の2打目で起きる。T5a の前の基準の版では、character-personality の2打目は問の見出しの字に落ちていた（t5a-measure.md 5-1）。答えが入れば結果がその人の答えでなくなるので、診断の価値そのものが崩れる。

どちらも、タスク2の「開始・回答・結果まで通して比べる」を目で行うだけでは見つけにくい（1 は 320・375 の幅に依り、2 は速い二度押しでしか起きない）。そこで、タスク2に次を書き足す。

- 本番と `design-rollout` の character-personality を並べ、375×550 と 320×550 で、全12問の選択肢の折れを比べる（行頭の約物と1字の行）。
- 同じ2つの版で、「はじめる」・答え→次の問・最後の答えを、タッチで 90ms と 300ms の間隔で二度押しして、2打目が何に落ちたかを比べる。この比べは character-personality だけでよい。T5a-7 の全15本×6画面の測りはしない。
- 本番より悪ければ直す。直し方の候補を計画に書いておく。1 の直しは、cycle-320 で一度レビューを通した T5a-4 の区切りの部分である。ただしオーナーは cycle-320 の変更を戻しているので、それを採るかは PM がオーナーの意図と照らして決める。2 の直しは「はじめる」の着地の最小の直しである。

本番の側も、B-620（答えの二重発火で1問飛ぶ）を抱えている。悪くなったかどうかは操作ごとに比べて決め、全体として良くなっていても、個々の操作の悪化は見落とさない。

### B. ゲームの判定を色で説明するブログ記事が、出荷した時点で誤りになる【重要】

`design-rollout` のゲームは、判定を色でなく印（◯△×。`src/play/games/kanji-kanaru/_lib/marks.ts`）で示す。一方、`src/blog/content/2026-02-14-japanese-word-puzzle-games-guide.md` は「緑（一致）、黄（近い）」「黄色フィードバックを大切にする」などと、色で遊び方を説明している。この記事はゲームのページの関連記事に出る（carryover-tasks.md の T7）。出荷すると、遊び方の案内が画面と食い違い、来訪者が本番より悪いもの（誤った説明）を受け取る。T7 は丸ごと出荷のあとに回されているが、この直しだけは出荷の前に要る。

色の語を含む記事は、ほかに `2026-02-15-yojijukugo-learning-guide.md` などがある。出荷の前に、ゲームと遊びの面について色で判定を説明している記事を grep で洗い出し、直す。

テーマの切替をいまあるものとして書いた技術記事2本（`2026-05-30-playwright-dark-mode-screenshot-next-themes.md`・`2026-05-05-nextjs-global-not-found-for-multiple-root-layouts.md`）も、出荷で事実と違う記述になる。ただし、日付のある実装の記録として読まれる記事なので、出荷のあとに回してもよい。どちらにするかは計画に書く。

### C. レビューを通っていないコードが、そのまま出荷される

decisions-t1-t3.md の30行目に、T3 の完了の判定のレビューを2巡目で止めたことと、そのあと builder が直したページ送りの番号の箱の幅（b5ee51a。`src/components/Pagination/` の3ファイル・約60行）はレビューを受けておらず、T11 で確かめると書いてある。builder が直した `DESIGN.md` の言い方（T3-3・T3-4・T3-6・T3-8・T3-9）も同じである。計画は T11 のうち「文書の参照の置き換え」だけを出荷のあとに回し、この確かめはどこにも書いていない。出荷すると、レビューを受けていないコードが本番に出る。「すべての作業はレビューを受ける」の決まりに当たる。

b5ee51a の差分（と `DESIGN.md` の該当の文）のレビューを、出荷の前のタスクに足す。量は小さい。見るのは、文字サイズ 200% で「前へ」「次へ」の位置が動かないことと、見えない中身として置いた総ページ数の番号を読み上げが読まないことである。

### D. OGP 画像の確かめが、T12 から落ちている

T12 には「本番での OGP のカード表示」があったが、タスク5には無い。`design-rollout` では T6-1〜T6-3・T6-9 で画像の作り（`share-image.tsx`・Route Handler の `opengraph-image/route.tsx`・`ogp-image.tsx` の書き直し。57ファイル）が大きく変わっている。一方で、残りの面（T6-4 以降）は古い描き方のままである。画像が 404 や 500 を返せば SNS のカードが空になり、本番より悪くなる。次を足す。

- タスク2で、本番のビルドの代表のページ（トップ・一覧・道具・診断のプレイ面と結果・ゲーム・辞典の詳細の各種・ブログの記事）の `og:image` の URL が 200 の PNG を返すことを確かめる。
- タスク5で、本番の同じページを確かめる。

### E. 出荷のあとに壊れていたときの決め方が無い

T12 にあった「壊れていたら、全面を戻すか直して出し直すかを決める」が、タスク5から落ちている。1129コミット分の差を一度に出すので、本番で何をもって戻すのか（例: 診断のプレイ面が開始・回答・結果まで通らない、ビルドや配信が失敗する）と、戻す手順（main のマージのコミットを revert して push）を、タスク5に1行で書いておく。

### F. タスク3に CLS を入れる

completion-criteria.md の速さの条件には、LCP のほかに CLS（変更後の中央値が変更前を上回ったら直す）があった。今回の刷新で Web フォントを足しており、読み込みのずれ（CLS）はその典型の悪化である。CLS は同じ5回の計測で一緒に取れるので、手間は増えない。Web フォントの転送量の記録（見込みの +85KiB を超えたら原因を調べる）も、同じ計測で取れる。

### G. 「backlog に移した」が、まだ行われていない

計画は、残りのタスクを `docs/backlog.md` に「移した」と書いている。しかし、主の木の `docs/backlog.md` には差分が無い（`git diff HEAD` が空）。また、B-614・B-624・B-623・B-641・B-644・B-649・B-650・B-755・B-621・B-788・B-789 の行は、どれも「design-rollout の T○ のサイクル」を着手の条件にしたままである。計画を確定する前に、次を行う。

- backlog を実際に書き換える。
- B-754 の行を、出荷で何を Done にし、何を残すかの形に直す。
- completion-criteria.md（「全ページが DESIGN.md §1〜§12 を満たす」を B-754 の完了の条件にしている）を、出荷の条件として使わないことを計画に書く。書いておかないと、後のサイクルがこの条件で出荷を止めうる。

cycle-320 で起票し、36be6b9a の戻しで消えた B-793（表のセルで語の中に折り所が残る）も、`design-rollout` の表に残る事実であれば、出荷のあとの項目として起票し直す。B-794 は T5a-4 の区切りに結びつく項目なので、A の1の扱いとあわせて決める。

## 3. 「出荷のあとに回したもの」の分け方

出荷の前に要るものが紛れているのは、次の3つである。

- **T5a-4**: 区切りの部分は、A の1の悪化を消す直しそのものである。丸ごと回さず、A の比べの結果で、出荷の前に要るかを決める。根の `touch-action` の部分は、本番にも無いので出荷のあとでよい。
- **T7**: ゲームの判定を色で説明する記事の直し（B）は、出荷の前に要る。ほかの T7 の項目は出荷のあとでよい。T7 のうちゲームの最初の読み込みに失敗したときに出る英語の文は、本番にもあるので悪化ではない。
- **T11**: レビューを通っていない b5ee51a と、builder が直した `DESIGN.md` の文の確かめ（C）は、出荷の前に要る。計画の一覧は T11 のうち文書の参照の置き換えだけを挙げており、この確かめはどこにも行き先が無い。

ほかは出荷のあとでよい。

- T5 の各面: 古いトークンの定義が `globals.css` に残っている。ページの CSS が参照する変数で定義の無いものを数えると、インラインの style や `next/font` が渡すもののほかには無かった。ただし、表示が壊れていないことはタスク2で確かめる。
- T6 の残り: 古い描き方の画像は本番と同じである。D の配信の確かめだけは要る。
- T8・T9: 出荷のあとでよい。
- T10 の残り: 出荷の日から計測の出方が変わるもの（目次の `toc_*`、410 の page_view、`surface="fuda"` の広がりなど）を ADR009 に書くことと、Search Console の Core Web Vitals の実地の値を B-758 に渡すことは、出荷の前に要らない。ただし、ADR009 の読み始め（+2週）より前に要るので、行き先として一覧に入れておく。Core Web Vitals の値は、レポートの期間（約3か月）のうちに取る。

T5-6 と T5-13 の途中の作業を持つ `design-rollout-wip`（origin に残っている）の扱いも、一覧に1行で書いておく。出荷されないので、出荷の前の作業ではない。

## 4. 小さい指摘

- タスク2のモバイルの幅を決めておく。A のとおり、悪化は 320・375 で出る。375×550 と 320×550 を入れる。
- character-personality の並べ比べの見方は、completion-criteria.md の5つの観点を流用すると、判定が個人の好みにぶれない。5つの観点は、開始ボタンがファーストビューに入るか、回答中に選択肢がすべて見えるか、押した選択肢が即座に選択状態として見えるか、結果が楽しいか、保存や共有をしたくなるかである。
- タスク5の「`design-rollout` を origin から消す」の前に、`cycle-completion` の手順7の最後のサイクルの処理を行うと書いておく。処理の中身は、`deploy.yml` の `on.push.branches` と backlog から統合のブランチの名前を外すことである。
