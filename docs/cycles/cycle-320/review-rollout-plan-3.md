## 2. 抜け・計画どおりに実行できない所

### 2-1. タスク5・6が `cycle-completion` の手順と両立しない【重要】

計画の書き方は次のとおりである。

- タスク5は、出荷を `cycle-completion` の手順7（最後のサイクル）の「完了のコミットを作り、main へ push」で行う。
- そのあと、同じサイクルの中で次を行う: 本番での確かめ、壊れていたときの Instant Rollback と出し直し、タスク6、B-754 を Done にすること。

ところが `cycle-completion` は、完了のコミットを作る前に次のことを求めている。

- 手順1: 全タスクのチェックと `completed_at` の記入
- サイクルの終了時のチェックリスト: Active に未完了が無いこと
- 手順5: アンチパターンの点検

一方、計画では B-754 の Done の条件をタスク6に置いている。そのため、完了のコミットの時点ではタスク5の後半とタスク6が終わっておらず、B-754 は Active のまま残る。手順1で止まり、出荷のための完了のコミットを作れない。チェックを入れて先に進めば、終わっていないタスクにチェックを入れることになる（AP-WF23）。

**直し**: 次のどちらかに決めて、計画に書く。

- (a) 出荷を、サイクルの途中のタスクとして行う。このタスクでは、`deploy.yml` と backlog から統合のブランチの名前を外すコミットを作り、`git merge origin/main` と `git push origin HEAD:main` を行い、CI と Vercel の本番のデプロイを確かめる。そのあと本番で確かめ、`design-rollout` を消す。以降は作業ブランチを main に切り替えて、タスク6を行い、ふつうの `cycle-completion`（main）で完了する。`cycle-completion` の手順7の「最後のサイクル」と順が違うので、違いを計画に1文で書く。
- (b) 出荷をサイクルの完了で行う。その場合は、B-754 の Done の条件を「出荷し、本番で確かめた」までにする。タスク6は、期限（出荷+2週より前）を書いた backlog の1行に出す。本番での確かめと戻し方は、手順8（CI の確認）のあと、同じセッションの中で行うと書く。

どちらを選んでも、出荷のあとにサイクルの記録を main に push すると本番のデプロイが1つ増え、Instant Rollback で戻れる先が新しいデザインの版になる。そのため、「確かめ終えるまで main に push しない」と並べて、記録のコミットは確かめのあとに push すると書く。

### 2-2. 二度押しの直しに、直し方の目安と退き方が無い【重要】

計画は、2打目が読んでいない問に答えを入れるなら、「選択肢を画面に入れるためのスクロールは保ったまま、2打目が答えにならないように直す」としている。

- cycle-320 の補足事項によれば、375×550 の character-personality など4本は (2) の型である。(2) の型とは、送りの範囲の中に、両方の組（「はじめる」の点の真下と選択肢）を外す送りがそもそも無いものをいう。つまり、スクロールの量の選び方だけでは避けられない。
- 残る直し方は、送りのあとしばらく押しを受けない、といった守りの形になる。しかし、carryover-tasks.md の T5a の制約（「時間の窓で回答を黙って捨てない」。B-620 と cycle-301 の取り消しの教訓）にぶつかる。cycle-320 は、まさにこの着地の作りの決め直しで、測りの道具とレビューが膨らんで失敗した。
- 計画は、cycle-320 の decision-landing.md・plan-t5a7.md・`measure/` を使わないとしている（carryover.md）。そのうえで、直し方の目安を何も示していない。次のサイクルは、ゼロから同じ設計に入ることになる。

**直し**: 計画に次の3つを書く。

1. 最小の直しの候補を1つ書く。例えば、「はじめる」から1問目へ移ったあとの短い間だけ、1問目の選択肢に入った押しを答えにせず、受けなかったことが見える形にする。この候補が T5a の制約と両立するかは、計画の段階で1行で決めておく。最初の問を読む前に答える来訪者はいないので、黙って捨てる窓の害（B-620）とは種類が違う、と言えるかどうか。
2. 退き方を書く。候補が通らないときは、「はじめる」では送らない。そうすれば、1問目の画面は本番と同じ程度になり、本番より悪くはならない。2問目からの送りは保つ。退いたあとも2打目が選択肢に落ちないことを、同じ二度押しで確かめる。
3. 直したあとの確かめの範囲を書く。cycle-319 の4本の 375×550 に加えて、cycle-320 の試しの走りで記録がある character-personality の 1280×800（(1) の型）と、200% の12本でも、本番の版と比べる。どちらも、いまの HEAD に残る T5a-6 の着地の作りで起きた件で、戻した T5a-4 の有無には依らない。道具は `measure/` を使わず、タッチの二度押しを送る小さなスクリプトでよい。

### 2-3. T4-5 の向きが逆に書かれている【重要（事実の誤り）】

「決め方」の段落は、意図した変更の例として「T4-5 で保存と共有のボタンを最初の画面に出したこと」を挙げている。しかし、事実は逆である。

- ADR009 には「保存と共有のボタンが 375px の最初の画面から出た」とある。
- review-t4-21.md には「T4-5 で保存のボタンを最初の画面から出した損」とある。

T4-5 は、結果の説明を先に置き、ボタンを最初の画面の外へ移した。

このままだと、タスク2で結果の画面を比べる人が、ボタンが最初の画面に無いのを見て「T4-5 の意図から外れた悪化」と取り、上へ戻しうる。そうなると、意図した設計が取り消され、ADR009 が見張る比べも壊れる。「最初の画面の外へ移したこと」に直す。

### 2-4. Instant Rollback のあとの出し直しの手順が無い

Vercel の Instant Rollback をすると、本番のドメインの自動の割り当てが止まる。そのあと直したものを main に push しても、本番に出ない（[Vercel Instant Rollback](https://vercel.com/docs/instant-rollback)）。計画は「直してから出し直す」とだけ書いている。このままでは、出し直したつもりで本番が古い版のまま残りうる。出し直すときは、新しいデプロイを本番に上げる（promote）か、戻しを解く操作が要ることを1文で書く。

### 2-5. GA で確かめる数を名前で書く

タスク5の「GA に page_view などの数が届いている」の「など」を、名前に置き換える。ADR009 が出荷の日からの28日で比べる数は `level_start`・`level_end`・`share`・`save` で、これらは出荷のあとに欠けると取り戻せない。`analytics.ts` と `google-analytics.ts`、410 のページの差し込みも変わっている。名前を挙げないと、page_view だけを見て済ませうる。

### 2-6. 選択肢の改行の直しの範囲を限る

「本番と同じブラウザの既定の改行に戻す」には、どこを直すかが書かれていない。

- 折れの原因は `PhrasedText`（`keep-all`・`overflow-wrap: anywhere`・`line-break: strict`）である。これはボタン・見出し・表のセルなど、サイト全体で共通に使われている。
- `PhrasedText` そのものを直すと、DESIGN.md §4 どおりに組めているほかの面まで変わる。

直す所は、`QuestionCard` の選択肢の面に限ると書く。選択肢の面は、押す前の `Button` と、押したあとの2つの `span` の両方である。確かめも、押す前と押したあとの両方の折れを見る（cycle-319 の記録は「押す前と押したあとで同じ折れ」）。

### 2-7. 機械の URL の確かめに、title・description・構造化データの差の一覧を足す（中くらい）

`seo.ts` などの差で、パンくずの JSON-LD の形とメタデータの組み方が変わっている。すでに sitemap の全 URL を引くスクリプトなので、各ページの `<title>`・meta description・JSON-LD の `@type` の並びを本番と比べ、違うものを一覧に出すのは小さな足し算である。直すのは、空になった・消えたといった、意図しない欠けだけにする。意図した文言の変更は直さない。検索から来る来訪者の入口が本番より悪くなっていないことを、canonical・robots だけでなく、ここまで見ておく。

### 2-8. 軽いもの（来訪者に届くが小さい・手順の明確さ）

- **404 は2種類ある**: どのルートにも一致しない URL と、ページの中の `notFound()`（例 `/dictionary/kanji/zz`）である。design-rollout では `global-not-found.js` を外して `not-found.tsx` に寄せているので、両方を開き、HTTP の 404 が返ることも確かめると書く。
- **「PC」の大きさを決める**: 1280×800 など（前回の指摘 2-7 の残り）。
- **タスク5で Vercel のデプロイを確かめる**: GitHub の CI は Vercel へのデプロイをしない（`deploy.yml` は検査だけ）。CI のあとに、Vercel の本番のデプロイが Ready で、本番のドメインに割り当たったことを確かめる、と書く。
- **Lighthouse の入れ方を書く**: Lighthouse は `node_modules` に無く、facts-speed-before.md の `./tmp/lh` も残っていない。`./tmp/` に版を決めて入れ、2つの版を同じものとブラウザで測る、と書く（軽い）。
