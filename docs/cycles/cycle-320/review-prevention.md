## 指摘

### 1. AP-WF01 が「記録の直しはもう一度のレビューを受けない」と食い違う（(a) を打ち消す）

`docs/anti-patterns/workflow.md` の AP-WF01 は、いまも「最後の修正のあと、**それがどんな修正であったとしても**レビューを実施したか？」と問う。完了の処理の手順5では、reviewer がこの workflow.md を読んで点検する。PM が新しい決まりのとおり記録を直して閉じると、点検の reviewer は AP-WF01 に当たると指摘できる。その指摘は「プロダクトの問題」とも「記録の誤り」とも読めるので、点検がもう1巡起きる。incident-1 の「止まる所が無い」の組み合わせが、別の入口から戻ってくる。

- 直す向き: AP-WF01 の問いを新しい決まりと同じ範囲にそろえる。来訪者に届くものと後の作業が従う中身を変えた修正は、どんな小さな修正でも最後にレビューを受ける。記録だけの直しは、PM が直して閉じる。そう読める1つの問いに書き直す（例外の注記を足すのではなく、問いそのものを書き直す）。あわせて reviewer.md の末尾の「すべての作業は必ずレビューを受ける。省略を認めない」が、記録の直しを閉じることと食い違って読めないかも確かめる。指摘を受けて記録を直すことはそのレビューを閉じる作業で、新しい作業ではない、と読める形にする。

### 2. 指摘の分け方の軸がファイルごとに違い、記録の外の内部文書で巡りが残る。コードのレビューを弱める読み方もできる（(a)(c) と、弱める側の懸念）

reviewer.md・kickoff 手順8の前段・CLAUDE.md・テンプレートは、**ものの種類**で分けている。「来訪者に届くもの（コード・見た目・記事）」「後の作業が従うもの（計画・設計・申し送り）」は、指摘が1つでもあれば全体を見直す。「サイクルの記録」は PM が直して終える。一方、kickoff 手順8の3回の決まりは、**直しの効き目**で分けている。「来訪者に届くものも、後の作業が従う中身も変えない修正」が数える対象である。この2つの軸のずれから、次の3つが出る。

- **分類の抜け**: 測りの道具・試験・スクリプト・hook・スキル・`.claude/rules/`・`docs/knowledge/`・アンチパターン集の本文（「実際に発生」の並びではない所）が、どちらの括弧にも入っていない。incident-1 の巡りの大きな所（道具 20回・knowledge 10回・アンチパターン集の更新 8回）は、まさにここで起きた。incident-1 自身も、再発防止の直しを「後の作業が従う**手順**なので」1度通すと書いている。ところが括弧の中に「手順」は無い。
- **申し送り・計画の言い回しの巡りが残る**: carryover.md や plan-t5a7.md は「申し送り」「計画」に入る。reviewer.md は、言い回しの直し1つでも「全体の見直しを含めてもう一度レビュー」を求める。incident-1 の全体のレビューの後半は、こうした申し送りの書き方の直しを含んでいた（7b0b6de1「送った仕事の書き方をそろえる」など）。この巡りは、3回の決まりでしか止まらない。そして3回で止めると、テンプレートの「後の作業が従うものへの指摘が残っていない」と、kickoff の「有効な指摘事項が残っている状態でサイクルを完了させることはできません」を満たせない。PM は、巡りを続けるか、残っている指摘を見ないふりをしてチェックを入れるかの二択に追い込まれる。後者は AP-WF23 そのものである。
- **コードを弱める読み方**: 3回の決まりの定義は「来訪者に届くものを変えない修正」である。コードのコメント・名前・試験の書き方・中の作りの直しは、来訪者に届く出力を変えない。字のうえでは、この定義に入る。コードのレビューでこうした指摘が3回続けば、「手を止めて次へ」と読める。AP-WF39（巡の数で品質のレビューを止めない）と食い違い、保守のしやすさの欠けを残したまま出荷する道になる。

直す向き: 分け方を1つの軸で1か所に定め、ほかのファイルはそれを指すか同じ形で言う。案は次のとおり。

1. 来訪者に届くもの（コード・試験を含む `src/` などの出荷物・見た目・記事）は、指摘の大きさを問わず直して、もう一度レビューを受ける。3回の決まりは当てない。
2. 内部の文書と道具（計画・設計・申し送り・スキル・規則・knowledge・アンチパターン集の本文・測りの道具など）は、直すと決めごとやふるまいが変わる指摘なら、直してもう一度レビューを受ける。言い回し・数え方・置き場所だけの指摘は、PM が直して閉じ、もう一度のレビューは受けない。
3. サイクルの記録は、PM が直して閉じる。

3回の決まりは 2 と 3 にだけ当てる。テンプレートの「指摘が残っていない」も、同じ軸の言葉にそろえる。

### 3. 記録だけの指摘のときに、reviewer がどの結論を出すかが決まっていない

reviewer.md は、結論を「承認」か「改善指示」に限る。そのうえで、記録だけの指摘のときは「PM が直して終えるよう伝え、もう一度のレビューは求めない」とする。このとき結論が「改善指示」なのか「承認」なのかが書かれていない。「改善指示」なら、PM は改善指示のまま次へ進むことになり、AP-WF01 や「レビュー結果」の欄の「最終判定」と食い違う。「承認」なら、指摘付きの承認として、条件付き承認と取り違えられうる。どちらでも、PM か点検の reviewer が「承認を得ていない」と読み、巡りが戻る。

- 直す向き: reviewer.md に、記録だけ（指摘2の案なら、2 の言い回しだけと 3 のもの）の指摘しかないときの結論をはっきり書く。たとえば「承認とし、PM が直して閉じるものとして分けて書く。承認はそれらの直しを条件にしない」とする。kickoff 手順8とテンプレートの「レビュー結果」の書き方も、それに合わせる。

### 4. 完了の判定で守る項目の範囲が「最初のコミット」に読め、計画で足した項目と、その場で範囲を狭める書き換えが抜ける（(b) の抜け道）

完了の処理の手順1・kickoff 手順7・テンプレートの新しい行・AP-WF23 は、守る項目を「キックオフでコミットした『実施する作業』」と呼ぶ。手順1のコマンドの注記は、それを「index.md の最初のコミット」と定めている。cycle-320 で走らせると、最初のコミット（7744a5b0）の一覧には T5a-8 が無い。それどころか、条件7・D5 の測りを「次のサイクルへの申し送り」とする項目が、すでに入っている。incident-1 が「キックオフの作業の一覧」と呼ぶ 334eea0d は、計画のレビュー第1回のあとのコミットである。事故で消えた T5a-8a などは、字のうえでは「キックオフの項目」ではない。2つ目のコマンドは消えた行をすべて拾うが、判定の文は「キックオフの項目を一覧から外した…なら完了していない」のままである。PM は「T5a-8a は計画で足したので、キックオフの項目ではない」と読める。

また、項目を消さずに、その場で中身を狭める書き換えも残っている（例: 「直してレビューに通す」を「直し方を決めてレビューに通す」にする）。この書き換えは消えた行として出る。それでも、「同じ作業が今の一覧に残り」の判定は PM の読みに任されている。「外す・送る・置き換える」の3つの名指しにも、「狭める」は入っていない。

- 直す向き: 守る範囲を「サイクルのあいだに一度でも『実施する作業』に載った項目すべて（キックオフ・計画・途中で足したもの）」と定め、両スキル・テンプレート・AP-WF23 で同じ言い方にする。禁じる形に「項目の中身を狭める書き換え（来訪者に届く所まで行かない形にする）」を足す。手順1の判定は、消えた行と、それに当たる今の行を並べて、来訪者に届く所までが同じかを見る文にする。

### 5. 3回の決まりがキックオフ手順8の中にしか無く、数え方の単位があいまい（(c)）

3回の決まりは、kickoff の「8. レビューの実施」の節にだけある。cycle-completion の手順5（点検の指摘からアンチパターン集の本文やスキルを直す）でも、手順2（ブログ）でも、同じ巡りは起きうる。incident-1 の「アンチパターン集の更新 8回」は、完了の処理の中で起きた。決まりの「次の作業」は「残っていなければ `/cycle-completion`」と書かれており、完了の処理の中にいるときに何へ進むのかが読めない。また「修正が続いた数」が、1回のレビューの指摘への直しをまとめて1回と数えるのか、指摘1件ずつを数えるのかが決まっていない。1件ずつと読めば、1回のレビューで出た記録の指摘3件で止まる。まとめて1回と読めば、巡りを3つまで許す。

- 直す向き: 3回の決まりを、サイクルのどの段にも効く場所（kickoff の手順8の外の、サイクル全体に効く節など）に置くか、cycle-completion の手順5からも指す。完了の処理の中で止めたときの「次」（完了手続きの次の手順へ進む）を書く。数える単位は「レビュー1回とそれへの直し」を1回と定める。

### 6. このセッションの PM と reviewer は、まだ古い定義で動いている

直した CLAUDE.md と `.claude/agents/reviewer.md` は、セッションの初めに読み込まれる。このレビューを頼まれた reviewer に渡った定義は、直す前の文である（「レビューの究極の目的は、エンドユーザーにとっての価値を最大化することです…どんな問題も見逃さずに」「指摘事項が1つでもある場合は」）。CLAUDE.md の Review always も、直す前の文で読み込まれている。cycle-320 は、このあと着地の作りの決め直しから T5a-8 まで進む。そのあいだ、このセッションで起こす reviewer は、記録の指摘1つでも全体の見直しを求める。そのため (a) は、このサイクルの残りに効かない。

- 直す向き: このセッションでレビューを頼むときは、依頼文に新しい扱い（記録だけの指摘は PM が直して閉じ、もう一度のレビューは求めない。指摘2・3を直したらその形）を書いて渡す。そうしていることを cycle-320 の文書に書いておく。

## 確かめて、問題なしとしたこと

- 完了の点検（手順5）の3分けと、「記録の網羅の照合は頼まない」は、incident-1 の点検11回の巡りを止める形になっている。
- AP-WF23 の追記は、incident-1 の再発防止4と合っている（守る範囲の言い方は指摘4のとおり直す）。
- `stop-cycle-guard.sh` の案内は「作業が残っているなら、続けてください」で始まり、「送れば完了」とは読めない。新しい決まりとも食い違わない。

- 来訪者に届くもののレビューについて、reviewer.md は「どんな問題も見逃さず」を残している。弱める読み方が出るのは、指摘2の3回の決まりの定義の所だけである。
