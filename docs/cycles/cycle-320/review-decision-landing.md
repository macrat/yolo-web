# レビュー: 着地の作りの決め直し（decision-landing.md）

- 対象: docs/cycles/cycle-320/decision-landing.md（主の木 design-rollout、HEAD f4bde082）
- 読んだもの: landing-options.md（とくに 1-1・2-1・2-5・3・4）、cycle-316/t5a-design.md 4-9・6章 条件7・8章、cycle-316/options.md「B-620 を含めない理由」、DESIGN.md §6・§11、docs/knowledge/input-events-and-guards.md（cycle-301 の窓の知見）、src/play/quiz/_components/QuizContainer.tsx・QuestionCard.tsx・ResultCard.tsx の押せるもの、node_modules/next の Link の `defaultPrevented` の扱い
- 結論: **改善指示**

## 良い所

- 方向は筋が通っている。landing-options.md 2-5・3・4 の実測で、送りと組み（A・A′・A″・B・B′・C）では 375×550 の character-personality（型 (2)、範囲の中で最も離せて 0.4px）と 200% が直らないことが示されており、時間で受けない形を、診断の答え→次の問から外して3つの切り替わりに絞るのは、cycle-301 の失敗（全問で 600ms 未満を捨て、速く答える人の答えを日常的に捨てた）の核を避けている。
- 見た目を変えない判断は、DESIGN.md §6（無効は来訪者が揃えられる条件を待つ形。読み込みの待ちを無効で出さない）と §11（動きは3つ、次の操作を待たせない）に合う。
- 試験に「窓のあとの押しは答えを入れる」「診断の答え→次の問の速い押しは答えを入れる」を入れており、空振りでない対（knowledge §2）になっている。

## 指摘（すべて来訪者に届く設計の決めごとで、改善指示の理由になる）

### 1. 守る範囲「新しく出た押せるもの」は、cycle-301 が実測で退けた「領域を絞った窓」と同じ型になる

input-events-and-guards.md §4 は、cycle-301 で intro の領域だけに窓を掛けたところ、窓の外の「X でシェア」と FAQ の `summary` に2打目が落ち、X の投稿画面が開いたことを記録し、「入れ替わったあとの画面で1打目の座標に来る操作要素のすべてを守る範囲にする。特定の領域だけに窓を掛けると、その外に来る操作要素が無防備で残る」と結んでいる。この決定の「新しく出た押せるもの（その問の選択肢・結果の画面のリンクとボタン）」では、切り替わる前からあって位置だけ動いたもの（`QuizContainer` の外のよくある質問の `summary`・関連・フッタ・ヘッダ）が守りから外れる。landing-options.md の測りでは、いまはそこに落ちた回が 0 でも、それは1つの答えの組と押す行2つでの値で（0章の「限り」）、Chromium の寄せる先は道具が集めるものより広い（0章）。

窓の中（2打目の時間）にページのどこかを意図して押すことは、新しく出たものでもそうでないものでも同じく考えにくいので、範囲を絞って得るものが無い。守る範囲を「窓の中に届いたポインタの click すべて（ページのどこでも）」にするか、除くものがあるなら除く理由と、除いたものに2打目が落ちないことの測り方を書くこと。あわせて、「新しく出た」を DOM で何と決めるか（例: 結果の画面の `ResultCard` の中か、あとから差し込まれる `ResultExtraLoader` を含むか）が決まっていないので、実装に渡せない。

### 2. キーボードと読み上げの扱い（窓を開く入力・窓が受ける入力）が決まっていない

input-events-and-guards.md §5 の軸2・軸3 は、cycle-301 の実測で、キーボードで答えたあとの指の押しや、キーボードだけの高速回答が窓に黙って捨てられたことを記録し、「非ポインタが起こした切り替わりでは窓を開けてはならない」「キーボードの click（`detail === 0`）は受ける側でも捨てない」としている。決定はどちらにも触れていない。次を決めること。

- 窓を開くのは、切り替えた押しがポインタの click（`detail >= 1`）だったときだけ。キーボードや読み上げの起動（`element.click()` と同じ合成 click として届く推論。knowledge §3）で切り替えたあとは開かない。
- 窓が受けないのはポインタの click だけで、`detail === 0` の click は通す。
- 診断の最後の答え→結果は、押してから 150ms（`ANSWER_SHOWN_MS`）のタイマーで切り替わる。窓の起点は切り替わりの時刻でなく答えた押しの時刻であること、その押しがポインタだったかで開くかを決めることを書く（起点を切り替わりにすると、窓が押しから 650ms まで伸びる）。

### 3. 時刻の取り方と境目が決まっておらず、測りの間隔 500ms が窓の境目に重なる

- 時刻は、2つの click の `event.timeStamp`（入力が起きた時刻。単調）で比べるのか、受け手が走った時刻（`performance.now()`）で比べるのかを書くこと。遅い端末では、1打目の描画に時間がかかると2打目の受け手が遅れて走るので、受け手の時刻で比べると、実際には 300ms の二度押しが窓の外と判定されうる。`Date.now()` は単調でない（knowledge §6）。
- 「500ms のあいだ」が 500ms ちょうどを含むかが無い。6章 条件7 は「はじめる」と結果への切り替わりを 0・90・150・300・500ms で押し、道具の間隔は指定から ±7ms ずれる（landing-options.md 2-4 の 293〜306ms）。500ms の回は、走りごとに窓の内と外にばらけ、合否が揺れる。窓の長さか条件7 の間隔を、境目から十分離して置き直すこと（例: 窓の中を確かめる回と、窓の外で答えが入ることを確かめる回を、境目から離した間隔に分ける）。

### 4. 理由の「500ms のあとの押しでは、いまの着地の選び方が押した点の真下を避ける」は、最重視の組で事実に反する

landing-options.md 1-1 では、型 (2) の 23/75（375×550 では character-personality を含む4本）は「範囲の中で最も離せて 0〜0.4px」で、いまの着地の選び方は点の真下を避けられない。したがって、500ms を越える2打目（Windows のダブルクリックの既定は 500ms で、来訪者が長く設定できる。手の動きが遅い人の二度押し。押しても変わらないように見えたあとの押し直し）は、閲覧の大半を占める character-personality の 375×550 で、いまも1問目の選択肢に答えを入れる。

決定はこの残りを「着地が受け持つ」と書いて、残りとして扱っていない。t5a-design.md 8章は「件を受け入れる」を「答えを入れるものには選ばない」と決めているので、この残りをどう扱うか（その決まりを覆して受け入れるのか、ほかの手当てを足すのか）を、理由の文を直したうえで決めること。

### 5. A″ を退ける理由が実装の手間になっている

「余白を足す A″ は『はじめる』の 42 件を直すが、……着地の関数を書き換えて測り直す手間に見合わない」は、CLAUDE.md の Decision Making Principle（実装の手間を、来訪者にとって劣る道を選ぶ理由にしない）に反する。landing-options.md 2-1 では、A″ はほかの操作の送りを1回も変えず（1,720 回・150 回・150 回のどれも 0）、足す送りは直した回の +3〜+15px だけで、来訪者への害は測った範囲で見つかっていない。直すのは窓のあとの押し（指摘4 の残り）と、Android の大きい触れ方で寄る 12.8〜13.7px の回である。A″ を採るか、退けるなら来訪者の側の理由を書くこと。

### 6. 測りの合否が決まっていない

「条件7・D5 の合否を、守りの形で数える（窓の中の2打目が何も起こさないこと、窓のあとの押しの着地はいまの数え方）」では、窓のあとの押しの回が何で、いまの数え方（16px 未満を数えて 0 を求める）を当てたら合格するのかが分からない。指摘4 のとおり、窓のあとの押しを今の数え方で数えれば character-personality の 375×550 などは 0 にならない。次を決めること。

- 窓の中の回の合否（2打目の click が答えも移動も開閉も起こさない）と、それが空振りでないことを示す対（窓のすぐ外の押しが答えを入れる・リンクが開く）。
- 窓の外の回をどの間隔で走らせ、どの線で合否を決めるか（指摘4・5 の扱いと合わせる）。
- 条件7 のマウスの回（`clickCount: 2`）とタッチの回で同じ線か。

### 7. 「意図した押しでありえない」は言い過ぎで、捨てた押しを見張る手段が出荷のときに無い

窓の中の押しが意図したものである見込みは小さいが、0 ではない（もう一度解く来訪者が1問目の位置を覚えていて素早く押す、など）。捨てられた押しは何も起こさず、それと分かる形も無いので、その来訪者には cycle-301 と同じ「押しても手応えが無い」が起きる。害は押し直し1回で、壊れるものは無いので受け入れてよい見込みは高いが、決定は受け入れる害として書いていない。

また、「確かめること」の見張りは B-613（問ごとの計装）に頼っているが、B-613 は Deferred（着手: 出荷後。cycle-316/options.md）で、出荷のときには数が無く、戻す判断の線も無い。t5a-design.md 8章 (iii) は「見張る数と戻す判断をする線は、T10 が ADR009 に書く」「見張れないものは、見張らずに受け入れたと書く」と決めている。どちらに当たるかを書き、見張るなら、守りが捨てた押しの数（窓の中で受けなかった click の数と、そのあと同じものが押されたか）を直に数えることも比べること。

あわせて、捨てる範囲を、1打目の点から一定の距離（二度押しとみなす `DOUBLE_TAP_SLOP` の 100px など）の中の押しに絞る道も比べること。二度押しの2打目は1打目の近くに落ちるので、遠くを意図して押した1打を捨てずに済む。採らないなら理由を書く。

### 8. 捨てる押しの止め方と、そのほかの既定の動きが決まっていない

- 止め方: `window` の捕捉の段階で `preventDefault` と `stopPropagation` の両方を掛けるのかを書くこと。`preventDefault` だけでは React の click の処理（共有のボタンの `onClick`、`FudaActions` の保存・共有、`InviteFriendButton`）が走る。`stopPropagation` だけでは素の `a[href]` の移動と `summary` の開閉が止まらない。Next の `Link` は `e.defaultPrevented` を見て移動をやめる（node_modules/next/dist/client/app-dir/link.js 336 行）ので、両方を掛ければ止まる。
- 捨てる押しの `mousedown` の既定の動きで、フォーカスが捨てたボタンへ移る。4-7 は切り替わりのあとにフォーカスを問の見出しや結果のボックスへ置くので、そこから外れ、キーボードと読み上げの位置が押していないボタンに変わる。捨てる押しの押し下げの既定の動きも止めるか、止めなくてよい理由を書くこと（いまの `guardSecondPress` は `detail >= 2` の `mousedown` だけを止めていて、Chromium のタッチの 500ms 前後の2打目は `detail` が 1 になる。6章 条件7）。

### 9. 直す文の一覧に抜けがある

「直すもの」に、t5a-design.md 8章（D5・D9 の扱いの行、「件を受け入れる」の決まり、B-620 の材料の5）と、4-9 の「2打目で語を選ばない」の「時間の窓ではない」の文、input-events-and-guards.md の冒頭の「時間ガードと `pointer-events` の窓は使っておらず」と §5 との対応が無い。指摘1〜8 を決めたあとの文の置き場として、一覧に入れること。

## 確かめた事実

- Android の `ViewConfiguration.DOUBLE_TAP_TIMEOUT` は 300ms で、決定の引用は正しい。500ms が道具の2打目（293〜306ms）を覆うことも landing-options.md 2-4 と合う。窓の長さそのものは、指摘3 の境目の扱いと指摘4 の残りの扱いを決めれば支えられる。
- 3つの切り替わりの選び方は、knowledge §5 の軸1（画面が実際に変わる切り替わりだけで基準の時刻を更新する）に合い、診断の答え→次の問を外すことは cycle-301 の 79〜559ms の「次へ」が捨てられた件の型を避ける。
