## 指摘

### 1. 目的に根拠の無い数がある（重大）

作業計画の目的の段落に「読みかけた選択肢の字が語の途中で折れると、10人のうち8人が、選ぶ前に読み直す。」とある。この割合を支える観測は、計画の参考の情報にも、根拠に挙げた文書のどれにも無い（GA は読み直しを測れない）。82.3%（スマートフォン）の数を取り違えた文に見える。来訪者の行動を作った数で語ることは、計画の根幹の仮定を確かめずに置くこと（AP-P01・AP-P16）で、`docs/constitution.md` の質の決まりにも反する。文を外すか、「10人のうち8人がスマートフォンで解く」のように GA の数が支える文に直す。目的の段落の他の文も、出自のある事実だけで書かれているか読み直す。

### 2. 組み直す道具と走査ごとの記録を次のサイクルへ残す手立てが無い（重大）

境の理由は「二度打ちの走査は、条件1〜6 と道具と版を共有する」ことだが、道具は主の木の `tmp/` に置くので、セッションを越えて残らない（cycle-319 のキャリーオーバー「レビュアーが主の木の `tmp/` とスクラッチパッドに置いたものはセッションを越えて残らない」、cycle-318 のキャリーオーバー）。このままでは次のサイクルが道具をまた文から組み直すことになり、このサイクルで確かめた手順の文と、次のサイクルの道具が同じものである保証も無い。T5a-2 で値が「参考の値」に落ちたのは、走査ごとの記録を残さなかったためだった（t5a-measure.md 5-2）。

計画に、道具（基準の版と変更後の版の作り方を含む）と走査ごとの生の記録を、次のサイクルとレビュアーが取れる形で残すこと（先例は cycle-316 の孤立したブランチ `cycle-316-records`。split-plan.md 4）と、それを申し送りに書くことを入れる。置き方は `.claude/rules/delegation.md` の push の決まりと合うかを PM が決めて書く。

### 3. 境の置き方で、二度打ちの結果がこのサイクルの測りを古くする道を比べていない（中）

cycle-319 のキャリーオーバーは、条件7 の結果で PM が「見せる範囲を広げる・組みを直す（開始の画面の「はじめる」の位置など）・第2の組を外す」を選ぶことを見込んでいる。「はじめる」の2打目が1問目の選択肢に落ちる4本には character-personality（閲覧の 85.8%）が入っており、着地のずれで h1 が切れる件もある。次のサイクルでコードを直せば、このサイクルで測った条件1（入る）・5（フォーカス）・6（「もう一度挑戦する」）・D1〜D4 などの変更後の値は、直す前の版の値になり、測り直しが要る。

比べた案は「全部をこのサイクルで」と「二度打ちの前で切る」の2つだけである（AP-P17）。少なくとも、条件7・D5 を先に測る順（コードを直す見込みの大きい測りを先にし、直したあとの版で残りを1度だけ測る）と、cycle-319 で分かっている件（「はじめる」の4本・着地のずれ）だけを先に測る案を比べ、選んだ理由を書く。いまの境を選ぶなら、次のサイクルでコードを直したときに測り直す条件の範囲と、その仕事の置き場を計画（と申し送りの項目）に書く。

あわせて、目的の段落の「測りで外れた件は、PM が t5a-design.md 8章のとおり件ごとに決める」は、8章の選択肢が条件7・D5 のためのもの（「T5a-7 の測りで避けられない件が出たとき」）なので、このサイクルの条件1〜6・8 の外れには当てはまらない。このサイクルの外れをどう扱うか（報告の先、直すならどのタスクで builder を起こし、どの条件を測り直すか、次のサイクルへ送るか）を書く。

### 4. D2・D6・D7 の置き場と、D2 の基準の版の測りが device-triage.md と食い違う（中）

- device-triage.md D2 の行き先は「条件3 のタッチの回に、次の問が出た直後（最初のフレームと 150ms 後）に…記録する」で、計画は条件3 を T5a-7a-3、D2 を T5a-7a-4 に分けている。
- D6 は「条件5 に足す」、D7 は「条件5 の毎フレームの記録に、次の問が出た最初のフレームで…」で、条件5 の走査の中で取る測りである。計画は D6・D7 を T5a-7a-4 に置いている。別の走査で取ると、「次の問が出た最初のフレーム」を条件5 と同じ記録で押さえられない。
- D2 は基準の版と変更後の版の両方で測る（device-triage.md D2「変更前の値は T5a-7 が基準の版で測る」、t5a-measure.md 0章の末尾）。T5a-7a-4 の文は D2 の版を書いていない（T5a-7a-2 だけが「基準の版と変更後の版」と書く）。

D2 を T5a-7a-3 の条件3、D6・D7 を T5a-7a-3 の条件5 に移し、各タスクに測る版（変更後だけか、両方か）を書く。条件3〜6 は T5a-2 で変更前の値を測っていない条件（条件6 を除く）があるので、どれが変更後だけでよいか（device-triage.md の「変更前の値は要らない」）も合わせて明記する。

### 5. T5a-4 の完了の条件に、根の `touch-action` が効くことの確かめと `QuizPlayPageLayout` の試験が無い（中）

T5a-4 の完了の条件は、区切りと罫線と撮った像を見るが、組んだ規則が本番ビルドで根に効くこと（診断・クイズのページで `document.documentElement` の計算値が `manipulation`、ほかのページと、診断のページからクライアントの遷移で `/blog` に移ったあとが `auto`）を見ない。これは T5a-7a-4 の D1 まで分からない。cycle-319 の補足事項は「2打目のためだけにある作りは、組んだタスクの完了の条件に実ブラウザの確かめを入れる」（AP-I07）と学んでいる。CSS モジュールの中の `:root:has(…)` が組めて効くかは、builder の段で安く確かめられる。

また、t5a-design.md 7章の T5a-4 の触るファイルは「`QuizPlayPageLayout.tsx` とテスト」だが、完了の条件は `questionPhrases` の試験だけを挙げる。箱で包むことの試験を条件に入れる。点ごとの祖先の測り（D1 の残り）は T5a-7a-4 のままでよい。

### 6. 「開始の画面の語」はもう済んでいる（軽）

T5a-4 の完了の条件の「開始の画面の説明のコメント…（T5a-6 で確かめていなければここで）」は、T5a-6 で済み、cycle-319 の全体のレビューが記録している（上の「確かめたこと」）。計画の段で確かめれば分かることを、条件つきの形で builder に渡している（AP-P16・AP-WF12）。この箇条を外す。

### 7. 祖先の値が根まで効く根拠の出典が違う（軽）

参考の情報は MDN `touch-action` を挙げて「根に書いた値が子孫の点に効くのは、ブラウザが点の要素から祖先までの値を合わせて扱うため」と書く。MDN の文は「the browser intersects the `touch-action` values of the touched element and its ancestors, up to the one that implements the gesture (in other words, the first containing scrolling element)」で、最初の送れる祖先までと読める。根まで見るのは拡大の身ぶりについての Pointer Events 3 の決まり（「between the hit tested element and the document element of the top-level browsing context」。device-triage.md D1 と device-triage-sources.md が引くもの）である。根拠に Pointer Events 3 を挙げ、MDN の文の範囲の違いを書く。

### 8. T5a-7a-4 が大きく、担当の分け方が書かれていない（軽）

T5a-7a-4 は、条件8（全15本の全問の見出しと選択肢を 320・375 の既定と 200% で、答えたあとの行も）・条件9・10・12・D1（全15本の3画面と点ごとの祖先、ほかのページの対）・D3・D4 と、条件11 の像（7つの画面 × ライト・ダーク × モバイル・PC × 前と後）を1つにまとめている。上の指摘4で D2・D6・D7 を移しても、まだ T5a-7a-2・3 より大きい。計画が T5a-7 を分けた理由（担当の文脈が溢れる・レビューが1回で全条件を見られない）がそのまま当たるので、少なくとも条件8 と条件11 を分ける（CLAUDE.md「Keep task smaller」）。あわせて、T5a-7a-1〜4 をそれぞれ新しい担当で起こすことを書く（作業内容の 3〜5 は担当の起こし方を書いていない。AP-WF07・AP-WF10）。

### 9. T5a-7a-1 の手順で2つ足りない（軽）

- `origin/cycle-316-records` はいまの主の木に無い（`git branch -a` に無く、`git ls-remote` では b42b12cf にある）。cycle-318 のキャリーオーバーと split-plan.md 4 のとおり `git fetch origin cycle-316-records` で取ることを依頼に書く（約 494MB で、ほかの fetch には含めない）。
- 計画は基準の版を「fff3d31f に da102212 の `character-personality.ts` を重ねたもの」と決め打ちしているが、t5a-measure.md 0章の「T5a-7 の前の確かめ」は、差が診断のページに掛かるなら「その差が影響する条件をその直前の版で測り直し、その版を基準にする」と定める。確かめの結果で基準の版が変わりうることと、そのとき T5a-7a-2〜4 が何を基準にするかを書く。

### 10. 申し送りの項目が粗く、このサイクルで測る値の使い道が書かれていない（軽）

- 「条件7・D5 の二度打ちの測り」の項目に、cycle-319 のキャリーオーバーの具体（「はじめる」の4本の比べ・着地のずれの数と量・切れる見出し・`spancheck.mjs` の置き方が6章の共通の決まりと違うこと）、t5a-measure.md 5-1 の 375×550 の 200% のマウスの5つの間隔と 5-3 の基準の版での測り直し、B-623 を閉じること（D9）を名指す。次のサイクルの計画が拾い落とさないためである。
- 5章の React の知見は「根拠: T5a-7 の実測（値を書く）」で、その値は条件5 の毎フレームの記録（`BODY` のフレーム・新しい画面の最初のフレーム）である。knowledge の書き直しは次のサイクルなので、T5a-7a-3 が knowledge に要る値を t5a-measure.md に書くことを完了の条件に入れる。
- B-624 は「T5a-7 の条件5 で確かめて Done へ」と backlog にある。条件5 はこのサイクルで測るので、B-624 をこのサイクルで Done にするか、T5a の完了のレビューまで待つかを決めて書く。

### 11. B-788 を Queued に移す時（軽）

B-788 は「T5a-4 が診断のページに入れたあと（同じ形を写す）」が着手の条件だが、写す形が効くと分かるのは D1 の測り（T5a-7a-4）か、指摘5を入れたなら T5a-4 の完了の条件のあとである。移すのを、効くと確かめたあとに置くと、写す先が確かめていない形を写さずに済む。指摘5を入れるなら「T5a-4 の取り込みのあと」のままでよい。
