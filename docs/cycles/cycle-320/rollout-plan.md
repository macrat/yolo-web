# B-754 サイトデザインの刷新: 出荷までの計画

統合ブランチ `design-rollout` を main へ出荷するまでに行うのは、この計画のタスクだけである。cycle-316 の [split-plan.md](../cycle-316/split-plan.md) の 7 の表と [carryover-tasks.md](../cycle-316/carryover-tasks.md) の残りのタスクは使わない。そこに残っていたタスクは、出荷のあとに扱う項目として `docs/backlog.md` に移した（下の「出荷のあとに回したもの」）。

## 決め方

出荷の前に行うのは、それが無いと出荷できないか、それが無いと来訪者が本番より悪い画面を受け取るものだけである。新しいデザインの細かい規則がまだ当たっていない面（h1 の大きさ・自前の余白・細い線の枠・古いトークンなど。cycle-316 の [t5-inventory.md](../cycle-316/t5-inventory.md) 11章）は、古いトークンの定義が `globals.css` に残っているので表示は壊れず、出荷のあとに続けて当てられる。そのため出荷の前には行わない。cycle-316 の [completion-criteria.md](../cycle-316/completion-criteria.md)（全ページが `DESIGN.md` を満たすこと）は出荷の条件に使わない。出荷の条件は、下の1〜4を満たすことである。

## 出荷の前に行うタスク

1. **CI を通す**: `design-rollout` の HEAD で `npm run typecheck`・`lint`・`format:check`・`test`・`build` を通す。落ちるテストがあれば、落ちる分だけを直す。
2. **本番より悪くなっていないことを確かめ、悪くなっていた所だけを直す**:
   - `/play/character-personality`（診断のプレイ面。閲覧の約8割）を、本番の版と `design-rollout` の版で並べ、375×550・320×550 と PC で、開始・回答・結果まで通して比べる。見るのは、開始のボタンがモバイルの最初の画面に入るか、回答中に選択肢がすべて見えるか、押した選択肢がすぐ選んだ状態に見えるか、結果を受け取ったときに楽しいか、保存やシェアをしたくなる形か。
   - 同じ面で、375×550・320×550 の全問の選択肢の字の折れ方を、本番と比べる。行頭に閉じ括弧が来る・1字だけの行が出るなど本番より悪ければ、本番と同じブラウザの既定の改行に戻す。
   - 同じ面で、「はじめる」・答え→次の問・最後の答えを、タッチで 90ms と 300ms の間隔で二度押しし、2打目の落ちる先を本番と比べる。読んでいない問に答えが入るなど本番より悪ければ、本番と同じふるまいに戻す。
   - ほかのテンプレート（トップ・一覧・ツール・ゲーム・辞典の詳細・ブログの記事・診断の結果・about・404）を1ページずつ、ライトとダーク・375×550 と PC で開き、表示が壊れていないことと主な操作ができることを確かめる。代表のページの `og:image` が PNG を返すことも確かめる。
   - ゲームの判定を色で説明しているブログ記事（`2026-02-14-japanese-word-puzzle-games-guide.md` など、ゲームのページの関連記事に出るもの）を、いまの印と数の示し方に直す。出荷すると記事の説明が画面と食い違い、来訪者を誤らせるからである。
3. **表示の速さが大きく悪化していないことを確かめる**: cycle-316 の [facts-speed-before.md](../cycle-316/facts-speed-before.md) の5ページを、同じ手順で `design-rollout` の版で測る。LCP の中央値が変更前の5回の最大を越えるページ、CLS の中央値が変更前を上回るページがあれば、原因を調べて直す。Web フォントの転送量も同じ計測で記録する。
4. **出荷するものをレビューに通す**: main との差分のうち、cycle-316 で途中の巡目で止めたレビューの確かめ（ページ送りの番号の箱の幅の直し b5ee51a と、builder が直した `DESIGN.md` の言い方。cycle-316 の [decisions-t1-t3.md](../cycle-316/decisions-t1-t3.md)）と、2・3 で直したものを、レビューに通す。
5. **出荷し、本番で確かめる**: `design-rollout` を main へマージして出荷し、CI と、本番の表示・favicon・theme-color・Web フォントの配信・代表のページの `og:image` を確かめる。
   - 本番で表示が壊れている・主な操作ができない・診断のプレイ面が本番の前の版より悪いと分かったら、main のマージのコミットを revert して出荷を戻し、直してから出し直す。
   - 確かめたあと、`cycle-completion` の手順7の「その変更の最後のサイクル」のとおり、`deploy.yml` と `docs/backlog.md` から統合ブランチの名前を外し、`design-rollout` を origin から消す。

1〜5 は1つのサイクルで行う。2・3 で直す所が多く出たときだけ、直しを次のサイクルに分ける。

## 出荷のあとすぐに行うもの

- **ADR009 の基線を取る**: Search Console の数は約16か月、GA の数は BigQuery に残るので、出荷の直前28日の数は出荷のあとでも取れる。出荷から2週の読み始めより前に、[ADR009](../../ADR/open/2026-10-23-ADR009-新しいコンセプトへのサイト全体の作り直し/index.md) の「次回確認時にやること」の2・3のとおり、出荷の直前28日の Search Console のカテゴリ別の基線と GA の数を取って保存し、撤退基準の値を確定する。あわせて、出荷の日から計測の出方が変わるものを ADR009 に書き、Search Console の Core Web Vitals の実地の値を B-758 に渡す。
