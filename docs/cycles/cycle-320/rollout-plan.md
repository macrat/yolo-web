# B-754 サイトデザインの刷新: 出荷までの計画

統合ブランチ `design-rollout` を main へ出荷するまでに行うのは、この計画のタスクだけである。cycle-316 の [split-plan.md](../cycle-316/split-plan.md) の 7 の表・[carryover-tasks.md](../cycle-316/carryover-tasks.md) の残りのタスク・[completion-criteria.md](../cycle-316/completion-criteria.md) は使わない。そこに残っていたタスクは、出荷のあとに扱う項目として `docs/backlog.md` に移した（下の「出荷のあとに回したもの」）。

## 決め方

出荷の前に行うのは、それが無いと出荷できないか、それが無いと来訪者が本番より悪い画面を受け取るものだけである。新しいデザインの細かい規則がまだ当たっていない面（h1 の大きさ・自前の余白・細い線の枠・古いトークンなど。cycle-316 の [t5-inventory.md](../cycle-316/t5-inventory.md) 11章）は、古いトークンの定義が `globals.css` に残っているので表示は壊れず、出荷のあとに続けて当てられる。そのため出荷の前には行わない。刷新が意図して変えたもの（T4-5 で、診断の解き終えた画面の保存と共有のボタンを最初の画面の外へ移したことなど。ADR009 が見張る）は、本番と違っても戻す対象にしない。

## 出荷の前に行うタスク（サイクルの「実施する作業」に置く）

1. **CI を通す**: `design-rollout` の HEAD で `npm run typecheck`・`lint`・`format:check`・`test`・`build` を通す。落ちるテストがあれば、落ちる分だけを直す。
2. **本番より悪くなっていないことを確かめ、悪くなっていた所だけを直す**:
   - `/play/character-personality`（診断のプレイ面。閲覧の約8割）を、本番の版と `design-rollout` の版で並べ、375×550・320×550・1280×800 で、開始・回答・結果まで通して比べる。見るのは、開始のボタンがモバイルの最初の画面に入るか、回答中に選択肢がすべて見えるか、押した選択肢がすぐ選んだ状態に見えるか、結果の名前が結果の画面に見えるか。
   - 同じ面で、375×550・320×550 の全問の選択肢の字の折れ方を、本番と比べる。行頭に閉じ括弧が来る・1字だけの行が出るなど本番より悪ければ、`QuestionCard` の選択肢の面（押す前と押したあと）だけを、本番と同じブラウザの既定の改行に戻す。共通の部品（`PhrasedText` など）は変えない。
   - 「はじめる」と、知識クイズの最後の「次へ」の速い二度押しで、2打目がどこに落ちるかを、本番の版と `design-rollout` の版の両方で、同じスクリプトで確かめる。組は、cycle-320 の記録で落ちると分かっているもの（「はじめる」は 375×550 の4本・character-personality の 1280×800・375×550 の文字サイズ 200% の12本、最後の「次へ」は結果の画面のおすすめのリンクに落ちた組。cycle-320 の [index.md](./index.md) の補足事項「試しの走りで見つけた着地の作りの欠け」）で、タッチの 90ms と 300ms の二度押しとする。線は「本番で読んでいない問に答えが入らない・ページを離れない組では、`design-rollout` でもそうならない」である。外れた組があるときだけ、その切り替わりのあとにスクロールしない（本番と同じふるまい）ように直し、同じ組で確かめ直す。直したら、`DESIGN.md` の同じふるまいを書いた節も実装と同じ中身に直す。
   - ほかのテンプレート（トップ・一覧・ツール・ゲーム・辞典の詳細・ブログの記事・診断の結果・about・`notFound()` の 404 とどのルートにも一致しない URL の 404・410）を1ページずつ、ライトとダーク・375×550 と 1280×800 で開き、表示が壊れていないこと、主な操作ができること、HTTP の状態が本番と同じであること、AI が運営する実験のサイトであることの告知が出ていることを確かめる。代表のページの `og:image` が PNG を返すことも確かめる。
   - 本番の sitemap の全 URL と転送の元の URL を、`design-rollout` のビルドに当て、404 にならないこと（転送は転送されること）を機械で確かめる。canonical・robots・title・description・JSON-LD の本番との差を一覧にし、意図しない差があれば直す。
   - ゲームの判定を色で説明しているブログ記事2本（`src/blog/content/2026-02-14-japanese-word-puzzle-games-guide.md` と `src/blog/content/2026-02-15-yojijukugo-learning-guide.md`。ゲームのページの関連記事に出る）を、いまの印と数の示し方に直す。テーマの切替のボタンを案内している `src/blog/content/2026-02-21-dark-mode-toggle.md` には、そのボタンをいまは置いていないことを1文で書き足す。出荷すると記事の説明が画面と食い違い、来訪者を誤らせるからである。
3. **表示の速さが大きく悪化していないことを確かめる**: 同じセッションで origin/main と `design-rollout` をそれぞれ本番のビルドにし、cycle-316 の [facts-speed-before.md](../cycle-316/facts-speed-before.md) の5ページを、同じ手順（Lighthouse のモバイルの既定）で交互に5回ずつ測る。`design-rollout` の LCP の中央値が main の5回の最大を越えるページと、CLS の中央値が 0.1（web.dev の「良好」の線）を越え、かつ main の中央値より大きいページがあれば、原因を調べて直す。
4. **出荷するコードをレビューに通す**: cycle-316 で途中の巡目で止めたレビューの確かめのうち、ページ送りの番号の箱の幅の直し（b5ee51a。cycle-316 の [decisions-t1-t3.md](../cycle-316/decisions-t1-t3.md)）と、2・3 で直したものを、レビューに通す。

## 出荷と本番での確かめ（サイクルの完了の処理の中で行う）

1〜4 を終えたら、`cycle-completion` の手順7の「その変更の最後のサイクル」のとおりに出荷する。

- 完了のコミットで、`deploy.yml` の `on.push.branches` と `docs/backlog.md` から統合ブランチの名前を外し、B-754 を Done にする。origin/main をマージしてから、main へ push して出荷する。
- 出荷の CI と Vercel のデプロイが済んだら、本番で、表示・theme-color・Web フォントの配信・代表のページの `og:image` と、GA に `page_view`・`level_start`・`level_end`・`share`・`save` の数が届いていることを確かめる。確かめ終えるまで、main にほかの push をしない（Instant Rollback で戻れるのは、すぐ前の本番のデプロイだけだからである）。
- 本番で表示が壊れている・主な操作ができない・診断のプレイ面が出荷の前の本番より悪いと分かったら、Vercel の Instant Rollback で出荷の前の本番のデプロイに戻し、B-754 を Queued に戻す。直したものを出すときは、直したものを main へ push し、そのデプロイを確かめてから Vercel で本番に promote する。
- 確かめたあと、`design-rollout` を origin から消す。本番での確かめの記録は、出荷のサイクルの文書に書き、確かめ終えてから push する。
- 出荷のサイクルでは、ブログの記事を書かない（`cycle-completion` の手順2）。書くかは出荷のあとのサイクルで判断し、出荷を遅らせない。
