## 2. 抜けているもの・このままでは進められないもの

### 2-1. タスク3: CLS の変更前の値が無い。変更前の LCP も同じ環境の値ではない【重要】

- facts-speed-before.md には、LCP と転送量の値はあるが、CLS の値は無い。
- 元の25回の JSON（`./tmp/lh/before/`）も残っていない。`origin/cycle-316-records` の `tmp-records/README.md` の「写す時点で無かったもの」に `tmp/lh/`（`before/blog-1.json`…）が挙がっている。
- `tmp-records/t1a3/work/lh/before/` に35個の JSON がある。しかし、たとえば blog-1 の LCP は 2,873ms で、facts-speed-before.md の5回の値のどれとも合わない。別の計測なので、変更前の値には使えない。
- 計測の環境も変わっている。変更前は Chromium `chromium-1194` で測ったが、いまの `/opt/pw-browsers` には `chromium-1243` しか無い。Lighthouse の模擬の減速の値は、ブラウザの版や機械によって揺れる。そのため、別の日に別の版で測った「変更前の5回の最大」と比べると、悪化していないのに悪化と出たり、その逆が起きたりしうる。悪化と出れば、そのたびに調べる手間が増え、出荷が遅れる。

**直し**: 同じセッション・同じブラウザで、本番の版（origin/main をビルドしたもの）と design-rollout の版を交互に5回ずつ測り、LCP と CLS をその場の値で比べる、と書く。facts-speed-before.md の値は参考に留める。ビルドが1回増えるだけで、判定は確かになる（AP-P01: 確かめていない前提の上に合否の線を置かない）。

### 2-2. タスク5: 戻し方として書いた「main のマージのコミットを revert」は、そのコミットが生まれないのでできない【重要】

- `git log design-rollout..origin/main` は空で、main（4e98a535）は design-rollout の祖先である。
- `cycle-completion` の手順7（最後のサイクル）は `git merge origin/main` のあと `git push origin HEAD:main` とする。この形では、main は fast-forward で design-rollout の先まで進み、マージのコミットは作られない。
- その結果、計画の「main のマージのコミットを revert して出荷を戻す」は、戻すコミットが無いので実行できない。1,000 を超えるコミットを revert で戻すのは現実的でない。
- 仮にマージのコミットがあったとしても、design-rollout の側から origin/main をマージした形では、`-m` で選ぶ親を誤ると何も戻らない。

**直し**: 戻し方を次のどちらかにして、計画に書く。

- (a) 本番を速く戻す道として、Vercel の Instant Rollback（ダッシュボード、`vercel rollback`、または Vercel の MCP）で、ひとつ前の本番のデプロイに戻す。ビルドをし直さず、すぐに切り替わる。ただし Hobby のプランでは、すぐ前の本番のデプロイにしか戻せない。また、戻したあとは本番のドメインの自動の割り当てが止まり、次の出荷のときに戻す操作が要る。そこで、出荷から確かめ終えるまで、main にほかの push をしないことも書いておく。
- (b) git の側でも戻せるようにするなら、main の上で `git merge --no-ff design-rollout` をして1つのマージのコミットを作り、`git revert -m 1 <そのコミット>` で戻せる形にする。この場合は `cycle-completion` の手順7と違う手順になるので、どちらを採るかを計画に書く。

あわせて、タスク5の「確かめたあと、`deploy.yml` と `docs/backlog.md` から統合ブランチの名前を外す」は、`cycle-completion` の手順7の順と合っていない。手順7は、名前を外したものを完了のコミットに入れてから main へ push する。計画は「手順7のとおり」と書きながら、手順を逆に書いている。どちらかに揃える。

### 2-3. タスク2: 「本番と同じふるまいに戻す」が、選択肢を画面に入れる直しを消しうる【重要】

二度押しの項は「本番より悪ければ、本番と同じふるまいに戻す」としている。

本番では、375×550 で4つの選択肢のうち見えるのは1つだけである（B-614）。design-rollout はこれを、「はじめる」を押したあとに、問のまとまりが画面に入るまで送る作り（T5a-5・T5a-6）で直した。2打目が1問目の選択肢に落ちるのは、この送りの結果である（cycle-319 のキャリーオーバー）。

「本番と同じふるまい」を文字どおりに取ると、送りをやめることになる。そうすると、同じタスクの1つ目の項（回答中に選択肢がすべて見えるか）と B-614 の直しが、また本番の悪い形に戻る。

**直し**: 直す目標を「2打目が答えにならない」ことに置き、選択肢が画面に入る形は保つ、と書く。

**範囲**: 「はじめる」の2打目が落ちる件は、cycle-319 の走査で character-personality・word-sense-personality・music-personality・character-fortune の4本で分かっている。4本は同じ部品（`QuizContainer`）で動くので、直したあとの確かめは、この4本の「はじめる」で行う（375×550・90ms と 300ms）。答え→次の問と最後の答えは、計画のとおり character-personality だけでよい。

字の折れも、`QuestionCard` は15本で共通である。直しは共通の CSS に入るので、確かめを character-personality で行うのは妥当である。

### 2-4. タスク2の1つ目の項に、悪かったときの扱いが無い。見る点も好みでぶれる

「結果を受け取ったときに楽しいか」「保存やシェアをしたくなる形か」は、比べた結果が悪かったときに何をするかが書かれていない。このままだと、出荷の前に結果の画面を作り直す（出荷のあとに回した T5-6 の中身）方向へ広がりうる。

そこで、本番と比べられる、目に見える点に置き換える。

- 375×550 の最初の画面に「はじめる」が入るか
- 回答中に見える選択肢の数
- 押した選択肢が選んだ状態に見えるまでの間
- 解き終えた画面で、タイプ名・結果の説明・保存と共有のボタンに、それぞれ何 px の送りで届くか

そのうえで、本番より悪い点だけを、その点に限って直すと書く。

ただし、T4-5 で保存と共有のボタンを結果の説明のあとへ移したのは、意図した変更である。その影響は ADR009 が GA で見張る（「character-personality の結果の保存と共有の率」）。この差は「悪化」として戻す対象にしない、と書いておく。

### 2-5. 出荷のあとに、GA に数が届いているかを確かめる項が無い【重要】

design-rollout では `src/lib/analytics.ts`（61行）・`src/lib/google-analytics.ts`（25行）と、410 のページの GA の差し込み（`src/middleware.ts`）が変わっている。

### 2-6. 本番の URL が design-rollout でも開けるかを、機械で確かめる項が無い

design-rollout では、URL の扱いに関わるものが変わっている。

タスク2のテンプレートごとの確かめは1ページずつなので、一部の URL が 404 になっていても見つからない。検索から来た来訪者が 404 を受け取れば、本番より悪い。

**直し**: タスク2に、機械の確かめを1つ足す。

スクリプト1本で済み、手間は小さい。
