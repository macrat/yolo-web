## 指摘（どれも来訪者に届く設計の決めごとで、改善指示の理由になる）

### 1. 「押しの単位」が `pointerdown` の `detail` で決めると書いているが、`pointerdown` の `detail` はいつも 0 で、連続の押しの守りがこの文のとおりには作れない

Pointer Events の仕様では、`detail` が数を持つのは `click` と `auxclick` だけで、ほかの PointerEvent（`pointerdown` を含む）では 0 である（W3C の public-pointer-events の議事 2016・2023。Chrome と Edge も 0 を返す）。決定の「守るかどうかは、押し下げ（`pointerdown`）の `event.timeStamp`・座標・`detail` で決め」をそのまま作ると、連続の押しの守り（`detail >= 2`）はどの押しでも成り立たず、診断の答え→次の問の2打目が1つも塞がれない。jsdom の試験は `MouseEvent` に `detail` を手で入れて通るので、この誤りは試験では見つからず、実ブラウザの条件7 でしか出ない。

連続の数を持つのは `mousedown` と `click` で、タッチでは `pointerdown` が触れた時に、`mousedown` と `click` が離した時にまとめて届く（互換のマウスの事象）。次を決め直すこと。

- 時刻と座標は対の `pointerdown` で取り、連続の数は `mousedown`（か `click`）の `detail` で取る、のように、どの値をどの事象から取るかを分けて書く。
- 対の `pointerdown` を持たない `click`（キーボードと読み上げの起動。`detail === 0`）は、直前のポインタの押し下げと対にせずに通すことを、押しの単位の文の中でも書く（いまは窓の文にだけある）。
- 試験に、`pointerdown` の `detail` が 0 のまま、`mousedown`・`click` の `detail` 2 で連続の押しを受けないことを入れる（`pointerdown` の `detail` を 2 にした偽の事象で通る試験にしない）。

### 2. 連続の押しの守りが意図した答えを捨てる場合が書かれておらず、4-9 が L2 を退けた理由の写しが事実と違う

決定は「読んでから答える押しは連続と数えられないので捨てない」と書くが、連続と数えるかは来訪者の OS の設定で決まる。Windows のダブルクリックの時間は既定 500ms で、`SetDoubleClickTime` で 5000ms まで延ばせる（Microsoft Learn）。macOS の `NSEvent.doubleClickInterval` もシステムの設定で、来訪者が遅くできる（Apple）。手の動きに難のある人にダブルクリックを遅くする設定を勧める案内もある（AbilityNet）。診断の次の問は前の問と同じ所に選択肢が並ぶので（t5a-design.md 4-9）、マウスを動かさずに同じ行の答えを続けて押す来訪者は、設定の時間の中で読んで押せば、その押しが `detail` 2 になって黙って捨てられる。すぐに押し直すと `detail` 3 になってまた捨てられ、間を空けるまで答えが入らない。cycle-301 の害の型（速く答える人の答えを黙って捨てる）が、ダブルクリックを遅くした人に限って戻る。

また、決定は「4-9 が L2 を退けた理由は、Chromium のタッチの 500ms 前後の2打目が `detail` 1 で届くことと iOS の Safari の数え方を確かめられないこと」と書くが、4-9 の表の L2 の行は「捨てる。黙って捨てる点は同じ。iOS の Safari が2打目に 2 を付けるかも未確かめ」で、1つ目の理由は害（黙って捨てる）である。Chromium のタッチの 500ms の件は 6章 条件7 の測り方の文で、L2 の退けた理由ではない。決定の「『全部は塞げない』であり『塞げる分を塞ぐと害が出る』ではない」は、写し違えた理由への反論になっている。

次を直すこと。

- 4-9 の L2 の退けた理由を事実のとおりに写し、「黙って捨てる」に正面から答える。
- 連続の押しの守りに、窓と同じ時間の上限（答えた click から 700ms 未満）を重ねる形を比べる。重ねると、Android の 300ms と Windows の既定 500ms の二度押しはこれまでどおり塞ぎ、次の問が出てから 550ms のうちに読んで押すことは無いので、ダブルクリックを遅くした来訪者の読んでからの答えを捨てない。失うのは、遅い設定の人の 700ms より後の2打目を塞ぐ分で、これは塞げない分として条件7・D5 で数えるものと同じ類になる。重ねないなら、その理由と、捨てる害を「受ける害」に書き、`quiz_press_guarded_retry` の `transition: answer` で見張ることを書く。

### 3. 測りの道具が、守りが止めた click を答えや落ちた先として数えてしまう

`measure.mjs` は、`window` の捕捉の段階の `mousedown`・`click` の受け手を読み込みの前に置き（knowledge §8 の受け手の走る順）、2打目の落ちた先と X・S を2つ目の `click` の要素と帯の番号で決める（t5a-measure.md 5-2 の「答えの出どころは捕捉の段階の `click` の記録にする」、`pressRecord` の `second`）。守りは同じ所の、あとから置かれた受け手なので、道具の受け手は守りより先に走り、止めた click も記録する。いまの数え方のままでは、窓の中で止めた2打目が「選択肢に落ちた」「第1の組に落ちた」に入り、決定の合否（外れた件 0）が守りの効き目と無関係に落ちる。

決定の「測りの道具: 下の『測りの合否』を数える」では、道具の担当がどう見分けるかを決められない。次のどちらかを決めること。

- 2打目の `click` が止められたか（`defaultPrevented`）を、事象を配り終えたあと（受け手の中で次の task に回して読むなど）に記録し、止められた click を落ちた先の数から外す。
- 落ちた先を click の要素でなく、押しのあとの結果（帯の番号・答えの数・URL・`details` の開閉・フォーカスの置き場）で決める。

あわせて、連続の押しの守りの回で、間隔ごと・入力ごとの2打目の `mousedown`・`click` の `detail` の分布を記録することを書く。マウスの `clickCount: 2` はどれも 2 で届く（10-1）が、道具のタッチの2打目が `detail` 2 で届くかは記録が無く、0 件のまま「外れた件 0」で合格すると、タッチの行は守りを試していない。

### 4. 数えるイベントの「同じ要素」と、送る時と、偶然の基準が、来訪者の害を見張れる形になっていない

- **同じ要素**: click の的は、押した所の一番内側の要素で、選択肢なら名前の `span`、ボタンなら中の字のことが多い（t5a-measure.md 5-2 も `closest("button")` で選択肢を決めている）。受けなかった押しが名前の字に、押し直しがボタンの余白に落ちると、同じ押せるものを押し直したのに「同じ DOM の要素」にならず、害が数えられない。比べるのは押せるもの（`reveal.ts` の集め方の `closest`）にすること。押せるものの上でない押し（字や余白）は、受けても何も起きなかったので、`retry` の元に入れるかを決める。
- **送る時**: 押しの単位を `pointerdown` で決めるので、窓の中で始まって送り（指で引く）になった押しは、`mousedown` も `click` も来ない。送るのは、`mousedown` か `click` を実際に止めたときだけ、と書く。
- **偶然の基準**: 「選択肢の数から出る偶然の割合（4択なら 25%）を基準に置き、それを越える割合で線を引く」は、害を隠す向きに働く。二度押しを正しく止めたあとに来訪者が読んで同じ選択肢を選ぶ割合は、3 秒の中で答える割合 × 同じ選択肢を選ぶ割合で、25% より小さい。たとえば止めた押しの 1 割が意図した押しで全部押し直され、残りの 9 割の 3 秒の中の偶然の一致が 5% なら、割合は 0.1 ＋ 0.9 × 0.05 ≒ 14.5% で、25% を越えず「害なし」と読まれる（算術）。また「はじめる」と結果への切り替わりで止めた押しは選択肢とは限らず、選択肢の数の基準が当てはまらない。基準を、経過 ms の分布（意図した押しの押し直しは読む時間を要らず早く来る）を主にするか、止めずに受けた押しの側から実測で取るなどに決め直すこと。

### 5. D5 の窓の中の走査の「100px の外のずれ」が定まっていない

決定は「窓の中は、1打目から 100px の中のずれで受けないこと・外のずれで受けることを合否に入れる」と書くが、いまの D5 のずれは (0, ±10)・(0, ±20)・(−10, 0) で、どれも 100px の中にある（t5a-measure.md 10-1）。外のずれの値が無いので、道具の担当が合否の回を決められない。境目の扱い（「以内」は 100 を含むか）と、ずれの値を、窓の 700ms を条件7 の 500ms から 200ms 離したのと同じく境目から離して決めること。タッチの調整で点が最大 16px 寄るので、境目から 16px 以上離す（例: 中は 80px 以下、外は 120px 以上）。あわせて、Android の `DOUBLE_TAP_SLOP` は2点の直線の距離で比べる（`GestureDetector`）のに対し、決定は max(dx, dy) の正方形で、斜めに 100〜141px の押しも受けない。広く取るのは塞ぐ側に倒した選びとして書くか、直線の距離に揃えること。

### 6. 残るものの書き方に、事実より強い文が2つある

この決定で、二度押しの2打目が読んでいない問に答えを入れる件と、結果を読まずにページを離れる件は、次のように分かれる。

- 無くなる: 3つの切り替わりの、700ms 未満・100px の中のポインタの2打目。診断の答え→次の問の `detail >= 2` の2打目。
- 残る: 診断の答え→次の問の連続と数えられない2打目（Android の 300ms を越えるもの、Chromium のタッチの 500ms 前後）。3つの切り替わりの 700ms 以上の2打目（ダブルクリックを遅くした人の2打目、手の遅い人の二度押し）。後者は、着地の A″ で 16px 以上離せない回で選択肢やリンクに落ち、375×800 の kotowaza-level の型 (3) のように結果を読まずにページを離れうる。

決定は残るものを決めごと 3 と理由に書いているが、次の2文が事実より強い。

- 「窓のあとの押しと、連続と数えられない押しは、新しい画面が見えてからの押し」: 連続と数えられない押しには、Android の 300ms を越えた二度押しの2打目が入り、診断では次の問が出てから 150〜350ms ほどの押しで、読んだあとの押しではない。窓のあとの 700ms 台の押しも、ダブルクリックを遅くした人の2打目でありうる。大半は別の押しで、そうでないものは塞げずに残る、と書くこと。
- 「組みを変えて結果の下の部品を下げる来訪者の側の得が無い」: 得は、700ms 以上の2打目が結果の画面のリンクに寄せられてページを離れる件を減らすことで、0 ではない。得が小さく、結果のボックスの下に 105px の空きを足す害と比べて採らない、と比べて書くこと。

## 確かめた事実

- `pointerdown` の `detail` が 0 で、連続の数を持つのが `click`・`auxclick`（と `mousedown`・`mouseup`）であること: W3C の public-pointer-events の議事（2016 の Rick Byers・Navid Zolghadr、2023 の Mustaq Ahmed）と MDN の click の頁（指摘1）。
- t5a-design.md 4-9 の表の L2 の行は「捨てる。黙って捨てる点は同じ。iOS の Safari が2打目に 2 を付けるかも未確かめ」で、Chromium のタッチの 500ms の件は 6章 条件7 の入力の文にある（指摘2）。
- Windows の `SetDoubleClickTime` は既定 500ms、上限 5000ms（Microsoft Learn）。macOS の `NSEvent.doubleClickInterval` はシステムの設定で、遅くする上限の値は Apple の文書に無い（指摘2）。
- `measure.mjs` は `window` の捕捉の段階の `touchstart`・`mousedown`・`click` を読み込みの前に置き、`pressRecord` が2つ目の `click` を `second` にする。t5a-measure.md 5-2 は X・S を捕捉の段階の `click` の記録から数えると決めている（指摘3）。
- t5a-measure.md 10-1 の D5 のずれは (0, ±20)・(−10, 0)・(0, −10) で、マウスの2打目の `detail` が 2 でない押しは 0、タッチの2打目の `detail` の分布は書かれていない（指摘3・5）。
- GA の引数は、カスタムディメンションに登録しなくても BigQuery で読める（docs/archive/visitor-value-measurement.md）。経過 ms を引数で送る決めごとは、T10 が BigQuery で分布を読めば足り、登録を直すものに足さなくてよい。
- `QuizContainer.tsx` の `guardSecondPress` は `mousedown` の `detail` を読んでいて、`pointerdown` の `detail` は読んでいない（いまのコードは指摘1 の誤りを持たない）。
