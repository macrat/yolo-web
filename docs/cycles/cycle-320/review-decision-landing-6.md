## 指摘

### 1. 条件7 の走査では、タッチの連続の押しの守りが、受けない側も受ける側も合否で試されない（測りの道具の決めごと。改善指示の理由）

道具のタッチは、`touchStart` と `touchEnd` を続けて送る（measure.mjs `sendPress`）。このため、押している時間はほぼ 0 になり、離しから次の押し下げまでの間隔は、指定した間隔とほぼ同じになる。指定 300ms の実際の間隔は 293〜306ms だった（t5a-measure.md 10-1 の「1度の押しで終わる回の実際の間隔」）。決定の「連続の押しの守りの回」を、この道具に当てると次のようになる。

- **0・90ms**: 2打目は答えた問の上に落ちる。守りを試さない（決定も、そう書いている）。
- **150ms**: 実際の間隔は 150ms の前後に散る。次の問が出る時刻（click のあとの描画から 150ms）とちょうど重なる。そのため、2打目が次の問に落ちるか、答えた問に落ちるかは回ごとに変わる。これを確かめた回は無い。
- **300ms**: 293〜306ms で、決定が合否から外す 280〜320ms の帯に入る。
- **500ms**: 受ける側の回である。ただし決定は、この回を「次の問に落ちた件を記録する（合否に入れない）」としている。

このため、タッチで「280ms 未満の回で2打目が答えを入れない」を確かめる回は、確実には1つも無い。150ms の回が1つも次の問に落ちなければ、外れた件 0 のまま合格になり、守りが Chromium の実際の事象の時刻で働くかは試されない。受ける側も同じである。たとえば、タッチにも 700ms の窓だけを掛ける誤った作りにしても、合否のどれも外れない。「空振りでないことの対」は 900ms の回しか持たず、300〜700ms で受けることを見ないからである。害の向きは、診断の速い答えを捨てるほうである。来訪者が最も多く通る切り替わりで、cycle-301 と同じ型の害が測りをすり抜ける。

あわせて、「守りを試しているのは 150・300・500ms の回だと記録に書く」の文は、タッチでは事実と合わない。タッチの 300ms の回は合否の外にあり、500ms の回は受ける側の回だからである。

次を決めること。

- タッチの受けない側を確実に試す間隔を、条件7 の診断の答えの走査に足す。離しからの間隔が、次の問が出る 150ms と合否の帯の 280ms の両方から離れている値にする（たとえば 220ms）。その回で、2打目が次の問の上に落ちたこと（落ちた先を押しのあとの状態で読む）と、答えを入れなかったことを合否に入れる。落ちた先が次の問でなかった回は、守りを試していない回として記録する。
- タッチの受ける側を合否に入れる。離しからの間隔が 320ms 以上で 700ms 未満の回（500ms など）で、100px の中の2打目が次の問に答えを入れることにする。D5 の 900ms の対だけでは、窓の誤りを見分けられない。
- 道具に、1打目の離し（`pointerup` か `touchend`）の時刻を記録させ、離しから2打目の押し下げまでの間隔を回ごとに残すことを、「測りの道具」に書く。いまの道具は、押し下げどうしの間隔（`touchstart` の差）しか記録していない（`pressRecord` の `gap`）。
- 「守りを試している回」の文を、マウスとタッチに分けて書き直す。

### 2. ペンを、iOS で `detail` に頼る側に置く理由が無い。前回の指摘が挙げた形（`touch` と `pen`）とも違う（来訪者に届く設計の決めごと。改善指示の理由）

決定は、自分で数えるのを `pointerType === "touch"` だけにしている。ペンは「マウスとペンは、ブラウザの数え方に任せ」とし、理由を書いていない。

- タッチを自分で数える理由は、iOS の Safari がタップを合成の click にするとき、`detail` を数えない見込みが高いことだった。iPad の Safari の Apple Pencil の押し（`pointerType` は `pen`）も、同じタップの合成で click になる。そのため、同じ見込みが当てはまると読むのが自然である（推論。確かめた資料は無い）。iOS の Safari の閲覧には、tablet が 1.3% 含まれる（cycle-318/device-triage.md 1章）。
- マウスを `detail` に任せる理由は、連続の時間が、来訪者が OS で選んだ設定に従うことだった（理由の項）。この理由は、iPad のペンには当たらない。
- ペンを自分で数える側に置いても、端末に頼らない作り（8章の (i)）のまま閉じる。害は、タッチと同じく、次の問が出てから約 150ms の押しに限られる。

人数は小さいが、ここは守りの働く範囲を決める行である。ペンを `touch` と同じ数え方にするか、マウスの側に置く理由（たとえば、ペンでは iOS の Safari も `detail` を数えると確かめた資料）を書くかを決めること。前者にするなら、試験と合否の行（タッチの行）にペンを含めると書く。

## 確かめた事実

- measure.mjs `sendPress` のタッチは、`Input.dispatchTouchEvent` の `touchStart` と `touchEnd` を待たずに続けて送る。`doublePress` は、1打目を送ってから `run.interval` だけ待ち、2打目を送る。`pressRecord` の `gap` は、押し下げ（タッチは `touchstart`）どうしの差で、離しの時刻は記録していない（指摘1）。
- t5a-measure.md 10-1: 指定 90ms の実際の間隔は 82〜123ms、300ms は 293〜306ms。指定 90ms の回のうち1つが 150ms の側を越えた（指摘1。150ms の前後に散ることの裏付け）。
- QuizContainer.tsx: 診断は、答えが入ってからの effect で `ANSWER_SHOWN_MS`（150）のタイマーを掛けて次の問へ進む。measure.mjs の `SHOWN_MS` も 150 で、`crossesShown` は 90・300ms の回だけを、境目を越えたかで見ている（指摘1）。
- cycle-318/device-triage.md 1章: iOS の Safari 48.6%（mobile 47.3%・tablet 1.3%）、iOS 合わせて 58.9%、Android 30.4%（指摘2）。
- t5a-design.md 4-9 の表: L1 は時間で捨てる、L2 は `detail ≥ 2` で捨てる、L3 は何もしない、L4 は着地の選び方（PM が直して閉じるもの）。
