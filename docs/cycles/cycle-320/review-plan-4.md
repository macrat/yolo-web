## 指摘

### 1. 分ける線の物差し（T5a-6 の15本の走査）が量の物差しにならず、途中で止まったときの続け方も無い（中）

作業内容 3 は「1人の担当が1回で走らせる量を、cycle-319 の T5a-6 の builder の15本の走査（1人で走らせ切った量）を目安に置き」とする。cycle-319 の補足事項によれば、その走査は 375×550 の1度押しだけで、約 157 の押しである。一方、条件7 は1つの版で数万の押しになる見込みと計画自身が書く。押しの数で物差しにすれば数百の担当に分ける線になり、時間で物差しにするなら、その走査に何分掛かったかの記録が無い。どちらに読んでも PM は線を引けない。これは計画が避けたかった「根拠の無い線」を、物差しの形で残している。

担当の負荷を決めるのは、押しの数ではなく、道具が自分で走るあいだの壁時計の時間（1回の背景のコマンドは最長2時間）と、担当が読んで t5a-measure.md に書く表の量である。cycle-316 の T5a-2 の打ち切りも、負荷で1回に時間が掛かり報告の期限に掛かったものだった（t5a-measure.md 5-1・5-3）。物差しを「T5a-7a-1 の見積もりの時間で、1人の担当が受け持つ時間（例: 背景のコマンド N 回分）と書く表の数」に替える。

あわせて、測りの担当が途中で止まったときの続け方を、T5a-7a-1 の道具と手順の文に入れる。道具は走査ごとに記録を書き、済んだ走査を飛ばして続きから走れること、次の担当は残りだけを測ることを書く。これが無いと、止まった担当の分を最初から測り直すか、どこまで済んだかを担当がその場で決めることになる。

### 2. 見積もりがこのサイクルに収まらないときの道と、基準の版で測り直す範囲が決まっていない（中）

見積もりのあとで決めるのは妥当だが、決めるときに選べる道を計画に置いていない。算術で見ると、変更後の版の「もう一度挑戦する」は、2,115点（5-4 の基準の版の点の数）× 2間隔 × 2入力で約 8,500回あり、どの回も新しい文脈で開いて結果まで解いてから押す（6章 条件7「どの回も、Web フォントを読み込んでいない新しい文脈から始める」）。1回に10秒掛かれば、それだけで約 23時間になる（推論。1回の時間は見積もりで分かる）。T5a-7a は並行させないので、このサイクルに収まらない見込みがある。そうなったとき PM が何を選ぶか（測りを次のサイクルへ分ける・6章の手順を変える（設計の文の直しとレビューが要る）・並べて走らせる（負荷で間隔が延びる。指摘11））が無いと、PM はその場で決めることになる。選べる道と、選ぶときの線（例: 見積もりの合計が何時間を超えたら）を作業内容 3 に書く。

もう1つ、基準の版の条件7 をどこまで測り直すかが曖昧である。作業内容 4 は「6章の…すべてを測る（…5-1 の 375×550 の 200% のマウスの5つの間隔を含む）」と書く。5-2・5-3 は「比べる先には使わない」と t5a-measure.md が書くので測り直しが要るが、5-1 と 5-4 はそう書いていない。5-4 は「押したあとに送らない変更前のコードでだけ成り立つ」静止の走査を正としており、基準の版ではそのまま使える。5-1 の欠けを名指すのは、5-1 のほかを使う読み方にも取れる。一方で、計画は記録をセッションを越えて確かめ直せる形に残すことを選んでおり、5-1・5-4 には走査ごとの記録が無い。どちらを採るか（5-1・5-4 を基準の値として使うか、記録を残すために測り直すか、5-4 は基準の版でも静止の走査でよいか）を計画で決めて書く。最も重い項目の量が半分ほど変わる。0章の確かめで基準の版を替えたときは、5-1・5-4 も使えなくなることも書く。

### 3. 作業内容 3 の PM の決定がレビューに通らない（中）

作業内容 3 は「PM が…決め、ここに書いてから担当を起こす」とだけ書き、reviewer に通す手順が無い。分け方と記録の上限は計画の一部で、何を main の履歴に残すか・何を捨てるかを決める。CLAUDE.md の「Review always」は計画を含むすべての作業にレビューを求める。作業内容 3 に「reviewer に通し、承認を受けてから測りの担当を起こす」を足し、「実施する作業」の行にも入れる。

### 4. T5a-8 で、設計の文の直しのあとに同じ builder へ SendMessage でコードの直しを頼む（中）

作業内容 6 は「承認を受けてから、同じ builder に SendMessage でコードの直しを頼む」とする。設計の文の書き直しとコードの直しは、別々のレビューを受ける別の仕事で、間に reviewer の往復を挟む。AP-WF10 は、SendMessage を同じタスクの軽い直しと問いに限り、別の仕事を同じ担当に続けて渡してコンテキストを積ませないことを求める。計画は T5a-7a では「前のタスクの担当を続けて使わず、新しい担当で起こす」と決めており、T5a-8 だけが逆になっている。

設計の文の枝をレビューのあとで PM が取り込み、そのあとの HEAD から新しい builder（担当の木）を起こしてコードを直させる形にする。新しい builder は取り込んだ設計の文を読んで直せるので、同じ担当である必要が無い。レビューの指摘を受けた設計の文の直し（同じタスクの軽い直し）に SendMessage を使うのは差し支えない。

### 5. 「組みを直す」ときの測り直しの範囲の決め方と、範囲を誰が決めるかが無い（中）

前回の指摘4の2つ目の箇条の残りである。作業内容 6 の測り直しの範囲は「差分が通るコードが掛かる操作の条件7・D5 の回」で、`reveal.ts` の洗い出しと、CSS の直しの撮り比べの範囲（読み込みの連なり）は書いた。だが、CSS の組みを直したときに、どの操作の測りをやり直すかは `grep` でも読み込みの連なりでも決まらない。例えば開始の画面の「はじめる」の位置を変えると、「はじめる」の2打目と、開始の画面に着く「もう一度挑戦する」の着地の両方が変わる。測りの担当に「差分が通るコードが掛かる操作」とだけ渡すと、「もう一度挑戦する」を外しうる。

組みを直したときは、変えた規則が当たる画面に着く操作とその画面から離れる操作をすべて範囲に入れる、と書く。範囲は、builder の洗い出しを受けて PM が決め、設計の文と同じレビューか、測り直しの依頼の前のレビューに通す、と書く。いまの文では、範囲を決めるのが builder か測りの担当か PM かが読めない。

### 6. D5 の操作に「もう一度挑戦する」が入っている（中）

作業内容 4 の D5 の箇条は、操作ごとの数を「「はじめる」・診断の答え・知識クイズの答えと「次へ」・最後の答えと最後の「次へ」・「もう一度挑戦する」」で書くとする。device-triage.md D5 の走査の操作は「はじめる」・答えと「次へ」・最後の答えと最後の「次へ」の3つで、「もう一度挑戦する」を含まない。このまま渡すと、担当は D5 に「もう一度挑戦する」のずらしを足すか（2,115点 × 6ずれ × 2画面…で、いちばん重い項目がさらに数倍になる）、D5 の文と食い違う計画のどちらに従うかで迷う。見積もり（作業内容 2）にも同じ食い違いが入る。D5 の操作に合わせて「もう一度挑戦する」を外すか、足すならその理由と D5 の文の直しを書く。

### 7. 5MB の目安に根拠が書かれていず、T5a-8 の測り直しの記録が数に入るかが無い（軽）

作業内容 3 の「合計 5MB を目安」は、前回の 2MB と同じく出どころが無い。計画は「計画の段で根拠の無い線を引かない」ために見積もりを待つ形にしたが、上限だけは線が先にある。参考の事実は、追跡のファイルで最大のものが約 1.1MB、`.git` が 57MB で、git は中身を圧縮して持つ（`.jsonl` はよく縮む）こと。目安を置くなら、この事実のどれに拠るかを1文で書くか、目安を外して作業内容 3 で PM が決める線にする。あわせて、合計に T5a-8 の測り直しの記録を入れるかを書く。

### 8. B-623 を閉じる値を、T5a-8 が「次へ」に掛からなかったときにどこから取るかが無い（軽）

前回の指摘7の後半の残りである。「B-623 を Done に移す」は「T5a-8 のあとの版で、条件7 と D5 の走査のどちらでも…0 と確かめたあと」とする。T5a-8 の測り直しは差分が通る操作だけなので、直しが「次へ」に掛からなければ、T5a-8 のあとの版の「次へ」の値は測られない。そのときは変更後の版（T5a-7a）の値をそのまま使う、と書く。直す件が無く T5a-8 を閉じたときも同じである。

### 9. `reveal.ts` を変えたときの洗い出しが、直に読み込む面だけで、`ResultBox` を使う面に届かない（軽）

作業内容 6 の列挙は直に読み込む10のファイルで、その中の `ResultBox` は部品である。`ResultBox` の `revealFocusedFrame` は `visibleRange()` を通るので、`visibleRange()` を変えると、`ResultBox` を使う面（試験でないファイルで15。道具の結果・日替わりのページ・診断の結果など）の送りが変わる。洗い出しを読み込みの連なりでたどることにし（CSS の直しと同じ書き方）、送りの位置の前と後の比べは `ResultBox` を使う面も含めると書く。

### 10. 記録の形と `format:check` の関係、T5a-7a-1 の試しの走りの記録の置き場が無い（軽）

上の「消えた文」のとおりである。Prettier は `.json` を扱うので、道具が `.json` で書いた記録は `format:check` に掛かり、整えていなければ push の前の検査と CI で止まる。作業内容 3 で形を決めるときに、`.jsonl`（Prettier が扱わない）にするか、`.json` なら `npm run format` を通すことを書く。また、T5a-7a-1 の数本の試しの走りは手順の文を直す前のもので、本番の測りの数ではない。その記録は `tmp/` に書いてコミットしない（または `measure/` に置くなら試しと分かる名にする）と書く。いまは「走査ごとの記録は、道具が `measure/` に直に書く」だけなので、試しの記録が本番の記録に混ざりうる。

### 11. 負荷で実際の間隔が 150ms の境を越えた回の扱いが無い（軽）

t5a-measure.md 0章は、測ったあいだの負荷（load average 26〜45）で実際の間隔が指定より長くなった回があったと書く。変更後の版では、90ms の回は「見せる 150ms の内」、300ms の回は「外」を試すための値である（6章 条件7）。90ms の指定が負荷で 150ms を越えると、その回は内を試しておらず、次の問に落ちた数（B-620 の材料）の束に別の条件の回が混ざる。T5a-7a-1 で、実際の間隔を押しごとに記録すること（いまは中央値だけ）と、境を越えた回を送り直すか、そのまま数えて別に書くかを決めて手順の文に書く、と足す。
