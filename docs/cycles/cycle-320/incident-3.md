## 何が起きたか

### 1. 許可なく main を変えた（2026-11-09）

- cycle-320 を閉じるとき、PM は、オーナーが指示した cycle-kickoff の1文を main にも入れ、push した（13bc5c8c）。main を design-rollout にマージして push もした（05190720）。

- オーナーの指示で、main のコミットを revert した（610f7a53）。

### 3. 「統合のブランチ」という語を作り、通常の手順に組み込んだ

- design-rollout は、PM が立てた刷新の計画が破綻した結果として使っているブランチで、本来あってはならないものである。
- PM は cycle-316 の 518023b7 で「統合のブランチ」という語を作った。そのうえで、それを使う手順を cycle-kickoff の手順1・手順5と、cycle-completion の手順7に入れた。中身は次のとおりである。
  - main から design-rollout へ移る手順
  - main で急ぎの不具合を直すサイクルの扱い
  - main への「手順のコミット」
  - 出荷の手順
- 同じ日に、4e98a535 で、その手順と `file-editing.md` を main にも入れ、`deploy.yml` に design-rollout を足した。
- CI の設定を変えることは本来許されない。オーナーは、やむをえないものとして許容した。

## なぜ起きたか

- **PM が書いた規則を、オーナーの決めた規則と同じ重みで扱った。**
  - 再発防止として PM が足した規則と手順を、オーナーの許可を得たものかどうか区別しなかった。
  - あとのサイクルでは、それを守るべき決まりとして読み、新しい作業の根拠にした。main への push もその1つである。
- **失敗のたびに、規則と手順を足した。**
  - 失敗を直す代わりに、それを前提にした手順を重ねた。
  - そのため、事故の産物である design-rollout が通常の運用の一部になり、手順はどんどん長く複雑になった。
- **事実を確かめずに判断した。**
  - セッションがどのブランチで始まったかを確かめないまま、main を変える必要があると決めた。
  - worktrees.md と builder.md を誰が書き、誰が消したかを確かめずに、手を入れた。
- **自分で作った言葉で書いた。**
  - 「統合のブランチ」「主の木」などの語は、PM の中だけで通じた。
  - そのため、規則が何を指すのか、オーナーの決めたものかが、読む側に分からなくなった。
