# cycle-317 のワークフローのアンチパターンの点検

対象: cycle-317 の index.md と補助ファイル18本、`git log --oneline f044286~10..HEAD`（HEAD は 0294b420）。照らしたもの: docs/anti-patterns/workflow.md の全項目と planning.md の AP-WF12 に近い項目。

## 項目ごとの確かめ

- AP-WF01（最後の修正のあとのレビュー）: T5-33（76de7152 → 第2回承認）、T5-8b・T5-20d（82262679 → 第2回承認）、B-784（第4回承認）、B-786（第2回承認）は、どれも最後の直しのあとにレビューを受けている。ただし、最後のコミット 0294b420（index.md の完了の記録、backlog の B-641 の更新と B-787 の起票）は、まだ誰のレビューも受けていない。作業内容4の「全体のレビュー」をこれから受けるのであれば違反にはならない。そのレビューの範囲に 0294b420 を必ず含めること。
- AP-WF02・AP-WF05（来訪者の目、画面の撮り比べ）: tmp/cycle-317/before/ には 320・375・1280 の画面幅で、明と暗の両方の画像がある（暗は27枚）。変更後の画像は、T5-33 と T5-8b の各レビューで撮っている。**当たる**: T5-33 の builder は、第1回の報告の時点で画面を確かめていなかった（review-t5-33.md の指摘3）。直す回で builder が撮ったので、来訪者に届くものへの害は無い。それでも AP-WF05 の型は起きている。index.md にこのことの記録は無く、workflow.md の AP-WF05 の発生の欄にも 317 が無い。
- AP-WF12（フレームワークの API の挙動を思い込みで書く）: **当たる**。b784-design.md の第3節は「注意の線を超えたら stderr に出して exit 0」としていた。設計のレビューは4回あったが通ってしまい、実装のレビュー第1回で誤りと分かった。公式文書（https://code.claude.com/docs/en/hooks）には「Stderr from a hook that exits 0 goes to the debug log only … Claude never sees it」とあり、点検の際に私も確かめた。設計の段階で一次の文書を確かめていれば防げた。ほかにも、設計が付け替えの先として挙げた `decisions-process.md` は実在しない名前で、実装に入ったあとに直した（review-b784-impl.md の指摘2）。最終形では2件とも直っていて、来訪者に届くものへの害は無い。ただし、どちらも index.md に記録されておらず、AP-WF12 の発生の欄にも 317 が無い。
- AP-WF08（PM の代行・改変）: **当たる**。33bd83af で、PM が planner の成果物の b784-design.md の第3節を自分で書き換えている。これは判断を伴う中身の変更で、機械的な整形ではない。この書き換えのあと、設計の文書としてのレビューは受けていない（実装のレビュー第2回は実装を見たもの）。中身は公式文書と合っていて正しい。それでも、planner に直させてレビューに通すべきだった。あわせて、review-b786-design*.md・review-b784-design*.md・review-b7*-impl.md は「reviewer の報告を PM が写した」とあり、5〜14行の要約になっている。これは「成果物を要約・解釈してファイルに保存」に近い。一方、T5 の2本は reviewer が自分で書いた形で、こちらは問題が無い。
- AP-WF03・AP-WF06: 依頼文そのものは記録に無いので、確かめられない。記録に残っている事実（git 2.43.0、git-worktree の仕様、0.1625 の再現の条件）は、どれも実測と出典が付いている。
- AP-WF07・AP-WF13: T5-8b と T5-20d は、元のコミット 83a8cbd9 を共有し、同じファイルを触る。だから1人に任せたのは妥当。builder は `joinDashes` を直し、その変更はサイト全体の `PhrasedText` に及ぶ。スコープの外へ出てはいるが、測りの中で見つけた欠陥で、reviewer も確かめて認めたので許容できる。ただ、「サイトの全体で悪くなる例は見つからなかった」と書いてあるのに、何件を見たのかが書かれていない（AP-WF09 の網羅の主張に近い）。重い指摘ではないが、件数を残しておくのが望ましい。
- AP-WF09・AP-WF14: 数値の採否は、reviewer が自分で測り直している（0.1625 の再現、45.8px と 34.8px の内訳、cycle-316 の文書の大きさ）。形式だけの通過は見当たらない。
- AP-WF10・AP-WF11: 再レビューは回ごとに別の記録になっている。PM の判断（0.0112 を受け入れる、45.8px をキャリーオーバーにする、4-2 の5を満たしたとする）は理由付きで記録されている。
- AP-WF15・AP-WF23: 完了のチェックリストにはまだチェックが入っておらず、先にチェックした跡は無い。
- AP-WF24・AP-WF27: Owner に許可を求めたり、Owner を駆動源として書いたりした所は無い（B-786 の第4回で、Owner に枝を消してもらう案を退けている）。
- AP-WF29: 記録と中身が食い違う所は見当たらない（index.md の表とレビューの記録の回数は一致する）。
- AP-WF30: B-787（45.8px）は、「来訪者に届くのは1000日より先」という評価を、着手の時期を決めるのに使っている。直すことをやめたわけではなく、規則を設計に足すことまでを backlog に起票している。だから範囲を縮めたことには当たらない。0.0112 を受け入れた判断は、代わりの形が来訪者にとってより悪いことを理由にしていて、到達性の評価で範囲を縮めたものではない。
- AP-WF38・AP-WF39: B-786 の設計は7回のレビューを受けた。指摘は、Owner の役割に反すること、b784 との順序の依存、行番号の事実のずれなど実体のある誤りで、磨き込みの巡回ではなかった。来訪者に届くものの品質レビューを途中で打ち切った所は無い。
- AP-WF41: 改稿のたびに、全体の見直しをレビューに含めている（T5-8b の第2回は「第1回に見た所を含めて見直した」と書いている）。
- AP-WF50: 取り込みは、担当の枝ごとの merge コミット（0dd6f6e4・b85ad60b・8b8a502b）で行っていて、各レビューは `f044286...<枝>` の差分で範囲を確かめている。B-786 の実測で使った probe の枝は取り込んでいない。

## ブログと ADR の判断

- ブログを書かない判断: 妥当。来訪者に届く変更は design-rollout の出荷まで本番に出ないので、いま書けば読者が確かめられない話になる。B-784・B-786 は内部の道具で、読者の学びになりにくい。ただし、**この判断が index.md のどこにも書かれていない**（index.md と split-plan.md を「ブログ」で grep して確かめた）。出荷のときに記事を考える担い手がどこにも書かれていないと、判断そのものが後に残らない。
- ADR を起票しない判断: 妥当。出荷した賭けは無く、worktree とコミットする者の決まりは `.claude/rules/delegation.md` などの規則に、文書の大きさの線は hook と doc-directory.md に、それぞれ入っている。これも**記録が無い**。

## プロダクトへの害

来訪者に届くもの（irodori の CLS、DataTable、漢字カナールの結果の表、joinDashes）は、最終形でどれもレビューの承認を受けている。上で当たった AP-WF05・AP-WF08・AP-WF12 が来訪者に届くものに残した欠陥は見つからなかった。害が出たのは道具（hook の注意が Claude に届かない設計）の側だけで、それも実装の段階で直っている。

## 要対応

1. index.md に、このサイクルで起きた AP-WF05（T5-33 の builder が画面を確かめなかった）、AP-WF12（b784 の stderr の前提と、実在しないファイル名）、AP-WF08（PM が設計の文書を直接書き換えた）を記録する。workflow.md の各項目の発生の欄に 317 を足す。
2. b784-design.md の第3節の書き換えは、planner の作業として扱い直してレビューに通す。少なくとも、この書き換えを全体のレビューの範囲に含め、PM が書き換えた経緯を index.md に書く。
3. ブログを書かない判断と ADR を起票しない判断を、理由とあわせて index.md の補足事項に書く。
4. 0294b420 以降の記録の変更（上の1〜3を含む）を、全体のレビューで見てもらう。
