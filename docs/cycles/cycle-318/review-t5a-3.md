## 指摘

### 1.（直す）開始の画面が画面より高いとき、押した点があると「はじめる」が画面の外に出る（builder の判断3）

`planFromPageTop` の範囲は `groupSpan` を使い、まとまりが画面より高いときは「上端を画面の上端から 8px に置く送り」の1点になる。ところが基準（`base`）は 4-8 のとおり「はじめる」の下端を画面の下端から 8px 上に置く送りで、この1点と一致しない。`chooseLanding` は範囲が空でなければ範囲の中から選ぶので、ポインタで押したときは必ずこの1点に着く。

担当の木で確かめた値（`npx tsx`。画面 0〜600、いまの位置 1200、事実の行から「はじめる」まで 900 の高さ。200% の開始の画面にあたる）:

```
plan { base: -592, span: { min: -908, max: -908 } }
keyboard -592   // 「はじめる」の下端が 592 に来る
pointer  -908   // 事実の行が 8 に来て、「はじめる」の下端は 908（画面の外）
```

- 4-8 の「入らないとき（200% など）は、「はじめる」の下端が画面の下端から 8px 上に来るまで送る」に反する。200% の来訪者が「もう一度挑戦する」を押すと、押した次の画面で「はじめる」が見えず、自分で送って探すことになる。キーボードで押した来訪者とは着く所が違う。
- 4-9 の表の「もう一度挑戦する」の行の見せる範囲は「事実の行から「はじめる」までが丸ごと入る送り」で、高いときの例外を持たない（「問のまとまり」の行だけが「画面より高ければ、帯を上端から 8px に置く送りだけ」を持つ）。丸ごと入らなければ範囲は空で、手順2 の「範囲が空なら s0 だけにする」により基準のままになる。
- 直し方: `planFromPageTop` の範囲は、まとまりが上下の 8px を除いた画面に入らないとき空にする（`groupSpan` の「高いときは上端 8px の1点」を共有しない）。単体試験に「画面より高い開始の画面は範囲が空で、押した点があっても基準（「はじめる」の下端を下端から 8px 上）に着く」を足す。いまの試験にはこの場合が無く、誤りが通った。

### 2.（直す）基準は丸め、範囲は丸めないので、ポインタとキーボードで着く所が端数ずれ、1px 刻みの候補が端数になる

`groupRevealDistance`・`planHeadedBox` の基準は 8px の空きが欠けない向きに整数へ丸めるが、`groupSpan`・`planHeadedBox` の範囲の端は丸めない。基準が範囲の外にあると `stepsNearBase` は範囲の端（端数）から始めるので、候補がすべて端数になる。

確かめた値: `planGroup({ top: 100.3, bottom: 800 }, { top: 0, bottom: 600 })` は `{ base: 92, span: { min: 92.3, max: 92.3 } }` で、押した点があれば 92.3、キーボードなら 92 に着く。

- 来訪者に見える差は1px に満たないが、同じ画面の着地が入力の手段で変わり、「基準は整数・候補は 1px 刻み」という 4-9 の手順5 の前提が崩れる。
- 直し方: 範囲の端を、8px の空きが欠けない向き（`min` は切り上げ、`max` は切り捨て）に丸めて持つ。丸めは1か所（範囲を作る所か `chooseLanding` の打ち切りの所）に置く。丸めて空になれば、手順2 のとおり基準になる。端数の試験を1つ足す。

### 3.（直す）同じ近さのときの向き（builder の判断1）を試験が固めておらず、理由もコメントに無い

判断そのもの（同じ近さなら下へ送るほうを選ぶ）は、設計が決めていない所を決定的にするもので、受け入れてよい。ただし:

- `stepsNearBase` の `+offset` と `-offset` の積む順を入れ替えても、いまの試験は1つも落ちない（試験の値はどれも同点にならない）。「基準が送らないとき」と「送るとき」それぞれに、上下に同じ近さの候補がある場合を1つずつ足す。
- コメントは「同じ近さなら下へ送るほうを先にする」と何をするかだけを書く。なぜ下か（たとえば、下へ送れば来訪者がこれから読む下の側が見える、など）を書く（coding-rules.md 4）。

### 4.（直す）古い定義のままの試験の名前

`reveal.test.ts` の2つの試験の名前が、変える前の範囲の式を言っている。

- 121行「visibleRange() の画面の下端（visualViewport の offsetTop + height）で測る」
- 213行「visibleRange() の画面の範囲（visualViewport の上端と高さ）で測る」

いまの下端は `offsetTop + min(visualViewport.height, 小さいビューポートの高さ)` で、この2つは jsdom で小さいビューポートが 0 と読める場合を通っているだけである。「文字盤で visualViewport が狭まったとき、その範囲で測る」のように、試験が確かめていることに合わせて名前を直す（No patchwork）。

### 5.（直す）`measureGroupPlan`・`measurePageTopPlan`・`measureHeadedBoxPlan` に試験が無い

3つは要素から測って純粋な関数へ渡す薄い関数で、T5a-6 が使う。とくに `measurePageTopPlan` は `window.scrollY` の符号（頭へ戻す送りは `-scrollY`）を持ち込み、`measureHeadedBoxPlan` は頭の要素の下端を渡す。渡し違えても今の試験は通る。`revealGroup` と同じく、置いた矩形と `scrollY` から期待の組が返ることを1つずつ確かめる（作業内容6 の「変わる所を単体試験で固める」）。

## `visibleRange()` の測りの費用

- 1回の呼び出しで、箱を付けて読む（スタイルとレイアウトの強制1回）と、外したあとの最初の矩形の読み（もう1回）が起きる。
- 担当の木の開発サーバーで、ゲーム4本と道具3本のページで、箱を付けて読み外し、`body` の矩形を読む組を100回回した1回あたりは 0.037〜0.072ms だった（コンテナの Chromium、375×667）。遅い端末で10倍としても 1ms に届かない。
- 呼ばれるのは操作ごとに1〜2回である: 道具の結果（`revealResult`。入力の確定や押したとき）、ゲームの推測の送信・語を4つ選んだとき・チェック・決定・次へ（`revealControl` と面の中の送り）、`ResultBox` の Tab での着地（`revealFocusedFrame` が2回）。打鍵ごとには呼ばれない（kanji-kanaru・yoji-kimeru は送信のあと、base64 は結果が出たあとに1回）。T5a-6 の着地も切り替わりごとに1回である。
- したがって来訪者の操作の応えは遅くならない。`resize` で測り直して値を持つ形は、測り直しの時（回転・拡大・ツールバーの出入りで `resize` が来るか）を端末ごとに見極める手間と、持った値が古くなる危険を足すだけで得が無いので、勧めない。いまの形のままでよい。
- 箱は `<html>` の直下に一瞬付く。`src` に `MutationObserver` は無く（grep）、CSP の見出しも無いので、ほかの仕掛けを起こさない。
