### 4. 2章: WebKit blog の要約が誤っている（重）

2章の「一次資料で決まらないこと」の1つ目（52行）は「WebKit blog は1回の押しの速さだけを言う」と書く。しかし blog は、`width=device-width` のページで初めの倍率のときは、**2度の押しの身ぶりを止めることで**1回の押しの遅れを無くした、と書いている（"we've implemented a mechanism for removing the delay for single taps by disabling double tap gestures"・"viewports that have width=device-width will have fast single tapping when the user is at initial scale"）。同じ blog は、`touch-action: manipulation` は**どの倍率でも**効く、とも書く（2章41行の要約に無い）。

### 5. 2章: WebKit の `button` の既定の要約が誤っており、D3 で足す宣言の選び方も理屈と合っていない（重）

2章47行は、WebKit の `button` の既定が「どの端末の版でも…`text-align: start` を持つ」と書く。しかし `html.css` では、まとめた規則（`input, textarea, select, button`）の `text-align: start` のあとに、`button` を含む規則が**どの端末でも** `text-align: center`・`padding-inline: 6px`・`cursor: default` を掛ける（main の `Source/WebCore/css/html.css` の `input:is([type="button"], …), button {` の規則）。まとめた規則は `text-shadow: none` も持つ。

`Button.module.css` が `text-align: start` を、`data-text-box` が左右の余白を決めるので、実害は無い。ただし事実の誤りなので直す。

D3 の (i) は、iOS の `font: 11px system-ui` が既定に戻すものを「太さや字形」とまとめ、6つの宣言を足す。しかし `font` の一括指定は、`font-variant-*`・`font-stretch`・`font-kerning` なども初期値に戻す。D3 の理屈（`span` は祖先から継ぐので、祖先が変われば分かれる）は、これらにも同じく当てはまる。一方で、T5a-7 で比べる計算値の一覧（117行）には `font-stretch`・`font-feature-settings`・`font-kerning` が入っている。足す宣言と比べる計算値が食い違っている。

- 直し: 2章の要約を直す。足す宣言は、`font` の一括指定で戻るものと、まとめた規則が決めて字の組みに効くもの（字の幅・位置・行に効くもの）をすべて洗い出したうえで、決める。外すものがあれば理由を書く。比べる計算値の一覧も、それに合わせる。

### 6. D4: `visibleRange()` を変えたときの、ほかの面への影響の見積もりが足りない（重）

D4 は「`revealResult`・`revealControl`（道具とゲーム）も同じ `visibleRange()` を使うので、同じ範囲になる」と1文で済ませている（129行）。実際は次のとおりである。

- `visibleRange()` を呼ぶもの: `revealResult`（base64・age-calculator・json-formatter）、`revealControl`（yoji-kimeru の2か所・nakamawake・irodori・kanji-kanaru）、`revealFocusedFrame`（`ResultBox`。キーボードで結果の送る区画に着いたとき。`ResultBox` を使うすべての面）。
- `visibleRange()` を使わず、同じ計算を面の中に書いているもの: nakamawake `GameContainer.tsx` 172〜177行の別の `visibleRange()`（`revealFocusedWord`・`revealResultHead` が使う）、kanji-kanaru `GameContainer.tsx` 295〜297行。`reveal.ts` だけを変えると、同じゲームの中で「画面」の定義が2つになる。kanji-kanaru では、入力の欄は新しい範囲で、結果のボックスは古い範囲で送ることになる。
- iOS（と Android の Chrome）でツールバーが縮んでいると、これまで見えているとみなして送らなかった、画面の下のツールバーの高さの帯にあるものを、送るようになる。道具の結果やゲームのコントロールで、送りが増える。来訪者の益になる向き（ツールバーが出ても隠れない）だが、どの面でいつ動きが増えるかを書いていない。
- Chromium では `100svh` が `innerHeight` に等しいので、この変更はコンテナの測りでは何も変えない。確かめられるのは単体試験だけである。この点も書いていない。
- jsdom では、見えない要素の高さが 0 になる。そのまま小さいほうを取ると範囲の高さが 0 になり、送りの関数を使うほかの面の試験とふるまいが崩れる。0 のとき（組まれていないとき）は `visualViewport` の高さに落とす決まりと、その試験が要る。
- index.md は、T5a-3 を「画面に繋がない純粋な関数なので、本体と切り離してレビューできる」とした（作業計画の「検討した他の選択肢」）。`visibleRange()` を変えると、T5a-3 を取り込んだ時点で、道具とゲームの出荷の中身が変わる。この前提と合わない。
- 直し: 影響を受ける面を上のとおり並べて、ふるまいがどう変わるかを書く。面の中の重複（nakamawake・kanji-kanaru）を `reveal.ts` にそろえるかどうかを決め、行き先（担うタスク、または PM が backlog に起こすこと）を書く。0 のときに落とす先と、その試験を T5a-3 の行き先に足す。T5a-3 がほかの面のふるまいを変えることを、PM が受け入れるかを判断できるよう、6章に書く。
