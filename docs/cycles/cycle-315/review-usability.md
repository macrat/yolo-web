## Blocker

### BL-1 押せる副操作と、押せない区画が、同じ形を持つ

§6 は L159 で「**押せるものと押せないものは形で区別される。色では区別しない。**」と宣言する。**定義自身がこれを満たしていない。**

| 何                     | 定義                                         | 押せるか     |
| ---------------------- | -------------------------------------------- | ------------ |
| 副操作（§6 L149）      | 「`--rule-w` の枠だけ。地は `--paper`」      | **押せる**   |
| 結果の区画（§8 L203）  | 「`--rule-w` の枠で囲んだ区画」              | 押せない     |
| 広告の区画（§12 L235） | 「`--paper-2` の区画 ＋ `--rule-w` の枠」    | ふつう押せる |
| 一覧の外枠（§5 L123）  | 「区画の枠は内容の幅で閉じる。…一覧の外枠…」 | 押せない     |

4つとも「`--paper` の地に 3px の `--ink` の枠」である。違いは大きさと中身の文言だけで、**形は同一**。
色も影も角丸も使えない（§5 L127・L128）ため、形以外に手がかりが無い。再描画したモックでも、副操作「やりなおす」・結果の区画・広告の区画は同じ 3px の枠で並んでいる。

実害は両方向に出る。押せる副操作が「ただの囲み」に見えて押されない。押せない結果の区画が押せると思われて空振りする。
**§6 L143「役割ごとに別の記号。一つの記号が二つの意味を持たない」が、§5・§8・§12 との間で破れている。**

### BL-2 ナビ・一覧の行・ページ送りに「押せる」記号が無い

§6 の記号表が持つのは **本文中のリンク／主操作／副操作** の3つだけである。一方、来訪者がもっとも多く押すのは次の3つで、どれも表に無い。

- **上端のナビ**——§5 L137「ナビは**文字だけ**で、背景色と影を持たない」。現在地だけは §6 L151 が縦罫＋太字を与えるが、**現在地でない項目には何も与えられていない。**
- **一覧の行**——§7 L172「**行全体が標的**」。行が押せることを示す記号は §7 にも §6 にも無い。
- **ページ送り**——§7 L183。記号も現在ページの示し方も無い（現在地の「左端の縦罫」は横並びのページ番号に当てはまらない）。

§6 L147 の下線は「**本文中の**リンク」に限定されており、§4 L103「下線はリンクの専有」は下線をリンク以外に使うなと言っているだけで、**すべてのリンクに下線を義務づけていない。**
再描画したモックでは、ナビ項目も一覧の行のリンクも `text-decoration: none` で、静的テキストと**完全に同一**だった（実測）。

§6 L150 の hover はタッチ端末に存在しないため、スマートフォンの来訪者にはこれらが押せるという手がかりが**ゼロ**になる。
「色を使わずに操作を示す」（担い手3・§1 L26）を掲げながら、**主要な操作の記号が定義されていない**。担い手3が成立していない。

### BL-3 エラーの記号が、入力欄の平常時に埋没する

§8 L198「**エラーは入力欄の左端の `--rule-w` の縦罫**と、直下の文字で示す。…**色では示さない。**」
§5 L112 は `--rule-w`（3px）の用途に「**操作の部品の枠**」を挙げる。**入力欄は平常時から四辺に 3px の `--ink` の枠を持つ**——左端にはすでに「`--rule-w` の縦罫」がある。

**したがってエラー時に入力欄の見え方は変わらない。** 再描画したモックでも、エラーを持つ「回数」欄は、エラーの無い欄と完全に同じに見える。

色が使えず（§8 L198）、絵文字も図像も使えない（§5 L131）ので、**欄そのものに付けられる印が定義の中に存在しない。**
残るのは直下の文だけで、項目が複数あるフォームでは、どこが誤りかを知るのに**全部の欄の下を読む**ことになる。拡大表示の人は画面外の欄を見落とす。

WCAG 3.3.1 は文字で示せば満たすため**違反ではない**。だが「誰もが使える」の水準としては、エラーの発見が確実に遅れる。

### BL-4 「左端の `--rule-w` の縦罫」が、現在地とエラーの二役をしている

- §6 L151 **現在地**——「反転しない。左端に `--rule-w` の縦罫 ＋ 太字」
- §8 L198 **エラー**——「入力欄の左端の `--rule-w` の縦罫と、直下の文字」

同じ記号である。区別できるのは太字かどうかだけで、**§6 L143「一つの記号が二つの意味を持たない」に真正面から反する。**
実物では、ナビの現在地「ぜんぶ」の左の罫と、エラー文の左の罫が同じ太さ・同じ色・同じ位置関係で並ぶ。
現在地は「ここに居る」、エラーは「ここが間違い」で、意味の向きが逆である。取り違えは、初見の人ほど起きる。

## Major

### MJ-1 hover の罫が、隣の行に食い込む

§6 L150「hover / active——**8px 離れた外側に `--rule-w-hair` の罫が1本増える。**」
§7 は一覧を「1行1項目・`--rule-w-hair` で区切る」と定め、§5 L130 は「罫の内側に最低 16px の余白」を要求する。
行の上下の余白は 16px しかないので、**8px 外側の罫は必ず区切り罫を越えて隣の行の領域に入る。**

モックで実際に hover させて確認した。ある行に hover すると、増えた罫は**上の行の説明文のすぐ下を横切り**、下の行の上端にも入る。
どの行を指しているのかが一目で決まらない。行が標的（§7 L172）である以上、これは押し間違いに直結する。

縦に積む操作（一覧の行・積み上げたボタン）に対して、「外側 8px」は定義として成立していない。

### MJ-2 広告と結果が同じ形で、分離を担うのは 14px のラベルだけ

§12 L235「広告は `--paper-2` の区画 ＋ `--rule-w` の枠 ＋『広告』ラベルで、**本文と結果から分離されている。境界を担うのは枠である。**」
ところが**その枠は、結果の区画（§8 L203）と同じ 3px の `--ink` の枠**である。枠は何も分離していない。
`--paper-2` は §2 L65 で「境界を担わない」と明言されている（比は light 1.12・dark 1.14）。

**残る手がかりは「広告」の文字だけ**だが、§12 はその大きさも濃さも決めていない。
§4 L97 の補助情報の下限（14px）と `--ink-2` を当てるのが定義上もっとも自然で、モックもそうなっている——**ページで一番弱い文字が、広告と中身を分ける唯一の手がかりになる。**

急いで見る人・拡大している人・認知の負荷が高い状態の人は、枠に囲まれた区画を結果と読む。
広告を中身と取り違えさせることは、constitution rule 2（来訪者を悲しませない）に触れる種類の失敗である。

### MJ-3 一覧に検索が無い

§7 L178「**項目は増え続ける。1画面に収まらなくなった時点で、走査の速さは設計で作るものになる。**」と書きながら、
用意されている手段は **既定の並び順・種別の絞り込み・全体の件数・ページ送り**の4つだけで、**名前で探す手段が無い。**

種別は絞り込みの粒度が粗い（モックの例で「しらべる／ためす／よむ／いろ／つかう」）。
「藍色」を見に来た人は、`いろ` で絞ってもなお数百件を**ページ送りで順に送る**ことになる。
§7 L168 は「探しに来た人にとっては、1画面に入る項目数と走査の速さが価値」と自ら言っている。その価値をもっとも大きく左右する道具が定義に無い。

### MJ-4 320px の主見出しは、§4 の折り方の規則と両立しない

§4 L99「主見出しの下限——**画面幅 320px で `33px`**」・L100「**見出しは意味の切れ目で折る。語の途中・括弧の前後で折らない。**」

320px のときの内容幅を実測すると **282px**（画面 320 − 縦罫 3×2 − 罫の内側の余白 16×2、§5 L120・L130）。
33px の全角で **8.5字**しか入らない。

- 「象牙色（ぞうげいろ）」= 10字 = 330px。**溢れる。**
- 折れる位置は括弧の前後しかないが、L100 がそこを禁じている。**折り位置が存在しない。**

§13 L243「320px 幅で**横スクロールなしに**全機能が成立する」があるので、実装は L100 を破って語中で折るしかない。
実際、モックの一覧の品名は `overflow-wrap: anywhere` を当てて語中で折ることで横スクロールを避けている。
**定義のとおりに作ると、320px では必ずどちらかの規則を破る。** 品名が長い項目ほど起きる（AI が作り続ける以上、長い品名は必ず出る）。

### MJ-5 狭い画面でのナビの畳み方が無い

§5 L137 は上端を「サイト名（明朝）＋ナビは文字だけ」と定めるだけで、入りきらないときの扱いを持たない。
実測で、320px・ナビ4項目のとき**上端だけで 148px**——画面の高さの1/4以上を占める。

§7 は「種別で絞り込める」と定めており、種別は中身が増えるほど増える。ナビ項目が6つ7つになれば上端は3行4行と伸び、
本文が押し下げられる。文字サイズ 200%（§13 L244）ではさらに倍になる。**上端の高さの上限も、畳み方（まとめる・送る・隠す）も定義に無い。**

### MJ-6 「器と中身の線」が、色（§2）にしか引かれていない

§1 L13 は「**器の色は、作れるものを狭める**」と言い、§2 は器と中身を明確に分け、中身の色には制限を置かないと決めている。**正しい判断である。**
ところが同じ理屈が要る他の規則で、線が引かれていない。

- §5 L131「**図像を持たない。** イラスト・写真・3D・**絵文字**を画面に置かない」
- §11 L229「**動きは3つだけ**」
- §5 L127「角丸は 0px」
- §4 L103「下線はリンクの専有」

これが中身にも及ぶなら、**図解・グラフ・地図・アニメーションを使う中身が作れない。**
数量の比較・手順・位置関係は、文字と表だけでは伝わりにくい。§1 L12「何が置かれるかは事前に決まっていない」と衝突する。

しかも **§9 L215「画像は、それが何かを説明する代替テキストを持つ」は、画像が存在することを前提にしている。**
§5 L131 と §9 L215 は、そのままでは両立しない。読む人は「画像は置けるのか置けないのか」を判定できない。

### MJ-7 明朝の配信条件（300KB 以下）と「書体が混ざらない」は両立しない

§3 L85「しっぽり明朝（ウェイト1本）。**WOFF2 で 300KB 以下**」／L90「**見出しの中で書体が混ざらない。** 明朝に無い字が出る面では、その字を含めて配信する」

実測した（Google Fonts の css2 から全断片を取得）。**しっぽり明朝 500 は 122 の unicode-range 断片に分かれ、合計 3,753,784 バイト**（平均 30KB／断片）。
**300KB は全体の約 8%** にあたる。常用漢字 2,136 字を単一ファイルで賄える量ではない。

結果、実装は次のどちらかになる。

- 字種を絞る → 見出しの一部がゴシックに化ける（**§3 L90 が禁じる状態そのもの**）。来訪者には字面の揃わない見出しが出る。
- 分割配信・動的サブセットにする → 「WOFF2 で 300KB 以下」という書き方が、何に対する上限なのか定義から読めない。

さらに §13 L245「**Web フォントの読み込みでリフローしない**」と重ねると、実装は読み込み完了まで見出しを出さない方向に追い込まれやすい。
**65px の主見出しがページの顔である以上、遅い回線の人はしばらく何も読めない。**
（この点は「サブセットを作り直す手順」の話ではなく、**下限どうしが両立するか**の話である。）

### MJ-8 無彩の帯（§2）が、主操作の反転（§6）と同じ形になる

§2 L74「色の上に文字が要る場合は、`--paper` か `--ink` の**無彩の帯を敷いて**その上に置く。」
`--ink` の帯に `--paper` の文字は、**§6 L148 の主操作（反転）そのもの**である。押せない帯が、ページでもっとも強い「押せる」記号を身にまとう。
§6 L143・L159 に反する。帯を `--paper` 側に限る、帯には枠を与えない等、どちらかに寄せる必要がある。

## Minor

### MN-1 hover の罫だけ、色トークンが指定されていない

§6 の記号表で、色が書かれていないのは hover の罫（L150）だけである（他は `--ink`・`--ink-2`・`--paper` を明記）。
hover は状態を示す視覚情報なので WCAG 1.4.11 の 3:1 の対象になる。`--rule-2` を当てると `--paper-2` の上で **3.14**（8bit 実測）——下限ぎりぎりになる。

### MN-2 hover と active が同じ記号

§6 L150 が2つの役割を1行にまとめている。§6 L143 の宣言の例外になっている。
タッチ端末には hover が無いため、押した手応えは 150ms の同じ罫だけになる。押せたかどうかが分かりにくい場面が出る。

### MN-3 選択の記号の大きさ・罫の太さが無い

§6 L152・L153 は「円形」「四角」とだけ定め、寸法を持たない。
§5 L112 に従えば「操作の部品の枠」は 3px だが、モックは 1px で描いている。**定義から出る太さと実装が割れている。**
20px の記号に 3px の枠は潰れるので、記号の寸法は定義側に必要である（§5 L126 の 8px 刻みの対象外であることも含めて）。

### MN-4 AI 運営の告知が、定義上もっとも弱い文字で成立してしまう

§5 L139・§9 L216 は置き場所と文言を決めるが、大きさと濃さを決めていない。
定義からもっとも自然に出るのは §4 L97 の下限（14px）＋ `--ink-2` で、モックもそうなっている。
constitution rule 3 が求める告知が、**ページで一番小さく一番薄い文字**で足りることになる。下限を1行持つべき箇所である。

### MN-5 §13 に無い WCAG 2.2 AA

§13 は「このデザインが**満たす**下限」と名乗るが、次が無い。いまの中身ではほぼ該当しないものの、フォームや問い合わせを持つ面が出た時点で穴になる。

| 達成基準                         | 内容                                                 | 定義側の状態                           |
| -------------------------------- | ---------------------------------------------------- | -------------------------------------- |
| 1.3.5 Identify Input Purpose     | 利用者自身の情報を集める欄の目的を機械可読に         | §8 に無し                              |
| 1.4.13 Content on Hover or Focus | hover/focus で出る内容の消し方・保持・触れられること | §6 L150 は罫しか出さないが、規則が無い |
| 3.2.6 Consistent Help            | ヘルプ・問い合わせの位置の一貫性                     | §5 L139「最小限のリンク」のみ          |
| 3.3.7 Redundant Entry            | 同一手続き内での再入力を求めない                     | §8 に無し                              |

（§13 の既存項目と §2・§6・§8 で、1.4.3 / 1.4.11 / 1.4.1 / 1.4.4 / 1.4.10 / 1.4.12 / 2.1.1 / 2.4.7 / 2.4.11 / 2.5.7 / 2.5.8 / 3.3.1 / 3.3.2 / 4.1.3 は覆えている。）

### MN-6 ページ送りの定義が無い

§7 L183 は「ページ送り」とだけ書く。1ページの件数・置き場所・現在ページの示し方・標的の大きさが無い。
現在地の記号（左端の縦罫＋太字）は横並びのページ番号には使えないので、**実装者は定義に無い記号を発明することになる。**

### MN-7 レビューに渡された実物が、現在の定義より古い

モックの HTML は、渡されたスクリーンショットより後に更新されている（`index.html` の更新時刻がスクリーンショットより新しい）。
実際、`design-mock-verification.md` が直したと記録している欠陥#3「65px の見出しが語の途中で折れた（見つからないも／のを、）」が、渡された画像にそのまま写っている。
**画像は修正前の状態である。** 今回は 1280px / 320px で再描画して判断した。AP-WF05（撮ったものと記述を1枚ずつ照合する）に当たる。

## Question

### QS-1 訪問済みリンクを `--ink-2` で示すこと——**可**

- リンクかどうかの識別は**下線**が担う（§6 L147・§4 L103）ので、色に依存していない。WCAG 1.4.1 の問題は起きない。
- 未訪問・訪問済みとも地に対して 4.5:1 を超える（`--ink`/`--paper` 19.12・17.24、`--ink-2`/`--paper` 7.55・8.15）。
- 訪問済みかどうかは WCAG が求める情報ではない。

ただし **`--ink-2` と `--ink` の差は light 2.53:1・dark 2.12:1** で、訪問済みの判別そのものは弱い（とくにダーク）。
「どれを見たか」を来訪者に確実に伝えたいなら、濃さ以外の手（下線の種類を変える等）が要る。**いまの定義のままでも害は無い。**

### QS-2 `--rule-2` / `--paper-2` の 3:1 の余裕

表の 3.15 / 3.12 は正しいが（8bit に丸めた実測でも 3.14 / 3.14）、**下限に対する余裕は 4.6%** しかない。
細罫を `--paper-2` の上で使う場面（広告区画の中の表・コード区画の中の罫）は、この 1 組だけが下限に張り付く。意図した設計か。

### QS-3 「結果は分割しない」と「1画面に収まらないときはページ送り」

§8 L206「**結果は即座に、全部見える。分割・段階表示を持たない。**」と §7 L183「1画面に収まらないときは**ページ送り**」は、
**結果そのものが長い一覧のとき**（例: 色の辞典で条件に合う 200 件）にどちらが優先するのかが定義から出ない。
前者を採れば 200 件を1ページに積むことになり、後者を採れば §8 に反する。どちらで読むべきか。

### QS-4 無限スクロールを持たないこと（§7 L183）——**妥当**

現在地を失わない・下端（一覧の外の導線）に辿り着ける・戻ったときに位置が保てる、という理由は正しい。
困るのは「絞り込みで狭められない探し方」だけで、それは無限スクロールの不在ではなく**検索の不在**（MJ-3）の問題である。ページ送りを保ったまま MJ-3 を塞ぐのがよい。

## 検算の結果——(C)

### §2 のコントラスト表（10個）——**全件一致。Blocker 無し**

無彩の oklch は linear luminance `Y = L³`（Oklab の L は中性色で `Y^(1/3)` に一致する）。比は `(Y_hi + 0.05) / (Y_lo + 0.05)`。

| 組み合わせ               | light 記載 | light 計算 | dark 記載 | dark 計算 |
| ------------------------ | ---------- | ---------- | --------- | --------- |
| `--ink` / `--paper`      | 19.12      | 19.1157    | 17.24     | 17.2423   |
| `--ink-2` / `--paper`    | 7.55       | 7.5475     | 8.15      | 8.1535    |
| `--ink-2` / `--paper-2`  | 6.71       | 6.7121     | 7.13      | 7.1325    |

**10個すべて、小数第2位まで記載と一致する。**

§2 L75 の「前景を `--paper` と `--ink` の2択にすると到達できる最大比は light **4.37** / dark **4.15**」も検算した。
`cr(c, paper) = cr(c, ink)` となる中間の明るさで最小値をとり、light `1.020299 / 0.233363 = 4.3722`、dark `0.962673 / 0.231836 = 4.1524`。**一致する。**
同じ計算から §6 L158「中身の色の上でも内外のどちらかが 3:1 を満たす」も成り立つ（最悪でも 4.15 ≥ 3）。

### §4 の本文幅——**整合する**

`--measure: 40rem`・ルート 16px → **640px**。本文 17px の全角は 1em = 17px。
`37 × 17 = 629px ≤ 640`、`38 × 17 = 646px > 640`。**「一行は全角37字以内」は 40rem と正しく対応する。**
モックの再描画でも読む面の実測幅は 640.0px だった。

§4 L98 の見出しのスケールも確認した。17px を基準に 1.4 倍を重ねると 17 / 23.8 / 33.3 / 46.7 / 65.3 → **17 / 24 / 33 / 47 / 65** で、記載と一致する。
