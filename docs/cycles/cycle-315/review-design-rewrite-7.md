# Major

## Major-1: 「結果より大きい文字を、面の中に持たない」が、同時に入れた段下げ規定・§4 の見出しの段・§5 の骨格と衝突する。320px ではほぼ常に偽になる

L284 は今回「数字・短い語より大きい文字を、面の中に持たない」から「**結果より大きい文字を、面の中に持たない。**」へ変わった。前版の語は参照先が2通りに読めた（6巡目 Minor-10）。今回の語は**一通りにしか読めない——その面に実在する結果の大きさ**である。そして、その読みでは次のすべてが破れる。

**(1) 段を下げた結果は、必ず主見出しより小さくなる。**

- §4 の表より、`45rem` 未満の画面の主見出しは `2.08rem`（既定のルートで 33.28px）。
- §5 骨格より、**主見出しは最初の節の頭に立つ**。結果の面にも必ずある。
- L279 より、結果が区画（212px）に収まらなければ `1.49rem`→`1.0625rem` と段が下がる。
- 実測で、320px で 2.08rem のまま収まるのは **漢字 6字まで**。7字以上の結果は必ず段が下がり、**主見出し（2.08rem）> 結果（1.49rem 以下）** になる。L284 に反する。

**(2) 結果が「文章」「図像」「それ以外」の面では、段下げ以前に常に破れる。**

結果が文章なら本文の大きさ（1.0625rem）である。主見出しは 2.08rem。どの画面幅でも主見出しのほうが大きい。**結果が数字・短い語でない面では、L284 は最初から成立しない。**

**(3) 読者は二択を迫られる。** 素直に従えば、結果の面では主見出しを本文の大きさまで落とすことになる——§4 の段の表と §5 の骨格に反し、§1 の担い手2「巨大なアンティーク体の見出し」という署名も消える。従わなければ L284 が死文になる。**どちらを選んでも文書のどこかが破れる。**

前版の「数字・短い語より大きい文字を持たない」は、1行目の「主見出しと同じ大きさ」を参照先に取れば真だった（結果 = 主見出し = 面の最大）。段下げを入れた時点で、**その前提そのものが消えている。** L284 は書き換えではなく、段下げと両立する形に**作り直す**必要がある（たとえば「その面で一番大きい文字は結果である。結果が段を下げたときは、見出しもその段まで下がる」のように、下がるものを揃えて書き切る）。

## Major-2: 「見出しは語の途中で折らない」が、320px と文字 200% で面を横に溢れさせる。結果には逃げ道を作ったが、見出しには無い

§4 L106:「**見出しは意味の切れ目で折る。** 語の途中・括弧の前後で折らない。」——例外は無い。
§5 L154–155: 見出しは組み幅の中に置かれ、組み幅いっぱいに伸びる（320px で 250px）。
§13: 320px で横スクロールせずに全機能が成立し、文字 200% で内容が欠けない。

実測（BIZ UDPGothic の実 advance width）。

| 見出しの語           | 320px・ルート 16px（2.08rem=33.28px） | 320px・文字 200%（66.56px） | 組み幅 250px |
| -------------------- | ------------------------------------- | --------------------------- | ------------ |
| 「シミュレーション」 | 235.0px                               | 469.9px                     | 収まらない   |
| 「ジェネレーター」   | 212.7px                               | 425.3px                     | 収まらない   |
| 漢字の上限           | 7.51字                                | **3.76字**                  | —            |

**文字 200% では、組み幅に入る主見出しは漢字 3.76字・カナ 4.13字しかない。** 5字を超える語（日本語では普通の長さ）は、語の途中で折れない以上**行の外に出る**。既定のルートでも、8字のカタカナ語（「シミュレーション」）が 250px を 176px 超える。

ブラウザの既定では和文は文字間で折れる（UAX #14 で仮名・漢字は ID クラス）ので、この溢れは**この規定を実装したときにだけ起きる。** つまり文書が自分で作っている。

そのうえ、**今回の書き換えで「面そのものは横に動かない」が L169・L170・L285 の3箇所から消え、§13 に一本化された。** §13 が横スクロールを禁じているのは **320px の行だけ**である。360px や 720px の画面で文字を 200% にした来訪者には、溢れを止める規定がどこにも無い（「拡大と上書き」の行は「内容が欠けない」であって、横に溢れることは禁じていない）。**逐語重複を消したこと自体は正しいが、一本化した先が 320px 限定の行だった。**

**逃げ道の型は、文書の中に既にある。** L279 は結果について「収まる段まで §4 の段を下げる。本文の大きさでも収まらないなら折り返す」と書いた。見出しにも同じ手当てが要る——段を下げるか、最後の手段として語中で折ることを認めるか。**来訪者から見れば、面の題が読めないのは結果が読めないのと同じ損である。**

| 部品どうしの間隔（16px × 5）      | 80px               |
| 合計                              | **約 630px**       |

ここに上端（サイト名＋横罫）と主見出しが乗るので、**一覧の1行目は画面の上端から 750px 以上下**になる。320×640 の画面では、**丸1画面ぶんの操作部を越えないと一覧に届かない。** 項目が増えるほど種別も増えるので、§7 の「増え続けることへの備え」が、増えるほど一覧を遠ざける。

さらに (A)-2 のとおり、320px の行の高さは 142–173px で、**1画面に 3〜4 行**しか入らない。§7 がカードを退けた理由（1画面に入る項目数）は、320px では成立していない。

**文書の中に矛盾もある。** §8 は「選ぶ欄が開いたときの候補も、同じ枠の中に並ぶ」として**選ぶ欄を正式な部品として認めている**——開くまで候補が見えない点では、選ぶ欄も「畳まれたもの」である。§7 だけが、一覧の絞り込みに限ってそれを禁じている。理由は書かれていない（由来は指摘しない）。

**来訪者の側から見れば、探しに来た人を一覧から遠ざけているのは操作部である。** 狭い幅では絞り込みを畳めるようにする（現在の絞り込みと件数は畳んでも見えるようにする）か、選ぶ欄を使えるようにするか、いずれかの逃げ道が要る。site-concept の「探し物が決まっている人にも、決まっていない人にも同じ状態」という読者像に対して、**どちらの人も最初に見るのが一覧ではなくフィルタになる。**

## Major-4: §9 を「生成された文章にもかかる」と広げたことで、器の文体規定が作れる中身を狭めた。§1 が芯として否定した構造そのものである

§1 L16–17 はこう書いている。

> サイトには多様なものが並び、入れ替わり続ける。何が置かれるかは事前に決まっていない。
> **器が色を持てば、その色と喧嘩しない中身しか置けなくなる。器の色は、作れるものを狭める。**

この論法が、色から文体へそのまま移る。今回 L290 に「**器の文章にも、生成された文章にもかかる。**」が入った結果、直後の4つの箇条が**すべて中身の文章に掛かる**。

| §9 の箇条                                                                                  | 中身に掛けたときに起きること                                                                                   |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 自然な日本語（翻訳調・抽象動詞の連打・コロン頻出の見出し・箇条書きと太字の過剰を持たない） | **翻訳調を出すこと自体が面白い生成物**（直訳ボット、ビジネス用語で言い換える生成物、機械翻訳の往復）が作れない |
| 具体（ヘッジの乱用と汎用最上級を持たない）                                                 | 大げさな言い回しを芸にする生成物が作れない                                                                     |
| 結果を出し惜しみしない                                                                     | 中身に掛けるのが正しい（site-concept のゴールそのもの）                                                        |
| AI 運営を正直に、簡潔に示す                                                                | 下端の告知の規定であり、生成された文章に掛ける意味が無い                                                       |

**4つのうち、中身に掛けるべきものと掛けてはならないものが混ざっている。** §2 は色を、§8 4行目は形を、§11 は動きを、いずれも「中身そのものは中身が決める」と手放しているのに、**文体だけが器から中身へ下りてきている。** 文書全体の筋が、この1文で割れる。

来訪者の側から見た損は具体的である。site-concept は「**定番のものを、より良く作り直そうとする。それは他所の土俵である**」「**誰も作っていない理由を確かめる**」と書いている。**言葉遣いそのものを題材にした生成物は、その筋のど真ん中にある**——そして §9 はいまそれを禁じている。

掛ける範囲を、箇条ごとに書き分ける必要がある（約束にあたるもの＝出し惜しみしない・煽らない は中身にも掛け、文体の作法は器に閉じ、中身が意図して選んだ文体は中身が決める、という切り方）。

## Major-5: 320px で中身に渡る幅が 212px（画面の 66.3%）しかない。器が両端で 108px を取る

入れ子を左右に開くと、320px では次のようになる。

| 内訳                                | 片側 | 両側      |
| ----------------------------------- | ---- | --------- |
| 画面の端から格子まで                | 16px | 32px      |
| 縦罫（3px）＋その内側の余白（16px） | 19px | 38px      |
| 区画の枠（3px）＋内側の余白（16px） | 19px | 38px      |
| 合計                                | 54px | **108px** |

結果・生成物は必ず区画にある（L275）ので、**中身が使えるのは 320px のうち 212px＝66.3%** である。図像なら面積で **(212/288)² = 54%**——格子いっぱいに置けた場合の半分強になる。360px でも 70%。

来訪者の側から見ると、これは「見に来たもの」に効く。

- **図像**: 212px。拡大して見る手立ては規定に無い。
- **動く中身・遊べるもの**: 操作する面積が 212px。指で触る中身では、この差は直接効く。
- **文章**: 区画の中の本文の幅は 212px で、文字 200% では **1行 6.24字**。器が 108px を返せば 8.47字になる（36%増）。

**§1 は器が中身を狭めることを芯として否定している。** 色では守られている原則が、幅では検討されていない——16px の余白は画面幅によらず固定で、入れ子のたびに同じ 16px を取る。**縦罫の 16px は署名の成立に必要だと §5 が説明しているが、区画の内側の 16px には理由が書かれていない。**

CLAUDE.md は「より良い UX が達成可能なら、実装コストを理由に劣る案を選んではならない」と定めている。**狭い幅で内側の余白を詰める（16px→8px で 212→244px、+15%）**、**結果の区画の枠を縦罫と兼ねる（212→250px、+18%）**、**中身にだけ帯と同じ外への張り出しを許す**——いずれも署名（端まで届く横罫・十字に切られた罫の端）を壊さずに取れる。どれを採るにせよ、**携帯の3分の1を器が使うことの是非が、文書のどこでも weigh されていない。**

## Major-6: 「ナビが1行に収まらない幅では、一覧へ戻る導線だけを残す」は、収まっていた項目まで落とす。320px の来訪者は、行ける先を失う

§5 骨格の上端:「**ナビが1行に収まらない幅では、一覧へ戻る導線だけを残す**」。

実測（サイト名 70.0px・間隔 16px・組み幅 250px）。

| ナビ                             | 合計幅  | 判定       |
| -------------------------------- | ------- | ---------- |
| 一覧＋ブログ                     | 185.1px | 収まる     |
| 一覧＋ブログ＋このサイトについて | 342.5px | 収まらない |

**3つ目が長いという理由で、収まっていた「ブログ」まで消える。** 残るのは一覧への導線1つだけ。落とした先の行き場は、§5 下端の「**最小限のリンク**」しか無く、その中身は規定されていない。したがって **320px の来訪者がブログに行ける保証は、この文書のどこにも無い。**

これは §13 の「**320px 幅——面を横にスクロールせずに全機能が成立する**」と正面からぶつかる。ナビ項目が指す先は機能であり、**320px でだけ存在しない機能**になる。

**費用の小さい代案がある。** ナビを2行に折る（上端が 31.45px 高くなるだけで、全項目が残る）か、下端のリンクにナビ項目を必ず含めると書き切るか。§4 は見出しについて「画面が狭くなると段がそろって下がる」という**落とさずに畳む**型を既に持っている。**落とす規定を採る理由は書かれていない。**

## 判定

**改善指示。**

6巡目の Major 2件は解消し、段下げは実数で機能している（320px で漢字 12.47字まで、以降は折り返し）。幾何も6巡連続で完全に閉じている。

残る問題は2種類ある。

- **Major-1 は、今回の修正が作った矛盾である。** 6巡目 Minor-10 の曖昧さを、段下げと両立しない側に確定させた。L284 は書き換えではなく、段下げと揃う形に作り直すこと。
- **Major-2〜6 は、6巡のあいだ一度も見られていなかった来訪者側の欠陥である。** 見出しが 320px・文字 200% で面から溢れる／絞り込みが一覧を画面外へ押し下げる／器の文体が作れる中身を狭める／中身に渡る幅が画面の 66%／携帯でナビが消える。どれも「この規定どおりに作ると来訪者が損をする」形で、内部整合をいくら回しても出てこない。

次の修正では、**Major-2・5・6 が共通して「狭い幅で何を落とすか」の問題である**ことに注意してほしい。文書は結果については「段を下げて残す」を選び、見出し・ナビ・中身の幅については「落とす／削る」を選んでいる。**同じ問いに違う答えを与えている**のが、来訪者側から見たときの一番大きな不揃いである。
