## (C) §2 のコントラスト比 10 個の検算——**無し（10個すべて一致）**

| `--rule-2`/`--paper` light   | 3.54     | 3.5387  | 一致 |
| `--rule-2`/`--paper` dark    | 3.56     | 3.5621  | 一致 |
| `--rule-2`/`--paper-2` light | 3.15     | 3.1470  | 一致 |

## Blocker

### BL-1 §4 行105 本文の `17px` 絶対指定と「ルートは 16px」が、弱視の最も一般的な調整手段を無効化する

> `- **本文**: 17px / 行間 1.85 / ベタ組み。**一行は全角37字以内**（--measure: 40rem。ルートは 16px）。`

本文の大きさを **絶対 px** で定め、行長だけを `rem` で定めている。結果、ブラウザの「既定の文字サイズ」設定を上げても**本文は一切大きくならず、行長だけが伸びる**。
`tmp/r-rem.mjs` の実測（1280px 幅・モック）:

| ルート | 本文の実効サイズ | 読む幅 | 1行の全角字数 |
| ------ | ---------------- | ------ | ------------- |
| 16px   | 17px             | 640px  | 37.6          |
| 20px   | 17px             | 800px  | 47.1          |
| 24px   | 17px             | 906px  | 53.3          |
| 32px   | 17px             | 906px  | 53.3          |

既定文字サイズを 24px にした利用者は、**文字は 17px のまま・1行が 37字から 53字へ 43% 伸びる**。調整すればするほど読みにくくなる。
`14px` を下限とする補助情報（行106）も同じく拡大されない。

WCAG 1.4.4 はブラウザズームで形式的には満たせるため「AA 違反」ではない。しかしブラウザの既定文字サイズは弱視の利用者が最初に触る調整であり、それを殺しているのは Owner 条件2（誰もが使える）の実質的な放棄である。「ルートは 16px」という断定は `html { font-size: 16px }` を定義に書き込むに等しく、これは広く知られたアクセシビリティのアンチパターンである（[Josh W. Comeau](https://www.joshwcomeau.com/css/surprising-truth-about-pixels-and-accessibility/)、[Craig Abbott](https://craigabbott.co.uk/blog/accessibility-and-font-sizes/)）。

**これは「個性のための規定」ではなく単なる取りこぼしなので、直せば個性は一切失われない。** 本文・補助情報・見出しのスケールを `rem` 基準にし、「ルートは 16px」の断定を落とすこと。

### BL-2 §6 行168 の hover と §8 行218 のエラーが、同じ「枠が太くなる」という記号になっている

> §6 `| hover / active | **要素の内側に --rule-w-hair の枠が現れる。** 外には出ない |`
> §8 `- **入力欄の枠は平常時 --rule-w-hair、エラーのとき --rule-w。** 枠が太くなることが、その欄に問題があるという記号である。`

入力欄は平常時 1px。hover すると内側に 1px が加わって**実効 2px**。エラーは 3px。**区別は線幅 1px 差だけ**である。
`tmp/r-input.png`（3倍拡大）で再描画した結果:

- hover（2px）とエラー（3px）は 3倍拡大でようやく差が見える程度で、等倍では同じ線に見える。
- **「エラー＋hover」は「エラー」と完全に同一**になる。エラー中の欄では hover のフィードバックが消える。
- つまり利用者は、**ただマウスを乗せただけで「この欄に問題がある」という記号を見せられる。**

§6 行161 は「一つの記号が二つの意味を持たない」と宣言しているが、ここで破れている。
そしてこれは **色を一切使わないという条件1のための規定が、状態の区別という条件2を削っている**典型である。色を捨てた結果、残った変数が線幅しかなく、そこに 1px 差で二つの意味を載せている。

### BL-3 §11 行251 の「中身の動き」carve-out と §12 の広告に、動きの下限が無い

> §11 `中身そのものの動き（遊べるもの・動く図解）はこの規定の外にあり、その中身が決める。`
> §11 `prefers-reduced-motion のとき、結果の登場は即時表示になる。`（＝**結果の登場だけ**）

このサイトの主力は「遊べるもの」「動く図解」であり、**動きの下限が最も必要な場所が、定義から丸ごと外れている。**
定義に一切違反せずに次のものが作れる:

- 5秒を超えて自動で動き続ける図解（WCAG **2.2.2 Pause, Stop, Hide — Level A** 違反）
- 毎秒3回を超える点滅を含む遊べるもの（**2.3.1 Three Flashes — Level A** 違反。光過敏性発作の危険）
- 自動再生の音（**1.4.2 Audio Control — Level A** 違反）
- `prefers-reduced-motion` を無視する中身（前庭障害のある利用者に実害）

§12 も同じ穴を持つ。広告は「`--paper-2` の帯・上下に全幅の横罫・『広告』ラベル・閉じた枠なし」と**形だけ**が決まっていて、動き・音・点滅・コントラストの下限が無い。`src/app/privacy/page.tsx` の記述どおり AdSense を使う前提なら、アニメーションするディスプレイ広告がそのまま入る。
加えて §1 行38「**無彩の器の上で、中身の色だけが立つ**」という4つ目の担い手は、色つきの広告クリエイティブが1枚入った瞬間に壊れる。§12 はそれに触れていない。

§13 は「面を横断して必ず成り立つもの」を置く節だが、**動きの下限が1行も無い。** Level A を割れる穴が定義に残っている以上、条件2は成立していない。

### BL-4 §3 行89 の「細い横画を持たない」は和文にしか当たらず、担い手2はサイト名と favicon で働いていない

> §3 `- **アンティーク体は、明朝の骨格に太さの揃った線を持つ書風である。** …細い横画を持たないため、**小さいサイズでもダークでも痩せない。**`
> §10 `- **favicon**: --ink の地に --paper で **y の一字**を見出し書体で。…16px で潰れない太さ。`
> §5 骨格 `| 上端 | サイト名（見出し書体）。…`

Zen Antique を実読み込みして描画した（`tmp/r-favicon.png`・`tmp/r-type.png` 3行目・`tmp/r-dark-header.png`）。

- **Zen Antique の欧文は、線幅が均一な書風ではない。** `yolos.net 2026` は明確な太細のコントラストとヘアラインのセリフを持つ、ごく一般的なトランジショナル・セリフである。「細い横画を持たない」という §3 の根拠は**和文（かな・漢字）にしか当たらない。**
- **サイト名は全ページの上端に出て、100% 欧文である。** つまりサイトで最も繰り返し目に入るブランド要素は、担い手2が働いていない部分で描かれている。ダークで撮った `tmp/r-dark-header.png`（4倍）では、`yolos.net` のヘアラインが痩せているのが見える。§3 の「ダークでも痩せない」はここで成り立たない。
- **favicon の `y` は 16px で潰れる。** 10倍拡大で確かめると、16px の枠に入る `y` は x ハイト約 7px・ヘアラインのセリフはサブピクセルで、灰色ににじむ。§10 の「16px で潰れない太さ」は実測で満たされない。

**(D) の判定もここで決まる。** ページ全体は見分けがつく（後述）。しかし §10 自身が「**デザインだけで見分けがつくかが最初に試される場所**」と書いたタブと共有カードでは、**黒い正方形に普通のセリフ体の小文字 `y`** であり、他の無数のサイトと区別がつかない。条件1が、条件1にとって最も決定的な場所で成立していない。

## Major

### MJ-1 罫の太さの割り当てが §5・§6・§8 で三つ巴に矛盾する

- §5 行121: `--rule-w`（3px）の使う場所に「**操作の部品の枠**」がある。
- §8 行218: 「入力欄の枠は平常時 `--rule-w-hair`（1px）」。入力欄は操作の部品なので §5 と矛盾。
- §6 行175: 「`--rule-w` の閉じた枠は、押せない**区画**の記号である。主操作だけが例外」。これに従うと、操作の部品に 3px の閉じた枠は付けられない。§5 行121 と矛盾。

さらに単一選択・複数選択の記号（§6 行170–171）は寸法も線の太さも定義されていない。§5 に従えば 3px、§6 に従えば 3px は禁止、§8 に倣えば 1px。**実装者はどれを採っても定義違反になる。**

### MJ-2 §6 の表で「リンク」と「副操作」が完全に同じ見え方になっている

> `| リンク（本文・ナビ・一覧の行・ページ送り） | **下線**。色は --ink。… |`
> `| 副操作 | **下線を持つ文字。枠を持たない**（枠は押せない区画の記号だから） |`

どちらも「下線を持つ文字・枠なし・`--ink`」で、**見え方が一致する。** §6 行161「一つの記号が二つの意味を持たない」は、§6 自身の表によって破れている。
来訪者は「やりなおす」（その場で状態が変わる）と「一覧へもどる」（ページが変わる）を、押すまで区別できない。色を捨てた設計では色による区別も使えない。

### MJ-3 §6 の「現在地」の 3px 縦罫が、§5 の構造の縦罫と同じ形をしている

> §6 `| 現在地 | **下線を持たない。** 左端に --rule-w の縦罫 ＋ 太字 |`
> §5 行125 `**縦罫**は…内容の枠の左右端を通り、上端から下端まで途切れない。`

`tmp/r-dark-header.png`（ダーク・4倍）で確認したとおり、ナビの「ぜんぶ」の左に立つ 3px の白い縦棒と、格子の縦罫は**同一の形・同一の太さ・同一の色**である。画像の中で両者を見分ける手がかりは無い。これも「一つの記号が二つの意味を持たない」に反する。

### MJ-4 和文に太字のウェイトが無いのに、§4 と §6 が太字を要求している

> §3 `| 本文・UI（和文） | **BIZ UDPGothic**（ウェイト400）… |`
> §4 行112 `- **強調**: 太字は一段落に一箇所まで。`
> §6 行169 `| 現在地 | …＋ 太字 |`

和文は 400 しか持たないので、太字は**合成太字**になる。実測（`tmp/r-cover.mjs`）: BIZ UDPGothic の「あ」は 400 と 700 で送り幅が 98 で同一のまま、ink の上端だけ 83→85 に膨らむ。これはブラウザによる合成の挙動である。
`tmp/r-type.png` 5行目で描画すると、合成された「ぜんぶ 現在地」は画線がにじんでいる。欧文は IBM Plex Sans の本物の 600 を持つ（§3 行87）ので、**同じ行の中で本物の太字と合成太字が混ざる**（`tmp/r-type.png` 6行目）。§4 行111 が要求する「和文と欧文の字面が揃っていること」は、太字の行で崩れる。

### MJ-5 §5 行133「幅ごとに中央寄せにしない」が二通りに読め、検証モックは一方の読みに違反している

> `- **内容の左端は全ページで同じ位置**。読む面（--measure）も操作面（--max-width: 960px）も同じ左端から始まり、右にだけ伸びる。幅ごとに中央寄せにしない。`

「幅ごと」が **画面幅ごと**（＝ビューポートに対して中央寄せしない）なのか、**面の幅ごと**（＝読む面と操作面をそれぞれの幅で中央寄せしない）なのかが定まらない。
実測（`tmp/r-layout.mjs`）では、検証に使われた `tmp/mock/index.html` は 992px 以上で `margin: 0 auto` を当てており、**1280px で左右 160px ずつ・1920px で左右 480px ずつの完全な中央寄せ**になっている。前者の読みでは定義違反である。
定義どおりに左寄せした状態は一度も描画されていなかったので、`tmp/r-left-1600.png` に起こした。1600px で右側に **624px の空白帯**ができる。破綻はしておらず、むしろ罫を引いた大判の紙のように見えて悪くない——**が、それは誰も確認していない見た目である。** どちらが正かを定義が決めていない以上、実装は賭けになる。

### MJ-6 §3 の「見出しに使う字だけを配信し、すべて配信されている」が、AI が生成し続ける見出しでは成立しない

> §3 `| 見出し・サイト名 | **Zen Antique**…**見出しに使う字だけを配信し、1ページ 100KB を超えない** |`
> §3 行99 `- **見出しの中で書体が混ざらない。** その面の見出しに出る字は、すべて配信されている。`

モックの `tmp/mock/zenantique.woff2` は 32,508 バイトのサブセットで、実測すると**「漢」「国」「H」「あ」を含まない**（`tmp/r-ink.mjs`・`tmp/r-cover.mjs`。これらの字は Zen Antique 指定でもフォールバックの計測値と一致する）。つまり**そのページの見出しに出ない字は落ちる。**

このサイトの見出しは、伝統色の名前・遊べるものの名前・生成物の名前など、**事前に確定しないもの**である。来訪者の入力を結果の見出しに出せば、その字は配信されていない。そのとき起きるのは、
「見出しの中で書体が混ざる」（行99 違反）・「書体が切り替わっても字面が動かない」（行100 違反）・**担い手2がその面から消える**、の三つである。
`docs/cycles/cycle-315/design-mock-verification.md` が記録するとおり日本語書体のフル配信は 122 分割・数 MB の規模なので、「1ページ 100KB」との両立は、見出しの字が静的に確定する面でしか成り立たない。**定義が、自分の中身の性質と噛み合っていない。**

### MJ-7 §6 行173 のフォーカスリングが要素の内と外のどちらに出るかが未定義で、外に出すと一覧で文字を横切る

> `| フォーカス | **密着した二重リング**——内側 2px --paper、外側 3px --ink |`
> §6 行178 `- **hover は要素の内側に出る。** 外に出すと、罫で詰めて並んだ行では隣に食い込む。`

「内側 2px・外側 3px」は二つのリングの**相互の**位置しか決めておらず、リング全体が要素の内か外かを決めていない。
行178 は hover について「外に出すと隣に食い込む」と自ら理由を述べているのに、**同じ理由が当てはまるフォーカスについては何も言っていない。**
モックは外に出す実装（`outline-offset: 2px`）で、`tmp/r-focus-list.png`（3倍）を見ると、3行目のリングの下辺が**その行のひとこと「#f8f4e6 — 淡いので、枠がないと地に溶ける。」を横切っている。**
さらに §7 行191「行全体が標的」に対して、リングはリンクの文字にしか付いていない。**見えている焦点と実際の標的が一致しない。** 定義はリングが何を囲むのかを決めていない。

§13 の下限に照らして、定義に無いために違反しうるものだけを挙げる（レベルは [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 本文で確認済み）。

## Minor

### MN-1 320px で内容幅が 250px（全角 14.7 字/行）まで痩せる

実測（`tmp/r-layout.mjs`）: 320px 幅で `wrapLeft = wrapRight = 16px`、内容の内側幅 **250px**。
内訳は 画面端の余白 16px × 2 ＋ 縦罫 3px × 2 ＋ 罫の内側の余白 16px × 2 = **70px（画面の 22%）**。本文 17px なので 1行 14.7 全角字になる。
16px の余白だけのレイアウト（288px = 16.9字）と比べて **2.2 字・13% の損失**。横スクロールは出ず（実測）、行長が短すぎて読めないというほどでもないので Blocker にはしない。ただし**署名（端から 16px 内側の縦罫）と太い罫が、最も来訪者の多い幅で一番高い代償を払っている**ことは記録しておく。

### MN-2 §4 行111「両者の字面の大きさ…が揃っていること」は、選んだ2書体では素のままでは満たされない

実測（`tmp/r-ink.mjs`、ピクセル走査、1em あたり）: IBM Plex Sans は キャップ 0.705 / x ハイト 0.520 / 数字 0.715。和文の漢字の字面はおよそ 0.88–0.90。
`tmp/r-mix.png` の A 行（実際の指定）を見ると、**ベースラインは揃っている**（CSS がアルファベティックベースラインを共有するので自動的にそうなる）。**字面の大きさは揃っていない**——欧文が 2 割ほど小さく見える。ただしこれは日本語組版として不自然な比率ではなく、C 行の 17px 実寸は十分読める。
問題は**定義の書き方**である。「揃っていること」が「等しい」なら実測で偽、「調和している」なら検証不能。§8 行226 が「数字は…大きい」と言っているのに、結果の主役である数字が和文より小さく出る関係を、定義が把握していない。

### MN-3 hover の 1px 内枠が、§7 の 1px 行区切りと同じ語彙である

`tmp/r-hover-light.png`（3倍）で確認。hover した行は 1px の `--ink` の内枠を得るが、隣の行区切りは 1px の `--rule-2`。**形は同じで濃さだけが違う**（5.40:1 の差）。等倍では「区切り線がやや濃くなった」程度にしか見えない。
マウス利用者にはカーソル形状という別の手がかりがあるので致命的ではないが、9つの状態のうち最も弱い。

### MN-4 単一選択・複数選択の記号の寸法と線の太さが定義されていない

§6 行170–171 は形（円・四角）と塗りだけを決め、大きさも線の太さも決めていない。MJ-1 の矛盾と重なって、実装者に判断が丸投げされている。

### MN-5 §1 行31「短い罫の端が、どの幅でも必ず残る」は広い画面で成り立たない

実測: 縦罫の外側に残る横罫の長さは 1280px で左右 160px ずつ、1920px で 480px ずつ（中央寄せの読み）。定義どおり左寄せすると 1600px で右側 624px（`tmp/r-left-1600.png`）。
「短い罫の端」と呼べるのは 1000px 前後の幅だけで、デスクトップの主要な幅では**広い空白帯**になる。署名は成立しているが、**説明が実物と合っていない。**

### MN-6 §13 行268「文字サイズ 200% の拡大…で内容が欠けない」が何を指すか曖昧

本文・見出しが px 固定（BL-1）なので、「文字サイズの 200% 拡大」＝ブラウザの文字サイズ設定であれば**そもそも拡大されない**（欠けようがない）。ブラウザズームの意味なら成立する。どちらを指すかで成否が逆になる規定を下限に置いている。

### MN-7 `tmp/mock/index.html` の 1行あたりの字数は 37.6 字で、§4 行105 の「37字以内」の実効的な余白がほぼ無い

`--measure: 40rem = 640px` ÷ 17px = 37.6。`palt` や約物処理で 38 字目が入る余地があり、規定と実装の境界が 0.6 字しかない。実害は小さいが、37 字を規定にするなら 629px が素直である。

## Question

### Q-1 「現在地」は押せるのか

§6 行160 の土台「押せるものは、下線か反転を必ず持つ。押せないものは、どちらも持たない」から逆算すると、下線も反転も持たない「現在地」は**押せない**ことになる。定義にその明記が無い。
モックは `<a href>`（押せる）に下線なしを当てており、土台に違反している。現在地を押せないと決めるのか、例外として認めるのかを定義が持つべきか。

### Q-2 §12 の広告は、何を許して何を許さないのか

形（帯・ラベル・枠なし・CLS を出さない）だけが決まっている。AdSense のディスプレイ広告は色・動き・音を持ち、§1 行38 の「無彩の器の上で、中身の色だけが立つ」を壊す。
広告の中身に下限を置く（静止のみ・テキスト広告のみ等）のか、§1 の4つ目の担い手を「広告のない面でだけ成り立つ」と限定するのか。

### Q-3 §3 の「1ページ 100KB」は見出し書体だけの上限か、3書体の合計か

見出し書体の行にだけ書かれているので前者に読めるが、BIZ UDPGothic の分割配信と IBM Plex Sans の ASCII 2ウェイト（`typeface-comparison.md` の記録で 64KB）を足した総量の上限が定義に無い。§13 行269「Web フォントの読み込みでリフローしない」と合わせて、総量の上限が要るのではないか。

## (D) 独自性は本物か——**ページは見分けがつく。タブと共有カードはつかない（BL-4）**

この定義どおりに作った画面と同じ見た目になりうる既存の類型を挙げ、何が違うかを述べる。

| 類型                                                   | 重なるところ                             | 何が違うか                                                                                                                                        |
| ------------------------------------------------------ | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Brutalist / スイス様式のポートフォリオ・スタジオサイト | 無彩・角丸 0・影なし・太い罫・巨大見出し | 欧文グロテスク（Helvetica / Suisse / Inter）を使う。**和文のアンティーク体は使わない。** また全幅の横罫が縦罫を貫く格子はまず作らない（箱を積む） |
| 新聞・エディトリアル系メディア                         | 罫で組む・明朝の大見出し・1行1項目の一覧 | **ブランドカラーを必ず持つ**（見出し色・タグ色・リンク色）。§2 の「器は完全に無彩」がここで分かれる                                               |
| 日本語 Web の巨大明朝トレンド（2025–）                 | 巨大な和文セリフ見出し                   | 明朝は細い横画を持ち、飾り・写真・グラデーションを伴うことが多い。Zen Antique の均一な画線と、図像を一切持たない器で分かれる                      |
| Tufte CSS / bear blog / sr.ht 系のミニマル文書サイト   | 無彩・装飾なし・読みやすさ優先           | **罫の格子を作らない**。1カラムの文章が流れるだけで、署名になる形を持たない                                                                       |
| Notion / Linear 風の SaaS UI                           | 一覧・入力・結果の構成                   | 角丸・影・淡い背景色で面を作る。§5 の「面は罫で作る・背景色で区切らない」と正面から分かれる                                                       |

**判定: ページ単位では見分けがつく。** 決め手は3つの同時成立である——(1) 全幅の横罫が縦罫を貫く格子、(2) Zen Antique の和文（Web でほぼ見ない）、(3) 器に色が1滴も無いこと。この3点を同時に満たす既存類型は挙げられなかった。

**ただし BL-4 のとおり、タブと共有カードでは成立しない。** §10 が「最初に試される場所」と名指した面で、担い手2（書体）が欧文＝普通のセリフ体に化け、担い手1（罫の格子）は favicon に入らない。**16px の `y` は、このデザインのどの特徴も運んでいない。**

## (E) 定義の穴——担い手が現れない面／下限を割る面は、定義に違反せずに作れるか

**作れる。手口は4つ。**

1. **見出し書体を消す**（MJ-6）。来訪者の入力や生成物の名前を見出しに出す。§3 は「その面の見出しに出る字はすべて配信されている」と性質として書いているだけで、**配信できない字が来る場合をどう扱うかを決めていない。** サブセットに無い字はフォールバックし、その面から担い手2が消える。定義のどの行にも違反していない。
2. **動きで下限を割る**（BL-3）。「動く図解」として 10 秒ループするアニメーションを置く。§11 行251 が中身の動きを規定の外に置いているので、定義違反にならないまま 2.2.2（Level A）を割れる。`prefers-reduced-motion` の規定（行253）は結果の登場にしか掛かっていない。
3. **広告で器の無彩を壊す**（BL-3・Q-2）。§12 は帯の形しか決めていない。色つき・アニメーションする広告クリエイティブを入れれば、§1 行38 の4つ目の担い手が壊れ、2.2.2 も割れる。定義違反にならない。
4. **hover だけでエラーに見せる**（BL-2）。入力欄に hover させれば、定義どおりの実装のままエラーの記号（太い枠）が出る。

**担い手3（操作の記号）が現れない面**は作れるが、これは穴ではない。§1 の署名は罫の交わりであり、§5「どの面にも現れるもの」が担い手1と担い手2の出現を保証している。操作の無い読む面に操作の記号が無いのは当然である。
