# レビュー: `DESIGN.md` は強い独自性を確実に発揮できるか

対象: `DESIGN.md`（247行・`e795a031`）。観点は Owner 条件1（デザインだけで yolos.net だと分かる強烈な個性）のみ。条件2（ユーザビリティ）は別レビューの担当。落とした手順（`design-scope.md`）を戻せという指摘は含まない。

**判定: 改善指示。** 定義が意図した個性は、(1) セッションの8割が見る幅で署名が構造的に出ない、(2) 個性の中核である明朝が実物の証拠のどれにも描画されていない、(3) 担い手が1つも出ない面を定義に違反せず作れる——の3点により、現状の定義では担保されない。

## 検証の方法

- モックの実描画を読み直し、見出し部分を等倍で切り出して書体を目視判定した。
- モック（`index.html`）をヘッドレス Chromium で再描画し、フォント読み込み・実測幅・h1 の行数を計測した。
- §2 のコントラスト表10値と §2 の「到達できる最大比 4.37 / 4.15」を独立に再計算した（**10値すべて一致・4.374 / 4.153 で一致。ここに指摘は無い**）。
- しっぽり明朝 w500 の配信実体サイズを実測した。
- 「担い手が珍しいか」を外部の現行トレンド資料と、実在サイトの DOM で確認した。

## Blocker

### B1. 署名が、セッションの約8割が見る幅で構造的に出ない

§1 L30–34 はこう宣言している。

> **全幅の横罫は、内容を挟む縦罫を貫いて、画面の端まで伸びる。** 交点で切らない。
> 画面の左右には、十字に切られた短い罫の端が必ず残る。
> …**この形は、どの面にも、どの幅にも現れる。文言を消しても残るのはここである。**

一方 §5 L120 は「**縦罫**は画面の幅を問わず内容の枠の左右端を通り」とし、モック検証で「狭い画面では画面の左右端に接する」と直した。**この2つは両立しない。** 縦罫が画面の左右端に接した瞬間、横罫の張り出し（＝十字の端）は長さ 0 になる。

- 実測: 320px 幅の描画では、縦罫は画面の最左端・最右端にあり、張り出しは **0px**。署名は1本も残っていない。
- 張り出し長は `(viewport − 内容の枠幅)/2` で決まる。モックの `--max-width: 960px` なら 1024px 幅で **32px**、1280px 幅で **160px**。**960px 以下では常にゼロ。**
- 誰が見るか: `docs/cycles/cycle-300/observation.md` L135 の実測で、セッションの **mobile 比率 79.8% → 83.0%**、PV でも 40.0%→56.4%。**「文言を消しても残る」と書いた唯一の形を、来訪者の約8割は一度も見ない。**

「どの幅にも現れる」は現在の定義では偽である。署名を幅に依存しない形（例: 張り出しの最小長を値で決める／狭い幅では別の形で署名を成立させる）として定義し直すか、§1 の言明を実態に合わせる必要がある。**前者でなければ条件1は達成できない**——モバイルで個性が消える定義は、条件1を8割の来訪者に対して放棄している。

### B2. 担い手2（巨大な明朝）が、提出されたすべての実物証拠で描画されていない

モックの見出しを等倍で切り出して確認したところ、**広い画面・上端の切り出しのどちらも、見出しは本文と同一のゴシック**である。横画と縦画の太さが等しく、うろこが無い。明朝の顔はどこにもない。

機械でも裏を取った（現行 `index.html` をヘッドレス Chromium で再描画）。

| 計測                                                      | 結果                                                                                                          |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `fonts.googleapis.com/css2?family=Shippori+Mincho` の取得 | **FAILED**（ネットワーク到達せず）                                                                            |
| `document.fonts` の登録数                                 | **0**                                                                                                         |
| 「他では見つからないものを、」の実測幅 65px               | mincho 指定 **755.34px** ／ `serif` **755.34px** ／ 存在しない書体名 **755.34px**（＝三者ともフォールバック） |

つまり、**この検証で「魅力的か」を判断した画面は、しっぽり明朝が1文字も当たっていない画面である。** それにもかかわらず `design-mock-verification.md` は「主見出し 65px（広い画面）→ **65px。しっぽり明朝が実際に当たっている**」「**巨大な明朝の見出し**が画面の顔になっている。既定 sans の画面とは一目で違う」と断定している。一次情報（`document.fonts` / 実測幅）を確認せずに担い手の成立を宣言したもので、AP-P01（根幹の仮定を実測せず先送り）・AP-P16（一次情報を確認する前に「達成された」と書く）に該当する。

より重いのは、**この誤った証拠が、同時に本物の failure mode を写している**ことである。日本語 Web フォントは 3G・オフライン・フォントのブロック・配信障害で普通に落ちる。**落ちたときに何が見えるかを `DESIGN.md` は定義していない。** §3 L88 は「見出しの明朝はシステム明朝に頼らない。**Web フォントで配信する。**」としか言わず、代替の顔を決めていない。落ちた画面が実際にどう見えるかは、この検証の描画がそのまま答えである——**本文と同じゴシックが大きいだけの画面**で、担い手2 は消える。個性の3本柱のうち1本が、外部要因で無定義に脱落する。

### B3. 担い手が1つも出ない面を、定義に違反せずに作れる

**手口（記事・about・利用規約のような「読む面」を 375px で開く）:**

1. **担い手1が出ない。** §5 L119 は全幅の横罫の**置き場所**（上端の下・下端の上・節と節のあいだ）を決めるだけで、**本数も密度も節の粒度も決めていない。** 節が1つの面では横罫はヘッダ下とフッタ上の2本だけ。加えて B1 により縦罫は画面端に接する。結果は「画面を囲む黒い枠＋上下2本の線」であって、格子ではない。
2. **担い手2がほぼ出ない。** §4 L99 が決めているのは主見出しの**下限**だけ。主見出しは冒頭に一度出るきりで、来訪者が大半の時間見るスクロール後の画面には**明朝が1文字も無い**（本文はシステムゴシック 17px）。B2 が起きればゼロになる。
3. **担い手3は定義上出ない。** 操作の記号は操作がある面にしか無い。読む面では「操作を色で示さない」は個性に寄与しない。
4. **4つ目（中身の色だけが立つ）も出ない。** 色を持つ中身が無い面では、画面は完全な無彩になる。

できあがるのは「白地・黒の細い枠・ゴシック本文」——**どの Markdown ブログとも見分けがつかない面**である。それでいて §1〜§13 のどの条にも違反していない。

実物にも同じ現象が写っている。広い画面の描画のうち、**上端の見出しを過ぎた下半分（入力と結果の節）は、33px の見出しを除けば全部ゴシック＋黒枠**で、無彩の管理画面に見える。担い手が効いているのは「巨大見出しが画面に入っている最初の一画面」だけで、**面の下半分ではすでに弱い。**

条件1は「ある面で見分けがつく」ではなく「**デザインだけで yolos.net だと分かる**」である。個性の出ない面を定義が許している限り、条件1は満たされない。**担い手のうち最低何本が、どの面にも必ず出るのか**を定義が決めていないことが根本原因である。

## Major

### M4-1. 図像の全面禁止が、§1 の自分の論理と §9 に矛盾する

§5 L131「**図像を持たない。** イラスト・写真・3D・絵文字を画面に置かない。」

- **§1 L12–13 と衝突する。** §1 は「サイトには多様なものが並び、入れ替わり続ける。何が置かれるかは事前に決まっていない。**器が色を持てば、その色と喧嘩しない中身しか置けなくなる。器の色は、作れるものを狭める。**」と論じ、だから色は「中身そのものであるときだけ」使う、という例外を **色にだけ** 与えた。**同じ論理は図像にそのまま当てはまる。** 図像を器の都合で全面禁止すれば、図像が中身そのものであるコンテンツ（キャラクターの札・図解・地図・グラフ・盤面）を作れなくなる。§1 が「作れるものを狭める」と断じた当のことを、§5 が図像に対して行っている。
- **§9 L215「画像は、それが何かを説明する代替テキストを持つ。」と直接矛盾する。** 画面に図像を置かないなら、代替テキストを持つ画像は存在しない。定義の内部で「図像はある」「図像は無い」が同居している。
- 実在するコンテンツを消す判断でもある（診断のキャラクター札画像が `public/blog/` に2点、絵文字はソース39ファイルで使用中）。刷新でそれを捨てる判断はありうるが、**その判断が定義のどこにも書かれていないまま、構造の節の1行で全サイトに及んでいる。**

**図像禁止は、実は §1 が挙げていない4本目の担い手である**（図像ゼロの画面は、それだけで量産サイトと分かれる）。中心の宣言に含めず構造の節に埋めたまま、例外の設計もしていないのは、定義として軽い。「器は図像を持たない／中身としての図像はこう扱う」を、色と同じ強さで決めること。

### M4-2. 明朝の配信条件が、内容が事前に決まらないサイトでは成立しない

§3 L85「WOFF2 で 300KB 以下」と L90「**見出しの中で書体が混ざらない。** 明朝に無い字が出る面では、その字を含めて配信する」は、§1 L12「何が置かれるかは事前に決まっていない」と組むと両立が難しい。

- 実測: しっぽり明朝 w500 の Google Fonts 配信実体は **122分割・合計 3,665KB**（最大の分割は 72KB、平均約30KB）。300KB は約10分割相当でしかない。
- 固定サブセットで 300KB に収めると、任意の見出し（人名・地名・旧字・記号）の字種を保証できない。保証しようとすれば 300KB を破る。面ごとの動的サブセットで解く道はあるが、**その場合「300KB以下」という単一の上限は定義として意味を失う**（面ごとに変わるため）。
- §13 L245「Web フォントの読み込みでリフローしない」と併せると、担い手2は「**落ちうる前提**」で設計されている。にもかかわらず B2 のとおり落ちたときの顔が未定義。

定義として決めるべきは「300KB」という一律の数字ではなく、**字種を保証する単位（面ごとか全体か）と、保証できないときにどの顔になるか**である。

### M4-3. 顔の大きさが決まっていない（実装者ごとに別の顔ができる）

§4 L98–99 が決めているのは、スケール（17 / 24 / 33 / 47 / 65px）と**主見出しの下限**（320px で 33px・1024px 以上で 47px）だけ。

- **どの見出しレベルが何 px かの割り当てが無い。** モックは h1=65px・h2=33px・h3=24px を採ったが、定義はこれを要求していない。
- 主見出しに上限も既定値も無いので、**下限どおり 47px を採った実装は定義に完全準拠しつつ、モックより明らかに弱い顔になる。** 65px と 47px は面の印象がまるで違う。
- 「巨大な明朝」が担い手なのに、**巨大さの値が決まっていない。** 個性の最大要素を実装者の裁量に置いている。

### M4-4. 縦罫の位置が決まっていない（署名の見え方が実装者ごとに変わる）

§5 L120「縦罫は…**内容の枠の左右端**を通り」・L124「**内容の左端は全ページで同じ位置**…幅ごとに中央寄せにしない」。

- 内容の枠の幅は `--max-width: 960px`（L124）と読めるが、**外側の余白の取り方が決まっていない。** 中央寄せなら張り出しは左右均等、左固定なら右だけに出る。**張り出しの長さ＝署名の見え方そのものが未定義。**
- モックは `margin: 0 auto` で中央寄せしており、L124「幅ごとに中央寄せにしない」と字面で食い違って読める（L124 が禁じているのは読む面と操作面で別々に中央寄せすることだ、とも読めるが、**定義が2通りに読める時点で欠陥である**）。
- 署名を条件1の柱に据えるなら、張り出しの最小長・外側余白の決め方は値で決めなければならない。

### M4-5. 検証記録の証拠が古く、直したはずの欠陥がそのまま写っている

`design-mock-verification.md` は修正 #3 で「**`--measure` は本文にかける。見出しはこの制約を受けない**」（見出しが「見つからないも／のを、」と語中で折れた件）を直したと書いている。しかし同梱の**広い画面ライトの描画は、その修正前の状態**である。

- 描画では主見出しが3行に折れ、1行目が「他では見つからない**も**」で切れて2行目が「のを、」——修正 #3 の症例そのもの。
- 現行 `index.html` を同条件（1280px・DPR2）で再描画すると **h1 の高さ 149.5px（＝行送り 74.75px × 2行）** で、3行にはならない。1024px・1440px でも同じ 149.5px。**つまり画像だけが修正前のまま残っている。**
- さらに **320px の描画は現行 CSS でも「見つからな／いものを、」と語中で折れている**（h1 の入る幅は 320 − 罫6 − 余白32 = 282px、33px 全角で 8.5字）。§4 L100「**見出しは意味の切れ目で折る。** 語の途中…で折らない」を、モック自身が満たしていない。

個性の顔である巨大見出しの**改行位置を決める規則が定義に無い**（「意味の切れ目で折る」という結果だけがあり、値も形も無い）。狭い幅では手で入れた改行だけでは足りず、**現に破れている。** 証拠画像の取り直しと、折り方の定義の両方が要る。

## Minor

### m1. 個性に寄与せず定義を重くしている規定（(D) への回答）

- **§7「増え続けることへの備え」L179–L185 のうち、「無限スクロールを持たない」以外の4項目**（既定の並び順・種別の絞り込み・全体の件数・どの面からも戻れる）は、見え方ではなく情報設計の要件。**形を決めていないので個性を生まない。**
- **§8 L199「送信や計算のあとに変わった内容は、読み上げにも伝わる」** は画面に見えないもので、§13 の下限にも入っていない。視覚の定義ではない。
- **§12 L236「枠は最初から確保され、CLS を出さない」** は性能要件。枠を最初から確保することは形の決定として残るが、CLS の言及は実装側。

いずれも「落とせ」ではなく「ここに置くと、条件1に効く規定が薄まる」という指摘である。

### m2. §9 の文章細目が他文書と重複している

§9 L212–L214（翻訳調・抽象動詞の連打・コロン頻出・ヘッジ・汎用最上級）は `docs/japanese-ai-slop.md` と `docs/anti-patterns/writing.md` の担当範囲。`japanese-ai-slop.md` は自ら「他のドキュメントとの役割分担」を定義しており、そこに `DESIGN.md` は入っていない。**§9 に要るのは「文章はこのデザインの一部である」という宣言と、L216 の AI 運営の告知が下端にあるという配置の決定だけ。**

### m3. ダークとライトの既定・切替が未定義

§2 は light と dark の値を持つが、**どちらが既定か、切替の手段を持つか、OS 設定に従うのか**を決めていない。§10 L223「`theme-color` は `--paper` の値」は、light と dark のどちらの `--paper` か決まらない。

### m4. favicon の「頭字」が決まっていない

§10 L222「`--ink` の地に `--paper` でサイトの頭字を明朝」。**「y」なのか「Y」なのか「よ」なのかが決まっていない。** §10 は自ら「デザインだけで見分けがつくかが最初に試される場所」と書いている。検索結果とタブで最初に出る 16px の記号——サイト外での個性のほぼ全部——を実装者の裁量に置いている。

### m5. 明朝のウェイトと字間が決まっていない

§3 L85「ウェイト1本」は本数の指定で、**どのウェイトかを決めていない。** 明朝は太さで顔が大きく変わる（モックは 500）。§4 L98 の `palt` も、併用する字間の値が無い（モックは `.01em`）。担い手2 の細部が実装者ごとに動く。

## Question

### q1. この視覚は、このサイトの中身と結びついているか

無彩・明朝・図像ゼロ・静かな器は「落ち着いた読み物」を名乗る形である。一方 `docs/site-concept.md` が掲げる独自性は「**AI が全自動で作り続けている／たくさん作って、たくさん試す／良かったものを伸ばし、そうでないものは引き上げる**」——実験場である。**想起（この画面は yolos.net だ）は、形の珍しさだけでなく、形と中身の結びつきで強くなる。** 形の珍しさだけを追うと「どこかで見た上品なサイト」で終わる可能性がある。この乖離は意図的か。意図的なら、その判断の理由が §1 に要る。

### q2. hover の外側の罫は、1px 罫で詰まった一覧でどう見えるのか

§6 L150「**8px 離れた外側に `--rule-w-hair` の罫が1本増える。**」と §7 の「1行1項目・`--rule-w-hair` で区切る」を重ねると、行の hover 罫は上下の隣接行の領域に食い込む（モックは `outline-offset: 8px` で実際に重なる）。個性として意図した見え方か、それとも一覧では別の見え方になるのか。

## (A) 独自性の外部照合——何が本当に珍しいか

| §1 の担い手                       | 同じ見た目になりうる既存の類型                                                                                                                                                                                                                                                                                                                                                    | 何がどう違うか                                                                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 端まで届く太い罫の格子         | **可視グリッド（2024–25 の現行トレンド）。** 「レイアウトの構造そのものを見せる」「アウトラインと罫が戻ってきた」と複数のトレンド資料が名指ししている。**構成は実在する**——`tailwindcss.com` の DOM には全幅の横罫 `absolute -mt-1 w-screen border-t …` と画面高の縦罫 `pointer-events-none absolute -top-1 -left-1 h-screen border-l …` が同居する（本レビューで実取得して確認） | **「貫くこと」は珍しくない。** 珍しいのは **3px・ベタ墨**という太さ（Tailwind は 1px・不透明度5%）。§1 L30 は差別化の所在を取り違えている |
| 1'. 太い黒枠・角丸0・黒ベタの操作 | **ネオブルータリズム。** 太い黒の輪郭・角丸なし・黒ベタのボタンはこの様式の定義そのもの                                                                                                                                                                                                                                                                                           | **ここは本当に分かれる。** ネオブルータリズムは「ハードな offset 影」と「原色」を必ず持つ。§5 の影なし・§2 の無彩の器がそれを外している   |
| 2. 巨大な明朝の見出し             | **和文タイポ系。** 2025 の日本語 Web フォント記事は明朝の再評価と「ミニマルと組み合わせる」を、タイポ記事は「巨大なタイポグラフィ」を、それぞれトレンド項目として挙げている                                                                                                                                                                                                       | **珍しくない。むしろ流行の中心。** 「既定 sans では作れない顔」は真だが、「だから見分けがつく」は成り立たない                             |
| 3. 操作を色で示さない             | **モノクロのミニマル／編集系。** 反転・罫・下線で操作を示す構成は Swiss 系の定番                                                                                                                                                                                                                                                                                                  | 反転・破線の無効・円と四角の選択記号まで**色を一切使わず通し切る**厳格さは珍しい。ただし操作のある面にしか現れない                        |

**結論。** 担い手を1本ずつ見ると、**単体で珍しいものは無い**（1'の影なし・無彩を除く）。珍しいのは4本を同時に、例外なく、**図像ゼロと器に色を一切置かないことまで含めて**通す厳格さのほうである。したがって個性は「**全部が同時に出ている面**」でしか成立しない。にもかかわらず定義は、B1（幅による署名の消失）・B3（担い手が出ない面）の2つの穴で、**全部が出ない面を大量に許している。** 「見分けがつかない」とまでは言わない——広い画面の一覧の面は確かに他と違う。しかし「**確実に**見分けがつく」は、現状の定義では成立しない。

## (C) 実物との一致——何が出ていて、何が出ていないか

| §1 が意図した個性                | 実物で出ているか                                                                                                                                                                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 端まで届く太い罫の格子           | 広い画面では**出ている**（外側に短い横罫の端が残る）。**320px では出ていない**（張り出し 0px）                                                                                                                                                 |
| 巨大な明朝の見出し               | **出ていない。** すべての描画でゴシック。フォント取得が FAILED、実測幅が三者一致（B2）                                                                                                                                                         |
| 操作を色で示さない               | **出ている。** 反転・破線・円と四角の記号が色なしで機能している。ライト／ダークの両方で成立                                                                                                                                                    |
| 無彩の器の上で中身の色だけが立つ | **出ている。** 藍色の見本だけが色を持ち、枠で地から切れている。ただし「並んだときに見えるのは中身の色だけ」という絵は、色を持つ項目が5行中2行のモックでは確認できていない（§1 L38 自身が「点数が少なければ起きない」と書いている＝**未検証**） |

**足りないのは定義のここ:** ①署名を幅に依存しない形で決めていない（B1）、②明朝が落ちたときの顔を決めていない（B2）、③どの面にも必ず出る担い手の最低本数を決めていない（B3）、④巨大さの値・縦罫の位置・改行の折り方という、顔を作る値を決めていない（M4-3・M4-4・M4-5）。

## 指摘の無い観点

- **§2 の数値**: コントラスト表10値すべてと「到達できる最大比 light 4.37 / dark 4.15」を独立に再計算し、**すべて一致**。指摘無し。
- **§6 の記号の設計**（役割ごとに別の記号・二重リング・形による区別）: 色を使わずに操作を区別し切れており、担い手3として実際に機能している。指摘無し。
- **§2 の中身の色の扱い**（範囲を制限しない・上に文字を置かない・枠を持つ）: 器と中身の分離として一貫している。指摘無し。
