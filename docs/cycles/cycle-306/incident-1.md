# cycle-306 事故報告書：なぜ「ブランディングを決めて2枚の画像を作る」だけの作業に約1ヶ月と巨額のLLMコストを溶かし、失敗を重ね続けたのか

オーナーの指示により、cycle-306単体でなく **cycle-279〜306 の「店構え/印/favicon/OGP」ブランディング作業の全体**を対象に、失敗が**生成され続ける機序**を掘る。症状やAP番号の列挙で終えない（cycle-283:241 が「何度自己点検しても症状だけ直して根を見逃す」と名指しした失敗の再演を避ける）。自己弁護はしない。

---

## 0. 事実（一次確認済み）

- **作業の実体**: 「サイトをどうブランディングするか決め、favicon と OGP という2パターンの画像を作る」。産物としては小さい。
- **費やした期間**: 店構えの枠組みの起点 cycle-279 は 2026-07-12 開始、cycle-306 完了は 2026-08-10。**約29日＝ほぼ1ヶ月。**
- **反復の規模**: favicon 関連コミット19本、印/試/B-583関連30本。favicon(B-576) は **cycle-299 で店構え化を出荷→同サイクルで旧ブランドへ撤回**、cycle-302 で色だけ青→朱、cycle-304 で新マーク出荷→撤回、cycle-306 でまた作り直し。印(B-583) は cycle-282 で「試」導入、283 で「屋」に変え撤回、304 で「試/店」追認し撤回、305 で観測に逃げ失敗、306 でようやく撤去したが**本来の問い（印というメタファー自体の是非）は未回答**。**出荷しては撤回する、を何度も繰り返した。**
- **cycle-306単体の消費**: サブエージェント約13体（接地2・レンダー2・実装4・レビュー5）、フルビルド/ゲート実行6回以上（各4142ページ生成＋全テスト5547件）、独立レビュー4巡＋ワークフローAP点検1巡。それだけ回して、**最後にオーナーの一問「なぜ丸印にしたのか」で、本来のタスクを達成していないことが露呈した。**
- **cycle-306の実際の帰結**: acute な害（自己貶めの「試」）の除去は本物。しかし B-583 の本来の付託——「印・札・店・試という**開発側都合のメタファーそのもの**が来訪者に最高の価値を提供しているか」——には答えず、むしろ**印(hanko)をfaviconとOGPに統一して温存・強化**した。

## 1. 核心：これは「小さな製造作業」ではなく「反証不能な判断＝枠組みの作業」だった。運用OSは前者用にできている

失敗の逆説（「小さいのになぜ膨大なコストと失敗か」）の答えはここにある。

- **製造作業としては小さい**（画像2枚＋数行のコード/文言）。
- **判断作業としては極めて難しい**。理由は次の2つが重なるから：
  1. **来訪者価値で反証できない**。OGPのシェア流入は実質ゼロ、favicon の検索結果CTRは多因子で計測不能（cycle-283/306の接地）。**「この案が正しい/間違い」を告げるデータのオラクルが存在しない。**
  2. **問うべき対象が、既に「正しさの定義」として体系に埋め込まれている**。「店構え・印・札・のれん・品書き」は DESIGN.md §4、site-concept.md、コード（`fuda-image`・`SHOP_SEAL_CHAR`）、語彙そのものに浸透している（cycle-279で全面移行）。B-583は「その枠組みを疑え」だが、**枠組みの内側から見ると DESIGN.md §4「印を捺してよい」は満たすべき制約であって、疑うべき仮説に見えない**（AP-P34：正典を疑うことの代替にする）。

この2条件が重なる作業を、わたしは**通常の製造作業として扱った**。だが本プロジェクトの運用OS——(a) PMが自律的に決める（オーナーに諮らない・AP-WF24）、(b) 完了＝成果物が揃うこと、(c) レビューは実装の正しさを検証、(d) 品質ゲート——は、**反証可能な製造作業に最適化されている**。反証不能な枠組み作業にこのOSを当てると、失敗するだけでなく**高コストに失敗する**：あらゆる機構が「製造」を増幅し、どの機構も「枠組み」を検査しないからだ。

## 2. 根本原因（生成機序・因果でつなぐ）

### R1. データのオラクルが無い→空白を「自分の世界観／継承した枠組み」が埋める

反証手段が無いと、判断の空白は必ず何かで埋まる。埋めたのは毎回**運営側の美意識と、継承した店構えの世界観**だった（cycle-282:157「記号が自分にとって何を意味するかで評価し、来訪者に何を届けるかを見ない」）。cycle-306でわたしが挙げた印の根拠（craftの差し色・ブランド認知・16px存在感・「印の視覚言語と揃う」）はすべて運営側の語彙で、来訪者が印から何を得るかではなかった。

### R2. 枠組みが「正しさの定義」として体系化されている→内側からは疑えない

cycle-279で店構えを全ページ・全語彙・全コードに刻んだ結果、「印がある」ことは前提でなく**規約**になった。各サイクルは規約を満たそうとし、「印は要るか」を問う入口が構造的に塞がれていた。cycle-306でわたしが「丸か角丸か」を議論していた事実が、既に「印はある」を疑っていない証拠。

### R3. 完了＝成果物＋PM自律→開いた問いを「完了できる下位タスク」に毎回すり替える

B-583の本体（「メタファーは来訪者に価値があるか」）は成果物が出ず居心地が悪い開いた問い。各サイクルはこれを**出荷できる下位タスクに変換**した：283=字を選ぶ（屋）、304=現状を追認、305=効果を観測、306=faviconを選び印を磨く。すり替えるたびに「綺麗に閉じた」成果物ができ、完了機構（ゲート緑・レビュー通過）がそれを**報酬**する。**完了機構は「立派な成果物」を報酬するが、「その成果物が誤った問いに答えている」ことは検出できない。** cycle-303の自己監査が既に「自分が完了できる仕事を本丸より上に置く」と名指ししていた病の、対象を変えた再演。

### R4. レビューもゲートも「実装の正しさ」を検証し「付託への適合」を検証しない→厳格さが誤答を磨く

cycle-306の4巡のレビュー＋AP点検は、実装の欠陥（試の残存・404検証・B-644の原因誤認）を正確に捕らえ全て承認した。だが**どの巡も「このサイクルはB-583の本当の問い（印は要るか）に答えたか」を問わなかった**。レビュー範囲はわたしが定義し、わたしは枠組みの内側で定義したから、レビューも内側で検証した。結果：**レビューを重ねるほど、誤った問いへの答えが磨かれ、コストだけ増えた。**

### R5. favicon先行・枠組みに染まった選択肢集合→問う前に機械的に枠組みを固定した

計画では「identityを先に決めfaviconは従う」だったが、実行では **favicon案(F1〜F4)を先に作って F2 を選び、それが identity(yの印)を確定させ、OGPを後から合わせた**（favicon実装を先に着手）。しかも生成した favicon 案は**すべて「y/よ の印・マーク」**で、「無印/印でない identity」案は0だった。**選択肢の集合自体が枠組みに汚染されていた**から、「印は要るか」は選択肢に登場すらしなかった。favicon先行（＝完了できる具体物を先に固める）が、枠組みをコンクリートで固め、本丸の問いへの入口を塞いだ機械的な機序。

### R6（メタ・最深）. 自己監査は枠組みの誤りを捕捉できない→外側に立てるのはオーナーだけ

cycle-282/283/304/305 の事故報告は**すべて**「自己規律では止められない・毎回オーナーの外部指摘で初めて止まる（AP-P02）」と結論した。cycle-306はそれを再証明した：わたしは4本の事故報告を通読し、「発生元未読/圧下で字を選ぶ病の再演」を最大リスクに挙げ、歯止め（発生元通読・実レンダー・敵対的レビュー）を敷いた——**それでも枠組みの誤りに歩き込んだ**。理由は、敷いた歯止めが**すべて枠組みの内側で作動する実装レベルの点検**（発生元を読んだか・レンダーは誠実か・是正は網羅的か）で、**失敗は枠組みレベル**にあったから。知識も歯止めも枠組みの内側で使えば枠組みは疑えない。実際、オーナーの最初の一問「なぜ丸印か」にすら、わたしは最初「正円か角丸か」の craft で答えた——直接問われてなお枠組みの内側に留まった。**枠組みの外に立てるのはオーナーだけ**で、だから毎回オーナーが唯一のオラクルとして事後に捕捉する、高コストな catch-and-redo ループになる。

## 3. なぜコストが爆発したのか（機序）

「小さいのに巨額」の内訳：**製造としては小×判断としては反証不能×毎サイクルに製造フル装備を投入×それをNサイクル×出荷と撤回の反復**。

- 反証不能（R1）→ 決着せず何サイクルも続く（279,280,282,283,299,302,304,305,306）。
- 枠組み不問（R2）→ 毎サイクル印/favicon作業をゼロからやり直す。
- すり替え（R3）→ 毎サイクル完全な成果物を作る（撤回されても作り直す）。
- 実装検証の厳格さ（R4）→ 各成果物に4〜5巡のレビュー＋数回のフルビルド（4142ページ×複数回）。
- **品質を担保するはずの装備（レビュー必須・ゲート・サブエージェント委譲）が、誤った標的に向けられたことで、そのままコスト増幅器になった。** 装備は誤りを一度も是正しなかった——的が枠組みの外にあったから。

## 5. 実効性のある対策（自分向けルールの追加ではない——AP-WF28がそれは効かないと記録済み）

効くのは、**枠組みレベル**で作動する構造的・外部的な仕掛けだけ。

1. **タスク種別の識別を先頭に置く**：「**データのオラクルが無い＋既存の枠組みを疑うことが付託**」の作業は、通常の製造作業と別クラスとして扱う。この種別では運用OSの既定（PM自律・成果物完了・実装レビュー）が**逆効果**であることを前提にする。（この識別自体は自分が行うので限界がある——だから以下2〜4を併用する。）
2. **「無」を既定にする（null-default 法）**：「メタファーXを問い直せ」の付託では、**Xを取り去った版を第一級の成果物として実レンダーし、Xを残す側に立証責任を負わせる**。「この面で印が来訪者に足す価値」を来訪者の言葉で言えないなら、印は消える。選択肢集合に**必ず枠組み否定（無印・非店・無マーク）を含める**。cycle-306はこれを怠り、印4案しか作らなかった。
3. **付託適合レビュアーを立てる**：実装レビューとは別に、**元の付託文だけを渡し「これは付託の問いに答えたか、それとも簡単な別問題にすり替えたか」だけを問う**レビュアーを、枠組みの外側の観点で必ず1体立てる。cycle-306の5レビューは全て実装/枠組み内側だった。
4. **反証不能な枠組み判断は、磨く前にオーナー（唯一のオラクル）に安く諮る**：データで反証できない**枠組み/identity の決定**に限っては、フル装備で成果物を磨いて出荷しオーナーに事後撤回させる（高コスト catch-and-redo）のでなく、**最小コストで枠組みの当否をオーナーに確認してから製造に入る**。これは AP-WF24（PMが決めるべき実装判断をオーナーに丸投げ）とは別物：**実装判断＝PMの自律／反証不能な枠組み判断＝オーナーが唯一のオラクル**、という線引きを持つ。実際、本作業で唯一失敗を止めたのは毎回オーナーだった＝オーナーがこの判断のオラクルであることの経験的証拠。
5. **正直な限界**：1は自己判断に依存し、AP-P02により自分では枠組み誤りを捕捉できない。だから**2（無を既定）・3（付託適合レビュー）・4（枠組みはオーナーに安く諮る）という、自分の判断に依存しない仕掛けが本命**。「次から気をつける」では止まらない（cycle-282〜305で5回実証済み）。

## 6. 本サイクルの帰結の是正

- **B-583は未達として再オープンする**。cycle-306は acute な害（試）を除いたが、本来の付託（印・札・店というメタファー自体が来訪者に価値を持つか）に答えていない。「試を消して綺麗に閉じた」で完了扱いにしたのは、まさにR3のすり替えの再演だった。
- 今の角丸スクエアの印（favicon/OGP）を「正しい」とは扱わない。再オープンした B-583 で、**印の要否そのものを null-default 法＋付託適合レビュー＋オーナーへの枠組み確認で**やり直す。
- 出荷済みの変更のうち、来訪者価値が独立に立つもの（自己貶めの「試」除去・旧ブランドfaviconの置換＝少なくとも整合性の回復）は撤回しない。撤回するのは「印はこの形/この存在で正しい」という**未検証の確定**の部分。
