### 0-4. 環境差についての正直な注記

同じ本番ページでも、**フォントのフォールバックが違うと折返し行数が変わり、値は 25〜80px ずれる**。実例:

- A1（measurement.md・MCP Playwright）: character-personality の説明文 **146.9px（6行）**・最終選択肢 bottom **735.3**。
- 本改訂（headless chromium・375×550）: 同じページで説明文 **122.4px（5行）**・bottom **710.9**。
- 本改訂を **360×550** で測ると説明文 **146.9px（6行）**・進捗 top **301.5**（＝A1 の track top 310.4 と中央揃えで整合）となり、A1 の上部の値を完全に再現する。ただし選択肢側は 360 で3行に折り返す設問があり bottom は 777.3 になるため、**A1 と本改訂の差は「幅の差」だけでは説明できず、フォントメトリクスの差を含む**。

したがって:

1. **絶対値を環境をまたいで比較しない**。合否は「同一環境で before/after を測る」ことで判定する（§6-A）。
2. **薄い余裕を「収まっている」と呼ばない**。折返しが1行増えると `line-height: 1.5` で +24px 動く。余裕はこの1行を吸収できる幅を要求する。
3. 判定は最も不利な条件（**360×550**）で行い、375×550 も併記する。

### 1-7. 原因の構造（コードの一次確認・行番号は B-620 第2段の実装後の作業ツリー基準）

## 2. 各案

初版の6案の骨子は維持し、数値だけを再実測に差し替える（案の追加・削除はしていない。実装形の比較は §4-7 で (iv) を加えた）。

### 案1: 回答中だけ、上部の非機能要素をレイアウトフローから退かせる

**何をするか**: playing フェーズのときだけ、パンくず領域と `.header`（h1＋説明文）をレイアウトフローから外す。DOM からは落とさない（初期 HTML には常に存在する）。h1 は視覚的にのみ隠して a11y ツリーに残す。

**375×550 の数値（退避のみ・実測からの算術）**: 退避量ぶんだけ全体が上がる。

| クイズ                                      | 退避量       | 最悪 bottom → 退避後        | 余裕     |
| ------------------------------------------- | ------------ | --------------------------- | -------- |
| character-fortune                           | 204          | 742.9 → **538.9**           | **11.1** |
| character-personality / word-sense / animal | 204          | 710.9 → 506.9               | 43.1     |
| science-thinking                            | 319.6        | 826.4 → 506.8               | 43.2     |
| japanese-culture                            | 179.6        | 686.4 → 506.8               | 43.2     |
| music-personality                           | 179.6        | 665.4 → 485.8               | 64.2     |
| kotowaza-level                              | 179.6        | 634.4 → 454.8               | 95.2     |
| その他6本                                   | 155.1〜179.6 | 545.9〜602.4 → 390.8〜443.8 | 106〜159 |

→ 375×550 では全15本が 550 以下になるが、**最悪の余裕は 11.1px**（初版の「11px」を再実測で追認）。**360×550 では character-personality が 548.8 で余裕 1.2px** まで落ちる。折返しが1行増えれば即座に未達に転落する水準であり、**退避だけでは「収まった」と言えない**。→ R1〜R3 が必要な理由はここにある（§4-3）。

参考（算術）: パンくずを残して h1＋説明文だけ退かせると退避量は 21+16=37 減り、character-fortune で 575.9 と未達。h1 を可視のまま残す形も 563.5 で未達。**3つすべてをフローから外すのは選択ではなく算術上の要件**である。

**副軸1（SEO）**: 影響なし。h1・説明文・パンくず（BreadcrumbList JSON-LD 含む）は初期 HTML に残る。さらに**クローラは playing フェーズに到達できない**（「はじめる」のクリックが必要）ので、クローラが見るのは常に intro 状態＝現状と同一の DOM/CSS である。`<meta name="description">` と JSON-LD は registry 由来で本文描画と独立（`src/app/play/[slug]/page.tsx` → `src/play/seo.ts`）。隠しテキストによるクローキング懸念も生じない（隠すのは操作後の状態で、内容の差し替えではない）。

**副軸2（a11y）**: h1 を視覚的非表示（フローから外すが DOM と a11y ツリーには残す）にすれば、見出し構造（h1 → 設問 h2 → FAQ h2）は回答中も維持される。`display:none` にすると回答中は h1 が a11y ツリーから消える（WCAG の達成基準違反ではないが、見出しジャンプで文脈に戻れない）。パンくず（nav ランドマーク）は回答中に消えるが、サイト共通 `Header` の nav は `<article>` の外にあるため、ナビゲーション手段は失われない。変化は「はじめる」押下という**ユーザー起点の1回だけ**で、同時に intro ブロック全体が設問に置き換わる。`QuestionCard` はマウント時に設問見出しへフォーカスを移す（`QuestionCard.tsx:78-81`・`preventScroll: true`）ので、SR 利用者は新しい文脈を読み上げられる。

**副軸3（他コンテンツへの波及）**: 15本＋専用ルートすべてに同じ機構が効く。**知識クイズの「次へ」は本案でも fold 下に残る**（実測からの算術: kotowaza-level で退避のみ 627.1・退避＋R1〜R3 で 594.7）。→ 初版は「別タスクへ起票」としたが、本改訂では同じ質の欠陥として本サイクルに含める（§4-4）。

**副軸4（intro / result への影響）**: intro は不変。result も不変（header が戻った状態で `resultRegionRef` への `scrollIntoView` + `focus` が走る＝`QuizContainer.tsx:123-144`）。ただし「最終回答 → phase=result → header 復帰 → scrollIntoView」の順序で、スクロール目標が復帰後のレイアウトで計算される必要がある（**推論**。§6-B で実測）。

**副作用と失敗の仕方**

1. **余裕が薄い**（退避のみで 11.1px／360 では 1.2px）。→ R1〜R3 で 21.2〜37.2px まで広げる。
2. スクロール済みで「はじめる」を押すと表示内容が跳ねる。→ R4 で潰す。
3. `handleRetry` で intro に戻ると header が復帰してページが伸縮する。既存挙動と同型だが検証対象。
4. CLS: ユーザー入力から 500ms 以内のレイアウトシフトは CLS に計上されない（**推論**。§6-B で確認）。intro の初期表示は変えないので LCP/CLS の初期値には影響しない。
5. 退避（即時）と `.card` の `fadeIn`（opacity + `translateY(8px)`・300ms）が**同一フレームで重なる**（m-10）。上へ 155〜320px 詰まると同時に設問カードが下から浮き上がる二重の動きになる。§6-B で見え方を評価する。

### 案2: 回答フェーズに入った時点でスクロール位置を設問へ移す

**何をするか**: `handleStart` で進捗ブロックの先頭へ `scrollIntoView`。既存の result リビール（`QuizContainer.tsx:123-144`）と同じ機構・同じ `prefers-reduced-motion` 分岐を流用する。DOM もフローも変えない。

**数値**: サイト header はスクロールで退く（`.header` に `position` 指定が無く既定の static）。進捗先頭まで送ると相対 bottom = 進捗 23.8 + 24 + 設問 + 選択肢 = **334〜452**（全15本・実測構成要素からの算術）。

**ただし第一の軸（scrollY=0 で4択が可視）を文字通りには満たさない**。scrollY は 155〜320 になる。この差は言葉遊びではない——`scrollY>0` はブラウザのスクロール復元・スクロールアンカリング・iOS のツールバー伸縮・戻る操作で崩れ、崩れると元の欠陥（4択が見えない）へ静かに戻る。

**副軸**: SEO 影響なし。a11y は最良（何も消えない）。ただし `QuestionCard` のフォーカス移動が `preventScroll: true` なのに親がスクロールするという同一フレーム内の2つのスクロール制御の競合が生じる（既存 result 側の N1 コメントが同じ罠を記録している）。知識クイズでは設問先頭に固定したままだと「次へ」が fold 下に残る（案1 と同じ未達）。実装は最小。

**失敗の仕方**: 上へ一度フリックすると回答中に機能しない紹介文が現れる＝問題を移動させただけ。**スクロール後の座標で測ると合格に見える**ため、自案に有利な測度を選ぶ危険が最も高い（AP-P02）。§0-2 に書いたとおり、本改訂の計測でも auto-scroll による汚染が実際に起きた——この案は「静かに測り間違える」性質を構造的に持つ。

### 案3: 説明文を `meta.shortDescription` に差し替える（器の取り違えの是正）

**数値（実測からの算術・375×550）**: 説明文が 3〜7行から 1〜2行（17〜40字）になる。削減量は「現在の説明文の高さ − 24.5（1行）または 49（2行）」。最悪の science-thinking は 826.4 → **679.5〜704.0**、character-fortune は 742.9 → 645.0〜669.5。**15本中 8〜12本が 550 未達**（短説明が1行に収まるか2行になるかで変わる。1行なら8本・2行なら12本）。→ 単独では第一の軸を満たさない（必要な削減は最悪 276.4px に対し、削減は最大 146.9px）。

**副軸**: head の description・JSON-LD は不変。ただし本文（初期 HTML）から 120〜160字の日本語が消える。a11y 影響なし（要素が常に存在し動かない＝全案中で最も静か）。15本ぶんの `shortDescription` の質が問われる。intro の初見体験は改善する（「はじめる」到達が 523.9 → 約 377 と算術で見込める）が、「これは何か」の情報量は落ちる。実装は1行。

**失敗の仕方**: 「短くしたから直った」と誤認して終わるのが最悪で、これは cycle-300 の「375×812 で測って収まったと結論した」誤りと同型。

### 案4: 回答フェーズを全画面レイヤーとして独立させる

**数値（算術）**: 上端 16 + 進捗 39.8 + 設問 + 選択肢 = **334〜452**。全15本で 98px 以上の余裕。数値上は最良で、上流に何を足しても壊れない。

**副軸**: a11y が最も重い（フォーカストラップ・`aria-modal` の是非・Esc・背後の `aria-hidden`・スクロールロック）。スクロールロックは `layout.tsx:31-32` の `<body style={{...}}>` と競合する既知の罠（AP-I07: `document.body.style` は JSX 由来の style で上書きされる。`classList` で切り替えること）。知識クイズは層の中でスクロールが必要になり入れ子スクロールの罠を全面に持ち込む。`100dvh` の iOS 挙動で層の下端が切れると、選択肢が見えない元の問題が別の形で再発する（しかもスクロールで救えない）。回答中に FAQ・関連診断・将来の広告区画から来訪者を切り離す。

### 案5: DOM 並び替え（説明文を本体より下へ恒久移動）

**数値（算術・375×550）**: 説明文と `.header` 内の gap 4 が上部から消える（削減 = 説明文の高さ + 4）。最悪 science-thinking 826.4 → **651.0**、character-fortune 742.9 → 616.5。**15本中 7本が未達**。単独では第一の軸を満たさない。

**副軸**: 本文は初期 HTML に残る（位置だけ変わる）ので案3 の本文減を補える。静的で動かず a11y 良好。intro の第一ビューから説明が外れる。result フェーズで「結果 → 開始前の紹介文 → おすすめ」という読み順の劣化が起きうる。

### 案6: 寸法・情報量のダイエット単独

**数値（実測からの算術）**: 削れるのは「進捗の下余白 24→16（−8）」「設問見出しの下余白 20→16（−4）」「選択肢 gap 10→8（−6）」「選択肢の上下 padding 12→8」で、選択肢の高さは行数により 47→44（−3）・68→66（−2）・89→90（**+1**）と変わる。合計 **−26〜−30px**（選択肢の行数による）。最悪 science-thinking は **800.4** で、**15本中 10本が未達**。原因（上部占有 139〜304px）と対処（−30px）の桁が合っていない。

設問見出しのフォント縮小で稼ぐ手は DESIGN.md §3 の見出しスケール（16/20/25/31/39px）と衝突し、選択肢の文字を 14px にするのは §3「文章として読ませる文は 16px」と衝突する（可読性を削って辻褄を合わせる行為）。

**ただし案1 の薄い余裕を厚くする補助としては有効**で、DESIGN.md §4 の 8px スケール逸脱（`.choices` gap 10px・選択肢 padding 12px・`.questionText` margin 20px・`ProgressBar .wrapper` margin 24px）の是正でもある。単独案としては不採用、併用要素としては採用（R1〜R3）。

- **幅条件を 480px にした理由**: 現行のスマートフォンの CSS px 幅は 320〜430 に収まり、480 はその上限に余裕を見た値（リポジトリの既存 CSS でも `max-width: 480px` を3箇所で使っており、新しい語彙ではない）。768px まで広げると、**実測で欠陥が無い 481〜768px の帯（余裕 33.5〜477.3px）でも文脈が消える**。決定2 の論理（得るものがない面から文脈を消すのは純損失）をそのまま適用すると 480 が正しい。
- **高さ条件 640px の役割**: 横向きのスマートフォン（812×375・844×390 等の短辺）と、デスクトップの短い窓を拾う。デスクトップでは media query の高さ＝実可視高なので、640 以下なら実際に危ない（実測の広幅最悪は 597.7 なので 640 は 42px の余裕を見た設定）。
- **iOS の動的ビューポートの評価**: iOS Safari ではツールバーの伸縮で**視覚ビューポート**は変わるが、media query が参照するレイアウトビューポート（＝large viewport）は伸縮しない（**推論**。CSS Values 4 の large/small/dynamic viewport の規定に基づくが、一次資料は未確認）。したがって `max-height: 640px` がスクロール中に付いたり外れたりして退避が明滅する事故は起きない見込み。**ただしこれは推論なので、§6-B で実機相当（iOS の縦横回転・ツールバー伸縮）を再現できる範囲で確認し、できなければ「未検証」と書き残す**。仮に明滅が起きても、モバイルは幅条件（480）で常に真になるため、明滅しうるのは「幅 481 以上かつ高さが 640 の前後を跨ぐ窓」だけである。
- **残差リスク（正直に書く）**: 幅 481〜768 かつ高さ 641 以上の帯（例 540×720 は余裕 33.5px）は退避が当たらない。実測では収まっているが、余裕が折返し1行（24px）+ 数 px しかない設問がある。→ §6-A の合格条件に 540×720 の計測を入れ、**余裕が 24px を下回っていたら幅条件を 600px へ広げる**という条件付きの取り決めにする（現状の数値で決め打ちしない＝AP-P03）。

**R1〜R3・F1・N1 は画面幅で条件分けしない**（余白の是正・押下フィードバック・「次へ」の可視化はどの画面でも劣化にならない）。デスクトップでの影響は算術で 1280×720 の最悪 597.7 → **567.7**、personality 群 573.3 → **543.3**（いずれも余裕十分・パンくず・h1・説明文は可視のまま）。

### 4-5. 選択の即時フィードバック（決定3・B-2）——F1

**現状の一次確認**: `QuestionCard.module.css` に `:active` は 0件。`:hover` はタッチ端末では押下の合図にならない（タップ後に残る hover 状態はむしろ紛らわしい）。personality では `selectedId` が state にあるのに `getChoiceClassName` が使わない。ただし `-webkit-tap-highlight-color` は上書きしていない（grep 0件）ので、**OS 既定の淡いタップハイライトだけは出ている**。「フィードバックが皆無」は CSS の話であり、実機の体験は「弱いハイライトが一瞬出る」である（index.md §E の記述を本改訂で限定した）。

**採用: `:active` に罫＋座布団を当てる（レイアウト不変）**。

```
.choiceButton:active:not(:disabled) { border-color: var(--accent); background-color: var(--accent-weak); }
```

- **レイアウトを変えない**（色と罫のみ）。§4-3 の px 予算に影響しない。
- DESIGN.md §2 は `--accent-weak` を「**操作・選択状態のハイライト（hover/selected の座布団）にのみ可**」と明記しており、hover と同じ語彙を押下に当てるのが器の作法に最も近い。§5 の「操作フィードバック（押下・選択・150ms 以下）」に該当し、既存の `transition: border-color .15s, background-color .15s` がそのまま 150ms 上限に一致する。
- リポジトリの前例7件のうち4件は `filter: brightness()`（`Button`・kanji-kanaru・yoji-kimeru・nakamawake）、1件は `transform: scale(.97)`（irodori）。紙地（`--paper`）のボタンに brightness を掛けても変化が乏しいので、**朱の座布団のほうが押下が読み取れる**（推論・§6-B の視覚評価で確認する）。`transform: scale()` はレイアウトを変えないが、44px のタップ標的が縮んで見えるので採らない。
- **なぜ state ではなく `:active` か**: personality では押下と同時に次設問へ遷移して `QuestionCard` が再マウントされるため、`selectedId` 由来のクラスは**描画されるフレームが無い**。ブラウザがネイティブに描く `:active` だけが押下の瞬間に出る。
- **未検証の点（§6-B へ）**: iOS Safari は歴史的に「祖先にタッチイベントリスナがある場合にだけ `:active` を適用する」挙動を持つ。React はルートにリスナを付けるため満たされる見込みだが（**推論**）、実機で確認する。効かない場合の代替は、`onPointerDown` で class を付ける実装（レイアウト不変・タイマー不要・`onPointerUp`/`onPointerCancel` で外す）を第2案として置く。

**F1 の位置づけ（B-620 第2段の実装確定を受けて）**

- **正しさ（結果が静かに変わらないこと）は F1 に依存しない。** それは B-620 第2段の冪等化（`reduceQuizProgress` の不変条件）と 600ms の間隔ガードが担保している（§4-6）。F1 が効かない環境でも診断結果は壊れない。
- **F1 の役割は「再タップする理由そのものを取り除くこと」**である。間隔ガードが塞げるのは「短時間に届いた2回目」までで、**600ms 以上経ってからの意図的な再タップ**——押したのに何も起きなかったと思った来訪者が、間を置いてもう一度押す——は、タイミング規則では正当な回答と区別できない（次の設問への回答として受理される）。この残存リスクを減らせる手段は、**押した瞬間に「効いた」と分かること**しかない。
- したがって F1 は「あれば良い付加」ではなく、**間隔ガードでは原理的に届かない領域を埋める唯一の対処**として第1段に入れる。効いているかは §6-B-15（実機で押下時の見え方）で確認する。

### 4-6. 二重タップの残存リスクと間隔ガード（決定3 の後半・**B-620 第2段が実装済み**）

なお、タイマーを使わない別の代替案として「`.card` の `fadeIn` キーフレームで `pointer-events` を離散アニメーションさせる」形も検討したが、(a) `prefers-reduced-motion` でアニメーションを切ると保護も消える、(b) CSS の離散アニメーションの挙動に依存し読み手に伝わらない、の2点で採らない（採用された時刻差ガードにはこの2つの弱点が無い）。

### 4-7. 実装形の選択（決定1・M-5・B-1）

| 形                                                | 仕組み                                                                                                                                                       | 依存            | 弱点                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------- | ---------------------------------------------------------------------- |
| (i) CSS `:has()` ＋ `data-quiz-phase`             | 子（`QuizContainer`）が属性を出し、親側の CSS が `:has()` で退避                                                                                             | `:has()` の対応 | **非対応環境では何も起きない**（静かに現状のまま）。ブラウザ依存が残る |
| (ii) サーバー JSX をスロットで渡す                | `QuizPlayPageLayout` が `<header>` を prop で渡し intro/result のみ描画                                                                                      | なし            | **h1 が DOM から消える**＝a11y ツリーからも消える。設計の利点を捨てる  |
| (iii) 状態のリフトアップ                          | フェーズを持つクライアント shell を新設して header と本体を包む                                                                                              | なし            | 変更範囲が最大。得るものは (i)(ii)(iv) と同じ                          |

**採用: (iv)**（PM 決定1）。理由:

- **全ブラウザで動く**。`:has()` の対応可否に賭けない。PM の実測（BigQuery・直近90日・総PV2,834／総セッション1,775）では `:has()` **非対応がセッション 2.70%・判定不能 1.80%＝約4.5%**（本エージェント未再現。内訳と一次資料は付録D）。**確認済みの欠陥を 4.5% の来訪者に残す理由がない**（CLAUDE.md 意思決定原則: より良い UX が達成可能ならそれを選ぶ。実装の手間は理由にならない）。
- **h1 を DOM から落とさない**（(ii) の欠点を回避＝M-5）。
- **jsdom でテストできる**。属性の遷移（intro→playing→result）と、`QuizPlayPageLayout` を含む統合レンダリングで祖先に属性が付くことを検証できる。初版の「§6-13: `:has()` 非対応環境の挙動は再現できなければ未検証」という項目が**消える**。
- (ii) はフォールバックとしても採らない（h1 の a11y 保持という本案の利点を捨てるため＝決定1）。

**具体の設計（builder への指示に足る粒度で。コードは書かない）**

1. **属性を立てる対象**: `QuizPlayPageLayout` が描画する `<article className={styles.layout}>` に、サーバー側で `data-quiz-layout` というマーカー属性を付ける。`QuizContainer` は自分のルートへの ref から `closest("[data-quiz-layout]")` で祖先を取得し、そこへ `data-quiz-phase={phase}` を設定する。
   - **`document.body` / `documentElement` を使わない理由**: (a) CSS Modules から参照するには `:global(...)` でスコープを越える必要がある、(b) サイト全体に見えるグローバル状態になり他機構と衝突しうる、(c) `layout.tsx:31-32` の `<body style={{...}}>` と同じ要素を触ることになる。**`data-*` は React が管理していない属性なので `style` のように上書きされることはない（推論・AP-I07 は `style` の話）が、同じ要素に触る必要が無い以上、避けるのが安い**。
   - マーカー属性を server 側に明示的に置くので、「誰が誰を見ているか」が両側のコードから読める（離れた依存なのでコメント必須）。`closest()` は祖先であることだけに依存し、DOM の段数・順序に依存しない。
2. **`useLayoutEffect` を使う（`useEffect` ではない）**: `useEffect` だと playing の DOM を描いた**後**に退避が効くため、1フレームだけ「上部あり＋設問あり」が描かれてから 155〜320px 跳ねる。`useLayoutEffect` は commit 後・paint 前に走るので同一フレームで確定する（**推論**。§6-B で連続キャプチャして確認する）。
   - **SSR の扱い**: 初期 phase は `intro` で属性が無いのが正しい状態なので、サーバー出力と一致し hydration mismatch を作らない。ただし React が SSR 時に `useLayoutEffect` へ警告を出すか（React 19.2.7 での挙動）は**未確認**。builder は `npm run build` と dev のログで確認し、警告が出る場合は (a) `handleStart`/`handleRetry` などの遷移地点で同期的に属性を設定する形、(b) `useEffect` に退避してちらつきを許容する形、のどちらを採るかを実測（ちらつきの有無）で決める。
3. **cleanup**: `useLayoutEffect` の返り値で `data-quiz-phase` を削除する（アンマウント時に属性を残さない）。依存配列は `[phase]`。
4. **CSS**（`src/app/play/[slug]/page.module.css`）:
   - `@media (max-width: 480px), (max-height: 640px)` の中に置く（§4-2）。
   - `.layout[data-quiz-phase="playing"] .contextZone { display: none; }`
   - `.layout[data-quiz-phase="playing"] .header { position: absolute; width: 1px; height: 1px; margin: -1px; padding: 0; overflow: hidden; clip: rect(0,0,0,0); white-space: nowrap; }`（`globals.css:248` の `.visually-hidden` と同等。CSS Modules で `composes` するか global を使うかは builder 判断）
   - **絶対配置にする理由**: `.layout` は `display:flex; gap:1rem` なので、`display:none` ではなく絶対配置にすると**flex item ではなくなり gap も生まない**（CSS Flexible Box Layout Level 1 §4.1「絶対配置された子は flex レイアウトに参加しない」。**推論だが仕様に根拠がある**）。退避量が「上部占有＋gap 16」ぴったりであることは §1-3 の実測（進捗 top − 73 = 155.1〜319.6 が bc+16+h1+4+desc+16 と一致）で確かめてある。§6-A の「進捗 top = 73±2」がこの検証になる。
   - h1 を a11y ツリーに残すため `.header` は `display:none` にしない。**説明文（`.shortDescription`）だけは `display:none`** にしてよい（回答中に SR が長文の紹介文へ迷い込む必要はない。DOM には残る）。
5. **アニメーションを付けない**（DESIGN.md §5・「動きを足さない」）。

## 付録C: 数値の作り方（推計モデルの廃止と、残した算術）

初版は character-personality の1点実測に校正した計算モデルで他14本を推計していた。**本改訂ではモデルを廃止した**——15本×全設問を機械的に実測できる手順（§0-2）を作ったため、現状値に推計を使う理由がなくなったからである。

### 変更後の値に使う算術（これは推計ではなく実測構成要素の四則演算）

- **退避後 = 現状の bottom − 退避量**（退避量 = 実測した「進捗ブロックの top − 73」）。
- **R1〜R3 適用後 = 73 + 23.8（進捗ラベル） + 16 + 設問見出しの実測高 + 16 + Σ選択肢の新しい高さ + 8×3**。
  - 選択肢の新しい高さ = `max(44, 8+8+2 + 24 × 行数)`。行数は実測高から逆算（`47→1行`・`68→2行`・`89→3行`。現状は `12+12+2 + 21×行数`）。
  - 1行 → 44（`min-height` が効く・現状 47）／2行 → 66（現状 68）／**3行 → 90（現状 89・+1px）**。
- **「次へ」= 上の値 + 16（解説の margin-top） + 解説の実測高 + 16（次への margin-top） + 44**。

### 定数（実測で確認済み）

サイト header 57（`--header-height: 3.5rem` + 1px 罫。`.header` に `position` の指定が無く**既定の static** なのでスクロールで退く。`Header.module.css` の `position` 指定は 119・177 行のモバイルオーバーレイ用のみ＝m-5）／`.layout` padding-top 16・gap 16（≤768px）／`.header` gap 4／進捗ラベル行 23.8／設問見出し 1行 32。

### 旧モデルの限界（記録として残す・同じ罠を後続が踏まないため）

- (a) 実機の日本語フォントメトリクスによる `normal` 行高の差を織り込めていなかった（R1 でこの依存を消す）。
- (b) 半角混在の折返しを全角換算で近似していた（±1行の誤差）。
- (c) 検証は実測が正であり、モデルは実測対象を選ぶための道具にすぎない。
- (d) **パンくずのセパレータ余白（`Breadcrumb.module.css` の `.separator { margin: 0 0.4em }`）を無視していた**（m-1）。実測では science-thinking のパンくずが **3行 63px**（モデルは2行 42px）になり、上部占有を 21px 過小評価していた。「文字数 ÷ 1行の字数」で行数を出すモデルは、区切り記号の左右アキのような**文字以外の幅**を落とす。
- (e) （本改訂で追加）**フォントのフォールバックが違う環境では値が 25〜80px ずれる**（§0-4）。モデルの誤差ではなく計測環境の差であり、モデルを精緻化しても消えない。だから合否は同一環境の before/after で判定し、余裕は「折返し1行を吸収できるか」で評価する。
