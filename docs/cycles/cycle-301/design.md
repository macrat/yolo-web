### 1-4. 原因の構造（コードの一次確認）

- 上部3要素はサーバーコンポーネント `QuizPlayPageLayout`（`src/play/quiz/_components/QuizPlayPageLayout.tsx:106-119`）が描画し、フェーズ状態はクライアントコンポーネント `QuizContainer`（同`QuizContainer.tsx:43`）が持つ。両者は親子で、親は子のフェーズを知らない。

  - `ToolPageLayout/index.tsx:57` は `meta.shortDescription` を描画している。
  - `QuizPlayPageLayout.tsx:118` は `quiz.meta.description` を描画している。CSS クラス名は `.shortDescription`（`page.module.css:37`）なのに、渡しているのは SEO 用の長文である。

  - `QuizMeta` には `shortDescription` が**全15本に存在**する（17〜40字）。
    → つまり「回答中に邪魔」以前に、**表示に使うフィールドを間違えている**。これは設計判断ではなく写し崩れである。

## 2. 各案

### 案1: 回答中だけ、上部の非機能要素をレイアウトフローから退かせる

**何をするか**: `QuizContainer` のルート要素に `data-quiz-phase={phase}` を出し、`page.module.css` 側で `.layout:has([data-quiz-phase="playing"])` のときにパンくず領域と `.header` をフローから外す。DOM からは落とさない（初期 HTML には常に存在する）。h1 は視覚的にのみ隠す（`display: contents` の親＋絶対配置の視覚的非表示）ことで a11y ツリーに残す（= 案1-A2）。単純に `display:none` する形（案1-A1）も選べる。

**375×550 の数値（推計・character-personality のみ実測差分）**

退避量 = パンくず(bc) + gap16 + h1 + gap4 + 説明文 + gap16。上端は「サイト header 57 + layout padding 16 = 73」に固定される。

| クイズ                                     | 退避量   | 選択肢 bottom                   |
| ------------------------------------------ | -------- | ------------------------------- |
| character-fortune / word-sense-personality | 204      | **539**（余裕 11px）            |
| science-thinking                           | 298      | 507                             |
| character-personality                      | 228.5    | **506.8**（実測 735.3 − 228.5） |
| animal / japanese-culture                  | 225      | 507                             |
| music-personality                          | 179      | 486                             |
| kotowaza-level                             | 179      | 455                             |
| その他                                     | 155〜179 | 391〜444                        |

→ **全15本で 550 以下**。ただし最悪2本の余裕は 11px しかない（後述の弱点）。

参考: **パンくずを残して h1＋説明文だけ退かせると 428〜576 で6本が未達**（science-thinking 565・character-fortune 576・word-sense 576・animal 565・japanese-culture 565）。**h1 を可視のまま残すだけでも 571〜580 で未達**。つまり第一の軸を満たすには「パンくず・h1・説明文の3つすべてをフローから外す」必要がある。これは選択ではなく算術上の要件である。

**副軸1（SEO）**: 影響なし。h1・説明文・パンくず（BreadcrumbList JSON-LD 含む）は初期 HTML に残る。さらに重要なのは、**クローラは playing フェーズに到達できない**（「はじめる」のクリックが必要）ため、クローラが見るのは常に intro 状態＝現状と同一の DOM/CSS である。`<meta name="description">` と JSON-LD は `playContentBySlug`（registry）由来で本文描画とは独立（`src/app/play/[slug]/page.tsx:25-30` → `src/play/seo.ts`）。隠しテキストによるクローキング懸念も生じない（隠すのは操作後の状態で、内容の差し替えではない）。

**副軸2（a11y）**:

- 案1-A2（h1 を視覚的非表示で a11y ツリーに残す）なら、見出し構造（h1 → 設問 h2 → FAQ h2…）は回答中も維持される。
- 案1-A1（`display:none`）だと回答中は h1 が a11y ツリーから消え、h2 だけのページになる。WCAG の達成基準違反ではない（h1 必須の SC はない）が、見出しジャンプで文脈に戻れなくなる。**A2 を推す**。
- パンくず（nav ランドマーク）は回答中に消えるが、サイト共通 `Header` の nav は `<article>` の外にあり残るため、ナビゲーション手段は失われない。
- 「要素が消える」混乱について: 変化は「はじめる」押下という**ユーザー起点の1回だけ**で、同時に intro ブロック全体が設問に置き換わる（既に大きな遷移が起きている）。加えて `QuestionCard` はマウント時に設問見出しへフォーカスを移す（`QuestionCard.tsx:42-45`、`preventScroll: true`）ので、SR 利用者は新しい文脈を読み上げられる。設問ごとの遷移では上部要素は動かない（playing 中は状態不変）。
- 回答中に消えた h1・説明文は、結果フェーズで戻る。ここも1回・ユーザー起点。

**副軸3（他コンテンツへの波及）**: 15本＋専用ルートすべてに同じ機構が効く。数値は上表のとおり全本で改善。知識クイズ固有の注意として、**回答後に増える領域（解説＋「次へ」）は本案でも fold 下に残る**。推計（kotowaza-level Q8・解説79字）: 選択肢 bottom 447 →解説 bottom 589 →「次へ」bottom 649。今日の 836 から約190px 改善するが 550 未達。**これは本案の未達点として正直に記録し、別タスクとして起票する**（選択肢の可視性＝本サイクルの芯は達成される）。

**副軸4（intro / result への影響）**: intro は不変（説明文はそのまま可視。開始前の判断材料を消さない）。result は不変（header が戻った状態で `resultRegionRef` への `scrollIntoView` + `focus` が走る）。ただし「最終回答 → phase=result → header 復帰（+約200〜300px）→ scrollIntoView」の順で、スクロール目標が復帰後のレイアウトで計算される必要がある。React は commit 後に useEffect を実行し、`scrollIntoView` は同期レイアウトを強制するため、属性変化による `:has()` の再評価済みレイアウトに対して計算される見込み（**推論。§6 で実測する**）。

**副作用と失敗の仕方（外すとどうなるか）**

1. **余裕 11px は薄い。最悪2本で崩れうる。** 最大の不確実要素は**選択肢の行送りが CSS で指定されていないこと**（`.choiceButton` に `line-height` がない）。実測 68px の内訳は `padding 12+12 + border 2 + 2行×21px` で、21px は Playwright（Linux フォールバックフォント）の `normal` 行ボックス。実機 iOS の Hiragino では `normal` が 1.45〜1.5 相当になり、2行の選択肢が1つあたり +3〜6px、4つで **+12〜24px** になりうる（推論・未実測）。そうなると 539 → 551〜563 で**未達に転落する**。→ 対策は §4 の R1（行送りを CSS で固定）と R2/R3（8px スケール是正）。
2. `:has()` 非対応環境（Safari 15.3 以下・Chrome 104 以下・Firefox 120 以下）では**何も起きず現状のまま**になる（機能低下ではなく無変化）。壊れ方は静かで、気づけない。→ 検証項目に「非対応時に現状と同じか」を入れる。CSS のみで完結する代わりに、効いたかどうかを DOM から読めないので実測は視覚・座標で行う。
3. スクロール済みで「はじめる」を押した場合、上部 200〜300px が消えて表示内容が跳ねる。押下前は通常 scrollY=0（はじめるボタンは推計 bottom 331〜500 で可視）だが、0 でない経路はある。→ R4（開始時に scrollY>0 なら 0 へ戻す）で潰す。
4. `handleRetry` で intro に戻ると header が復帰してページが伸縮する。既存挙動と同型だが、オフセットが変わるので「retry 後に来訪者がどこを見ているか」は検証対象。
5. CLS: ユーザー入力から500ms 以内のレイアウトシフトは CLS に計上されない（推論。§6 で Lighthouse/実測で確認）。intro の初期表示は変えないので LCP/CLS の初期値には影響しない。

### 案2: 回答フェーズに入った時点でスクロール位置を設問へ移す

**何をするか**: `handleStart`（および必要なら playing 突入時の useEffect）で、進捗ブロックの先頭へ `scrollIntoView({ block: "start" })`。既存の result リビール（`QuizContainer.tsx:59-80`）と同じ機構・同じ `prefers-reduced-motion` 分岐を流用する。DOM もフローも変えない。

**375×550 の数値**: サイト header はスクロールで退く（`position: static`。`Header.module.css:8-15`）ので、進捗先頭までスクロールすると可視域は「進捗 → 選択肢」で埋まる。相対 bottom = 進捗 47.8 + 設問+選択肢（270〜418）= **318〜466 ≤ 550**（全15本・余裕 84px 以上）。

**ただし第一の軸（scrollY=0 で4択が可視）は文字通りには満たさない。** 満たすのは「来訪者の操作なしに4択が見える」という達成基準の趣旨のみで、`scrollY=0` の条件は満たさない（scrollY は 301〜371 になる）。この差は言葉遊びではない: **scrollY>0 の状態は、ブラウザのスクロール復元・スクロールアンカリング・iOS のツールバー伸縮・戻る操作で崩れる**ため、幾何学的に保証された状態ではない。

**副軸1（SEO）**: 影響なし（DOM 不変）。
**副軸2（a11y）**: h1・説明文・見出し構造は保持されるので**この点は全案中最良**。一方で「意図しないスクロール移動」は WCAG 的には問題ないが、`prefers-reduced-motion` の尊重が必須。`QuestionCard` のフォーカス移動が `preventScroll: true` なのに親がスクロールする、という**同一フレーム内での2つのスクロール制御の競合**が生じる（既存 result 側の N1 コメントが同じ罠を記録している）。
**副軸3（波及）**: 全15本に効く。知識クイズでは「回答 → 解説＋次へ が下に伸びる」ため、設問先頭に固定したままだと「次へ」が fold 下に残る（案1と同じ未達）。設問ごとに再スクロールすると、解説を読んでいる来訪者を引き戻す。
**副軸4（intro/result）**: intro 不変。result は既存の `scrollIntoView` があり、**同じ機構を2箇所で使うことになるので相互作用が読みにくくなる**（playing→result の遷移で「設問へのスクロール」と「結果へのスクロール」が連続発火する順序依存）。
**副軸5（実装の素直さ）**: `QuizContainer` 内で完結し、サーバー/クライアント境界に触らない。バンドル増もほぼゼロ。実装量は最小。

**副作用と失敗の仕方**

1. **来訪者の位置感覚を奪う**: 押した直後に画面が300px 動く。上へ戻ると回答中に機能しない紹介文が出てくる（問題の本体は残る）。
2. **設問ごとに再スクロールする実装にすると、来訪者のスクロールと戦う**。特に知識クイズは解説を下へ読む導線なので、次設問で強制的に上へ戻される。
3. **崩れ方が環境依存で、静かに戻る**: スクロール復元（ブラウザバック）、`overflow-anchor`（本リポジトリでは未指定）、iOS のアドレスバー伸縮で位置がずれる。ずれても「見えない選択肢」に戻るだけで、エラーは出ない。
4. スクロール後の状態はスクリーンショット検証で「合格」に見えるが、実機で来訪者が一度上へフリックすれば元の問題が再現する。**測り方によって成功に見えてしまう案**であり、AP-P02（自案に有利な測度を選ぶ）に最も引っかかりやすい。

### 案3: 説明文を `meta.shortDescription` に差し替える（器の取り違えの是正）

**375×550 の数値（推計）**: 説明文が 6〜7行から 1〜2行になる（17〜40字）。

| ------------------------------ | ------------- |
| science-thinking               | 683           |
| character-fortune / word-sense | 669           |
| animal                         | 658           |
| character-personality          | 637           |

**副軸1（SEO）**: head の description・JSON-LD は不変。ただし**本文（初期 HTML）から120〜160字の日本語が消える**。この経路の初期 HTML の可読テキストは「h1＋説明文＋FAQ＋関連リンク」だけで（設問は playing フェーズのみ描画）、削ると本文量が実際に減る。→ 緩和策として長い description を本体より下に「この診断について」として残す（案5と併用）。
**副軸2（a11y）**: 影響なし（要素は常に存在し、動かない）。全案中で最も静か。
**副軸3（波及）**: 15本すべてで説明文が短くなる。**shortDescription の質が15本ぶん問われる**（例: japanese-culture・kanji-level は 18〜24字で、開始前の判断材料としては薄い可能性がある。内容レビューが必要）。
**副軸4（intro/result）**: intro の初見体験は「短い説明＋開始ボタンが一目で入る」に改善する（はじめるボタンの推計 bottom: character-personality 430→331、science-thinking 500→376）。ただし**「これは何か」の情報量は落ちる**。開始前に消してはいけないという要件は満たすが、薄くはなる。

1. **単独では問題が解けない**（8本未達）。「短くしたから直った」と誤認して終わるのが最悪の失敗で、これは cycle-300 が犯した「375×812 で測って収まったと結論した」誤りと同型である。
2. shortDescription が薄い診断で、初見の来訪者が「何が出てくるか」を判断できず、開始前離脱が増えうる（未検証。B-614 の対象は完走率だが、開始率を落とせば差し引きで損をする）。
3. 本文テキスト減による検索面の影響は小さいが**測れない**（前後比較では帰属できない・AP-P31）。ゆえに「SEO に効く/効かない」を主張せず、head 不変という構造的事実だけを根拠にする。

### 案4: 回答フェーズを全画面レイヤーとして独立させる

**何をするか**: playing の間だけ、設問＋選択肢を `position: fixed; inset: 0` の層に描画する（ページのスクロール文脈から切り離す）。上部に何があっても影響を受けない。

**375×550 の数値（推計）**: 上端 padding 16 + 進捗 47.8 + 設問+選択肢（270〜418）= **334〜482**。全15本で 68px 以上の余裕。**数値上は最良**で、しかも将来ページ上部に何を足しても壊れない（構造的に上流から独立）。

**副軸1（SEO）**: 影響なし（クローラは intro 状態しか見ない）。
**副軸2（a11y）**: 最も重い。全画面層は事実上のモーダルで、フォーカストラップ・`aria-modal`/`role="dialog"` の是非・Esc の扱い・背後コンテンツの `aria-hidden`・スクロールロックの実装が必要。スクロールロックは `layout.tsx` の `<body style={{...}}>` と競合する既知の罠がある（AP-I07: `document.body.style.overflow` は JSX 由来の style で上書きされる。`classList` で切り替えること）。診断は「モーダルで中断できないタスク」ではないので、**モーダルの語彙を来訪者の認知モデルに持ち込むのが妥当か疑わしい**（AP-P07）。
**副軸3（波及）**: 15本すべてが全画面回答になる。知識クイズは回答後に解説＋次へで伸びるため、層の中でスクロールが必要になり**入れ子スクロールの罠**（外側と内側のどちらが動くか、iOS の慣性）を全面に持ち込む。
**副軸4（intro/result）**: intro 不変。result は層を解体してから `scrollIntoView` する必要があり、遷移が2段になる。
**副軸5（実装の素直さ）**: 最も遠い。fixed 層・スクロールロック・フォーカス管理・`100dvh` の iOS 挙動（ツールバー伸縮）まで抱える。バンドルは増えないが、複雑度が上がる。

**副作用と失敗の仕方**

1. **「ページを読んでいた人を閉じ込める」**。FAQ・関連診断・広告区画（§9 の将来）から回答者を切り離すので、回遊が止まる。
2. iOS の `100dvh`／ツールバー伸縮で層の下端が切れると、**選択肢が見えない元の問題が別の形で再発する**（しかもスクロールで救えない）。
3. 実装の重さで検証が浅くなり、a11y の穴（フォーカスが背後に抜ける等）が残る。
4. DESIGN.md §1「器は静か」「店の言語で組む」から離れ、サイトの他の面と別の作法を1箇所だけ持ち込む（一貫性の損失）。

### 案5: DOM 並び替え（説明文を本体より下へ恒久移動）

**何をするか**: フェーズに依存させず、説明文（長文のまま）を `QuizContainer` より**下**に置く。h1・パンくずは上に残す。フェーズ状態を一切参照しないのが売り。

**375×550 の数値（推計）**: 上部は「パンくず＋h1」だけになる。bottom = 57+16+bc+16+h1+16+47.8+（設問+選択肢）= **science-thinking 572 / character-fortune 580 / word-sense 580 / animal 572 / japanese-culture 572 / character-personality 544 / 以下 496〜580**。→ **15本中6本が未達**。単独では第一の軸を満たさない。

**副軸1（SEO）**: 本文は初期 HTML に残る（位置だけ変わる）。h1 は先頭のまま。**案3の本文減の弱点を補える**。
**副軸2（a11y）**: 静的で動かない。見出し構造も保たれる。良好。ただし「説明が本体の下」という順序は、SR で上から読む人にとって「何の診断か」の説明に本体を越えて到達する形になる（h1 と FAQ があるので致命的ではない）。
**副軸3（波及）**: 15本共通。副作用は小さい。
**副軸4（intro/result）**: intro の第一ビューは「パンくず・h1・値札・はじめる」になり、開始判断の材料が説明文からは得にくくなる（スクロールすれば読める）。result フェーズでは結果カードの下に紹介文が挟まり、回遊導線（ResultNextContent）との順序を再考する必要がある。
**副軸5（実装の素直さ）**: JSX の並べ替えのみ。境界に触らない。素直。

**副作用と失敗の仕方**

1. 単独で未達（6本）。「並べ替えたから軽くなった」で止めると測度未達のまま出荷する。
2. result フェーズの縦並びが変わり、結果 → 紹介文 → おすすめ、という読み順の劣化が起きうる（成果物の後に開始前の説明が来る違和感）。
3. intro の情報設計を静かに劣化させる（開始前に「何が出てくるか」が第一ビューから外れる）。案3 と組むと二重に薄くなる。

### 案6: 寸法・情報量のダイエット単独（選択肢・設問側を詰める）

**何をするか**: 上部には触らず、選択肢の padding・行間・gap、設問見出しの下余白、進捗の下余白を詰める。

**375×550 の数値（推計）**: 現実的に削れるのは「進捗の下余白 24→16（-8）」「設問見出しの下余白 20→16（-4）」「選択肢 gap 10→8（-6）」「選択肢の上下 padding 12→8（-16）」＝ **-34px**。→ bottom は **512〜771** で、**15本中13本が未達**。設問見出しのフォント縮小で稼ぐ手は DESIGN.md §3 の見出しスケール（16/20/25/31/39px）と衝突し、16px にすると本文と同サイズで見出しとして立たない。選択肢の文字を 14px にするのは §3「文章として読ませる文は 16px」と衝突し、可読性を削って辻褄を合わせる行為になる。

**副軸1（SEO）**: 影響なし。**副軸2（a11y）**: タップ標的は `min-height: 44px` で維持できるが、padding を削るほど誤タップ余地は減る（§10 の下限は満たす）。**副軸3（波及）**: 15本＋結果面の一部にも波及しうる。**副軸4**: intro/result に影響なし。**副軸5**: CSS のみで最も素直。

**副作用と失敗の仕方**

1. **単独では解けない**（13本未達）。原因（上部 212.5〜298px）と対処（-34px）の桁が合っていない。
2. 可読性・操作の余裕を削る方向なので、やり過ぎると「見えるようになったが押しにくい・読みにくい」に化ける。来訪者側の損失で数値を買う形。
3. ただし**案1 の薄い余裕（11px）を厚くする補助としては有効**で、しかも DESIGN.md §4 の 8px スケール逸脱（`.choices` gap 10px・選択肢 padding 12px）の是正でもある。単独案としては不採用、併用要素としては採用。

## 4. 推奨案とその理由

### 推奨: **案1（回答中の退避・h1 は a11y ツリーに残す A2 形）＋ 案6 の一部を「余裕確保」として同時投入**。加えて**案3＋案5 を第2段**として同一サイクルで入れる（別コミット・別検証）。

**第1段（必須・第一の軸を満たす部分）**

- S1: `QuizContainer` のルートに `data-quiz-phase` を出し、`page.module.css` の `:has()` でパンくず領域と `.header` を playing 時にフローから外す。h1 は視覚的非表示で a11y ツリーに残す。
- R1: `.choiceButton` に `line-height: 1.5` を明示する。**これは「効く施策」ではなく「未実測の依存を消す施策」である**。現在の 68px は実機フォントメトリクスの `normal` に依存し、iOS では +3〜6px/選択肢の可能性がある（推論）。CSS 側で固定すれば、この未検証要因が消える。
- R2: DESIGN.md §4 の 8px スケールへ是正: `.choices` gap 10→8、`ProgressBar .wrapper` margin-bottom 24→16、`.questionText` margin-bottom 20→16（計 -18px）。
- R3: `.choiceButton` の上下 padding 12→8（`min-height: 44px` は維持＝§10 準拠）。R1 と合わせると2行選択肢の外形は 68→66px でほぼ同じだが、内訳が「余白多め・行間狭め」から「余白少なめ・行間広め」に移り、**行送りがデバイス非依存になる**。
- R4: `handleStart` 時に `window.scrollY > 0` なら 0 へ即時復帰（「scrollY=0 で見える」という前提を仮定でなく事実にする）。

**第1段の数値（推計・最悪ケース = character-fortune Q5 / word-sense-personality Q4: 設問41字3行・2行選択肢4つ）**

```
73（サイト header 57 + layout padding 16）
+ 39.8（進捗 23.8 + 下余白 16）
+ 96（設問見出し 3行 × 32）
+ 16（設問見出しの下余白）
+ 288（選択肢 66 × 4 + gap 8 × 3）
= 512.8 ≦ 550（余裕 37.2px）
```

他の代表値: science-thinking 480.8 / character-personality 480.8 / kotowaza-level 446.8 / kanji-level 約 400。**15本すべてで 550 以下、最悪でも 37px の余裕**。

参考（なぜ R1〜R3 が必要か）: S1 のみ = 539（余裕 11px・実機フォント差で 551〜563 に転落しうる）。S1+R1 のみ = 544.8（余裕 5px）。S1+R1+R2+R3 = 512.8。**11px を「収まっている」と呼ばない**ためにここまでやる。

**第2段（intro の是正・第一の軸には影響しない）**

- S2: `QuizPlayPageLayout` の header で `quiz.meta.shortDescription` を使う（`ToolPageLayout` の契約に戻す＝写し崩れの是正）。
- S3: 長い `description` は捨てず、`QuizContainer` の下に「この診断について」として置く（本文テキストを初期 HTML に保持＝案3 の SEO 上の弱点を案5 で埋める）。回答中は S1 の対象外（本体より下にあるので上部占有に無関係）。
- 第2段は第1段の数値を悪化させない（playing 中は上部が退避済みで、説明文の長短は無関係）。intro の「はじめる」到達は推計で character-personality 430→331、science-thinking 500→376 に改善する（未校正の概算・§6 で実測）。

### なぜ他案でないか

- **案2（スクロール）でない**: 第一の軸を文字通り満たさない。より本質的には、`scrollY>0` の状態はスクロール復元・アンカリング・iOS のツールバー伸縮で崩れる**保証のない状態**であり、崩れたときに元の欠陥（4択が見えない）へ静かに戻る。上へ一度フリックすれば回答中に機能しない紹介文が現れるという点で、**問題を移動させただけ**でもある。さらに、検証をスクロール後の座標で行うと合格に見えるため、自分に都合の良い測度を選ぶ危険が最も高い（AP-P02）。ただし R4（開始時に 0 へ戻す）という形で、案2 の機構のうち安全な部分だけを取り込んでいる。
- **案3（短説明）でない（単独では）**: 8本が未達で、原因（上部 212.5〜298px）に対して削減が最大 122px と桁が足りない。ただし「表示に使うフィールドを間違えている」という是正としては正しく、第2段として採用する。
- **案4（全画面）でない**: 数値の余裕は最大だが、その余裕は**a11y とスクロール制御の複雑さで買っている**。案1 が同じ達成基準を余裕 37px で満たせる以上、モーダル相当の作法・入れ子スクロール・`100dvh` の iOS 挙動・フォーカストラップを持ち込む理由がない（AP-P28 の逆＝「安く済ませるために品質を落とす」ではない。品質同等でリスクが低い方を選ぶ判断である）。加えて回答中に FAQ・関連診断・将来の広告区画から来訪者を切り離す。
- **案5（並び替え）でない（単独では）**: 6本未達。result フェーズで「結果 → 開始前の紹介文」という読み順の劣化を生む。第2段の S3 として、位置を本体下に限定して採用する。
- **案6（ダイエット）でない（単独では）**: 13本未達。可読性を削って辻褄を合わせる方向は来訪者の損失（index.md の判断と一致）。ただし §4 の 8px スケール逸脱の是正としては正しく、R2/R3 として採用する。

### 案1 の実装形の選択（副軸5・境界の扱い）

3通りある。**(i) を推奨**。

| 形                                                | 仕組み                                                                                      | バンドル                                                           | 境界                                                              | 弱点                                                                                                |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **(i) CSS `:has()` ＋ `data-quiz-phase`（推奨）** | `QuizContainer` が属性を出し、`page.module.css` が親側で退避                                | 属性1つ。registry import を増やさない（既存コメントの意図を保つ）  | サーバー/クライアント境界を**動かさない**。状態のリフトアップ不要 | `:has()` 非対応で無変化。CSS が「離れた場所の状態」に依存するので読み手に説明が必要（コメント必須） |

## 5. 推奨案の実装手順の骨子（コードは書かない）

**Step 0（先に文書を直す・AP-I08）**: DESIGN.md に「フェーズ状態を持つ器の視覚状態」と「操作要素の可視性の下限」の規定がない。実装前に付録A の2条を DESIGN.md に追記し、reviewer の確認を得る。未定義の視覚表現（フェーズによる要素の退避）を実装都合で先に入れない。

**Step 1（外部依存の確認）**: BigQuery/GA4 raw で直近90日の `device.web_info.browser` / `browser_version` 分布を集計し、`:has()` 非対応（Safari ≤15.3 / Chrome ≤104 / Firefox ≤120）の比率を出す。無視できる（例: 1% 未満）なら (i)、そうでなければ (ii) に切り替える。**この判断を design.md に追記して残す。**

**Step 2（退避機構の実装 = S1）**

- `QuizContainer` の3つの return（intro の `.stage` / playing の `.stage` / result の `.resultPhase`）のルート要素に `data-quiz-phase={phase}` を付ける。属性の意味と「親の CSS が参照している」ことをコメントに書く（離れた依存なので必須）。
- `QuizPlayPageLayout` で `<Breadcrumb>` を `styles.contextZone` の `<div>` で包む（共有 `Breadcrumb` コンポーネント（21箇所から利用）には手を入れない）。
- `page.module.css` に playing 時の規則を追加: `.contextZone` を非表示、`.header` をフローから外し、h1 は視覚的非表示（`globals.css:248` の `.visually-hidden` と同等の指定。CSS Modules 内に持つか global を使うかは builder 判断）、説明文は非表示。**h1 をフローに残すと未達になる**（§2 案1 の数値）ので、絶対配置などで**フロー高さ 0 かつ gap を生まない**形にする必要がある。gap を生まないことは推論なので Step 6 で実測する。

**Step 3（余裕の確保 = R1〜R3）**: `QuestionCard.module.css` の `.choiceButton` に `line-height: 1.5` を明示、上下 padding を 8px に、`.choices` の gap を 8px に、`.questionText` の margin-bottom を 16px に。`ProgressBar.module.css` の `.wrapper` margin-bottom を 16px に。`min-height: 44px` は維持（§10）。DESIGN.md §4 の 8px スケールに合わせる是正であることをコメントに書く。

**Step 4（開始時のスクロール前提の固定 = R4）**: `handleStart` で `window.scrollY > 0` のときのみ即時に 0 へ戻す（`prefers-reduced-motion` を跨がない即時指定）。`window` 未定義環境（jsdom/テスト）でのガードは既存 `useEffect` の流儀（`QuizContainer.tsx:59-80`）に合わせる。
