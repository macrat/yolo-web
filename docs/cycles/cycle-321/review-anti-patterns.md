### (b) 複合動詞の途中の折れを出荷のあとに回した判断: 妥当（優先度は見直してよい）

fix-choice-wrap.md によれば、本番は選択肢の文を語の途中のどこででも折る（「思 / い返し」「納得で / きる」）。直した版で語の中で折れるのは 375px・320px で4か所ずつで、行頭の句読点と1字だけの行は 0 になった。1か所ずつ見れば本番より悪い所があるが、選択肢の読みやすさ全体では本番より良い。直すには見出しにも効く `splitIntoPhrases` を変え、全ページの見出しの折れ方を確かめ直すことになり、出荷の直前に入れれば、見出しの折れ方で本番より悪い所を新しく作る危険のほうが大きい。B-803 は全体を直す範囲で書かれていて、範囲は縮んでいない。

### (c) レビューを途中で止めた2か所: 決まりから外れている（製品への害は無い）

### (d) GA の数の確かめを、ブラウザの送信の記録に替えた判断

rollout-plan.md は「GA に `page_view`・`level_start`・`level_end`・`share`・`save` の数が届いていることを確かめる。確かめ終えるまで main にほかの push をしない」と決めていた。5d794ef は、もとの出荷の順序にあった「数は翌日に BigQuery で確かめる」を消し、「当日はブラウザの送信の記録で確かめる」だけにした。この書き直しはレビューを通っていない。BigQuery のエクスポートが翌日なので当日に数を見られないのは事実で、送信が出ていることは確かめられている。2つ目の pull request は記録と `deploy.yml` だけなので、出しても刷新の前へ戻る道を狭めるだけで、来訪者への害は小さい。ただし、ADR009 の観測は GA の数が届いていることを前提にしているので、B-801 に「出荷の日（2026-11-17）からのイベントが、release `852f2c4-20261117` つきで BigQuery に届いていることを確かめる」を明記すること。いまの B-801 の文と prod-verification.md の「B-801 で、基線を取るときに見る」だけでは、手順として拾われない。
