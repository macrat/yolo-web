## 作業計画

### 目的

本番のサイトは、刷新が止まっているあいだ古いデザインのままで、来訪者は更新の止まったサイトを見続けている。作り直した画面（読みやすい組版・ブラウザの文字サイズの設定が効くこと・フォーカス時に拡大しない入力欄・狭い画面で4択が見える診断の回答画面など）は、作業ブランチの中にあるだけで誰にも届いていない。このサイクルは、それを来訪者に届ける。

`docs/site-concept.md` の来訪者への約束は「面白いものがここにあります」と渡すものを決め、面白いかを来訪者の行動で確かめると定める。行動で確かめるには、まず本番に出ていなければならない。出荷は、ADR009 の観測（出荷の直前28日を基線にする）が始まる条件でもある。

**達成の条件**: 新しいデザインが本番（yolos.net）で配信され、本番で表示と主な操作と計測が確かめられていること。出荷の前の確かめは、「来訪者が、いまの本番より悪い画面を受け取らない」ことだけを線にする。

### 作業内容

タスクの中身と線は [cycle-320/rollout-plan.md](../cycle-320/rollout-plan.md) にあり、ここには進め方だけを書く。

- **順序**: T1 を最初に行う（ビルドが通らなければ、ほかの確かめができない）。T2a〜T2e と T3 は互いに独立なので、1タスクを1つのサブエージェントに頼む。同じファイルを直すことになったタスクは、並べずに順に行う。T4 は T1〜T3 の直しが出そろってから行う。
- **比べる相手**: T2a・T2c・T2d は、本番（https://yolos.net 。2026-11-11 にこの環境から 200 で届くことを確かめた）と、作業ブランチを `npm run build` して `npm run start` で起こしたものを比べる。T2b と T3 は、通信の遅れが結果に混ざらないよう、origin/main もこの環境でビルドして比べる。T2d の転送の元の URL は、origin/main の `next.config` の `redirects()` から取る。
- **見る画面の選び方**: 変わったファイルは、別々の部品を持つ画面に散らばっている。目で見るのは、部品が画面ごとに違うもの（ゲーム4本・知識クイズ・占い・辞典4種）を1つずつとし、同じ部品を使い回す画面（ツール・診断ごとの結果のページ）は、T2d の全 URL の巡回で JavaScript のエラーと横へのはみ出しを拾う。
- **直す範囲**: 確かめで見つけたもののうち、直すのは「本番より悪い」「表示が壊れている」「主な操作ができない」「記事の説明が画面と食い違う」ものだけである。本番にもある不具合と、新しいデザインの細かい規則が当たっていないだけの所は、backlog に書いて直さない。刷新が意図して変えたもの（解き終えた画面の保存と共有のボタンの位置など。ADR009 が見張る）は戻さない。
- **レビュー**: 確かめのタスクは、結果の一覧と撮った画面を reviewer に通す。直しを伴ったタスクは、その差分も通す。指摘への対応のなかで、来訪者が受け取るものを変えない修正だけが3回続いたら、そこで止めて次へ進む（cycle-kickoff の手順8）。
- **出荷の順序**: このセッションの作業ブランチは `ccr-a14a408a-0hld66`（開始時点で `design-rollout` と同じコミット a8070aa。origin/main は取り込み済みで、main へは早送りで入る）で、ほかのブランチへの push は許されていない。そこで次の順に行う。
  1. T1〜T4 を終えたら、結果を添えて、オーナーに次の3つの許可をまとめて求める: 出荷のための main への push、本番での確かめの記録を入れる2度目の main への push、`design-rollout` を origin から消すこと。
  2. 出荷の前に、いまの本番のデプロイの ID を Vercel で控える。戻す操作（Instant Rollback と promote）をこのセッションの Vercel の接続でできるかを確かめ、できなければ、戻すときはオーナーに頼むことを 1 の報告に書く。
  3. main へ push する前に、同じコミットで CI が通ることを確かめる。この環境の Node は v22 で CI は 24 なので、手元の検査だけでは足りない。作業ブランチから main への pull request を作ると `deploy.yml` の CI が走るので、それで確かめる（pull request を作ることも 1 で許可を求める）。
  4. main へ push し、Vercel のデプロイが済んだら、本番で rollout-plan.md の項目（表示・theme-color・Web フォント・`og:image`・GA のイベント）を確かめる。無くなったページ番号の転送が Vercel の上でも 308 を返すこと（`/blog/page/3` と `/blog/tag/設計パターン/page/2` に `curl -I`）も確かめる。GA のイベントは BigQuery のエクスポートに翌日まで出ないことがあるので、当日は GA4 のリアルタイムかブラウザの送信の記録で確かめ、数は翌日に BigQuery で確かめる。
  5. 確かめ終えるまで、main にほかの push をしない。出荷のあとに CI が落ちても、直しを push しない。Hobby プランで戻れるのはすぐ前の本番のデプロイだけで、直しを push すると出荷の前の本番へ戻れなくなるからである。本番が壊れている・主な操作ができない・診断のプレイ面が出荷の前より悪いと分かったら、まず出荷の前のデプロイに戻し、そのあとで直す。戻したあとは Vercel が本番ドメインの自動の割り当てを止めるので、直したものを出すときは promote する。
  6. 本番での確かめを終えてから、記録と完了の処理を main へ push し、`design-rollout` を消す。
- **記録**: 確かめの結果は `docs/cycles/cycle-321/` に、タスクごとの別ファイルで置き、ここには結果の1行とリンクだけを残す。撮った画面は `./tmp/` に置く。

### 検討した他の選択肢と判断理由

- **確かめを省いてすぐに出荷する**: 最も早い。けれど 1,892 ファイルが変わっていて、閲覧の約8割を占める診断のプレイ面が本番より悪くなっていれば、出荷がそのまま来訪者の害になる。Hobby プランでは戻れる先がすぐ前のデプロイだけなので、出してから直すやり方は戻す道を狭くする。採らない。
- **cycle-316 の計画の残り（T5・T5a・T6〜T12）を終えてから出荷する**: cycle-316〜320 がこれを試み、出荷に必須でない作業に日数を使って何も届けなかった（cycle-320 の incident-2.md）。残りは、古いトークンの定義が残っているので表示を壊さず、出荷のあとに続けられる。採らない。
- **選んだ案（本番より悪くないことだけを確かめて出荷する）**: 確かめの線を「本番との比較」に置くので、作業の終わりがはっきりし、来訪者にとっての害だけを拾える。cycle-320 でレビューを4回通した rollout-plan.md を、そのまま使う。
- **T2 を1つのタスクにまとめる**: 頼む文は短くなるが、1人が診断の通しの比較・二度押し・全テンプレート・sitemap・記事の直しを抱えると、文脈が溢れて途中で止まり、レビューも1回で全体を見られない。5つに分ける（CLAUDE.md の「Keep task smaller」）。

- **出荷の前の本番のデプロイ**（2026-11-11 に Vercel で確かめた）: `dpl_FRCp5jYJy1q71LUwGvQ99Kb5hTbf`（main の 385f99f）。出荷のあとに戻すときの戻り先である。このセッションの Vercel の接続には、戻す操作（rollback）の道具がある。
- **「はじめる」のあとに画面を送らない案は効かなかった**: rollout-plan.md は、二度押しの害を「切り替わりのあとにスクロールしない」ことで直すとしていた。そのとおりに直して測ると、新しい版でだけ害が起きる組は 38 から 40 に増えた。原因は送りではなく、新しい版では「はじめる」の真下に1問目の選択肢が組まれることだった（[fix-start-double-tap.md](./fix-start-double-tap.md)）。そこで、「はじめる」を押してから 500 ミリ秒のあいだだけ、1問目の選択肢への押しを受け付けない形に替えた。開始の直後に1問目を読んで答える人はいないので、ふつうに答える人には影響しない。過去に取り消した「押しを捨てる」直し（cycle-301）は、問から問への切り替わりに掛けて、速く答える人の答えを捨てたもので、開始の直後だけに限るこの形とは違う。

- **確かめに使うビルドを push の前の検査が壊した（2026-11-11 04:01 UTC）**: 確かめの担当3つ（T2a・T2c・T2d）が、リポジトリの直下の `.next` を使うサーバー（ポート 3100）を見ているあいだに、PM が push をしようとした。push の前の検査（`pre-push-check.sh`）は `npm run build` を走らせるので、`.next` が作り直しの途中で壊れた。担当3つを止め、作業ブランチを `tmp/cycle-321/branch/` に取り出して別にビルドし、そこからサーバーを起こし直した（ポート 3101）。04:01 より後にポート 3100 で取った結果は使わない。確かめのあいだは、リポジトリの直下の `.next` を使うサーバーを確かめの相手にしない。
- **記事の直し方を、ブログの規則に合わせた**: rollout-plan.md は、ゲームの判定を色で説明している記事2本を「いまの示し方に直す」としていたが、`.claude/rules/blog-writing.md` は、前提が古くなった記事の本文を書き換えず、日付つきの注記を足すよう定めている。既存の規則が優先なので、本文は元のまま保ち、注記を足す形にした（担当の blog-writer の指摘で気づいた）。
