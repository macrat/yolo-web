承認。直さないと来訪者が損をする、または不具合になる指摘はない。

## 確かめたこと

### 1. 来訪者の目で

- 本番（https://yolos.net）の一覧 41 個（ブログ全体、分類 5、本番の記事が貼っているタグ 33、ツール、遊び、辞典 4）を、`page/2` から順に 404 になるまで当てた（あいだを 0.4 秒あけ、全体で 61 回）。本番で 200 か 308 を返したページ番号つきの URL は 20 本だった。内訳は `/blog/page/2`〜`8`、`dev-notes` の 2・3、`ai-workflow` の 2、`tool-guides` の 2、タグ `Web開発` と `設計パターン` の 2・3、タグ `失敗と学び`・`Next.js`・`SEO`・`UI改善` の 2、`/tools/page/2`（本番でも `/tools` への 308）。このうち `/blog/page/2` はいまもあるページで、残りの 19 本は担当の報告の 19 本と一致する。ほかの一覧は、本番でも `page/2` が 404 だった。
- 直した版（3103）では、20 本すべてが「200」か「308 を1回経て 200」になった。
- 着いた先の中身をブラウザで突き合わせた。本番の `/blog/page/3`〜`8` に載っていた記事（12・12・12・12・12・2 件）のうち、着いた先に載っている数は 12・12・10・12・12・2。`/blog/page/5` の残りの 2 件は `/blog` にある（担当の表のとおり、多くが載っているほうへ送っている）。分類・タグの 12 本とツールの 1 本は、本番のそのページの記事・ツールが、着いた先にすべて載っていた（たとえば `/blog/category/dev-notes/page/3` は 11/11、`/blog/tag/設計パターン/page/3` は 4/4、`/tools/page/2` は 36/36）。
- 着いた先の title・canonical・robots は、どれも着いた先のページのもの（例: `/blog/page/5` は `ブログ（2ページ目） | yolos.net`・`https://yolos.net/blog/page/2`、`/blog/tag/Web開発/page/3` は `Web開発 - ブログ | yolos.net`・`https://yolos.net/blog/tag/Web開発`。robots はどれも `index, follow, max-image-preview:large` の1つ）。`/blog/page/5` から着いた画面を撮り、「全86件のうち51〜86件目」と一覧がふつうに出ることを見た。

### 2. 境界

3103 に `curl` を当てた結果（転送はすべて辿った）。

- 最後のページ `/blog/page/2` は 200。その次からの `3`〜`8` は 308、`9`・`10`・`99999999999999999999` は 404。
- `0`・`-1`・`-3`・`03`・`005`・`3.0`・`1e1`・`abc` は 404。`/blog/page/%33` は `/blog/page/3` と同じに扱われて 308 → `/blog` ⇒ 200（本番は 200）。
- 存在しない分類・タグ（`no-such`、`DEV-NOTES`、`seo`）と、本番でも2ページ目の無い分類・タグ（`site-updates`、`japanese-culture`、`新機能`、`Claude Code`）の `page/2` は 404。和文のタグは百分率符号化した形でも同じに動く。
- `/blog/page/1`・`/tools/page/1` は元のパスへ 308 ⇒ 200。`/blog/page/3/` は2回の 308 で `/blog` に着く。
- 古い分類名からの転送: `technical`・`ai-ops`・`guide`・`behind-the-scenes` の `page/2`（`technical` は `page/3` も）は2回の 308 で 200 に着く。`release/page/2` は `site-updates/page/2` の 404 に着くが、手元の本番と同じ版（3200）も同じ。
- 送り先はいつも、いまある最後のページ以下の番号なので、送り元に戻ることはなく、輪にならない（コードでも確かめた）。
- sitemap の 573 本は、直す前（3101）と直した版（3103）とで集まりが同じで、すべて 200。
- 一覧のページから、送る番号の URL へのリンクは出ていない（`/blog`・`/blog/page/2`・分類・タグ・`/tools` の HTML を見た）。

### 3. コード

- `listPageStaticParams` は、いまの区切りと古い区切りのページの数の大きいほうまで出すので、0 件・50 件・51 件・12 と 50 の公倍数（600 件）でも、送る番号はいつも 2 以上で、送り先はいつも 1〜最後のページに入ることを、式で確かめた。記事が増えて本当の3ページ目ができれば、`parseListPage` が先に番号を返すので、転送は自然にやむ。
- 静的な生成は保たれている。直した版のビルドの出力で、`page/` 以下の `.meta` は 87 個で、`status: 308` を持つのは上の 19 本ちょうど。`location` は送り先（例: `/blog/page/5` は `/blog/page/2`）。
- 関係する4つのテストのファイル（84 件）が通る。共通の関数のテストが送り先・308・404 の境界を値で確かめ、経路のテストが、記事の数に依らずに「生成する番号は開けるか、その一覧のいまあるページへ 308 で送るか」と「その次は 404」を確かめている。
- コメントに経緯の言葉は無く、`list-pages.ts` の先頭の説明は送る番号を含めた一つの説明として読める。`.claude/rules/coding-rules.md`・`.claude/rules/testing.md` に反する所は見当たらない。
- `docs/knowledge/nextjs.md` の 14 番は、フレームワークのふるまいの記録で `.claude/rules/knowledge-directory.md` に合う。中身は、`.meta` の中身、`node_modules/next/dist/export/routes/app-page.js` で `hasNextSupport` のときだけ `meta` 全体を返すこと、`node_modules/next/dist/build/index.js` がそれを `initialStatus`・`initialHeaders` に書くこと、`?utm_source=x` が落ちること（3103 に当てた）で、事実と合う。
- コミットには、ほかの担当が作業中のファイルは入っていない。

### 4. 検索への害

Google は 308 を 301 と同じ恒久の転送として扱う（[Redirects and Google Search](https://developers.google.com/search/docs/crawling-indexing/301-redirects)）。関係の無いページ（トップページなど）へまとめて送ると soft 404 と見なされることがあると言われるが、ここでは、その番号に載っていた記事が載っているページへ送っているので当たらない。仮に soft 404 と扱われても、直す前の 404 より悪くはならない。送るページは sitemap に載らず、内部リンクも無く、送る番号には上限があり、それより後ろは 404 なので、際限のない URL も見せない。
