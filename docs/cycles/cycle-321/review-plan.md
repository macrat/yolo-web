## 直さないと来訪者が損をする、または出荷が失敗する指摘

### A1（重要）: 閲覧の8割を占める診断のプレイ面を、ダークモードで見ていない

- **根拠**: T2a（rollout-plan.md のタスク2の1・2項）は、character-personality を 375×550・320×550・1280×800 で比べるとしているが、テーマには触れていない。T2c はライトとダークの両方で開くが、対象は「診断の結果」で、開始と回答の画面は入っていない。
  - 刷新ではテーマの切替のボタンを外したので（T2e の記事の直しの理由）、OS がダークの来訪者は、必ずダークの画面を受け取る。
  - それなのに、閲覧の 85.8%・mobile 82.3% の面の開始と回答の画面が、ダークでは一度も確かめられないまま出荷される。選択肢の押した状態の色・文字と背景の差などがダークだけで壊れていても、見つける道が無い。
  - workflow.md の AP-WF05（モバイル/PC とライト/ダークの組で見る）にも当たる。
- **直し方の案**: T2a の条件に「ライトとダークの両方」を足す。比べるのは見え方だけなので、少なくとも 375×550 と 1280×800 のダークで、開始・回答・結果を撮れば足りる。

### A2（重要）: T2c の「テンプレートを1ページずつ」では、それぞれ別の UI を持つ面の大部分が確かめられない

- **根拠**: `git diff --name-only origin/main a8070aa` で調べると、変わったファイルは次のように、別々の UI を持つ面に散らばっている。
  - ゲーム: 4本がそれぞれ自前の部品を持ち、変わったファイルは nakamawake 32・yoji-kimeru 30・irodori 30・kanji-kanaru 27。
  - クイズの部品: 82。
  - 診断ごとの専用のルート: music-personality・traditional-color・character-fortune・contrarian-fortune など約10本。結果のページには専用の `page.module.css` がある。
  - 占い: `play/daily`。
  - 辞典: kanji・yoji・colors・humor で詳細の部品が別。
  - ツール: 42 のうち、ほぼすべての部品。
  - 「ゲーム」「ツール」「辞典の詳細」を1ページずつ見ても、残り3本のゲーム、知識クイズのプレイ面（「次へ」と正誤の表示。T2b は二度押しだけを見る）、占い、残りの辞典の種類、30を超えるツールの部品が壊れていれば、そのまま出荷される。来訪者は、いまの本番より悪い画面を受け取る。
  - planning.md の AP-P33 にも当たる。この項は、確かめの標本を形の振れ幅でなく価値の種類で選び、種類ごとに最低1枚は確かめることを求めている。
- **直し方の案**（作業を増やしすぎない形）:
  - T2c の「1ページずつ」の単位を、別の UI を持つ面ごとに直す。目で見るのは、ゲーム4本・知識クイズ1本（開始・回答・結果）・占い・辞典の4種の詳細とする。
  - ツールと、診断ごとの結果のページは、T2d の機械の巡回に任せる。T2d は sitemap の全 URL をどのみち開くので、同じ巡回で、375×550 の JS のエラー・横にはみ出すこと・HTTP の状態だけを拾う。人が見るのは、そこで引っかかったページだけにする。
  - 線は rollout-plan.md と同じ「壊れている所だけを直す」のままでよい。

### A3（重要）: 出荷の手順と cycle-completion の手順の順序が決まっておらず、戻す道を失いうる

- **根拠**:
  - **順序が決まっていない**: rollout-plan.md は出荷を「サイクルの完了の処理の中で行う」としている。一方、index.md は出荷を「実施する作業」のチェックの項目に置いている。終了時のチェックリストは、すべてにチェックが入ってから `/cycle-completion` を実行せよと言い、cycle-completion は手順1で `completed_at` を入れ、手順7で main へ push する。どの push が出荷で、どの push が記録なのかが文書から決まらない。
  - **戻す道を失う**: cycle-completion の手順8は「CI が失敗したら、直して再びコミット・push し、緑になるまで繰り返す」と命じている。Vercel は CI の結果を待たずに main をデプロイする（deploy.yml にデプロイの job は無く、`vercel.json` の Git 連携で出る）。出荷のあとに CI が落ち（たとえば、この環境の Node は v22.23.4、CI は Node 24）、手順8のとおりに直しを push すると、そのたびに新しい本番のデプロイができる。Hobby では、すぐ前のデプロイにしか戻れない。出荷の前の本番へ戻す道は、そこで消える。index.md の「本番で確かめ終えるまで main にほかの push をしない」と、手順8が食い違ったまま残っている。
  - **戻す手段が確かめられていない**: 誰がどうやって Instant Rollback と promote を行うのか（オーナーがダッシュボードで行うのか、PM が Vercel の MCP や CLI で行えるのか）が書かれておらず、`docs/knowledge/` にも記録が無い。本番が壊れたときにすぐ戻せなければ、壊れた画面がその間ずっと来訪者に配られる。
  - **許可の範囲が足りない**: オーナーに確かめる許可が「main への push」だけになっている。実際には、記録のための main への2度目の push と、`design-rollout` を origin から消すこと（これも push の操作である）が要る。
- **直し方の案**: 出荷の項に、次の4点を短く書く。
  1. 順序。たとえば「出荷の push → Vercel のデプロイと CI を待つ → 本番で確かめる → 壊れていれば、まず戻す → そのあとで記録の push（cycle-completion の手順7）」。
  2. 出荷のあと、本番で確かめ終えるまでは、CI が落ちても直しを push せず、先に本番を確かめて戻すかを決めること（手順8より、この順を先にする）。
  3. 出荷の前に、戻す手段を確かめること。いまの本番のデプロイの ID を控え、Vercel を操作できる手段（オーナーか、使える道具か）を確かめる。
  4. オーナーに求める許可に、記録の push と `design-rollout` の削除を含め、1回で確かめること。

## 直さなくても来訪者は損をしないもの（言い回し・進め方）

- B1（軽微）: T2b で比べる相手を、遠くの本番ではなく、T3 で起こす origin/main のローカルのビルドにしてもよい。二度押しの2打目の落ち先は、画面が切り替わる時刻で決まる。本番は網を通るので、版の差でなく網の差が結果に混ざるおそれがある。同じ機械で比べるほうが、「本番で起きない害」の判定が安定する。
- B2（軽微）: T2d の「転送の元の URL」は、本番の転送（origin/main の `next.config.ts` の `redirects()`）から取ると書くとよい。作業ブランチ側の一覧から取ると、本番にあって作業ブランチで消えた転送を見落とす。いまの差分では、消えた転送は見当たらない。
- B3（軽微）: 出荷のあとに GA の数（`page_view`・`level_start` など）が届いたかを確かめる手段と、届くまでの遅れ（BigQuery の日ごとのエクスポートなら翌日になる）を書いておくと、「確かめ終えるまで main に push しない」期間の長さが見積もれる。この環境では `bq ls` が「Invalid Credentials」で通らなかった。
- B4（軽微）: この環境の clone は shallow だった（上の事実の確かめを参照）。T3 と T4 の担当が b5ee51a や origin/main を参照するときに同じ現象に当たりうる。担当への依頼で、そのことに触れておくとよい。
- B5（軽微）: 「線」「組」「落ちる」は、サイクルの文書の中だけで通じる言い方に近い（incident-2.md の4）。オーナーへの報告では「基準」「条件の組み合わせ」「押した先」などに言い換えるとよい。
