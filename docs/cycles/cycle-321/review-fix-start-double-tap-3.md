## 何も確かめていない行・働いていない準備・名前と中身の食い違い

見つからなかった。

- answer の各テストの準備（指やマウスでの開始・時計の進め・選択肢へのフォーカス）は、どれも後の確かめに効いている（上の表で、壊せば落ちることを確かめた）。
- reveal「「はじめる」のあとは…送らない」の矩形の差し替え（点 500 の真下に最初の選択肢）は、避ける作りにすると送りが起きて落ちるので、働いている。
- DESIGN.md §8 の項（押しは何も起こさず、答えを記録せず、フォーカスも画面も動かさない／キーボードの押しはすぐ受け付ける／2問目からはすぐ受け付ける／送りでは1問目の選択肢を避けない）と、テストの名前と中身は食い違わない。

## 参考（指摘ではない。直さなくてよい）

- answer の `start()` と secondPress の `renderAndStart()` は `element.click()`（jsdom では click の detail が 0）で始めるので、キーボードで始めた扱いになり、受け付けないあいだに入らない。answer「キーボードで「はじめる」を押したあとは…」の本文は `await start();` だけで、キーボードであることが本文からは読み取りにくい。ただし、開始を指やマウスの押しに変えれば多くのテストがはっきり落ちるので、黙って偽になることはない。読みやすさのためなら、reveal の `pressWithKeyboard` のように detail 0 を明示した名前の手続きにする手がある。
- answer「受け付けなかった押しのあと、500ms を過ぎて押し直すと答えになる」と「「もう一度挑戦する」のあと…」は、ちょうど 500ms 進めてから押し直すので、境目（`<` か `<=` か）にも依存する。境目の決まりは DESIGN の「500ms のあいだ」と「500ms の指やマウスの押しは、すぐ答えになる」のテストのとおりで、いまは正しく通る。
- フォーカスが実ブラウザで選択肢へ移らないこと自体は jsdom では確かめられず、mousedown の既定の動きが止まることで代えている（AP-I07）。本番での確かめは prod-verification の側の範囲。
