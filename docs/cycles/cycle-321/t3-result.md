# 新しいデザインの版と本番の版の、表示の速さの比較（実測）

計測日: 2026-11-11

## 結論

- **実際に遅くした回線と CPU で測ると、新しい版の LCP は本番の版とほぼ同じ**（5ページとも差は −4〜+88ms、どちらも 1.9〜2.0 秒）。大きな悪化は無い。
- 指定の測り方（Lighthouse の既定＝回線と CPU の遅さを計算で模擬する方式）では、**漢字辞典の詳細ページが判定の線（LCP）に当たった**。負荷が落ち着いた2巡とも当たっている。ブログ記事と診断のプレイ面は、2巡のうち1巡だけ、4ms と 15ms の差で当たった。
- 当たった原因は、ページが実際に遅くなったことではなく、**模擬の計算の性質**と見ている。新しい版は Web フォントのファイルが減って早く届き終わるため、計算の上で「最初の描画より前に届いたもの」に数えられ、その分が LCP に足される。本番の版はファイルが多く届き終わらないので数えられない（下の「原因の見立て」）。
- CLS の線に当たったページは無い。ブログ記事は 0.115 → 0 に良くなった。
- 転送量と Web フォントは5ページとも減った（漢字辞典の詳細は 1,517KiB → 736KiB、フォントは 50 ファイル → 15 ファイル）。
- 線とは別に、気になる点が2つある: ブログ記事で、実際に CPU を遅くしたときの TBT が 137ms → 321ms に増えた。診断のプレイ面で、サーバーが応答を返し始めるまでの時間が約 11ms → 約 50〜70ms に延びた。

## 条件

- 本番と同じ版: origin/main（`385f99f67`）の本番用ビルド。`http://localhost:3200` で起動済みのものをそのまま使った
- 新しい版: コミット `e3472ea` を別の場所に取り出して `npm run build` し、ビルドが終わってから `next start -p 3105` で起動したもの
- 計測器: Lighthouse 12.8.2。performance カテゴリのみ。モバイルの既定（模擬の回線と CPU の減速）
- ブラウザ: Playwright 同梱の Chromium（`/opt/pw-browsers/chromium`、Chrome for Testing 153）、`--headless=new --no-sandbox`
- 手順は `docs/cycles/cycle-316/facts-speed-before.md` と同じ。違いは、2つの版を交互に測ったこと（本番→新→本番→新…、各5回）
- 機械は CPU 4個。負荷は、各回の直前と直後の load average（1分平均）を記録した。Lighthouse 自身が走っているだけで 1 前後になる
- URL は5ページとも新しい版で変わっていない
- 補助として、同じ5ページを `--throttling-method=devtools`（回線と CPU をブラウザの中で実際に遅くする方式）でも5回ずつ交互に測った

## 判定の線に当たったページと、原因の見立て

### 当たったページ

- **辞典の詳細**: 既定の方式で、落ち着いた2巡とも当たった（+353ms、+331ms）。負荷が高かった2巡では当たっていない。
- **ブログ記事**: 落ち着いた1回目で 4ms、負荷が高かった1巡目で 43ms 越えた。落ち着いた2回目は当たっていない。
- **診断のプレイ面**: 落ち着いた2回目で 15ms 越えた。1回目は当たっていない。

### 原因の見立て: フォントが早く届き終わるようになったことで、模擬の計算に数えられるようになった

Lighthouse の既定の方式は、遅い回線で実際に読み込むのではなく、この機械で速く読み込んだ記録から「最初の描画より前に終わっていた通信と処理」を拾い、それらが遅い回線ならどれだけかかるかを計算して LCP を出す。

この機械での実際の最初の描画は、どちらの版もページを開いてから 120〜220ms のところで起き、ちょうど Web フォントが届いている最中に当たる。

- 本番の版の辞典の詳細は、和文フォントの分割ファイルを 48 個取りに行く。最初の描画の時点で届き終わっているのは 0〜12 個で、計算にほとんど数えられない。
- 新しい版は 13 個で、最初の描画の時点でほぼ全部届き終わっている。そのため全部が「描画より前に要ったもの」として計算に入り、その分の時間が足される。

落ち着いた2巡の 10 回を、「最初の描画の時点で和文フォントの 4分の3 以上が届き終わっていたか」で分けた LCP の中央値:

| ページ         | 版   | 届き終わっていた回 | その中央値 | 届き終わっていなかった回 | その中央値 |
| -------------- | ---- | -----------------: | ---------: | -----------------------: | ---------: |
| 辞典の詳細     | 本番 |                0回 |          — |                     10回 |      2,663 |
|                | 新   |                8回 |      3,363 |                      2回 |      2,816 |
| ブログ記事     | 本番 |                2回 |      4,004 |                      8回 |      2,815 |
|                | 新   |                4回 |      3,768 |                      6回 |      3,400 |
| 診断のプレイ面 | 本番 |                5回 |      3,761 |                      5回 |      3,469 |
|                | 新   |                8回 |      3,780 |                      2回 |      2,870 |
| ツール         | 本番 |                3回 |      3,914 |                      7回 |      2,785 |
|                | 新   |               10回 |      3,012 |                      0回 |          — |

同じ側どうしで比べると、新しい版は本番の版と同じか速い（ツールは 3,914 → 3,012、ブログ記事は 4,004 → 3,768）。中央値の差は、どちらの側の回が多いかでほぼ決まっている。同じページの5回の幅が広いのも同じ理由による。

フォントは `swap` なので、実際のブラウザでは字の描画はフォントを待たない。回線と CPU を実際に遅くした補助の測定で LCP が2つの版でほぼ同じになったのは、これと合っている。つまり、既定の方式で出た辞典の詳細の +330〜350ms は、訪問者が体感する遅れではないと見ている。

### 実際に残る小さな差（補助の方式で +27〜+88ms、ブログ記事は差なし）

補助の方式では、5ページ中4ページで新しい版が少し遅い。最初の描画より前に必ず要るもの（HTML・スタイルシート・先に読み込む指定の欧文フォント2個）の転送量を足すと、新しい版が 2〜9KiB 多い（辞典の詳細 107.9 → 109.6KiB、ツール 99.9 → 107.2KiB、プレイ面 127.6 → 136.2KiB、結果面 105.8 → 112.2KiB、ブログ記事 117.9 → 124.6KiB）。内訳は、先に読み込む欧文フォント2個が 36KiB → 42KiB、スタイルシートが 2〜3KiB 増。模擬の回線（毎秒約 200KiB）では 10〜45ms に当たる。これが差の一部と見ているが、残りの原因までは確かめていない。

### 考えられる直し方（直していない）

- 実際の遅れは小さいので、出荷を止めるほどの直しは要らないと見る。
- 小さな差を詰めるなら、先に読み込む指定の欧文フォントを2個（標準と太字）から1個（標準）に減らす、または欧文フォントに含める字を絞って小さくする。
- 既定の方式の値は、フォントが描画より前に届き終わるかどうかで数百 ms 動く。今後この数字で版どうしを比べるときは、回線と CPU を実際に遅くする方式（`--throttling-method=devtools`）を併せて測ると、幅が狭く比べやすい。

## 線とは別に見つけたこと

- **ブログ記事の TBT**: 回線と CPU を実際に遅くする方式で、137ms → 321ms（5回とも 300ms 台）。スクリプトの実行時間が 456ms → 1,585ms に増え、ほとんどが React 本体の入ったファイルに計上されている。ページを開いて約 4.5 秒のところに 240〜260ms の長い処理が1つ増えていて、その直前に、目次・共有ボタン・折りたたみなどの部品が入ったスクリプト（11KiB）が遅れて読み込まれている。どの部品の処理かまでは特定していない。既定の方式の TBT では差が小さい（135 → 139、107 → 168）。ツールでもスクリプトの実行時間は 394ms → 888ms に増えているが、TBT は変わらない（130 → 138）。
- **診断のプレイ面のサーバーの応答**: 応答を返し始めるまでの時間が、本番の版 9〜17ms に対して新しい版 47〜92ms（`curl` 5回とLighthouse の記録）。このページはどちらの版もリクエストごとにサーバーで描く。結果面では差が無い（どちらも約 9〜10ms）。原因は調べていない。
- **リンク先の先読みの数**: 新しい版は、辞典の詳細を除く4ページで、リンク先の先読みの通信が 6〜7 本多い（転送量で 26〜40KiB 増。辞典の詳細は 38 本 → 29 本に減）。最初の描画より後に起きるので LCP には効かない。

## 確かめられなかったこと

- 実機のスマートフォンや、本番の配信環境（Vercel の配信網・圧縮・キャッシュ）での値。測ったのは、同じ機械の中で動かしたサーバーへの接続だけ。
- 既定の方式で、負荷がまったく無い状態の値。測っているあいだ、ほかの担当の作業が断続的に走り、落ち着いた巡でも load average は 0.5〜2.1 だった。
- 補助の方式のツール・プレイ面・結果面は load average 1.4〜4.9 のなかで測った（5回の幅は 230ms 以内に収まっている）。
- 補助の方式で残った +27〜+88ms の原因の全部。転送量の増加で説明できるのは一部まで。
- ブログ記事の TBT が増えた原因の部品、プレイ面のサーバーの応答が延びた原因。
- 5ページ以外のページ（トップ、一覧、字の種類が多い辞典の一覧など）。
