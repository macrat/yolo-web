## 3. 指摘

### major-1: 「表示の速さ」の合格の線が、facts-speed-before の実測に照らすと判定として機能しない（AP-P01・AP-P16・AP-P18）

**どこ:** index.md:93、facts-speed-before.md

**なぜ問題か:**

1. **(2) の 2.5 秒の線は、実際には5ページすべてで「変更前を超えない」になる。**
   - 辞典の中央値は 2,508ms で、2,500 を超えています。つまり5ページ中5ページが 2.5 秒を超えています。facts:158 の「4ページ（辞典は 2,508ms）」は事実の誤りです。
   - 「変更前を超えない」は許容0%です。(1) の「悪化10%以内」より常に厳しいので、(1) は死んだ条件になります。
2. **許容0%は、この測り方の揺れの中では硬貨投げになる。**
   - 5回のあいだの幅は 722〜1,980ms です。中央値の15〜65%にあたります。
   - `./tmp/lh/before/` の5回の値を再標本化して試算しました。同じビルドどうしを比べても、1ページあたり約36〜50%の確率で「変更後＞変更前」になります。
   - 5ページすべてが合格する確率は、約3〜11%です。**何も悪化していなくても、ほぼ確実に不合格が出ます。**
   - 不合格のあとの手順は、T1 への差し戻し、それでも越えれば「`DESIGN.md` §3 の書体の規定を疑う」です。**揺れだけを根拠に、書体の規定を変える道が開いています。**
   - 逆に、測り直せばいつか合格が出るので、「合格が出るまで測る」運用にも流れやすくなります。
   - Lighthouse の公式文書も、5回の中央値で安定性は「2倍」にとどまるとし、同じ機械の負荷を揺れの主な原因に挙げています。この計測でも、benchmarkIndex が 2,216〜2,699 まで動いています。
3. **LCP は、この変更の主な危険（和文 Web フォント）をとらえにくい。**
   - 5ページとも、LCP の要素は文字です（p・h1）。
   - next/font の既定は `display: swap` です（facts-external:172）。代わりの書体で先に描かれるので、フォントの重さは LCP に出にくくなります。
   - 一方で転送量は、5回で ±0.5% 以内とほぼ決まった値です（例: 辞典は 1,435KiB が5回とも同じ）。
   - いまでもフォントの転送は、1ページあたり15〜50ファイル・232〜834KiB あります（Lighthouse の JSON の network-requests より）。
   - 1巡目で求められ、review-response:12 で「LCP と転送量の比較を入れた」とした**転送量の条件が、1702a15 から b1e9a5c のあいだに黙って消えています。** 転送量は facts に記録されているのに、合否には使われていません。

**どう直すか:**

- **合否の主な線を、揺れのない指標に置く。** ページごとの総転送量と、Web フォントの転送量・ファイル数です。変更前の値（facts に追記）に対する上限を数字で決め、根拠を書きます。
- **LCP は、揺れの幅を実測してから線を決める。**
  - T9 で、変更前どうしを交互に測る A/A を先に行い、揺れの幅を記録します。
  - 回数は、揺れの幅が線より十分小さくなるまで増やします（目安は各10〜15回、交互に）。
  - 合格は「悪化が、A/A の揺れの幅と10%の大きいほうを超えない」にします。
  - 「変更前を超えない」（許容0%）は外します。
- **2.5 秒の扱いを書き直す。** 5ページすべてがすでに超えているので、判定の線としては使えません。「実験室ではすでに全ページが超えている」という事実を書いたうえで、次のどちらかにします。
  - 実地の値（Search Console の Core Web Vitals レポート、または CrUX）を出荷前後で見る。
  - 変更前から超えている問題として、backlog に起票する。
- 「実地の値が取れるなら」ではなく、何で見るかを具体的に書く。
- facts-speed-before:158 を「5ページすべて」に直す。フォントの転送量とファイル数も記録する。

## 5. 来訪者にとっての価値

計画が届けるものの価値ははっきりしています。

- 入力欄の拡大、文字サイズが追随しない問題、表が縦に潰れる問題、空の SNS カードが解消する。
- PV の78%の面で、回答中に選択肢が見えない欠陥が解消する。
- サイト全体が1つの顔になる。

ただし、速さの線がいまのままだと、次の2つのどちらかになります。

- 揺れのせいで不合格が出て、書体の規定を誤って見直す。
- 何度か測り直して合格を得て、本当に和文フォントが重くなったかは見えないまま出荷する。

どちらも、「重いフォントの害を出荷前に止める」という来訪者のための線の意味を失わせます。転送量を主な線にし、LCP は揺れの幅を測ってから線を決めれば機能します。知識クイズの「次へ」も1行足せば閉じられます。
