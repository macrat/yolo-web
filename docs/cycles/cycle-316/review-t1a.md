### B1. ツールの「入力はサーバーに送信されない」という約束を破る（憲法の規則1・2、AP-P24）

- **どこが**: 「方式 C」と「前提と、確かめられなかったこと」に「入力された字でも、その字を含むファイルが作られる」「ページが読み込みの後で描く字（…入力された字）は、その字の分だけ追加で読み込む」とある。試作の読み込み用スクリプト（`tmp/t1a/varC/loader.js`）は、`MutationObserver` で本文のテキストノードをすべて拾います。字は `?t=` に入れて自サイトへ送ります。代わりの案の C-Google なら Google へ送ることになります。
- **なぜ**: ツールには次の約束が書かれています。
  - `src/tools/_components/ToolPageLayout/index.tsx:87`「このツールはブラウザ上で動作します。入力データがサーバーに送信されることはありません。」
  - `src/app/tools/page.tsx:87`「入力した内容はすべてブラウザの中で処理され、外部に送信されません。」

  ツールの出力（全角半角変換の結果、文字数カウントに貼った文章を反映した表示など）はテキストノードとして描かれます。そのため、来訪者が入力した文章の字の集合が URL に載ります。送り先は Vercel のリクエストログと CDN のキャッシュで、C-Google なら Google です。並べ替えて重複を除いても、字の集合そのものは漏れます。

- **どう直すか**: 来訪者の入力に由来する字は、切り出しの要求に含めない設計にする。たとえば入力欄と結果の領域に、事前に作った静的なサブセットか端末の書体を使う。そのうえで、この扱いが §3 と両立するかを判断文書に書く。C-Google を代わりの案にするなら、同じ問題に加えて、ツールの約束とプライバシーポリシーの書き換えが要ります。これは「プライバシーポリシーに加える」だけでは済まず、来訪者への約束を変える判断になります。

### B2. 「ページごとのサブセットを事前に決めて静的に配る」案を比べていない（AP-P17・AP-P14、観点4）

- **どこが**: 比べた配り方は A・B・C（その場で切り出す C と C-Google）だけ。3,526 ページのうち 3,299 ページは事前に書き出されるので、字の集合はビルドの時点で分かります。リクエストごとに描くページ（診断の結果・`?with=`・知識クイズの結果）も、描く中身はデータファイルで決まっています。
- **なぜ**: ページごとの正確なサブセットは、ビルドの時か、サーバーで描くときに決めることもできます（以下「C-静的」）。転送量は方式 C と同じ下限のままで、方式 C の弱点を次のとおり除けます。
  - **JavaScript が要らない**: JavaScript を切った来訪者やスクリプトが失敗した来訪者でも、§1 の「巨大なアンティーク体の見出し」が出る。
  - **ブラウザが早く見つけられる**: `<head>` に URL が書けるので `<link rel=preload>` で先に読める。方式 C は、HTML の読み込みと解析、先に置いたスタイルシート、スクリプトの実行が終わってから要求を出す。そのため最初の描画に間に合うことがなく、すべてのページで字の差し替え（swap）が必ず起こる（M4 に関係）。
  - **濫用の窓口が無い**: 任意の字を切り出させる配信口を公開しなくてよい（M3）。
  - **CDN の冷えた状態（初回、デプロイ直後、キャッシュから追い出された後）の待ちが無い**（M2）。
  - **入力された字を送らない**（B1）。

  読み込みの後で現れる字だけを、実行時に補う混成の形も取れます。診断の設問のように、データで決まっている字は最初のサブセットに含めることもできます。

- **どう直すか**: C-静的（と混成の形）を比べ、次の点を並べて判断し直す。
  - ビルドの時に役割（見出し／本文 400／700）をどう決めるか（HTML の要素やクラスから決める、Playwright で描いて決める、など）
  - Vercel のビルド時間の上限 45 分と出力ファイルの数
  - 役割を近似した場合に転送量がどれだけ増えるか

  「来訪者の側で見ても最も良い」という主張は、この比較をしてから書く。

### M1. ライセンス：試作は著作権表示とライセンスを消し、IBM Plex Sans には Reserved Font Name がある（観点5）

一次資料で確かめました。

- OFL.txt の冒頭（google/fonts リポジトリ）:
  - Zen Antique「Copyright 2021 The Zen Antique Project Authors」。RFN は無い。
  - BIZ UDPGothic「Copyright 2022 The BIZ UDGothic Project Authors」。RFN は無い。
  - IBM Plex Sans「Copyright © 2017 IBM Corp. with **Reserved Font Name "Plex"**」。
- SIL OFL FAQ（openfontlicense.org/ofl-faq/）:
  - 2.6「Is subsetting a webfont considered modification? Yes. … would not normally allow the use of RFNs.」
  - 2.5 最適化した版は Modified Version で、「appropriate renaming」が要る。
  - 2.8 Functional Equivalence（名前を残してよい例外）の条件には、全字種の維持と、著作権・ライセンスのメタデータの保持が含まれる。ページごとのサブセットはこの条件を満たさない。
  - 1.10 OFL の本文（またはフォントのメタデータ内の記載）を添えずに配ってよいのは、文書への埋め込みか、プログラムへの同梱のときだけ。

問題は次の3つです。

- `tmp/t1a/subset.py:34` の `opts.name_IDs = []` は name テーブルをほぼ空にする。nameID 0（著作権）と 13・14（ライセンス）も消えるので、OFL の条件2に反する。Node の subset-font も、既定では name の大半を捨てる（README の `preserveNameIds`）。
- Plex を 400 と 700 に固定し、ASCII だけに切り出したものは Modified Version になる。フォントの中の名前（nameID 1・4・6・16 など）に「Plex」を使えない。CSS の `font-family` の名前も、FAQ 5.3 の「mechanisms that specify a font in a document」に当たりうる。
- 判断文書にライセンスの検討が一切無い。

**どう直すか**:

- 3書体とも nameID 0・13・14 を残すことを実装の条件にし、その分のバイト数（数百 B/ファイル）を見積もりに足す。
- Plex は次のどちらかにする。
  - 名前を変える（フォントの中の名前と CSS の名前の両方）
  - IBM が自ら配っている分割済みの woff2（npm `@ibm/plex-sans@1.1.0` の `fonts/split/woff2/IBMPlexSans-Regular-Latin1.woff2` 20,984B・Bold 21,256B）を改変せずに使う。この場合、結論の表の 13KB×2 より約 16KB 増えるが、余裕の最小 103KiB の中に収まる。
- どちらを採るかと、その根拠を書く。

### M2. 本番で成り立つかを確かめないまま「T1 で最初に確かめる」に回している。一次資料で分かることも誤っている（観点2、AP-P01・AP-P19・AP-WF12）

一次資料と手元の実測で確かめた結果です。

- **CDN のキャッシュ**（Vercel「CDN Cache」）: Functions の応答を CDN に置くには `s-maxage=N`（または `CDN-Cache-Control`／`Vercel-CDN-Cache-Control`）が要る。試作の応答ヘッダは `public, max-age=31536000, immutable` だけなので、Vercel では CDN に置かれない。
- **キャッシュのキー**（Vercel「Purging Vercel CDN Cache」）: キーはリクエストの URL・ホスト・**デプロイごとの URL** から作られ、クエリは静的ファイルの場合だけ無視される。つまりクエリ付き URL ごとに Function の応答は置けるが、**デプロイのたびに空になる**。
- **地域ごとの分割と追い出し**: キャッシュは地域ごとに分かれ、「If your asset is rarely requested (e.g. once a day), it may be evicted」。main は push のたびにデプロイされます（`vercel.json`。直近30日のコミットは121件）。3,500 ページの大半は来訪の少ないページです。そのため「ほとんどの来訪者と同じ状態」（「測り方」の「環境」）は裏付けが無く、ロングテールの来訪者の多くは冷えた経路に当たると見込まれる（GA での裏付けも無い）。
- **Function の地域**: 既定は `iad1`（Vercel「Functions Limits」）。プロジェクトの設定は**未確認**。
- **URL の長さ**: CDN の上限は 14 KB（Vercel「URL_TOO_LONG」）。`all.jsonl` から計算すると、最長は `/dictionary/kanji/grade/7` の見出しの役割で約 10.2KB（1,136字 × `encodeURIComponent` で1字9バイト）。漢字の追加や T2〜T7 の変更で越えうる。越えると、そのページの見出しのフォントが丸ごと落ちる。
- **Node で切り出せるか**: 手元で npm `subset-font@2.9.0`（harfbuzz の hb-subset の wasm 版）を実フォントに掛けた。
  - `/blog/sql-cheatsheet` の本文 400（393字）を切り出す時間は、BIZ UDPGothic で 512〜926ms、Zen Antique で 362〜389ms。
  - 大きさは**既定の設定で 107,756B**。fontTools の試作では 62,252B なので +73%。`noLayoutClosure: true` なら 58,668B。
  - つまり切り出しは動くが、冷えた経路では役割ごとに約0.4〜0.9秒が足される（Vercel の 1 vCPU での値は**未確認**）。**転送量は道具と設定で ±70% 以上動く**。
- 元のフォントは 4.6〜5.5MB で、関数の大きさの上限 250MB には収まる。コールドスタートの時間は**未確認**。

**どう直すか**: 上の事実を判断文書に書き、その後の扱いを次のようにする。

- 実行時に切り出す部分が残るなら、`s-maxage`、道具と設定の固定（レイアウトの閉包を切る、ヒンティング、残す name）、URL の長さ対策（字の範囲の圧縮か、サーバーが発行する ID）を、T1 の条件として明記する。
- 冷えた経路での、フォントの表示が終わるまでの時間の見積もりを添える。
- 見積もりの転送量は、本番で使う道具で出した大きさに差し替える。

   - 転送量の見積もりが本番の道具では ±70% 動く（M2）
   - LCP と FCP の計り方（M5）

   facts とのずれの原因は先読み（m2）。

2. **本番で成り立つか**: 切り出しは Node で動く（subset-font と harfbuzz、手元の実測は上のとおり）。クエリ付き URL も CDN に置ける。ただし `s-maxage` が要り、デプロイごと・地域ごとに冷える。URL は 14KB が上限。Function の地域、コールドスタートの時間、Vercel での実行時間は未確認（M2）。
3. **安全とコスト**: 備えが要るのに、記述が無い（M3）。
4. **来訪者への影響**: JavaScript への依存、差し替えが必ず起こること、仮名と約物のプロポーショナルによるずれ、FCP の悪化、入力の送信。ページごとのサブセットを事前に決めて静的に配る案の方が良い見込みが高い（B1・B2・M4・M5）。スクリーンリーダーの読み上げへの影響は無い（フォントの読み込みは DOM を変えない）。
5. **ライセンス**: 3書体ともサブセット化して自前で配ることは許される。ただし著作権表示とライセンスを残すこと、Plex は RFN のため名前を変えるか IBM が配る分割済みのファイルを使うことが条件（M1）。
6. **計画との整合**: 上限は動かしておらず、帰結の順序も守っている（方式 A → A2 の検討は正しい）。測り方を T1a と T9 で決めてレビューで確かめる形にも沿っている。ただし、LCP の計り方と、冷えた経路・流れ全体の扱いは直す必要がある（M5・m1）。スキルへの提案は直す必要がある（m3）。
