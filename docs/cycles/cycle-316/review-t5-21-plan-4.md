## 良い所

- **E は来訪者にとって最も良い形になっている。** 見出しが和文だけになり、全体が Zen Antique で組まれるので、`45rem` 未満で本文と同じ 17px でも字の形で見出しと分かる。「第三者サービスの利用」の章の見出しの下で、「アクセス解析」「広告」は何に使うサービスかを言う見出しとして読め、サービスの名前は見出しのすぐ下の1行目にある。「Google Analytics を止めたい」来訪者も、見出し「アクセス解析」→ 1行目の「Google Analytics」→ 同じ節のオプトアウトの案内、と迷わず届く。ページ内の検索（「Analytics」「AdSense」）でも本文に当たる。本文の文言を変えないので、規約の中身も動かない。
- **「広告」は本文より強く言わない。** 話題の名前で、配信しているとは読めない。
- **実測の表が完全に正しい。** 本番のビルドで全セルを測り直して一致した。200% で受け入れる5つも、どれも1行に収まらない文節の中の折れから出たもので（§4 の 200% の項）、1字だけの行・行頭の長音符を具体的に名指ししている。375px の 200% の「プライバ／シー／ポリシー」も文節の中の折れだが、1字だけの行も禁則の破れも出さないので、名指しに入らないのは正しい。
- **builder は行と 9-b だけで組める。** 組み方の箇条（最初のセクション・章ごとの `Section`・h3 の線の有無の名指し・文言・制定日・`Link`）が1か所に並び、完了の条件は表と名指しの5つで数えて確かめられる。
- **ツギハギ・tmp/ の参照は無い。** 9-b は「本文の列」「見出しの段」「文言の比べ」「大きさ」「折れの実測」の順に1つの状態として読め、前の案 C を採っていた痕跡（「C の組み方」の段落）は消えている。T5-21 の行も新しい形だけを言う。

## 指摘

### 指摘1（planner）: 条件1「和文で始まる」が、計画が残す h3「Google Analyticsによるアクセス情報」を否定しており、9-b の中と完了の条件とで食い違う

条件1は「見出しの頭が欧文だと、目を止める頭の字で1行の段落と見分けられません」と一般の形で言い切る。一方で、「収集する情報」の章の h3「Google Analyticsによるアクセス情報」は頭が欧文のまま残り、しかも章の見出しのすぐ下で上の線を持たない方の h3 である。条件の書き方どおりなら、ページで最も見分けにくい h3 をそのまま残していることになり、9-b を読む人（builder・次のレビュー・後のサイクル）は、なぜこれだけが外れるのかを読み取れない。T5-21 の行の完了の条件も「privacy の h3 の5つがどれも和文を含み」と、前の条件（含む）の言い方のままで、9-b（始まる）と食い違う。

来訪者の側で見ると、この h3 は章の見出し（23.84px）のすぐ下に立ち、「による／アクセス情報」の和文が Zen Antique で組まれ、行間も `1.25` なので、見出しとして読める。だから文言を変える必要があるとは限らない。どちらかにそろえる（決めるのは planner）。

- 条件1を、この章の2つの文言を選ぶための条件として範囲を言い、「Google Analyticsによるアクセス情報」が頭の欧文でも見出しとして読める理由（章の見出しのすぐ下に立つ・後ろの和文が見出しの書体で組まれる、など）を1文で書く。完了の条件の「和文を含み」はそのままでよい。
- あるいは、この h3 も条件1を満たす文言に変える。その場合は、E の「アクセス解析」と頭が重ならないこと（条件2）、本文と合うこと、折れの表の行を取り直すことが要る。

どちらを採っても、9-b の条件と、T5-21 の行の完了の条件の言い方をそろえる。

### 指摘2（planner、小）: 200% の定義を2回書いている

「見出しと本文の大きさ」の前置き（「200% はブラウザの既定の文字サイズを 32px にした状態で、§4 の閾値も一緒に動くので、どの幅も `45rem` 未満の段になります」）と、「見出しの折れ（実測）」の前置き（「200% はブラウザの既定の文字サイズを 32px にした状態です」）が同じことを言う。後者を消すか、前者を指す形にする。

### 指摘3（planner、T5-21 の範囲の外。T5-6 の行）: `next build --webpack` の型の検査を落とす export が、行の名指しの3つのほかにもう1つある

依頼の確認の中で見つけた。T5-6 の行は「結果のページ3本の `export const CTA_TEXT` を page.tsx の外へ移し、`next build --webpack` の型の検査を通す」と書くが、HEAD の `--webpack` のビルドは次の4つで落ちる。

- `src/app/play/{contrarian-fortune,impossible-advice,unexpected-compatibility}/result/[resultId]/page.tsx` の `CTA_TEXT`（行が名指しする3つ）
- `src/app/play/character-fortune/result/[resultId]/page.tsx` の `export const THIRD_PARTY_HEADING`（行に無い。作業ツリーでも残っている）

T5-6 の builder が行のとおり3つだけを移すと、`--webpack` のビルドは通らないまま完了の条件を満たせない。T5-6 の行の名指しに `THIRD_PARTY_HEADING` を足す（あるいは「page.tsx から Next.js がページに許さない export をすべて外へ移す」と言う）。T5-21 の判定とは別に、PM が planner に回す。

## 本番のビルドが型の検査で落ちる件（依頼の確認）

planner の「本番ビルドが HEAD のまま結果のページの追加の export で型検査が落ちた」は、`--webpack` のときだけである。HEAD（`ada21225`）の木を scratchpad に2つ取り出して（`node_modules` は `cp -al`）次を確かめた。

- 既定の `npm run build`（Turbopack）: `Running TypeScript ...` を含めて通り、exit 0。この本番のビルドを `next start` で配信して上の実測をした。
- `npx next build --webpack`（`generate:release-id` のあと）: `Compiled successfully` の後の `Running TypeScript ...` で、上の指摘3の4つの `TS2344`（「… is not assignable to type 'never'」）で落ち、exit 1。

したがって、T5-21 の実測のために webpack の開発サーバーを使う必要は無く、既定のビルドで本番の状態を測れた。9-b 自体は測った環境を書いていないので、直す所は無い。builder の実測（`frontend-design` スキルの手順）は既定の `npm run build` で行えばよい。

## 見たが指摘にしないこと

- **F を捨てる理由の「全ページの見出しにかかる部品の変更」** は作る側の事情に見えるが、判断の芯は「E で4つの条件を満たせるので、この2つのために部品を変える得が無い」で、来訪者の得失で決めている。
