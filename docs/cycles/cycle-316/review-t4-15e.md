## UTF-8 の直し

- 正しい。ライブラリ 2.0.4 の `qr8BitByte` は符号にするたびに `qrcode.stringToBytes` を引くので、モジュールの読み込み時に差し替えれば効く。TextEncoder はサロゲートペア（絵文字）も4バイトにする。「こんにちは」「日本語」「東京駅で待ってます」「明日の会議は…」「カフェ☕ 🍣寿司」「ｱｲｳ半角カナ」「é café」は、変更前はどれも jsQR・ZXing の両方で化けるか読めず、変更後はどれも両方で元の文に戻った。
- ASCII に後退は無い。32通りすべてで、変更前後のモジュールの並びが同一だった。
- 文字コードの宣言（ECI）を持たないバイトのモードで UTF-8 を入れる形は、多くの生成器と同じやり方で、ZXing は推測で UTF-8 と判定した。iPhone の標準のカメラは実機が無いので確かめていない。
- テストは通るが、確かめ方が間接的（Minor-5）。

## 指摘

### Critical

なし。

### Major

#### Major-1 FAQ の「入力できる長さ」の答えが、この道具では成り立たない

`meta.ts` の FAQ は「数字のみなら最大7,089文字、英数字なら4,296文字、バイナリデータなら2,953バイトまで」と答える。これは QR の規格の数字・英数字のモードの上限で、この道具は `addData(text)` を型の指定なしで呼ぶので、ライブラリの既定の**バイトのモードだけ**で符号にする（`qrcode.mjs` の `mode = mode || 'Byte'`）。測った上限は次のとおり。

| レベル    | 数字だけ | 半角英数 | 日本語（ひらがな） |
| --------- | -------- | -------- | ------------------ |
| L         | 2,953    | 2,953    | 984                |
| M（既定） | 2,331    | 2,331    | 777                |
| Q         | 1,663    | 1,663    | 554                |
| H         | 1,273    | 1,273    | 424                |

来訪者に起きること: 電話番号や数字の列を 3,000 字入れた人は、FAQ が 7,089 字まで入ると言うのに「文が長すぎて」と断られる。日本語の文を入れる人（この変更で初めて使えるようになった人たち）には、UTF-8 で1字が3バイトになり、既定のレベルでおよそ 777 字までという、いちばん要る数が書かれていない。FAQ は画面に出て FAQPage の JSON-LD にも入るので、検索結果でも誤った数を言いうる。

直し方: 答えを、この道具が実際に入れられる量で書き直す（既定のレベル M で半角英数およそ 2,300 字・日本語およそ 770 字、L ならそれぞれおよそ 2,900 字・980 字、レベルを上げると減る、など）。規格の数字・英数字のモードの数は、この道具では使わないので書かない。数は上の表のように測って確かめる。

### Minor

#### Minor-1 いちばん低いレベル（L）でも「エラー訂正レベルを下げてください」と言う

L を選んで 3,000 字を入れると、欄の直下に「文を短くするか、エラー訂正レベルを下げてください。」と出る（375px・ダークで撮って確認）。L より下は無いので、来訪者は選ぶ欄を開いて下げる先が無いことを知り、何をすればよいかをもう一度考えることになる。L のときは短くすることだけを言う。あわせて、どれだけ短くすればよいか（そのレベルでおよそ何字まで入るか）を添えると、直し方が具体になる（§8「何が問題でどう直すかを文字で書く」）。欄の直下に 8px で置かれること・欄が太い線になること・`aria-invalid` と `aria-describedby` が文を指すこと・`role="alert"` で読まれることは、どの幅・200%でも満たしていた。

#### Minor-2 `updatedAt` を更新していない

`src/tools/types.ts` は `updatedAt` を「Set when main content is updated.」と定め、`src/app/sitemap.ts` の最終更新日と `src/lib/seo.ts` の JSON-LD の `dateModified` がこれを使う。今回は、日本語の QR が読めなかった誤りを直し（道具が出すものが変わった）、description・howItWorks・FAQ の文も変えた。見た目だけの組み直しと違い、中身の更新にあたるので、`updatedAt` をこの変更の日時にする。いまのままだと、検索エンジンにも来訪者にも、日本語が読めるようになった版が 2026-02-28 のままに見える。

#### Minor-3 画面の大きさの根拠として書いた文が、測った事実と合わない

`logic.ts` の `CELL_SIZE` の説明は「短い URL の QR が 150px ほどになり、画面から読み取れる大きさで、保存のボタンと一緒に1画面に収まる」と言う。測ると、1280×800 で短い URL を入れたとき、ボタンの下端は 806px で画面の外（変更前は 716px で中にあった）。375×667 では画像の下端が 705px、ボタンの下端が 776px で、どちらも最初の画面に収まらない。実際のブラウザは画面の高さからツールバーの分が減るので、さらに外になる。

読み取りには 4px／モジュールで足りる（上の「読み取り」）ので、大きさそのものを直す必要は必ずしもない。ただし、書いてある理由が成り立たないまま残ると、次にこの見本を写す道具が「1画面に収まる」を前提に組む。成り立つ理由（等倍の画面で1モジュールが整数の画素になり、PC の画面からスマートフォンで読める大きさであること、など）に書き直すか、1画面に収まることを本当に満たす大きさと置き方を選び直す。1280px では 884px のボックスに 148px の画像が左に寄って小さく見えるので、選び直すなら、PC で画像を大きめにして読み取りやすくする案も比べてほしい。

#### Minor-4 FAQ の「スマートフォンでは、画像を長押しして保存することもできます」を確かめていない

画面の画像は `data:` の URL の PNG である。iOS の Safari の長押しの保存はふつう使えるが、Android の Chrome で `data:` の画像を長押しから保存できるかは、このコンテナでは確かめられず、公開情報でも確かな裏付けを得られなかった。できない端末の来訪者は、FAQ のとおりにして保存できず、サイトの言うことを疑う。実機で確かめるか、確かめられるまで文から外し、確実な手段（「PNG画像をダウンロード」のボタン）だけを言う。

#### Minor-5 UTF-8 のテストが、バイト列を直に確かめていない

`logic.test.ts` の「日本語の文を UTF-8 のバイトで符号にする」は、「こんにちは」が2型になることで間接に確かめている。下位8ビットに戻れば落ちるので役には立つが、ほかの誤った符号化（Shift_JIS など、同じ型の大きさになるもの）は通ってしまい、ASCII が変わらないことと、絵文字（サロゲートペア）が4バイトになることは確かめていない。`qrcode.stringToBytes` の出力を、日本語・ASCII・絵文字について `TextEncoder` のバイト列と直に比べるテストを足す。

#### Minor-6 使われていない型の宣言 `src/types/qrcode-generator.d.ts` が残っている

ライブラリ 2.0.4 は自分の型（`dist/qrcode.d.ts`）を持つ。このファイルを外して `tsc --noEmit` を流しても通る（使い捨ての worktree で試し、戻した）。中身も、今回のコードが使う `renderTo2dContext` と `stringToBytes` を持たない古い形で、読む人に「このライブラリの型はこれだけ」と誤って伝える。T4-15e の範囲（`src/tools/qr-code/` だけ）の外なので、PM がこのタスクに含めるか、別のタスクか backlog に載せるかを決める。

#### Minor-7 description の「対応」が2度続く

「日本語の文にも対応し、PNG画像で保存可能。エラー訂正レベルの設定に対応。」と、短い文の中で「対応」が2度出る。検索結果の抜き出しとして読むと単調で、「保存可能」「設定に対応」は体言止めが続いて硬い。たとえば「テキストやURLからQRコードを作り、PNG画像で保存できる無料ツール。日本語の文も読み取れるQRコードになり、エラー訂正レベル（L/M/Q/H）も選べます。登録は不要です。」のように、何ができるかを動詞で言う（§9）。howItWorks の「スマートフォンの読み取りアプリで正しく読めます」は、2つの読み取り器で確かめた範囲では言い過ぎではない。
