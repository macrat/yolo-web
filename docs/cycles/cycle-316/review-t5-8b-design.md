## 指摘

### 1. 見出しの列に指定する幅が、サイトの `border-box` では足りず、長い見出しが広い画面で折れる（直す）

3-1 の手順2は「値は、左右の余白を除いた中身の幅である」と書いている。4-3 の試験も「見出しの列の max-content（余白を除く）が指定されること」とする。

しかしサイトは `globals.css` で、すべての要素を `box-sizing: border-box` にしている。セルの `width` は余白を含む幅として効く。今の `applyTableLayout` の細くする道も、`columns.outer[j] - columns.mins[j] + plan.widths[j]` と、余白を含む幅を入れている。

中身の幅を入れると、列は右の余白 8px（200% では同じ 8px）の分だけ max-content より細くなる。1文節の見出しでは、列の最小の幅が勝つので見えない。しかし yoji-kimeru・nakamawake の「いちばん／長く／続けて／正解した（勝った）／日数」は、試作で 884px の表でも2行に折れた。(a) のねらいの「見出しを1行に組める幅」と逆の結果になる。

planner の実測は「素の HTML の表」で、既定の `content-box` だったので、この差が出なかった。

- 3-1 の手順2を、余白を含む幅（測ったセルの `getBoundingClientRect().width`。今の細くする道と同じ数え方）にする。
- 4-3 の試験の文も、同じ数え方に直す。
- 試作と 4-2 の条件2の測りは、サイトの CSS（本番のビルド）で行うと書く。

### 2. 狭い画面で、見出しの列が値の列より先に幅を取り、長い見出しと長い値を持つ表の値が文節1つずつの縦の並びになる（直す）

2章の (a) の行は「狭い画面では、ブラウザがもともと見出しの列を中身の幅以内に収めているので、ほぼ変わらない」とする。これは、今の5面では正しい。成績の表の値は1文節で min と max が等しく、漢字カナール・伝統色・irodori の見出しは短いからである。

しかし列に幅を指定すると、配り方の順が変わる（上の「試作」の CSS Tables 3 の段）。見出しの列が max-content に届くまで、値の列は最小の幅（いちばん長い文節）に留まる。見出しと値のどちらも長い表では、狭い画面で見出しが1行に伸び、値が文節1つずつ縦に並ぶ。試作では、299px で値が3行から8行になった。

T5-6 の逆張り運勢診断の数字の表は、まさにこの形である。1-3 は T5-6・T5-10・T5-11・T5-18 を「いまは影響を受けない」とした。しかし、この設計が §5 に書く規則は、そうした表がこれから従う規則である（AP-P03・AP-P33）。

§5 に入れる文の「値の列のいちばん長い文節が入らないときは、見出しの列が…幅を譲る」も、この順を規則として書いている。見出しは1行にするが、値は文節ごとに折れる所まで削ってよい、という規則になる。ラベルより値を読みに来た来訪者には逆である。

直し方は planner が比べて決める。たとえば次の形がある。

- 見出しの列を max-content に留めるのは、表に余りがあるとき（何も指定しない組みで、見出しの列が max-content を超えるとき）だけにする。余りの無い幅では、今のブラウザの配り方のまま（見出しと値に、それぞれの min と max のあいだで配る）にする。見出しの列が max-content を超えないという (a) の中身は保たれる。そのうえで、狭い画面の配り方は今と変わらない。
- 組の幅 G を、余りの無い表に指定したときの扱いも同じ考えで決める。漢字カナールの 200% の狭い画面で、G のために値の列から何 px 取るのかを書く。

どの形にしても、次を直す。

- 2章の (a) の行の「狭い画面ではほぼ変わらない」の文。
- 5章の §5 の文。
- 4-2 の条件2。「値の文節が入る限り max-content に等しいこと」は、この順を合格の条件にしている。
- 4-2 に、長い見出しと複数の文節の値を持つ表の見本を足し、狭い画面（320・375、既定と 200%）で値の行数が前の版より増えないことを確かめる条件。T5-6 の表のデータを `DataTable` に入れた見本などを使う。

### 3. サーバーで描いた組では、表のあいだと下の中身が、組む前に描かれてから動く（直す）

3-2 は、組の枠が「組の最後の文が組むまで隠れたままになる」ので、「先に届いた表を描いたあとで…組み直して動かすことが無い」とする。

たしかに隠れるのは表の枠である。しかし、組の中の表と表のあいだの中身（漢字カナールでは小見出し）は隠れない。回線が遅く HTML が途中まで届いたところで描かれると、次のことが起きる。

1. 1つ目の表は、組む前の幅（中身に比例して配った列）で場所を取ったまま隠れている。
2. その下の小見出しが、その高さの下に描かれる。
3. 最後の文が 1つ目の表を組むと、値の列が広がって表の高さが変わる。
4. すでに描かれた小見出しとその下が動く。

§5 の「列の幅と、横に送るかは最初の描画から決め、描いたあとに組み直して表とその下を動かさない」に反する。今の表ごとの組み方では、表の直後の文がその場で組むので起きない。

4-2 の条件5の見方でも、これは見つからない。`renderToString` の HTML を Chromium で開くだけでは、HTML がいちどに読まれ、途中で描かれる機会が無い。ページの CSS（組む前の枠を隠す規則）が無ければ、「描かれない」ことも確かめられない。

- 組を組み終えるまで、組の中身（表のあいだの中身を含む）を描かない形にする。`visibility` は `display: contents` の要素からも子に継がれるので、組の印で組の全体を隠せる。あるいは、表ごとの文がその場で表を組み、あとの表で G が変わっても前の表の高さが変わらないことを示す。どちらにするかを決める。今はサーバーで描く組を使う面が無いので、サーバーで描く組を今は持たないと決めて、その理由を書く形もある。
- 条件5の「サーバーで描いた組」の測りは、ページの CSS を入れた HTML を、組の途中（1つ目の表のあと）で止めて流す小さなサーバーから読ませる形にする。止めているあいだと組んだあとのフレームで、組の中と下の要素の位置が変わらないことを確かめる。

### 4. 結果のボックスの中の表（`inBox`）を組に入れると、組めずに3秒隠れる（直す）

`placedWidth` は、`data-in-box` の枠では `frame.parentElement` を結果のボックスとみなして幅を測る。`DataTable` の ResizeObserver も `frame.parentElement` を見る。`ResultBox` の `kind="table"` の `markContentFrame` は、ボックスの子の幅で横に送るかを決める。

組の div は `display: contents` なので、枠の親が組の div になると、その幅は0になる（試作で確かめた）。すると次のことが起きる。

- `layoutTable` は幅0で何もせずに戻る。表は組んだ印を持たず、3秒隠れる。
- ResizeObserver は幅の変わらない組の div を見るので、組み直しにつながらない。
- ボックスは子の幅0を見て、はみ出す表を送る印を付けない。

3-2 の手順4は、「結果のボックスの中で横に送る表」が組に入る場合を書いている。つまり、`inBox` の表を組に入れられる部品として設計している。今は `inBox` を渡す面が無いので、来訪者には出ない。しかし、部品がこの組み合わせを受け付けたまま壊れていると、次に使う人が踏む。

次のどちらかにし、設計と試験に書く。

- ボックスを探す所（`placedWidth`・ResizeObserver の相手・`markContentFrame` の子の幅）が組の div を飛ばすようにする。
- 組は結果のボックスの `kind="table"` の中に置かない、と決めて部品の説明に書く。

### 5. SKILL.md の項は他のタスクの変更と同じ1行にあり、「自分の塊だけを載せる」ができない（直す・小）

6章は、T5-8b のコミットに自分の塊だけを載せるとする。しかし SKILL.md の「記事の外の表は `DataTable` で組み…」の項は、Markdown で1行の長い段落である。この行には、作業ツリーにすでに別のタスクの変更がある（「セルに置くコントロール（行の頭の開閉のボタン）と中身を見せる見本（色見本）は要素で渡し…」。review-t5-20d.md の指摘2の直し）。

同じ行の2つの変更は、`git add -p` で分けられない。T5-8b の builder が手順どおりにしようとすると、ここで止まる。

次のどれかを 6章に書く。

- その変更を持つタスクが先にコミットし、T5-8b はそのあとにする。
- T5-8b がその変更も一緒に載せ、どのタスクの変更かをコミットの本文と index.md に書く。
- HEAD の行に自分の文だけを足した版を index に置く（`git hash-object -w` と `git update-index --cacheinfo` など）。

`DESIGN.md` の §5 の表の項と `DataTable/index.tsx` の組の部分は、他のタスクの変更と別の塊なので、このままでよい。

### 6. DESIGN.md と SKILL.md に入れる文の置き場所と中身（直す・小）

- **DESIGN.md**: 入れる場所が「表の字の左端は本文の字の左端とそろう。」の直後である。そのため、入れる文の最後の「横に送る表は自分のボックスに入るので、そろえる組に入らない」が、同じ項であとから出てくる「表をボックスに入れ、その中で横に送る」より先に来て、まだ言っていないことを前提にする。「ボックスに入れた表は、ほかのボックスと同じ内側の余白の内に組む。」の後ろに入れれば、項が1つの文章として順に読める。指摘2の直しに合わせて、見出しの列が幅を譲る文も直す。
- **SKILL.md**: 項の今の文「サーバーで描いた表は、枠の前のスクリプトが組み方を定め、枠の直後のスクリプトがその表を組む」は、組の中の表では正しくなくなる（組の直後の文が組む）。この文のあとに「組の最後で1度だけ組み」を足すと、前の文を例外で打ち消す形になり、ツギハギの規則（CLAUDE.md）に当たる。組を含めた形で、この文そのものを書き直す文を設計に書く。`DataTable` の JSDoc の同じ段落（3-4 で直すと書いてあるもの）も同じである。

## 問いへの答え

1. **来訪者の価値**: 1280 で値がラベルのすぐ右から始まるのは、今の広がりより良い。ラベルと値の組が近いほど、どの値がどのラベルのものかを取り違えない。漢字カナールの罫線も、既定の文字サイズではそろう（4-1 の見込み。全2136字に3字の見出しがあることを確かめた）。200% の狭い画面で、ずれを1字以内に留めて値の文節を割らない判断は正しい。「最長連続」は1文節で、そろえるには値の文節を割るしかなく、§4 はそれを許さない。ただし、見出しの列を指定する仕組みのまま規則にすると、狭い画面で長い値が縦に崩れる（指摘2）。1280 で見出しが折れる不具合もある（指摘1）。
2. **`DataTableGroup` は原理に基づくか**: 基づく。どれを続けて読ませるかは書き手が決める中身の単位で、§5 に規則として書き、呼ぶ側は幅を指定しない。自動の組（b2）は、irodori の列の見出しを持つ表を外す例外と、どのボックスにも置く組む文が要り、劣る。ただし組の div の `display: contents` が、ボックスの幅を親で測る今の仕組みと噛み合わない（指摘4）。
3. **サーバーで描いた組の最初の描画**: 表の前後の文の置き方と、組の中の枠で表ごとの文が何もしない決め方は正しい（組の div の開きタグは表より先に届くので、`closest` で見分けられる）。しかし、表のあいだと下の中身は動く（指摘3）。
4. **実装できるか・条件は測れるか**: 組むときの流れ（最初の表の effect が組の全体を組み、あとの表は印で飛ばす。組の effect が表の増減を拾う）は、React が同じ描画のすべての DOM の変更を済ませてから layout effect を動かすので成り立つ。全2136字の数え・AP-I14 の撮り比べ・ブラウザで描く表のフレームの記録は測れる。ただし、指摘1の幅の数え方、指摘2の条件2、指摘3の条件5を直す必要がある。
5. **DESIGN・SKILL の文**: 指摘6と指摘5。§5 の表の項には、他のタスクの未コミットの変更は無い（`git diff DESIGN.md` で確かめた）。index.md の決定 (4) の「最後に終わるタスク」が入れる §5 の文は別の項（ページの割り方など）で、重ならない。
6. **順序**: T5-8b → T5-20d → T5-20f は正しい。部品が先で、使う側（漢字カナールの囲み）が T5-20d のコミットに入り、T5-20f は T5-20d のあとの面を前の版として測る。T5-12 はどちらが先でもよい、とする扱いも正しい。T5-12 があとなら、T5-12 のレビューが T5-8b のあとの表を見る。
7. **釣り合い**: 指摘は、来訪者に見える崩れ（1・2・3）、部品を次に使う人を壊す穴（4）、builder が止まる所（5）、規則（ツギハギ）と文の順（6）に限った。
