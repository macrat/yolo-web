## Major

### Major-1: 文節で折らないブラウザ（Safari）では、語の中で折れ、1字だけの行も残る

PM の決定は「どのブラウザでもそのブラウザで描いた折れを確かめてから幅を決めるので、`auto-phrase` の無いブラウザでも崩れない」を前提にしている。WebKit の近似（箱の文に `word-break: normal`）で測ると、この前提が成り立たない。

| WebKit の近似 | 1字の行 | 横に送る図 |
| ------------- | ------- | ---------- |
| 375・既定     | 0       | 16         |
| 1280・既定    | 0       | 6          |
| 375・200%     | 5       | 19         |
| 1280・200%    | 5       | 8          |

- 200% の1字の行: spawner の「プロンプト取／得」「子プロセス生／成」、nextjs-server-only の「ReactNode／を prop で注／入」、workflow-simplification の図4の「ownerの手作／業」、url-structure の「業界標準に合／致」。漢字の熟語が割れ、最後の1字だけが次の行に落ちる。
- 既定の字の大きさでも、カタカナ語が割れる。1280 の spawner の「ライフサイク／ル管理」「プロンプトテンプレート読み／込み」、workflow-simplification の図1の「owner inboxメモの無断アーカ／イブ」（撮った画像で確かめた）。これは確かめの数に出ない。`lineProblems` は英数字の語の割れしか数えないので、「アーカ／イブ」を読みにくい折れとして捕まえない。
- 1280・既定で横に送る図が 6 になる（Chromium は 4）。playwright-dark-mode と workflow-simplification の図2が増え、workflow-simplification の図1は元の幅が 925 → 1341px に広がる。PM が受け入れた「1〜2 増える」を超える。
- 描き直す回数も増える。spawner は Chromium で 5回、WebKit の近似で 31回描く。

原因は2つある。1つは、確かめの物差し（`lineProblems`）が日本語の語の割れを見ないことで、`auto-phrase` の効く Chromium ではそれが表に出ないだけである。もう1つは、候補の幅（`wrapCandidates`）が「短いかたまりの幅＋1」なので、字のどこでも折れるブラウザでは、長いかたまりが最後の1〜2字だけ溢れる幅ばかりになることである。

来訪者から見ると、iPhone の Safari で読む人（スマートフォンの来訪者の多く）に、PC の Chromium で見るより読みにくい図が出る。字を大きくして読む人には1字の行が出る。

**直してほしいこと**: 日本語の語の割れを、どのブラウザでも同じに数えられる形で確かめる。`Intl.Segmenter("ja", { granularity: "word" })`（Safari 14.1 以降にもある）で語の切れ目を求め、固めた折れが語の途中にあれば `splitWords` に数える、などである。候補の幅にも、長いかたまりを均して折る幅（かたまりの幅の 1/2・1/3 など）を足し、1字の行が出ない幅を選べるようにする。直したあとに、WebKit の近似（`word-break: normal`）で、1280（目次の開閉）と 375 の既定と 200% の、1字の行・禁則・語の割れ（日本語を含む）・横に送る図の数を記録する。PM の決定の前提の文（「`auto-phrase` の無いブラウザでも崩れない」）は、測った結果で言えるようにする。

### Major-2: 折り返しの幅を探すあいだ、ページが数秒止まる

ad8003d は、流れ図を1枚につき何度も描き直して幅を探す。描き直しのあいだにイベントループへ戻らないので、探す全体が1つの長いタスクになる。CPU を 4倍に遅くして最初の図を画面に入れて読み込むと、いちばん長いタスクは次のとおりである。

| 記事                         | 508fa37（375 / 1280） | ad8003d（375 / 1280） |
| ---------------------------- | --------------------- | --------------------- |
| playwright-dark-mode         | 424 / 508 ms          | 2366 / 2933 ms        |
| spawner-experiment           | 444 / 317 ms          | 1581 / 2576 ms        |
| workflow-skill-based         | 791 / 648 ms          | 2309 / 1749 ms        |
| workflow-simplification      | 879 / 1333 ms         | 2485 / 4454 ms        |
| url-structure-reorganization | 525 / 275 ms          | 1159 / 1918 ms        |
| nextjs-server-only           | 382 / 326 ms          | 2028 / 1291 ms        |

1回目の測りでも同じ幅（375 で最大 2704ms）だった。図を描き終えるまでの時間も、375・4倍で 508fa37 の 2.2〜4.5秒から 2.5〜7.0秒に延びた（workflow-skill 3.3 → 7.0/5.7秒、workflow-simplification 4.5 → 7.0秒）。

来訪者から見ると、記事を開いてすぐに目次のリンクや本文のリンクを押しても、2〜4秒反応しない（INP が悪い）。手の届く価格のスマートフォンでは、4倍の遅さは珍しくない。WebKit では Major-1 のとおり描き直す回数がさらに増える。

**直してほしいこと**: 試しの描き直しのあいだに、描くたびにイベントループへ戻る（`await new Promise((resolve) => setTimeout(resolve))` や `scheduler.yield()`）。描き直す回数も減らす。たとえば、折らずに描いた図の、箱の文の幅と図の幅から、収まる見込みの無い候補を描く前に捨てる。直したあとに、375・1280 の CPU 4倍で、記事ごとのいちばん長いタスクと描き終えるまでの時間を 508fa37 と並べて記録する。

### Major-3: 固めた改行が、読み上げで元の文を割る

`freezeLines` は、ブラウザが折った所に `<br data-wrap>` を入れる。`<br>` は読み上げでは行の区切りになるので、支援技術が読む文は元の文と同じにならない。workflow-simplification の図1の `ariaSnapshot` は次のとおりである。

- 「レビュー未完了での完了宣言」→ `paragraph: レビュー未完了での 完了宣言`
- 「ブログ記事の品質基準未達」→ `paragraph: ブログ記事の 品質基準未達`
- 図2: `paragraph: エージェントが 追従しきれない`

Chromium では文節の所で折れるので、区切りは文節の間に来る。ただし Major-1 のとおり、Safari では「取／得」「アーカ／イブ」のように語の中で折れ、VoiceOver はそこを別の行として読む。熟語の読みが変わる（「取得」が「と」「とく」になるなど）。空白の所で折れた行は、空白を消して `<br>` に置き換えるので（`trimEnd`）、文の中身も「ownerinboxメモの無断アーカイブ」になり、ページ内検索で「owner inbox」が見つからない。

PM の条件（固めた改行は読み上げで元の文として読まれる）を満たしていない。

**直してほしいこと**: 読み上げには元の文を渡し、見た目の行だけを固める。たとえば、見た目の行を `aria-hidden` のかたまりにし、元の文を画面に見えない字として添える。空白の所の折れでは空白を残す。直したあとに、固めた図の箱の文を `ariaSnapshot` で読み、元の文（書き手の改行を除く）と一致することを、Chromium と WebKit の近似の両方で確かめる。

## Minor

### Minor-1: `data-wrap` の値を読む所が無い

`freezeLines` は `<br>` に `data-wrap`（空白で折れたら "space"）を付け、コメントは「書き手が入れた改行と見分けられるようにする」と書く。ソースのどこもこの属性を読まない（`grep -rn "data-wrap\|dataset.wrap" src`）。読まれない印は、読む人に「どこかで見分けている」と読み違えさせる。Major-3 を直すときに、使う形にするか消す。

### Minor-2: 探す手順の分岐が、テストの届かない所にある

`renderFlowchart` の中の手順（まず折らずに描く、いちばん狭い幅が収まるかで広い順か狭い順かを決める、段の間隔を広げて試し直す、最後に `chooseWrap`）は、この直しの中心だが、描く処理と混ざっていて単体テストが無い。`chooseWrap` と `wrapCandidates` は試されているが、「どの順に試し、どこで止めるか」は試されていない。Major-2 で描き直す回数を減らすときに、次に描く幅を決める部分を純粋な関数に切り出し、試す順と止まる所をテストする。
