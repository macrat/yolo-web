## 判定: 改善指示

量の帯は §5 のとおりに組まれています。どの幅と文字の大きさでも、同じ並びの枠の左端と幅は行をまたいで同じで、1行の組みの枠は並びの幅の半分以上、半分に届かない並びは全体が2行の組みになり、値は帯の右（2行の組みでは名前の行の右端）にあります。読み上げは行ごとに名前・値・「今回」で、帯と `progressbar` は読まれません。結果のボックスも、太い線・内側の余白・コンテンツ幅いっぱいで、コードと表の見本で枠が二重にならず、1,000行のコードでもコピーのボタンが上端から 11px にあります。

一方で、サーバーで描いた量の帯は、開発のサーバーでは1つごとに水和の不一致のエラーを出します（Major-1）。JavaScript が動かない来訪者には、狭い画面の 200% で帯が潰れ、字がボックスからはみ出します（Major-2）。ほかに、結果のボックスの API と組み方に Minor が6つあります。

## 指摘

### Major-1 サーバーで描いた量の帯が、開発のサーバーで水和の不一致のエラーを出す

開発のサーバー（`next dev`）で `/storybook` を開くと、コンソールに次のエラーが出ます。量の帯の3つの見本のそれぞれで、並びの直後のスクリプトが `ul` に付けた `data-layout` が、クライアントの props に無い属性として差分に出ます。

```
A tree hydrated but some attributes of the server rendered HTML didn't match the client properties. This won't be patched up.
  <ul ... className="QuantityBars-module__..._list ...">
-   data-layout="inline"
```

本番のビルドではこの検査が走らないので、来訪者の見え方は変わらず、属性も残ります（本番のコンソールにエラーは無かった）。しかし、T4-6・T4-7・T4-11〜T4-14 で量の帯をサーバーで描く面を作ると、その面を開発のサーバーで開くたびに Next のエラーの印が出ます。builder とレビューは、そこに本当の水和の不一致が混ざっても見分けられなくなります。jsdom のテストは水和を通さないので、これを捕まえません（AP-I07）。

- `ul` に `suppressHydrationWarning` を付け、なぜ付けるか（サーバーの HTML ではスクリプトが組みを付けるので、属性がクライアントの props と違うこと）をコメントの1文で言う。
- `renderToString` の HTML を置いてスクリプトを動かし（または `data-layout` を付け）、`hydrateRoot` で水和して `console.error` が呼ばれないことを確かめるテストを足す。

### Major-2 JavaScript が動かないと、狭い画面の 200% で帯が潰れ、字がボックスからはみ出す

組みの既定（`data-layout` が無いとき）は1行の組みです。JavaScript を切った Chromium で 320px・200% の storybook を開くと、irodori の見本は1行の組みのままで、枠は 6px（線だけ）になり、並びが 254px とボックスの中の幅 244px を超え、「今回」がボックスの右の線に掛かります。どの帯も同じ 6px の線なので、分布の形はまったく読めません。375px・200% でも枠は 45px（並びの幅の 15%）です。

2行の組みは、どの幅と文字の大きさでも枠が並びの幅いっぱいになり、はみ出しません。測れないときの組みを2行の組みにし、測って1行の組みが半分の決まりを満たすときだけ `data-layout="inline"` を付ける形にすると、JavaScript が動かない来訪者（スクリプトを止める設定・読み込みの失敗）も、いつも読める形で見ます。JavaScript が動くときの見え方は今と同じです。

- CSS の既定を2行の組みにし、1行の組みを `[data-layout="inline"]` に掛ける（`layout.ts` の判定はそのまま）。
- JavaScript を切った 320px・200% と 1280px の既定で撮り、はみ出しが0で分布の形が読めることを確かめる。

### Minor-1 表とコードの結果の横に送る枠に、キーボードで着けない

`kind="table"` は `.body` を、`kind="code"` は中の `pre` を横に送る枠にしますが、どちらも `tabindex` と名前を持ちません。Chromium（130 から）と Firefox は横に送れる枠を自動で Tab に入れますが、Safari は入れないので、Safari でキーボードを使う来訪者は、320px で右が切れる整形した JSON（storybook の見本は 320px で必ずはみ出す）や列の多い表の右を読めません。同じ問題を、ブログの表は設計 5-2 で「はみ出す表だけが枠・`tabindex="0"`・読み上げの名前を持つ」と決めています。結果のボックスの中だけ違う扱いにする理由はありません。

- 表とコードの結果で、横に送る枠を部品の側に持ち（コードは `pre` を中に受けるので、`.body` を送る枠にするか、はみ出しを測って `pre` に付けるかを決める）、はみ出すときだけ `tabindex="0"` と名前を付ける。名前の文言は 5-2 と T7 に合わせる。
- 決めきれないなら、planner に設計（2-1 と 5-2 のつながり）で決めさせる。

### Minor-2 名前を必ず持つはずの型が、名前の無いボックスを通す

`ResultName` の `caption` は `ReactNode` なので、`undefined`・`null`・`false`・`""` を渡せます。`heading` を持たずに `caption={undefined}` と書くと型が通り、`section` の `aria-labelledby` は無い要素を指し、名前の無い region になります。`caption={null}` では空の `p` が描かれ、名前が空になります。型のコメントが言う「必ず持つ」が型で守られていません。

- `caption` の型を `string` にする（見本と設計の例はどれも文）。JSX が要る場面があるなら、`null`・`undefined`・真偽を外した型にする。

### Minor-3 ページを開いたときに初めからある結果のボックスも、登場の動きを持つ

登場の動きは `.box` に常に掛かるので、サーバーで描いた HTML に初めからあるボックス（入力の初めの値で結果を出す道具・T4-15 の見本など）も、ページを開くたびに 300ms かけて現れます。来訪者の操作に応えたものでない、開いたときの一律の fade-in で、§11 の「一律の fade-in を持たない」に当たります。結果の登場は操作への応え（§11・6-4）なので、動くのは操作で現れたボックスだけにするのが §11 の趣旨に合います。

- 水和で引き継いだボックス（サーバーの HTML にあったもの）は動かさず、ブラウザで新たに描いたボックスだけを動かす（水和の最初の描画で決めた値を `useState` に留める、など。`QuantityBars` の `useIsServerRendered` と同じ見分け方が使える）。テストを足す。
- 設計で決めるべきと判断するなら、planner に 2-1・6-1 に書かせる。

### Minor-4 頭の行で、補助情報の行とコピーのボタンの字の高さがずれる

`.head` は `align-items: flex-start` なので、44px の押せる範囲の中ほどにあるボタンの字（「コピー」）が、補助情報の行（「整形した JSON」）より約 9px 下に出ます（375px の撮影）。同じ行に並ぶ2つの字の高さが揃わず、ボタンが頭の行から落ちたように見えます。

- 名前の1行目とボタンの字の並びを揃える（`align-items: baseline` など）。名前が見出しのときと、補助情報だけのときの両方を 320・375・1280px で撮って確かめる。

### Minor-5 ソースのコメントがサイクルのタスクの名を指す

`StorybookContent.tsx` の `voiceOverSamples` の説明（「T9 で VoiceOver の読み上げを比べるタイプ名」）と、`page.tsx` の `VOICE_OVER_TYPE_IDS` の説明（「T9 で iOS の VoiceOver に読ませて比べるタイプ」）が、cycle-316 のタスクの名を指します。T9 が終わると何を指すか分からない語になり、ソースに経緯を残さない決まり（CLAUDE.md のツギハギ禁止）に反します。

- 「iOS の VoiceOver で見出しの読み方を聞き比べるタイプ名」のように、見本の目的だけを言う。

### Minor-6 irodori の 320px の見立てが記録されていない

完了の条件は「irodori の見本を 320px の既定で撮り、2行の組みの10行で分布の形を一目で見られるかを記録する」ですが、画像（`tmp/cycle-316/t4-3/irodori-320-default.png`）があるだけで、見立ては t4-design.md にも index.md にもありません。`tmp/` は追跡されないので、T4-14 で irodori の統計を組む builder が拠り所にできません。

レビューの見立て: 2行の組みでは、どの帯も並びの幅いっぱいの枠を持つので、行どうしの長さの差（とくに「50〜59点」がいちばん長いこと）ははっきり読めます。ただし 10 行で並びは約 640px になり、375×667 では見出しと並びの全体が1画面に入らず、形の全体を見るには送る必要があります。T4-14 で、結果のボックスの中のほかの内容と合わせて、画面の中にどこまで入るかを測る必要があります。

- この見立て（builder の見立てと合わせて）を、PM が t4-design.md の末尾の決定の節か index.md の補足に残し、T4-14 の確かめに渡す。

## よかった点

- 量の帯の組みを、字そのものの幅を Range で測って決めるので、どちらの組みで描かれていても同じ判定になり、組み直しが組み直しを呼ばない。ResizeObserver が見る要素の選び方（目盛りと値・「今回」の列）の理由もコメントで言えている。
- 帯の上限・0の行・「今回」の列の幅・値の形は §5 と 3-1 のとおりで、テストも来訪者に見える結果（塗りの割合・読み上げの並び・列の有無）を確かめている。
- `ResultBox` は `className` を受けず、ref と `tabIndex` だけを渡せるので、面ごとに見た目がずれにくい。
