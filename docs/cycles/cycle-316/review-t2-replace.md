## 指摘

### Minor-1 選択肢のラベルが、狭い幅で語の途中で折れる。長いラベルは細切れになる

f83d0e2 は、選択肢のラベルに `word-break: auto-phrase` を足し、「選択肢のラベルを文節で折る」とした。しかし、ひとつの文節が行に収まらないと、Chrome は文節の中で折る。その結果、狭い幅では語の途中で折れる。

- `/tools/line-break-remover` の 320px: 「PDFスマートモー／ド」（`tmp/review-t2-replace/line-break-remover-320-light.png`）
- `/tools/image-resizer` の 320px（画像を読み込んだあと）: 「パーセント指／定」（`image-resizer-320-light.png`）

逆に、長いラベルは文節ごとに行が切れて、細切れになる。storybook の 8番の見本「ラベルが長く、狭い画面で2行に折り返しても、四角は1行目の字の中央に並ぶ」は、320px で5行になった（`sb-cr-320.png`）。道具のラベルは短いものが多いので、細切れが目に付くのはいまはこの見本だけである。それでも、長いラベルを持つ組が来れば同じことが起きる。

来訪者から見ると、「スマートモー」「指」で行が終わるのは、コミットが防ごうとした読み違えそのものである。

**直し方**: builder が、ラベルの折り方を決め直す。たとえば次の手がある。どれを採ったかと、その理由をコメントに書く。

- 文節が行に収まらないラベルは、語の区切りに `<wbr>` を置く
- 並びの幅を詰めている入れ子の余白を見直す（image-resizer は、ボックスの中にもう1つボックスがある）
- 通常の禁則に戻したうえで、上の2本のラベルを見直す

どの形でも、上の3か所を 320px で撮り直して確かめる。

### Minor-2 種別を「・」でつなぐと、語の中の「・」と区別できない

`Shinagaki`・`DictionaryEntryList`・`BlogList` は、複数の値を「・」でつないで1行にする。つなぐ値のほうにも「・」を含む語がある。

- ブログ: 「日本語・文化・6分で読める」（`/blog/category/japanese-culture`。`tmp/review-t2-replace/bloglist-375.png`）。カテゴリ「日本語・文化」と読了時間の2つが、3つの語に見える。
- 四字熟語辞典の検索結果: 「対立・闘い・上級」。カテゴリ「対立・闘い」と難易度の2つが、3つの語に見える。

§7 は、種別を「それが何の仲間かを一語で言う」と定める。来訪者が種別を一語として読み取れないのは、この規定の目的に反する。

**直し方**: builder が、値のあいだの区切りを、語の中に現れない形にする。たとえば、全角の空白で分ける、読了時間のように種別でない値は別の要素にする、などがある。上の2か所を撮り直して確かめる。

### Minor-3 自前で書いた値札が、結果のあとの案内とおすすめの一覧に残っている

f83d0e2 は、`Nefuda` を import していた7か所を文字に置き換えた。しかし、`Nefuda` を使わずに同じ形を自前で書いた値札は、次のとおり残っている。

- `src/play/_components/RecommendedContent.module.css` の `.badge`: 13px の枠付きのカテゴリ。同じファイルの冒頭のコメントは「罫で囲んだ小さなラベル」に書き換えた。一方で、70行目は「カテゴリの値札」のままである。
- `src/blog/_components/BlogList.module.css` の `.newMark`: 12px・`--accent`・太字の「新着」。f83d0e2 は同じ行の値札を文字にしたが、これは残した。t2-inventory.md §2-2 は、これを「値札・印に似た表示」に挙げている。

どれも一覧の行の中の種別か補助情報なので、同じサイトで、枠付きの 11〜13px と、枠なしの 14px が混在する。コミットメッセージの「一覧・結果の値札を --ink-2 の補助情報の文字にし」とも合わない（AP-WF04）。t2-inventory.md §2-2 は、ほかに `EmailValidatorTile` の `.badge*` と irodori `FinalResult` の `.rankBadge` も挙げている。

**直し方**: builder が、上の3つを f83d0e2 と同じ形（枠と地を持たない 14px の `--ink-2`）にする。「新着」を朱の色で示さない形も、同時に決める。`EmailValidatorTile` と `rankBadge` を T2 で扱うか T4・T5 に回すかは、PM が決めて index.md に書く。

ラジオボタンの行は 44px の高さを持ち、組ごとに見出しの行が付く。そのため、絞り込みを持つ道具では、狭い画面で絞り込みが縦に長くなる。四字熟語辞典の検索（`/tools/yoji-search`）では、画面の高さを 667px にして測ると次のようになった（`tmp/review-t2-replace/yoji-search-320-dark.png`）。

### Minor-6 「種別」と呼んでいるものの多くが、§7 の種別ではない

f83d0e2 は、値札をすべて「種別」と呼び替えた（`.kind` のクラス名、`ShinagakiItem.tags` の JSDoc、各ページのコメント）。しかし、渡している値の多くは、§7 の種別（「それが何の仲間かを一語で言う」）ではない。件数（「58語」「40色」）、問題数（「全10問」）、所要時間（「6分で読める」）、画数（「4画」）、カラーコード（HEX）、更新の頻度（「毎日更新」）がそうである。

### Minor-7 決めたことが記録されていない。道具のあいだで組の見出しが揺れる

**記録について**

- **前回 Minor-5（選ぶ欄の候補の hover）**: 前回は「PM が決め、planner が §6 か §8 に書く」を求めた。67c563a は候補に hover の細い線を出した。しかし、`DESIGN.md` にも index.md の補足事項にも、決めたことが書かれていない。§6 は「書き込む欄と選ぶ欄は hover で見え方を変えない」のままである。index.md の補足事項は「選ぶ欄の下向きの印・候補の選択済みの印…は、ブラウザの既定のままにした」と書き、候補の hover には触れていない。そのため、実装だけを見ると §6 に反して見える。
- **見た目**: 候補の枠と hover の線が同じ細い線なので、端の候補（最初と最後）の hover は、候補の枠と重ならない1辺だけが見える。その結果、囲みではなく区切りの線に見える（`tmp/review-t2-replace/select-hover-375.png`。真ん中の候補は囲みに見える: `select-hover-mid-375.png`）。
- **セグメント切替・値札の置き換え**: トグルスイッチの置き換えは、index.md の補足事項に理由とともに書かれている。セグメント切替をラジオボタンの組にしたこと、組の名前を見える見出し（`legend`）で持たせ入力欄のラベルと同じく上に置いたこと、値札を「・」でつないだ補助情報の文字にしたことは、どこにも書かれていない。§5 の「ラベル」は、ラジオボタン1つのラベルを「横に置く」と定める。一方で、組の見出しの置き場所は定めていない。

**組の見出しの揺れ**

- 同じ「エンコード／デコード」の組を、base64・html-entity・image-base64 は「変換モード」、url-encode だけ「変換方向」と呼ぶ（§12 位置の一定）。
- cron-parser の「モード」（解析／ビルダー）は、何のモードかを言わない。
- storybook の13番は、aria-label の見本を「単位（秒／ミリ秒）」で見せる。しかし、実際にこの組を持つ unix-timestamp は、見える見出し「単位」を使う。20本のどれも aria-label の形を使っていない。

**直し方**:

- 端の候補の hover が区切りに見えないよう、builder が hover の線の出し方を見直す。たとえば、候補の枠の内側に 1px あけて囲む。

- builder が、url-encode の見出しを「変換モード」に揃え、cron-parser の見出しを中身の分かる語にする。storybook の aria-label の見本は、実際に使う場面に合わせる。使う場面が無いなら、aria-label の形を部品から除くことも考える（AP-I02）。
