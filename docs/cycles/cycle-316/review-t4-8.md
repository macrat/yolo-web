## 指摘

### Major-1 「電車運 定時運行」の説明が、人身事故に来訪者自身が遭うことを冗談にしている

`src/play/fortune/data/daily-fortunes.ts` の `densha` の説明は「今日のあなたは電車のように正確です。予定通りに物事が進みます。ただし人身事故で遅延する可能性があります（自分の）。」です。日本語の「人身事故」は、鉄道では人が列車にひかれる事故（多くは命にかかわるもの）を指し、「（自分の）」はそれに読んだ本人が遭うことを言っています。身近な人をその事故で亡くした来訪者や、つらい時期にいる来訪者がこの運勢を引けば、占いの冗談として受け取れず、傷つきます。constitution の 2「人を傷つけたり悲しませたりするものを作らない」に反します。

このファイルは T4-8 が受け持ち（t4-design.md の受け持ちの表の `src/play/fortune/`）、builder も誤字を直すために触っているので、ここで直します。説明の文だけを変え、運勢の名（来訪者に渡した結果の名前）は変えません。たとえば「ただし隣の人の寝過ごしに巻き込まれて、一駅乗り過ごす可能性があります。」のように、電車にまつわる害の無い小さな失敗にします。60件のほかの文は読んだかぎり、この種の問題はありません（ほかの件は Minor-6）。

### Minor-1 `DailyFortuneCard.test.tsx` の後半に、経緯のコメントと、ソースの字を調べるだけのテストが残っている

builder はこのファイルの冒頭の説明を書き直していますが、後半の `describe("DailyFortuneCard Hydration Error prevention (source code verification)")` はそのままです。

- コメントが経緯を語っています（「修正後は useSyncExternalStore を使い」「旧パターン (useEffect + setState) は使われていないこと」「Hydration Error の原因: useState(computeInitialFortune) の lazy initializer は…」）。CLAUDE.md の「ツギハギ禁止」は、触ったファイルに過去の経緯を見つけたらその場で直すことを求めています。
- テストの中身は、ソースの文字列に `useState(computeInitialFortune)` や `setState(computeInitialFortune())` が無いこと、`useSyncExternalStore` と `getFortuneServerSnapshot` の字があること、を正規表現で見ているだけです。もう存在しない関数名が無いことを確かめても何も守らず、書き方を変えれば同じ振る舞いでも落ち、振る舞いが壊れても字が残っていれば通ります。

守りたいのは「サーバーの描画と最初の描画では運勢を描かず、占っていることを字で言う」という振る舞いなので、`react-dom/server` の `renderToString` で `DailyFortuneCard` を描き、「運勢を占っています」を含み、運勢の名・説明を含まないことを確かめる1つのテストに替え、ソースを読むテストと `readFileSync`・`SOURCE_PATH` を消します。ストアのキャッシュ変数が部品の中に無いことは、import の形でなく振る舞い（同じ日に2回描いても同じ運勢）で見るか、要らなければ消します。

### Minor-2 読み込み中の「...」と、「明日も来てね!」の約物が §4 と違う

書き直した部品が描く文のうち、次の2つが §4「約物」（三点リーダは「……」、感嘆符の後は全角アキ）に合っていません。どちらも JavaScript が動くまでの画面と、共有のすぐ下に、来訪者に見える字です。

- 読み込み中: 「運勢を占っています...」（半角のピリオド3つ）→「運勢を占っています……」
- 結果の下: 「明日も来てね! 毎日運勢が変わります」（半角の「!」と半角の空白）→「明日も来てね！　毎日運勢が変わります」

共有の文（`shareText` の「でした!」）も、サイトが書く文として（§9「サイトが書くすべての文章にかかる」）全角の「！」にそろえます。テストの期待の文字列も合わせて直します。

### Minor-3 日付の変わり目を過ぎても、開いたままのページは前の日の運勢を出し続ける

`fortuneStore.ts` の説明は「日本時間の日付が変わったらキャッシュを捨てるので、真夜中を過ぎてページを開いたままの来訪者も、いつも今日の正しい運勢を見る」と言っていますが、`subscribeFortuneStore` は購読を受けるだけで、日付が変わっても誰にも知らせません。`useSyncExternalStore` はこの部品が描き直されるときにしか `getFortuneSnapshot` を呼ばないので、タブを開いたまま翌朝に戻った来訪者には、前の日の運勢と前の日の日付の行が出たままです（その下に「明日も来てね」とある）。

T4-8 の受け持ち（`src/play/fortune/`）の中なので、ここで直します。購読のあいだ、次の日本時間の 0 時にタイマーを掛けて購読者に知らせる（タブが裏にあって遅れた場合に備え、`visibilitychange` で見えたときにも知らせる）形にすると、説明のとおりになります。タイマーは購読の解除で止めます（AP-I11）。直さないなら、説明から事実でない約束を消します。どちらにしても、説明が振る舞いと食い違ったままにはしません。

### Minor-4 星の数が評価の切り捨てで決まり、4.8 と 4.0、2.9 と 2.0 が同じ星に見える

`StarRating` は ★ の数を `Math.floor(rating)` で決めています。60件の評価には x.6〜x.9 が 23件あり（4.8 の猫運、4.7 の風鈴運、2.9 の消しゴム運など）、これらは星だけ見ると 1つ近く低く見えます。星は一目で良し悪しを読むためのもので、数字は端数を言うためのものなので、星は評価にいちばん近い数にするほうが、来訪者が一目で受け取る印象と値が合います。t4-design.md 3-3 は「半分の星は ☆ と同じ形なので数字を残す」とだけ決めていて、切り捨てか四捨五入かは決めていません。

星の数を四捨五入（`Math.round`。2.5 は ★3つ）にし、部品の説明とテストの表（`test.each`）をそれに合わせます。星が数字と1つ食い違って見える件（4.8 の ★★★★☆ など）がなくなり、残るのは 0.5 の端数の丸めだけです。

### Minor-5 評価の数字の桁が運勢によってそろわない

評価が整数の運勢（信号運 5、雲運・のれん運 4、コンパス運・扇風機運 3、の5件）は「(5)」「(4)」、ほかは「(4.4)」のように出ます。毎日違う運勢を見る来訪者には、同じ物差しの値が日によって違う形で出ます。読み上げも「5つ星のうち4」と「5つ星のうち4.4」が混ざります。

数字を小数第1位までの形（`toFixed(1)` で「(4.0)」「(5.0)」）で出し、読み上げの名前と共有の文（「(4.0/5)」）も同じ形にします。形を作る関数を1つにし、3か所がそれを使います。

### Minor-6 「電柱運」の今日のアクション「すべての移動を後ろ歩きで行う」が、そのまま行えば危ない

今日のアクションは、来訪者に「やってみる」ことを勧める欄です。「すべての移動を後ろ歩きで行う」は、道路や駅の階段で行えば転倒や事故につながります。ほかの運勢のアクションは、どれも行っても害の無いこと（お辞儀・つぶやく・眺めるなど）にとどまっていて、信号運は「実際の交通信号については責任を負いかねます」とわざわざ断っているので、この1件だけが外れています。Major-1 と同じく、名前は変えずに文だけ、「家の中で一度だけ後ろ歩きをしてみる」のように安全な範囲に収まる言い方にします。
