## 指摘

### Major-1: 伝統色の名前の欄のラベルが「読み」で探せると言うが、仮名の読みでは1色も当たらない

**どこで何が起きているか**: `/dictionary/colors` の名前の欄のラベルは「色名・読み・カラーコードで探す」だが、探しているのは色名・ローマ字（`romaji`）・カラーコードである（`color-list.ts` の `colorListItems`、`readings: [color.romaji]`）。「あい」と打つと「条件に合う色はありません（全250色）」になる。「藍」なら6色、「ai」なら当たる。「とき」も0件で、「toki」なら鴇が出る。変更前の検索は、プレースホルダで「色名・ローマ字・カラーコードで検索...」と言っていた。

**来訪者にどう効くか**: 伝統色の名前は「鴇」「纁」「礪茶」のように漢字で打ちにくいものが多い。読みを知っている来訪者ほど、ラベルに従って仮名で打つ。ところが結果は0件で、この辞典にその色が無いと受け取って離れてしまう。ラベルは §7「何で探せるかは欄のラベルが言う」の要で、来訪者が最初に読む約束が守られていない。

**直し方**: 少なくとも、ラベルを探せるものに合わせる（「色名・ローマ字・カラーコードで探す」）。t3-design.md 3-1 の探す字とラベルの表も同じに直す。できれば、ローマ字から仮名の読みを作って探す字に足し、「あい」「とき」で当たるようにする。データのローマ字には「cyohsyun」「taikoh」のように表記の揺れがあるので、仮名を足すなら、変換の結果を250色すべてで確かめる。どちらにするかは、来訪者の価値で PM が決め、設計書に残す。

### Minor-1: `/dictionary` の行から辞典ごとの収録数が消え、漢字の説明が一覧で探せない「意味」を約束している

- **収録数**: 変更前の `/dictionary` は、各行に「2136字」「400語」「250色」「30語」を補助情報として出していた。いまは件数の行の「全4件」だけで、どの辞典がどれだけの規模かが見えない。収録数は辞典を比べて選ぶ手がかりで、§7 の補助情報（「項目を比べて選ぶ手がかりになる短い値」）そのものである。コミットのメッセージも「辞典ごとの件数の行を出す」と言っていて、実物と食い違う。補助情報に「2,136字」「400語」「250色」「30語」を戻す（桁区切りを付ける）。
- **漢字の説明**: 「常用漢字を、読み・意味・画数・部首から引けます。」の「意味」は、T3-7 の一覧で探す字から外した（英語の語なので）。一覧に意味で引ける道は無い。行の説明を、いま引ける道（字・読み・熟語、学年・画数・部首）に合わせる。「由来つき」を直したのと同じ種類の食い違いである。

### Minor-2: 伝統色のトップの説明が、一覧に無い「RGB/HSL」と「カテゴリ別に検索」を約束している

`colorListDescription` のトップの文「色名・ローマ字・カラーコード（HEX/RGB/HSL）をカテゴリ別に検索できます。」は、検索結果と SNS のカードにそのまま出る。しかし一覧の行が見せ、名前の欄が探すのは HEX だけである。色みは索引で移る別のページで、「カテゴリ別に検索」もしない。色みのページの説明は今回「色見本とカラーコードを見比べられます」に直しているので、トップも同じ考え方で直す（例「日本の伝統色250色の一覧。色見本・色名・ローマ字・カラーコードを並べ、色みや明るさの順で見比べられます。」）。review-t3-7 の Minor-2 と同じ種類の指摘である。

### Minor-3: 色み順で、色みの薄い白・灰・黒が鮮やかな色の途中に1色だけ挟まる

データの色みは有彩色なのに、ほとんど色を持たない色（OKLCH の C が 0.02 未満）がある。その色相は測れても目には見えないので、色相で並べると前後の色とつながらない。

| 色                       | 色み             | C            | 並んだ位置                         |
| ------------------------ | ---------------- | ------------ | ---------------------------------- |
| 黒橡 `#0b1013`（ほぼ黒） | 青系             | 0.010        | 露草と勿忘草（明るい空色）のあいだ |
| 白練 `#fcfaf2`（ほぼ白） | 黄系             | 0.011        | 菜種油と刈安のあいだ               |
| 胡粉 `#fffffb`（ほぼ白） | 黄系             | 0.005        | 鶸茶と溝鼠のあいだ                 |
| 溝鼠・白鼠・銀鼠         | 黄系・緑系・青系 | 0.009〜0.013 | 同じく色の流れの途中               |

**来訪者への効き方**: 色の移り変わりで並びを読み取る一覧（3-1「並んだ色の移り変わりで何の順かが分かります」）で、そこだけ流れが切れる。見た目の違和感は小さくないが、影響は6色に限られる。

**直し方の候補**: 有彩色の色みの中でも、C が小さい色を色相を持たないものとして扱い、その色みの最後に明るい順で置く。色みそのものを無彩色へ直すことも考えられるが、それはデータの見直しになる。どちらにするかを planner が決め、2-6 に書く。

### Minor-4: 文字サイズ 200% の 320px で、漢字の索引の見出し「部首（198）」が括弧の前で折れる

索引の見出しを区切りの見出しと同じ `max(--text-heading-sub, 1.49rem)` にしたため、200% では 47.68px になる。その結果、320px のコンテンツ幅（266px）に収まらなくなった。「部首」と「（198）」が2行に分かれ、その直下に同じ大きさの「1画」が続く（`tmp/cycle-316/rv38/shots/kanji_320_200_bushu.png`）。

これは §4「括弧の前後で折らない」に当たる。しかも「（198）」が行頭に来て「1画」と並ぶので、「（198）」がどちらの見出しの添え書きか読み取りにくい。

横にはみ出さない点は §12 を満たしている。見出し全体が1行に収まらないときにどこで折るかを、DESIGN.md §4 の例外として書くか、語の数を見出しの下の行に分けて組むかを決める。影響は 200% の狭い画面に限られるので Minor とした。

### Minor-5: 一覧のページの外枠の CSS が5つの部品に同じ形で写されている

`YojiListView.module.css`・`ColorListView.module.css`・`HumorListView.module.css`・`KanjiListView.module.css`・`BlogListView.module.css`（と `src/app/dictionary/page.module.css`）は、どれも同じ `.view`（縦積み・16px の間隔）・`.title`・`.description` を持つ。一覧の上の索引を共有の部品にしたのと同じ理由（§12 位置の一定を1か所で守る）が、ページの外枠にも当てはまる。1か所の値を変えたときに、ほかの一覧が取り残される。T3 のどこかで、一覧のページの頭（パンくず・見出し・導入の文・索引・一覧の積み方）を共有の部品にする。T3-8 の中で直すか、T3-11 の前にタスクを立てるかを PM が決める。
