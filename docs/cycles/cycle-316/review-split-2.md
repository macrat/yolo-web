### 4. 完了の処理の順と、hook の下で使うコマンドが書かれておらず、取り違えの余地が残る（中。split-plan.md 2・4、cycle-completion の手順7・8）

依頼の「手順のコミットを main に入れたあと main を design-rollout にマージする流れで、衝突や取り違えが起きないか」について確かめた。決めた中身は正しい。ただし、手順の順が書かれていない。

- **最も重い取り違えは、完了のコミット（T1〜T5 の実装を含む）を main に push してしまうこと**である。手順のコミットは main（`origin/main`）の上に別に作る必要がある。そうしないと、スキル・`deploy.yml`・candidates.md だけでなく、backlog も手で直すことになる（ブランチの backlog をそのまま持ち込むと、main に「B-663 Done」などの出荷していない記述が入る）。push の前に `git diff --stat origin/main..HEAD` が5つのパスだけを示すことを確かめる、と書いておくとよい。
- **最初の push では CI が走らない。** `design-rollout` に完了のコミットだけを push した時点では、そのコミットの `deploy.yml` にはまだ `design-rollout` が無い（`deploy.yml` の変更は手順のコミットにだけ入るので）。CI が走るのは、main をマージしたコミットを push したときである。cycle-completion の手順8の `wait-for-ci.sh`（既定は HEAD）は、そのマージのコミットで走らせる。main への push（本番へのデプロイも起きる）の CI も確かめる。
- **衝突の解き方**: split-plan.md 2 は「衝突が出たときは `design-rollout` の側を取る」とする。backlog は、両方の側が B-754 の行を変え、`design-rollout` の側が隣の B-755 の行を消しているので、衝突する見込みが高い。candidates.md も、ファイルの末尾で衝突する。ところが、`git checkout --ours/--theirs` は `block-destructive-git.sh` が止める。Edit で解くか、`git merge -X ours` を使うかを書く。
- **途中の作業の分け方**: cycle-completion の手順7は「すべてのファイルをコミット」「`git add .`」とする。split-plan.md 4 は途中の作業を除く。どうやって除くか（例: 途中の作業のパスを `git stash push -- <パス>` で退けてから完了のコミットを作り、push し、`git stash pop` で戻して `design-rollout-wip` に積む）が無い。`pre-push-check.sh` は push の時点の作業ツリーでフルスイートを走らせる。途中の作業が作業ツリーに残ったまま `design-rollout` に push すると、完了のコミットでなく途中の作業を検査することになる。

直し方: split-plan.md に「cycle-316 の完了の手順」を、番号付きの順で書く。たとえば、(1) 途中の作業を退ける → (2) 完了のコミット → (3) `design-rollout` を作って push → (4) `origin/main` から手順のコミットを作り、差分が5つのパスだけかを確かめて main に push し、CI を確かめる → (5) main を `design-rollout` にマージし、衝突を Edit で解いて push し、CI を確かめる → (6) 途中の作業を戻してタスクごとに `design-rollout-wip` に積んで push する。

### 5. 分割の決定を、オーナーの指示に帰している（中。AP-WF24。index.md・split-plan.md）

オーナーの言葉は「サイクルを分割できないか検討してください。途中でデプロイできずとも構いません。その場合は…」である。分割するかどうかの検討を PM に求め、分割する場合の進め方を指定している。しかし、文書は分割そのものをオーナーの決定として書いている。

- split-plan.md 16行は「オーナーの指示（2026-10-01）: サイクルを分割する。」と言い換えている。
- index.md の作業内容は「オーナーの指示（2026-10-01）で、…分けることにした」、キャリーオーバーの頭は「（…オーナーの指示 2026-10-01）」としている。

AP-WF24 は「判断…の駆動源を Owner に帰属させていないか」を問う。分割すると決めたのは PM である（split-plan.md の「何が起きたか」がその根拠を書いている）。

直し方: オーナーの言葉を原文のまま引き、「これを受けて PM が分割すると決めた（根拠は「何が起きたか」）」と書く。ブランチの運用（main と別のブランチで続け、完成してからマージする）は、オーナーの指定として書いてよい。

### 6. 「rebase ではなくマージ」の理由の書き方が不正確（軽い。cycle-kickoff の手順1・split-plan.md 3）

cycle-kickoff の手順1は「rebase ではなくマージのコミットにします。最後に main へ戻すときの衝突を小さく保つためです」と書いている。最後の衝突を小さく保つのは、キックオフのたびに main を取り込むこと（取り込む頻度）である。マージか rebase かの選び方ではない。rebase を避けるべき本当の理由は、`design-rollout` が push 済みで、次のセッションと共有しているブランチであることだ。rebase すると force push が要り、それは `block-destructive-git.sh` が止める。split-plan.md 3 の書き方も同じ趣旨なので、合わせて直す。

### 7. 細かな記述の正確さ（軽い。split-plan.md・candidates.md）

- split-plan.md 5行の「週の利用上限に2回達した」は、AP-WF43 の発生の事実にもなっている。しかし、リポジトリのどこにも記録が無い（index.md の一時停止の記録は「Owner の指示で一時停止」とだけ書いている）。出どころ（いつ・何で分かったか）を書く（AP-WF27）。
- AP-WF43 の発生件数は「1サイクルで進める案の代償に作業の量だけを数えた」と書いている。しかし、split-plan.md 7行と options.md の「A の代償」は、作業の量に加えて「そのあいだ他の修正を出荷できないこと」も数えている。「長いサイクルそのものの費用（中断・往復）を数えなかった」と書けば、split-plan.md と食い違わない。
- split-plan.md 3 は「サイクルが main に別の修正を並行して出すことはない」とする。cycle-kickoff の手順1のとおりにすると、B-754 以外の項目（B-746・B-685 など）を選ぶサイクルも `design-rollout` の上で進み、出荷は最後のマージまで待つことになる。これを意図しているならそう書く。本番で急ぎの不具合（セキュリティなど）が出たときにどこへ出すかも、一言決めておく（main に出してキックオフで取り込む、など）。
