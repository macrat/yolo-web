## 指摘

### Major-1 統計の分布の帯を `--paper-2` で塗ると、分布の形がほぼ見えない。§2 の「`--paper-2` は境界を担わない」とも食い違う

- **どこが**: §2 の `--paper-2` の用途の「統計の分布の帯の地（§8）」と、§8 の「当てるまでの回数ごとの帯を `--paper-2` で塗り、今回の帯だけを `--ink` で塗って」。設計 3-1 と8章の「食い違わない理由」（「どれも背景の調子を変えるだけで、境界を担わない」）も同じ前提に立っている。
- **何と食い違うか**:
  - 分布の帯は、帯の長さが回数を表すグラフで、帯の右端が情報を運ぶ境界になる。§2 の「`--paper-2` は背景の調子を変えるだけで、境界を担わない。境界は罫線が担う」と正面から食い違う。
  - 語の食い違いもある。§2 は「帯の**地**」と書くが、§8 は帯そのものを `--paper-2` で塗るので、地（下敷き）ではない。
- **数**:
  - `--paper-2` の帯と `--paper` の地のコントラストは、ライトで 1.12:1、ダークで 1.14:1 しかない。
  - いまの `--ink-2` の帯は 7.55:1（ライト）・8.15:1（ダーク）ある。
  - 回数の字が帯の外にあるので、数そのものは読める。WCAG 1.4.11 の上では、帯が情報に必須とまでは言えない。
- **来訪者にどう効くか**: 解き終えたゲームの来訪者は、これまでの成績の分布の形を一目で見たくて統計を見る。いまはその形が見えているが、変更後は 1.1:1 台の帯になり、とくにダークのスマホや屋外では、`--ink` の今回の帯だけが浮いた、ほぼ数字の列になる。変更前より悪くなる。
- **直し方**（planner が設計 3-1 と8章を直し、builder が `DESIGN.md` を直す）: 帯の長さが読める形にする。候補は次の2つ。
  - (a) Major-2 の「量を見せる帯」と同じ部品にする。太い線で囲んだ `--paper-2` の地を、いちばん多い回数に対する割合だけ `--ink` で塗る。今回の行は「今回」の字で示す。
  - (b) どの帯も枠を持たずに `--ink` で塗り、今回の行は「今回」の字と太字の回数で示す。

  どちらでも、PM が決めた「回数の字は帯の外」はそのまま生きる。375px のライトとダークで撮り比べて決め、§2 の用途の語も合わせて直すこと。

### Major-2 理系思考タイプ診断のスコアの帯の規定が `DESIGN.md` に無く、§6 の読み分けでは「進み具合の帯」になる

- **どこが**: 設計 3-3 は「スコアの帯は、§5 の進み具合の帯と同じ形（太い線で囲んだ `--paper-2` の地を `--ink` で塗る）で組む」と決め、T4-6 がそれを実装する。`DESIGN.md` にはこの部品が無い。builder は、書かなかった理由を挙げている。
- **何と食い違うか**:
  - §6 の太い線の読み分けの表は、「中を左から `--ink` で塗る → 進み具合の帯（§5）」とする。
  - その §5 の進み具合の帯の規定は「いまの問が全体の何番目か」を見せ、左に「3 / 10」を添え、「塗りと数と読み上げは同じ数を言う」とする。どれもスコアには当てはまらない。
  - スキルの「`DESIGN.md` に無いコンポーネントを足したくなったら、先に `DESIGN.md` へ書く」にも、T4-6 が守れなくなる。T4-6 の前に書くのは T4-1 の受け持ちである。
- **来訪者にどう効くか**:
  - T4-6 の builder が、`DESIGN.md` の「進み具合の帯」を部品として当てるおそれがある。T4-14 がそれを `src/components/ProgressBar/` に移し、その部品は `role="progressbar"`・`aria-valuetext="{total}問中{current}問目"` を持つ。当てれば、スクリーンリーダーの来訪者は自分の結果のスコアを「進行状況」として聞く。
  - 見た目の上でも、同じ形が「設問の進み」と「結果の量」の2つの意味を持ち、§6 の「形で読み分ける」が崩れる。
- **直し方**: §5 に、量を見せる帯（例「量の帯」）を1項目として書く。書くことは次の4つ。
  - 形は進み具合の帯と同じにする。
  - 見せるものは「上限に対する量」で、軸の名前と値を字で添える。
  - 読み上げは量として言う（`meter` 相当）。
  - 結果の中では、ボックスと一緒に出て、自分の登場の動きを持たない（§11）。

  §6 の表の行は「進み具合の帯・量の帯」にする。Major-1 の (a) を採るなら、統計の分布もこの項に入る。8章の表にも行を足すこと。

### Major-3 §11 の `prefers-reduced-motion` の規定が、判定の動き（設計 6-2）と、いまの実装を覆っていない

- **どこが**: §11 の末尾は「`prefers-reduced-motion` のとき、自動で始まる動きは止まる。結果の登場は即時表示になる」と、止まるものを列挙している。builder は、書かなかった理由を挙げている。
- **何と食い違うか**:
  - 列挙の形なので、操作フィードバック（判定が盤に現れる動き・進み具合の塗りの伸び）とアコーディオンの開閉は、reduced-motion でも動くと読める。
  - 一方で、設計 6-2 は判定の動きを「`prefers-reduced-motion` で即時にする」と決め、T4-11 の完了の条件にも「`prefers-reduced-motion` で盤と結果に動きが無い」とある。
  - いまの実装も、アコーディオンの三角（`DisclosureTriangle.module.css:21`）と進み具合の帯（`ProgressBar.module.css:36`）を reduced-motion で止めている。
  - つまり、設計と実装が拠っている決まりが、単一情報源の `DESIGN.md` に無い。
- **来訪者にどう効くか**: 動きで気分が悪くなるので reduced-motion を設定している来訪者に、`DESIGN.md` だけを読んで作った部品が、回る判定のマスや伸びる帯を見せる（WCAG 2.3.3「操作が引き起こす動きは止められる」の考え方にも外れる）。§11 の3つの動きは、1文で揃えられる。
- **直し方**: §11 の最後の項を、次のように1つの規定にする。
  - 「`prefers-reduced-motion` のとき、自動で始まる動きは止まり、UI の3つの動き（結果の登場・操作フィードバック・アコーディオンの開閉）はどれも即時になる」。
  - 理由は来訪者の側から1文で書く。

  あわせて設計 6-2 の「最後の推測では行に動きを持たせず、結果のボックスの登場だけにする（動きを2つ同時に走らせない）」も、§11 のスクロールの項と同じ考え方の一般の規定として書けるか判断すること。書かないなら、その理由を設計に残す。

### Major-4 注記の先頭の太字の語が、§4「太字は一段落に一箇所まで」と衝突する（置き場所が書かれていない）

- **どこが**: §5 の注記の「先頭に種類を言う語（補足・ヒント・重要・注意・警告）を太字で置く」。builder は、書かなかった理由を挙げている。
- **何と食い違うか**:
  - 「先頭に」が、1行目に単独で置くのか、最初の段落の頭に続けて置くのかを言っていない。後者に読むと、§4 の「太字は一段落に一箇所まで」に反する段落ができる。
  - 実際に、ブログの注記100件のうち5件は、最初の段落がすでに太字を持っている（例 `2026-02-28-game-dictionary-layout-unification.md` の「**追記（2026-03-15）**:」、`2026-02-17-regex-tester-guide.md` の「**ReDoS（…）**」）。段落の頭に続けて置くと「**補足** **追記（2026-03-15）**:」のように太字が2つ並ぶ。
  - 注記を「段落」と単数で定義しているが、100件のうち7件は複数の段落を持つ。
- **来訪者にどう効くか**: 太字が並ぶと、どちらが種類でどちらが書き手の強調かが分からなくなる。強調も弱まる。T4-17 の builder は、どちらの形を取るかを自分で決めることになり、markdown-preview と記事で組み方がずれうる。
- **直し方**: 「種類の語は、注記の1行目に単独で置く」と書く。設計 5-1 の `marked-alert` の出力（題の行が別の要素）とも合う。これで、段落の太字と数え合わない。定義は「本文の中で補足や注意として分けて読ませる、1つ以上の段落」にする。

### Minor-1 §3 の1文が、字の形を見せる字をいつも本文書体で組む、とも読める

### Minor-2 §3 の理由の「辞書や教科書が見出しの字に使う形に近い」は、教科書について不正確

小学校の教科書と、学習用の漢字辞典の親字は、多くが教科書体（手書きに近い字形）で組まれる。明朝の骨格が近いのは、一般の辞書と印刷物の標準の字形である。来訪者に言う理由として誤りを含まないよう、「印刷の標準の字形（明朝）に近い」のように書く（設計 4章の表の文も同じ）。

### Minor-3 §3 の本文の中のコード片「どこからどこまでがコードかを地で見せる」が、§2 の「`--paper-2` は境界を担わない」と食い違う

- `--paper-2` の地は、字の並びの調子を変える。

### Minor-7 図の幅を本文の幅にする PM の決定について（意見）

表・コード・画像はコンテンツ幅なのに、図だけが本文の幅になっている。設計 5-5 も、図を「表・コードと同じ扱い」と書いている。1280px では本文の幅が 640px で、コンテンツ幅は 922px ある。記事11本の図には横に長いもの（`flowchart LR`・4者以上の `sequenceDiagram`・`gantt`）があり、本文の幅では、922px なら収まる図まで字が小さくなるか横に送ることになる。モバイルでは2つの幅が同じなので、差が出るのは PC の来訪者だけで、PC では図が大きいほど読める。画像と同じ「コンテンツ幅を超えない範囲でコンテンツが決める」にするほうが、来訪者にとって得だと考える。

本文の幅を保つなら、来訪者にとっての理由（行の流れを切らない、など）を設計 5-5 に書くこと。変えるなら、§5 のボックスの定義の「本文の中に置くもの（注記・横に送る図）」も直す。

### Minor-8 knowledge の1字ずつの Range が、サロゲートペアの字で誤る

`playwright-mcp.md:46` は「字ごとに `range.setStart(node, i); range.setEnd(node, i + 1)`」で、UTF-16 の単位で進める。Zen Antique に無い字の例の「𠮟」（U+20B9F）はサロゲートペアで、辞典の見出しを測ると、半分の字の矩形を読んで行の切れ目を誤る。スキルの手順は「見出し」一般に掛かるので、コードポイントで進める（`for (const ch of text)` で UTF-16 の位置を `ch.length` ずつ足す）と書く。

### Minor-9 スキルの「ブラウザは Chromium だけで測る」が、環境の事情を全体の決まりとして言っている

WebKit を使える環境なら、WebKit で直接測るほうが来訪者の見え方に近い。Chromium で測るのはこのコンテナに Chromium しか無いからで、`playwright install` をしない決まりも、このコンテナのものである。スキルの1文目は「このリポジトリの作業のコンテナには Chromium しか無いので」のように、理由を添えて書く。knowledge の節の書き出しは、すでにそうなっている。
