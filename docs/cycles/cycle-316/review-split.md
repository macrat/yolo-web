## 指摘

### 1. 統合のブランチに push しても CI が走らない（重い。split-plan.md・cycle-completion スキル）

`.github/workflows/deploy.yml` の起動の条件は `push: branches: [main]` と `pull_request: branches: [main]` だけである。`design-rollout` に push しても GitHub Actions は動かず、`scripts/wait-for-ci.sh` は「CI run が見つかりません」で終了コード 2 を返す。split-plan.md の「このブランチに push し、CI を通す」と、cycle-completion の「次の「CIの成功確認」も同じブランチで行ってください」は、このままでは実行できない。最初の統合のサイクルの完了の処理で止まるか、「CI が無いから確かめられない」として手順を飛ばすことになる（AP-WF23 の型）。

直し方の例: `design-rollout` から main への**下書きのプルリクエスト**を最初に開く（`pull_request` の起動の条件で、push のたびに CI が走る。マージはしない）。そのことを split-plan.md とスキルの両方に書く。workflow の起動の条件にブランチの名前を足す方法もあるが、スキルは特定の名前に依らない書き方のほうがよい。

### 2. 次のセッションが統合のブランチを見つけられない（重い。split-plan.md・cycle-kickoff スキル）

`origin/main` には cycle-316 のディレクトリが無く（最新は cycle-315）、main のバックログでは B-754 が cycle-316 の前の文言のまま Queued にある。cycle-316 の 663 のコミットは `claude/cycle-kickoff-rv3l21` にしか無い。次のサイクルのセッションが main から始まると、cycle-kickoff の手順1は cycle-315 を「最新のサイクル」として読み、B-754 を最初からやり直す新しい「cycle-316」を作りうる。cycle-completion の文の「サイクルドキュメントに名前を書く」は、そのサイクルドキュメントが読める場所にあって初めて効く。

あわせて、次のことも split-plan.md に書かれていない。

- `design-rollout` を**どこから作るか**（cycle-316 の最後のコミットから）。
- **cycle-316 自身の完了の push 先**。split-plan.md が統合のブランチを指定しているのは「B-754 の残りのサイクル」だけで、cycle-316 の index.md にも「このサイクルは `design-rollout` に push する」とは書いていない。cycle-316 には T1〜T5 の実装が入っているので、cycle-completion の既定どおり main に push すると、新旧の混ざった面がそのまま本番に出る。

直し方の例: main から読める所に案内を置く（たとえば main のバックログの B-754 の行に「`design-rollout` で進行中。最新のサイクルは cycle-316」と書いた、文書だけのコミット）。cycle-kickoff の手順1（状態の確認）に、統合のブランチの上で進んでいる変更があればそのブランチから始めることを書く。split-plan.md には、作る元と、cycle-316 自身も `design-rollout` に push することを書く。

### 3. 「何が起きたか」の診断が記録と合わず、AP-WF43 の根本原因の見立てがずれている（重い。split-plan.md・candidates.md）

- [options.md](./options.md) は、**案 D「統合ブランチで複数サイクル」をはっきり比べたうえで退けている**。退けた理由は「main の旧デザインに入れた修正を、ブランチ側でもやり直すことになり、163 の CSS module で衝突する」である。また「A の代償」は作業の量を見積もっている（土台5・部品12前後・面70前後……、それぞれにレビュー）。そのため、split-plan.md の「見積もりと分割をしないまま」と、AP-WF43 の「足りなかったのは……統合のブランチで続け……取れると認識していなかったことである」は、どちらも事実と違う。
- split-plan.md は `docs/rebuild-plan.md` R-2 を「1サイクルで完了できるかを見積もり、収まらなければ分割する」と鉤括弧で引いているが、原文はこうではない（「「1サイクルで完了できるか」を見積もる（部分出荷禁止のためブランチの長期保持は腐敗リスク——収まらない見積りなら分割方針をオーナーに相談してから着手する）」）。さらに R-2 はフェーズ R の節で、同じ節の「部分出荷の禁止」は「効力は既に尽きている」と書かれている。このサイクルを縛る規定として引くのは正確でない（AP-P34 の型）。
- 記録から読める実際の取り違えは、**「何サイクルに分けるか」と「いつ出荷するか・そのあいだ main に別の修正を出すか」を1つの案の軸に束ねて比べた**ことである。D は「main に並行して出す」ことと抱き合わせで評価されて退けられた。main を止めて D を取れば、A と同じ「出荷は1回」のまま、サイクルを小さくできた。そして A の代償には「長いサイクルが利用上限・中断・レビューの往復に当たる」という費用が数えられていなかった。
- 同じ理由で、**options.md が D を退けた理由（main への修正との衝突）に、split-plan.md は答えていない**。統合のブランチを続けるあいだ main をどう扱うか（B-754 以外は main に出さないのか、急ぎの直しは main に出してすぐ `design-rollout` に取り込むのか）を決めて書くこと。

直し方の例: split-plan.md の「何が起きたか」を、options.md の D の比較と A の代償の見積もりに合わせて書き直す。R-2 を引くなら原文のままにして、効力が尽きていることを踏まえた書き方にするか、引くのをやめる。AP-WF43 は、この型を一般化して書き直す（例:「進め方の案を比べるとき、作業を何サイクルに分けるかと、いつ出荷するかを1つの軸に束ね、長いサイクルの費用を数えずに退けていないか」）。AP-WF28 の観点では、根本原因の見立てが変わると、cycle-kickoff に足す文（手順4）が根本に当たっているかも変わる。見立てを直してから、スキルに足す文がそれに当たっているかを見直すこと。

### 6. 作業ツリーにある途中の作業を、cycle-316 を閉じるときにどう扱うかが決まっていない（中。split-plan.md）

直し方の例: 次のどちらかに決めて書く。(a) 途中の作業を、レビューまで cycle-316 の中で終えてから閉じる（その場合は、それらを「済んだ」に入れ、1つ目のサイクルから外す）。(b) 途中の差分を `tmp/` にパッチとして残して作業ツリーから外し、1つ目のサイクルのキックオフで戻す（このサイクルの一時停止のときと同じやり方）。
