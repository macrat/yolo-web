### 1-2. favicon と apple-touch-icon

- **commit された資産と、生成するスクリプトが食い違っている。** `public/icon.svg`・`favicon.ico`・`apple-touch-icon.png` の最後の変更は `6b6592c`（2026-09-21）で、朱の角丸タイル（`#af3622`）と地 `#f8f7f2` を持つ。スクリプトはそのあと `db7e525`（2026-09-25）で色を `utsuwaHex` の `INK`・`PAPER` に替えたが、資産は作り直されていない。スクリプトがいま作るのは「紙の地に墨の角丸（rx は1辺の 22%）の印と白抜きの `y`」で、これも §10 と合わない。

試作（ソースを変えずに `ImageResponse` で描いたもの。値は出発点で、builder が PNG を見て詰める）:

- 1200×630、地 `PAPER`。縦の線（コンテナの左右）を x=56 と x=1138〜1144 に、横の線（上端のサイト名の下と、下端）を画像の左端から右端まで引く。線の太さは 6px（§5 の太い線 3px の2倍。カードはタイムラインで幅 500〜600px ほどに縮めて見られるので、そこで 2.5〜3px になる）。色は `INK`。
- 上端: サイト名「yolos.net」を IBM Plex Sans 400・36px・`INK` で、コンテナの内側の左に置く。
- 中身: 補助情報（「{診断名}の結果」・「ブログ」・「伝統色辞典」など）を本文の書体（BIZ UDPGothic）・`INK_2` で置き、その下に名前を見出しの書体で置く。読みがあれば名前のすぐ下に補助情報の大きさで添える。
- **数字の結果**（知識のクイズの点数「10問中8問正解」・irodori の合計点「72点」）があるときは、補助情報のすぐ下、名前より上に、見出しの書体で、**名前の段に依らない決まった大きさ（出発点は 134px）**で置く。画面では §8 の「数字・短い語」が主見出しの段、「名前」がセクションの見出しの段で、2つの差は §4 で約 1.4 倍（4.08 / 2.92）ある。画像の名前の段のいちばん上（96px）の約 1.4 倍にすれば、名前がどの段に選ばれても数字の結果が名前より大きく、画面と同じ順と重みになる。名前の段に合わせて1段上にする決め方は採らない（名前がいちばん上の段に選ばれるとその上の段が無く、段どうしの差も約 1.14 倍しかなく、名前を持たない irodori の画像には基準が無い）。数字の結果は、この大きさで1行に収まらないときだけ、渡された区切り（`FittedNumber` と同じ「10問中｜8問正解」）で折る（「10問中8問正解」は漢字5字と数字3字で、134px では約 900px になり、中身の枠（試作で約 1,000px）に収まる見込み。字の送り幅からの見積もりで、PNG では確かめていない。T6-2 の条件で確かめる）。
- 色が主題のページ（traditional-color の結果・伝統色辞典）だけ、名前の左に色見本を1つ置く（試作は 200px 四方、`RULE_2` の細い枠）。見本の上に字を置かない（§2）。
- 印・回した `y`・画像の縁の枠・和色の面は持たない。
- X の 2:1 の切り取り（上下 15px）に掛かる所に字を置かない（試作では、いちばん上の字の上端が y=26 より下にある）。
- 枠の寸法（線の位置と太さ・内側の余白・字の大きさの段）は、クライアントからも読める1つのモジュール（`next/og` を読まないもの）に置き、OGP の描き方と irodori の画像（3-5）の両方がそこから取る。`next/og` を読む描き方のモジュールはクライアントから import できないので、寸法を描き方の中に書くと、2つの画像の枠が別々にずれていく。

試作で分かった、組むときに要ること:

- **欧文と和文の書体の分け方は、字の範囲で分けたまとまり（`span`）で指定する。** Satori（`next/og`）の `fontFamily` に「Plex, Zen」と並べると、「Markdown」は Plex で組まれたのに、同じ題の「GFM」は Zen Antique で組まれた。サイトと同じく U+0000-007F を IBM Plex Sans、それ以外を和文の書体（名前は Zen Antique、補助情報・読み・副題は BIZ UDPGothic）にするには、字をその範囲で分けて、まとまりごとに `fontFamily` を渡す。
- **名前・補助情報・読み・副題のどれも、サイトの見出しと同じ文節の区切り（`splitIntoPhrases`、`src/lib/phrase-breaks.ts`）で分け、文節を1つずつ flex の子にして、子の中を `white-space: pre` で組む。** 字の範囲で分けた `span` をそのまま並べると、Satori は `span` の境目で行を送り（「締切1」のあとで改行した）、境目の空白を落とした（「layoutで not-found」の空白が消え、試作の伝統色辞典の読み「ときいろ #eea9a9」も「ときいろ#eea9a9」になった）。文節ごとの子にすると、名前は §4 の見出しと同じく文節の切れ目で折れ（「締切1時間前に突然スイッチが入って傑作を／叩き出す情熱の画家」）、道具の副題「テキストとBase64の相互変換 (UTF-8 対応)」・伝統色辞典の読み「toki #eea9a9」・ブログの題の空白は、どれも PNG に残った。補助情報の文は短いが、和文と欧文が混ざるもの（道具の `shortDescription`・「イロドリ #212の結果」・hex）が多いので、同じ組み方を全部の字に使う。
- **文節の頭の空白は、前の文節の終わりに移す。** 空白で始まる文節が行頭に来ると、字下げに見える。前の文節の終わりに付けると、行の終わりの空白は見えない。試作では、空白を移した組み方で、行頭に空白の出た行は無かった。
- **1行に収まらない文節は、字の範囲のまとまりごとに子に分け、それでも収まらないまとまりだけを、中身の枠の幅（`maxWidth`）で字の所で折る（`word-break: break-all`）。** §4 の「文節が1行に収まらないときだけ、その文節の中で折る」にあたる。試しの題「とても長い語 Supercalifragilisticexpialidociousandevenlongerwordthatcannotfit のテスト」で、この組み方は枠からはみ出さず、英字の語だけが枠の幅で2行に割れた（描く時間 約 350ms）。文節の子のまま `white-space: pre` を掛けると、語は枠の外まで1行で伸びた。**文節の子（和文と欧文の `span` が混ざるもの）に `word-break: break-all` と `white-space: pre-wrap`（または `normal`）を一緒に掛けると、Satori は 30 秒たっても描き終えなかった**（同じ指定を欧文だけの1つの `div` に掛けたときは 170ms で描けた）。この組み合わせを使わない。
- **名前の段は、字の数でなく、3行以内で中身の枠に収まるいちばん大きい段を選ぶ。** 文節ごとの幅を、描くのと同じ書体のファイルの送り幅（`opentype.js` の `getAdvanceWidth`）で足して行に詰め、段（試作は 96・84・72・64・56・48・42px）を大きい方から試す。試作の結果: character-personality の35字の名前は 84px で3行、ezo-shika は 84px で2行、ブログの69字の題は 48px で2行、伝統色辞典の1字は 96px で1行。見積もりの詰め方は、描くときの子の分け方（上の3つ）と同じにする。試作の見積もりは、1行に収まらない文節を分けた試しの題で3行と出たのに、PNG は4行だった（見積もりが子の分け方を真似ていなかったため）。見積もりの行数と PNG の行数が合うことをテストで確かめる。
- **幅 400px に縮めて読めるか。** 試作の PNG を幅 400px（カードの小さい表示の目安）に縮めると、84px の名前は約 28px、48px のブログの題は約 16px で読めた。補助情報の 32px は約 11px で、読みにくかった。補助情報・読み・副題は 36px 以上（400px で 12px 以上）にし、名前の段のいちばん小さい段も 400px で 14px（1200px で 42px）を下回らないようにする。
- **Zen Antique で組むと「——」は1本の線になる。** 同じ ezo-shika の題を Zen Antique 50px で組むと、線の画素は x=240〜339 の1本で、隙間が無い（3-4）。
- **書体のファイルの出どころ**: IBM Plex Sans は、画面と同じ `@ibm/plex-sans` 1.1.0 の WOFF 1（`fonts/complete/woff/IBMPlexSans-Regular.woff`・`-Bold.woff`）をリポジトリの `src/fonts/ibm-plex-sans/` に写す（1-3。版が画面と同じで、ビルドがネットワークに依らない。`@ibm/plex-sans` を依存に加えないのは fonts-decision.md のとおり）。同じ版であることは、`name` の版（3.005）と U+0020〜007E の送り幅が画面の woff2 と一致することを、テストで確かめる。Zen Antique（5.5 MB）・BIZ UDPGothic（4.4 MB）・BIZ UDGothic は、いまと同じく Google Fonts の CSS に古い UA で問い合わせて TTF を取る（Zen Antique は画面と同じ出どころ。1-3）。
- 名前に Zen Antique に無い字（𠮟・剝・塡・頰・纁。t4-inventory.md 3-2）があるときは、§3 のとおり名前の和文を丸ごと `"BIZ UDGothic"` で組む（`charsMissingFromZenAntique`、`src/lib/zen-antique-charset.ts`）。BIZ UDGothic にも無い字（纁・彐など）は、§3 の本文の書体の並びの末尾の Noto Sans JP で描き、幅もその書体で測る。Noto Sans JP はこのモジュールが自分で取り、取れなければ例外を投げてビルドを止める（`next/og` が黙って別の書体を取りに行き、失敗すると豆腐の画像を 200 で返すのに頼らない）。4つの書体のどれにも無い字は、絵文字のほか「₂」「₃」「✔」「✕」「✗」「❤」などもあり、画像に書く欄に来るとビルドが止まる。画像を出すルートを足すタスク（T6-3 以降）は、そのルートの欄の字を4書体の字の表で確かめる。
- **書体を取れなかったら、ビルドを失敗させる。** いまは取れないと黙って `sans-serif` に落とし、違う顔の画像がそのまま出荷される（`ogp-image.tsx:213-214` のコメントのとおり）。画像はビルドで書き出すので、そこで止めれば出荷の前に分かる。

## 4. 実装の分け方

どのタスクも、レビューを受けてから完了とします。**どのタスクも、終わった時点で `npm run build`・型の検査・lint・テストが通ることを完了の条件に含めます**（途中のコミットでもビルドを壊さない）。**名前と面の区切りの規則**: 名前や面を書いたか書き換えたタスク（T5-3b のあとに終わる T5 の各タスク・T5a・T6-6・T6-9・T7 を含む）は、次の3つを完了の条件に含める。(a) 字で渡すものは、t5-design.md 4-g の数え方（`npm run check:phrased-names`）の数が0。(b) 値で渡すもの（数え方が値で渡す所として出す位置）は、名前が出る状態を開いて 320px の既定と 200% で測り、語の中の折れが0（§4 が受け入れる、1行に収まらない文節の中の折れを除き、それは記録する）。位置と状態と測った値を記録に残す。(c) `.ts` に手で書いた区切りの並びは、`followsPhraseRules` を満たすことを試験で確かめる。触ったファイルに残るほかのタスクの受け持ちの分は、受け持ちのタスクの名前とともに記録に残す（失敗させずに出す指定で数え、書いたか書き換えたものは、始めたコミットと終えたコミットの出力の差で見分ける）。T5-26 は最後に、`src/` の全体を同じ規則で測る。**変更の前の PNG** は、どのタスクも同じ基準にするため、このコミット（`fc9b08c`）のビルドが書き出す PNG（`.next/server/app/**/opengraph-image.body` など）を、タスクの始めに取り出して使います。変更の後の PNG は、変更したビルドから同じ所を取り出します。前と後の PNG を並べて見たことと、測った数を、タスクの記録に残します。

**進め方の考え方**: 新しい描き方は、いまの `ogp-image.tsx` を書き換えず、**新しいモジュール**（例 `src/lib/share-image.tsx`。名前は今の中身の呼び名にし、`new` を含めない）として作ります（T6-2）。画像のルートは、面ごとのタスクで新しい描き方へ移り、どのルートも使わなくなってから、古い `ogp-image.tsx`・`fuda-image.tsx` と札だけのファイルを消します（T6-11）。こうすると、どのタスクの途中でも、古い描き方を使うルートは古いまま描けてビルドが通り、同じファイルを2つのタスクが触りません。出荷は全部がそろってから1度なので（index.md）、途中で2つの描き方が混ざる状態は来訪者に出ません。
