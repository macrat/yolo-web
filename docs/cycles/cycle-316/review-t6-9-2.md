## 指摘

### 指摘1（コメント）: 守りのコメントの2文目が、目的と逆の意味で読める

`GameContainer.tsx` の214行:

```ts
// 画像を描くあいだは書体の読み込みを待つので、そのあいだの押下は捨てる。同じ画像が2枚落ち、保存が2回数えられない。
```

2文目の「同じ画像が2枚落ち、保存が2回数えられない」は、連用中止の「落ち、」が「落ちる」と言い切っています。このため、「同じ画像が2枚落ちる。そして保存は2回数えられない」と読めます。言いたいのは、捨てないと起きる2つのこと（2枚落ちる・2回数えられる）が、どちらも起きないことのはずです。

この ref は、コメントを読まないと「なぜ state でなく ref で、なぜ押下を捨てるのか」が分かりません。コメントは、この守りを次に触る人が目的を知る唯一の所です。そこが逆の意味に読めると、守りを外してよいと取られかねません。

直し方: 2文目を、2つのことがどちらも起きないと読める文に直す。例:「同じ画像が2枚落ちたり、1度の保存が2回数えられたりしないように。」、または1文にまとめて「…待つので、そのあいだの押下は捨て、同じ画像を2枚落とさず、保存を2回数えない。」。

## 確かめたが、直さなくてよいもの

- **`generateResultImage` が例外を投げたとき**: `.finally()` は守りを外すが、`.catch()` が無いので、例外は未処理の Promise の拒否になる。ただ、今の描き方に投げる所は無い。`document.fonts.load` は失敗を拒否で返し、それを `Promise.allSettled` が受ける。`toDataURL` は `try` の中にある。前の同期の描き方でも、例外はそのまま出ていた。`FudaActions` が失敗を知らせの文で出すのは、通信で失敗しうるからで、端末の Canvas で描くこの画像とは事情が違う。
- **待つあいだに何も出さないこと**: `FudaActions` は「画像を用意しています。」を出すが、irodori の待ちは、結果のボックスが「点」を Zen Antique で組み終えたあとにしか起きない。そのため、描く字の書体はふつう読み込み済みである。1枚は 14〜30ms（ページで最初の1枚でも約 120ms）で終わる（t6-log.md の測り。自分では測っていない）。書体の取得を 1.5秒遅らせた回でも、落ちた PNG は遅らせない回とバイト単位で同じだった。知らせを出すほどの待ちは無い。
- **`ShareSurface` の説明**: `analytics.ts` を T6-9 で触らないのは、4章の頭の表のとおりで正しい。作業ツリーの `analytics.ts` の差分は、ブログの目次の出来事を足すもので、`ShareSurface` には触れていない。**T6-6 はまだ終わっていない**ので、PM は出荷の前に T6-6 を終えること（前回の判断3のとおり）。
