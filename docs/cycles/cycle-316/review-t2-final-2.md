## 指摘

### Minor-1 `DESIGN.md` §6 の書き足しが例外の継ぎ足しで、表と §5 に反映されていない

8f711dc は、§6 の2つの箇条の末尾に1文ずつ足した。

- 「二重リングは、押せる範囲の内側に密着して出る。」の箇条に、「太い枠を持つ押せるものでは、リングは枠の内側に `--paper` を挟んで出る。」
- 「hover のボーダーは押せる範囲の内側に出る。」の箇条に、「反転した地の上では、ボーダーを `--paper` で…」

このため、次の食い違いが残る。

- §6 の表の「フォーカス: 押せる範囲に密着した二重リング」と、太字の読み分けの表の「押せる範囲に密着した二重リング＝フォーカス」は、太い枠のものでは成り立たない。
- 「太い枠を持つ押せるもの」という種類そのものが、§5 の線の表（太い線を使う場所）にも、§6 の読み分けの表にも無い。読み分けの表に従うと、なかまわけの語のマスは「どれでもない＝ボックス」になる。
- §5 の線の表は、hover の細い線の色を `--rule-2` と定める。反転の地では `--paper` にしたが、表はそのままである。前回挙げた `--rule-2` でも見えるという見積もりに対して、`--paper` を選んだ理由は、index.md の補足事項にも無い。
- 1つ目の書き足しは「からである。 太い枠を…」と、句点の後に半角の空白が入っている。

箇条の見出しが言うことと、末尾の文が言うことが逆になっている。CLAUDE.md の「ツギハギ禁止」（例外や特別扱いを後から足した跡を残さない）にあたる。前回の直し方は「planner が §5・§6 に書き足してレビューを受ける」だったが、書き足しは builder の実装のコミットに入っている。

**直し方**: planner が、「太い枠を持つコントロール」を §5・§6 に種類として立てる。そのうえで、§5 の線の表、§6 の種類と状態の表、読み分けの表、フォーカスと hover の箇条を、はじめからそう書いたように書き直す。`--paper` を選んだ理由は、補足事項に書く。書き直しは単独でレビューを受ける。

### Minor-3 笑辞典の評価を押すと、フォーカスが `body` に落ちる

`EntryRatingButton` は、押すとボタンそのものを取り除く。キーボードで押した来訪者のフォーカスは `body` に移る（実測で `document.activeElement` が `BODY`）。Chrome は次の Tab で続きから進むが、フォーカスの見える場所が消える。そのため、どこにいるかを見失う（WCAG 2.4.3・2.4.7 の趣旨）。

また、評価済みの来訪者がページを開くと、マウントのあとに `role="status"` の段落へ文が入る。スクリーンリーダーによっては、開くたびに「送りました」を読み上げる。

**直し方**: builder が、次の2つを直す。

- 押したあと、文の段落（`tabIndex={-1}`）へフォーカスを移すか、ボタンを残して無効の形と理由の文にするかを選ぶ。
- 読み戻しのときは、ライブリージョンに入れずに文を出す。

キーボードで押して、フォーカスが見えることを撮って確かめる。

### Minor-4 ゲームの通信の失敗が、入力欄のエラーとして英語で出る

kanji-kanaru・yoji-kimeru の `handleGuessSubmit` は、`fetchEvaluate` が失敗すると `err.message` をそのまま返す（`GameContainer.tsx` の `catch`）。このため、「Evaluate API error: 500」や「Failed to fetch」が、8f711dc で作った欄のエラーの形で出る。欄は太い線になり、`aria-invalid` が立つ。

入力は正しいのに「入力が誤り」と示すことになる。文も英語で、どう直すかを言わない（§8）。起きるのは通信が失敗したときだけだが、T2 の「入力欄とラベルとエラー」の範囲である。

**直し方**: builder が、通信の失敗を入力の誤りと分ける。欄に `aria-invalid` を立てずに「通信に失敗しました。もう一度送信してください」のような日本語の文を出す（2本とも）。
