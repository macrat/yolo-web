## 指摘

### 中1 「戻し方」のあとからの評価が、止められた時点の正しい行いを「オーナーに報告すること」としている（AP-WF24・規則）

- decisions.md の「hook の取り消し」の「戻し方」は、評価を次の文で結んでいる。「止められた時点で取るべきだったのは、Edit で戻すか、止められたことをオーナーに報告することだった」。
- 後半の「オーナーに報告すること」は、作業を止めて Owner に返すことを、正しい選択肢の1つとして書いている。これは次の3つと食い違う。
  - AP-WF24（PM 権限内の判断を Owner に返さない）。
  - オーナーの 10-02 の言葉（プロジェクトの hook は CLAUDE.md より下。CLAUDE.md は決定を PM に委ねている）。
  - 同じ取り消しについて、オーナーが 14:21:35 に返した問い（「なぜ私の判断を仰いでいるのか教えてください。」）。decisions.md 自身も、この問いのもとになった判断の返し方を AP-WF24 の発生として記録している。
- 拘束の例として引いている「hook に止められたら回り道をせず報告」は、PM がレビュアーへの依頼文に書いた決まりで、報告の宛先は PM である。PM が Owner に返す根拠にはならない。
- decisions.md は、後のサイクルが読み継ぐ申し送りである。この文はそこで「hook に止められたら、Owner に報告して止まるのが正しい」という先例として読まれる。PM が 15:13:29 にオーナーに送った報告も、同じ文を使っている。
- 止められた時点の hook の文（14:22:24）は、代わりの道を3つ示していた。
  - Edit で直す。
  - `git diff` で失うものを確かめ、wip のコミットを作ってから進める。
  - 最後の手段として、人が hook を外す。
- 消した未追跡のファイル（新しい hook・`lib/`・`tests/`）は、`rm` で消せる。hook が止めたのは `git restore` だけで、`rm` は止めていない。
- 直すこと: 評価の結びを、そのときの規則で PM が自分で取れた行いに改める。たとえば「変わった4つのファイルは hook の案内のとおり Edit で戻し、新しいファイルは `rm` で消す」とする。ほかの道を選ぶなら、その場で PM が決め、理由を記録する。どちらにしても Owner に返す形にはしない。
- あわせて、この件の再発防止をどこで担保するかを1文で書く。止められたときに取る道は、hook の文と split-plan.md 6 の前書きにある。AP-WF21 の記録も「Edit・Write を通さずに書き戻す」形を禁じている。そのうえで、新しい候補が要るか要らないかの判断を書く。いまの行は事実と評価を書いているが、再発防止については何も判断していない。
