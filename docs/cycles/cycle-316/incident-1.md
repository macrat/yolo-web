# 事故報告: サブエージェントの完了をコマンドで待ち続け、その再発防止をアンチパターン集に書くというルール違反を重ねた

## 何が起きたか

### 1. コマンドで待ち続けた

T1a（Web フォントの判断）とその各巡のレビューを、バックグラウンドのサブエージェントに任せた。完了は通知で届く。それなのに、`until grep -q '"stop_reason":"end_turn"' …; do sleep …; done` というコマンドで完了を待ち、10分の上限で切れるたびに同じコマンドを出し直した。途中で出力ファイルの大きさや動いているプロセスを確かめ、「まだ作業中」という経過も出した。これを T1a の各巡とレビューのたびに繰り返した。待機のコマンドは数十回に及んだが、正確な回数を確かめられる記録はリポジトリに残っていない。

Owner から「サブエージェントが完了すると通知が来るので何もせず待つこと。コマンドで能動的に待つことを禁止する。コンテキストが圧迫されて仕事の質が著しく落ちる」と指摘された。

### 2. その再発防止を、アンチパターン集のルールに反する形で書いた

指摘を受けて、`docs/anti-patterns/candidates.md` に「AP-WF42 候補: サブエージェントの完了を、コマンドで能動的に待っていないか」を書き、コミットした。Owner から、ルール違反として取り下げを指示された（取り下げのコミット 89db69f）。この候補は取り下げたもので、いまの candidates.md には無い。番号の AP-WF42 も、cycle-312 が撤回して再利用しないとした欠番（workflow.md の欠番の節）で、使ったこと自体が誤りだった。

`.claude/rules/anti-patterns-directory.md` は次のことを Don't と定めている。この候補は2つとも犯していた。

- **あとから気付いても回復できないアンチパターンを記録する。** コマンドで待つことの害（コンテキストの圧迫）は、待った時点ですでに生じている。チェックリストで気付けるのは待ったあとで、取り返しがつかない。ルールは、このような問題は手順書に書くかフックで防ぐ、としている。
- **どのような手順でやるべきかを記録する。** 候補の「対症療法案」は、「何も出さずにターンを終える」「差し戻されたらもう一度終える」という手順そのものだった。

## なぜ起きたか

### コマンドで待った理由

- **サイクルの進行中にターンを終えようとすると `stop-cycle-guard.sh` に差し戻される。** 差し戻しの文面は「作業が残っているなら、続けてください」で、サブエージェントを待っている状態をどう扱うかは書かれていない。記録に残る行動は、差し戻しのあとターンを終えずに、ターンの中で待つコマンドを出したことである（差し戻しの文面をどう読んだかは記録に無い）。
- **フックの中身を読んだのは、Owner に指摘されたあとだった。** フックは、同じ停止を2度は止めない作り（`stop_hook_active`）である。待つコマンドを出す前に、規則の実体（フックのコード）を読んだ記録は無い。
- **フォアグラウンドで起動すればフックは発動しない**（Owner の指摘）。このセッションの初めに、レビュアーを `run_in_background: false` で2回起動したが、どちらも「バックグラウンドで起動した」という応答が返った。わたしはこの食い違いを調べず、以後は最初からバックグラウンドで起動し、待つ手段をコマンドに求めた。
- **待つあいだのコンテキストの消費を、費用として数えた記録が無い。** 1回の待機は小さく見えるが、何時間もの作業のあいだに積み上がり、このあとの判断の質を落とす。待ち方を決めるときに、この費用を比べた記録は無い。

### ルールに反する候補を書いた理由

- **`.claude/rules/anti-patterns-directory.md` はこのセッションで読んでいた。** AP-WF09 に発生サイクルを足すとき、どこに書くかを確かめるために開いた。同じファイルには何を書いてはいけないかの Don't もあるが、候補を書く前にそれに照らした記録は無く、書いた候補は Don't の2つに反していた。
- **候補を、加えてよいものかを確かめずに書いた。** CLAUDE.md「Check anti-patterns on failure」の文は、既存の項目に当たるかを確かめ、当たらなければ加える、である。加えてよいものかどうかは、アンチパターン集のルールが決める。候補を書く前に、その確かめをした記録は無い。

## 影響

- 待機のコマンドと経過の出力が、このセッションのコンテキストを消費した。その分、以後の判断に使える余地が減った。
- ルールに反する候補が一度コミットされ、main へ向かうブランチに載った（取り下げ済み）。

## 何が正しかったか

- サブエージェントを起動したら、ほかに進められる作業が無ければ、何も出さずにターンを終える。完了は通知で届く。
- フックを発動させずに結果を待つなら、サブエージェントをフォアグラウンドで起動する。起動の応答が指定と食い違ったら、その場で調べる。
- 規則の文面に従って行動を決めるときは、その規則の実体（フックならコード）を先に読む。
- Owner に指摘された失敗を記録するときは、アンチパターン集のルール（書いてよいもの・いけないもの）を読み直してから、置き場所を決める。あとから気付いても回復できないものと、手順そのものは、手順書かフックの側で扱う。

## 再発防止

待った時点で害が出ているので、アンチパターン集には書かず、オーナーの決まり（待つだけのときは何もせず待つ）と、セッションをまたいで残る knowledge で担保した。

- 待ち方は、`docs/knowledge/ai-agent-communication.md` の「バックグラウンドのサブエージェントの完了は、何もせずに待つ」に書いた。ほかに進められる作業が無ければ何も出さずにターンを終えること、完了は通知で届くこと、`stop-cycle-guard.sh` が差し戻すのは1回の停止につき1度だけなので、差し戻されたらもう一度何も出さずに終えればよいこと、sleep・until・出力ファイルの確かめなどのコマンドで待たないことである。`stop-cycle-guard.sh` の差し戻しの文は変えていない（文に待ち方を書く直しは作ったが、取り消した。decisions.md の hook の取り消しの行）。
- `run_in_background: false` で起動したのに「バックグラウンドで起動した」と返った食い違いは、`docs/knowledge/ai-agent-communication.md` の「サブエージェントの起動の形（フォアグラウンドとバックグラウンド）」に、分かっている事実と分かっていないこと（原因と再現の条件。再現は Agent ツールを持つ PM のセッションでしか試せず、完了の処理の builder は試せなかった）、MCP を使う確かめを頼むときにフォアグラウンドで動いているかを確かめる手順を書いた。
