## Minor

### Minor-1: 「色見本を1つ持つのは、主題が色であるページの画像だけ」と、ゲームの結果の画像の色見本が食い違う

§10「画像の中身」は「**主題が色であるページの画像だけが、色見本を1つ持つ。**」と書き、その置き方（中身の左端に置き、名前と読みはその右から始める）を定めています。一方、「保存・共有する結果の画像」では、色のゲームの結果の画像が、問ごとにお題と回答の色見本を持ちます。1つ目の規則をそのまま読むと、ゲームの画像は色見本を持てないか、持っても1つで名前の左に置くことになり、T6-9 の builder が迷います。読む人には、「だけ」「1つ」の規則を後ろの項が破る、前回の Minor-1 と同じ例外の形に見えます。

直し方: 色見本の規則を、画面から出る形で1つにしてください。例えば「**色見本は、画面がその色を見本で見せる所にだけ、画面と同じ形で置く。** 見本は細い線で囲み、上に字を載せない（§2）。伝統色辞典の詳細では、画面の見本と同じく1つを中身の左端に置き、名前・読みはその右から始める…。色のゲームの結果では、画面と同じく問ごとにお題と回答の見本を置く」。ゲームの項の括弧の中の見本の説明（正方形・細い線・字を載せない）は、この規則に寄せて重ねないようにします。

### Minor-2: いちばん下の段でも中身が縦に収まらないときに、何を譲るかが無い（builder の問い1）

§10 は「名前の段は、名前が3行以内に収まり、…中身が枠の縦に収まる、いちばん大きい段」「いちばん下の段でも名前が3行を超えるときは、いちばん下の段のまま行を増やす。どの字も中身の枠からはみ出さない」と書いています。いちばん下の段で行を増やしたり、副題が長かったりすると、縦に収まらないことがありえます。このとき §10 は「はみ出さない」とだけ言っていて、どうやってはみ出さないようにするかを決めていません。T6-2 の builder は、「いちばん長い名前」「長い副題」を試しの入力で描くので、ここで必ず選ぶことになります。選ばずに組むと、字が枠の下で切れたり、下の罫線に重なったりします。

いまのデータでは起きにくいです。ブログの69字の題は 48px で2行（t6-design 3-2 の試作）、道具の `shortDescription` はいちばん長くて約80字（36px で3行ほど）、ユーモア辞典の副題はすでに `truncateDefinition` で詰めています。ただ、「起きない」と決めてそれを確かめる形にするか、「起きたら何を譲るか」を決めるか、どちらかを §10 が言わないと、それぞれのルートで違う扱いになります。

**§10 に1文で決めてください。** 勧めるのは、「名前・数字の結果・補助情報は切らない。いちばん下の段でも縦に収まらないときは、副題を文節の切れ目で切り、終わりに「…」を置く」です。名前は h1 と同じで、カードを見た人がどのページかを知る字なので残します。副題は添える字なので、譲っても画像の仕事は果たせます（ユーモア辞典が定義を詰めているのと同じ扱いです）。名前だけでも枠に収まらない長さは、いまのデータに無いので、スキルの「はみ出しと折れ」の確かめで、すべてのページの名前がいちばん下の段で枠に収まることを確かめる形にすれば足ります。別の決め方（例: 縦に収まらない入力はビルドを失敗させ、副題の文を短くする）を採っても構いませんが、どちらか1つを §10 に書いてください。

## builder の問い2: 段の値（96〜42px）を §10 に書いてよいか

**書いてよいです。そのままにしてください。** いちばん上の 96px は数字の結果の大きさ（約 1.4 倍）の基準で、いちばん下の 42px は「400px で 14px」の下限から出た値です。どちらも §10 の中の別の規則が拠っているので、DESIGN.md に数で要ります。§4 も段を rem の値で書いています。あいだの段は T6-2 で変えうりますが、変えるときは DESIGN.md の値も同じ変更の中で直せば済みます（スキルの「値を変えるときの手順」の「DESIGN.md が先」と同じ扱い）。値を書かずに T6-2 に任せると、T6-3 以降の builder と §10 の読み手が、段がいくつあるかを知る所が無くなります。
