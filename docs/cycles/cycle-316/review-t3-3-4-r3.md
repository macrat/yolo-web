### 読み上げ（t3-design.md 2-4）

2-4 の確かめ方（`ariaSnapshot` と `MutationObserver`）で、375・1280 の両方で再現した。

- 着いたとき: `/storybook/list/101`・`?q=一`・`/page/2` のどれでも `status` は空。
- 「いっ」を 60ms おきに打つ: 見えている行は2回替わり（98語 → 9語）、`status` は打ち始めから 0.39秒（375）・0.41秒（1280）で「9語（全101語）」に1回替わり、その 5.0秒後に空に戻った。3秒の時点の木は `paragraph: 9語（全101語）` → `status: 9語（全101語）`、6秒の時点は `paragraph: 9語（全101語）` → `status`（文なし）。
- `/storybook/list/11` で種別を「人生」、3秒後に「努力」: `status` は 0.06秒で「5語（全11語）」、3.1秒で「6語（全11語）」、8.1秒で空。待ちは最後の書き換えから数え直されている。
- `?sort=easy` で「次へ」を Enter: 見えている行が1回替わってフォーカスを受け（`P`、`tabindex=-1`）、`status` は0回。行の上端は画面の 16px。

5秒の決め方は妥当だと考える。

- 丁寧なライブリージョンは、読み上げソフトが手の空いたときに読む。打鍵や変換の読み上げのあとに読まれる間を残す必要があり、書き換えのすぐあとに空へ戻すのは危ない。
- 長く残すほど、一覧の頭から読み直したときに件数を2度聞く。件数の行は名前の欄の上にあり、欄から読み進めても着かないので、5秒のうちに戻る来訪者は少ない。
- 広く使われている実装でも、同じ考え方で数秒後に消している。React Aria の `LiveAnnouncer` は、既定で 7,000ms 後に文を消す（[LiveAnnouncer.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/@react-aria/live-announcer/src/LiveAnnouncer.tsx) の `LIVEREGION_TIMEOUT_DELAY`）。5秒はそれより短いが、同じ桁である。
- 空に戻すことが読み上げられないのは、`aria-relevant` の既定（`additions text`）のとおり。
- 実際の読み上げソフトで読まれるかどうかは、この測り方では確かめられない。2-4 はそれを T3-11 で NVDA か VoiceOver で聞くことにしていて、そのままでよい。
- タイマーは `useEffect` の cleanup で止めている（AP-I11）。

## 指摘

### Minor-1 §5 の「線を持たない小見出し」が、ボックスの頭の小見出しを言っていない

- どこ: DESIGN.md §5「ページの割り方」の「セクションの見出しやアコーディオンのラベルのすぐ下に立つ小見出しは、分ける内容を前に持たないので、線を持たない」。
- 何が起きるか: 規則は小見出しの上に線を引き、例外を「セクションの見出しかアコーディオンのラベルのすぐ下」の2つに限っている。ところが date-calculator（「日付の差分」）と cron-parser（「Cron式を入力」）は、ボックス（`Panel`）の上の太い枠のすぐ下に最初の小見出しを置き、線を持たない（320・375・1280 で確かめた。2つ目からは細い線がある）。前に分ける内容を持たないのは同じで、見た目はこれで正しいが、DESIGN.md の字面ではこの2つのページは規則に反する。§7 の「索引の見出しかアコーディオンのラベルのすぐ下」も、§5 の「セクションの見出し」と言い方がずれている（索引の見出しがセクションの見出しでなく小見出しの段で立つ場所では、§5 の例外に当たらない）。
- 来訪者にどう効くか: いまの見た目には効かない。次にボックスの中を小見出しで分ける道具を作る人が、DESIGN.md のとおりに最初の小見出しにも線を引くと、太い枠のすぐ下に細い線が並び、区切りが二重に見える。
- 直し方の方向: 例外を列挙でなく理由で言う（「前に分ける内容を持たない小見出し——セクションの見出し・索引の見出し・アコーディオンのラベル・ボックスの枠のすぐ下に立つもの——は線を持たない」のように）。§7 の区切りの見出しの文もそれに合わせる。

### Minor-2 §6 の「押せる範囲」が、フォーカスの行の1か所だけ字の箱を言い、ほかの3か所と食い違う

- どこ: DESIGN.md §6。表の「フォーカス」の行は「押せる範囲（押せないものは字の箱）に密着した二重リング」になったが、同じ節の次の3か所は押せる範囲だけを言う。
  - 読み分けの表「押せる範囲に密着した二重リング | フォーカス」
  - 「二重リングは、押せる範囲の内側に密着して出る。押せる範囲の外に出ないので……」
  - 「フォーカスリングはタップターゲットと一致する。」
- 何が起きるか: ページ送りのあとの件数の行は、押せないのでタップターゲットを持たない。リングは字の箱（375 で x=19・幅 235・高さ 31。字は x=27）の内側に出ていて、実装と §5 は合っているが、§6 の「タップターゲットと一致する」とは字面で食い違う。括弧の注記を1行にだけ足した形は、あとから差し込んだ跡として読める（ツギハギ）。また §5 のコンテンツ幅の中の表の「コントロール」の行は、いまも「押せる範囲の幅（字の左右に 8px。44px に届かなければ、届くまで右へ広げる）」と、字の箱の定義を名前を使わずに言い直している。同じものに2つの言い方がある。
- 来訪者にどう効くか: 直接には効かない。見出しへの移動などフォーカスを受ける押せない要素を次に作る人が、§6 の3か所を読んでリングの置き場所を決められない。
- 直し方の方向: §6 で「リングが出る範囲」を1回決め（押せるものは押せる範囲、押せないものは §5 の字の箱）、表・読み分けの表・箇条の3か所をその言い方でそろえる。「タップターゲットと一致する」は、押せるものについての文として言い直す。§5 の表の「コントロール」の行は「字の箱の幅」のように、定義した名前で言う。

### Minor-3 単字の索引の例外で、狭い画面ではセクションの見出しと区切りの見出しが同じ大きさになることが DESIGN.md に無い

- どこ: DESIGN.md §7「漢字1字だけを並べる索引では、小見出しの段が字の大きさを下回る幅でも、区切りの見出しを字と同じ大きさで組む」と、§4「階層は相対で、画面が狭くなると段がそろって下がる」・§3「階層は大きさと罫線が作る」。
- 何が起きるか: `45rem` 未満では、セクションの見出しが `1.49rem`、単字の索引の区切りの見出しも `1.49rem` になる。いま漢字「水」の詳細ではセクションの見出しがページの CSS で 20px なので目立たないが、T5 でそれを §4 の段にそろえると、375px で「同じ部首の漢字（117字）」と「5画」がどちらも 23.84px になる。段がそろって下がるという §4 の約束から、この索引だけが外れる。
- 来訪者にどう効くか: 見出しの親子が大きさでは見分けられず、上の全幅の罫線と区切りの細い線だけで見分けることになる。117字の索引の中で「5画」「6画」を拾う目的にはいまの形が合っているので、形を変えるべきとは考えない。ただ、DESIGN.md がこの帰結を言わないと、T5 でセクションの見出しを直した人が「区切りの見出しが大きすぎる」と読んで戻すか、逆にほかの小見出しにも同じ例外を広げるおそれがある。
- 直し方の方向: §7 の文に、その幅では区切りの見出しがセクションの見出しと同じ大きさになり、親子は罫線で見分けることを添える（§3 の「階層は大きさと罫線が作る」と合う）。index.md の T5 の漢字・四字熟語の詳細の項に、直したあと 375px でこの見え方を確かめることを足す。
