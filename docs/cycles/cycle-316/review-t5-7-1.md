## 指摘

### 指摘1: 開閉のラベルが、1行に収まる丸括弧の一続きの中で折れる（375px の既定）。builder の読み方は §4 と、それを形にした仕組みに合わない

測った値（後。375px の既定、組の開閉を開いた状態）:

| ページ                                      | 開閉のラベルの行                                                   |
| ------------------------------------------- | ------------------------------------------------------------------ |
| `/tools`・`/play`                           | 絞り込みと並び順（すべて、／種別順）                               |
| traditional-color-palette                   | 絞り込みと並び順（すべて、／色み順）                               |
| yoji-search                                 | 絞り込みと並び順（すべて、／読みの五十音順）                       |
| `/storybook/list/11`・`/storybook/list/100` | 絞り込みと並び順（すべて、／読みの五十音順）・（すべて、／画数順） |

ラベルの幅は 277px、「（すべて、種別順）」は折らずに組んで 154px で、1行に収まる。それでも括弧の中で折れている。

**読み方について。** builder は、§4 の「丸括弧で囲んだ一続き（読み仮名・添えた数）の中では折らない」を、読み仮名と数にだけ当たり、値を並べた括弧には当たらないと読んだ。この読み方は採らない。

- §4 は、括弧の中を文節で折る例外を表のセルにだけ、わざわざ別の項で書いている（「丸括弧の中も文節で折る。表のセルの括弧は読み仮名や数でなく説明を囲み」）。見出しとコントロールの名前の括弧に例外は無い。
- この規則を形にした仕組みも、どれも括弧を種類で分けない。`frontend-design` スキルの「実装の技術」の2（「丸括弧の一続きの中の切れ目を、折り所から外す」）、`followsPhraseRules`（括弧の深さが 0 でない所の区切りを偽にする）、`splitIntoPhrases`（builder の `split.txt` でも「（すべて、読みの五十音順）」を1つの文節にしている）、スキルの合格の条件（「既定の文字サイズ（320px・375px・1280px）では…丸括弧の中の折れが、どれも0」）。
- 試験 `括弧の外の区切りは禁則を満たし、…` は、`followsPhraseRules(label.slice(0, 3))` と括弧の手前までだけを確かめている。ラベルの全体を渡すと偽になるので、試験が規則を避ける形になっている。
- builder の measure の出力（`after-sum.txt`）も、この折れを `inParen=1` と数えたまま、失敗として扱っていない。規則の読み替えは builder が1人で決めることではなく、採るなら PM の決定と DESIGN.md §4・スキル・`followsPhraseRules` の書き換えが要る。

**折れの良し悪しについて。** 来訪者から見ると、1行目に「絞り込みと並び順（すべて、」、2行目に「種別順）」だけが来る形は、いまの選択の2つの値が別の行に割れ、ボタンが何を言っているかが読み取りにくい。「絞り込みと並び順」／「（すべて、種別順）」なら、1行目がボタンの名前、2行目がいまの選択になる。375px は来訪者のいちばん多い幅で、`/play` の一覧は一覧のページの中でも来訪者が多い。

一方、括弧の一続きが1行に収まらないとき（200%）は、builder の区切り（「、」の後ろと名前の文節の切れ目）が、§4 の「一続きが1行に収まらないときだけ、その中で折る」の折り所として良い。括弧の中の区切りを外して1つの文節にすると、`overflow-wrap: anywhere` が字の所で割り、「（読みの五十／音順）」（320px の 200%）や「並び順／（読みの五十音順／）」（375px の 200%。「）」1字の行）になる（`/dictionary/yoji` で区切りを外して測った）。なお 375px の既定の「（すべて、／種別順）」は、括弧の中の `<wbr>` を外しても消えない。ブラウザは `keep-all` でも「、」の後ろを折り所にするので、区切りの並びを変えるだけでは直らない（HEAD の Chromium の `auto-phrase` でも同じ折れで、前からあるもの）。

**直し方の方向**（形は builder が決める）: 括弧の一続きが1行に収まるなら丸ごと次の行へ送り、収まらないときだけ中の区切り（「、」の後ろと名前の文節の切れ目）で折る組み方にする。確かめた一例として、括弧の一続きを `display: inline-block` の要素に入れて測ると次のとおりで、どの状態でも §4 に合い、どの状態でも今より悪くならない:

| 状態                             | 今（builder）                        | inline-block に入れたとき            |
| -------------------------------- | ------------------------------------ | ------------------------------------ |
| `/tools` 320px の既定            | 絞り込みと並び順／（すべて、種別順） | 同じ                                 |
| `/tools` 375px の既定            | 絞り込みと並び順（すべて、／種別順） | 絞り込みと並び順／（すべて、種別順） |
| `/tools` 320px・375px の 200%    | …／（すべて、／種別順）              | 同じ                                 |
| `/dictionary/yoji` 320px の 200% | 並び順／（読みの／五十音順）         | 同じ                                 |
| `/dictionary/yoji` 375px の 200% | 並び順（読みの／五十音順）           | 並び順／（読みの／五十音順）         |

`PhrasedText` は要素の中に字と `<wbr>` だけを置く約束なので（見出しの読み上げのため）、ボタンのラベルで中に要素を置くなら、その約束との関係（ボタンの名前は1続きで読まれる）も説明に書く。直したら、`controlsLabel` の説明を今の組み方だけを言う形に書き直し、試験はラベルの全体を確かめる形にする（`slice` で規則を避けない）。直したあと、上の表の状態と、下の指摘3のページを測り直して記録に残す。

### 指摘2: 値を差し込むラベルの試験が、実際の選択肢の組を回していない

`controlsLabel` は `.ts` で区切りの並び（「絞り込みと」「並び順」と、選んだ値の名前の並び）を組む。`frontend-design` スキルの「実装の技術」は「値を差し込む並びは、差し込む値のどの組でも確かめる」、t5-design.md 10章の頭の (c) は「定義のすべての要素を回す形」と決めている。今の試験は「人生・初級」「色」などの決めた例だけで、一覧の実際の組（`TOOL_KINDS`×`TOOL_SORTS`、`PLAY_KINDS`×`PLAY_SORTS`、並び順だけの一覧の `BLOG_SORTS`・`kanjiListSorts`・`YOJI_LIST_SORTS`・`colorListSorts`、「すべて」を含む）を回していない。指摘1の組み方に合わせて、括弧の外の並びと括弧の中の並びがそれぞれ規則を満たすことを、実際の定義のすべての組で確かめる試験にする（`list-choice-names.test.ts` と同じく、あとから足した選択肢も同じ試験にかかる形で）。

- 漢字と四字熟語の詳細: 区切りの見出しは折れず、見た目の変化は無い（判断3）。
- **`/storybook/list/101` と `/storybook/list/11`**: `src/app/storybook/list/samples.ts`（T5-24 の受け持ち）が並び順の名前を「読みの五十音順」の1続きの字で渡しているため、開閉のラベルが `keep-all` の1つの文節になり、200% で次のように崩れた（HEAD の Chromium は `auto-phrase` で文節で折れていた）。
