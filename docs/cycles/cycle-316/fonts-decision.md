# Web フォントの配り方と表示の速さの条件（決め直し）

作業日: 2026-09-25

[t1a-fonts.md](./t1a-fonts.md) と [t1a-closure.md](./t1a-closure.md) は、計画に書いた転送量の上限「増分0」を動かせない前提にして、それを満たす専用の配信の仕組み（ページごとの切り出し・共通の予備・閉じたページ・自作の解析器）を作り込んだ判断である。増分0は、必要性も達成の見込みも確かめずに置いた線だった（[incident-2.md](./incident-2.md)）。この文書で、Web フォントの配り方と表示の速さの条件を、サイクルの目的（`DESIGN.md` をサイト全体に届ける）に釣り合う形で決め直す。上の2つの文書の判断は取り下げる。レビューは [review-fonts-decision.md](./review-fonts-decision.md)。

## 決めたこと

### 書体と配り方

**見出しの和文は Zen Antique、欧文・数字は IBM Plex Sans を、Next.js の標準の仕組みで配る。本文・UI の和文は端末のゴシックで組む。**

| 役割            | 書体                                                                                                  | 配り方                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 見出しの和文    | Zen Antique（400）                                                                                    | `next/font/google`、`display: swap`、`preload: false`、`adjustFontFallback: false`（自動の代わりの書体は範囲を持たず、読み込みのあいだ「——」「……」を欧文の字形で描くため）                                                                                                                                                                                                                                                                                                                        |
| 本文・UI の和文 | 端末のゴシック（いまの `--font-gothic` の並び: ヒラギノ角ゴ・游ゴシック・Noto Sans JP・`sans-serif`） | 配らない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 欧文・数字      | IBM Plex Sans（400・700）                                                                             | `next/font/local`、`display: swap`、`adjustFontFallback: false`。IBM が配る分割ファイル（`@ibm/plex-sans` の `IBMPlexSans-Regular-Latin1.woff2`・`IBMPlexSans-Bold-Latin1.woff2`、各約 21KB）を手を加えずにリポジトリに置き、OFL.txt を添える（作者自身が配るファイルなので、Reserved Font Name の問いが起きない）。`declarations` で `unicode-range: U+0000-007F` を指定する。代わりの書体は、`local("Arial")` にメトリクスを合わせる値と同じ `unicode-range` を付けた `@font-face` を自分で置く |
| コード          | `ui-monospace`                                                                                        | 配らない（`DESIGN.md` §3 のまま）                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

- いまのサイトは、見出しの Noto Serif JP を `next/font/google`（Google Fonts の `unicode-range` の分割ファイルを、ビルドの時に自分のオリジンに置いて配る形）で配っている（`src/lib/fonts.ts`）。Zen Antique は `next/font/google` の一覧にある（Next.js 16.3.0 の `font-data.json` で確かめた）。
- IBM Plex Sans だけ `next/font/local` にするのは、`DESIGN.md` §3 が Plex で組む範囲を `U+0000-007F` と定めているからである。Google Fonts の latin のファイルは `U+2000-206F` も覆うので、`next/font/google` のままでは和文の中の「——」「……」「“”」まで Plex の欧文の字形（ベースラインに乗る短い線と点）で組まれる。`next/font/google` には `unicode-range` を変える手段が無い。`next/font/local` が自動で作る代わりの書体（`local("Arial")`）にも `unicode-range` が付かず、読み込みのあいだ同じ字が Arial で組まれるので、自動の代わりの書体は止めて、範囲を付けたものを自分で置く。
- 見出しが Zen Antique に無い字を含むときの §3 の規定（その見出しの和文を丸ごと本文の書体で組む）は、ビルドの時に決まる見出し（コードに書かれた見出しと、辞典の項目の名前など、データから描く見出し）を Zen Antique の字の表と照らす試験で確かめる。辞典の「𠮟」などがこの対象である。入力から描く見出しまで網羅する仕組みは作らない。
- `DESIGN.md` §3 の本文・UI の和文を端末のゴシックに書き換え、§4 の連続約物の規定を実装できる形に改める（下の「`DESIGN.md` の変更」）。
- 端末のゴシックの太字（700）が、各 OS で合成太字にならないことを T1 で確かめる（§4「合成太字を作らない」。並びの「Yu Gothic Medium」に 700 を指定すると Windows で合成太字になるという報告がある）。

### 表示の速さの条件

代表の5ページ（[facts-speed-before.md](./facts-speed-before.md)）を、出荷するビルドと変更前のビルドで、同じ環境で各5回測る。

- **転送量**: 変更前と変更後の値を記録する。Web フォントの増分が、下の見込み（全ページで最大 +223KiB）を越えたら、出荷の前に原因を調べる。
- **LCP**: 変更前の5回の幅は 722〜1,980ms あり、5回で見分けられるのは揺れを越える大きな悪化だけである。そこで、**変更後の中央値が変更前の5回の最大を越えたら**、出荷の前に原因を調べて直す。直さずに出すなら、その理由を記録してレビューを受ける。
- **CLS**: 変更後の中央値が変更前を上回ったら、Web フォントの読み込みのずれ（§12）として原因を調べて直す。

## なぜこの形か

判断の材料は、T1a の最初の版（コミット 487e5fc の `t1a-fonts.md`）で、変更前のビルドの前に中継サーバーを置き、フォントの読み込みだけを差し替えて Lighthouse で測った値である（HTML・JS・画像は変更前のまま）。変更前の値もそのとき測り直したもので、[facts-speed-before.md](./facts-speed-before.md) より 3.8〜6.5KiB 小さい。

| ページ                                       | 変更前（総転送量） | 3書体とも `next/font/google` |
| -------------------------------------------- | -----------------: | ---------------------------: |
| 診断のプレイ面 `/play/character-personality` |           554.9KiB |         1,082.8KiB（+527.9） |
| 診断の結果面 `…/result/blazing-strategist`   |           543.7KiB |         1,459.4KiB（+915.7） |
| ツール `/tools/char-count`                   |           488.9KiB |           949.3KiB（+460.4） |
| 辞典の詳細 `/dictionary/kanji/哀`            |         1,428.5KiB |         1,962.5KiB（+534.0） |
| ブログ記事 `/blog/sql-cheatsheet`            |           571.2KiB |         1,471.3KiB（+900.1） |

- **本文の和文を Web フォントにすると、転送量が 1.4〜2.7 倍になる。** 増分の大半は本文の BIZ UDPGothic（400・700 の各124分割、1ファイル平均約 23KB）である。本文の字はページに多く散らばるので、1ページで数十のファイルに触れ、1ファイルのうち使う字は数文字にとどまる。PV の78%が集まるプレイ面で +527.9KiB、Lighthouse のモバイルの既定の回線（約 200KiB/秒）で約2.6秒の読み込みにあたる。83.7% のセッションは1ページで終わるので、来訪者の多くはこの 460〜916KiB を1ページのために払う。
- **本文を端末のゴシックにすると、増分は1ページあたり百 KiB 前後にとどまる。** 同じ版の見積もりで、Zen Antique と IBM Plex Sans だけを配った場合、Web フォントの増分は、代表の5ページと境界の2ページの計7ページで +6〜+85KiB だった（ページごとに読むファイルの集合から計算した値。この計算は、変更前の全ページで、ブラウザが実際に読んだファイルの集合と一致した）。3巡目のレビューが同じ計算を全 3,526 ページに広げたところ、増分の中央値は約 +70KiB、+100KiB を越えるページは 1,163 で、大半は漢字辞典の詳細（2,136 ページ。中央値 約 +92KiB、最大 約 +223KiB）だった（[review-fonts-decision-3.md](./review-fonts-decision-3.md)）。漢字辞典の詳細は字形が主題の面で、見出しの字の多さがそのまま増分になる。この転送量は、字形が主題の要素を刷新後もアンティーク体で組むかを判定する T4 に材料として渡す。フォントの CSS は gzip で約 4KB 減る。増分が出るのは、見出しの分割ファイルが Noto Serif JP から Zen Antique に替わり、Zen Antique の字形が重い（1字あたり平均約 355B）ことと、数字の Zilla Slab が IBM Plex Sans に替わることによる。
- **個性は保たれる。** `DESIGN.md` §3 は本文の仕事を読みやすさとし、§1 は個性を罫線・見出しの書体・コントロールが担うと定めている。本文を端末のゴシックにしても、巨大なアンティーク体の見出し・罫線・コントロールは変わらない。端末のゴシック（iOS・macOS のヒラギノ角ゴ、Windows の游ゴシック、Android の Noto Sans CJK JP。Android では並びの末尾の `sans-serif` と `lang="ja"` で選ばれる）は、各 OS が日本語の標準として備え、長文の本文に使われてきた書体で、いまのサイトの本文もこの並びで組んでいる。
- **捨てるもの。** 本文の字形が端末によって変わる。BIZ UDPGothic の、読みやすさのための字形の工夫は得られない。約物が詰まる組み（§3）は、`text-spacing-trim` を実装しているブラウザでだけ得られ、実装していないブラウザでは約物が全角のまま並ぶ。和文と欧文の字面の大きさ（§4 和欧混植）は、端末のゴシックの字面が OS ごとに違う（游ゴシックは小さい）ので、OS ごとの近似になる。これを、来訪者の多くが1ページのために払う 460〜916KiB と比べて、払わせるほどの得ではないと判断する。
- **専用の配信の仕組みを作らない理由。** 本文まで Web フォントにしたうえで転送量を抑える道（ページごとの切り出し）は、T1a で7巡の設計を要し、そのたびに自作の解析器の穴が見つかった。仕組みの複雑さと保守の負担が、本文の書体の得に見合わない。

## `DESIGN.md` の変更

`DESIGN.md` §3・§4 を次のとおり書き換える（T1 で行う）。

- 表の「本文・UI の和文」を「端末のゴシック」にし、並び（ヒラギノ角ゴ・游ゴシック・Noto Sans JP・`sans-serif`）を書く。`system-ui` は使わない（Windows では Yu Gothic UI に解決され、OS の言語によっては中国語の字形が出る）。
- 「本文の仕事は読みやすさである」の箇条の、BIZ UDPGothic の理由を、端末のゴシックを使う理由（日本語の本文に使われてきた書体が端末に備わっていて、来訪者に転送量を払わせない）に書き換える。
- §4 の「約物: 連続約物のアキ調整」を、「連続約物のアキを `text-spacing-trim` で詰める（実装しているブラウザで効き、ほかでは全角のまま組む）」に改める。
- §4 の「和欧混植」の「両者の字面の大きさとベースラインが揃っていること」を、「欧文の字面の大きさとベースラインを、主要な OS の端末のゴシックに合わせる」に改める。
- 「Zen Antique に無い字を含む見出しは、その和文を丸ごと本文書体で組む」は残す（本文の書体は端末のゴシックになる）。

[options.md](./options.md)「`DESIGN.md` を変えるとき」の手順（速さに効く規定は、来訪者に払わせる量を測り、規定の得と比べて示す）に沿って、上の表と「なぜこの形か」でこの変更を示した。

`frontend-design` スキルの「書体を変えたら、サブセットを作り直す。収録する字種は、サイトで実際に使う字から決める」は、この判断と食い違う（自前の切り出しに戻る入口になる）ので、配り方の記述に改める。
