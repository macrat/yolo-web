# Web フォントの配り方と表示の速さの条件（決め直し）

作業日: 2026-09-25

[t1a-fonts.md](./t1a-fonts.md) と [t1a-closure.md](./t1a-closure.md) は、計画に書いた転送量の上限「増分0」を動かせない前提にして、それを満たす専用の配信の仕組み（ページごとの切り出し・共通の予備・閉じたページ・自作の解析器）を作り込んだ判断である。増分0は、必要性も達成の見込みも確かめずに置いた線だった（[incident-2.md](./incident-2.md)）。この文書で、Web フォントの配り方と表示の速さの条件を、サイクルの目的（`DESIGN.md` をサイト全体に届ける）に釣り合う形で決め直す。上の2つの文書の判断は取り下げる。

## 決めたこと

### 書体と配り方

**見出しの和文（Zen Antique）と欧文・数字（IBM Plex Sans）を、いまのサイトと同じ `next/font/google` で配る。本文・UI の和文は端末のゴシックで組む。**

| 役割            | 書体                      | 配り方                              |
| --------------- | ------------------------- | ----------------------------------- |
| 見出しの和文    | Zen Antique（400）        | `next/font/google`、`display: swap` |
| 本文・UI の和文 | 端末のゴシック            | 配らない                            |
| 欧文・数字      | IBM Plex Sans（400・700） | `next/font/google`、`display: swap` |
| コード          | `ui-monospace`            | 配らない（`DESIGN.md` §3 のまま）   |

- いまのサイトは、見出しの Noto Serif JP をこの形（Google Fonts の `unicode-range` の分割ファイルを、ビルドの時に自分のオリジンに置いて配る）で配っている（`src/lib/fonts.ts`）。Zen Antique と IBM Plex Sans は `next/font/google` の一覧にある（Next.js 16.3.0 の `font-data.json` で確かめた）。
- 見出しの書体が Zen Antique に無い字を含むときの §3 の規定（その見出しの和文を丸ごと本文の書体で組む）は、コードに書かれた見出しを Zen Antique の字の表と照らす試験で確かめる。データや入力から描く見出しまで網羅する仕組みは作らない。
- `DESIGN.md` §3 の本文・UI の和文を「端末のゴシック」に書き換える（下の「`DESIGN.md` の変更」）。§4 は変えない。

### 表示の速さの条件

- **転送量**: 代表の5ページ（[facts-speed-before.md](./facts-speed-before.md)）で、変更前と変更後の値を記録する。Web フォントが増やす量は、下の見込み（数十 KiB）の桁にとどまることを確かめる。桁を越えて増えたら、出荷の前に原因を調べる。
- **LCP**: 代表の5ページを、変更前と変更後で同じ環境で5回ずつ測る。中央値が変更前より 10% を超えて悪化し、それが揺れの範囲を越えるなら、出荷の前に原因を調べて直す。直さずに出すなら、その理由を記録してレビューを受ける。
- **読み込みのずれ（§12）**: 代表の5ページの CLS を、変更前と変更後で比べる。

## なぜこの形か

判断の材料は、T1a の最初の版（コミット 487e5fc）で、フォントの読み込みだけを差し替えて Lighthouse で測った値である（変更前のビルドの前に中継サーバーを置いた試作。HTML・JS・画像は変更前のまま）。

| ページ                                       | 変更前（総転送量） | 3書体とも `next/font/google` |
| -------------------------------------------- | -----------------: | ---------------------------: |
| 診断のプレイ面 `/play/character-personality` |           554.9KiB |         1,082.8KiB（+527.9） |
| 診断の結果面 `…/result/blazing-strategist`   |           543.7KiB |         1,459.4KiB（+915.7） |
| ツール `/tools/char-count`                   |           488.9KiB |           949.3KiB（+460.4） |
| 辞典の詳細 `/dictionary/kanji/哀`            |         1,428.5KiB |         1,962.5KiB（+534.0） |
| ブログ記事 `/blog/sql-cheatsheet`            |           571.2KiB |         1,471.3KiB（+900.1） |

- **本文の和文を Web フォントにすると、転送量がほぼ倍になる。** 増分の大半は本文の BIZ UDPGothic（400・700 の各124分割、1ファイル平均約 23KB）である。本文の字はページに多く散らばるので、1ページで数十のファイルに触れ、1ファイルのうち使う字は数字にとどまる。PV の78%が集まるプレイ面で +528KiB、Lighthouse のモバイルの既定の回線（約 200KiB/秒）で2秒あまりの読み込みにあたる。83.7% のセッションは1ページで終わるので、来訪者の多くはこの量を1ページのために払う。
- **本文を端末のゴシックにすると、増分は数十 KiB にとどまる。** 同じ試作で、見出しの Zen Antique と IBM Plex Sans だけを配った場合、Web フォントの増分は7ページで +6〜+85KiB だった（フォントの CSS は gzip で約 4KB 減る）。いまの見出しの明朝の分割ファイルが、Zen Antique の分割ファイルに置き換わるだけだからである。
- **個性は保たれる。** `DESIGN.md` §1 は、本文の仕事を読みやすさとし、個性は罫線・見出しの書体・コントロールが担うと定めている。本文を端末のゴシックにしても、巨大なアンティーク体の見出し・罫線・コントロールは変わらない。端末のゴシック（iOS・macOS のヒラギノ角ゴ、Android の Noto Sans CJK、Windows の游ゴシック・メイリオ）は、どれも画面で読むために作られた書体である。いまのサイトの本文もこれで組んでいる。
- **捨てるもの。** 本文の字形が端末によって変わる。BIZ UDPGothic の、約物が詰まる組み（§3）と、読みやすさのための字形の工夫は得られない。これを、来訪者の多くが1ページのために払う 0.5〜0.9MB と比べて、払わせるほどの得ではないと判断する。
- **専用の配信の仕組みを作らない理由。** 本文まで Web フォントにしたうえで転送量を抑える道（ページごとの切り出し）は、T1a で7巡の設計を要し、そのたびに自作の解析器の穴が見つかった。仕組みの複雑さと保守の負担が、本文の書体の得に見合わない。

## `DESIGN.md` の変更

`DESIGN.md` §3 を次のとおり書き換える（T1 で行う）。

- 表の「本文・UI の和文」を「端末のゴシック（`system-ui` の和文）」にする。
- 「本文の仕事は読みやすさである」の箇条の、BIZ UDPGothic の理由を、端末のゴシックを使う理由（画面で読むための書体が端末に備わっていて、転送量を払わせない）に書き換える。
- 「Zen Antique に無い字を含む見出しは、その和文を丸ごと本文書体で組む」は残す（本文の書体は端末のゴシックになる）。

[options.md](./options.md)「`DESIGN.md` を変えるとき」は、速さに効く規定の変更を「計画で先に決めた上限を越えることを示す」ことに結び付けていた。上限を取り下げたので、その手順も「測った害と、規定が来訪者にもたらす得を比べて示す」に改める。この変更は、上の表と「なぜこの形か」で示した。
