## 判定: 改善指示

2巡目の5つの指摘は、どれも直っている。押しても動かないこと（押したときに何かが動いた回数: 前 149〜150 → 後 0）、ボタンの字がボタンの外に出ないこと（前 36 → 後 0）、写せなかったことを面の字・名前・知らせの3つで言うことは、来訪者にとってはっきりした得であり、unix-timestamp と伝統色の配色では、値の折れも前より減った（押す前の字の行の比べで、行が減った所が25）。

一方で、200% の狭い幅では、押す前の面で見出しや値が前より細かく折れる所が新しく8つ出ており（指摘1）、押したあとの面の字も「コピー済／み」「コピー失／敗」と1字だけの行を作る（指摘2）。どちらも、面の字の場所の取り置きの組み方から来ており、DESIGN.md §6 がこのタスクで書いた「取っておく場所のために値の幅を削ることはしない」と、§4 の折り方に反する。

## 指摘

### Major

#### 1. 200% の狭い幅で、押す前の面から、取り置きの幅が見出しと値を削り、1字だけの行や1字ずつの縦の並びを新しく作る

- 押す前の面の、main の中のすべての字の行を前（c2c1f48）と後（8e0e564）で比べ、行が増えた所が8つあった。どれも 200% で、既定の字の大きさでは増えていない。
  - cron-parser（375px・200%）: 結果の値「`* * * * *`」が、前は2行（`* * *` / `* *`）だったのが、後は5行（1行に1字）になる。値の箱は幅が約 100px に縮み、ボタン「コピー」は右に大きな空きを持って離れて出る（撮った絵で分かる）。`.builtExpression` の `flex: 1`（基準の幅 0）の値が、取り置きの箱（いちばん長い「コピー済み」の幅）の残りしかもらえないためである。
  - 結果の見出しが1字だけの行を作る: text-replace「置換結／果」、fullwidth-converter・kana-converter・line-break-remover「変換結／果」、dummy-text「生成結／果」（いずれも 320px・200%。前は1行）、base64「Base64出／力」（375px・200%。前は1行）。image-base64 の「Data URI」も 320px・200% で2行になった（語の切れ目なので§4 には合う）。
  - 既定の字の大きさでは、hash-generator の 1280px で値の折れる所が数字数個ぶん前へ寄る（行の数は同じ）。取り置きが値の幅を削っていることは、ここでも読み取れる。
- 来訪者への影響: 文字を大きくして使う来訪者は、コピーを押す前から、道具の答えそのもの（Cron 式）が1字ずつの縦の並びになり、結果の見出しが「置換結」/「果」のように読みにくく折れる。押さない来訪者も含めて全員が損をする形で、§6 の「取っておく場所のために値の幅を削ることはしない。……場所が足りない並びでは、ボタンを名前の行か値の次の行に置き、値に行の幅を渡す」にも、§4 の「1字だけの行」にも反する。T4-16 の3巡目の決定が完了の条件にした「どのページも撮り比べる」の、押す前の面での見落としである（AP-I14）。
- 直し方の方向: 取り置きが並びの隣を削らない組みにする。たとえば、狭いときは取り置きの箱のほうが先に縮む（指摘2の折り所で「コピー」/「済み」と2行に折れる幅まで）ようにし、それでも見出しや値の文節が1行に入らない並びは、ボタンを次の行に送る。cron-parser の値のように基準の幅が 0 で縮むものは、値が語の途中で折れない幅を先に取る。直したあと、この8か所を含む全ページで、押す前の面の字の行の数が前より増えないことを、200% を含めて確かめる。

#### 2. 200% の狭い幅で、押したあとの面の字が「コピー済／み」「コピー失／敗」と折れ、1字だけの行を作る。同じ幅でも道具によって折れる所が違う

- 押したあとの面の字の行を測ると、200% の 320px で、9つの道具（business-email・dummy-text・fullwidth-converter・image-base64・kana-converter・line-break-remover・password-generator・text-replace・unix-timestamp）が「コピー済／み」「コピー失／敗」と折れる。375px・200% では base64・markdown-preview が同じ形になる。一方で、csv-converter・html-entity・色の辞典4ページと、320px の base64・markdown-preview では「コピー／済み」「コピー／失敗」と語の切れ目で折れる。どちらになるかは並びの残りの幅しだいで、来訪者には違いの理由が無い。
- 原因は、`CopyButton.module.css` の `.reserve` が画面の幅 20em 未満で `overflow-wrap: anywhere` を持ち、面の字を任意の字の間で折るためである。「コピー済み」「コピー失敗」は「コピー」と「済み」「失敗」の2語で、折ってよい所は1つしかない。
- 来訪者への影響: 押した瞬間に、目を向けているボタンの字が「コピー済」/「み」になり、壊れて見える。AP-I14 が例に挙げた「コピ／ー」と同じ種類の崩れで、§4 の「200% の1字だけの行は、1行に収まらない文節の中の折れから出たものに限って受け入れる」にも当たらない（「済み」は2字で1行に入る）。前（c2c1f48）はボタンの字がボタンの外にはみ出していたので、それよりはよいが、このタスクの完了の条件（200% で字が枠の外へ出ない）を、別の崩れで満たしている。
- 直し方の方向: 面の字の折り所を「コピー」と「済み」「失敗」の間の1つに決める（`<wbr>` と `word-break: keep-all` で、`anywhere` を使わない）。取り置きの箱も同じ所でだけ折れるので、箱の最小の幅は「コピー」の幅になり、指摘1の取り置きの縮み方ともかみ合う。直したあと、23の道具と色の辞典を 320・375px × 200% で押し、どの面の字も1字だけの行を作らないことを確かめる。

### Minor

#### 3. DESIGN.md §8 の「結果を写すコピーのボタン」が、§6 が決まりの外に置いた共有の「結果をコピー」と、言葉で取り違えやすい

- §6 は規則の対象を「値を写すコピーのボタン」と呼び、共有の区画の「URLをコピー」「結果をコピー」を外に置いた（2巡目の指摘2は直った）。ところが §8 の「結果」の節（391行・404行）は、同じボタンを「結果を写すコピーのボタン」と呼び続けており、`ResultBox` のコメント（`src/components/ResultBox/index.tsx` 44行）と storybook の説明文（1388行）も同じ言い方である。§8 を読んだ人には、「結果を写す」ボタンが §6 の外の「結果をコピー」と同じものか分からない。
- 直し方の方向: §8 と部品のコメントも「値を写すコピーのボタン（§6）」、あるいは「結果の値を写すコピーのボタン」のように、§6 の名前にそろえる。

#### 4. storybook のボタンの見本が、`CopyButton` を使わない「結果をコピー」のボタンを出している

- `src/app/storybook/StorybookContent.tsx` 604〜620行の「プライマリでない、実行するボタン」の見本は、ただの `Button` に「結果をコピー」と書き、無効の見本も「結果をコピー」である（T4-4c の前からある）。見本帳を見た作り手には、§6 の面の字（「コピー」）に従わず、`CopyButton` も使わないコピーのボタンが、正しい組み方に見える。フロントエンドのスキルが「値を写すコピーのボタンは `CopyButton` で組む」と言うのとも食い違う。
- 直し方の方向: `Button` の見本の字を、コピーでない実行の操作（「変換する」など）にする。

#### 5. `CopyButton` に無効の理由を渡す道が無く、写すものが無いあいだの無効のボタンが §6 の「理由を文字で添える」を満たせない

- 29か所の `CopyButton` が `disabled` を渡し（例: base64 の `disabled={!output}`）、押す前は破線の枠の「コピー」だけが出る。§6 の無効は「理由を文字で添える」で、`Button` は `disabledReason` を持つが、`CopyButton` はそれを受けない。storybook の「無効（写すものが無いとき）」の見本も理由を出さない。
- index.md の T5 には「道具の無効のボタンに、理由の文（`Button` の `disabledReason`）を添える」があるが、コピーのボタンはこのタスクで部品の中に入ったので、T5 の作り手が道具の側で直せない。
- 直し方の方向: `CopyButton` が `disabledReason` を受けて `Button` に渡すようにし、見本にも理由を足す。道具ごとの理由の文を T5 で書くなら、その受け持ちを index.md の T5 の項目に「CopyButton を含む」と書いておく。

#### 6. 写したあとの知らせの文が、面が戻ったあともボタンのすぐ後ろに残る

- ariaSnapshot で見ると、「コピー済み」が2秒で「コピー」に戻ったあとも、見えないライブリージョンに「出力をコピーしました」が残る（base64・business-email・toki で同じ）。読み上げの仮想カーソルで読み進める来訪者は、そのあと入力を変えて新しい結果が出たあとも、「出力をコピー ボタン」の次に「出力をコピーしました」を聞き、新しい結果も写したかのように受け取りうる。
- 直し方の方向: 面が「コピー」に戻るときに知らせの文を空にする（空にしても読み上げは何も言わない）。「コピー失敗」は面と同じく次に押すまで残してよい。

## 2巡目の指摘の直り方（確かめた結果）

1. 写せなかったあいだの名前: 直った。名前は「出力のコピー失敗」「HEXのコピー失敗」「メール全文のコピー失敗」のように見えている字「コピー失敗」を含み、次に写せると「〜をコピー」に戻る。「コピー済み」のあいだは名前を変えない。27ページのすべてのボタンで、押す前・写せたとき・写せなかったときの名前が、この決まりどおりだった。DESIGN.md §6 と部品のコメントも同じことを言っている。
2. §6 の共有の区画との線引き: 直った。「道具や辞典が出した値を、来訪者がその場で貼り付けて使うために写すボタン」と目的で言い、共有の区画の操作は「人に渡すための操作で、面の字を変えず、区画の知らせの行で言う」と、実際の `ShareButtons`・`FudaActions`・`InviteFriendButton` の振る舞いに合う言い方になった。§8 の呼び名だけが残る（指摘3）。
3. unix-timestamp の値の字の始まり: 直った。どの幅と字の大きさでも、名前の字と値の字の左端が同じ（例: 375px 既定で x=50.0 と 50.0）。
4. unix-timestamp のボタンの位置のばらつき: 直った。7行のどれも、同じ幅と字の大きさではボタンの右端と名前との上下の関係が同じ（320・375px の 200% はどの行も次の行、ほかはどの行も名前の行）。
5. 同じ名前のボタン: 直った。日時から求めた側は「日時から求めた秒をコピー」「日時から求めたミリ秒をコピー」になり、ページの中で名前が重ならない。
6. フックの形: 直った。`useCopyToClipboard` は1つのボタンの `copy` と `status`（idle・copied・failed）だけを返し、キーや `resetDelay`、面の字は残っていない。使うのは `CopyButton` だけで、テストの名前も今の使い方で書かれている。道具のソースに、道具ごとのコピーの文言（`COPIED_LABEL`・`copiedKey`・「コピーしました」）は残っていない（残るのは道具のテストの「コピー済み」の確かめだけ）。

## 測った結果のまとめ

- 押したときの動き: 押したボタンの升（取り置きの箱）とそのまわりの要素・ページの高さは、どの組みでも動かなかった（後 0 / 684 回。前は 149〜150 / 684 回が動いた）。押せる範囲とリングは、いま出している字に沿って縮み伸びする（§6 のとおり）。
- ボタンの字がボタンの外に出る: 後 0（前 36。200% の「コピーしました」）。押す前の「コピー」が「コピ／ー」と折れる所は無い。
- フォーカスのリング: キーボードで押したどの回も、ボタンにフォーカスが残り `:focus-visible` のリングが出る。ライト・ダークとも、「コピー済み」「コピー失敗」の面でリングが字を囲むのを撮った絵で確かめた。
- 知らせ: 押すたびにライブリージョンに新しい要素が入る（同じ文が続いても、写せた2回・写せなかった2回・写せた1回の5回すべて）。文は「〜をコピーしました」「〜をコピーできませんでした」。
- 色の辞典の表が 200% で画面の外に出る件: 200% の toki・aikobicha・shironeri の 320px と ai の 320・375px で、3つのボタンがどれも画面の右端（320px）を越えて出る（右端 364〜378px。ページは横に送れない）。前（c2c1f48）も同じ5つの組みの同じボタンが、同じ右端で画面の外に出ており、T4-4c の前からある。builder の言う24件とは数え方が違い、私の数え方では 5組 × 3ボタン の15件である。t4-design.md 1177行の決定どおり T5 の受け持ちで、index.md 278行にも書かれている。
- 既定の字の大きさ: 320・375・1280px のどれでも、押す前の面の字の行の数が前より増えた所は無い（hash-generator の 1280px で値の折れる位置が寄るだけ）。

## アンチパターンの確かめ（docs/anti-patterns/implementation.md）

- AP-I01（来訪者目線）: 押す前・押したあとの両方を来訪者の目で見た。押したあとの得は大きいが、200% の押す前の面で全員が損をする所があるので、指摘1・2にした。
- AP-I02（場当たりの回避）: 部品に面の字・名前・知らせ・取り置きを集めた形で、道具ごとの手当ては unix-timestamp のコンテナクエリなど並びの組みに限られている。ただ、`.reserve` の 20em を境に `anywhere` と `break-word` を切り替える形は、折り所を決めずに字の数で逃げている（指摘2）。
- AP-I03（Core Vitals・バンドル）: 押しても升が動かないので CLS は前より良い。部品は小さく、重いデータの読み込みは無い。
- AP-I04（指標を目的にした配置）: 該当なし。
- AP-I05（目的に無関係の足し算）: 該当なし。足したのは写せなかったときの知らせで、道具の目的に沿う。
- AP-I06（反対の極端）: 2巡目の指摘への直しは、名前を常に変える／常に変えないの両極でなく、残る面だけ名前に含める形で、極端に振れていない。
- AP-I07（jsdom で見えない崩れ）: 単体テストは通るが、指摘1・2は本番のビルドを実際の幅と字の大きさで開かないと見えない。完了の確かめに、200% の押す前の面の字の行の比べを入れる必要がある。
- AP-I08（DESIGN.md に無い表現）: 新しい見え方は足していない。面の字は §6 に書かれ、取り置きも §6 に書かれている。
- AP-I09（コミットの順）: 3つのコミットはどれも部品と使う側を同じコミットに入れており、途中で壊れる順ではない。
- AP-I10（@keyframes）: 該当なし。
- AP-I11（タイマーの片付け）: フックはタイマーを `useRef` で持ち、外すときと写し直すときに止める。外したあとの状態の変更を試すテストもある。
- AP-I13（撤去の残骸）: `COPIED_LABEL`・`copiedKey`・`failedKey`・`resetDelay` を src の全体で探し、道具と辞典のソースに残っていないことを確かめた。
- AP-I14（共有の部品の全ページの撮り比べ）: 27ページを 320・375・1280 × 既定・200% × ライト・ダークと3つの状態で比べた。この比べで指摘1・2が見つかった。builder の撮り比べは、押す前の面で見出しや値の折れが前より増えていないかを見ておらず、200% の押したあとの「コピー済／み」も見落としている。

作業の進め方（docs/anti-patterns/workflow.md）:

- AP-WF01（最後の直しのあとのレビュー）: 8e0e564 のあとにこの3巡目があり、形は守られている。
- AP-WF05（すべての画面・ライトとダーク）: 上のとおり、このレビューで全ページを撮った。
- AP-WF09（形だけの確かめ）: 2巡目の6つの指摘を、どれも数か絵で確かめた。
- AP-WF14（数を自分で集計する）: builder の「24件」をそのまま採らず、自分で測って15件（前と同じ）とした。

## ほかに確かめたこと（指摘ではない）

- DESIGN.md §6・§8 とフロントエンドのスキルに、経緯の書き方や「以前は」のような跡は無く、今の決まりとして読める（§8 の呼び名だけ指摘3）。
- business-email の「メール全文をコピー」は、200% の 320px で「メール全／文を／コピー」と折れる。「メール全文を」がボタンの幅（約 200px）に入らないので §4 の受け入れの範囲だが、前はボタンの外にはみ出していたので良くなっている。
