## 指摘

### 1. 2語をつないだ比べで、つないだ所でない所に語の中の折り所が残り、index.md の完了の条件を満たさない。残る形は builder の報告より広い

index.md の PM の決定は、完了の条件に「`src/` の語から2語をつないだ比べで、つないだ所以外に新しい折り所を置かない」ことを足した。上の比べでは、種ごとに 15〜27 組が新しい折り所を持ち、そのうち 5〜8 組が語の中である。builder の報告（16 組、語の中は「プログラマ|ティック」の3組だけ）は1つの種の結果で、語の中の形は「プログラマ|ティック」だけではない。

形は2つである。

- **前の語の終わりが欠片に刻まれる**: 「フレンド|リー」「トレーサ|ビリ|テ|ィ」「プログラマ|テ|ィ|ッ|ク」「ハンター|ズ」。前の語の終わりの欠片が、次の辞書に無い外来語とつながり、「リーバリデーター」「ティックジェネレーター」が1つの語になる。
- **前の語が次の語の頭を取る**: 「ホバート|ラン|ジ|ション」「フロート|ラフ|ィ|ッ|ク」「クラスト|ラフ|…」。辞書が「ホバー＋ト」を「ホバート」（地名）として取り、次の語の残りが2字以上の欠片で始まるので、頭の欠片が1字のときの見分け（`firmHead`）が効かない。

どちらも、辞書の刻みそのものが語の境目を誤っている（「フロー|トラフィック」と「フロート|ラフィック」は字の並びでは区別できない）ので、この決め方の手がかりでは見分けられない。「ホバートランジション」は CSS の記事の見出しや道具の名前として十分に来うる。語の中の `<wbr>` は、続きが1行に収まる広い画面でも行の終わりに来れば使われる（§4）ので、HEAD より悪い。

手がかりの強さを確かめた（`pb-*.ts` の差し替えで、種7と23の2つ）。

- `firmHead`・撥音の決まり・語尾の3字の決まりは、どれを外しても、新しい折り所が増えるか、指摘2（リング）が戻る。今の決め方の部品は、どれも仕事をしている。
- `MIN_KATAKANA_WORD_BEFORE_JOINED` を 4→5 にすると、語の中の折り所は「プログラマ|ティック」の形（前の語が5字）だけになり、上の2つの種では0組になる（新しい折り所は 9・8 組で、どれも語の切れ目）。email-validator（前の語は「メールアドレス」）と password-generator（「パスワード」）は保たれる。失うのは、前の語が4字のときの正しい折り所（カスタム／プロパティ、カラー／パレット／ジェネレーター、ドメイン／オーソリティ、ランダム／シャッフル、テキスト／ジェネレーター、フォント／レンダリング）で、これらは HEAD と同じく分けなくなる（悪くはならない）。今それらが出るのはどれも記事の本文の見出しか本文の行で、区切られていないので、来訪者に見える所は変わらない。

次のように直す。

- builder は、2語をつないだ比べを少なくとも3つの種で走らせ、語の中の折り所をすべて挙げて報告する（形ごとに数える）。
- builder は、上の2つの形を減らす決め方を比べる。`MIN_KATAKANA_WORD_BEFORE_JOINED` を 5 にする案は、語の中の折り所をいちばん多く減らし、今見える所を何も失わない。正しい折り所を失うのは HEAD と同じ形なので、語の中の `<wbr>` を置くより害が小さい（語の中の `<wbr>` は広い画面でも使われ、分けないことは続きが1行に入らないときだけ効く）。5 にするなら、`つないだ語と、となりの語のあいだで分ける` の試験の「AIカラーパレットジェネレーター」「CSSカスタムプロパティ」を、前の語が5字以上の名前に置き換え、4字の前の語の名前（「フレンドリーバリデーター」「ホバートランジション」）を「分けない」側に足す。
- どの決め方でも残る語の中の折り所（少なくとも「プログラマ|ティック」の形）は、完了の条件を満たさない。PM は、残る組の一覧と、その形が辞書の刻みから見分けられないことを見たうえで、完了の条件をどう扱うか（残りを受け入れるなら、どの形を受け入れるか）を index.md に書く。受け入れるなら、`katakanaWordStarts` の注記に、見分けられずに語の中に折り所を置く形（前の語の終わりが欠片に刻まれるとき）を、決め方の性質として書く。
- 直したら、`src/` の前と後の比べと、2語をつないだ比べをやり直す。

### 2. コードの注記に、決め方と食い違う例がある

`katakanaWordStarts` の注記の最後の文は、「どこまでが1つの語かを決められないので、続きの中には語の頭を置かない（「リ|ファクタ|リング」「デザイン|トーク|ン」「レン|ダ|リング」）」と書く。

- 「デザイン|トーク|ン」は、撥音の決まりで「トークン」になり、欠片が無くなるので分ける（試験も「デザイン」「トークンの」「移行」を求めている）。決められない例ではない。
- 「レン|ダ|リング」は、つないで語尾を付けた「レンダリング」が続きの唯一の単位になるので、中に語の頭が無いだけで、決められないのではない。前に辞書の語があれば「フォント／レンダリング」「サーバー／レンダリング」と分ける。

決められない例は、「リ|ファクタ|リング」（頭の欠片が続きの途中にある）、「アク|セ|スト|ラッカー」、「リュウ|グ|ウノ|ツ|カイ」（前の語が短い）、「サプライ|ズ|ガ|ッ|コウ」（頭が1字）のように、決め方のどの条件で外れるかが分かる例に替える。

あわせて次を直す。

- `LOANWORD_SUFFIX` の注記は、この3字を外来語の終わりとしか書かないが、「リング」「キング」は語そのもの（ring・king）でもあり、そのときも前に付けるので「フォーカスリング」を分けない。決め方の性質として、そう書く。
- `settled` の `units.length === 1` は、つないだ語が続きの唯一の単位のとき `units[index - 1]` を読まないための条件だが、式からはそう読めない。単位が1つなら先に返すなど、条件の役目が読める形にする。

### 3. `docs/knowledge/playwright-mcp.md` の測り方が、片仮名の欠片の切れ目を語の切れ目に数える

71 行目は、名前に括弧で数を添えたものの折れを「名前の中の語の切れ目（`Intl.Segmenter` の語の境目）と始め括弧の直前のどちらでもない所」で数えると書く。`splitNameAtWords` は `wordStartsOf` の語の頭を使うので、T5-29 の後は「バリ|デー」の切れ目は語の切れ目ではない。SKILL.md の 46 行目だけを直すと、同じ測り方の2つの文書が違うことを言う。SKILL.md の「実装の技術」の5の語の頭を指すように直し、T5-29 のコミットに入れる。

### 4. SKILL.md の測り方が、測る人が得られない語の頭を指す

46 行目は「片仮名の続きの中は `katakanaWordStarts` が組み直した語の頭だけ」で数えると書く。`katakanaWordStarts` と `wordStartsOf` は書き出されておらず、`phrase-breaks.ts` は `server-only` を読み込むので、測るスクリプト（ページの中の JavaScript か、Node のスクリプト）からはそのまま呼べない。第1回と今回のレビューは、`server-only` の行を除いた写しを作って測った。測る人が決め方を自分で書き直すと、決め方とずれる。語の頭を得る方法（例: 語の頭を返す関数を書き出し、Node で要素の字から語の頭を求めてページの測りに渡す）を決め、SKILL.md（または knowledge の書き方の要点）に書く。

### 5. index.md の PM の決定の「公開中の見出し」は事実と違う（PM への指摘）

index.md の「T5-29 のレビュー（review-t5-29.md）を受けた PM の決定」は、「リング」の誤りを「公開中の見出し「フィルタ／リング／パイプライン」など」とする。これは第1回のレビューの指摘2の誤りを写したもので、記事の本文の h2・h3 は区切らず、本番のビルドの HTML にも `<wbr>` は無い。「リング」の直しは今見える所を何も変えず、これから来る見出しと名前のための直しである。決めたこと（T5-29 で直す）はそのままでよいが、PM は理由の事実を index.md で正す（サイクルの文書なので、正したことを書き足す形でよい）。

## DESIGN.md と SKILL.md の T5-29 の行だけをステージする

`git add -p` は使えないので、1行の置き換えだけの差分を作って索引に当てる。3つの行は、どれも1行を1行に置き換えるので、行の番号は HEAD と作業ツリーで同じである。

```sh
cd /home/user/yolo-web
git diff -U0 DESIGN.md \
  | awk '/^@@/{keep=($0 ~ /^@@ -109 /)} /^(diff|index|---|\+\+\+)/{print;next} keep' \
  > tmp/design-t529.patch
git diff -U0 .claude/skills/frontend-design/SKILL.md \
  | awk '/^@@/{keep=($0 ~ /^@@ -(46|129) /)} /^(diff|index|---|\+\+\+)/{print;next} keep' \
  > tmp/skill-t529.patch
git apply --cached --unidiff-zero tmp/design-t529.patch tmp/skill-t529.patch
git diff --cached -U0 | grep '^@@'   # @@ -109 +109 @@ と @@ -46 +46 @@・@@ -129 +129 @@ だけが出る
```

写しの索引（`GIT_INDEX_FILE`）で試し、ステージされるのが DESIGN.md の 109 行目と SKILL.md の 46・129 行目だけで、T5-28 の行（DESIGN.md 82・124、SKILL.md 123）が作業ツリーに残ることを確かめた。行を直したあとは、`@@` の行の番号を `git diff -U0` で見直してから当てる。
