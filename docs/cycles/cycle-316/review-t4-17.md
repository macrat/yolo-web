## 指摘

### Major-1: セルの語の切れ目が語の中に入り、語が割れる

`Intl.Segmenter` の語の切れ目は、複合語や外来語を語の中で分ける。そこに `<wbr>` を置き `keep-all` で組むので、表のセルが語の途中で割れる。設計 5-2 の「セルの字が語の途中で割れない」に反する。

- 実際に割れているもの（どれも1字だけが行に残る）: 「リ／ロード時の変化」（nextjs-hydration-mismatch-seeded-random。**1280px でも**割れる）、「無／指定」（cron-cheatsheet。1280px でも）、「コ／ロケーション最重視」（nextjs-directory-architecture）、「リ／ダイレクトの扱い」（url-structure-reorganization）、「全／組み合わせ」（sql-cheatsheet・ai-agent-concept-rethink-2）、「別／ディレクトリ」（git-command-cheatsheet）、「量／指定子」（regex-cheatsheet）、「副／リンク」（clickable-list-row-stretched-link）、「正／バイアス」、「全／ページ一律」など、11本・12表。画像は `tmp/cycle-316/rv-t4-17/hyd-1280.png`・`cron2-375.png`。
- 語の切れ目ごとに折れるので、助詞だけの行（「ユーザー／が／「見た目の文字数」を」の「が」、「メインスレッド／の」など）も多く出る。320px では 1字だけの行が 1003 行（変える前の 3398 行よりは減った）。
- サイトはすでに、見出しを文節で折る仕組み（`src/lib/phrase-breaks.ts`。BudouX と、行頭・行末の禁則と、数字の後ろと丸括弧の中で折らない規則）を持つ。`markdown-extensions.ts` はこれと別の規則（語の切れ目と、その場の例外）で2つ目の区切りを作っており、同じサイトで折り方の考え方が2つになっている。
- 直し方: 記事（サーバーで組む）の表のセルは、文節の区切りで折る。markdown-preview はクライアントで組むので、BudouX の表を配るか、別の形にするかを決める必要がある（`phrase-breaks.ts` は server-only）。文節で折るとセルの最小の幅が広がり、横に送る表が増えるので、その数も測って決める。**折り方の考え方を決め直すことなので、planner が設計（5-2）を直してから builder が組む。**

### Major-2: 何も隠れていない表が「横に送る表」になる（2〜8px のはみ出し）

375px で、はみ出しが 12px 以下の表は 15表ある。そのうち 13表は、**字は1字も枠の外に出ておらず**、はみ出しは最後の列のセルの右の余白（8px）だけだった（`tmp/cycle-316/rv-t4-17/small.mjs` の結果。字の右端は枠の内側に 0.3〜7.2px 入っている）。320px と 200% でも同じ形のものがある（metrics-after.json）。

来訪者にとっては、隠れているものが無いのに、太い枠と横のスクロールバーが付き、Tab で止まり、読み上げは「表（横にスクロールできます）」と言う。送っても数 px 動くだけで、新しく見えるものは無い。枠と止まりどころと名前が、どれも事実と違うことを言っている。

- 同じ根から、表の字の左端は、枠の有無にかかわらず本文の字の左端より 8px 右にある（最初の列のセルの左の余白）。設計 5-2 は枠の描き方を「表の字の左端がほかの本文の左端とそろうほう」で決めるとしていたが、どちらの案でもそろっていない。builder の報告はこれを言っていない。
- 外枠を持たない表では、端の列の外側の余白は何とも接していない。これを持たなければ、字の左端が本文とそろい、見かけだけのはみ出しも消える。ただ、枠を付けた表では、字が枠に接しないための内側の余白が要り、それを後から足すと表の字が横に動く。どう組むか（端の余白を持たない形にして枠の付いた表の内側の余白をどう取るか、はみ出しの測り方を変えるか）は、表と枠の組み方の決め直しになる。**planner が 5-2 を直し、必要なら DESIGN.md §5 の表の書き方も直す。**
- ブログの記事のページは、コンテナの中にさらに左右 24px の余白を持っている（`page.module.css` の `.contentColumn`。375px で本文の左端が 27 でなく 51）。T5 でこれが外れると表の幅が 48px 広がり、どの表がはみ出すかは変わる。数ではなく、組み方として決める。

### Major-3: フォーカスのリングを枠の外に出すのは §6 と §5 に反する。コードのボックスも同じ

- §6 は「二重リングは、フォーカスを受ける範囲の内側に密着して出る」「範囲の縁が太い線と重なるものでは、線の内側に `--paper` を挟んで出る」とし、外に出してよいのは書き込む欄・選ぶ欄と本文の中のリンクだけとしている。§5 の「コンテンツ幅の外へ出るもの」の列挙にも、横に送るボックスのリングは無い。横に送る表のリングは枠の外に 6px 出ており、両方に反する。
- builder が言っていないこと: **横に送るコードのボックス（`pre`）も、globals.css の既定の `:focus-visible` で、太い枠の外にリングを出している**（`tmp/cycle-316/rv-t4-17/focus-pre-light.png`）。表だけの話ではない。
- 撮った見え方（`focus-table-light.png`・`focus-table-scrolled-dark.png`・`focus-pre-light.png`）では、外に出したリングははっきり見え、中身に重ならない。内側に出すと、横に送るセルやコードがリングの下を流れ、表では最初の列の字（縁から 8px）にリングが重なる。来訪者にとっては外に出すほうが良いと考える。
- ただし、それを決めるのは DESIGN.md の側である。規定に反したまま実装に理由のコメント（`Prose.module.css` の「内側に出すと、横に送るセルと罫線がリングに重なる」）を置くのは、規定と実装の食い違いを残すことになる。**PM が決め、planner が DESIGN.md §6（外に密着して出るものに「横に送るボックス（表・コード・図）」とその理由を足す）と §5（コンテンツ幅の外に出るものの列挙）を書き直し、表とコードのボックスのリングを同じ規則で組む。** 内側に出すと決めるなら、表の枠の中に余白を取る組み方（Major-2）と一緒に決める。

### Minor-1: 変える前と後の撮り比べが、すべての記事でなかった（AP-I14）
