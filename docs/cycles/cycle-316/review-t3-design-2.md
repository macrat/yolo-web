- かつて存在したページへの 308 を固定の一覧で書くと、一覧が育ったときに本物のページを隠す（Major-1）。

## Major

### Major-1 かつて存在したページへの 308 を `next.config.ts` に固定の一覧で書くと、一覧が育ったときに本物のページを隠す（2-7・8章）

2-7 は、かつて存在した18本を `next.config.ts` の redirects に並べるとしている。しかし Next.js の redirects は、ページより先に判定される（`redirects.md`「Redirects are checked before the filesystem which includes pages」）。

一覧が育つと、次のことが起きる。

- **`/blog`**: 101件目の記事で `/blog/page/3` が本物のページになる。それでも redirect が `/blog` へ送るので、3ページ目は開けない。
  - 「次へ」を押すと1ページ目に戻される。
  - いまは86件で、2026-03 以降の公開のペースは月 1〜17件（03 に 17、06 に 16、08 に 1）である。数か月のうちに起きうる。
- **分類とタグ**: dev-notes・Web開発（35）が51件になると、`/page/2` が同じ形で開けなくなる。
- **ツール**: 51本になると、2-7 が残すとした `/tools/page/2` → `/tools` が同じ形で本物のページを隠す。

これは、§7「増え続けることへの備え」がまさに防ぐべき事態である（AP-P03 今の件数を所与にしない）。しかも壊れても、ビルドもテストも落ちない。

**求めること**

- 「かつて存在したページ」への 308 は、**いまのページの数を超える番号のときだけ**効く形にする。
- 形は builder に任せてよい（AP-P20）。例は次のとおり。
  - redirects の一覧を、ビルドのときのデータから「かつての最大 ≥ n > いまのページの数」で組む。
  - 経路の側で、いまのページの数を超える番号だけを 308 にする。
- 完了の条件（T3-4 か T3-5）に、次の2つを足す。
  - 件数を増やしたデータで、2ページ目・3ページ目が 200 で開ける。
  - 308 の送り元と静的に生成したページが重ならない。
- `/page/1` の 308 は、いつまでも本物のページにならないので、このままでよい。

### Major-2 名前で探す欄を狭い画面で畳むと、検索が主な使い道の面で、主な操作が隠れる（2-3・3-1・7章）

2-3 では、45rem 未満の画面で `ListControls` が初めは閉じている。その中に名前の欄が入るので、375px の来訪者は「絞り込みと並び順（…）」を押すまで検索の欄を見られない。

これが害になる面は次のとおり。

- **`/tools/yoji-search`**: 四字熟語を検索するための道具である。いまは h1 のすぐ下（y=232）に検索の欄がある。変更後は、ボタンを押してからでないと打てない。
  - index.md の B-621「各面の主操作が、モバイルのファーストビューに入る」と食い違う。
- **辞典のトップ（漢字・四字熟語・伝統色）**: いまの主な操作は、検索の欄（`DictionarySearch`）である。変更後は、畳んだ枠の中に入る。
- **ボタンの文言**: 「絞り込みと並び順」は、検索の欄を探す来訪者には、そこに検索があると読めない。

一覧を押し出しているのは、ラジオボタンの組である。inventory 5章では、yoji-search のカテゴリ・難易度・出典の組が 292〜839 を占める。名前の欄は1つで、約60px にすぎない（inventory 2-3・5章。欄の上端から次の要素まで 60px）。

**求めること**

- 次の案を比べて決める（AP-P17）。
  - 名前の欄を畳む枠の外に出し、いつも見せる。ラジオボタンの組と並び順だけを畳む。
  - いまのとおり、すべてを畳む。
  - 面ごとに分ける。検索が主な使い道の面（yoji-search・辞典のトップ）だけ欄を外に出す。
- 比べるときは、次の2つを測る。
  - 欄を外に出したときに、375×667 で最初の行が画面に入るか。
  - 畳んだままのときに、来訪者が検索に着くまでの手数。
- 欄を外に出すなら、`DESIGN.md` §7「絞り込みと並び替えのコントロールは…アコーディオンに畳み」の書き方が合わなくなる。その場合は options.md「`DESIGN.md` を変えるとき」の手順で §7 を直し、単独でレビューを受ける。

## Minor

### Minor-1 パスを元のパスに替えたあとの描き方が、書かれていない（2-7・2-8）

- 2-7 の「見出しの「（2ページ目）」も消えます」は、事実と合わない。
  - いまの h1 は、どのページでも「AI試行錯誤ブログ」である（`BlogListView.tsx`）。「（2ページ目）」は `<title>` にだけある。
  - `replaceState` では `<title>` は変わらないので、`/blog?q=…` の URL でタブの名前が「（2ページ目）」のまま残る。どうするか（クライアントで `document.title` を直す、または受け入れる）を書く。
- `replaceState` はいまの木を残す（上の「確かめたこと」）。そのため `/blog/page/2` の `BrowsableList` は、パスが `/blog` に変わったあとも、props として「パスが示すページ＝2」を持ったまま残る。
  - 「絞り込みを外すと…中身はその1ページ目に戻ります」を成り立たせるには、表示するページを props でなく、そのときの URL のパスから決める必要がある。そう書き添える。
- 名前の欄の値は、URL へ 300ms 遅れて書く。そのため、欄の値そのものは URL（`location.search`）でなく、部品の中に持つ必要がある。そうでないと打った字が遅れたり消えたりする。1行書き添える。

### Minor-2 keigo-reference の既定の並び順が、決められていない（7章）

- 「普通語の五十音順」は、データに読みが無い（`KeigoEntry` にあるのは `casual: "行く"` と英字の `id: "iku"` だけ）。
- 行に読みが見えないので、2-6 の「行に見えている最初の読みで比べる」も当てはまらない。
- データの並びは分類ごと（`basic` → `business` → `service`）で、使う頻度の順を示す注記も無い（`logic.ts`）。いま確かめられることなので、builder に任せず決める。
- 例: 既定を「分類順」（種別として見えている）にし、選ぶ理由のある順がほかに無いので並び順の組を出さない。既定の順は件数の行の後ろに言う（2-2）。

### Minor-3 ツールの種別「変換」が、名前に「変換」を持つツールの半分以上を含まない。同じ日付の中の順が見えない（3-1）

- 「変換」に入るのは5本である。名前に「変換」を持つのに別の種別に入るものが、6本ある。
  - 開発: カラーコード変換・進数変換・CSV/TSV変換・UNIXタイムスタンプ変換
  - 文章: 全角半角変換・ひらがな・カタカナ変換
- 種別の語が、用途（文章・開発）と働き（計算・生成・変換）の2つの軸で混ざっている。そのため「変換」で絞った来訪者は、探しているツールが無いと思いうる。次のどちらかにする。
  - 軸を1つに揃える。
  - 「変換」を、用途で言える語に替える（例「エンコード」）。
- 3-1 の「同じ日付の中は公開の日時の順です」は、2-6 の「同じ値の中の順は、見えている値で決める」に反する（時刻は行に見えない）。
  - 同じ日付の中は種別順か名前の順にする。
  - または、見えない値で並ぶことを例外として書く。

### Minor-4 名前の欄のラベルが、2-5 の自分の規則と合わない（3-1）

2-5 は「行に見えないもので探すときは、ラベルがそれを言う」と定めている。これに合わないものがある。

- **四字熟語**: 例文で探すのに、ラベル「語・読み・意味で探す」は例文を言わない。
- **ブログ**: 連載名で探すのに、ラベル「題名・説明・タグで探す」は連載名を言わない。連載名は行に見えない。

次の直し方がある。

- ラベルに足す。
- 探す字から外す。

あわせて、漢字の英語の意味を外す理由の書き方を直す。いまの理由「当たった理由が行に見えない」は、熟語（これも行に見えない）を探す字に残すことと食い違う。ラベルが言えば探せるのが 2-5 の規則なので、外す理由は「日本語の来訪者が英語で探さない」とするほうが、ほかの箇所と一貫する。

### Minor-5 伝統色の「明るい順」の明るさの測り方が、決められていない（3-1）

- データには `hsl` があるが、HSL の L で並べると、目で見た明るさの順にならない。純粋な黄と青は、どちらも L=50% になる。
- 来訪者は色見本の移り変わりで順を確かめる（3-1 の理由）ので、見た目に合う明るさ（例: OKLCH の L）で並べると書く。
- 「色み順（色見本の色相）」も、無彩色（achromatic 10）の色相の扱いを1行で決める。

### Minor-6 辞典のトップで、同じ分類を2つの操作で出している（3-1）

- 漢字のトップには、次の2つがある。四字熟語のカテゴリ・伝統色の色みも同じである。
  - `ListControls` の種別「学年」のラジオボタン（ページの中で絞り込む）
  - 「学年から探す（7）」のアコーディオン（学年のページへ移る）
- 同じ「小学1年」の語が、押すと違うことをする2つの操作として並ぶ。
- 次のどちらかにする。
  - 違いを来訪者が読み分けられる理由を書く。
  - どちらかを外す。例えば種別の組は画数・読みの組み合わせで使うので残し、学年のアコーディオンは外す。
- 分類のページの索引は、一覧の上にしか無い。一覧が最多118行（375px で約1万px）ある部首のページで、読み終えた来訪者がほかの部首へ移るには、上まで戻る必要がある。部首のページは PV の最も多い一覧である（476 PV）。一覧の下にも置くか（ブログと同じ）、置かない理由を書く。

### Minor-7 完了の条件が、改善を検出できないもの・担い手の無いものを含む（8章）

- **「最初の行の上端が画面の下端より上」は弱い。**
  - keigo-reference はいま 661 で、変更の前から条件を満たしている（画面に入るのは 6px）。
  - 「最初の行の全体が画面に入る（下端が 667・800 以下）」にする。

  - 一覧の上にアコーディオン3つ（約132px）が足され、最初の行が下がる。PV の最も多い一覧なので、T3-7 の画面の条件に部首のページ（「水」）を加える。

  - 各辞典に `page` という見出し語・slug が無いことのテスト（2-7）。
  - 上の2つを、T3-4 か T3-7・T3-8 に割り当てる。
- **T3-8 の条件が、並行するタスクに依存している。**
  - 条件は「`Shinagaki`・`DictionaryEntryList`・`DictionarySearch`・`FacetIndex` の参照が0件」である。しかし `Shinagaki` は T3-6（`/tools`・`/play`）が、`DictionaryEntryList` は T3-7（漢字）が消す。
  - 8章は T3-5〜T3-9 を並行としている。この条件は T3-11 に移すか、T3-8 が T3-6・T3-7 のあとだと書く。

### Minor-8 GA の数値の出どころが記録されていない（0章・3-1）
