## 指摘

### Major-1: 遅い回線と遅い端末では、最初の表が組む前の形で一度描かれ、表とその下が動く（§5「最初の描画から決め、描いたあとに組み直して表とその下を動かさない」）

回線を絞り（下り 50KB/s・往復 400ms）、CPU を4倍遅くして、320px・200% で試しのページを開いた。カラーコードの表は8回のうち6回、ボタンを値の横に置いた、はみ出した形で一度描かれた。次の描画でボタンが下へ移り、layout-shift は 0.016（source はコピーのボタンとその行）だった。

- 画面の録画（`Page.startScreencast`）の2枚目に、値の右で切れた「コ」が映っている。3枚目で下に送られる。
- 描画の直前（requestAnimationFrame）で数えると、「中身まで読み終えたスクリプトが枠の直後にあるのに、表がまだ組まれていない」描画が、4回すべてで最初の表に1回ずつあった。
- 同じ条件の記事（sql-cheatsheet の 375px）では、4回とも0だった。

置き場所を入れ替えて比べた（ビルドした HTML を中継で書き換えた）。

| スクリプトの置き方                                                         | 組む前の表が描かれた回 |
| -------------------------------------------------------------------------- | ---------------------- |
| いまの形（表ごとに枠の直後に 3.3KB）                                       | 4回のうち4回           |
| 定める文を `<head>` に1回、枠の直後は呼ぶだけの短い文                      | 4回のうち3回           |
| 定める文を最初の表の直前（本文の中）に1回、枠の直後は呼ぶだけの短い文      | 4回のうち0回           |
| `<head>` の文が、描画の直前に組んでいない枠を組む（requestAnimationFrame） | 8回のうち0回           |

- 大きさ（3.3KB）は関わらない。本文の中の最初の表より前に、スクリプトが1つも無いことが原因である。
- 記事は、定める文（`TABLE_LAYOUT_DEFINE`）が最初の表の前にあるので起きない。Chromium が、本文の中の最初のスクリプトを動かす前に描画の機会を作るように見える（計った振る舞いで、ブラウザの内部の仕様としては確かめていない）。

直し方（builder）: 定める文を枠の前に置き、枠の直後の文は直前の表を組むだけにする。たとえば、部品が枠の前に `window.yolosFrameLayout||(window.yolosFrameLayout=(…)())` を置き、後ろに短い呼び出しを置く。前の文の中身は表ごとに繰り返してよい（gzip で1本 0.2KB ほど）。

直したら、同じ条件（回線を絞り、CPU を4倍遅く、320px・200% ほか）で、最初の表を含むどの表でも、組む前の形で描かれた回が0であること、layout-shift の source に表とその中が入らないことを、何回か繰り返して確かめる。コメントとスキルの項の「枠の直後のスクリプトで最初の描画から組む」も、置き方に合わせて書き直す。

### Major-2: 320px の既定の大きさで、コピーのボタンが値を削って折る（§6「値が削られて折れると…読みにくくなる。場所が足りない並びでは…値の次の行に置き、値に行の幅を渡す」、t5-design 7-f）

320px の既定の大きさで、カラーコードの表は次のように組まれる（`e-colour-light-320-16`）。

- 値の列は 223px で、ボタンは値の横にある。
- 「rgb(238, 169,／169)」と「hsl(0, 67%,／80%)」が2行に折れている。
- ボタンを値の次の行に送れば、どちらの値も1行に入る。

原因は、ボタンを送るかを「どの列も細くせずに文節の幅で収まるか」で決めていることにある。値がいちばん長い文節の幅に入れば、ボタンの横で値が何行に折れても、横に置く。§6 がボタンの場所のために値を削らせないのは、この場面である。

直し方（builder）: ボタンを値の横に置くのは、コピーを持つどの行でも、値の1行の幅（max-content）とあき・ボタンの幅が、値の列に取れる幅に入るときだけにする。入らなければ、どの行も送る。送ったあとに値が行の幅でも折れるときは、いまのとおり文節で折ってよい。部品の試験に「文節は収まるが、値がボタンの横で折れる」場合を足す。

### Major-3: コピーのボタンを持つ表の枠が 1px 横に送れ、止まりどころを持たない送れる区画になる

どの幅でも、カラーコードの表の枠は `scrollWidth` が `clientWidth` より 1px 大きい（320px で 267 と 266、1280px で 923 と 922）。枠の `scrollLeft` に値を入れると 1 まで動く。

原因は `CopyButton` の中の `.visually-hidden` の知らせの箱（`position: absolute`・幅 1px・`margin: -1px`）で、右に寄せたボタンの端から 1px 外に出て、`overflow-x: auto` の枠の送れる幅に数えられる。

- 触れる画面では、表が 1px 横にずれる。
- 常に出るスクロールバーの環境（Windows の既定など）では、どの伝統色のページでも、表の下に何も隠れていないスクロールバーが出るおそれがある。headless はスクロールバーを重ねて出すので、目では確かめられなかった。
- 枠は `tabindex` を持たないので、キーボードで送れない送れる区画になる（§5「何も隠れていない表に枠と止まりどころを付けると…」の裏返しで、隠れたもの無しに送れる）。

直し方（builder）: 知らせの箱がボタンの升の外に出ないようにする（`CopyButton` の側で箱を升の内側に置く、など）。`CopyButton` は多くの面が使うので、直すなら使うすべての面を前と後で撮り比べる（AP-I14）。直したあと、コピーを持つ表の枠の `scrollWidth` と `clientWidth` が6条件のすべてで等しいことを確かめる。

### Minor-4: 開いた行（`detail`）の中身にも `word-break: keep-all` が掛かる

`.table :is(th, td)` と、その子孫に `overflow-wrap: inherit` を当てる規則が、`colSpan` の詳細の行にも及ぶ。開いた行に置くのは、区切りの並びでなく例文や注記の文章なので、句読点と空白のあいだが1つの塊になる。敬語のいまのデータでは、いちばん長い塊が22字（「自分の身体への動作のため固有の謙譲語形はない」、既定で約 374px）である。広い画面の表は 45rem 以上でしか出ないので、いまは入る。ただ、部品の約束（「開いた行の例文など」）としては通常の禁則で折るべきで、ほかの面が長い文を渡すと折れずにはみ出す。

直し方（builder）: 詳細の行のセルを見分けられるようにし（class か属性）、そのセルでは `word-break: normal` と `overflow-wrap: anywhere` に戻す（§4 の本文の折り方）。試しの表を開いた形で、320・375・1280px の既定と 200% で撮る。

### Minor-5: 使う側が描くたびに新しい配列を渡すと、毎回すべてを組み直す

`useLayoutEffect` の依存は `[columns, rows, inBox]` で、変わるたびに `layoutTable(frame, true)` で枠と幅を外して測り直す。使う側（辞典の詳細・keigo など）は `rows` をたいていその場で作るので、中身の変わらない描き直し（keigo の検索の欄に打つたびなど）でも、表を組み直すレイアウトが走る。見た目は変わらないが、行の多い表（敬語早見表）では打つたびの応え（INP）を重くしうる。

直し方（builder）: 組み直すかを、配列の同一性でなく中身で決める。たとえば、渡された行と列の字を連結した鍵を覚えておき、同じなら組み直さない。
