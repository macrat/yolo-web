### Minor-1: §4 の「表のセルは文節で折る」が、サイトのすべての表の規則として書かれているのに、記事の表でしか成り立っていない

§4 の折り方の項は「次の3つは、意味のまとまりを割らないよう折る所を限り、一覧の中にあってもこちらに従う」とし、その3つ目を「表のセルは文節で折る…」としている。例外は「来訪者が書いてその場で組む文（プレビュー）」だけである。ところが区切りと列の幅の決め方を持つのは Markdown から組む記事の表だけで、keigo-reference の表・色の辞典のカラーコードの表・`ContrarianFortuneContent` の指標の表・結果のボックスの表（道具の結果）は、通常の禁則で折っている。DESIGN.md が、実際にはない規則をサイト全体の規則として言っている。

直し方（planner）: 規則は一般の形のまま残し、記事の外の表を §4 に合わせることを、T5（面ごとに組み直す）の受け持ちとして t4-design.md の9章か index.md に書く。記事の外の表は、中身が短く、1字の列にはならないので、T5 まで待ってよい。一般の規則にしない理由があるなら、§4 のほうを「記事の表のセル」に書き分ける。

### Minor-2: 開発のビルドで、Link で記事へ移るたびに React が console.error を出す

`page.tsx` の `<script dangerouslySetInnerHTML={{ __html: proseLayoutScript }} />` は React の要素なので、クライアントでの移動のときにブラウザで作られる。React 19 の開発のビルドは、そのとき `Encountered a script tag while rendering React component…` を console.error で出す（`react-dom-client.development.js` の、`script` の要素を作る所。本番のビルドでは出ない）。builder の開発のビルドの確かめは、アドレスから開いたときの水和だけだった。来訪者には見えないが、開発のオーバーレイと、エラーが0であることを見る以後の確かめで毎回ノイズになる。

直し方（builder）: 組む関数を定めるスクリプトも、`markdownToHtml` が本文の HTML の中（最初の表の前）に置く。`dangerouslySetInnerHTML` の中は React の要素ではないので警告は出ず、表の無い記事にスクリプトを配らずに済む。開発のビルドで、一覧から Link で記事へ移っても console.error が0であることを確かめる。

### Minor-3: 水和のとき、すべての表を2回続けて組み直し、遅い端末で長いタスクになる

`Prose` の layout effect は、表の直後のスクリプトがすでに組んだ表を、水和のときにもう一度すべて組み、さらに `document.fonts.ready` がすでに解けているとすぐにもう一度組む。組み直しは表ごとに枠と幅を外して測るので、レイアウトを何度もやり直させる。CPU を4倍遅くして1回すべての表を組む時間を測ると、git-command-cheatsheet（11表）で 375px 113ms・1280px 56ms、html-tags-cheatsheet（8表）で 97ms・85ms だった。水和のときにその2回分が続けて走り、そのあいだの操作への応えが遅れる（INP）。見た目は変わらない。

直し方（builder）: 組んだときの置かれた幅を表の枠に覚えさせ（`data-` 属性など）、同じ幅なら組み直さない。`document.fonts.ready` は、差したときにまだ読み込み中（`document.fonts.status !== "loaded"`）のときだけ待つ。直したあと、同じ測り方で水和のときの時間を記録する。
