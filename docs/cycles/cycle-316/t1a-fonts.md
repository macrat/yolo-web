## 結論

### 配り方

**ページごとのサブセット（速い道）に、全ページ共通の予備（静的な分割ファイル）を重ねる。** 予備を重ねるかどうかは、ページが来訪者との間に持つ約束で分ける。

1. **速い道は、3巡目の形を引き継ぐ。** ページの字は、ページ固有の家族名でビルドの時に切り出し、静的なファイルで配る。
   - その `@font-face` は、ページが描く `<style>` に置く。
   - 書体の変数は、**ページ自身の外枠の要素（`data-pf` 属性を持つ要素）にだけ当てる**（M-3）。
   - preload は、ページが描く生の HTML に書く。
2. **予備は、全ページ共通の家族「Yolos JP」（本文 400・700）と「Yolos JP H」（見出し）である。**
   - 書体の全体を、コードポイントの連続した範囲で 100 字ずつに分けた静的な woff2 である（本文 400・700 が各117ファイル、見出しが78ファイル）。
   - 宣言は全ページ共通の CSS に置く。1つの面に `unicode-range` は1区間だけなので、宣言の全体は gzip で 4,474B である。
   - 書体の並びは「欧文 → ページの家族 → 予備 → 欧文の代わり → 端末の書体」とする。ページの家族にある字はページのファイルで描き、無い字だけをブラウザが予備から読む。Chromium・Firefox・WebKit の3つで確かめた（「字の集め方と自己回復」）。
   - **事前の予測は、正しさの条件ではなくなり、速さの最適化になる。** 当て損ねた字は、予備が届くまでの一時だけ端末の書体で出て、その後は揃う。
   - **予備を書体の並びに入れるのは、最初のフォントが揃った後である。** ルートのレイアウトが `load` と `document.fonts.ready` の後に `<html data-fb>` を付ける。最初の描画のときから予備を並びに入れると、Chromium で最初の描画（FCP）が約 0.4〜0.8 秒遅れた（「差し替えのずれ」）。
3. **来訪者の入力と答えを映しうるページ（「閉じたページ」）には、予備を重ねない。**
   - 閉じたページは、ツールの全ページと、診断・クイズのプレイ面（`/play/[slug]`。結果や正誤が答えで決まる）である。
   - 予備を読むかどうかは、画面に出た字で決まる。そのため予備があると、ツールの出力や診断の結果が、どの分割ファイルを要求したかに映る（「入力に由来する字」）。
   - 閉じたページでは、そのページのコードが描きうる字をすべて、入力に依らずにページの層へ入れる。
     - ルートのクライアントの JS に現れる字をすべて、本文 400 に入れる。
     - コードの文字列を、要素の役割（見出し・太字）ごとに振り分ける。
   - 閉じたページで起きたフォントの要求は、読み込みの時のものだけである。操作のあとに要求が0であることを確かめた（ツール4本と上端のメニュー、診断の流れ全体）。
4. **データで決まる面は、ビルドの時に「層で配るか、予備に任せるか」を計算して選ぶ。** 候補の全体をまとめた層の大きさと、予備に任せたときの1回の来訪の見込み（その日の項目の字が触れる分割ファイルの合計）を比べる。サーバーが日付で中身を描くページは、日付ごとのサブセットにする（「日替わりのゲームとデータで決まる面」）。

### 書体

- **本文・UI の和文は BIZ UDGothic** の派生（400・700、`font-display: swap`）にする。
  - 派生で変えるのは、U+2014（EM DASH）に全角の横線の字形（U+2015 と同じ字形）を当てることだけである。元の字形は半角で、「——」が半分の長さになる（M-1）。
  - 本文は `text-spacing-trim: space-all` とし、約物を全角のまま組む。
- **見出しは Zen Antique** を swap で配る。見出しの書体を当てるすべての要素（クラスで当てているものを含む）で、`palt` を掛けない。
- **欧文は IBM Plex Sans の派生（Yolos Sans）** を `optional` で配る。ロゴは SVG にする（3巡目のまま）。

### 上限（増分0）

**測った12ページ（代表5ページと、境界の候補7ページ）のうち、11ページで満たす。`/tools/keigo-reference` だけが +38.7KiB で越える。**

- 越える原因は、役割の分からない文字列（JS だけが描く敬語の表）を、ページが持つすべての役割に入れる規則にある。
- この表を最初の HTML に描けば、表の字はマークアップから役割どおりに集まる（タブの中身が閉じていてもよい）。見積もりでは −64KiB になる。
- これは「配り方を変えても越える」場合にあたらない。そこで、T1〜T7 の条件（「ビルドの経路」の条件6）とビルドの門（全ページで変更前を越えたら失敗させる）で扱う。§3 は改めない。
- 全ツールの見積もりでは、同じ規則のままだと `/tools/business-email`（+15KiB）と `/tools/yoji-search`（+152KiB）も越える見込みである。`yoji-search` は検索の結果（入力で選ばれる表示）の字で、端末のゴシックで組む表示にあたるので、その字を層に入れない（−24KiB の見込み）。

### 判断

- **案A を採る。** 比べた案の中で、次の3つを同時に満たしたのは案A だけだった。
  - 落ち着いた後に1つの要素で書体が混ざらない。
  - 入力と答えが要求に映らない。
  - 上限を満たす（1ページは条件つき）。
- 案A' は、予備の宣言を全ページの `<style>` に持ち、HTML と RSC で二重に運ぶことになる。書体の並びで重ねても（案A）同じ自己回復が得られるので、採らない。
- 案A'' は、ツールと診断で出力と結果の区画が要求に映る。そのため採らない（「入力に由来する字」）。
- 案B は、B-1 そのものである。
- 案C は、上限を越える。そのうえ、読み込みのあいだは字ごとに書体が混ざる。
- 案D は試作していない。日付（日替わり）と入力（ツール・ゲーム）の組は列挙しきれないので、正しさは予測の完全さに依ったままになる。
- 案E は試作していない。JS が描く字（ツールの結果・エラー・ゲームの盤面）がすべて端末の書体になり、「和文を読ませる書体を Web フォントで出す」（§3 の役割）が、サイトの操作の面で失われる。

## 字の集め方と自己回復

### 予備の組み方（PM の見立ての確かめ1）

`tmp/` の静的な試験のページで、BIZ UDGothic のページのサブセット（本文の38字）と予備（100字ずつの分割）を組み合わせた。本文に、サブセットに無い字を3つ（縷・纁・璽）足した。

| 組み方                                                        | Chromium 141                           | Firefox 151    | WebKit 26.5    |
| ------------------------------------------------------------- | -------------------------------------- | -------------- | -------------- |
| 並び「ページの家族, 予備」。ページの面に `unicode-range` なし | ページ＋予備2つ                        | 同左           | 同左           |
| 同じ。本文がサブセットの字だけ                                | ページだけ                             | 同左           | 同左           |
| 同じ家族名。予備を先、ページの面を最後に宣言                  | ページ＋予備2つ                        | 同左           | 同左           |
| 同じ家族名。ページの面を先、予備を後に宣言                    | ページ＋**予備17**（予備が優先される） | ページ＋予備17 | ページ＋予備18 |

- **ページのサブセットにある字は予備を読まず、無い字だけ予備を読む。** 3つのブラウザで同じだった。
  - ページのファイルを 1.5 秒遅らせて返しても、その間に予備を余計に読むことは無かった（3つのブラウザ）。
  - 同じ家族名に面を重ねるときは、**後に宣言した面が先に使われる**（CSS Fonts 4 の規定どおり）。順を誤ると、予備がページの面より優先され、ページに無い字どころか全部の字の区画を読む。
- 採る形は、書体の並びで重ねる形（表の1行目）である。順の誤りが起きない。予備の宣言は全ページ共通の CSS に1回だけ置けばよい。
- ページの面には `unicode-range` を付けない。付けなくても、無い字だけが予備に回ることを確かめた。
  - 付けないと、予備の要求はページのファイルが届いた後になる（遅い 4G で、付けると 943ms、付けないと 1,201ms）。
  - 当て損ねはまれにしか起きない。そこで、ページの `<style>` を小さく保つほうを採る（m-3）。
- 纁（U+7E81）は BIZ UDGothic に無い字である。予備の区画を読んだあとも、端末の書体で出る。**書体に無い字は、どの配り方でも揃わない。**
  - サイトの本文の字で BIZ UDGothic に無いのは9字（纁 7ページ、彐 3ページ、絵文字 6字・ZWJ、₂）。
  - 見出しの字で Zen Antique に無いのは14字（絵文字・記号）。
  - 見出しは要素ごと本文の書体にする（§3、3巡目のまま）。本文の9字は「書体に無い字」として明記し、揃えない。

### 予備の分け方

| 1区画の字数 | 区画の数（本文 400／700／見出し） | 区画の大きさの中央値（本文 400／見出し） | 宣言の大きさ（gzip） |
| ----------: | --------------------------------- | ---------------------------------------- | -------------------: |
|     **100** | 117／117／78                      | 23.5KB／34.2KB                           |               4,474B |
|         200 | 59／59／39                        | 43.0KB／66.7KB                           |               2,294B |
|         400 | 30／30／20                        | 83.5KB／128.2KB                          |               1,243B |

- 区画は、書体の cmap のコードポイントを小さい順に並べ、100字ずつに切った。
  - 1区画の `unicode-range` は1区間なので、宣言が小さい。
  - Google Fonts のように字の頻度で分けると、宣言が大きくなる。同じ BIZ UD の2ウェイトで gzip 60.8KB だった。この宣言を全ページで払うことになる。
- **100字を採る。** 宣言は全ページで払う量で、区画は当て損ねたときだけ払う量である。宣言が 4.5KB で済み、区画1つが 23.5KB で済む点を取った。
- 弱点: 漢字はコードポイントの上で散らばる。そのため、当て損ねた漢字が多いと、1字ごとに別の区画を読むことになる。
  - 例: 試作の初版（r4）の `/play/kanji-kanaru` は、UI の文字列の役割を取り違え、最初の読み込みで区画を10個（約 250KB）読んだ。上限を +74KiB 越えた。
  - 予備は正しさを保つ網で、配る道ではない。**当て損ねを少なく保つことが、上限を守る条件である**（下の集め方と、「測り方」の門）。

### 集め方（ビルドの時、Chromium を使わない）

1. **マークアップ**: 書き出された HTML（リクエストごとに描くページは、ビルドの中で列挙したキーを HTTP で取る）を解析する。役割はタグと属性で決める（3巡目のまま）。
2. **ルートのコードの文字列（B-1 の構造の解き方）**:
   - ルートが読み込むソースのモジュール（データのディレクトリを除く）を TypeScript の構文木で読む。
   - JSX の文字列は、それを囲む要素の役割に振り分ける（h1〜h6 は見出し、`strong`・`b`・`th` と属性で宣言した要素は太字）。
   - 1段の props も辿る。部品の中で `<h2>{title}</h2>` と描く prop に、呼ぶ側が文字列を直接渡す場合である。
   - **役割の分からない文字列**（定数・変数を通るもの）は、ページが持つすべての役割に入れる。
3. **閉じたページ**は、2に加えて、ルートのクライアントの JS チャンク（ページの HTML の `<script src>`）に現れる字（`\uXXXX` を含む）を、すべて本文 400 に入れる。データも含む。
4. **日付と時刻の字**（年・月・日・時・分・秒・曜）は、全ページの本文 400 に入れる。`Intl.DateTimeFormat` が描く字で、ソースに現れないからである。
5. **上端・下端の家族**には、全ページ共通の JS チャンクの字を足す。開いたときにだけ描くメニューなど、73字足した。本文 17,384B で、3巡目より +2.8KB。

試作で、この集め方の各段が何を拾ったか:

- `/tools/email-validator`: チャンクの字は204字、JSX の役割は見出し41字・太字16字。
  - B-1 で混ざった「エラー」（`<h2>` の中）、「ローカルパート:」（太字のクラス）、`logic.ts` のエラー文（チャンク）が、すべて入った。
- `/play/kanji-kanaru`: 役割の分からない文字列を、すべての役割に入れた（r4b 以降）。
  - 最初の読み込みで読む予備は、10区画（r4）から2〜3区画に減った。
  - 残りは、変数を通って見出しに描かれる題（「遊び方」「統計」）などである。
- `/tools/keigo-reference`: 役割の分からない文字列（JS だけが描く敬語の表）が多い。そのため、すべての役割に入れると上限を越える（結論）。

### 試作で見つかった、遷移の3つの落とし穴

1. **Next.js のルートの読み上げ（`next-route-announcer`）が、ページの題名を描く。**

2. **`data-pf` を `display: contents` の包みに付けると、遷移のあとに先頭へスクロールしない。**
   - Next.js が遷移先の最初の要素へスクロールするとき、箱の無い要素を起点にしてしまうためと考えられる（原因は Next.js のコードでは確かめていない）。
   - 辞典で `scrollY` が 874 のまま残り、画面に入ったリンクの先読みで全体が約 +220KB 増えた。

## 入力に由来する字

### 決めたこと

- **閉じたページ（ツールの全ページ・診断のプレイ面）には、予備を重ねない。** ページの層に、ページのコードが描きうる字をすべて入れる（「字の集め方」の2〜4）。
  - 読み込むファイルの集合は、ページを開いたときに決まり、入力・答え・操作の中身で変わらない。
- **来訪者が入力した字と、それをそのまま、または変換して映す表示は、和文を端末のゴシックで組む**（3巡目のまま）。欧文は派生の2ファイル（全ページ共通）で組む。
- **入力で選ばれる表示は、候補の全体を層に入れても上限を越えないなら、層に入れて Web フォントで組む。** 越えるなら、端末のゴシックで組む。
  - 入力で選ばれる表示とは、検索の結果や、入力で選ぶ定型文などである。
  - 例: `traditional-color-palette` の色の名前（465字）は層に入れる（上限を満たした）。`yoji-search` の検索の結果（1,047字）は端末のゴシックにする。
- **開いたページのゲームの推測**（盤面）は Web フォントで組み、予備に任せる。推測は評価の API にすでに送っている。

### 理由

- ツールの約束（`src/tools/_components/ToolPageLayout/index.tsx:87`「このツールはブラウザ上で動作します。入力データがサーバーに送信されることはありません。」、`src/app/tools/page.tsx:87`）を、字そのものだけでなく、要求のしかたからも推し量れないように守る（上の「当て損ねたときの見え方と転送量」）。
- 診断は、結果の区画の要求から答えが分からないようにする。結果の層は24通りをまとめた1つのファイルを、答えに依らない合図（「はじめる」）で読む。
- 予備の無い閉じたページで字を当て損ねると、見える形で混ざる。これを CI の操作のシナリオで検出し、ビルドの字の集め方か要素の役割の宣言を直す。

## ビルドの経路

### 分かっていること

- Vercel のプランと機械の種類は、API では確かめられなかった（3巡目）。Hobby は常に Basic（2 vCPU・8GB）、Pro と Enterprise の新しいアカウントは Elastic が既定である（Vercel「Managing Builds」2026-09-17 更新）。
- 3巡目の工程の時間（この機械の 4 vCPU）に、今回の工程を足す:
  - ルートの JS チャンクの字を集める: 1ルート数十 ms（HTML から `<script src>` を読むだけ）。
  - ソースの構文木で文字列の役割を集める: 1ルート 1 秒未満。
  - 予備の312ファイルを作る: 約 34 秒（1プロセス）。
    - 予備は書体のファイルと設定だけで決まり、ページに依らない。書体が変わらない限り、ビルドのキャッシュからそのまま使う。
    - 合計 8.2MB。
- 見積もったビルド時間は、3巡目の約 8 分（4 vCPU）／約 16 分（2 vCPU）に、予備の初回の 1 分前後を足した程度である。

### 決めたこと

1. **経路は3巡目のまま**、`next build`（1回目）→ 字を集める → 切り出す → `next build`（2回目）とする。
2. **字を集める工程は、「字の集め方」の1〜5で行う。** Chromium は使わない。
3. **データで決まる面は、ビルドが層の大きさと予備の見込みを計算して、配り方を選ぶ。**
   - 層の大きさと予備の見込みは「日替わりのゲームとデータで決まる面」の計算で、表とともにビルドの記録に残す。
   - サーバーが日付で中身を描くページは、予定表の日付ごとにサブセットを作る。範囲は、予定表のある日付と、ビルドの日から少なくとも60日である。
   - 予定表の外の日付（ハッシュで選ぶ予備の選び方）の日は、予備に任せる。
4. **予備は、書体の版ごとに1回作り、ハッシュの名前で `public/` に置く。** 宣言は全ページ共通の CSS に置く。
5. **失敗したら、ビルドを失敗させる**（3巡目の条件に次を足す）。
   - 閉じたページで、ルートの JS チャンクの字がページの本文のファイルに入っていない。
   - すべての HTML に、そのページの `data-pf` の外枠と `<style>` がある。部品を入れ忘れたページが無いこと（m-6）。
   - 1回目と2回目の出力の両方に、上の自己点検を掛ける（m-6）。
   - **変更前に同じ URL があるページで、Web フォントの転送量が変更前を越える**（上限の門）。変更前の値は、T1a の全ページの計算（3,526 ページ）を基線として持つ。
6. **T1〜T7 の条件（書体の役割）**:
   - 見出しと太字の書体は、タグ（h1〜h6、`strong`・`b`・`th`）と属性だけで当てる（3巡目のまま）。
   - 閉じたページで JS が見出し・太字として描く文字列は、役割の要素の JSX に直接書くか、その要素を描く部品の props に文字列で渡す。どちらでもなければ、役割の分からない文字列として、ページのすべての役割に入る。
   - **決まった中身（参照の表、タブの中身、よくある質問など）は、最初の HTML に描く**（閉じていてよい）。`keigo-reference` と `business-email` はこれで上限を満たす見込みで、T1 の最初のデプロイで測る。
   - UI の印（▶ ↗ ‹ › ©）は、字の幅に依らない箱か図形で描く（M-2）。
   - `data-pf` は、箱を持つページ自身の外枠の要素に付ける（`display: contents` にしない）。
   - 入れ子のレイアウト（遷移しても残る部分）が字を描くときは、ページの外枠の外に置く。そうすると、既定の書体の並び（上端・下端の家族＋予備）で描かれ、遷移で替わらない。その字は、上端・下端の家族に集める（m-8）。
   - `next-route-announcer` の書体は端末のサンセリフにする。
7. **T9 のプレビューは CLI で配る。** CLI の上限は3巡目と同じ。予備の 8.2MB は、ソースのアップロードの上限（Hobby で 100MB）に収まる。

## 測り方

### 転送量（合否の線）
