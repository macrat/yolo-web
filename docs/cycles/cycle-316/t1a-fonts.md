## 結論

### 配り方

**配り方は「混成」を維持し、宣言の置き場所を作り直す。** 混成とは、ページごとのサブセットをビルドの時に決めて静的なファイルで配り、データで決まる字（診断の設問・結果）も同じくビルドの時に作った層で配る方式である。実行時に字を切り出す配信口は置かない。来訪者が入力した字は、どの要求にも載せない。

2巡目で見つかった欠陥（遷移で字ごとに書体が混ざる）は、次の3点で構造から解いた。

1. **ページの字は、ページ固有の家族名で宣言する。** その `@font-face` と、書体の変数をその家族に向ける規則は、**ページ自身が描く `<style>`** に入れる。
   - 文書を読み込むときは HTML で届き、クライアント側で遷移するときは遷移先の RSC で届く。ページを離れると消える。
   - 前のページの面が遷移先の字を拾うことが起きない。静的なページでも、リクエストごとに描くページ（プレイ面・結果面）でも、同じ部品がそのまま動く。
2. **上端と下端（遷移しても残る部分）の字は、全ページ共通の家族にする。** 1役割につき1ファイルとし、上端と下端の要素にだけ割り当てる。遷移のたびに上端の書体が替わることが無い。
3. **preload は、ページが描く「React が中を見ない生の HTML」に書く**（`dangerouslySetInnerHTML` で中身を入れた隠し要素）。
   - 文書を読み込むときは、HTML のプリロードスキャナが拾う。
   - Link の先読みで取った RSC では、フォントの要求が出ない。React の `<link rel="preload">` を使うと、サーバーの部品でもクライアントの部品でも、Next.js 16.3.0 は RSC に `:HL` の指示を入れ、先読みのたびにフォントを読む（試作で確かめた）。
   - クライアント側で遷移するときは、ページが挿入された時点で要求が出る。

## 比べた案

### 配り方の案

B-1（遷移のあとに、1つの要素の中で Web フォントと代わりの和文の書体が同居する）を解けるかを軸に並べた。

- **案1: ページ固有の家族名＋宣言をページが描く＋preload を生の HTML に書く（採る）。** 結論のとおり。
- **案1': 案1で、preload を `proxy.ts`（Next.js 16 の middleware）の HTTP `Link` ヘッダで文書の要求にだけ付ける。**
  - Next.js 16.3.0 の proxy は、RSC の要求では `rsc`・`next-router-prefetch` などの見出しを隠す（同梱の文書 `proxy.md`「During RSC requests, Next.js strips internal Flight headers」）。
  - そこで、ブラウザが付ける `Sec-Fetch-Dest: document` で文書の要求を見分けた。
- **案2: 全ページ共通の家族を、`unicode-range` で分けた共有のファイルで配る**（前回の方式 B の系統。変更前の見出しの Noto Serif JP も、この形である）。
- **案3: 着地のページはページごとのサブセット、遷移先は共有の分割ファイル。**
- **案4: ページの字の woff2 を HTML に埋め込む**（data URI。ページが描く `<style>` の中）。
- **案5: 前回の形**（家族名は全ページ共通、`unicode-range` はそのページの字、宣言は HTML の `<head>` にだけ置く）。2巡目のレビューで B-1 が再現された形である。
- **案6: サイト内のリンクを文書の遷移（ページの読み込み）にする**（クライアント側の遷移をやめる）。試作していない。

### 判断

- **案1を採る。** 比べた案の中で、次の3つを同時に満たすのは案1だけだった。案6は試作していないので比較から外している。
  - 遷移で書体が混ざらない（B-1）。
  - 上限を満たす。
  - FCP を悪くしない。
- 案1' は同じ結果を出すが、FCP が遅くなり、文書の要求ごとに関数が動く。Next.js の文書も proxy には最後の手段として頼るよう勧めている（`proxy.md`「We recommend users avoid relying on Middleware unless no other options exist」）。案1で足りるので採らない。
- 案2・案3 は、`unicode-range` で分けた面が、読み込み中に字ごとに別々に届く。そのため、読み込み中に1つの要素の中で書体が混ざる（変更前の見出しで実測した）。§3「一つの見出しの中で和文の書体が混ざらない」を読み込み中も守れない。案2 は、そのうえ上限を越える。
- 案4 は、埋め込んだフォントが HTML の中で二重になり（ページの `<style>` と、同じ HTML に入る RSC）、Link の先読みでも運ばれる。上限を越える。
- 案5 は、B-1 そのものである。

## 欧文とロゴ

### 事実

- 欧文の2ファイル（各 約 11KB）は全ページ共通で、preload の先頭に置いた。
  - 遅い 4G では、400 は採る形の前段（欧文 block）の21回すべてで FCP より前に届いた（1.34〜1.40秒）。
  - 700 は 21回中9回で、FCP より後（最大 +321ms）に届いた。
- 欧文を止めた状態から欧文を足すと、結果面で16要素（最大 53px）、ブログ記事で232要素（最大 56px）が動いた（上の表）。代わりの書体は、`size-adjust`・`ascent-override` などで IBM Plex Sans に合わせたサンセリフである。
  - 平均の字幅で合わせても、行の折り返しが変わる行が残る。
- 前回の試作では、ロゴと見出しの欧文を明朝の書体の並びで組んでいた。そのため、欧文が届く前は端末の serif（Liberation Serif など）で出た（2巡目の M-2）。

### 判断

- **欧文は `font-display: optional` にする。**
  - 最初の描画に間に合ったとき（遅い 4G で、400 は欧文 block の前段のビルドの21回すべてで FCP より前に届いた。採る形 (e) の35回では、見出しと段落の欧文に代わりの書体が出た回は0だった）だけ使う。
  - 間に合わなければ、そのページのあいだ代わりのサンセリフのままにし、差し替えない。
  - これで §12 は必ず成り立ち、§3 の欧文は測った範囲ではすべての回で出た。
- **欧文の代わりの書体を、serif に落ちない並びにする。** すべての書体の並びで、欧文の派生のすぐ後に、次の `@font-face` を置く。
  - `unicode-range` は欧文の基本範囲。
  - `src: local()` で端末のサンセリフ（Arial・Helvetica・Roboto・Liberation Sans）を指す。
  - メトリクスは合わせる（400 は `size-adjust: 100.2%`、700 は `98.3%`。IBM Plex Sans と Liberation Sans の平均の字幅から計算した）。
  - 和文の見出しの代わりは端末の明朝、本文の代わりは端末のゴシックのまま。欧文だけが serif に落ちることは無くなる。
  - 採る形の試作では、見出し・段落・ロゴのどこにも serif が出なかった（35回）。
- **ロゴ「yolos.net」は、欧文 700 の字形を SVG にして、上端に直接描く。**
  - 大きさは 2,593B（gzip で 1,280B）。上端はレイアウトにあるので、文書の読み込みでだけ運ばれる（遷移の RSC には入らない）。
  - フォントの読み込みに依らないので、最初の描画からいつも同じ形で出て、動かない。§1「デザインだけで yolos.net だと分かること」の要が、回線に左右されない。
  - 読み上げの名前はリンクの `aria-label`（「yolos.net」）が担い、SVG は `aria-hidden` にする。
  - 大きさは `em` で指定し、文字サイズの上書き（§4・§12）に従って大きくなる。色は `currentColor` にする。ドットの扱いは T1 のデザインで決める。
  - ライセンスは OFL FAQ 1.1.1 で扱う。フォントで作った図形は作った者の著作物であり、フォントの再配布にあたらない（「ライセンス」）。
- **欧文 700 は、太字の欧文を描くページだけで preload する。** ロゴが SVG になるので、700 が全ページで要る理由は無くなる。どのページが太字の欧文を描くかは、ビルドの時に字を集めるときに決まる。
- 見出しの欧文は、見出しのウェイトが 400（§3）なので、欧文 400 で出る。全ページで preload する。

## 入力に由来する字

前回の判断を変えない。

### 決めたこと

- **来訪者が入力した字（入力欄の中）と、その字をそのまま、または変換して映す表示（全角半角変換の結果など）は、欧文を IBM Plex Sans の派生、和文を端末のゴシックで組む。**
- 欧文の派生は `U+0020-007E` の全体を収めた静的な2ファイルで、どのページでも同じものを読む（入力に依らない）。
- 入力によって**どれが現れるかが決まる**表示（検索の結果など）も、その字の読み込みが入力を映すことになるので、同じく端末のゴシックで組む。候補の全体が小さく、全部を最初から含められる場合だけ、ページの層に入れてよい。
- **「入力に依らない」の意味**: 読み込むファイルの集合が、来訪者の入力・答え・操作の中身によって変わらないこと。
  - `unicode-range` で分けた静的な分割ファイルも、入力に現れた字に応じて読まれるファイルが変わる。そのため、入力由来の字には使わない。
  - 診断の結果の層は24通りを1つのファイルにまとめ、答えに依らない合図（「はじめる」）で読む。

### 理由

- ツールには「このツールはブラウザ上で動作します。入力データがサーバーに送信されることはありません。」（`src/tools/_components/ToolPageLayout/index.tsx:87`）と書いてある。ツール一覧にも「入力した内容はすべてブラウザの中で処理され、外部に送信されません。」（`src/app/tools/page.tsx:87`）とある。この約束は守る。
- 入力されうる字を最初から全部含める形は上限を越える。BIZ UDPGothic 400 を JIS X 0208 の非漢字と第1水準（3,489字）で切り出すと 564,468B で、どのページの余裕も大きく越える。
- 入力欄に Web フォントを当てたまま、ページの層にない字だけを端末の書体に落とすと、一つの文の中で字ごとに書体が混ざる。欄の和文を丸ごと端末のゴシックにするほうが読みやすい。
- 試作で、`/tools/traditional-color-palette` の入力欄の値が本文の家族で描かれている箇所があった（入力欄の部品の CSS が `font-family` を継承に戻していた）。T1 では、入力欄の部品の書体を、この規則で一か所から決める。

## ビルドの経路

### 分かっていること

- **プランとビルドの機械の種類は、確かめられなかった。** Vercel の API では、チーム（`macrats-projects`）の情報にプランの項目が無く、プロジェクトからも機械の種類は取れなかった。
- Vercel「Managing Builds」（2026-09-17 更新）によると、機械は次のとおりである。
  - Hobby は常に Basic（2 vCPU・8GB）。
  - Pro と Enterprise の新しいアカウントは Elastic（4〜30 vCPU）が既定。
- 直近の本番のデプロイ（`dpl_94FGe7RPX76jV8yEwPzuZJiageor`、2026-09-23）は、ビルドの開始から公開まで 238 秒だった。
- ビルドの上限は 45 分（Vercel「Limits」、2026-09-16 更新）。超えるとデプロイが失敗する。
- この機械（4 vCPU）で測った各工程の時間:

| 工程                                                          | 時間                                                     |
| ------------------------------------------------------------- | -------------------------------------------------------- |
| `next build`（写し、1回）                                     | 69〜99 秒                                                |
| 書き出された HTML 3,299 ファイル（200MB）を解析して字を集める | 2.5 秒（1プロセス）                                      |
| 全 3,526 ページ・3役割の切り出しと woff2 への圧縮             | 204〜209 秒（4プロセス。前回の計測）                     |
| Chromium で全ページを描いて字を集める                         | 約20分（6並列、各ページで読み込み後に 1.8 秒待つ。前回） |

### ビルドの中で字を集める方法を比べた

- **Chromium で描いて集める（前回の方式）。**
  - 役割は、描いたページの算出スタイルから正しく決まる。
  - ただし、Vercel のビルドの環境（Amazon Linux 2023。「Build image」2026-08-11 更新）では、NSS が無く Playwright の Chromium が起動しない。起動させるには `installCommand` で `dnf install -y nss` などを足す必要がある（2巡目のレビューが示した実例）。
  - さらに、この機械で約20分かかる。2 vCPU なら 40 分前後と見込まれ、上限の 45 分に近い。
- **マークアップから集める（Chromium を要さない）。**
  - 書き出された HTML とリクエストごとに描くページの HTML を、HTML の解析だけで読み、役割をマークアップで決める。
  - 今の CSS（見出しの書体をクラスで当てている箇所がある）のまま役割を「h1〜h6 は見出し、`strong`・`b`・`th` は太字、ほかは本文」と決めると、Chromium で集めた字と比べて次のようになった。
    - 16ページで見出しの字が 12〜74字足りない（例：ツールのカードの題名、辞典の大字の一覧）。
    - 太字の字が 0〜20字足りない。
    - 本文の字が 0〜65字多い。
  - 足りない字は、その要素で書体が混ざる原因になる。
  - **役割をマークアップだけで決まるように作れば**（下の条件）、集め方はマークアップから決まり、正確になる。

### 決めたこと

- **ビルドの中では Chromium を使わず、マークアップから字を集める。** そのため、T1 で書体の役割を次のようにマークアップで決める。
  - 見出しの書体は h1〜h6 と、見出しの書体を使うと属性で宣言した要素だけに当てる。
  - 太字は `strong`・`b`・`th` と、属性で宣言した要素だけにする。
  - コードは `code`・`pre`・`kbd`・`samp` だけにする。
  - 入力由来の表示は、属性で宣言する。
  - CSS はこの属性とタグにだけ書体を当てる。
  - 見出しの役割は要素ごとに決める。Zen Antique に無い字を含む見出しは、要素ごと本文の書体にする（§3、2巡目の m-4）。全 3,526 ページのうち 377ページで、見出しの役割の字に Zen Antique に無い字があった（例 `𠮟`）。
- **Chromium での確かめは、GitHub Actions の CI で行う**（Vercel のビルドには入れない）。
  - 代表のページについて、描いたページの算出スタイルの役割と、マークアップの役割が一致することを確かめる。
  - また、`CSS.getPlatformFontsForNode` で、入力由来の表示を除いて代わりの書体が出ないことを確かめる。
  - 現在の CI（`.github/workflows/deploy.yml`）は `npm run build` まで行っているので、その後に足す。
- **操作で現れる字（設問・結果、端末に保存された状態を映す字）は、データから集める。** 診断のデータのモジュールから、設問と24通りの結果の文を読む。
- **経路は、1つのビルドの中で、次の順に行う**（`npm run build` を書き換える）。
  1. `next build`（1回目）。
  2. 字を集める。書き出された HTML を解析する。リクエストごとに描くページは、ビルドの中で `next start` を立て、列挙したキーの HTML を HTTP で取る（Chromium は要らない）。操作で現れる字はデータから集める。
  3. 切り出す。harfbuzz と woff2 の設定は固定する（「試作の中身」）。中身のハッシュをファイル名にして `public/` の下に置き、キー → ファイルの表を書く。
  4. `next build`（2回目）。ページの部品が表を読み、`<style>` と preload を出す。
  - 2回ビルドするのは、ページの字が1回目のビルドの結果から決まり、表が無いとページを描けないからである。2回目で変わるのはページの `<style>` と preload だけで、ページの字は変わらないので、1回目の表がそのまま正しい。
- **切り出しは、ビルドのキャッシュに持つ。** 「書体のファイルのハッシュ＋設定＋字の集合」をキーに woff2 を Next.js のキャッシュのディレクトリ（`.next/cache` の下）に置き、変わったページだけ切り出す。ビルドのキャッシュは Basic・Standard で最大 1.5GB、1か月保持される（「Limits」）。
- **失敗したら、ビルドを失敗させる。** 字を集める工程と切り出す工程は、次のいずれかで 0 以外の終了コードを返し、`npm run build` 全体を失敗させる。Vercel では失敗したデプロイは公開されず、前の本番が残る。
  - 列挙したページに表の項目が無い。
  - 切り出しか圧縮が失敗した。
  - ページのマークアップの字が、そのページのファイルに入っていない（自己点検）。
  - 出力の数が列挙と合わない。
- **見積もったビルド時間**（キャッシュが空の最初のビルド）:
  - 4 vCPU（この機械）では、1回目 1.7 分＋集める 1 分未満＋切り出し 3.5 分＋2回目 1.7 分で、**約 8 分**。
  - 2 vCPU（Basic）で時間が倍になると見て、**約 16 分**。
  - 2回目以降のビルドは、変わったページだけ切り出す。
  - どちらの機械でも 45 分の 3分の1 前後に収まる。プランと機械が分からなくても、Basic（最も小さい機械）で収まる見込みなので、経路は成り立つ。
  - 実際の時間は T1 の最初のデプロイで記録する。30 分を越えたら、集める・切り出す工程の並列度とキャッシュを見直す。
- **T9 のプレビューは CLI で配る。**
  - `vercel.json` は main 以外の git のデプロイを止めているので、プレビューは `vercel deploy`（リモートでビルドする。`--prebuilt` ではない）で作る。
  - CLI の上限は、ソースのアップロード 100MB（Hobby）／1GB（Pro）と、ソース 15,000 ファイル（「Limits」）。git で管理しているファイルは 2,151 個・38.9MB で、どちらにも収まる。
  - `tmp/` など管理外のファイルが上げられないように、`.vercelignore` を置くかきれいな作業コピーから配る。CLI が `.gitignore` を使うかは確かめていない。
  - `--prebuilt` で配ると、出力（フォントだけで約 197MB）が上げるファイルになり、Hobby の 100MB を越えうるので使わない。
  - Vercel の changelog「CLI deployment limits removed」（2026-06-17）は CLI 固有の上限を取り除いたと書く。しかし、どの上限かは書いておらず、「Limits」の表には上の値が残っている。どちらが正しいかは確かめられなかった。上の経路は、上限が残っている場合でも成り立つ。
- **出力のファイル数と総量:** 全 3,526 ページで中身のある役割が 7,358 ファイル・197.1MB（前回の見積もり）。出力ファイルの数に上限は無い（「Limits」の Files）。総量の上限は一次資料に見つからなかった。T1 の最初のデプロイで、出力の量と公開までの時間を記録する。

## 測り方

### 転送量（合否の線）

- **計測器と設定**:
  - Lighthouse 12、`--only-categories=performance`、モバイルの既定。
  - Chromium は `/opt/pw-browsers/chromium-1194`、`--headless=new --no-sandbox`。
  - 値は `total-byte-weight` の numericValue。内訳は `network-requests` の `resourceType`（`Font`・`Fetch`・`Document`・`Stylesheet`）で見る。
  - 転送量は回線の模擬のしかたに左右されないので、simulate のままでよい。
- **回数と統計**: 各ページ・各ビルドで5回、中央値をとる。変更前と変更後は同じ機械で測る。
- **揺れの範囲の扱い**: 変更後の中央値 − 変更前の中央値 ≤ max(変更前の5回の幅, 変更後の5回の幅) なら「超えない」とみなす。
- **先読み（Fetch）の分を分けて残す**:
  - 合否は総転送量で決める（来訪者が払う量なので）。
  - 記録には、先読みの分と、それを除いた値を並べる。上端・下端のリンクが T2〜T7 で変われば、先読みの量も変わるからである。
- **流れ全体**:
  - `/play/character-personality` で、開始 → 12問 → 結果までを答え方3通りで通し、CDP の `encodedDataLength` を足す。変更前を越えないことを確かめる。
  - 着いた結果の見出しと、段階ごとの内訳の生の出力を残す（2巡目の m-5）。
- **遷移**: 上の10通りで、クリックのあとの全応答を記録する（合否には使わず、変更前と並べて残す）。

### LCP と FCP（調査の引き金）

- **回線を模擬した実測で取る**:
  - Playwright と CDP の `Network.emulateNetworkConditions`・`Emulation.setCPUThrottlingRate` で、遅い 4G（往復 562.5ms・下り 1,474.56Kbps・CPU 4倍）を掛ける。
  - 中継を通さず、出荷するビルドを直接開く。
  - simulate の LCP・FCP は、実際の読み込みの順序を反映しないので、判定に使わない。
- **回数と統計**:
  - 各ページ・各ビルドで20回、交互に測る。
  - 変更後の中央値 ÷ 変更前の中央値の比を、ブートストラップ（各群を復元抽出で10,000回）で95%区間にする。**区間の下限が 1.10 を超えたら「10% を超えて悪化した」とみなして原因を調べる。** LCP と FCP の両方に当てる。
  - 点推定が 1.10 を超え、下限が 1.10 以下なら、各40回に増やす。
  - 測る前に負荷平均が 1.0 を下回ることを確かめ、重い処理と同時に走らせない。
- **フォントが最初の描画に間に合ったか**も記録する。`CSS.getPlatformFontsForNode` で、FCP の直後と6秒後に、ロゴ・見出し・最初の段落を描いた書体を読む。
- **CLS** も同じ実測から取る（`layout-shift` のうち入力直後でないもの）。§12 の判定は CLS ではなく、下の矩形の比較で行う。

### 差し替えのずれ（§12）

- スキルの方法で、フォントを止めた状態 → 見出し → 欧文 → 本文、と段階ごとに足して、矩形を比べる。
  - 見出しと本文（swap）の差し替えで、動く要素が0であることを確かめる。
  - 欧文（optional）は、フォントを遅らせて返しても、読み込みの前後で矩形が変わらないことを確かめる。
- 遷移のあと（h1 が替わった直後と、落ち着いた後）の矩形も比べる。
- 端末の書体は機械によって違う。iOS（ヒラギノ）・Android（Noto Sans CJK）・Windows（游ゴシックなど）で、次の2点を T9 で WebKit と実機で確かめる。
  - 見出しと本文が動かないこと（とくに `palt` と `text-spacing-trim` の扱い）。
  - 欧文の代わりの書体の `local()` がサンセリフに当たること。

### 書体が混ざらないこと（§3）

- `CSS.getPlatformFontsForNode` で、1つの要素に和文の Web フォントと代わりの和文の書体が同居しないことを確かめる。対象は次の3つ。
  - 代表のページの最初の読み込み。
  - 上の4系統の遷移（ツール→ツール、結果面→結果面、辞典→辞典、ブログ→ブログ）と、結果面→プレイ面（遅い 4G と模擬なし、遷移の直後と落ち着いた後）。
  - 診断の流れ全体（開始の直後、各設問、結果）。**層をまたぐ文で字ごとに書体が混ざらないこと**を含む（2巡目の m-6）。
- コード（等幅）と入力由来の表示は、端末の書体で組むので対象から除く。

### 冷えた経路

- 配るのは静的なファイルだけなので、関数の起動や切り出しの待ちは無い。残る冷えは、ブラウザのキャッシュが空であることと、CDN の地域のキャッシュに無いこと（デプロイ直後の最初の要求）である。
- T9 で、プレビューのデプロイで、新しいファイル名のフォントを最初に要求したとき（`x-vercel-cache: MISS`）と2回目（`HIT`）の時間を比べて記録する。

### 変更前の値（facts-speed-before.md への追記の内容）

- 今回の変更前の値（上の表）を、`facts-speed-before.md` に追記する。追記は PM がこの判断の承認のときに行う。
- facts の値（プレイ面 558・結果面 549・ツール 493・辞典の詳細 1,435・ブログ記事 575KiB）との差（3.4〜6.5KiB）は、トップ `/` の RSC を先読みした応答が facts の実行に入っていたためである（1巡目のレビューで確かめられた）。

## スキルへの提案

`.claude/skills/frontend-design/SKILL.md` の次の箇所を、次のように直すことを提案する（このタスクでは編集しない）。スキルを直すのは T1 の中で、`DESIGN.md` §3 の書き換えと同じ変更に含める（スキルが `DESIGN.md` と食い違う期間を作らないため）。

1. 「値を変えるときの手順」の **「書体を変えたら、サブセットを作り直す。収録する字種は、サイトで実際に使う字から決める。」** を次に置き換える。

   > **和文の Web フォントは、ページごとにビルドの時に切り出して静的に配る。**
   >
   > - ページの字は、ページ固有の家族名で宣言し、その `@font-face` と書体の変数は、ページ自身が描く `<style>` に置く。遷移で前のページの面が残らないためである。
   > - 上端と下端の字は、全ページ共通の家族にする。
   > - 字は、マークアップで決めた役割ごとに集める（書体の役割はタグと属性で決め、CSS もそれにだけ当てる）。操作で現れる字のうちデータで決まるものは、来訪者の入力や答えに依らない層として作る。
   > - 来訪者が入力した字は、どのフォントの要求にも映さない。
   > - 実行時に字を切り出す配信口、`unicode-range` で分けた共有のファイル（next/font/google を含む）、サイト全体の字から作った共有のサブセットは使わない。
   > - 切り出しの道具と設定（レイアウト機能の一覧、ヒンティング、残す name）は固定する。name には著作権とライセンス（nameID 0・13・14）を残し、Reserved Font Name を持つ書体は名前を変えて配る（元の名前は説明の欄にだけ書き、STAT を除く）。
   > - 字を集める工程か切り出しが失敗したら、ビルドを失敗させる。
   > - 書体を変えたら、境界のページで総転送量が変更前を越えないことを測り直す。

2. 「実装の技術」の **「Web フォントは `font-display: swap` と `size-adjust` で、読み込みの前後で行の高さと字面を揃える。§12 の「読み込みのずれ」はこれで満たす。」** を次に置き換える。

   > **和文（本文の BIZ UDGothic・見出しの Zen Antique）は `font-display: swap`、欧文は `optional` にする。**
   >
   > - 和文の2書体は仮名と約物が全角で、端末の和文書体と字幅が揃うので、差し替えても動かない。これを崩さないため、見出しに `palt` を掛けず、本文の `text-spacing-trim` は `space-all` にする。
   > - 欧文は字ごとの幅が端末の書体と揃わないので、間に合わなければ差し替えない。欧文の代わりの書体は、`local()` の端末のサンセリフにメトリクスを合わせた `@font-face` を並びの2番目に置き、serif に落とさない。
   > - ロゴはフォントに依らない SVG で描く。
   > - preload は、ページが描く生の HTML（`dangerouslySetInnerHTML` の隠し要素）に書く。React の `<link rel="preload">` や `ReactDOM.preload()` は RSC に入り、Link の先読みのたびにフォントが読まれるので使わない。
   > - §12 は「作ったあとに確かめる」の矩形の比較で確かめる。

3. 「機械で確かめる」の表の **「Web フォントで内容がずれない」** の行に、確かめ方を書き足し、行を1つ足す。

   > **Web フォントで内容がずれない**: フォントを止めた状態から、見出し・欧文・本文の順に足して、レイアウトの矩形を比べる。swap の書体で動く要素が0であること。optional の書体は、フォントを遅らせて返したときに読み込みの前後で矩形が変わらないこと。クライアント側の遷移のあと（直後と落ち着いた後）も比べる。
   >
   > **一つの要素の中で和文の書体が混ざらない**: `CSS.getPlatformFontsForNode` で、1つの要素に和文の Web フォントと代わりの和文の書体が同居しないこと。最初の読み込み、クライアント側の遷移（直後と落ち着いた後）、操作で現れる字（層をまたぐ文を含む）で確かめる。
