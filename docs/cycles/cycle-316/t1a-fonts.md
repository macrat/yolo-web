## 比べた案

### 案の中身

- **A: next/font/google の分割配信。** Google の `unicode-range` ごとの woff2 を自己配信する。
- **A2: A で本文を端末のゴシックに改めたもの**（帰結の手順の最初の段）。
- **B: サイトで実際に使う字から共有のサブセットを作って静的に配る**（スキルの現在の記述）。分け方を3通り試した。
- **C-実行時（前回の方式 C）:** 読み込みの後にスクリプトが描いた字を集め、自サイトの切り出し口でその場で切り出す。
- **C-Google:** C-実行時の切り出しを Google Fonts の CSS API の `text=` に任せる。
- **C-静的:** ページごとの字の集合をビルドの時に決め、静的な woff2 にして、HTML の `<head>` から preload する。読み込みの時に描かれる字だけを扱う。
- **混成（採る）:** C-静的に、データで決まる字の層を足す。層は、ページが描く字の層・設問の層・結果の層のように、どの来訪者でも同じ中身をビルドの時に作る。層を読み込む合図は来訪者の入力や答えに依らない（ページの読み込み、開始の操作）。入力に由来する字は端末の書体。
- 表示のしかた（`font-display`）の案: swap（遅れても差し替える）・optional（最初の描画に間に合わなければ差し替えない）・block（届くまで字を描かない）・HTML への埋め込み（data: URI）。混成の中で比べた（「差し替えのずれ」）。

### 判断

- **上限を満たし、入力を送らず、読み込みに JavaScript を要さず、濫用の窓口を持たない案は、比べた中では C-静的と混成だった。** C-実行時と C-Google は B1（入力の送信）で外れる。A・A2・B は上限で外れる。
- **C-静的だけでは、読み込みの後に現れる字（診断の設問・結果）が Web フォントで描けない。** 混成はそれを、来訪者の答えに依らない静的な層で補う。PV の78%が集まる面で、設問の字（開始の画面に無い字が見出しで96字・本文で202字）と結果の字を扱えるのは混成だけなので、混成を採る。
- ページごとの正確なサブセットは、どの配り方でも下回れない転送量の下限である（前回の結論のまま）。C-静的と混成は、この下限を静的なファイルで実現する。

## 入力に由来する字の扱い

### 決めたこと

- **来訪者が入力した字（入力欄の中）と、その字をそのまま、または変換して映す表示（全角半角変換の結果など）は、欧文を IBM Plex Sans の派生、和文を端末のゴシックで組む。**
- 欧文の派生は `U+0020-007E` の全体を収めた静的な2ファイルで、どのページでも同じものを読み込む（入力に依らない）。入力欄の中の欧文と数字は §3 のとおり Plex で出る。
- 入力によって**どれが現れるかが決まる**表示（検索の結果など）も、その字の読み込みが入力を映すことになるので、同じく端末のゴシックで組む。候補の全体が小さく、全部を最初から含められる場合だけ、ページの層に入れてよい。
- **「入力に依らない」の意味**: 読み込むファイルの集合が、来訪者の入力・答え・操作の中身によって変わらないこと。`unicode-range` で分けた静的な分割ファイルも、入力に現れた字に応じて読まれるファイルが変わるので、入力由来の字には使わない（字そのものは送らなくても、どの分割ファイルを要求したかで入力の一部が分かる）。

### 理由

- ツールには「このツールはブラウザ上で動作します。入力データがサーバーに送信されることはありません。」（`src/tools/_components/ToolPageLayout/index.tsx:87`）、ツール一覧には「入力した内容はすべてブラウザの中で処理され、外部に送信されません。」（`src/app/tools/page.tsx:87`）と書いてある。この約束は守る。
- 入力欄に Web フォントを当てたまま、ページの層にない字だけを端末の書体に落とすと、一つの文の中で字ごとに書体が混ざる。欄の和文を丸ごと端末のゴシックにするほうが読みやすい。
- 入力されうる字を最初から全部含める形は上限を越える。BIZ UDPGothic 400 を JIS X 0208 の非漢字と第1水準（3,489字）で切り出すと 564,468B で、どのページの余裕（最小 約94KiB）も大きく越える。

### §3 との両立

§3 は本文・UI の和文を BIZ UDPGothic と定めている。入力欄とその映しは UI・結果の一部なので、この扱いは §3 の例外になる。約束（憲法の規則1・2）と上限（計画）のどちらからも、§3 のままでは成り立たないことを上の事実で示せるので、「`DESIGN.md` を変えるとき」の手順で §3 に書き加える。書き加える文の案:

> **来訪者が入力した字と、それを映す表示は、和文を端末のゴシックで組む。** 入力を Web フォントの読み込みに映さないためである。欧文と数字は IBM Plex Sans で組む。

見た目の妥当さ（欄の中の和文だけ字形が変わること）は、T9 で来訪者の目で確かめる。

## リクエストごとに描くページと、流れ全体

### リクエストごとに描くページ

- **診断の結果（`/play/<slug>/result/<id>`）・知識クイズの結果・`?with=` 付きの結果**は、リクエストごとに描くが、描く中身はデータで決まっていて列挙できる。結果の id は 15本で計 139（前回の巡回で数えた）、`?with=` の組は最大でその自乗の和 1,413。
- **ビルドの時に、列挙できるキー（id、id と with の組）ごとにページとして字を集めて切り出し、キーからファイル名を引く表（マニフェスト）を作る。** サーバーは描くときに表を引いて `<head>` に書くだけで、実行時に切り出さない。キーは既存の検証（`isValidCharacterPersonalityTypeId` など）を通ったものだけで、通らない値は `?with=` の無いページと同じファイルを使う。
- 全ページの見積もりには、知識クイズの結果 22 と `?with=` 付き 129 が入っていて、すべて変更前より減る。`?with=` のすべての組を試作したわけではない。

- **見出しの Zen Antique は swap。** 差し替えてもずれない（7ページで0）。§1 の「巨大なアンティーク体の見出し」は、遅れても必ず出る。

## 測り方

### 転送量（合否の線）

- **計測器と設定**: Lighthouse 12、`--only-categories=performance`、モバイルの既定。Chromium は `/opt/pw-browsers/chromium-1194`、`--headless=new --no-sandbox`。値は `total-byte-weight` の numericValue。内訳は `network-requests` の `resourceType`（`Font`・`Fetch`・`Document`・`Stylesheet`）。転送量は回線の模擬のしかたに左右されないので、simulate のままでよい。
- **回数と統計**: 各ページ・各ビルドで5回、中央値。変更前と変更後を同じ機械で1回ずつ交互に測る。
- **揺れの範囲の扱い**: 変更後の中央値 − 変更前の中央値 ≤ max(変更前の5回の幅, 変更後の5回の幅) なら「超えない」とみなす。
- **先読み（Fetch）の分を分けて残す**: 合否は総転送量で決める（来訪者が払う量なので）。記録には、先読みの分と、それを除いた値を並べる。上端・下端のリンクが T2〜T7 で変われば先読みの量も変わるので、差が先読みから来たのかを読めるようにする。
- **流れ全体**: `/play/character-personality` で、開始 → 12問 → 結果までを答え方3通りで通し、CDP の `encodedDataLength` を足す。変更前を越えないことを確かめる（上限と同じ考え方を流れにも当てる）。

### LCP と FCP（調査の引き金）

- **回線を模擬した実測で取る**。Lighthouse の `--throttling-method=devtools`、または Playwright と CDP の `Network.emulateNetworkConditions`・`Emulation.setCPUThrottlingRate` で、遅い 4G（往復 562.5ms・下り 1,474.56Kbps・CPU 4倍）を掛ける。simulate の LCP・FCP は、実際の読み込みの順序（どのフォントが最初の描画に間に合ったか）を反映しないので、判定に使わない。
- **回数と統計**: 各ページ・各ビルドで20回、交互に測る。変更後の中央値 ÷ 変更前の中央値の比をブートストラップ（各群を復元抽出で10,000回）で95%区間にし、**区間の下限が 1.10 を超えたら「10% を超えて悪化した」とみなして原因を調べる**。LCP と FCP の両方に当てる。点推定が 1.10 を超え下限が 1.10 以下なら各40回に増やす。測る前に負荷平均が 1.0 を下回ることを確かめ、重い処理と同時に走らせない。
- **フォントが最初の描画に間に合った割合**も記録する（`CSS.getPlatformFontsForNode` で、見出しと最初の段落を描いた書体を読む）。§3 に書き加える扱いのもとで、本文がどれだけ端末のゴシックになっているかを知るためである。
- **CLS** は同じ実測から取る（`layout-shift` のうち入力直後でないもの）。§12 の判定は CLS ではなく、下の矩形の比較で行う。

### 差し替えのずれ（§12）

- スキルの方法で、フォントを止めた状態・見出しだけの状態・全部読み込んだ状態の矩形を比べる。見出しの差し替え（swap にするもの）で動く要素が0であることを確かめる。本文と欧文は optional なので、差し替えが起きないことを、フォントを2秒遅らせて返す状態で、読み込みの前後の矩形が変わらないことで確かめる。
- 端末の書体は機械によって違う。iOS（ヒラギノ）・Android（Noto Sans CJK）・Windows（游ゴシックなど）の代わりの書体で見出しが動かないことは、今回確かめていない。T9 で WebKit と実機で確かめる。

### 冷えた経路

- 混成で配るのは静的なファイルだけなので、関数の起動や切り出しの待ちは無い。残る冷えは、ブラウザのキャッシュが空であること（Lighthouse と上の実測は毎回空で測っている）と、CDN の地域のキャッシュに無いこと（デプロイ直後の最初の要求）。
- T9 で、出荷する前のプレビューのデプロイで、新しいファイル名のフォントを最初に要求したとき（`x-vercel-cache: MISS`）と2回目（`HIT`）の時間を比べて記録する。

## 本番での成り立ち

### 仕組み（T1 で作るもの）

1. **1回目のビルド**（`next build`）のあと、書き出されたページと、列挙できるリクエストごとのページ（結果の id、id と with の組）を描いて、役割ごとの字を集める。集め方は「字の集め方の条件」のとおり。
2. **切り出し**: 役割ごとに woff2 を作り、中身のハッシュをファイル名にして静的なファイルとして置く。ページの URL（またはリクエストごとのページのキー）からファイル名を引く表を作る。
3. **2回目のビルド**: 表を読んで、各ページの `<head>` に preload と `@font-face` を書く。2回目で変わるのは `<head>` のフォントの記述だけで、ページの字は変わらないので、1回目の表がそのまま正しい。
4. 実行時は、リクエストごとのページで表を引くだけ。切り出しの配信口は無い。

### 分かっていること（一次資料と実測）

- **静的なファイルは CDN に自動で置かれる。** Vercel「CDN Cache」（2026-09-14 更新）: 「Static files are automatically cached on Vercel's global network for the lifetime of the deployment after the first request.」「If a static file is unchanged, the cached value can persist across deployments due to the hash used in the filename」。中身のハッシュをファイル名にするので、ページの字が変わらなければデプロイをまたいでキャッシュが残る。`s-maxage` は要らない（関数の応答ではない）。
- **ビルド時間の上限は 45 分**（Vercel「Limits」、2026-09-16 更新）。直近の本番のデプロイ（`dpl_94FGe7RPX76jV8yEwPzuZJiageor`、2026-09-23）は、ビルドの開始から公開まで 238 秒だった（Vercel の API で取得）。
- **出力ファイルの数に上限は無い**（同「Limits」の Files: 「Although there is no upper limit for output files created during a build, you can expect longer build times as a result of having many thousands of output files (100,000 or more, for example).」）。混成で増えるファイルは、全 3,526 ページで中身のある役割が 7,358 ファイル（重複を除く前）、合計 197.1MB。`?with=` の組をすべて作ると、最大で約 4,200 ファイル増える。
- **ビルドの機械**: Hobby は Basic（2 vCPU・8GB）、Pro の新しいアカウントは Elastic（4〜30 vCPU）（Vercel「Managing Builds」、2026-09-17 更新）。このプロジェクトのプランと機械の種類は確かめていない。
- **切り出しの時間**: 全 3,526 ページ・3役割の切り出しは、手元の 4 プロセス並列で 204〜209 秒（1ファイルあたり約 0.1 CPU 秒。ほとんどが woff2 への圧縮）。2 vCPU なら約 7 分の見込み。
- **関数の地域**: 直近のデプロイの `regions` は `iad1`。混成では関数で切り出さないので、地域は字の配信に効かない。
- **濫用の窓口は無い**（M3）。来訪者が指定できるのは静的なファイルの URL だけで、存在しないファイルは 404 になる。リクエストごとのページでも、表を引くキーは既存の検証を通った id だけである。

### 確かめられなかったこと（T1 の最初に確かめる）

- **Vercel のビルドの中で Chromium を動かして字を集められるか。** 手元（Linux・Playwright の Chromium 1194）では動く。Vercel のビルドの環境で Playwright の Chromium が起動するかは確かめていない。
  - 動かないときの代わり: ブラウザを使わず、HTML の本文と RSC の中の文字列から字を集める。試作では、この形は7ページで +2〜+18KB 多く含み（本文 400）、プレイ面では RSC に入っている診断のデータ全体を拾って +123KB になった。また、`/blog/tag/漢字` など一覧をクライアントで描くページ（`BAILOUT_TO_CLIENT_SIDE_RENDERING`）は HTML だけでは字が足りない（RSC を含めれば足りる）。この形を採るなら、プレイ面は設問・結果の層を別に作り、ページの層から除く処理が要る。
  - もう一つの代わり: GitHub Actions でビルドして `vercel deploy --prebuilt` で配る。デプロイの経路を変えることになる。
- **2回ビルドしたうえで字を集めて切り出す時間が 45 分に収まるか。** 前回の巡回（6並列、各ページで読み込み後に 1.8 秒待つ設定）は 3,526 ページで約20分だった。待ちを短くできるかと、Vercel の機械での時間は確かめていない。収まらないときは、ビルドのキャッシュ（最大 1.5GB 以上、1か月保持。Vercel「Limits」）に「ページの HTML のハッシュ → 字の集合」「字の集合のハッシュ → woff2」を置き、変わったページだけ描き直して切り出す。
- **197MB の出力が問題にならないか**（出力の総量の上限は一次資料に見つからなかった）。
- **preload をページの HTML にだけ置く方法。** 試作で、RSC の中にフォントの preload の指示（`:HL[…]`）を入れると、Next.js が自動でリンク先を先読みしたときに、その指示どおりにフォントが読まれることを確かめた（辞典の詳細で、先読みされた36件の RSC のうち25件分のフォントの要求が出た）。ページごとのサブセットは先読みの数だけ転送量を増やすので、**preload は HTML にだけ置き、RSC には入れない**ことを条件にする。React の `preload()` や、React が資源として巻き上げる `<link rel="preload">` は RSC に入る（Next.js 16.3 同梱の文書 `generate-metadata.md` の「Resource hints」が案内する方法）。HTML にだけ置く具体的な方法（React が巻き上げない形の link 要素、ビルド後の HTML への書き込みなど）は T1 で決め、先読みでフォントが読まれないことを試作と同じ方法で確かめる。
- **クライアント側の遷移で、遷移先のフォントがどう読まれるか**（上の「差し替えのずれ」の最後）。

### 字の集め方の条件（M6）

- 描いたページのすべてのテキストノードを、表示されているかに関わらず集める（閉じた `<details>`、タブ、`display: none` の中も）。役割は各テキストノードの親要素の算出スタイル（`font-family` と `font-weight`）で決める。入力欄の値と placeholder、`::before`/`::after` の `content` も含める。
- 入力由来の字を描く要素（入力欄と、入力を映す表示）は、`font-family` が端末のゴシックなので、自然に Web フォントの層から外れる。
- 設問・結果のように操作で現れる字は、ビルドの時にその状態を描いて集める（結果の表示を24通り描く、など）。
- 確かめ方: T9 で、フォントを読み込んだ状態で、入力由来の表示を除くすべての文字が Web フォントで描かれていること（`CSS.getPlatformFontsForNode` に代わりの書体が出ないこと）を、代表のページと流れ全体で確かめる。

### 字の集合が増えていくこと（AP-P03）

- ページごとに閉じているので、あるページの字が増えても、他のページの転送量は変わらない。URL の長さの問題も無い（ファイル名はハッシュ）。
- 増えるのはビルド時間である。ページ数に比例して、切り出し（1ページあたり約 0.24 CPU 秒）と字を集める描画が伸びる。ビルドの時間を毎回記録し、30 分を越えたら上のキャッシュを入れる。
- 1ページの字が増えれば、そのページの転送量が増える。上限は T9 で出荷するビルドで測り直す。

## 試作の中身

- **切り出しの道具と設定（本番で使うもの）**: harfbuzz の hb-subset（npm `harfbuzzjs` 1.6.2 の wasm）で切り出し、Google の woff2 エンコーダ（npm `wawoff2` 2.0.1）で圧縮する。元の書体は Google Fonts のリポジトリの `ofl/zenantique/ZenAntique-Regular.ttf`・`ofl/bizudpgothic/BIZUDPGothic-{Regular,Bold}.ttf`・`ofl/ibmplexsans/IBMPlexSans[wdth,wght].ttf`。
  - **レイアウト機能は許可した一覧だけ残す**: `ccmp`・`locl`・`kern`・`mark`・`mkmk`・`palt`・`halt`・`chws`（フォントに無いものは無視される）。縦書きの `vert` や `jp78` などの字形の閉包を入れない。npm `subset-font` の既定（すべての機能を残す）では、`/tools/email-validator` の本文 400 が 25,816B → 55,836B（+116%）になった。道具と設定で大きさが大きく動くというレビューの指摘（M2）はこのためで、設定を固定すれば動かない。
  - ヒンティングは残す（BIZ UDPGothic の `fpgm`・`prep`）。name は 0〜6・13・14 を残す。
  - 1回目に書体を読み込み、それを使い回して切り出す（1ファイルの切り出しは 1〜3ms、圧縮は 14〜372ms）。
  - 前回の試作（fontTools、name を消す設定）との比較: `/tools/email-validator` の本文 400 は fontTools 27,680B、harfbuzz 25,816B。harfbuzz のほうが小さく、name を残しても見積もりは増えなかった。
- **中継サーバー**: 変更前のビルドの応答を通し、(1) CSS から `@font-face` をすべて除いて全ページ共通の規則（欧文の派生の `@font-face`、書体の変数の上書き、入力欄を欧文の派生＋端末のゴシックにする規則、見出しをウェイト 400 にする規則）を足し、(2) HTML・RSC・HTTP の `Link` ヘッダから変更前のフォントの preload を除き、(3) HTML の `<head>` にそのページの preload（欧文の派生 400、太字の欧文を描くページは 700、ページの層）と `@font-face`（ページごとの家族名。`unicode-range` はそのファイルの字）を書き、(4) プレイ面には設問の層（`fetchpriority="low"` の preload）と、「はじめる」で結果の層を読む数行のスクリプトを足した。フォントは `cache-control: public, max-age=31536000, immutable` で返した。
- 変更前は `next start` に直接、変更後は中継サーバーを通して測った。中継による転送量の差はフォントを変えずに通したとき −0.5KiB（前回の確認）。中継は HTML をまとめて返す（ストリーミングしない）ので、FCP の比較には中継の分が入っている。
- **前回の方式 C の値の注意**: 前回の中継サーバーは HTTP の `Link` ヘッダを除いていなかったので、プレイ面（リクエストごとに描き、`Link` ヘッダに変更前の Noto Serif JP の preload 2件が載る）の方式 C の値には、変更前のフォント2ファイルが入っていた。今回の中継では除いた。

## スキルへの提案

`.claude/skills/frontend-design/SKILL.md` の2か所を、次のように直すことを提案する（このタスクでは編集しない）。スキルを直すのは T1 の中で、`DESIGN.md` §3 の書き換えと同じ変更に含める（スキルが `DESIGN.md` と食い違う期間を作らないため）。

1. 「値を変えるときの手順」の **「書体を変えたら、サブセットを作り直す。収録する字種は、サイトで実際に使う字から決める。」** を次に置き換える。

   > **和文の Web フォントは、ページごとにビルドの時に切り出して静的に配る。** ページが描く字（隠れている字を含む）を役割ごとに集め、操作で現れる字のうちデータで決まるものは、来訪者の入力や答えに依らない層として作る。来訪者が入力した字は、どのフォントの要求にも映さない。実行時に字を切り出す配信口、`unicode-range` で分けた共有のファイル（next/font/google を含む）、サイト全体の字から作った共有のサブセットは使わない。切り出しの道具と設定（レイアウト機能の一覧、ヒンティング、残す name）は固定する。name には著作権とライセンス（nameID 0・13・14）を残し、Reserved Font Name を持つ書体は名前を変えて配る。書体を変えたら、境界のページで総転送量が変更前を越えないことを測り直す。

2. 「実装の技術」の **「Web フォントは `font-display: swap` と `size-adjust` で、読み込みの前後で行の高さと字面を揃える。§12 の「読み込みのずれ」はこれで満たす。」** を次に置き換える。

   > **差し替えても字幅が変わらない書体（見出しの Zen Antique）は `font-display: swap`、字幅が変わる書体（本文の BIZ UDPGothic・欧文）は `font-display: optional` にする。** プロポーショナルな仮名や欧文は `size-adjust` では揃わない。どちらも `<head>` の preload で最初の描画に間に合わせる。preload はページの HTML にだけ置き、RSC（先読みの応答）には入れない——先読みされたページのフォントまで読まれる。§12 は「作ったあとに確かめる」の矩形の比較で確かめる。

3. 「機械で確かめる」の表の **「Web フォントで内容がずれない」** の行に、確かめ方を書き足す。

   > フォントを止めた状態・swap の書体だけを読み込んだ状態・全部を読み込んだ状態で、レイアウトの矩形を比べる。swap の書体で動く要素が0であること。optional の書体は、フォントを遅らせて返したときに読み込みの前後で矩形が変わらないこと。
