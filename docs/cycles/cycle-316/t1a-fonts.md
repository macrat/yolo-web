## 測り方

### 転送量（合否の線）

- **計測器と設定**: Lighthouse 12、`--only-categories=performance`、モバイルの既定（模擬の回線と CPU の減速）、Chromium は `/opt/pw-browsers/chromium-1194`、`--headless=new --no-sandbox`。値は `total-byte-weight` の numericValue。Web フォントの内訳は `network-requests` の `resourceType` が `Font` のもの。
- **回数と統計**: 各ページ・各ビルドで **5回、中央値**。
- **理由**: 総転送量はほとんど揺れない。今回の計測でも、同じページの5回（または2回）の幅は最大 1.6KiB（0.3%）で、7ページ中5ページは5回とも同じ値だった。facts の揺れも最大 0.33%。5回あれば、たまたま外れた1回に左右されない。
- **「揺れの範囲の差」の扱い**: 変更後の中央値 − 変更前の中央値 ≤ max(変更前の5回の幅, 変更後の5回の幅) なら「超えない」とみなす。幅を越えて増えていれば上限を越えたと判定する。
- **環境**: 変更前と変更後のビルドを別のポートで同時に起動し、同じ機械で1回ずつ交互に測る。方式 C の切り出し口は、本番では最初の来訪者のあとは CDN に置かれた応答を返す。そのため、計測の前に各ページを1度開いておき、ほとんどの来訪者と同じ状態で測る（転送量はこれで変わらない。変わるのは LCP だけ）。

### LCP（調査の引き金）

- **設定**: 転送量と同じ実行から取る（`largest-contentful-paint` の numericValue と、`largest-contentful-paint-element` の要素）。
- **回数**: 各ページ・各ビルドで **20回**。変更前と変更後を1回ずつ交互に測る。計測の前に負荷平均が 1.0 を下回っていることを確かめ、ビルドや巡回など重い処理と同時に走らせない。
- **統計**: 変更後の中央値 ÷ 変更前の中央値の比について、ブートストラップ（各群を復元抽出で10,000回）で95%区間を求める。**区間の下限が 1.10 を超えたら「10% を超えて悪化したと言える」とみなし、原因を調べる。** 比の点推定が 1.10 を超えているのに区間の下限が 1.10 以下のときは、各40回まで増やして判定し直す。
- **理由**: 今回の各5回で、変更前の LCP の変動係数はページによって 0.04（ツール）〜0.28（ブログ記事）あった。5回では比の95%区間の幅が ±15〜30% になり、10% の悪化を見分けられない（例: ブログ記事は 0.61〜1.22）。20回にすると区間はおよそ半分になる。交互に測ると、機械の負荷の移り変わりが両方に同じように掛かる。
- **LCP の要素が変わったとき**: 要素が変わると別の物を比べることになる。そのときは要素ごとに記録し、比べられるかどうかを記録に残す（今回 `/tools/traditional-color-palette` では、変更前は見出し、方式 C では説明文の段落が LCP の要素だった）。

## 見積もりの方法と前提

### 変わらない部分と変わる部分

- **変わらない**: HTML・JS・画像・フォント以外の CSS。試作では、変更前のビルドの応答をそのまま通した。
- **変わる（試作で差し替えた）**:
  - フォントの CSS。ビルドの CSS `3oowozwf2g6q4.css` から `@font-face` をすべて除き（Noto Serif JP・Zilla Slab。gzip で約 33KB）、方式の `@font-face` と、書体の変数の上書き（`--font-mincho` → Plex, Zen Antique／`--font-gothic` と `--font-number` → Plex, BIZ UDPGothic）を足した。
  - フォントの preload。HTML と RSC（プリフェッチの応答を含む）の `:HL[…font…]` から Noto Serif JP と Zilla Slab の preload を除き、各方式の preload を足した（方式 C・A とも Plex 400 のみ）。
  - 方式 C では、`</body>` の直前にインラインの読み込み用スクリプト（1,281 バイト、gzip 757 バイト）を足した。
- 中継サーバーは HTML・CSS・RSC を gzip で返す（`next start` と同じ）。中継による差は、フォントを変えずに中継した同じページで −0.5KiB（488.9 → 488.4KiB）だった。

### 方式 C の試作の中身

- 読み込み用スクリプトは、表示されているテキストノードの親要素の算出スタイルから役割（先頭2つの `font-family` に Zen があれば見出し、Plex で始まれば本文。本文は `font-weight` 600 以上で 700）を決め、`U+0080` 以上の字を役割ごとに集め、まだ要求していない字だけを `FontFace` で読み込む（`unicodeRange` にその字、`display: swap`）。`MutationObserver` で、あとから描かれた字も50ミリ秒まとめて読み込む。
- 切り出し口は、元の書体ファイル（Google Fonts のリポジトリ `https://raw.githubusercontent.com/google/fonts/main/ofl/` の `zenantique/ZenAntique-Regular.ttf`・`bizudpgothic/BIZUDPGothic-Regular.ttf`・`bizudpgothic/BIZUDPGothic-Bold.ttf`）から、fontTools 4.66 の `subset` で指定の字だけを切り出して woff2 で返す。既定のレイアウト機能に `palt` を足し、TrueType のヒンティングは残した（Google Fonts が BIZ UDPGothic と IBM Plex Sans の配信ファイルにヒンティングを残しているのに合わせた。配信ファイルに `fpgm`・`prep` があることを確かめた）。
- IBM Plex Sans は `ibmplexsans/IBMPlexSans[wdth,wght].ttf` を wght 400・700（wdth 100）で固定し、`U+0020-007E` を切り出した（400: 12,992B、700: 13,152B）。`unicode-range: U+0000-007F`。
- **切り出しの大きさが Google と同じ水準であることを確かめた**: Google Fonts の分割ファイルから字の集合を取り出し、同じ集合を上の手順で切り出すと、大きさは Google の 80〜100% だった（BIZ UDPGothic 4件で 93〜100%、Zen Antique 4件で 80〜99%。字の少ないファイルほど差が大きい）。見積もりが Google の配信ファイルより大きく出ることはない。

### 全ページの見積もり（方式 C）

全 3,526 ページについて、上の字の集合から方式 C の Web フォントの転送量を近似した（字ごとの字形のバイト数に係数を掛け、ファイルごとの固定分を足す一次式。係数は実際の切り出しから決めた: BIZ UDPGothic は固定分 3.3KB・係数 0.575、Zen Antique は 0.66KB・0.44）。ページが読み込みの後で字を足す分として、本文 400 のファイルを1つ余分に数えた（5.6KB）。

- **3,526 ページすべてで、Web フォントの転送量が変更前より減る。** 減り方が最も小さいのは `/tools/email-validator`（−89.7KiB）、中央値は −387.1KiB。
- このうえ全ページ共通で、フォントの CSS が約 34KiB 減り、読み込み用スクリプトが約 0.8KiB 増える（試作の実測で CSS は 54〜60KiB → 20〜26KiB）。

### 前提と、確かめられなかったこと

- **字の集合は変更前のページのもの。** T2〜T7 で見出しと本文の割り当てや文言が変わる。方式 C はページが描く字に合わせて切り出すので、配り方としてはそのまま追随する。ただし上限を満たすかどうかは T9 で測り直す。
- **本番の切り出し口は試作していない。** 試作では手元の Python（fontTools）で切り出した。本番の Next.js（Vercel）で、関数の中で切り出して woff2 に圧縮する処理が実用的な速さで動くか、URL のクエリごとに CDN に応答が置かれるかは確かめていない。T1 で最初に確かめる。確かめられなかった場合の代わりの切り出し口は、Google Fonts の CSS API の `text=` 引数である（下の「比べた配り方」）。
- **ページが読み込みの後で描く字**（診断の設問、ツールの結果、入力された字）は、その字の分だけ追加で読み込む。Lighthouse の総転送量には、読み込み時点までの分しか入らない。
- **JavaScript が動かない環境**では Web フォントが読まれず、端末の書体で表示される。
- **CLS**: 試作には代わりの書体の `size-adjust` を入れていないので、方式 C の CLS はわずかに増えた（中央値で、メールアドレスのツール 0 → 0.021、ブログ記事 0.115 → 0.146）。T1 では、メトリクスを合わせた代わりの書体の `@font-face`（`size-adjust`・`ascent-override` など）を置く。
- **LCP（参考）**: 各5回の中央値の比（方式 C ÷ 変更前）は 0.78〜1.09 で、区間の下限が 1.10 を超えたページは無かった。5回では判定できない（上の「測り方」）。フォントの読み込みの開始がスクリプトの実行を待つことが LCP に出るかどうかは、T9 の20回の計測で確かめる。

## 比べた配り方

全ページの数字は Web フォントの転送量（応答ヘッダを含む）の、変更前との差。上限の判定には、これに CSS の差（下に記す）を足す。

### A: next/font/google の分割配信

Google の CSS にある `unicode-range` ごとの woff2 を自己配信する（`facts-external-specs.md` §3）。Zen Antique 122面、BIZ UDPGothic 248面（400・700）。IBM Plex Sans は可変フォントで、400 と 700 が同じファイルになる（latin 45,712B）。

- **7ページすべてで越える**（+449〜+1,809KiB。試作を Lighthouse で測った値）。全 3,526 ページでは 3,505 ページで Web フォントが増え、最大は +1,754KiB。
- 原因は分割の粒度にある。BIZ UDPGothic の分割ファイルは1つ平均約 23KB で、字の出現が偏った1万字余りをおよそ120字ずつに分けている。本文の字が200字あるページでも40ほどのファイルに触れ、1ファイルのうち使う字は数字にとどまる。
- フォントの CSS も、gzip で 33KB から 90KB に増える。
- **A2: 本文を端末のゴシックに改めた場合**（Zen Antique の分割配信 + Plex。帰結の手順の最初の段）でも、7ページすべてで Web フォントが増え（+6〜+85KiB）、全ページでは 3,318 ページで増える。フォントの CSS は gzip で約 4KB 減る（Zen Antique の122面で 29.0KB）ので、総転送量では `/tools/email-validator` の差は約 +2KiB になるが、ほかの6ページは越える。同じ字を覆う分割ファイルの数は Noto Serif JP とほぼ同じで、1ファイルが重い（Zen Antique の全字形の平均は1字あたり約 355B）。next/font を採ると、帰結は見出しの Zen Antique を端末の書体に改めるところまで進む。

### B: サイトで実際に使う字から、共有のサブセットを作る（frontend-design スキルの記述どおり）

全ページで使う字を集め、共有のファイルに分けて、静的に配る。

- **サイト全体を1ファイルにする形**は越える。サイト全体で使う字は Zen Antique の役割で約 2,400字以上あり、1ファイルにすると 1MB を超える。すべてのページがそれを読む。
- **分け方を最適化した形**も越えた。次の3つを試した。
  1. 使うページ数の順に字を並べ、上位を1ファイル、残りを一定の字数ずつに分ける形
  2. ページごとにまだ割り当てていない字をまとめる形
  3. 同じページの組で使われる字をまとめ、合わせると全ページの合計が減る組を順に合わせていく形。上限を越えたページの重みを上げて10回やり直した

  3が最も良かったが、1,462 ファイルに分けても、73 ページで Web フォントが変更前を越えた。最大は `/tools/yoji-search` の +159KiB。7ページでは `/tools/traditional-color-palette` が +144.7KiB、`/tools/email-validator` が +34.1KiB、`/blog/sql-cheatsheet` が +20.8KiB だった。フォントの CSS は gzip で 38.7KB（変更前 33.3KB）。

- 越える理由: 珍しい字は、それぞれ違うページの組で使われる。字の「使われるページの組」は字の数とほぼ同じだけある（Zen Antique の役割で 2,440字に 1,934通り。巡回した最初の 900 ページで数えた）。そのため共有のファイルは、どう分けても、どこかのページに使わない字を運ぶ。
- 運用上の弱み: 文章を足すたびに字の集合が変わるので、全ページを描いて字を集め直し、分け直す工程がビルドのたびに要る。集め漏れた字（新しい記事、入力された字）は、覆う書体ファイルが無ければ端末の書体に落ちる。
- これより良い分け方が無いことまでは示していない。示したのは、試した3つの分け方がどれも上限を越えたことである。

### C: ページが描く字だけを、その場で切り出して配る（採用）

上の「方式 C の試作の中身」のとおり。7ページすべてで総転送量が減り（−122〜−791KiB）、全ページの近似でも全ページで Web フォントが減る。ページが描く字だけを運ぶので、どの配り方よりも少ない（ページごとの正確なサブセットが、どの配り方でも下回れない下限になる）。文章が増えても、入力された字でも、その字を含むファイルが作られる。

切り出し口の2つの形:

- **C-自己配信（採る）**: 自サイトの Route Handler で切り出す。外部に接続しない。
- **C-Google**: Google Fonts の CSS API の `text=` 引数で、Google に切り出させる。代表の5ページで実際に取得すると、woff2 は fontTools の切り出しより 7〜22% 大きく（例: `/play/character-personality` の本文 400 が 38,740B。fontTools では 31,800B）、1回ごとに CSS の応答（gzip で 0.3〜2.5KB）が加わる。これでも上限は満たす。ただし、ページごとに2つの外部オリジン（`fonts.googleapis.com`・`fonts.gstatic.com`）へ接続し、来訪者の IP アドレスとページの字が Google に送られる。C-自己配信が T1 で成り立たないときの代わりとする。

### 本文のウェイトを減らす

`DESIGN.md` §4 は合成太字を禁じているので、700 を持たずに太字を出すことはできない。方式 C では、700 のファイルは太字で描いた字だけを収めるので小さい（7ページで 0〜11KB）。減らしても得はほとんどない。検討から外した。

## 判断

- **上限（変更前を越えない）を満たす配り方は方式 C だけだった。** 方式 A は7ページすべてで越え、本文を端末のゴシックに改めても越える。方式 B は、試した分け方では 73 ページで越える。
- **よって方式 C を採り、書体は `DESIGN.md` §3 のままにする。** 本文・UI の BIZ UDPGothic も、見出しの Zen Antique も、端末の書体に改めない。`DESIGN.md` §3 の書き換えは要らない。上限は動かしていない。
- 方式 C は、来訪者の側で見ても最も良い。変更前より各ページ 122〜791KiB 軽くなる（Lighthouse のモバイルの既定の回線、約 200KiB/秒で約 0.6〜4.0 秒分）。
- **T1 で実装するときの条件**（この判断の前提）:
  1. 切り出し口を Next.js の Route Handler で作り、本番（Vercel）で、切り出しと woff2 への圧縮が動くこと、応答が CDN に置かれることを最初に確かめる。成り立たなければ C-Google に切り替え、プライバシーポリシーに Google Fonts を加える。
  2. 代わりの書体の `@font-face` に `size-adjust` などのメトリクスを合わせ、読み込みの前後で行の高さと字面を揃える（`DESIGN.md` §12、frontend-design スキル）。
  3. 境界の2ページと代表の5ページで「測り方」の手順どおりに測り、上限を確かめる（T9 でも出荷するビルドで測り直す）。
  4. `DESIGN.md` §3「Zen Antique に無い字を含む見出しは、その和文を丸ごと本文書体で組む」は配り方と別に実装する（Zen Antique に無い字は、切り出しても収められない）。

## スキルへの提案

採った配り方は next/font ではなく、スキルの「サイトで実際に使う字から決める」とも違う（サイト単位ではなくページ単位で切り出す）。`.claude/skills/frontend-design/SKILL.md` の2か所を、次のように直すことを提案する（このタスクでは編集しない）。

1. 「値を変えるときの手順」の **「書体を変えたら、サブセットを作り直す。収録する字種は、サイトで実際に使う字から決める。」** を次に置き換える。
   > **和文の Web フォントは、ページが描く字だけをその場で切り出して配る。** サイト全体の字から作った共有のサブセットや、`unicode-range` で分割された配信ファイル（next/font/google を含む）は使わない——どう分けても、字の少ないページに使わない字を運ぶ。書体を変えたら、切り出しの元になる書体ファイルを差し替え、境界のページで総転送量が変更前を越えないことを測り直す。
2. 「実装の技術」の **「Web フォントは `font-display: swap` と `size-adjust` で、読み込みの前後で行の高さと字面を揃える。」** に、手段を書き足す。
   > **Web フォントは `font-display: swap` と、メトリクスを合わせた代わりの書体の `@font-face`（`size-adjust`・`ascent-override`・`descent-override`・`line-gap-override`）で、読み込みの前後で行の高さと字面を揃える。** 和文はページごとに切り出して読み込むので、next/font の自動の代わりの書体は使えない。代わりの書体の値は自分で計算して置く。
