## 結論

### 配り方

**ページごとのサブセット（速い道）に、全ページ共通の予備（静的な分割ファイル）を書体の並びで重ねる。** 予備を重ねるかどうかは、ページが来訪者との間に持つ約束で分ける。入力欄と、打った語で選ばれる表示は、どのページでも端末のゴシックで組む。

1. **速い道。** ページの字を、ページ固有の家族名でビルドの時に切り出し、静的なファイルで配る。
   - `@font-face` は、ページが描く `<style>` に置く。
   - 書体の変数は、ページ自身の外枠の要素（`data-pf` 属性を持つ、箱のある要素）にだけ当てる。
   - preload は、ページが描く生の HTML に書く。
2. **予備。** 全ページ共通の家族「Yolos JP」（本文 400・700）と「Yolos JP H」（見出し）で、書体の全体をコードポイントの連続した範囲で100字ずつに分けた静的な woff2 である（本文 400・700 が各117ファイル、見出しが78ファイル）。
   - 宣言は全ページ共通の CSS に置く（gzip で 4,564B）。
   - 書体の並びは「欧文 → ページの家族 → 予備 → 欧文の代わり → 端末の書体」とする。ページの家族に無い字だけを、ブラウザが予備から読む（3つのブラウザで確かめた）。
   - 予備を並びに入れるのは、最初のフォントが揃った後である（`load` と `document.fonts.ready` の後に、ルートのレイアウトが `<html data-fb>` を付ける）。最初の描画から入れると、Chromium で最初の描画が遅れる（「差し替えのずれ」）。
3. **閉じたページには予備を重ねない。** 閉じたページとは、**入力欄か設問への回答を持ち、その内容をサーバーに送らないページ**である。ルートのクライアントのコードに入力欄（`input`・`textarea`・`contenteditable`）か診断の設問の部品があれば閉じたページとし、ビルドが決める。入力を評価の API に送るゲーム（`kanji-kanaru`・`yoji-kimeru`）は、ルートの設定で開いたページと宣言する。
   - いまの対象: ツール36本、診断・クイズのプレイ面15本、辞典の一覧3つ（`/dictionary/kanji`・`/yoji`・`/colors`。検索を持つ）、ブログの一覧（`/blog` とそのページ送り・カテゴリ・タグ。検索を持つ。54ページ）、`/storybook`。
   - 閉じたページでは、ページに届くテキスト（HTML とその中の RSC のデータ、ルートの JS チャンク）の字をすべて本文 400 に入れる（「字の集め方」の3）。読み込むファイルの集合はページを開いたときに決まり、入力・回答・操作で変わらない。
4. **入力欄と、打った語で選ばれる表示は、どのページでも「欧文, 端末のゴシック」で組む**（「入力と、入力で選ばれる表示」）。ページの家族も予備も並びに入れない。
5. **データで決まる面は、ビルドの時に「層で配るか、予備に任せるか」を計算して選ぶ。** サーバーが日付で中身を描くページは、日付ごとのサブセットにする（「日替わりのゲームとデータで決まる面」）。

### 字の集め方（役割の決め方）

- **役割は、字を描く要素で決まる。** マークアップはタグと属性で決める。クライアントのコードでは、役割の要素（見出し・太字）の中で描く式を、構文木と型で辿って、描きうる文字列をすべて求める。
- 求めた文字列のうち、そのページに届くものだけをその役割に入れる。**辿れない式が閉じたページにあれば、ビルドを失敗させる。**
- この規則は、中身を最初の HTML に描くか JS で描くかに依らない。そのため、決まった中身を HTML に描き直す条件は置かない。

### 書体

- **本文・UI の和文は BIZ UDGothic の派生**（400・700、`font-display: swap`）。派生で変えるのは、U+2014（EM DASH）に全角の横線の字形（U+2015 と同じ字形）を当てることだけである。`halt` などのレイアウト機能は足さない。
  - 本文は `text-spacing-trim: space-all` とし、約物を全角のまま組む。
- **見出しは Zen Antique** を swap で配る。見出しの書体を当てるすべての要素（クラスで当てているものを含む）で、`palt` を掛けない。
- **欧文は IBM Plex Sans の派生（Yolos Sans）** を `optional` で配る。ロゴは SVG にする。

## 字の集め方と自己回復

### 予備の組み方

静的な試験のページで、BIZ UDGothic のページのサブセット（本文の38字）と予備（100字ずつの分割）を組み合わせた。本文に、サブセットに無い字を3つ（縷・纁・璽）足した（4巡目、`e1run.mjs`、2026-09-24 20:00）。

| 組み方                                                        | Chromium 141                           | Firefox 151    | WebKit 26.5    |
| ------------------------------------------------------------- | -------------------------------------- | -------------- | -------------- |
| 並び「ページの家族, 予備」。ページの面に `unicode-range` なし | ページ＋予備2つ                        | 同左           | 同左           |
| 同じ。本文がサブセットの字だけ                                | ページだけ                             | 同左           | 同左           |
| 同じ家族名。予備を先、ページの面を最後に宣言                  | ページ＋予備2つ                        | 同左           | 同左           |
| 同じ家族名。ページの面を先、予備を後に宣言                    | ページ＋**予備17**（予備が優先される） | ページ＋予備17 | ページ＋予備18 |

- **ページのサブセットにある字は予備を読まず、無い字だけ予備を読む。** 3つのブラウザで同じだった。ページのファイルを 1.5 秒遅らせて返しても、その間に予備を余計に読むことは無かった。
- 同じ家族名に面を重ねるときは、後に宣言した面が先に使われる（CSS Fonts 4 の規定どおり）。採る形は書体の並びで重ねる形（表の1行目）で、順の誤りが起きない。
- ページの面には `unicode-range` を付けない。付けないと予備の要求はページのファイルが届いた後になる（遅い 4G で、付けると 943ms、付けないと 1,201ms）が、当て損ねはまれなので、ページの `<style>` を小さく保つほうを採る。
- 纁（U+7E81）は BIZ UDGothic に無い字で、予備を読んだあとも端末の書体で出る。**書体に無い字は、どの配り方でも揃わない。** サイトの本文の字で BIZ UDGothic に無いのは9字（纁 7ページ、彐 3ページ、絵文字 6字・ZWJ、₂）、見出しの字で Zen Antique に無いのは14字（絵文字・記号）である。見出しは要素ごと本文の書体にする（§3）。本文の9字は揃えない。

### 集め方（ビルドの時、Chromium を使わない）

1. **マークアップ**: 書き出された HTML（リクエストごとに描くページは、ビルドの中で列挙したキーを HTTP で取る）を解析する。役割はタグと属性で決める。入力欄と、`data-input-view` を付けた要素の中の字は集めない。
2. **ルートのクライアントのコード**: ルートが読み込むモジュールを、`"use client"` のファイルとそれが読み込むもの（`import()` を含む）まで辿る。
   1. **役割の要素の中で描く式を辿る。** 役割の要素は、h1〜h6（見出し）、`strong`・`b`・`th` と属性で宣言した要素（太字）である。タグを変数で決める要素（``const Heading = `h${level}` as "h2" | "h3"``）は、型が取りうるタグで役割を決める。その中の JSX の式を、構文木と型で辿って、描きうる文字列をすべて求める。辿るもの:
      - 文字列、テンプレート、条件式と `&&`・`||`・`??` の両辺、定数
      - 部品の props（ルートの中で、その部品を呼ぶすべての JSX で渡した値）と、役割の要素の中に置いた部品に渡す文字列
      - 関数の返り値、`useState` の初期値とセッターに渡すすべての値、`useMemo`・`useSyncExternalStore` の関数
      - 配列の `map` などの要素、`LABELS[key]` のような表の引き当て（表のすべての値）
      - 型の付いたプロパティ（ルートのモジュールの中で、そのプロパティに代入されるすべての文字列）。データのモジュールの、型の付いていないオブジェクト（`satisfies` の無い配列など）のプロパティは、名前で照らす（重い側に倒す）
   2. **届く文字列だけを入れる。** 求めた文字列のうち、そのページの HTML・RSC か、ルートの JS チャンクに現れるものだけを、その役割の層に入れる。共通の部品が別のページのデータを持つとき、それを入れないためである。
   3. **辿れない式**（実行時にだけ決まるデータ、入力の値など）は、閉じたページではビルドを失敗させる。直し方は、式を型の文字列リテラルの合併にする、役割の要素の外に描く、入力を映す表示なら `data-input-view` を付ける、のいずれかである。開いたページでは記録だけする（予備が揃える）。
   4. ルートのクライアントのコード（データのモジュールを除く）の文字列は、すべて本文 400 に入れる。
3. **閉じたページ**は、2に加えて、ページに届くテキスト（HTML とその中の RSC のデータ、ルートの JS チャンク）の字（`\uXXXX` を含む）をすべて本文 400 に入れる。サーバーの部品が文字列を props で渡し、クライアントが操作のあとに描くもの（診断の結果の画面の「毎日更新」など）も、これで入る。
   - チャンクは、HTML の `<script src>` と、そこから参照されるチャンクを再帰的に辿って集める（`next/dynamic` で読み込む部品のチャンクを含む）。T1 ではビルドのマニフェストから同じ集合を取る。
   - **除くのは2種類のデータである。** 除くかどうかは、構文木の上で、そのデータの値を描く式がどこにあるかで決め、ビルドはその文字列をテキストから引いてから字を集める。
     - 入力で選ばれる表示の中でだけ描くデータ（`data-input-view` の要素の中にしか描く式が無いもの）。例: `yoji-search` の `src/data/yoji-data.json`（チャンクの字 1,572字 → 229字）、辞典の一覧の検索の候補（RSC で渡す）。

   - 試作では、診断のプレイ面のチャンクの字を「ルートのコードの文字列＋自分のデータのモジュールの字」で近似した。ブログの一覧の検索の候補（全記事の題と説明。RSC で渡す）は除かずに入れた（重い側。`/blog` の本文の層は 86.7 → 148.7KB）。

- ツールの約束（`src/tools/_components/ToolPageLayout/index.tsx:87`「このツールはブラウザ上で動作します。入力データがサーバーに送信されることはありません。」、`src/app/tools/page.tsx:87`）を、字そのものだけでなく、要求のしかたからも推し量れないように守る。

- 閉じたページを「入力を持ち、送らないページ」とコードから決めるので、入力を持つページが増えても、パスの一覧を直さずに扱いが決まる。

## ビルドの経路

### 分かっていること

- Vercel のプランと機械の種類は、API では確かめられなかった（3巡目）。Hobby は常に Basic（2 vCPU・8GB）、Pro と Enterprise の新しいアカウントは Elastic が既定である（Vercel「Managing Builds」2026-09-17 更新）。
- 3巡目の工程の時間（この機械の 4 vCPU）に、今回の工程を足す:
  - ルートの JS チャンクの字を集める: 1ルート数十 ms。
  - ソースの構文木で役割の要素の式を辿る: 全80ルートで 3.7 秒（型の検査器を作る時間を除く）。
  - 予備の312ファイルを作る: 約 34 秒（1プロセス）。予備は書体のファイルと設定だけで決まり、ページに依らない。書体が変わらない限り、ビルドのキャッシュからそのまま使う。合計 7.9MB。
- ページの `<style>` と preload は `<body>` の中に出る。`<link rel="preload">` は body に置いてよいが、`<style>` を body に置くのは HTML の仕様に適合しない（Chromium・Firefox・WebKit のどれでも効く）。React の `precedence` 付きの `<style>` は `<head>` に上がるが、試していない。
- 見積もったビルド時間は、3巡目の約 8 分（4 vCPU）／約 16 分（2 vCPU）に、予備の初回の 1 分前後を足した程度である。この機械の `next build` は、4,142 ページで約 8 分だった（2026-09-25）。

### 決めたこと

1. **経路は3巡目のまま**、`next build`（1回目）→ 字を集める → 切り出す → `next build`（2回目）とする。
2. **字を集める工程は、「字の集め方」の1〜5で行う。** Chromium は使わない。
3. **閉じたページかどうかは、ルートのクライアントのコードから決める**（入力欄か診断の設問の部品を持つ）。入力を API に送るページは、ルートの設定で開いたページと宣言する。
4. **データで決まる面は、ビルドが層の大きさと予備の見込みを計算して、配り方を選ぶ。**
   - 層の大きさと予備の見込みは、表とともにビルドの記録に残す。
   - サーバーが日付で中身を描くページは、予定表の日付ごとにサブセットを作る。範囲は、予定表のある日付と、ビルドの日から少なくとも60日である。予定表の外の日付（ハッシュで選ぶ日）は予備に任せる。
5. **予備は、書体の版ごとに1回作り、ハッシュの名前で `public/` に置く。** 宣言は全ページ共通の CSS に置く。
6. **失敗したら、ビルドを失敗させる**（3巡目の条件に次を足す）。
   - 閉じたページで、辿れない式が役割の要素の中にある。
   - 閉じたページで、ページに届くテキスト（HTML・RSC・ルートの JS チャンク。「字の集め方」の3で除くデータを除く）の字が、ページの本文のファイルに入っていない。
   - すべての HTML に、そのページの `data-pf` の外枠と `<style>` がある。部品を入れ忘れたページが無いこと。
   - 1回目と2回目の出力の両方に、上の自己点検を掛ける。
   - **変更前に同じ URL があるページで、Web フォントの転送量が変更前を越える**（上限の門）。変更前の値は、T1a の全ページの計算（3,526 ページ）を基線として持つ。
7. **T1〜T7 の条件（書体の役割）**:
   - 見出しと太字の書体は、タグ（h1〜h6、`strong`・`b`・`th`）と属性だけで当てる。
   - 入力欄は全ページ共通の CSS の1規則で端末のゴシックにする。部品の CSS で入力欄の `font-family` を上書きしない。
   - 打った語で選ばれる表示と入力を映す表示には `data-input-view` を付け、その中のリンクは `prefetch={false}` にする。診断の結果の画面のリンクも先読みしない。
   - UI の印（▶ ↗ ‹ › ©）は、字の幅に依らない箱か図形で描く。
   - 文字を描く要素の `line-height` は数値にする（`normal` を残さない）。
   - 字の並ぶフレックスの行（パンくずなど）は、`align-items: baseline` にしない。
   - `data-pf` は、箱を持つページ自身の外枠の要素に付ける（`display: contents` にしない）。
   - 入れ子のレイアウト（遷移しても残る部分）が字を描くときは、ページの外枠の外に置き、その字を上端・下端の家族に集める。
   - `next-route-announcer` の書体は端末のサンセリフにする。
8. **T9 のプレビューは CLI で配る。** 予備の 7.9MB は、ソースのアップロードの上限（Hobby で 100MB）に収まる。

## 測り方

### 転送量（合否の線）

上の「上限と境界のページ」と同じ（Lighthouse 12、モバイルの既定、各5回の中央値。変更後の中央値 − 変更前の中央値 ≤ 幅なら「超えない」。先読みの分を分けて残す）。対象は、代表5ページと境界の7ページ（`keigo-reference`・`word-sense-personality`・`email-validator`・`business-email`・`dictionary/humor/read-receipt`・`kanji-kanaru`・`nakamawake`）である。

- `nakamawake` は、日付ごとのサブセットの大きさの最大の日と、今日の2つで測る。
- `kanji-kanaru` は、端末の日付を3通りに変えて測る。予備を読む量が変わるためである。
- 流れ全体と遷移は、上の10通りに戻る・進むを足して記録する。
- T9 では、出荷するビルドで全ページの見積もりをやり直し、境界の選び方がなお妥当かを確かめる。

### 字が揃うことと、入力が要求に映らないこと（CI）

GitHub Actions の CI で、`npm run build` の後に Chromium で次を行う（Vercel のビルドには入れない）。

- **閉じたページ**（ツールの全36本、診断・クイズのプレイ面の全15本、辞典の一覧3つ、ブログの一覧の各ルートの1ページ）:
  - 読み込み → 代表的な操作 → 落ち着いた後に、次を確かめる。
    - 1つの要素に和文の Web フォントと端末の和文の書体が同居しない。印の付いた子孫の字は、親の要素の字から除いて数える。
    - **入力欄と `data-input-view` の中に、和文の Web フォントが1字も無い。**
    - **操作のあとのフォントの要求が0である。印の中のリンクの先読みが0である。**
  - 操作は、ツールではどのページの層にも無い字を含む和文の入力（例: 「鬱蒼とした森で麒麟を見た。」）と、代表的な正しい入力・誤った入力、結果の表示、「コピー」、タブやボタンである。辞典とブログの一覧では、検索の結果が出る語、出ない語、多く出る1字である。診断では、結果の種類ごとに、その結果になる答え方で開始 → 結果まで通す（結果の画面の見出しと本文を、すべての種類で見る）。
  - 手順はページごとに1つのファイルに書き、ページを足すときに同じ変更で書く。
- **開いたページ**（代表のページ、ゲーム4本、`/play/daily`、辞典の humor）:
  - 落ち着いた後の同居が0であること。ゲームは、端末の日付を当日・翌日・5日後に変えて、1手打つ。
  - 最初の読み込みで予備を読んだ区画の数と大きさを記録する（合否ではなく、上限の門が見る量の内訳）。
- **遷移**: 上の4系統と結果面 → プレイ面で、遷移・戻る・進むの直後と落ち着いた後に、同居0・矩形の移動0。
- **前のページが隠れて残るとき**: 上の手順で、家族が今のページのままで、同居が0であること。
- **書体の役割の静的な検査**: stylelint で、`font-family` と `font-weight` を許した選択子（タグと役割の属性）にしか書けないようにする。`line-height: normal` を禁じる（フレックスのベースライン揃えは、矩形の比較で見つける）。コード全体に掛かるので、代表のページから外れたページも見逃さない。

- 3巡目と同じ（回線を模擬した実測、20回・ブートストラップの95%区間の下限が 1.10 を超えたら原因を調べる。矩形の比較。T9 で WebKit と実機）。
- T9 の実機では、次を見る。
