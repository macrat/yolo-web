## 結論

### 配り方

**ページごとのサブセット（速い道）に、全ページ共通の予備（静的な分割ファイル）を書体の並びで重ねる。** 予備を重ねるかどうかは、ページが来訪者との間に持つ約束で分ける。入力欄と、入力で選ばれる表示・入力を映す表示は、どのページでも端末のゴシックで組む。

1. **速い道。** ページの字を、ページ固有の家族名でビルドの時に切り出し、静的なファイルで配る。
   - `@font-face` は、ページが描く `<style>` に置く。
   - 書体の変数は、ページ自身の外枠の要素（`data-pf` 属性を持つ、箱のある要素）にだけ当てる。
   - preload は、ページが描く生の HTML に書く。
2. **予備。** 全ページ共通の家族「Yolos JP」（本文 400・700）と「Yolos JP H」（見出し）で、書体の全体をコードポイントの連続した範囲で100字ずつに分けた静的な woff2 である（本文 400・700 が各117ファイル、見出しが78ファイル）。
   - 宣言は全ページ共通の CSS に置く（gzip で 4,564B）。
   - 書体の並びは「欧文 → ページの家族 → 予備 → 欧文の代わり → 端末の書体」とする。ページの家族に無い字だけを、ブラウザが予備から読む（3つのブラウザで確かめた）。
   - 予備を並びに入れるのは、最初のフォントが揃った後である（`load` と `document.fonts.ready` の後に、ルートのレイアウトが `<html data-fb>` を付ける）。最初の描画から入れると、Chromium で最初の描画が遅れる（「差し替えのずれ」）。
3. **閉じたページには予備を重ねない。** 閉じたページとは、**入力欄か設問への回答を持ち、入力・回答と、そこから決まる結果を、サーバーに送らないページ**である。ルートのクライアントのコードに入力欄（`input`・`textarea`・`contenteditable`）か診断の設問の部品があれば閉じたページとし、ビルドが決める。入力を評価の API に送るゲーム（`kanji-kanaru`・`yoji-kimeru`）は、ルートの設定で開いたページと宣言する。
   - いまの対象: ツール36本、診断・クイズのプレイ面15本、辞典の一覧3つ（`/dictionary/kanji`・`/yoji`・`/colors`。検索を持つ）、ブログの一覧（`/blog` とそのページ送り・カテゴリ・タグ。検索を持つ。54ページ）、`/storybook`。
   - 閉じたページでは、ページに届くテキスト（HTML とその中の RSC のデータ、ルートの JS チャンク、同じオリジンの API が返すデータの元）の字を、役割ごとの層に入れる（「字の集め方」）。読み込むファイルの集合は、ページの URL で決まり、入力・回答・操作で変わらない。
   - 閉じたページのクライアントのコードが送る要求は、ページの URL が持つ値と定数だけを運ぶ。来訪者が送ることを選ぶ操作（診断の結果の画像の保存・共有、結果のページへの移動）は、その操作のときにだけ送る。
4. **閉じたページの安全網は二重にする。** ビルドは、閉じたページの**すべての JSX のテキストの式を、役割を問わず辿る**。辿れない式（入力の値など）が1つでもあれば、ビルドを失敗させる。CI は、**サイトの和文の家族で組む要素が、端末の和文の書体で字を描いていないこと**を、入力・操作のあとの各状態で調べる（要素がまるごと端末の書体に落ちる型と、1つの要素の中で混ざる型の両方を見つける）。
5. **入力欄と、入力で選ばれる表示・入力を映す表示は、どのページでも「欧文, 端末のゴシック」で組む**（「入力と、入力で選ばれる表示」）。ページの家族も予備も並びに入れない。
6. **データで決まる面は、ビルドの時に「層で配るか、題ごとに切り出すか、予備に任せるか」を計算して選ぶ**（「日替わりのゲームとデータで決まる面」）。

### 字の集め方（役割の決め方）

- **役割は、字を描く要素で決まる。** マークアップはタグと属性で決める。クライアントのコードでは、役割の要素（見出し・太字）の中で描く式を、構文木と型で辿って、描きうる文字列をすべて求める。求めた文字列のうち、そのページに届くものだけをその役割に入れる。
- **太字の役割は、ウェイトで決まる。** 600 以上は 700 の層、500 以下は 400 の層である（ブラウザは 400 と 700 の面から、600 には 700 を、500 には 400 を選ぶ）。T1 では stylelint で `font-weight` を 400 と 700 だけにし、書ける選択子をタグと役割の属性に限る。
- **見出しの役割のテキストに Zen Antique に無い字があれば、その要素を丸ごと本文の書体で組み**、その字を本文の層に入れる（§3）。ビルドが無い字の一覧を作り、部品が要素に印を付け、2回目の出力で付け忘れを検査する（「見出しの字が Zen Antique に無いとき」）。
- この規則は、中身を最初の HTML に描くか JS で描くかに依らない。そのため、決まった中身を HTML に描き直す条件は置かない。

### 書体

- **本文・UI の和文は BIZ UDGothic の派生**（400・700、`font-display: swap`）。派生で変えるのは、U+2014（EM DASH）に全角の横線の字形（U+2015 と同じ字形）を当てることだけである。`halt` などのレイアウト機能は足さない。
  - 本文は `text-spacing-trim: space-all` とし、約物を全角のまま組む。
- **見出しは Zen Antique** を swap で配る。見出しの書体を当てるすべての要素（クラスで当てているものを含む）で、`palt` を掛けない。
- **欧文は IBM Plex Sans の派生（Yolos Sans）** を `optional` で配る。ロゴは SVG にする。

### `DESIGN.md` への変更

- **§3**: 本文・UI の和文を BIZ UDGothic にする。入力欄と、入力で選ばれる表示・入力を映す表示の和文は、端末のゴシックで組む。
- **§4**: 「約物: 連続約物のアキ調整」を「全角のまま組み、連続しても詰めない」に改める。
- 見た目は、代表の4ページと約物の段落で、採る形を変更前と並べて撮り、来訪者の目で比べた（「本文の書体の見た目の比較」）。

### 上限（増分0）

**測った17ページ（代表5ページ、境界のページ7、ほか5）のすべてで満たす。** 変更後から変更前を引いた差は −53.9〜−754.6KiB だった。

- 境界のページは、全 3,526 ページの見積もりで増分が大きい順に選んだ。見積もりで増えるページは0だった。
- 最も差が小さいのは `/tools/keigo-reference` の −53.9KiB である。表を HTML に描き直さずに満たした。HTML の増分は、`<style>` と preload の分（+2.1KiB）だけである。

### 判断

- **案A を採る。** 比べた7案の中で、次の3つを同時に満たしたのは案A だけだった。
  - 落ち着いた後に1つの要素で書体が混ざらない。
  - 入力と答えが要求に映らない。
  - 測ったすべてのページで上限を満たす。
- 案A' は、予備の宣言を全ページの `<style>` に持ち、HTML と RSC で二重に運ぶ。書体の並びで重ねても（案A）同じ自己回復が得られるので、採らない。
- 案A'' は、ツールと診断で出力と結果の区画が要求に映るので、採らない。
- 案B は、JS が描く字と日付で変わる字を集めきれず、混ざる。
- 案C は、上限を越える。そのうえ、読み込みのあいだは字ごとに書体が混ざる。
- 案D は試作していない。日付（日替わり）と入力（ツール・ゲーム）の組は列挙しきれないので、正しさは予測の完全さに依ったままになる。
- 案E は試作していない。JS が描く字（ツールの結果・エラー・ゲームの盤面）がすべて端末の書体になり、「和文を読ませる書体を Web フォントで出す」（§3 の役割）が、サイトの操作の面で失われる。

## 字の集め方と自己回復

### 予備の組み方

静的な試験のページで、BIZ UDGothic のページのサブセット（本文の38字）と予備（100字ずつの分割）を組み合わせた。本文に、サブセットに無い字を3つ（縷・纁・璽）足した（`e1run.mjs`、2026-09-24 20:00）。

| 組み方                                                        | Chromium 141                           | Firefox 151    | WebKit 26.5    |
| ------------------------------------------------------------- | -------------------------------------- | -------------- | -------------- |
| 並び「ページの家族, 予備」。ページの面に `unicode-range` なし | ページ＋予備2つ                        | 同左           | 同左           |
| 同じ。本文がサブセットの字だけ                                | ページだけ                             | 同左           | 同左           |
| 同じ家族名。予備を先、ページの面を最後に宣言                  | ページ＋予備2つ                        | 同左           | 同左           |
| 同じ家族名。ページの面を先、予備を後に宣言                    | ページ＋**予備17**（予備が優先される） | ページ＋予備17 | ページ＋予備18 |

- **ページのサブセットにある字は予備を読まず、無い字だけ予備を読む。** 3つのブラウザで同じだった。ページのファイルを 1.5 秒遅らせて返しても、その間に予備を余計に読むことは無かった。
- 同じ家族名に面を重ねるときは、後に宣言した面が先に使われる（CSS Fonts 4 の規定どおり）。採る形は書体の並びで重ねる形（表の1行目）で、順の誤りが起きない。
- ページの面には `unicode-range` を付けない。付けないと予備の要求はページのファイルが届いた後になる（遅い 4G で、付けると 943ms、付けないと 1,201ms）が、当て損ねはまれなので、ページの `<style>` を小さく保つほうを採る。
- **書体に無い字は、どの配り方でも揃わない。** 纁（U+7E81）は BIZ UDGothic に無い字で、予備を読んだあとも端末の書体で出る。書体に無い字の数え方は「書体に無い字」に書く。

### 予備の分け方

| 1区画の字数 | 区画の数（本文 400／700／見出し） | 区画の大きさの中央値（本文 400／見出し） | 宣言の大きさ（gzip） |
| ----------: | --------------------------------- | ---------------------------------------- | -------------------: |
|     **100** | 117／117／78                      | 23.5KB／34.0KB                           |               4,564B |
|         200 | 59／59／39                        | 43.0KB／66.7KB                           |               2,294B |
|         400 | 30／30／20                        | 83.5KB／128.2KB                          |               1,243B |

- 100字の行は、採る形の派生で作った分割（`shards5.mjs`、2026-09-24 23:13）を数えた。合計 7,883,468B（本文 400 が 2,666,612B、700 が 2,696,528B、見出しが 2,520,328B）。200字・400字の行は、`halt` を持つ前の派生での計算である（字の数は同じ）。
- 区画は、書体の cmap のコードポイントを小さい順に並べ、100字ずつに切った。1区画の `unicode-range` は1区間なので、宣言が小さい。頻度で分けると宣言が大きくなる（BIZ UD の2ウェイトで gzip 60.8KB）。
- **100字を採る。** 宣言は全ページで払う量で、区画は当て損ねたときだけ払う量である。宣言が 4.6KB で済み、区画1つが 23.5KB で済む点を取った。
- 弱点: 漢字はコードポイントの上で散らばるので、当て損ねた漢字が多いと、1字ごとに別の区画を読む。予備は正しさを保つ網で、配る道ではない。**当て損ねを少なく保つことが、上限を守る条件である**（下の集め方と、「測り方」の門）。採る形の最初の読み込みで予備を読んだページは、測った17ページで0だった（Lighthouse のフォントのファイルの数）。

### 集め方（ビルドの時、Chromium を使わない）

1. **マークアップ**: 書き出された HTML（リクエストごとに描くページは、ビルドの中で列挙したキーを HTTP で取る）を解析する。役割はタグと属性で決める。入力欄と、`data-input-view` を付けた要素の中の字は集めない。
2. **ルートのクライアントのコード**: ルートが読み込むモジュールを、`"use client"` のファイルとそれが読み込むもの（`import()` を含む）まで辿る。
   1. **役割の要素の中で描く式を辿る。** 役割の要素は、h1〜h6（見出し）、`strong`・`b`・`th` と、役割の属性を付けた要素（見出し・太字）である。タグを変数で決める要素（``const Heading = `h${level}` as "h2" | "h3"``）は、型が取りうるタグで役割を決める。
   2. **閉じたページでは、役割を問わず、すべての JSX のテキストの式を辿る。** 印（`data-input-view`）の付いた要素の中と、コード（`code`・`pre` と等幅の役割）の中は除く。
   3. 式は、構文木と型で辿って、描きうる文字列をすべて求める。辿るもの:
      - 文字列、テンプレート、条件式と `&&`・`||`・`??` の両辺、定数、即時に呼ぶ関数
      - 部品の props（ルートの中で、その部品を呼ぶすべての JSX で渡した値）と、役割の要素の中に置いた部品に渡す文字列
      - 関数の返り値と、ルートの中の関数の引数（その関数を呼ぶすべての箇所で渡した値）
      - `useState` の初期値とセッターに渡すすべての値、`useMemo`・`useSyncExternalStore` の関数
      - 配列の `map` などの要素、`LABELS[key]` のような表の引き当て（表のすべての値。別のモジュールから読み込んだ表を含む）
      - 型の付いたプロパティ（ルートのモジュールで、そのプロパティに代入されるすべての値。省略記法を含む。代入の値を辿って新しいプロパティが見つかれば、見つからなくなるまで繰り返す）。宣言の型が違っても、そのプロパティの型の必須の名前をすべて持つオブジェクトは同じものとして照らす。データのモジュールの、型の付いていないオブジェクトは、名前で照らす（重い側に倒す）
      - 静的に読み込むデータのモジュール（JSON を含む）の値。チャンクに入って届く

### 当て損ねたときの見え方と転送量

- **落ち着いた後に混ざらない**: 採る形で、CI の検査（「安全網が混ざりを見つけること」）の67の手順を通し、サイトの和文の家族で組む要素が、書体に無い字の外で端末の和文の書体を使ったものは0だった。紹介者のある流れ・ない流れと遷移14通りでも、落ち着いた後に1つの要素の中で混ざったものは0だった（遷移の直後の一時的なものは「遷移」）。

### 理由

- ツールの約束（`src/tools/_components/ToolPageLayout/index.tsx:87`「このツールはブラウザ上で動作します。入力データがサーバーに送信されることはありません。」、`src/app/tools/page.tsx:87`）を、字そのものだけでなく、要求のしかたからも推し量れないように守る。
- 入力欄を端末のゴシックにすると、打った字の中で書体が混ざらない。ページの家族を並びに入れると、ページにある字だけ Web フォントになる（`char-count` のテキストエリアの「吾輩は猫である。名前はまだ無い。」で「名前」だけが BIZ UDGothic になった）。入力欄の字は、どのページでも来訪者が決めるので、層に入れて揃えることはできない。
- 閉じたページを「入力を持ち、送らないページ」とコードから決めるので、入力を持つページが増えても、パスの一覧を直さずに扱いが決まる。

## ビルドの経路

### 分かっていること

- Vercel のプランと機械の種類は、API では確かめられなかった。Hobby は常に Basic（2 vCPU・8GB）、Pro と Enterprise の新しいアカウントは Elastic が既定である（Vercel「Managing Builds」2026-09-17 更新）。
- 工程の時間（この機械の 4 vCPU）:
  - ルートの JS チャンクの字を集める: 1ルート数十 ms。
  - ソースの構文木で式を辿る: 全49ルートで 10.8 秒（型の検査器を作る時間を含む。閉じたルートの JSX のテキストの式 1,008）。
  - 予備の312ファイルを作る: 約 34 秒（1プロセス）。予備は書体のファイルと設定だけで決まり、ページに依らない。書体が変わらない限り、ビルドのキャッシュからそのまま使う。合計 7.9MB。
- ページの `<style>` と preload は `<body>` の中に出る。`<link rel="preload">` は body に置いてよいが、`<style>` を body に置くのは HTML の仕様に適合しない（Chromium・Firefox・WebKit のどれでも効く）。React の `precedence` 付きの `<style>` は `<head>` に上がるが、試していない。
- 見積もったビルド時間は、約 8 分（4 vCPU）／約 16 分（2 vCPU）に、予備の初回の 1 分前後を足した程度である。この機械の `next build` は、4,142 ページで約 8 分だった（2026-09-25）。

### 決めたこと

1. **経路は** `next build`（1回目）→ 字を集める → 切り出す → `next build`（2回目）とする。
2. **字を集める工程は、「字の集め方」の1〜5で行う。** Chromium は使わない。
3. **閉じたページかどうかは、ルートのクライアントのコードから決める**（入力欄か診断の設問の部品を持つ）。入力を API に送るページは、ルートの設定で開いたページと宣言する。
4. **見出しの字の一覧**: 1回目の出力の見出しの役割の字と辞典のデータから、Zen Antique の cmap に無い字の一覧を作り、生成したモジュールに書く（「見出しの字が Zen Antique に無いとき」）。
5. **データで決まる面は、ビルドが層・題ごとのファイル・予備の見込みを計算して、配り方を選ぶ。**
   - 大きさは、表とともにビルドの記録に残す。
   - サーバーが日付で選ぶ題は、候補の全体の層が小さければ層に入れ、大きければ題ごとに切り出す。
   - 同じオリジンの API の応答で描く字は、要求が運ぶ値（紹介者の型など）ごとに切り出す。
6. **予備は、書体の版ごとに1回作り、ハッシュの名前で `public/` に置く。** 宣言は全ページ共通の CSS に置く。
7. **失敗したら、ビルドを失敗させる。**
   - 閉じたページで、JSX のテキストの式に辿れないものがある（役割を問わない）。
   - 閉じたページのクライアントのコードの送信（`fetch`・`sendBeacon`）が、ページの URL の値と定数のほかの値を運ぶ。ただし、来訪者がボタンで送ることを選ぶ操作として宣言したものを除く。
   - 閉じたページで、ページに届くテキスト（HTML・RSC・ルートの JS チャンク。「字の集め方」の3で除くデータを除く）の字が、ページの本文のファイルに入っていない。
   - 見出しの役割の要素のうち、Zen Antique に無い字を含み、本文の書体で組む印の無いものがある。
   - すべての HTML に、そのページの `data-pf` の外枠と `<style>` がある。部品を入れ忘れたページが無いこと。
   - 1回目と2回目の出力の両方に、上の自己点検を掛ける。
   - **基線のあるページで、Web フォントの転送量が基線を越える**（上限の門）。基線は、Web フォントの配り方を変える前のサイトの全ページの計算（3,526 ページ）で、配り方を変えたときだけ更新する。
8. **T1〜T7 の条件（書体の役割）**:
   - 見出しと太字の書体は、タグ（h1〜h6、`strong`・`b`・`th`）と役割の属性だけで当てる。`font-weight` の値は 400 と 700 だけにする（stylelint）。
   - 見出しの役割の要素を描く部品は、テキストに Zen Antique に無い字があれば本文の書体で組む印を付ける（`headingFace`）。
   - 入力欄は全ページ共通の CSS の1規則で端末のゴシックにする。部品の CSS で入力欄の `font-family` を上書きしない。
   - 打った語で選ばれる表示と入力を映す表示には `data-input-view` を付け、その中のリンクは `prefetch={false}` にする。診断の結果の画面のリンクも先読みしない。
   - 相性の API は、紹介者の型だけを受け取り、24の型との相性を返す。クライアントが自分の結果の行を選ぶ。
   - UI の印（▶ ↗ ‹ › ©）は、字の幅に依らない箱か図形で描く。
   - 文字を描く要素の `line-height` は数値にする（`normal` を残さない）。
   - 字の並ぶフレックスの行（パンくずなど）は、`align-items: baseline` にしない。
   - `data-pf` は、箱を持つページ自身の外枠の要素に付ける（`display: contents` にしない）。
   - 入れ子のレイアウト（遷移しても残る部分）が字を描くときは、ページの外枠の外に置き、その字を上端・下端の家族に集める。
   - `next-route-announcer` の書体は端末のサンセリフにする。
9. **T9 のプレビューは CLI で配る。** 予備の 7.9MB は、ソースのアップロードの上限（Hobby で 100MB）に収まる。

## 測り方

### 転送量（合否の線）

上の「上限と境界のページ」と同じ（Lighthouse 12、モバイルの既定、各5回の中央値。変更後の中央値 − 変更前の中央値 ≤ 幅なら「超えない」。先読みの分を分けて残す）。対象は、代表5ページと境界の7ページ（`keigo-reference`・`word-sense-personality`・`email-validator`・`business-email`・`dictionary/humor/read-receipt`・`kanji-kanaru`・`nakamawake`）である。

- `nakamawake` は、題ごとのファイルが最大の題の日と、今日の2つで測る。
- `kanji-kanaru` は、端末の日付を3通りに変えて測る。予備を読む量が変わるためである。
- 流れ全体（紹介者のある流れを含む）と遷移は、上の手順に戻る・進むを足して記録する。
- T9 では、出荷するビルドで全ページの見積もりをやり直し、境界の選び方がなお妥当かを確かめる。

### 字が揃うことと、入力が要求に映らないこと（CI）

GitHub Actions の CI で、`npm run build` の後に Chromium で次を行う（Vercel のビルドには入れない）。

- **閉じたページ**（ツールの全36本、診断・クイズのプレイ面の全15本、辞典の一覧3つ、ブログの一覧の各ルートの1ページ）:
  - 読み込み → 入力（ボタンを押す前）→ ボタン → 落ち着いた後の各状態で、「安全網が混ざりを見つけること」の A〜C を確かめる。
  - 入力は、どのページの層にも無い字を含み、結果の出ない和文（例: 「鬱蒼とした森で麒麟を見た。ｶﾀｶﾅとＡＢＣも。」）と、代表的な正しい入力・誤った入力である。ファイルを入れるツールには、和文の名前のファイルを入れる。辞典とブログの一覧では、検索の結果が出る語、出ない語、多く出る1字である。
  - 診断では、結果の種類ごとに、その結果になる答え方で開始 → 結果まで通す（結果の画面の見出しと本文を、すべての種類で見る）。紹介者のある流れを、紹介者の型ごとに通す。
  - 印の中のリンクの先読みが0であること。
  - 手順はページごとに1つのファイルに書き、ページを足すときに同じ変更で書く。
- **開いたページ**（代表のページ、ゲーム4本、`/play/daily`、辞典の humor、見出しに Zen Antique に無い字を含む辞典のページ（部首の一覧を持つ部首のページ、字の詳細、分類の一覧、伝統色の詳細））:
  - 落ち着いた後に A が成り立つこと。ゲームは、端末の日付を当日・翌日・5日後に変えて、1手打つ。
  - 最初の読み込みで予備を読んだ区画の数と大きさを記録する（合否ではなく、上限の門が見る量の内訳）。
- **遷移**: 上の4系統と結果面 → プレイ面で、遷移・戻る・進むの直後と落ち着いた後に、A が成り立ち、矩形の移動が0。
- **前のページが隠れて残るとき**: 上の手順で、家族が今のページのままで、A が成り立つこと。
- **書体の役割の静的な検査**: stylelint で、`font-family` と `font-weight` を許した選択子（タグと役割の属性）にしか書けないようにし、`font-weight` の値を 400 と 700 に限る。`line-height: normal` を禁じる（フレックスのベースライン揃えは、矩形の比較で見つける）。コード全体に掛かるので、代表のページから外れたページも見逃さない。

### LCP と FCP、差し替えのずれ

- 回線を模擬した実測（20回・ブートストラップの95%区間の下限が 1.10 を超えたら原因を調べる）、矩形の比較、T9 で WebKit と実機。
- T9 の実機では、次を見る。
  - 「——」「▶」、全角でない字（上の表）を含む行
  - Chrome（Android・Windows・Mac）で、連続約物が差し替えの前後で詰まり方を変えないこと（`space-all`）
  - 遅い回線での遷移で、本文がまるごと端末のゴシックから Web フォントに替わる見え方（字の位置は動かない）
  - 辞典とブログの検索の結果、`keigo-reference` の「見つかりません」のメッセージが端末のゴシックで出る見え方
  - 見出しを本文の書体で組む辞典のページ（漢字の詳細 `剝`、部首のページ `疒`）の見え方
