## 作業計画

### 目的

**来訪者が目にするすべての面を、`DESIGN.md` のとおりにする。**

`DESIGN.md` が決めているのは、`docs/site-concept.md` の約束を来訪者の画面で守るための見た目である。

- **サイトには多様なものが並び、入れ替わり続ける**（約束の「たくさん作って、たくさん試します」）。`DESIGN.md` §1 は、UI が色を持てばその色と喧嘩しないコンテンツしか置けなくなると考え、UI を無彩にして色をコンテンツに渡した。いまの UI は朱のアクセントを持っている。
- **来訪者は選別を経たものを探しに来る**（「ここに残っているのは、その結果です」）。だから一覧は1画面に入る項目数と目で追う速さを優先する（§7）。
- **誰もが使えること。** 入力欄にフォーカスすると画面が勝手に拡大する（B-663）。ブラウザで文字を大きくしても本文が追随しない（B-632）。狭い画面で表が1文字ずつ縦に潰れる（B-641）。これらは、いまの面が来訪者に掛けている実害で、`DESIGN.md` §4・§5・§12 が防ぐと定めている。

### 作業内容

進め方は [options.md](./options.md) の比較で **A（全面を1サイクルで、揃ってから1度だけ出荷）** に決めた。同じファイルを書き換える backlog 26件の振り分け（含める18件・含めない8件）も同じファイルにある。

作る順は、**下の層が決まらないと上の層が作れない順**にする。

1. **土台**（T1a・T1）——Web フォントの判断のあとに、トークン・書体・組版・枠。これが決まると、すべてのページの地と字と罫線が決まる。
2. **部品**（T2〜T4）——コントロール・入力・一覧・結果。面は部品の組み合わせなので、部品を先に `DESIGN.md` どおりにする。
3. **面**（T5）——部品で組み直し、ページ固有の CSS から `DESIGN.md` に無い値を消す。
4. **外と文章**（T6・T7）。
5. **確かめる**（T8・T9）。**出荷**の直前に基線を取り（T10）、出荷して本番で確かめる（T12）。

**作業の分け方**

- サブエージェント1体に渡すのは、**部品1つ、または面1つ**（ツールなら1本、診断なら1本）。数十の面を1体に丸ごと渡さない。
- **同じファイルを触る作業は直列にする。** `globals.css`・layout・共有部品は1体ずつ順に。面の作業は、部品が揃ってから並行させる。
- 部品1つ・面1つごとにレビューを受けてから、完了とする。

**作業中に守ること**

- **トークンの別名で旧値を新値に付け替えて済ませない**（AP-P28）。朱で示していた操作は、§6 の下線・反転・形で示し直す。
- **`DESIGN.md` を実装に合わせて書き換えない。** 変えてよいのは、その規定が来訪者にとって誤りだと示せたときだけで、判断と根拠をこのディレクトリの文書に残してレビューを通してから変える（[options.md](./options.md)「`DESIGN.md` を変えるとき」）。

### 完了の条件

**主な条件は、全ページが `DESIGN.md` の §1〜§12 を満たすことである。** 以下はそれを確かめる手段と、この作業に含めた項目が解消したことを来訪者の側で確かめる項目である。

**「全ページ」の範囲**: `src/app` の80ルートと、404・410。

- **機械の検査は、sitemap の全 URL と、sitemap に載らないページ（404・410・storybook・noindex の結果ページ）、それに操作で現れる状態（診断の設問の画面・回答後の結果・ダイアログなど、面の種類ごと）に掛ける。** 検査は安いので、見本の抽出にしない。
- **目視と操作は、テンプレートごとに実際のページを選んで確かめる。** 選び方は、中身の種類（色が主題・字形が主題・数字が結果・文章が結果・表を含む・コードを含む・図を含む）ごとに少なくとも1枚。そのうえで**境界の値**を必ず含める——ほぼ白・ほぼ黒の色、最も長い名前、最も多い件数、項目0件、**見出し書体に無い字を含む見出し**（漢字辞典の「𠮟」。[facts-design-gap.md](./facts-design-gap.md) §12-2）。

**機械で確かめる**

- `src/` で **UI のトークンとして定義する** CSS 変数は、`DESIGN.md` に名のあるもの（§2 の6色・§5 の `--rule-w`・`--rule-w-hair`・`--max-width`・`--measure`）と、§3 の4書体の役割を表す書体の変数だけ。中身の色を渡すための変数（ビルド時にコードの色分けが生成するものや、中身の色をインラインで渡すもの）はトークンではないので、この条件の範囲の外にある（§12「コンテンツの色はトークンを持たない」）
- `border-radius` の宣言はラジオボタンの円だけ。影・グラデーション・半透明ぼかしは、中身の色（§2）を除いて0件
- `frontend-design` スキルの「機械で確かめる」6項目（コントラスト・320px 幅・文字サイズ 200%・色の直書き・タップターゲット・Web フォントでのずれ）を満たす
- 行間・字間の上書き（§12・WCAG 1.4.12 の値）で内容が欠けない
- 入力欄が、何を書く欄かを `autocomplete` などで機械に伝えている（§12 自動入力。個人の情報を書く欄が無ければ、その確認の記録）
- このサイクルで書き換えたファイルに、`DESIGN.md` に無い節番号（`§8-1` など）の参照が0件（B-672 のうちこのサイクルで扱う分）
- `npm run typecheck && npm run lint && npm run format:check && npm run test && npm run build` が通る

**来訪者の目と操作で確かめる**

- 面の種類ごとに、ライト/ダーク × モバイル/PC の4枚で、`frontend-design` スキルの「目で確かめる」の各項目を満たす
- キーボードだけで全機能に到達でき、フォーカスが常に見え、隠れない（§12）
- 同じ働きの部品が、どのページでも同じ位置・同じ形にある（§12 位置の一定）。hover やフォーカスで現れたものは、消さずに読めて、消せる（§12 一時表示）
- 一度入力させたものを、同じ流れの中で二度入力させない（§12 入力の節約）。画面の向きを固定せず、操作に必要な入力手段を1つに限らない——タッチ・マウス・キーボードのどれでも全機能を使える（§12 向きと入力手段）
- 一覧で、名前と種別で絞り込め、並び順が見えて変えられ、件数が見え、ページを送れ、どのページからも一覧へ戻れる（§7）
- 結果が、それを生んだ操作の直後に出る（§8）。`prefers-reduced-motion` のとき結果の登場は即時表示になる（§11）
- **色・字形・図が中身の面で、来訪者が得ていた情報が変更後も同じだけ得られる。** ゲームは実際に1局ずつ遊び、判定（正解・近い・違う）を色を使わずに読み分けられることを確かめる
- **PV の78%が集まる `/play/character-personality`** を、変更前と変更後で並べて、来訪者の目で比べる。見るのは、プレイ面の開始ボタンがモバイルのファーストビューに入るか、回答中に選択肢がすべて見えるか、回答した選択肢が即座に選択状態として見えるか、結果を受け取ったときに楽しいか、保存やシェアをしたくなる形か。変更後が劣るなら、`DESIGN.md` の規定が来訪者にとって誤りでないかを判断する（[options.md](./options.md)「`DESIGN.md` を変えるとき」）
- **表示の速さ**: 代表の5ページ（`/play/character-personality` のプレイ面と結果面、ツール1本、辞典の詳細1件、ブログ記事1本。変更前の値は [facts-speed-before.md](./facts-speed-before.md)）と、境界のページで確かめる。**境界のページ**は、変更前と変更後で同じ中身を描くページ（比べる相手が同じであるため。ページ送りが入る一覧や、文言・画像が変わるページは除く）のうち、**変更後と変更前の総転送量の差（増分）が最も大きくなると見込まれるページ**で、リクエストごとに描くページも含む全ページから T1a で選ぶ（代表のページと重なれば加えない。本文と見出しで増分の出方が違い、1ページで最悪の場合を代表できないなら複数を選ぶ）。T9 では、出荷するビルドで境界の選び方がなお妥当かを確かめ、外れていれば選び直して測る。変更前と変更後は、出荷前に同じ環境で測る。測り方（回数・統計の扱い・計測の設定）は T1a と T9 の作業で決め、そのレビューで確かめる。
  - **転送量（合否の線）**: 対象のページのそれぞれで、**変更後の総転送量が変更前を超えない**（増分0。計測の揺れの範囲の差は超えないとみなす）。**この上限は、新しい書体の転送量を見積もる前に、この計画で決める。** 根拠は来訪者の側にある——83.7% のセッションは1ページで終わり、そのページで払った転送量は次のページで取り返せない。Lighthouse のモバイルの既定の回線（1,638.4Kbps。約 200KiB/秒）では、100KiB の増分は約0.5秒の読み込みにあたる。刷新の得（見た目・読みやすさ）を、来訪者の時間で買わない。
    **越えたときの帰結**: Web フォントが原因なら、配り方を変えても越えるとき、本文・UI の和文（BIZ UDPGothic）を端末のゴシックに改めて、[options.md](./options.md)「`DESIGN.md` を変えるとき」の手順で §3 を書き換える（§1 は本文の仕事を読みやすさとし、個性は罫線・見出し・コントロールが担うと定めているので、最初に外すのは本文の Web フォントである）。それでも越えるなら、転送量の大きい書体から順に端末の書体に改める。見出しの書体を改めると §1 の「巨大なアンティーク体の見出し」が失われるので、その場合は失う得を記録する。端末の書体に改めるときは、改めた画面を見て組み方を決め、失う得を記録する。この見比べは上限を覆す材料にしない。フォント以外（CSS・JS・画像）が原因なら、この作業の中で減らしてから出荷する
  - **LCP（調査の引き金）**: 合否ではなく、原因を調べる引き金にする。変更前の5回のあいだの幅は 722〜1,980ms あり、少ない回数では差を見分けられないので、揺れを越えて**変更前より 10% を超えて悪化したと言えるなら**原因を調べる。Web フォントが原因なら T1a に差し戻す。それ以外が原因なら、この作業の中で直してから出荷する。直さずに出すなら、その理由を記録してレビューを受ける。Web フォントが LCP に出るかどうかは仮説で、この計測で確かめる
  - **2.5 秒について**: web.dev が「良好」とする 2.5 秒は、実地の計測の75パーセンタイルに掛ける値である（[facts-external-specs.md](./facts-external-specs.md) §8）。実験室では変更前の5ページすべてがすでに超えているので、このサイクルの合否には使わない。変更前から遅いこと自体は B-758 として起票した。Search Console の Core Web Vitals レポートの実地の値は、上限を緩める材料にはせず、T10 で基線と一緒に記録して B-758 に渡す

### 検討した他の選択肢と判断理由

[options.md](./options.md) に6案の比較がある。要点は次のとおり。

- **B（土台と部品を先に出荷）** は、ページ本体の組み方（§5 のページの割り方とコンテナ）を後に回すため、§1 の仕掛けと罫線が作る形がページに出ない。
- **C（面の種類ごとに出荷）** は、1ページで終わるセッションが83.7%なので、面をまたいで混ざる害は小さい。しかし共有の枠と部品が全ページ共通のため、コードに2つのデザインを同居させるか、ページの中で2つのデザインを混ぜるかのどちらかになる。
- **D（統合ブランチで複数サイクル）** と **F（フラグで切り替え）** は、来訪者が見るものが A と同じで、作業中に他の修正を出荷できる。しかし D は旧と新の両方に同じ修正をすることになり、F は main のすべての部品が複数サイクルにわたって2つの見た目を抱える。
- **E（引き上げの判定を先に）** の利点は、引き上げる面にかける手間を省けることだけである。手間は判断の基準にならない。その間、残る面の来訪者に旧デザインを見せ続けることになる。

**A の代償**——このサイクルのあいだ他の修正を出荷できない（PV の78%が集まる面で回答中に選択肢が画面に入らない欠陥 B-614 は、同じファイルを書き換えるので含めた。B-620 は前回の修正が来訪者に正味でマイナスだったため含めず、B-614 のあとで改めて見る）、出荷が全部か無しかになる、PV の78%が集まる面が1度で大きく変わる、和文の Web フォントが増える——は [options.md](./options.md) に書いた。Web フォントは T1a で判断し、ほかは完了の条件で確かめる。
