## そのほかに確かめたこと

- **幅と文字サイズ 200%**: 320・375・1280px と 200% の 320・375・1280px で、12ページすべての `scrollWidth` が画面幅と同じ。`main` の中で `scrollWidth` が `clientWidth` を超える要素は無い。

- **§6 の 44px**: 押せるもののうち 44px に届かないのは、見えないラジオボタンの `input`（1×1。押せる範囲はラベルを含む行）だけ。
- **ライト／ダーク**: UI に色は出ず、角丸・影も無く、全幅の罫線がコンテナの左右のボーダーを貫いている。色が出るのは伝統色の色見本だけで、細い線で囲まれている。`/dictionary` の収録数は `--ink-2` の補助情報の大きさで出る。

## PM の判断への意見

- **伝統色を仮名の読みで探せるようにせず、ラベルを「色名・ローマ字・カラーコードで探す」にしたこと**: 妥当。ローマ字から機械で作った仮名が約20色で誤れば、正しい読みで打った人ほどその色だけ見つけられない。ラベルが実際に探せるものを言うので、来訪者は空振りしたときに打ち方を替えられる。人が確かめた読みをデータに持たせる B-763 の方向もよい。
- **/tools の文を「登録不要。入力は手元で処理。」にしたこと**: 妥当。事実と合い、320px で1行に収まる。「手元」は、端末の中で処理するという意味で広く通じる。
- **「部首（198）」を §4 の例外として受け入れたこと**: 同意しない。Minor-1 に書く。

## 指摘

### Minor-1: 「部首（198）」の折り方は、§4 の例外の条件に当たらず、語を割るほうが読みにくい

**どこで何が起きているか**: 文字サイズ 200% の 320px で、漢字の索引の見出しが「部／首（198）」と折れる。`IndexName` が数を名前の最後の字と折れないまとまりにし（`.joined`）、語の中だけに折れる所を残すためである。コードのコメントも PM の判断も「1語が幅に収まらないときの §4 の例外」としている。

しかし §4 の例外は「一語がコンテンツ幅に収まらないときだけ、語中で折る」で、「部首」の1語（約 95px）はコンテンツ幅（266px）に収まる。収まらないのは語と数を合わせた幅である。このとき §4 の「語の途中で折らない」と「括弧の前後で折らない」のどちらかを破るしかなく、DESIGN.md はどちらを先に守るかを書いていない。いまの実装は、書かれていない優先を選び、それを §4 に沿うと言っている。

**来訪者にどう効くか**: 見出しの字は 47.68px で、「部」が1字だけの行に立ち、次の行が「首（198）」になる。来訪者は「部」と「首」を別々の字として読み、索引の名前がすぐに伝わらない。前回の指摘の心配（数がどの見出しのものか分かりにくい）も、「首（198）」が「1画」のすぐ上に来るので解けていない。日本語の組版では始め括弧は行頭に置いてよい（行頭で禁じられるのは終わり括弧のほう）ので、「部首／（198）」なら語は読めたまま、数が語のすぐ下に来る。影響は文字サイズを大きくした狭い画面に限られるが、文字を大きくして読む来訪者のための画面である。

**直し方**: 語と数が1行に収まらないときは、語を割らずに括弧の前で折る（数の前にだけ `<wbr>` を置き、名前の語は `keep-all` のまま）。どちらを選ぶにしても、DESIGN.md §4 に「語に添えた数が語と1行に収まらないとき、どこで折るか」を書き、コードのコメントをそれに合わせる。

### Minor-2: `/dictionary` の導入の文が、伝統色とユーモア辞典に無い「由来」「意味」を約束している

`/dictionary` の見出しの下の文は「気になる言葉や色を引いて、読み方や意味、由来を確かめてください。」のまま。

- 伝統色は仮名の読みも由来も持たない。前回、同じページの伝統色の行から「由来つき」を外したのと同じ食い違いが、行のすぐ上の文に残っている。
- ユーモア辞典は、自分の導入の文で「本当の意味ではありません」と言う。

このコミットは、行の説明を「一覧と字のページにあるもの」に合わせたが、同じページの導入の文を見直していない。来訪者は伝統色を開いて由来を探し、見つけられない。

**直し方**: 4つに当てはまることだけを言う文にする（例「気になる言葉や色を引いて、読み方や意味、色見本を確かめてください。」のように、何がどの辞典にあるかを混ぜない言い方）。375×667 で最初の行が画面に入ること（いまの下端 588）を測って確かめる。

### Minor-3: 伝統色のトップの導入の文が、すぐ下のラベルを繰り返し、ページが何かを言わない

導入の文「色名のローマ字とカラーコードを引けます。」のすぐ下（アコーディオンと件数の行を挟んだ先）に、名前の欄のラベル「色名・ローマ字・カラーコードで探す」がある（同じ3語が1画面の中で2度続く）。設計（t3-design.md 3-1）は「導入の文は、件数の行とアコーディオンが言うことを繰り返さない」とし、ほかの辞典の導入の文は、字のページで何が分かるか（「読み方・部首・画数・熟語・英語の意味」「読み方・意味・由来と例文」）を言っている。伝統色だけ、色のページにある RGB・HSL や、色見本を並べて見比べられることを言わず、欄の使い方を繰り返している。さらにこの文のために、375px で導入の文が2行になり、最初の行の余りが 16px に減った。

**直し方**: 字のページと一覧が見せるものを言う文にする（例「色見本とカラーコードを並べています。色のページでは RGB と HSL も確かめられます。」）。375×667 で最初の行が画面に入ることを測って確かめる。

### Minor-4: /play とユーモア辞典の metadata の説明が、一覧の中身と合っていない

- `/play` の metadata の説明（`PLAY_LIST_DESCRIPTION`）は「占い・診断・クイズ・パズルなど」のまま。導入の文は種別の語に合わせて「運勢」に直したが、検索結果と SNS のカードに出る文だけ「占い」が残る。「占い」で探す人に届けたいのなら、それは判断として残してよいが、そのときは種別の語と並べる形（例「運勢（占い）・診断・クイズ・パズル」）にして、来訪者が一覧で「占い」の組を探さないようにする。
- `/dictionary/humor` の metadata の説明（`src/humor-dict/meta.ts`）は「日常のあらゆる言葉をユーモラスに再定義した辞典。クスッと笑える新解釈で、言葉の別の側面を楽しもう。」。収録は30語で「あらゆる言葉」は事実より大きく（§9「具体」）、「楽しもう」の呼びかけもほかの一覧の説明の文体と違う。導入の文と `/dictionary` の行は正直な言い方になっているので、検索から着いた人だけが大きな約束を読んでから30語の一覧を見ることになる。

**直し方**: 2つの説明を、一覧が並べるものと数に合わせる（例「身近な言葉30語を、AIがまじめな顔で定義し直したユーモア辞典。本当の意味ではありません。」）。

### Minor-5: `ListPage` の `trail` の説明が、ブログのトップだけパンくずを持たない理由を事実と違う形で言う

`ListPage` の `trail` の説明は「サイトの上端のナビから直に着く一覧（ブログのトップ）は持たない」。しかし `/tools`・`/play`・`/dictionary` も上端のナビから直に着く一覧で、どれもパンくずを持つ。さらに t3-design.md の T3-10 と index.md の補足の決定は、`/blog` にパンくずを足すことを決めている。

この説明を読んだ次の builder は「上端のナビから着く一覧はパンくずを持たない」という規則があると受け取り、ほかの一覧からパンくずを外しかねない。§12「位置の一定」に反する方向へ誘う説明になっている。`trail` を省けるのが1つの一覧のためだけにある形（AP-I02）でもある。

**直し方**: 説明を事実だけにする（例「パンくず。」）。T3-10 で `/blog` にパンくずを足したら、`trail` を必須にし、ListPage のテストの「パンくずを持たない」形も外す。

### Minor-6: `/dictionary` の件数の行と一覧のあいだの 24px が、`BrowsableList` の値の写しとして残る

`src/app/dictionary/page.module.css` の `.list` は「ほかの一覧のページと同じく 24px あける」と書き、`BrowsableList.module.css` の `.browsable` と同じ `gap: var(--space-24)` を持つ。今回 `ListPage` にまとめたのは、1か所の値を替えたときにほかの一覧が取り残されないためで（§12 位置の一定）、件数の行と一覧の積み方だけが写しのまま残った。`BrowsableList` の間隔を替えると、`/dictionary` だけ件数の行と一覧の距離がずれる。

**直し方**: 件数の行と一覧を積む形を1か所にする（例: `/dictionary` が `BrowsableList` と同じ積み方の部品を使う、または件数の行と一覧を積む小さな部品を切り出して両方が使う）。

### Minor-7: seo.test.ts に cycle の経緯のコメントが15か所残り、バックログにも無い

前回のレビューは、seo.ts と seo.test.ts の両方の経緯のコメントを挙げた。今回 seo.ts は直ったが、`src/lib/__tests__/seo.test.ts` には「cycle-277 決定(a)」「cycle-251: …」などが15か所残る（テストの名前の中にも「(cycle-277 決定(a))」がある）。バックログにも積まれていない。CLAUDE.md の規則ではその場で直す対象で、T3-6・T3-8 がこのファイルを触っている。

seo.ts にも、四字熟語の説明の長さの「全 400 件で実測（…をループして算出）: base+AI で最大 90 字…」という、データが替われば古くなる実測の記録が残る。上限の値を持つ理由（説明が長くなりすぎないため）だけを書けば足りる。

**直し方**: seo.test.ts のコメントとテストの名前から経緯を外し、理由だけにする。seo.ts の実測の記録を理由に書き替える。この直しで量が大きいと判断するなら、バックログに積む。

### Minor-8: 索引の名前の語の切れ目を `Intl.Segmenter` に任せ、「色み」を2語に割る

`IndexName` は語の切れ目を `Intl.Segmenter("ja", { granularity: "word" })` で求める。Node の結果では「色みから探す」が「色／み／から／探す」に分かれ、「色」と「み」のあいだにも `<wbr>` が入る。今回測った幅では「色みから／探す（7）」と折れて害は出ていないが、もう少し狭いと「色／み」で割れうる。辞書による分かち書きは実行環境の ICU の版で変わることもある。

同じコミットの `ListPage` は、見出しの意味の切れ目を呼び出し側が明示する（`headingPhrases`）。§4 の同じ規則を、見出しでは明示の区切り、索引では自動の分かち書きという2つの仕組みで組んでいる。
