## Major

### Major-1: 途中まで遊んだ来訪者が開き直すと、多くの回で CLS が 0.1 を超える

3回推測したあとに開き直すのを幅ごとに繰り返した（1回ごとに新しいタブで開き、1.2 秒待って測った）。

| 幅       | CLS（回ごと）                                                                                                         |
| -------- | --------------------------------------------------------------------------------------------------------------------- |
| 320×667  | 0.1171・0.1171・0.1171・0.1171・0.1171・0.1138・0.1138・0.0329（8回のうち7回で 0.1 超え。別の5回も 0.1138×4・0.0329） |
| 375×667  | 0.0419・0.1367・0.1396・0.1367・0.1367（5回のうち4回で 0.1 超え。別の4回はどれも 0.0419）                             |
| 1280×800 | 0.0487・0.0067×4。4回目で勝った回を開き直したときも 0.0452 の回があった                                               |

原因は2つある。

1. **行の高さを取っておくスクリプトが、最初の描画より後に動く回が多い。** 盤の直後のスクリプトが `--board-rows: 4; --hint-lines: 3` を書き込んだ時刻と、最初の描画の時刻を並べると、0.1 を超えた回はどれも描画が先だった（例: 描画 288ms・書き込み 421ms、描画 380ms・書き込み 386ms）。0.0329 だった回だけ、書き込み 77ms・描画 404ms で順が逆だった。描画が先の回では、盤が1行ぶん（64px）の高さで一度描かれ、記録を戻したときに 183px（320px）へ伸び、入力欄・くわしい遊び方・難易度の組が下へ押される（320px で 0.0808〜0.0843、375px で 0.0948〜0.0977）。スクリプトは要素の**後ろ**にあるので、ブラウザが要素まで読んだところで描くと、取っておく前の高さが画面に出る。
2. **高さを取っておけた回でも、盤の空の行とヒントの帯の最後の行が動く。** サーバーの HTML の空の1行は、記録の3行が前に入ると4行目の位置へ下がり、「3回目のあとに読みの最初の字」の行も、その上に「読みの最初の字 れ」が入って1行下がる。高さが変わらなくても要素の位置が変わるので数えられ、320px で 0.0328、375px で 0.0418、1280px で 0.0067 になる。

来訪者にとっては、毎日遊ぶ人が朝に途中まで遊び、昼に続きを開いたとき、盤の下の入力欄に指を伸ばしたところで入力欄が 100px 以上下へ跳ぶ。設計の条件（「3回推測したあとに開き直した来訪者で 0.1 以下」）を、来訪者の多い 320・375 の幅で、ほとんどの回で満たしていない。

直し方の向き: 取っておく値を、盤より**前**で決まるようにする（盤より前に置いたスクリプトが `document.documentElement` などに値を書き、CSS がそれを読む。パーサーはスクリプトを動かしてから後ろを読むので、取っておく前の盤は描かれない）。あわせて、空の行とヒントの最後の行を、取っておいた行の数から決まる最終の位置に最初から置く（例: 空の行を `grid-row` で最後の段に置く、次に出るヒントの行の上に取っておいた行ぶんの余白を置く）。直したら、上の表と同じく幅ごとに複数回開き直して、どの回も 0.1 以下（できれば初めての来訪者と同じく 0 に近い値）であることを記録する。1回だけの計測では、今回のように回ごとの差を取りこぼす。

## Minor

### Minor-1: 送っているあいだ送信のボタンが「送信中...」に広がり、入力欄が縮んで戻る

送信のボタンは「送信」50px と「送信中...」81px で幅が変わり、`flex: 1` の入力欄が推測のたびに 31px 縮んで戻る。判定を 1 秒遅らせたときの CLS（375: 0.0021・320: 0.0024・1280: 0.0003）は、全部がこのボタンのずれ（判定が返ってボタンが縮む所）で、行を先に置いた直しで盤の側のずれは消えている。来訪者には、送るたびに欄の右端とボタンがぴくりと動いて見える。また「...」は §4 の三点リーダ（「……」）でない。ボタンの場所を広いほうの字で取っておくか（§6 のコピーのボタンの「面の字が替わっても動かない」と同じ考え方）、面の字を変えずに無効の見た目と読み上げで待っていることを伝える。

### Minor-2: 結果の成績の表で、200% の 320px では数と単位が別の行に割れる

320px・200% で、成績の表の値の列が狭くなり、「1／回」「0／日」と数と単位が2行に分かれる（`th` の列が幅を取り、`td` が1字ぶんしか残らない）。DESIGN.md §8「数字を折るのは桁区切りの位置だけで、単位は数字から離さない」に反する。文字を大きくして読む来訪者が、自分の成績を読み取りにくい。値のセルを `white-space: nowrap` にするなど、値の列が数と単位の幅を必ず持つようにする。

### Minor-3: registry.ts の新しい説明の「!」のあとに空きが無い

書き直した `seo.description` は「6回以内に正解を見つけよう!4文字の漢字を入力すると、…」で、半角の「!」の直後に字が続く。検索の結果の説明文として読むと、「!4」が1語のように詰まって見える。§4 は感嘆符のあとを全角アキにすると決めている。書き直した行なので、ここで「！」のあと全角アキ（または「。」）にする。`ogDescription` の末尾の「!」も全角にそろえる。

なお、説明の中身は盤と合っている（1字ずつ ◯・△・× が付き、語は凡例と同じ）。102字で、狭い画面の検索結果では「◯（正しい位置）」のあたりで切れうるが、切れても前半で何のゲームかは伝わる。

### Minor-4: FAQ の「漢字カナールとの違いは？」の答えだけ「フィードバック」のまま

3つ目の FAQ は「字の下に付く◯・△・×の印を手がかりに」と印の語に直したが、2つ目の答えは「各文字ごとにフィードバックが表示されます」のまま残っている。同じページの FAQ で、同じものを「印」と「フィードバック」の2つの語で呼ぶことになり、「フィードバック」が何を指すかは読む人には分からない。「1字ずつ◯・△・×の印が付きます」のように、同じ語にそろえる。

### Minor-5: HintBar.tsx の部品の説明が、別の関数の上に置かれている

`HintBar.tsx` では「ヒントの帯。難易度と読みの字数は初めから出し、…」の JSDoc のすぐ下に `hintLineCount` の JSDoc と関数が続き、`HintBar` 本体には説明が付いていない。あとから `hintLineCount` を差し込んだ跡がそのまま残っており、読む人はこの説明を `hintLineCount` のものと取り違える（CLAUDE.md のツギハギ禁止）。説明を `HintBar` の直前に移す。
