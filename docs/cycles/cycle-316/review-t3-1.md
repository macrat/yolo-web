## 指摘

### Major-1: 全件で同じ種別を行に出している（§7）

§7 は「その一覧が並べる全件で同じになる種別は、行に出さない」と定めている。`RelatedArticles` は、分類をいつも `kind` に渡している。`getRelatedPosts` は同じ分類に大きな点を与えるので、3件がそろって同じ分類になることが多い。`getRelatedPosts` を全86記事に掛けて数えると、**81記事で3件すべてが同じ分類**だった。例えば `/blog/character-counting-guide` では、3行すべてに「ツールガイド」が出る。この語は項目を見分ける手がかりにならず、行を長くするだけである。

storybook の見本「読みを持ち、説明を持たない行」も、3行すべてが「小学1年」で、規則に反する形を見本として示している。

直し方の方向: この規則は一覧ごとの判断ではなく §7 の一般の規則で、T3-2a・T3-2b の一覧にも同じように当たる。`ItemList` の中で「全件の `kind` が同じなら出さない」とするのがよい。テストを足し、storybook の見本も規則に沿う形にする。

### Major-2: Safari と VoiceOver では一覧として読まれない

`.list { list-style: none }` の `ul`/`ol` は、Safari では list のロールを失う。VoiceOver（macOS・iOS）は「一覧、3項目」を言わず、一覧の名前（`aria-labelledby`）も読まない。WebKit はこれを意図した挙動としていて、2026年でも続いている（[Scott O'Hara](https://www.scottohara.me/blog/2019/01/12/lists-and-safari.html)、[Matuzovic](https://www.matuzo.at/blog/2023/removing-list-styles-without-affecting-semantics)、[modelrails_ui #190](https://github.com/dschmura/modelrails_ui/issues/190)）。例外は `nav` の子孫だけで、`ItemList` はどの面でも `nav` の中にない。

t3-design.md 6章は、B-599 の結果として「読み上げでリストとして扱われ、件数が伝わるようになります」と約束している。T3-1 は、この約束を部品1つで守るための土台である。しかし iOS の Safari では、それが成り立たない。jsdom のテストでは検出できない型の問題でもある（AP-I07）。

直し方の方向: `ItemList` の `ul`/`ol` に `role="list"` を明示する。テストでは、その属性があることを確かめる。T3-3 の `LinkIndex` も同じ組み方になるので、あわせて知らせておく。

### Major-3: ボックスを持たない形で、端の行の hover の線が閉じない（§6）

`boxed={false}` の形（storybook「ボックスを持たない形（Panel の中）」）では、`Panel` が上下に余白（8px、広い画面で 16px）を持つ。そのため最初の行の上にも最後の行の下にも、線が無い。hover すると左右の細い線だけが出て、上が開いた形になる（撮影で確かめた）。§6 は「一覧の行では左右に細いボーダーが現れて閉じ、上下は行の区切りがそのまま辺になる」と定めていて、これに反する。

§7 の書き足しは「ボックス」の場合しか決めていない。結果のボックスや `Panel` の中に置く形（t3-design.md 1-1）で、端の行の上下の辺が何になるかは、`DESIGN.md` のどこにも書かれていない。この形は T3-1 の成果物（「ボックスを持たない形」）で、T3-2a・T4 の結果のボックスで使われる。

直し方の方向: 次の2つのどちらかにして、§7（か §8）の文面と実装を合わせる。

- ボックスを持たない形では、最初の行の上と最後の行の下に細い罫線を引く。
- 置き場所のボックスが、一覧に接する辺では余白を持たないと決める。

storybook の見本も、決めた形で示す。

### Major-4: 見出しの大きさ `1.375rem` が §4 の段に無い（AP-I08）

この変更で新しく書いた `src/app/page.module.css` の `.shelfHeading` と、新設の `src/blog/_components/RelatedArticles.module.css` の `.heading` は、`font-size: 1.375rem` を持つ。§4 の見出しは5段（1.0625 / 1.49 / 2.08 / 2.92 / 4.08rem）で、画面幅ごとに段が下がる。`1.375rem` はどれでもない。index.md 補足事項の「`DESIGN.md` に無い値を部品が持ち込まない」にも反する。値は `Shinagaki` から写したものだが、`Shinagaki` を消す作業で同じ値を2か所に増やしている。

直し方の方向: 上書きを消して見出しの既定（`h2` の段）に従わせるか、§4 のトークン（例 `--text-heading-sub`）を使う。どの段にするかは、その一覧がセクションの頭の見出しか、セクションの中の小見出しかで決める（§5）。

### Minor-1: 関連記事の説明が長く、狭い画面で3件が約1.7画面を占める

関連記事の説明は記事の `description`（100〜150字程度）で、375px では1行が 342〜405px になる。3件で約 1,150px ある。320px では1行が 493〜556px になる。§7 は説明を「何ができるか・何であるかを短く言う」と定めている。題名と公開日だけだった前と比べて、記事の下端から次の行動までが遠くなった。3-2 で説明を足すと決めた理由（開く前に中身が分かる）は妥当である。そのうえで、T5 でページの自前の余白を外したあとの高さを測り、長すぎるなら短い説明の持ち方を決めてほしい。字を切り詰める（`line-clamp`）のは §4「高さを固定した領域を持たない」に反するので、取らない。T3-2a の `RelatedBlogPosts` も同じデータを使う。

### Minor-2: 見出しで名前を付けた `section` が region のランドマークを増やしている

トップの4つの棚・`/about`・404・関連記事で、`<section aria-labelledby>` を足した。名前の付いた `section` は region のランドマークになる。トップのランドマークは5つ増え、読み上げでは「辞典 領域」「辞典 一覧」と同じ名前が2回続く。一覧の名前は `ItemList` の `labelledBy` で付いているので、`section` の `aria-labelledby` は要らない。ランドマークは少なく保つのがよいとされる（WAI-ARIA APG「Landmark Regions」）。

### Minor-3: 触ったファイルに、捨てた「品書き・棚」の見立ての語と古いトークン名がコメントに残る

`src/app/page.tsx` のコメントには、次のものが残っている。

- 「品書きの行に変換する」（105行）
- 「品書き（よろず＝広さの棚）…行の一覧（ItemList）の棚で並べる」（27〜28行。新旧の語が1文に混ざる）
- 「--rule-strong の枠」（21行）

`src/app/page.module.css` の57行（`--rule-strong`）、`src/app/about/page.tsx` の45行（「トップの品書きの重複再掲」）にも同じものがある。

`Shinagaki` を消したので、「品書き」はもう部品の名前でもない。これらの語は事実と合わない説明である（ツギハギ禁止）。この変更で触った範囲だけでも、いまの語（行の一覧・見出し）に直してほしい。

### Minor-4: `ol` の見本に番号が見えない

`.list { list-style: none }` は `ol` にも掛かり、「順に読む一覧（ol）」の見本に番号が出ない。連載は見出しが回数を言う（3-2）ので、規定には反しない。ただし storybook の見出しが「ol」を言うのに、見た目では `ul` と区別がつかない。順が目で見えるべきかどうかを、T3-2a（`SeriesNav`）の前に決めておいてほしい。

### Minor-5: §5 の「ボックスは…コンテナと同じ内側の余白を持つ」と §7 の例外が並んでいる

§5 はボックスの余白を例外なく書いていて、§7 が行の一覧のボックスだけ上下の余白を外している。§7 だけを読めば分かるが、§5 から読む人は、行の一覧のボックスにも上下の余白があると受け取る。§5 のボックスの一文で「行の一覧のボックスは上下の余白を持たない（§7）」と参照するか、書き方を揃えてほしい。Major-3 の決め方も、同じ所に置けば1か所で読める。
