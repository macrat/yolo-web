# 事故報告: 転送量の「増分0」に執着し、サイトの開発を丸一日以上止めた

## 何が起きたか

サイクル316の目的は、`DESIGN.md` をサイト全体に届けること（B-754）である。その中の1項目「表示の速さ」の合格の線として、計画に「各ページの総転送量が変更前を超えない（増分0）」を書いた。

この線を満たすために、T1a「Web フォントの判断」は7巡に及んだ。ページごとのサブセット、共通の予備、閉じたページ、自作の静的解析器、CI の検査という専用のフォント配信の仕組みを、`tmp/` の写しで設計・試作し直し続けた。各巡でレビューが試作の穴を見つけ、それを塞ぐ往復が続いた。

- 計画の承認から T1a の7巡目を止めるまで、`src/` には1行の変更も入らず、来訪者には何も届かなかった。サイクルの開始から数えると1日半になる。
- その間の Claude Code の実行コストは、Owner の指摘では数百ドル以上である。

Owner から「転送量を増やさないということは、サイトの開発を丸一日止めて、数百ドル以上の実行コストをかけてまでやるべきことか」「フォントを新たに配信するのに増分ゼロを達成できる蓋然性と必要性は確認したか」と問われた。答えはどちらも**否**である。

## 線がどうやって生まれ、硬くなったか

1. **計画の1巡目**: レビューが「和文の Web フォントを足すので、表示の速さの悪化を検出する条件が無い」と指摘した。わたしは「LCP と転送量を出荷前後で比べ、悪化したら原因を詰めて手を打つ」と書いた。ここまでは、悪化を見逃さないための確認だった。
2. **計画の2〜5巡目**: 「合否の線が無い」「揺れで判定できない」と指摘されるたびに、線を数字にし、測り方を細かくした。
3. **計画の6〜7巡目**: 「本文を Web フォントにすると 110% の線を確実に越える」「上限を見積もりの前に決めないと落ちない判定になる」と指摘された。わたしは上限を**増分0**とし、「刷新の得を来訪者の時間で買わない」と理由を書いた。レビューはこれを「自案に不利な向きの健全な線」と評価した。
4. **T1a**: 増分0を「動かせない前提」として T1a に渡した。前提が動かせないので、それを満たす方式を作り込むしかなくなり、7巡の往復になった。

どの段でも、わたしは指摘された点に局所的に応えた。「この線は、サイクルの目的に対して釣り合っているか」という問いは、一度も立てなかった。

## 確かめなかったこと

### 必要性

- **増分0が来訪者にとって必要かを確かめていない。** 根拠に書いたのは「1ページで終わる 83.7% のセッションは転送量を取り返せない」「100KiB は約0.5秒」という一般論だけだった。来訪者が実際に速さで困っているか（GA の離脱や Search Console の Core Web Vitals）も、フォントの数百 KiB が来訪者の体験をどれだけ変えるかも、見ていない。
- **比べる相手を置いていない。** 和文の Web フォントを使うサイトで一般的な配り方（Google Fonts の分割配信）の転送量を、許せる代償の目安にすることを考えなかった。
- **変更前がすでに遅いことを知っていたのに、線を見直さなかった。** 変更前の5ページはすべて LCP 2.5秒を超えていた。フォントを増やさないことだけを厳格に守っても、来訪者の速さの問題は解けない。この事実を B-758 に切り出したところで止まり、増分0の厳しさを問い直す材料にしなかった。

### 蓋然性

- **増分0を達成できる見込みを、線を決める前に確かめていない。** 変更前の本文は端末の書体で、フォントの転送は0だった。そこへ本文の和文 Web フォントを足して、総量を変えずに済む見込みは低い。実際、計画の6巡目のレビューは「本文の 400 だけで線を越える」と見積もっていた。わたしは「上限を先に決める」ことを優先し、その上限が現実的に満たせるかを問わなかった。
- 結果として増分0は満たせたが、それは専用の配信の仕組みを作り込んだからで、その仕組みは自作の解析器の健全性に依存し、3巡続けて穴が見つかっていた。達成の蓋然性が低い線を固定したことが、作り込みを強いた。

## なぜ起きたか

- **目的が派生作業にすり替わった**（AP-P22）。サイクルの目的は「来訪者が目にする面を `DESIGN.md` のとおりにする」ことで、転送量はその副作用を見張る条件の1つにすぎなかった。それが T1a の中で、それ自体を最大化する目標になった。計画の目的の文は正しいままだったので、各巡のレビューの AP-P22 の点検は「目的は B-754 と一致」として通過し続けた。**点検が、文書に書かれた目的だけを見て、実際に時間と費用がどこへ流れているかを見ていなかった。**
- **計画の根幹の仮定を確かめなかった**（AP-P01）。「増分0が必要」「増分0は満たせる」の2つの仮定を、線を固定する前に確かめていない。
- **レビューの指摘に局所的に応え続けた。** 指摘はどれも正しかった。しかし、正しい指摘に1つずつ応えることと、その作業全体が目的に対して釣り合っているかを判断することは別で、わたしは後者を一度もしなかった。レビュアーは、渡された前提（増分0は動かせない）の中で指摘するので、前提の釣り合いを問うのは PM の役目だった。
- **CLAUDE.md の「実装コストは劣る UX を選ぶ理由にならない」を、費用を顧みない理由に読み替えた。** この原則は、来訪者の体験に差があるときに手間で妥協しないためのものである。来訪者の体験の差を確かめないまま、大きな費用をかける理由にはならない。
- **経過を見る目を持たなかった。** T1a が何巡目か、`src/` に何が入ったか、何時間たったかを、判断の材料にしていなかった。

## 影響

- サイトの開発が1日半止まり、来訪者に届くはずだった刷新（旧デザインの解消、入力欄の拡大、選択肢が見えない診断の修正など）が、その分遅れた。
- 数百ドル以上の実行コストを、来訪者の価値に釣り合わない作業に使った。
- T1a の文書（878行）と7本のレビューの記録が、専用の配信の仕組みを前提に積み上がった。直前に書いた [t1a-closure.md](./t1a-closure.md) も、この仕組みを T1 に持ち込む内容で、同じ執着の延長にあった。

## 何が正しかったか

- 表示の速さの条件は、目的（`DESIGN.md` を届ける）を妨げない形で置く。例えば「一般的な配り方で出したときの悪化を測り、来訪者に害がある大きさなら手を打つ」。線を固定する前に、必要性（来訪者が困っているか）と蓋然性（その線を満たせる見込み）を確かめる。
- 1つの項目が何巡も往復し始めたら、指摘に応える前に、その項目にかけている時間と費用が、サイクルの目的に対して釣り合っているかを判断する。レビューが渡された前提の中で指摘している限り、前提を問い直すのは PM である。
- 「実装コストは理由にならない」は、来訪者の体験の差を確かめたうえで使う。
