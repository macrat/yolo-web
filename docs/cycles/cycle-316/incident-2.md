# 事故報告: 転送量の「増分0」に執着し、サイトの開発を約21時間止めた

## 何が起きたか

サイクル316の目的は、`DESIGN.md` をサイト全体に届けること（B-754）である。その中の1項目「表示の速さ」の合格の線として、計画に「各ページの総転送量が変更前を超えない（増分0）」を書いた。

この線を満たすために、T1a「Web フォントの判断」は6巡に及んだ（レビューの記録は [review-t1a.md](./review-t1a.md)〜[review-t1a-6.md](./review-t1a-6.md) の6本）。ページごとのサブセット、共通の予備、閉じたページ、自作の静的解析器、CI の検査という専用のフォント配信の仕組みを、`tmp/` の写しで設計・試作し直し続けた。各巡でレビューが試作の穴を見つけ、それを塞ぐ往復が続いた。

- git の記録では、サイクルの開始（2026-09-24 10:51）から最初の `src/` のコミット（885c9243、09-25 07:42）まで約21時間（計画の承認（b6967d75、09-24 14:12）からは約17時間半）、`src/` には1行の変更も入らず、来訪者には何も届かなかった。T1a を閉じたのは 293d212d（09-25 05:33）と 13c4c3c3（09-25 07:25）である。
- その間の Claude Code の実行コストは、Owner の指摘では数百ドル以上である。

Owner から「転送量を増やさないということは、サイトの開発を丸一日止めて、数百ドル以上の実行コストをかけてまでやるべきことか」「フォントを新たに配信するのに増分ゼロを達成できる蓋然性と必要性は確認したか」と問われた。答えはどちらも**否**である。

## 線がどうやって生まれ、硬くなったか

1. **計画の1巡目**: レビューが「和文の Web フォントを足すので、表示の速さの悪化を検出する条件が無い」と指摘した。わたしは「LCP と転送量を出荷前後で比べ、悪化したら原因を詰めて手を打つ」と書いた。ここまでは、悪化を見逃さないための確認だった。
2. **計画の2〜5巡目**: 「合否の線が無い」「揺れで判定できない」と指摘されるたびに、線を数字にし、測り方を細かくした。
3. **計画の6〜7巡目**: 「本文を Web フォントにすると 110% の線を確実に越える」「上限を見積もりの前に決めないと落ちない判定になる」と指摘された。わたしは上限を**増分0**とし、「刷新の得を来訪者の時間で買わない」と理由を書いた。レビューはこれを「自案に不利な向きの健全な線」と評価した。
4. **T1a**: 増分0を「動かせない前提」として T1a に渡した。前提が動かせないので、それを満たす方式を作り込むしかなくなり、6巡の往復になった。

どの段でも、計画の直しは指摘された点に局所的に応えるものだった。「この線は、サイクルの目的に対して釣り合っているか」という問いは、計画にもレビューへの応答にも記録が無い。

## 確かめなかったこと

### 必要性

- **増分0が来訪者にとって必要かを確かめていない。** 根拠に書いたのは「1ページで終わる 83.7% のセッションは転送量を取り返せない」「100KiB は約0.5秒」という一般論だけだった。来訪者が実際に速さで困っているか（GA の離脱や Search Console の Core Web Vitals）も、フォントの数百 KiB が来訪者の体験をどれだけ変えるかも、見ていない。
- **比べる相手を置いていない。** 和文の Web フォントを使うサイトで一般的な配り方（Google Fonts の分割配信）の転送量を、許せる代償の目安にした記録は無い。
- **変更前がすでに遅いことを測っていたのに、線を見直さなかった。** 変更前の5ページはすべて LCP 2.5秒を超えていた。フォントを増やさないことだけを厳格に守っても、来訪者の速さの問題は解けない。この事実を B-758 に切り出したところで止まり、増分0の厳しさを問い直す材料にしなかった。

### 蓋然性

- **増分0を達成できる見込みを、線を決める前に確かめていない。** 変更前の本文は端末の書体で、フォントの転送は0だった。そこへ本文の和文 Web フォントを足して、総量を変えずに済む見込みは低い。実際、計画の6巡目のレビューは「本文の 400 だけで線を越える」と見積もっていた。計画は「上限を先に決める」形で上限を置き、その上限が現実的に満たせるかを問うた記録は無い。
- 結果として増分0は満たせたが、それは専用の配信の仕組みを作り込んだからで、その仕組みは自作の解析器の健全性に依存し、3巡続けて穴が見つかっていた。達成の蓋然性が低い線を固定したことが、作り込みを強いた。

## なぜ起きたか

- **計画の根幹の仮定を確かめないまま、合否の線を固定した**（AP-P01）。「増分0が必要」「増分0は満たせる」の2つの仮定を、線を固定する前に確かめていない。
- **固定した線が、それ自体を最大化する目標になった**（AP-P01）。サイクルの目的は「来訪者が目にする面を `DESIGN.md` のとおりにする」ことで、転送量はその副作用を見張る条件の1つにすぎなかった。それが T1a の中で、満たすこと自体が目標になった。計画の目的の文は正しいままだったので、目的の文を派生元と突き合わせる各巡のレビューの AP-P22 の点検は「目的は B-754 と一致」として通過し続けた。**点検が、文書に書かれた目的だけを見て、実際に時間と費用がどこへ流れているかを見ていなかった。**
- **レビューの指摘に局所的に応え続けた。** 指摘はどれも正しかった。しかし、正しい指摘に1つずつ応えることと、その作業全体が目的に対して釣り合っているかを判断することは別で、後者の判断は記録に一度も無い。レビュアーは、渡された前提（増分0は動かせない）の中で指摘するので、前提の釣り合いを問うのは PM の役目だった。
- **来訪者の体験の差を確かめないまま、大きな費用をかけ続けた。** CLAUDE.md の「実装コストは劣る UX を選ぶ理由にならない」は、来訪者の体験に差があるときに手間で妥協しないための原則である。T1a の各巡で、その差を確かめた記録も、かけている費用と比べた記録も無い。
- **経過を判断の材料にした記録が無い。** T1a が何巡目か、`src/` に何が入ったか、何時間たったかを、次の巡に進む判断に使った記録は無い。

## 影響

- サイトの開発が約21時間止まり、来訪者に届くはずだった刷新（旧デザインの解消、入力欄の拡大、選択肢が見えない診断の修正など）が、その分遅れた。
- 数百ドル以上の実行コストを、来訪者の価値に釣り合わない作業に使った。
- T1a の文書（[t1a-fonts.md](./t1a-fonts.md)、879行）と6本のレビューの記録が、専用の配信の仕組みを前提に積み上がった。直前に書いた [t1a-closure.md](./t1a-closure.md) も、この仕組みを T1 に持ち込む内容で、同じ執着の延長にあった。

## 何が正しかったか

- 表示の速さの条件は、目的（`DESIGN.md` を届ける）を妨げない形で置く。例えば「一般的な配り方で出したときの悪化を測り、来訪者に害がある大きさなら手を打つ」。線を固定する前に、必要性（来訪者が困っているか）と蓋然性（その線を満たせる見込み）を確かめる。
- 1つの項目が何巡も往復し始めたら、指摘に応える前に、その項目が前提にしている線（ここでは増分0）と、そこにかけている時間と費用が、サイクルの目的に対して釣り合っているかを判断する。レビューが渡された前提の中で指摘している限り、前提を問い直すのは PM である。
- 前提の釣り合いを問うことと、成果物の欠陥が出ているレビューを止めることは別である。この教訓が問い直させるのは派生した線の必要性と見込みで、来訪者に届く成果物のレビューの巡目ではない。欠陥が出続けているレビューを、巡の多さを理由に止めるのは、効率の規律を品質レビューの打ち切りに流用する失敗（workflow.md の AP-WF39）に当たる。同じサイクルの T3・T4 のレビューの止め方は、この教訓をその理由に引いて AP-WF39 の発生になった（[decisions.md](./decisions.md)）。
- 「実装コストは理由にならない」は、来訪者の体験の差を確かめたうえで使う。
