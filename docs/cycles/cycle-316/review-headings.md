## 指摘

### Critical-1: 長い文節の中の折り所が、広い行でも語を割る

`splitWidePhraseAtWords` は、全角6字（`NARROWEST_HEADING_LINE`）より広い文節に、画面の幅や見出しの段によらず `<wbr>` を足す。`<wbr>` には優先の順が無いので、ブラウザは行に入る所まで詰め、そこにある折り所を使う。「最後の手段」の片仮名の語の中の折り所（順位 3）も、平仮名どうしの所（順位 2）も、文節がまるごと次の行に入る幅でも使われる。

1280px・既定の記事の h1（86件）で、足した折り所で実際に折れた見出しは 42件。同じページで足した折り所だけを外して組み直すと、外したほうが良いのが 18件、足したほうが良いのが 6件だった。Chromium の利用者が変更の前に見ていた `auto-phrase` の組みと比べると、悪くなったのが 15件、良くなったのが 10件で、片仮名の語の中の折れは 13 → 28 に増えた。記事の閲覧は 13週で desktop 462・mobile 31（t4-design.md 5章）なので、いちばん多く読まれる形で悪くなっている。

いまの組み（1280px・既定。スクリーンショットは `tmp/cycle-316/review-headings/shot-1280-*.png`）:

- `JSON整形・フォー／マッターの／使い方ガイド`（前の Chromium: `JSON整形・／フォーマッターの／使い方ガイド`）
- `AIが指示を守ら／ないなら、／ルールより先に／『望み』／を渡してみてほしい`（`守らないなら、` は7字なので `守ら|ないなら、` に分けられ、1280px で使われる）
- `ツールを10個から／30個に拡充しました: ／プログラマ／ティックSEO戦略の／実践`
- `日本の伝統色250色の／辞典を作りました: ／プログラマティッ／クSEOの実践`
- `ゲームと辞典の／Layout共通化: ／品質要素を全コン／テンツに広げる第3弾`
- `四字熟語クイ／ズ2テーマ追加: …`・`ゲーミフィ／ケーションを作り、…`・`コンテキストエンジ／ニアリング`・`サイクルドキュ／メントとレビュー／ループの設計`・`AI臭を消すのに／夢中で、わたしは／何も主張していな／かった`

狭い幅でも同じことが起きる。WebKit の近似で変更の前より悪くなった既定の見出しは、ほとんどがこの形だった。

- 320px `一覧の／行全体を／クリッ／クできる／CSSと、…`（`クリックできる` は、片仮名から「で」に移る所が順位を持たないので、片仮名の語の中で分けられる）
- 375px `セッション／長期化がAIエー／ジェントの／…`、`AIエー／ジェントは／「最後の／確認」…`（`エージェントの` が `エー|ジェントの` に分けられ、前の `AI` と同じ行に詰められる）

このコードのファイルの頭には「この折り所は、文節が1行に収まる広い行でも、行の終わりに来れば使われる」と書いてある。つまり、この損は分かったうえで出荷されている。しかし §4 の最初の規則（文節が1行に収まらないときだけ、その文節の中で折る）とも、依頼の条件（既定で何も悪くしない）とも合わない。§4 の新しい項「いちばん狭い画面の1行より長い文節は、中に折り所を持つ」も、優先の順の無い `<wbr>` で作る限り、同じ節の最初の規則とぶつかる。

直す向き（どれを採るかは PM と planner が決め、全面を測り直す）:

- 語を割る折り所（片仮名の語の中・平仮名どうし・「〜する」の頭）は `<wbr>` にしない。広い行でも使われてよいのは、そこで折れても語が割れない所（字の種類が変わって語が始まる所、3字以上の片仮名の語どうし）だけに絞る。そのうえで、狭い画面だけで起きる非常の折り（`anywhere`）の損を数えて比べる。
- 足す折り所を、見出しの段と組む幅（主見出しの段の 320px など、文節が本当に収まらない所）に限る。たとえば、狭い行でしか出ない組み方は、狭い画面でしか効かない形で持たせる。
- §4 の文（planner が書いている所）には、文節の中の折り所は「広い行では使われない」ことを満たすものだけ、と書く。満たせない折り所は置かない。

### Major-1: 既定の 320px で「—」だけの行ができる（Cron の早見表）

`/blog/cron-cheatsheet` の h1 は、320px・既定で `Cron式 早見表 ／— ／フィールド・／特殊文字・／実用パターン／一覧` になる（`shot-320-cron-cheatsheet.png`）。前は `— フィール／ド・…` と語が割れていたが、1字の行は無かった。「・」のあとの折り所が足されて `— フィールド・` が1行に入らなくなり、「—」の前後の空白で折れて、「—」だけの行が残った。§4 の「既定の文字サイズでは、見出しに1字だけの行を作らない」に反する。同じ形の題（`SQL 早見表 — …`・`正規表現 早見表 — …`・`Git コマンド 早見表 — …`）は、200% で同じように「—」だけの行を作っている。空白に挟まれた約物（「—」「--」）は、後ろの語と1つの文節として扱うなどの直しが要る。

### Minor-1: `tableCell` の説明とふるまいが合わない

`PhraseOptions.tableCell` の説明は「見出しのための語の切れ目の折り所は足さない」と書く。しかし `splitIntoPhrases` は、`tableCell` のときも `splitFirstPhraseAtWords(phrases[0], tableCell)` を当てる（`splitIntoPhrases("コロケーション最重視", { tableCell: true })` は `["コロケーション", "最重視"]`）。T4-17 がこの分け方を前提にしているのなら説明を直し、そうでないならコードを直す。

### Minor-2: BudouX の採点をコードの中で組み直している

`boundaryScores` は、BudouX の `Parser` の中身（特徴の名前 `UW1`〜`TW4`・その位置・`baseScore` の出し方）を写して組み直している。`budoux` を上げて中身が変わると、`parser.parse` の境目と採点が黙ってずれる。`boundaryScores(t)[i] > 0` の所が `parser.parse(t)` の境目と一致することを、いくつかの文で確かめるテストを置く。

### Minor-3: 200% の記事の h1 の1字の行が増えた

320px・200% で、記事の h1 の1字の行が 37 → 143 に増えた（例 `全回答／を／数え上／げて`、`緑でも／、`）。200% では、文節の中の非常の折りから出たものは受け入れる決まりになっている。ただ、Critical-1 を直すときに、この数も既定と並べて測り直し、受け入れる形の中に収まっているかを1件ずつ分けて報告する。

## 依頼の問いへの答え

1. **前と後（WebKit の近似）**: 既定で、道具・ゲーム・診断・結果・一覧・漢字・四字熟語・色・ユーモア・トップ・404・about・privacy は、どの幅でも悪くなった所が無かった。記事の h1 は 10件が悪くなった（Critical-1 と Major-1）。数は上の表のとおり。
2. **広い画面で長い文節の折り所が悪さをするか**: する（Critical-1）。1280px の記事の h1 で、足した折り所で折れた 42件のうち 18件が、足さない組みより悪い。
3. **閉じ括弧のあとの助詞が行頭に来ること（「『望み』｜を渡して…」）**: 受け入れてよい。助詞は行頭の禁則に入らず、読むときも『望み』のあとで区切れて自然に読める。この規則が無いと、狭い画面で「に」だけの行が出る（`「yolos.net」／に／変更しました:`）。ただ、1280px では `『望み』` だけの短い行ができ、`auto-phrase` の `『望み』を／渡してみてほしい` よりやや落ちる。指摘にはしない。同じ見出しの `守ら／ないなら、` は Critical-1 に入る。
4. **読み上げ**: 見出しの字は、前と後で同じ見出しがすべて一字も違わなかった（375px の既定で 2,689 件）。違ったのは、文を変えた2件だけだった。404 の h1 は「ページが見つかりませんでした」から「ページが見つかりません」に変わり、`<title>` と同じになった。ユーモア辞典の見出しは中身の更新による。`<wbr>` を持つ見出し 1,059 件のうち `span` を持つのは 20 件で、どれも一覧の索引の「分類（5）」の形。前から持っていたもので、この変更では足していない。
5. **コードの質**:
   - 純粋さ: `splitIntoPhrases` は入力だけで決まる。遅延して作る `parser` と `scorer` はモジュールの中の値にしまうだけで、結果を変えない。
   - 速さ: 見出しの文 312件を 131ms（平均 0.42ms。最初の1回は表の読み込みで 43ms、1件の最悪は 24ms）で分けた。ビルドの時間の問題にはならない。400字の平仮名だけの文では 395ms かかる（分ける所の探し方が2乗に近い）。いまのデータには無い長さなので指摘にはしない。
   - 使われないコード・履歴のコメント: 見つからなかった。`breakInParens` から `tableCell` への名前の変更は、`markdown.ts` の呼び出し元まで揃っている。
   - テスト: `phrase-breaks`・`markdown` のテストは 107件すべて通る。新しい規則ごとにテストがある。ただし、広い行で折り所が使われること（Critical-1）は、単体テストでは捉えられない。Critical-1 を直したら、広い行で語を割らないことを確かめる実測を完了の条件に入れる。
