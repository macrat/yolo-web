## 指摘

### Major-1: 採った H2n の折れ方と、書き直す §4 の文が食い違う。結果のページの h1 は既定の文字サイズで語の中で割れる

- 所: 2-2「結果のページ」の1つ目（158行）、2-3 の H2n の組み方と「§4 の文を書き直します」、8章の §4 の行、T4-7 の完了の条件、index.md の T5 の行。
- (a) **しきい値のせいで、文節が1行に入らないときに語の切れ目が効かない。** 文節の中の語の切れ目の `<wbr>` は「1行に入る字が約8字より少ない幅」でだけ効く。結果のページの h1 は主見出しの段（375px で `2.08rem`＝33.28px）で、置かれる幅はコンテンツ幅 321px なので、1行に約9.6字が入る（計算）。しきい値の外なので2つ目の `<wbr>` は `display: none` のままで、2-2 が「24のうち6タイプで文節が1行に入らない」とした所は、`overflow-wrap: anywhere` で語の途中で割れる。2-2（158行）の「そのときはまず文節の中の語の切れ目で折れます」と T4-7 の「文節の中の語の切れ目で折れる見込み」は、H2n の決まりでは起きない。結果のページは28日で35表示（mobile 30）で、既定の文字サイズの来訪者がそのまま見る。
- (b) **しきい値の内では、文節が次の行に入るときにも文節の中で折る。** 行の折り方は、行に入る最後の折り所を取る。2つ目の `<wbr>` が効くと、文節が丸ごと次の行に入る場合でも、前の行の残りに文節の頭の語を詰めて折る。0章の表がこれを示している: 375px の 200% で、文節の中で折れたタイプは Fg の18から H2 の21に、320px の 200% で21から22に増えた。Fg で文節の中の折れが無かった（どの文節も1行に入った）タイプが、H2 で文節の中で折れた、ということである。書き直す §4 の「文節が1行に収まらないときは、文節の中の語の切れ目で折る」と合わない。
- (c) **書き直した文でも、残る折れは規定に反する。** 設計は §4 を「この組み方が実際に守れることに合わせ」るとするが、200% で残る語の中の折れ（375px 12・320px 16タイプ。「調べてか／ら」「確認しなが／ら、」）は、新しい文の「それでも収まらないときだけ、語の中で折る」にも反する（「から」「ながら」は1行に収まる）。新しい文は、いまの文（「語の中で折るのは、一語が1行に収まらないときだけ」）と意味がほぼ同じで、実装が守れる形にもなっていない。「語の切れ目を持たない仮名の続き」という説明も不正確で、ICU は「調べ|て|から」と切れ目を返し、設計の絞り込み（次の語が漢字・片仮名・開き括弧で始まる所だけ）が落としている。
- (d) **変える手順に乗っていない。** options.md「`DESIGN.md` を変えるとき」は、規定が来訪者にとって誤りだと示せたときだけ変え、「実装が難しい」は理由にならないとする。2-3 の理由は「この組み方が実際に守れることに合わせます」で、来訪者にとっての比べ（見た目の規定なので、変更前と変更後を来訪者の目で比べる）が無い。手順のある場所も「index.md の」と書いているが、index.md はリンクだけで、手順は options.md にある（209・525・640行）。
- (e) **ほかの文と食い違う。** `DESIGN.md` §4 の「語の中で折るのは、どちらも一語が1行に収まらないときだけ」の「どちらも」は、2つ目の項（名前に括弧で数を添えたもの）にも掛かる。8章は2つ目の項を変えないとするが、この文を置き換えたあとの2つ目の項の書き方が無い。`frontend-design` スキルの「目で確かめる」（48行）にも同じ規則があり、T4-1 はスキルの「実装の技術」しか直さない。index.md の T5 の行は「文字サイズ 200% の 320px で語の中で折れないことを確かめる」とし、設計が測った 16/24 と合わない。
- 来訪者への効き方: 既定の文字サイズで結果のページを開いた来訪者が、6タイプで自分のタイプ名を語の途中で割られて読む。200% の来訪者は、次の行に丸ごと入る文節も割られる。規定と実装が食い違ったまま出荷すると、T5 がページの見出しに当てたあとの確かめで、どちらを正とするかが決まらない。
- 直し方: 文節の長さでしきい値を変える形を試作して比べる。例: サーバーは文節の字数 L を知っているので、その文節の中の `<wbr>` に L ごとの印を付け、コンテナクエリで「置かれた幅が L 字より狭いときだけ効く」にする（コンテナクエリの条件の `em` はコンテナの字の大きさで測る）。これなら「文節が1行に収まらないときだけ、文節の中の語の切れ目で折る」がそのまま実装になり、結果のページの h1 の既定の文字サイズでも語の切れ目で折れる。そのうえで、24のタイプ名を 0章と同じ4つの条件に、結果のページの h1（主見出しの段・321px）を足して測り直す。残る折れを §4 でどう扱うかは、options.md の手順で、変更前と変更後を来訪者の目で比べて示してから決める。§4 の2つ目の項の書き方・スキルの48行・index.md の T5 の行・2-2（158行）・T4-7 を、決めた形にそろえる。

### Major-2: 読み上げの天秤が、`<wbr>` を安全とみなし、この環境で行えない聞き取りに決定を預けている

- 所: 2-3「VoiceOver の読み上げと禁則の破れの天秤」、2-3 の T9 に渡す型、11章の4つ目。
- (a) **片側だけに危険を数えている**（AP-P02）。設計が引く Axess Lab の記事は、見出しの中の `span` だけでなく `<br>` でも VoiceOver が見出しを2つのものとして読むと書く。`<wbr>` は `<br>` と同じく行の折り所を作る要素で、H2n は1つのタイプ名に文節の数だけ（2つ目の `<wbr>` を含めて最大十数個）置く。天秤は「見出しの中の要素は `<wbr>` だけで、文字を分ける `span` を持たない」を H2n の利点として数えるが、`<wbr>` で切れるかは `span` と同じく確かめていない。どちらも未確認なら、天秤は「切れるおそれのある組み方」どうしの比べで、H2n を選ぶ理由にならない。
- (b) **聞き取りの手段がこの環境に無い。** `docs/knowledge/input-events-and-guards.md` は、TalkBack と VoiceOver を「実行できる環境が無い」と記録している。index.md の T11 の行も「使えるなら」と書く。11章は T9 の聞き取りで H2 に切り替えるかを決めるとするが、聞けないときにどうするか、切り替えるならどのタスクが T5 まで当てた見出しを直すかが無い。
- (c) **両方の危険を消す組み方が比べられていない**（AP-P17）。例えば、読み上げの名前を1つの文字の並びで持ち、見た目の折り所（`<wbr>` や禁則のまとまり）を持つ側を読み上げから外す組み方がある。これなら禁則のまとまり（H2）を持っても読み上げは切れない。代わりに、同じ文が DOM に2度あることの損（写したときの文・ページ内検索・翻訳・検索エンジンの読み方）がある。この損と、H2n・H2 の損を並べて決める。
- 来訪者への効き方: iPhone でスクリーンリーダーを使う来訪者（結果に着いた回数の66%が WebKit）が、自分のタイプ名を切れ切れに聞くおそれは、H2n でも残る。確かめる手段が無いまま出荷すると、そのおそれが残ったことを誰も知らない。
- 直し方: 3案以上（H2n・H2・読み上げの名前を分ける組み方）を、いま確かめられること（Chromium の読み上げの名前、出典に書かれた振る舞い）で比べて決める。T9 に渡す型には、iOS の版、見出しへの移り方（1本指の左右のスワイプ・ローターの見出し・全体の読み上げ）、比べのための `<wbr>` を持たない同じ見出し、結果のページの h1、iPhone で 320px と 200% を作る方法（Safari のページの拡大と、既定の文字サイズの 32px は同じ組み方にならない）を足す。聞けない場合の扱いと、切り替えるときに直すタスクを 11章に書く。

### Major-4: 推測を重ねたあと、入力欄が最初の画面から外れる。T4-11 の条件がそれを測れない

- 所: 2-6 の V7 の判断（「いちばん新しい推測の行がいつも入力欄のすぐ上にあり、キーボードを開いても隠れにくい」）、T4-11 の完了の条件。
