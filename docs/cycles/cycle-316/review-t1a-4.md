## blocker

### B-1. 入力欄は、ページの家族で組まれている。そのため、入力の中で字ごとに書体が混ざる。開いたページの検索では、打った字が予備の要求に映る（§3 の新しい文・結論3・「開いたページでは来訪者だけが知る情報は要求に映らない」・憲法4）

**どこが**:

- 「入力に由来する字」（「来訪者が入力した字…は、和文を端末のゴシックで組む」）
- 測り方の CI（「入力欄と、入力を映すと印を付けた表示は除く」）
- 「開いたページでは…来訪者だけが知る情報は、要求に映らない」

**なぜ**:

- r4g の入力欄の `font-family` は `"Yolos Sans", pf5f626643, …` で、ページの家族を含んでいる。2巡目の試作では、入力欄を `"Yolos Sans", 端末のゴシック` にしていた。
  - `email-validator` の入力欄に「ユーザー@例え.jp」と打つと、1つの `input` に BIZ UDGothic 4字と IPAGothic 2字が同居した。
  - `char-count` のテキストエリアに「吾輩は猫である。名前はまだ無い。文字数を数える。」と打つと、「吾輩」「猫」「無」は端末の書体で、「名前」「文字数」は UDGothic で描かれた。目で見て字の太さが違う（`inp-cc-big.png`）。
  - どのツールでも、来訪者が最初に触る面で B-1 と同じ種類の混ざりが出る。しかも CI は入力欄を除外しているので、見つからない。
- 開いたページ（予備あり）でクライアントの検索に打つと、打った字に応じて予備の区画を読んだ（`srch.mjs`）。
  - `/dictionary/yoji` に「臥薪嘗胆」と打つと、区画を8つ読んだ（本文6、見出し2。検索結果の描画を含む）。
  - `/dictionary/kanji` に「鬱」と打つと2つ、`/blog` の絞り込みに「麒麟」と打つと1つ読んだ。
  - `DictionarySearch` はクライアントだけで動く。これまでは検索語がサーバーに届く道は無かったが、この形で新しく道ができる。
  - 文書は「閉じたページ」をツールと診断のプレイ面に限っている。入力と、入力で選ばれる表示（検索の結果）を持つ開いたページを扱っていない。一方で、`kanji-kanaru` の入力欄は端末のゴシックになっていて、扱いが揃っていない。
- 案A を採った3つの理由の1つが「入力と答えが要求に映らない」なので、この穴は判断の前提に関わる。

**どう直すか**:

- 入力欄（`input`・`textarea`・`contenteditable`）の書体は、**すべてのページで**「欧文, 端末のゴシック」にする。ページの家族と予備を並びに入れない。これを §3 の文とスキルの提案に書く。
- 「入力で選ばれる表示」の規則（層に入れるか、端末のゴシックにするか）を、ツールだけでなく、開いたページの検索（辞典3種・ブログ・そのほかのクライアント検索）にも掛ける。対象を列挙して決める。
- CI の同居の検査では、入力欄を除外しない。代わりに「入力欄に Web フォントの和文が0」を検査する。開いたページの検索にも「操作のあとの要求0」を足す。
- 試作で直し、`char-count`・`email-validator`・辞典の検索で確かめ直す。

### B-2. keigo-reference と business-email を T1 の条件で満たすとした見込み（−64.1・−76.1KiB）は、文書が退けた規則で計算されている。しかも、文書が定める集め方の規則のもとでは、表を HTML に描いても減らない（問い3・index「越えたときの帰結」）

**どこが**: 上限の節（「見積もりでは −64KiB」）、境界のページの選び直し（「−64.1・−76.1KiB」）、ビルドの経路の条件6の3点目。

**なぜ**:

- `toolsmargin.mjs` を写して、条件だけを変えて走らせた（`tm.mjs`）。
  - 環境変数なし: keigo **−64.1**、business-email **−76.1**。これは、役割の分からない文字列を**本文だけ**に入れる規則で、r4e の規則にあたる。文書は、この規則を「keigo で混ざったので採らなかった」と書いている。
  - `UNK=1`（r4f の規則。マークアップにある字を除いて、すべての役割に入れる）: keigo −8.4、business-email −15.1。これも keigo で混ざったので採らなかった規則である。
  - `ALLROLES=1`（文書が採る規則）: keigo +49.6、business-email +15.3。
- 文書の集め方の2は、「役割の分からない文字列（定数・変数を通るもの）は、ページが持つすべての役割に入れる」と定めている。表を HTML に描いても、`logic.ts` のデータを `{entry.x}` で描く文字列は、構文木の上では役割が分からないままである。この規則なら見出しと太字に入り続けるので、減らない。
  - 「HTML に描けば役割どおりに集まる」を成り立たせるには、マークアップが全状態を覆うという前提が要る（件数の文言・展開した例文・「よくある間違い」のタブなど）。そのうえで、マークアップを優先する別の規則が要る。どちらも文書に書かれておらず、試されてもいない。
- 見込みは Web フォントだけの計算である。表・カード・タブの中身を HTML に描いて増える HTML の分（`logic.ts` は 37KB。表とモバイルのカードで二重になる）が入っていない。
- T1 で越えたら、帰結は「本文を端末のゴシックに改めて §3 を書き換える」になる。土台を作ったあとでこれを判断することになる。T1a を T1 の前に置いたのは、これを避けるためである。
- 写しのリポジトリとビルドの手順はそろっている。実測にかかる手間は小さい。

**どう直すか**:

- 「決まった中身を HTML に描く」ときの集め方の規則を、1つに決めて文書に書く（何を「役割が分かる」とみなすか、全状態を覆うことをどう確かめるか）。
- keigo と business-email を写しで実際に書き換えてビルドし、Lighthouse の5回で上限を満たすことと、操作のあとの同居0を示してから承認に進める。
- 満たせないときは、index の帰結の順に従う。

**問い3への答え**: T1 の条件にして進めることは認められません。T1a の中で実測してください。
