## 結論

**改善指示**（Blocker 0・Major 4・Minor 5）

「いつも見えているものの左端で揃える」という性質で分けたのは、来訪者の目に入るもの同士を揃えるという点で筋がよい。字だけのコントロールの字が見出しや本文と同じ列に立ち、プライマリボタンの地と入力欄の枠が同じ縦の線に立つ。休んでいる状態で見えない箱ではなく、見えているもので揃えるのは、来訪者の側から見て正しい。前回の Major-1（「形」の範囲）は地・枠と中身が分かれて解けた。前回の Major-2（例外の広がり）は「文の中のリンク」にそろえて、方向としては解けた。

ただし、次の4つが残る。

1. 箱をコンテナとボックスの余白へ張り出すと決めたのに、§5 の「コンポーネントを置けるのはコンテンツ幅の中だけ」「すべてそこから始まり、右にだけ伸びる」がそのまま残り、同じ節の中で食い違う。
2. 張り出す先が「コンテナかボックスの内側の余白」に限られ、何の左端に揃えるかも書かれていない。箇条書き・表のセル・一覧の行の中にあるリンクで、規則が一意に掛からない。
3. 「文の中のリンク」の境目が決まらない。「リンク — 説明」の形の項目と、リンクだけのセルを、builder が判断で分けることになる。
4. 決めた理由として書かれた撮り比べの結果が、実測とも、書かれた規則とも合わない（サイト名と見出しは同じ列に立っていない。一覧は規則と逆の組み方で撮られている）。

## 指摘

### Major-1 張り出した箱が、§5 の「コンテンツ幅の中だけ」「右にだけ伸びる」と食い違う

新しい箇条は、地も枠も持たないコントロールの箱を「コンテナかボックスの内側の余白へ張り出す」と言う。箱には hover の線・無効の枠・フォーカスのリングが出る（直前の箇条）。つまり、線とリングがコンテンツ幅の外に描かれる。

同じ「ページの割り方」の中に、次の文がそのまま残っている。

- 「**コンポーネントを置けるのはコンテンツ幅の中だけ。** 全幅の罫線はコンテンツ幅の外へ出る。」——外へ出るものとして挙がるのは全幅の罫線だけである。
- 「**コンテンツ幅の左端は、どのページでも同じ位置。** すべてそこから始まり、右にだけ伸びる。」——箱はそこより 8px 左から始まる。
- 「**ボックス**は……コンテナと同じ内側の余白を持つ。」——余白が何も置かない場所なのか、箱が入る場所なのかが書かれていない。

2つの箇条を続けて読むと、「すべてコンテンツ幅の左端から始まる」の直後に「箱は余白へ張り出す」が来る。後から足した例外に見え、どちらが正しいのかを builder が選ぶことになる。

この食い違いは、狭い画面で見た目に出る。`45rem` 未満ではコンテナとボックスの内側の余白が 8px で、張り出しも 8px なので、**箱の縁がコンテナやボックスの太いボーダーにぴたりと接する**（撮り比べ B の実測で、320px のサイト名の箱は x=19＝コンテナのボーダーの内）。そのとき:

- フォーカスの外リング（`--ink`）が、ボーダー（`--rule` = `--ink`）と接して 6px の1本の線に見える。
- hover の細い線の左辺は、ボーダーに埋もれる。
- プライマリでないボタンの**無効の破線**が、ボーダーの実線に接し続ける。`StorybookContent.tsx` に「結果が出ると押せます」の無効のボタンがあり、ツールのパネル（ボックス）の中に置けば、結果が出るまでずっとこの形である。§6 の「太い線で囲まれたものは、線種・大きさ・位置で読み分ける」は、破線とボックスの実線が1本に重なると、その左辺で読み分けられない。前々回（review-design-left-edge-2 の Minor-3）で指摘された形が戻っている。

**直し方**: planner が、§5 の「ページの割り方」を、張り出しを最初から含む形に書き直す。例えば「見えているものはコンテンツ幅の中に置く。コンテナとボックスの内側の余白に入るのは、全幅の罫線と、地も枠も持たないコントロールの箱の余白だけ」のように、コンテンツ幅と余白の役割を1か所で言う。「すべてそこから始まり、右にだけ伸びる」も、何が始まるのか（見えているもの）を言う形にする。あわせて、`45rem` 未満で箱がボーダーに接することを受け入れるか（受け入れるなら、無効の破線・リング・hover の線がボーダーと重なっても読み分けられる理由）、接しないようにするか（例えば狭い画面の余白を張り出しより広くする、無効の破線は字の側に寄せる）を決め、理由をサイクルの文書に書く。

### Major-2 何の左端に揃えるのか、どこへ張り出すのかが、コンテンツ幅の端にないコントロールで決まらない

新しい箇条は「いつも見えているものの左端を揃える」と言うが、**何に**揃えるのかを書かない。前の箇条の「コンテンツ幅の左端」に揃えると読むのが自然で、張り出す先も「コンテナかボックスの内側の余白」に限っている。

ところが、依頼の対象のうち次のものは、コンテンツ幅の左端にも、ボックスのコンテンツ幅の左端にもない。

- **箇条書きの中のリンク**（リンクだけの項目。`src/blog/content` の 8本の記事にある）。揃える相手は、点の後ろの項目の字の列である。箱を 8px 左へ広げると、張り出す先は点と字のあいだで、コンテナの余白ではない。点と字のあいだが 8px 前後なら、リングと hover の線は点に接するか重なる。
- **表のセルのリンク**（リンクだけのセル。`2026-02-28-game-dictionary-layout-unification.md` の表など）。2列目より右では、揃える相手はセルの字の列で、箱の 8px は列を区切る細い罫線をまたぐかもしれない。§5 は表のセルの内側の余白を決めていない。
- **一覧の行の中に置く別のリンク**（§7「行の中に別のリンクを置くときは、それだけを独立に押せる」）。行の中身は行の箱の内側 8px から始まるので、中のリンクの箱を 8px 広げると、行の箱の縁に接し、行の hover の線とフォーカスのリングに重なる。
- **折り返したナビの2行目の最初の項目**。1行目の最初の項目と同じく張り出すのか、字の列が1行目とずれるのか。規則の文面は「張り出す」を並びの最初のものに限っていない。

どれも builder がその場で決めることになり、部品ごとに違う答えが出る。前の2巡で起きた「分類に入らない部品」と同じ形の問題である。

**直し方**: planner が、揃える相手を性質で言う。例えば「字だけのコントロールの最初の字は、それが置かれた字の列（コンテンツ幅・ボックスのコンテンツ幅・箇条書きの項目・表のセル・一覧の行の中身）の左端に立つ。箱の左右 8px は、その列の外の余白に重なる」。そのうえで、余白が 8px に足りない場所（点と字のあいだ、表のセルの内側、一覧の行の内側）で箱をどう扱うかを決める。表のセルの内側の余白は §5 の表のコンポーネントの規定で決める。

### Major-3 「文の中のリンク」の境目が決まらない

タップターゲットの例外は「文の中のリンク」になった。WCAG 2.5.8 の例外は "The target is in a sentence or its size is otherwise constrained by the line-height of non-target text" で、方向は合っている。ただし、Markdown から組むブログの本文では、次の2つの形がどちらにも読める。

- **「リンク — 説明」の項目**。`src/blog/content` に 19 項目ある（例: `- [MDN: ARIA: status role](…) — role="status" の暗黙的…の根拠`）。リンクの後ろに同じ行で字が続くので「文の中」とも読めるし、項目の頭に単独で立つリンクとも読める。
- **表のセルのリンク**。リンクだけのセル（`| cycle-45 | [信頼レベルUIの実装](/blog/…) | … |`）と、セルの文の終わりにあるリンク（`…理由は[ファイルの変更を捨てる](/blog/…)`）が同じ記事群に混ざる。

どちらに分けるかで、箱・44px・左端の張り出し・リングの位置（箱の内側か字の外か）・hover（細い線か太い下線か）がすべて変わる。Markdown の描画は機械的に分けるしかないので、DESIGN.md が判定できる形で言わないと、builder が決めた線引きが規則の代わりになる。来訪者の側では、同じ見た目のリンクの並びが記事によって 44px の行になったりならなかったりする。

**直し方**: planner が、「文の中のリンク」を判定できる言い方で定める。例えば「同じ行にリンクでない字が並ぶリンク」（WCAG の "constrained by the line-height of non-target text" に当たる）か、「段落・項目・セルの中身がそのリンクだけでないもの」か。どちらを選ぶかは、上の2つの形を来訪者の側から見て決め、理由をサイクルの文書に書く。§5 の箱の箇条と §6 のタップターゲットの箇条は、同じ定めを指す。

### Major-4 決めた理由として書かれた撮り比べの結果が、実測とも規則とも合わない

サイクルの文書は、撮り比べの結果として「いつも見えているもので揃えると、サイト名・パンくず・見出しの字が同じ列に立ち」と書く。撮り比べ B の `measurements.json` では、次のとおりである。

| ページ・幅       | サイト名の字 | パンくずの字 | 主見出しの字 |
| ---------------- | ------------ | ------------ | ------------ |
| 年齢計算・320px  | 27           | 43           | 43           |
| 年齢計算・1280px | 179          | 195          | 195          |
| トップ・320px    | 27           | —            | 51           |
| ブログ・1280px   | 179          | —            | 203          |

パンくずと見出しは揃ったが、**サイト名は見出しより 16〜24px 左にある**。ページの中身が、まだ DESIGN.md の割り方に移っていない分だけ内側に入っているためで、A でも B でもサイト名と見出しは揃っていない。前回の Major-3 が「形を作って見て決める」ことを求めたのは、まさにサイト名と見出しの縦の並びだった。幾何の上では B で揃うはずだが、見て確かめたとは言えず、文書の記述は実測と食い違う（AP-WF14）。

もう一つ、撮り比べ B の関連ツールの一覧は、`data-text-box="rows"` のまま、**罫線を 8px 左へ張り出し、行の名前の字を見出しの字（x=43）に揃えて**組まれている（一覧の箱 x=35、名前の字 x=43）。書かれた規則は一覧を「地や枠を持つもの」に入れ、罫線の左端を揃えて中身を 8px 内側に置くので、名前の字は見出しより 8px 右に立つ。つまり、一覧については、書かれた規則の形は撮られておらず、撮られた形は規則と逆である。一覧は §7 でこのサイトの探す面の主役で、「見出しと名前の字の列がずれる」か「罫線が見出しの左へはみ出す」かは、ナビで B を選んだ理由（字の列のがたつき）と同じ問いである。

**直し方**: PM（または planner）が、ページの中身をコンテンツ幅の左端に置いた状態で、書かれた規則どおりの形（一覧は罫線を揃え、名前を 8px 内側）を 320px と 1280px、ライトとダークで撮り直す。そのうえで、一覧をどちらで揃えるかを見て決め、サイクルの文書の撮り比べの記述を実測に合わせて書き直す。一覧の扱いが変わるなら、§5 の箇条の括弧と §7 の「ボックスのコンテンツ幅いっぱいの細い罫線」を合わせて直す。

### Minor-1 「地や枠を持つもの（プライマリボタン・入力欄・一覧）」の「一覧」と「枠」が指すものが揺れる

- 揃えるのは「一覧」ではなく「一覧の行」である。一覧はボックスに入る（§7）ので、「一覧の枠」はボックスの太いボーダーとも読める。
- 一覧の行の「枠」は、上下の行の区切りだけで、左右には休んでいるときに線が無い（hover で左右に細い線が出る）。「枠の左端」とは行の区切りの罫線の左端のことだと書かないと伝わらない。
- ラジオボタンの円・チェックボックスの四角も「太い線で描く」枠である。括弧の例示で「地も枠も持たないもの」に入ることは分かるが、分ける性質そのものは「箱の縁に地や枠が見えるかどうか」である。

**直し方**: 「箱の縁に地か線が見えるもの（プライマリボタンの地・入力欄の枠・一覧の行の区切り）は、その左端を揃える」のように、性質と、何の左端かを1文で言う。

### Minor-2 文の中のリンクのリングの位置が、タップターゲットの箇条に足されている

§6 の「タップターゲットは 44px 以上」の箇条に「そのフォーカスのリングは字の外に出る」が入った。リングの位置は直前の「二重リングは、コントロールの箱の内側に密着して出る」の箇条が決めることで、タップターゲットの箇条の中にあると、リングの出方を探す読み手が見つけられず、後から書き足した注記に見える（ツギハギ）。二重リングの箇条で「箱を持つものは箱の内側に密着し、文の中のリンクは字の外に密着する」と1か所で言い、「フォーカスリングはタップターゲットと一致する」とも同じ言い方でつなぐ。

### Minor-3 §6 の2つの表で「要素に密着した二重リング」が残る

hover の行と hover の箇条は「箱」になったが、表のフォーカスの行と「太い線で囲まれたもの」の読み分けの表は「要素に密着した二重リング」のままである。字だけのコントロールでは、要素（字）と箱が 8px 違うので、リングが字に密着するのか箱に密着するのかが揺れる。文の中のリンクも含めて言うなら「箱に密着（文の中のリンクは字に密着）」、表では短く「箱に密着した二重リング」にそろえる。

### Minor-4 幅の表の「コントロール」と、ラジオボタン・チェックボックスの「行全体」

- 幅の表の「コントロール」の行は、入力欄と一覧の行を別の行に置くので、表の中では「字で幅が決まるコントロール」の意味で、箇条の「コントロール」（入力欄・一覧の行を含む）より狭い。前回の Major-1 の後半で指摘した点が残っている。表の行の名前を「ボタン・リンク・ナビ項目などのコントロール」のように範囲を言う形にする。
- §6 は、ラジオボタンとチェックボックスで「ラベルを含む行全体がタップターゲット」と言う。「行全体」がコンテンツ幅いっぱいなのか、幅の表のとおり「字（円とラベル）の左右に 8px」なのかが読めない。箱はタップターゲットと一致するので、これで箱の幅と hover の線の長さが変わる。

### Minor-5 実装のレビューで確かめること（規則の文面は変えなくてよい）

- フォーカスのリング（6px）と中身（8px）のあいだが 2px になる。入力欄の書いた字とカーソル、プライマリボタンの字、ラジオボタンの円が詰まって見えないか。
- プライマリボタンの地の左右が 8px になる。反転の地の中で字が窮屈に見えないか。
- 箇条書きと表のセルのリンクが 44px を持つとき、項目の並びと表の行の高さがどう変わるか。
- 折り返したナビ・パンくずの2行目の最初の字が、1行目の最初の字と同じ列に立つか。
- 上の各項目を、320px と 1280px、ライトとダークで撮る。
