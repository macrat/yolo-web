### 2. 指摘

**major-1 T1 のフォントの判断が、判定になっていない（基準が無く、決める順も決まっていない）。行き先の手順とも噛み合っていない**

- どこ:
  - index.md:15（T1）と :94 の「上限は T1 で…比べて決め」
  - options.md:66
  - options.md:73 の「`DESIGN.md` を変えるとき」にある「示し方は、変更前と変更後を来訪者の目で比べること（T9 の観点）」
- なぜ:
  1. 「来訪者の得（読みやすさ）」と「払う量」を何の単位で比べるかが書かれていません。上限を決めるのは、コストを見積もるのと同じ T1 です。上限を見積もりの後に決めれば、出た値に合わせて置けてしまいます。この判定は落ちようがありません。計画自身がこれを「この刷新で最も大きな来訪者のトレードオフ」と呼んでいます。そこに、落ちることのない線を置くことになります。
  2. 行き先として示した「`DESIGN.md` を変えるとき」は、証拠の出し方を「T9 で変更前と変更後を来訪者の目で比べる」に限っています。T1 の時点に T9 はありません。しかも、転送量の害は目で見比べても出ません。いまの文面のままでは、T1 で「許せない」と判断しても §3 を変える正当な道が無く、手順どうしが矛盾します。
- どう直すか:
  1. 払う量を、来訪者の側の量に直して書く。たとえば「Lighthouse のモバイル既定の回線で何秒ぶんか」です。この計測の設定は `throughputKbps: 1638.4` で、`tmp/lh/before/*.json` の configSettings で確かめました。この回線では 362KiB が約1.8秒にあたります。1ページで去る 83.7% のセッションに、その秒数を課してよいかを問う形にします。
  2. 上限（または上限を決める式）は、**新しい書体の転送量を見積もる前に**決めて、レビューを通す。そのあとで見積もりや試作をして、照らし合わせる。この順番を T1 に書く。
  3. 得の側も、比べる対象を決める。たとえば、5ページのモバイルの画面で、BIZ UDPGothic と端末のゴシック（iOS はヒラギノ、Android は Noto Sans CJK）を並べて比べる。§3 が挙げる「約物が詰まる」という利点が、端末の書体で `palt` を使っても得られないかも、材料に入れる。
  4. options.md「`DESIGN.md` を変えるとき」の示し方を直す。見た目の規定は T9 の目視で、転送量や速さの規定は T1 の計測と、来訪者の得の比較で示す、とする。
  5. T1 の判断そのものを単独でレビューに出してから土台に入る、と明記する。
