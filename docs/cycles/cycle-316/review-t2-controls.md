### `box-shadow` で内の輪を塗る書き方（観点6）

妥当と判断した。§5 の「影を持たない」が禁じているのは、奥行きを見せる影・グロー・ぼかしである。`--focus-ring-fill` と `--hover-line` は、ずらしもぼかしも持たない。広がりだけで §6 の線を引いている。見た目は線で、影ではない。`outline` は1本しか引けない。二重の輪で内の輪を地に任せると、反転やコンテンツの色の上で内の輪が消える。`border` で引けば要素の大きさが変わる。design-gate の例外はトークンの値と完全に一致するときだけ効くので、ほかの `box-shadow` を通す穴にはならない。

## 指摘

### Major-1 パンくずの 44px を箱の幅で取ったため、字の間隔がそろわず、狭い画面で縦に伸びる

`Breadcrumb.module.css` の `.link` は、`min-width: 44px` と `justify-content: center` で標的の幅を取っている。2字の項目（「遊ぶ」「ツール」など）は箱が字より広い。そのため、字の前後に左右 8px ずつの空きができる。320px と 375px の `/play/character-personality` では「ホーム /␣␣遊ぶ␣␣/ あなたに似たキャラ診断」と並び、区切りの前後の間隔が項目ごとに変わる。どの行も 44px の高さを持つので、パンくずが2行に割れる幅では上端の下に約 90px を使う。パンくずはすべての詳細ページの頭に出るので、来訪者はどのページでも最初にこれを目にする。

同じ問題は、上端のナビ（`FrameLink`）ですでに解いてある。FrameLink のコメントには「箱を広げると字の後ろの間隔だけが広がるので、広げるのはこの範囲だけにする」とある。押せる範囲を `::after` に広げ、`data-hit-area="after"` で hover とリングをその範囲に出す作りである。同じ働きの部品が別の作り方をしているのは、§12「位置の一定」の精神にも反する。

**直し方**: パンくずのリンクも FrameLink と同じく、字の箱は字の大きさのまま置く。押せる範囲は `::after` で 44px 四方に広げ、`data-hit-area="after"` を付ける。縦の標的を行の高さの中で重ねて取れるかは、2行に割れた幅で確かめる。

### Major-2 ページ送りの端で「前へ」「次へ」を置かないため、「次へ」の位置がページごとに動く

実測（375px 以下）:

| ページ | 「前へ」 | 「n / 8」 | 「次へ」  |
| ------ | -------- | --------- | --------- |
| 1      | なし     | x=51      | **x=110** |
| 2      | x=51     | x=119     | **x=178** |
| 8      | x=51     | x=119     | なし      |

1ページ目で「次へ」を押した来訪者が同じ場所をもう一度押すと、2ページ目では「2 / 8」の手前の何もない場所に当たる。§12「位置の一定——同じ働きのコンポーネントは、どのページでも同じ位置・同じ形にある」に反する。変更前は無効の `span` が場所を取っていたので、この害はこのコミットで生まれた。

押しても何も起きない項目を並べないという判断そのものは妥当である。端は §6 の「無効」（条件が揃えば実行できるもの）には当たらない。ただし、置かないことと、場所を詰めることは別である。

**直し方**: 端では、項目の代わりに同じ幅の空きを置く。例えば、`aria-hidden` を付けてフォーカスを受けない、見えない場所取りである。そうすれば「前へ」「番号（または n / N）」「次へ」の位置が、どのページでも同じになる。index.md の T3 の行に「一覧の設計でこれを見直す」とあるが、害を出しているのはこの部品なので、この部品で直す。T3 に残すなら、「端のページと隣のページで『前へ』『次へ』の x が同じ」を T3 の完了の条件として書く。

### Major-3 プライマリでないボタンの字が、コンテンツの左端から 11px 右にずれる

`.button` は、無効のときの破線の幅（3px の透明なボーダー）と左右 8px の余白を持つ。プライマリは反転の箱が見えるので、箱の左端がそろって見える。プライマリでないボタンは箱が見えず、下線の付いた字だけが見える。そのため、字が左端から 11px 右に置かれて見える。例を挙げる。

- 共有のボタン: どの道具とブログの記事にも出る。「X でシェア」が見出しと本文の左端より右から始まる（`/tools/date-calculator` の 1280px、storybook の ShareButtons の 375px dark）。
- storybook の Button: 320px で、有効な「結果をコピー」は無効の破線の箱と縦に並ぶ。有効な字だけが右にずれる。
- 道具のボタン: 「今日に設定」、cron-parser のプリセットの列など。

§5「コンテンツ幅の左端は、どのページでも同じ位置。すべてそこから始まり、右にだけ伸びる」に反する。一覧の行の 8px のずれは index.md の T3 に送ってあるが、ボタンはどのタスクにも送られていない。

**直し方**: プライマリでないボタンは、見える字の左端を並びの左端にそろえる。例えば、先頭のボタンだけ箱を左へ出す負の余白を持たせる方法がある。字の後ろの余白と破線の幅をそろえる方法もある。そのうえで、hover の線・リング・無効の破線が左の隣（コンテナの余白）に収まることを 320px で確かめる。一覧の行と同じ決め方（T3）にそろえるなら、その決め方を先に決めて、両方に掛ける。

### Minor-3 `DESIGN.md` §6 の表に、プライマリでないボタンの行が無い

`default` を下線にした判断は、§6 から導ける。冒頭の文は、押すとそのページで何かが実行されるものに「下線か反転を必ず持つ」ことを求める。反転はプライマリの1つに限られる。すると、ほかの実行するボタンは下線を持つしかない。「下線は、進むもの・実行するものの専有」にも合う。だから判断は正しい。

ただし、§6 の表には「プライマリボタン」と「リンク・一覧の行・ページ送り」の行しかない。プライマリでないボタンの見え方は、導出を経ないと分からない。T5 では、ページの CSS が独自に持つボタン（約80件）をこの部品に寄せる。そのとき各 builder が同じ導出をやり直すことになり、解釈がぶれる。§6 の表に「プライマリでないボタン——下線（細い線と同じ太さ）」の行を足し、リンクと同じ見え方であることを明記する。

### Minor-4 ページ送りの番号を畳む幅を、480px から `45rem`（720px）に広げた理由が無い

変更前は 480px 以下で番号を畳んでいた。変更後は 720px 未満で畳むので、480〜720px の端末（大きい電話の横向き・小さいタブレット）では番号で飛べなくなった。畳むと、最初のページと最後のページへ直接行く手段も消える。番号の並びは `flex-wrap: wrap` になって 320px でも折り返して入るので、畳む必要そのものが薄れている。畳む幅を決めた理由（§4 の段の切り替えにそろえた、など）をサイクルの文書に書き、来訪者が失う操作と比べて決め直す。

### Minor-5 button モードのページ送りで、端に着くとフォーカスが失われる

button モードでは、「次へ」を押して最後のページに着くと、フォーカスを持っていた「次へ」が DOM から消える。そのため、フォーカスは `body` に落ちる。いまこのモードを使うのは storybook だけなので、来訪者への害はまだ無い。Major-2 の場所取りで直すときに、フォーカスを押したボタンの場所（場所取りか現在地）に残すように作る。

### Minor-6 FileDropZone（`role="button"`）に hover の線が出る

グローバルの hover が `[role="button"]` を拾うので、ファイルを選ぶ欄にも内側の線が出る。この部品は `--accent` の枠を hover で出す規則も持つので、2つが重なる。ファイルを取り込む口が §6 の「選ぶ欄」（hover で見え方を変えない）か「実行するもの」かは、入力を扱う次のタスクで決め、その判断で hover の扱いをそろえる。
