## 指摘

### 1. §4 に書く「ボタンの面の字」の理由が、算術として成り立たず、範囲の外としたコントロールに当たる

4-4 と5章の §4 の行は、理由を次のように書く。

> ボタンは面の字を縁（反転の地・hover の線・フォーカスのリング）の内側 8px に置くので、本文の行間では2行に折れた面の行のあいだが縁までより広くなり、1つの面が縁の中で2つの名前に見える。

4-4 の算術は「行のあいだの空き（約 14px）が縁までの 8px より広く」「1.4 では行のあいだの空き（約 7px）が縁までより狭く」（(1.85−1)×17 と (1.4−1)×17）である。ここで比べている2つの長さは、測り方が違う。

- 「行のあいだの空き」(L−1)×17 は、字の四角から次の行の字の四角までで、上下の行の半分の行送り（half-leading）を2つ含む。
- 「縁までの 8px」は `padding-block` で、縁から**行の箱**までである。字の四角までは、そこにさらに半分の行送り (L−1)×17÷2 が足される。

同じ測り方（字の四角から）でそろえると、次のとおりになる。

| 組み                                                                | 縁から字まで       | 行のあいだの字どうし | 行のあいだは縁までより   |
| ------------------------------------------------------------------- | ------------------ | -------------------- | ------------------------ |
| ボタン・行間 1.4（`padding-block: 8px`）                            | 8＋3.4＝**11.4**   | **6.8**              | 狭い                     |
| ボタン・本文の行間 1.85（`padding-block: 8px`）                     | 8＋7.2＝**15.2**   | **14.45**            | **ほぼ同じ（やや狭い）** |
| アコーディオンの行・1.85（`padding-block: (44px − 1lh)/2`＝約 6.3） | 6.3＋7.2＝**13.5** | **14.45**            | **広い**                 |

（17px の字。Noto Sans JP の上下の余白の偏りを入れても、上 16.2・下 14.3 対 14.45 で、ボタンの 1.85 は「ほぼ同じ」のままである。）

したがって、

- ボタンを本文の行間で組んでも、「行のあいだが縁までより広くなる」ことは起きない。§4 に書く文の中心の主張が事実と違う。
- その条件が実際に起きるのは、4-4 が「この理由の外にある」とした、`padding-block: max(0px, (44px - 1lh) / 2)` で1行目を中央に置く組みのほうである。§4 に書けば、`DESIGN.md` がアコーディオンの行を自分の理由で否定することになる。第3回の指摘1 (c) の「理由がこの行の外のコントロールにも当たる」が、向きを変えて残っている。
- 同じ組みは、4-4 が挙げる `ListControls` の `.toggle` と `DisclosureRow` のほかに、`Accordion.module.css:10`（§6 のアコーディオンそのもの）・`ChoiceRow.module.css:11`（ラジオボタンとチェックボックスの行。hover の線とリングを行に出す）・`KeigoReferenceTile.module.css:80` にもある。4-4 の「直す行は起こさない」の判断は、この5つについて下す必要がある。
- 「フォーカスのリングの内側 8px」も事実と違う。部品のリングは縁の内側に出る（`--focus-ring-offset: -3px` の外の輪と、6px の `--paper` の塗り。`globals.css` 387〜388行）。リングの内側の縁から行の箱までは約 2px である。
- 「1つの面が縁の中で2つの名前に見える」は、測りも撮った像も無い言い切りである。§4 の文は来訪者の見え方を決める規範なので、推論を事実の形で書かないこと（AP-P32）。

直すこと: 次のどちらかを選び、4-4 と5章の §4 の行をそろえること。

- (A) 近さを理由にするなら、字の四角でそろえた算術（上の表）で書き直す。その理由はアコーディオンの行・`ChoiceRow` などにも当たるので、範囲を「コントロールの名前」に広げるか、当たらない理由を別に示す。広げるなら、1.85 で組んでいる5つを直す行を T5a か backlog に起こす。
- (B) 近さを理由にしないなら、ボタンに本当に固有で、上の算術と食い違わない理由を書く。見つからなければ、1.4 を選ぶ根拠を撮った像で比べて示す（2行に折れたボタン・選択肢を 1.4 と 1.85 で撮る）。

どちらでも、「リングの内側 8px」を実際の組み（縁、または行の箱の内側 8px）に直すこと。

### 2. 切り替わりの `useLayoutEffect` が、ページを開いた直後の開始の画面と、「もう一度挑戦する」のあとの開始の画面を分けていない

4-7 は、送りとフォーカスを「画面（段階・いまの問・その問の答えの有無）が変わったときに」`QuizContainer` の1つの `useLayoutEffect` で行うと決め、その範囲に「「もう一度挑戦する」のあとの送りとフォーカス」（`scrollY = 0`・「はじめる」へのフォーカス。4-8）を入れている。ところが、やり直したあとの状態（段階＝開始・番号 0・答えが空）は、ページを開いた直後の状態と同じ値である（4-3 の reducer の表）。

段階などを依存に持つ `useLayoutEffect` は、マウントのときにも走る。区別を書かずに実装すると、ページを開いただけで「はじめる」にフォーカスが移り、ページの頭へ送られる。検索から着いた来訪者のページの途中へのリンク（`#faq` など）や、戻る操作の位置の復元を壊し、読み上げでは開いた直後にページの頭でなく「はじめる」を読む。いまのコードは、結果の段階へはページを開いただけでは進めないことでこれを避けている（`QuizContainer.tsx` 72〜74行の説明）が、開始の画面にはその守りが効かない。

直すこと: この `useLayoutEffect` が、来訪者の操作で起きた切り替わりのあとだけに働き、マウントのとき（ページを開いた直後と bfcache から戻ったとき）は送りもフォーカスも行わないことを 4-7 に書くこと。6章 条件5 か条件6 に、「ページを開いた直後（`scrollY=0` と、`#` 付きの URL で途中に着いたとき）に、`document.activeElement` が `body` のままで、送りが起きない」ことを加え、jsdom の試験にも入れること。

### 3. 8章の入口と「見せる範囲を広げる」の文に、名前を範囲の条件に入れる前の文が残っている

第3回の指摘3を受けて、結果の名前の下端が画面に入ることは、見せる範囲の条件そのものになった。名前が画面から外れるのは、範囲が空になって s0 にしたときだけで、4-9 はそれを決め方の中で扱い、条件7 は「その旨と値を記録する」としている（合否には入れていない）。

ところが 8章は、PM の道の入口に「または結果の名前が画面から外れるとき」を残し、「見せる範囲を広げる」の道に「見せるものが画面に入る量が減るので、結果の名前が見えることを条件7 で確かめ直す」と書いている。

- 範囲を広げても、名前の条件は範囲に掛かったままなので、広げたことで名前が外れることはもう無い。「確かめ直す」は前の決め方の名残である。
- 入口の「名前が外れるとき」に当たるのは範囲が空の場合だけだが、4つの道はどれもこの場合に効かない（第3回の指摘3で挙げたとおり）。入口だけがあって、選べる道が無い。

直すこと: 入口から「結果の名前が画面から外れるとき」を外し、「見せる範囲を広げる」の後半の文を消すこと。範囲が空の場合（ボックスの上端から名前の下端までが画面の高さ − 16 を超える）を受け入れるのか、PM に渡すのかは、4-9 の結果の箇条で1つに決めること。あわせて、4-9 の「名前だけで画面より高く範囲が空になるとき」は、実際には「ボックスの上端から名前の下端まで（名札を含む）が画面の高さから上下の 8px を除いた高さを超えるとき」なので、そのように書くこと。

### 4. 知識の文書に書く React の文が、文書の「may」を言い切りにしている

5章の `docs/knowledge/` に足す文は、「クリックのような操作の中で起きた更新の `useEffect` は塗る前に流される」と書く。react.dev の文書は「If your Effect is caused by an interaction (like a click), React **may** run your Effect before the browser paints the updated screen」で、さらに「Even if your Effect was caused by an interaction (like a click), React may allow the browser to repaint the screen before processing the state updates inside your Effect」と断っている。知識の文書は次のサイクルでも事実として読まれるので、文書が保証していないことを言い切らないこと。

直すこと: 「塗る前に走ることがある（react.dev は may と書く）」とし、続く「切り替えがクリックの中で起きていたあいだは問題が見えず」を「見えにくく」にすること。結論（切り替わりのあとのフォーカスと送りは `useLayoutEffect` に置く）は変わらない。4-7 の「いまのコードでは診断の最後の答えはクリックの中で結果に移るので、これは T5a のタイマーが持ち込むもの」も、同じ程度の言い方（持ち込む、または目立たせる）にそろえるとよい。

### 5. PM が足す行の6が、index.md に無い行を置き場に指している

PM が足す行の6は、置き場を「index.md の、T5 の辞典の面のタスク（四字熟語辞典の詳細）とツールの面のタスクの行か、PM の決定の記録」とする。index.md には T5 の1行しか無く、面ごとのタスクの行は t5-design.md 10章の表にある。四字熟語の詳細は **T5-11**（`YojiDetail`）、道具の頭と `ErrorBoundary` は **T5-17** である。

直すこと: 置き場を「t5-design.md の T5-11 と T5-17 の行（その中身に、見出しの行間を §4 に合わせることを足す）」のように、実在する行とタスクの名で名指しすること。t5-design.md を PM が書き換える形にするのか、index.md の PM の決定の記録に T5-11・T5-17 への申し送りとして書くのかも、1つに決めること。
