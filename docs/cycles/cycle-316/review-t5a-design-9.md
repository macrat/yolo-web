## 指摘

### 1. §6 の冒頭の定義は「押してから実行が終わるまで、同じ下線か反転を持ったままでいる」と言うが、サイトのボタンには、押してから実行が終わるまで無効の形になるものがある

5章が §6 の冒頭の1つ目の定義に書き入れる文（444行）:

> 押してから、ページが開くか実行が終わるまでのあいだ（実行のさいちゅう）も、同じ下線か反転を持ったままでいる。

これは §6 の土台で、リンク・一覧の行・ページ送り・ボタンのすべてについての決まりになる。いまのコードでは、次のボタンがこれを満たさない。

- `src/play/games/kanji-kanaru/_components/GuessInput.tsx:115` と `src/play/games/yoji-kimeru/_components/GuessInput.tsx:110` の「送信」は、プライマリボタン（反転）で、押してから推測の判定が終わるまで `disabled={submitting}` になる。`Button.module.css` の `.button:disabled` は、反転を外して（`background: transparent`）太い破線の枠と `--ink-2` の字にする。面の字も「送信中……」に替わる。押してから実行が終わるまでのあいだ、反転を持っていない。
- 同じ2つは、§6 の「無効」（条件が揃うまで実行できないもの・理由を字で添える）の形を、実行のさいちゅうに使っている。書き入れる定義のもとでは、この2つは `DESIGN.md` に反する面になるが、文書はそれに触れず、どのタスクが直すかも決めていない。

依頼の条件（サイトのリンクとボタンが持たないふるまいを主張しない）に当たる。加えて、冒頭の定義は操作の種類を分ける土台なのに、1つの面の例（「診断で押した選択肢は、次の問が出るまで下線を持つ」）を名指しで持つ。§6 の箇条（465行）が同じことを言っており、土台の中に特別な場合を足した形になる（ツギハギ禁止）。

直すこと: どちらかを選び、選んだ形で冒頭の定義・4-2・§6 の箇条をそろえる。

- (a) 冒頭の定義はいまのサイトが持つことだけを言う。たとえば、実行のさいちゅうを「押したものの印を持ったまま」とする決まりを、実行のあいだ面を残すもの（リンク・診断の選択肢）に限って言い、無効の形に替えるボタンを含めない。診断の例は冒頭の定義から外し、§6 の箇条に置く。
- (b) サイトの全体の決まりにするなら、ゲームの「送信」2つが決まりに反することを 8章に書き、直すタスク（T5 の該当の面か backlog）を「PM が足す行」に入れる。直すまで `DESIGN.md` と面が食い違うので、(b) を選ぶなら、その食い違いを置いておく理由も書く。

### 2. 診断で押した行の hover の線が、押した瞬間に消える。「実行のさいちゅう」は実行するものなのに、hover をどうするかが決まっていない

§6 は「hover は、進むもの・実行するもの・状態を変えるものに出る」と決めている。5章は、診断で押した選択肢を「実行のさいちゅう」として実行するものの側に数え、「押したリンクと同じ種類」とする。押したリンクは、次のページが出るまで hover の線も持ったままである。

一方この設計では、押した行はボタンから字の `span` に替わり、4-4 は押せる範囲を行へ広げる指定（`data-hit-area="after"` と `::after`）を `Button` の側にだけ置く。`globals.css` の行の hover の線は `[data-hit-area="after"]:hover::after` に出るので、押した行の字はこれを持たない。文書には hover の語が1-2 の表に1度出るだけで、押した行の hover を決めた所が無い。

実測（上の組み。押した行の上にポインタを置いたまま）:

| 状態                                                                    | 押した行                                                                                                                                    |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 押す前（`button`、ポインタが上）                                        | 行の左右に `--rule-2` の細い線（`::after` の `box-shadow`）                                                                                 |
| 押したあと、設計のとおり（`span`、`data-hit-area` なし）                | 線が消える。押す前の像と違う                                                                                                                |
| 押したあと、`span` にも `data-hit-area="after"` と `::after` を持たせた | マウスでは押す前の像とピクセル単位で同じ                                                                                                    |
| タッチ（`hasTouch`・`touchscreen.tap`）                                 | tap のあと `button` が hover になり線が出る。`span` に替えると、どちらの形でも線は消える（新しい要素はポインタが動くまで hover にならない） |

- マウスの来訪者には、押した瞬間に、押した行の枠が消え、同時にほかの行の下線が消える。4-2 と review-t5a-design-8.md が押した形の印とした「押した行だけが押す前のまま残る」が、押した行の側でも変わる。
- タッチでは、Chromium の再現では tap のあと押したボタンに hover の線が出ている。押した行を別の要素に替える限り、この線は消える。iOS の Safari の hover のふるまいは Chromium と同じでない（推論。T9 の実機で見る）。

直すこと: 見せている 150ms のあいだの押した行の hover を決めて、4-2・4-4・5章 §6 の箇条に書く。たとえば次のどれか。

- 押した行の字に `data-hit-area="after"` と `::after` を残し、ポインタが上にあれば押す前と同じ線を出す（マウスでは実測で同じ像になる。タッチでは消える件が残るので、その扱いも書く）。
- 押した行はボタンの要素のまま 150ms 残す（同じ要素なので下線・hover・フォーカスがそのまま続き、4-4 の下線の共有も要らなくなる）。この形なら、押し直しを reducer が捨てることを「押せる形のまま黙って捨てる」（R3・D1 で捨てた形）と区別する理由を書く。
- 線が消えることを受け入れるなら、それが §6 の hover の箇条と食い違わない理由を書き、条件3 の撮る像に「ポインタを押した行の上に置いたまま」の像を入れて目で見る。

どれを選んでも、条件3 に押した行の hover の見え方を加える。

### 3. §5・§6 のリングの範囲の文が、診断で押した行を含まない

第8回の直しで、「答えた選択肢」は「答えたあとの問の選択肢のうち実行のさいちゅうでないもの」と定義された（448行・452行）。診断で押した行は答えた選択肢でなくなった。一方、5章がリングの範囲について書く2つの文は、縁が見えるものの例を「答えた選択肢のうち押したものの行」とだけ言う。

- §5 コンテナ（436行）: 「縁が見えるもの（答えた選択肢のうち押したものの行）は、その縁の内側がリングの範囲になる」
- §6 の二重リングの範囲（456行）: 「縁が見えるもの（答えた選択肢のうち押したものの行）はその縁の内側である」

これは知識クイズの押した行だけを指す。診断で押した行も、4-2・4-7 のとおり 150ms のあいだフォーカスを受け、キーボードの来訪者にはリングが出る（4-7 の範囲、条件5 の毎フレームの記録）。その行はボタンでなく字の `span` を持つ `li` で、押せないがフォーカスを受けるものにあたるが、リングの範囲を決める文のどちらにも入らない。467行の §6 の箇条（「押した行は押せないがフォーカスを受け、二重リングは行の縁の内側に出る」）は両方を含む言い方なので、同じ `DESIGN.md` の中で範囲の言い方が食い違う。

直すこと: 436行と 456行の括弧を、診断と知識クイズの押した行の両方を指す言い方にする（たとえば「押した選択肢の行（診断の実行のさいちゅうのもの・知識クイズの答えた選択肢）」）。

### 4. 前の置き方の文が、3-1 の案1 と 4-2 の R2 に残っている

- 3-1 の案の表の案1（130行）: 「押すと、その問のどの選択肢も下線を外し、押したものに『あなたの回答』と添える。診断はこの形を 150ms 見せてから次の問へ」。いまの設計では、診断は字を添えず、押したものは下線を持ったままで、知識クイズの添える字は「あなたの回答は正解／不正解」と「正解」である。
- 同じ表の「再入力」の行の案1（140行）: 「見せているあいだは押しても何も起きず、下線が無いことで見える」。診断で押した行は下線を持ったままで、押しても何も起きない。「下線が無いことで見える」のはほかの行だけである。
- 4-2 の再入力の表の R2（208行）: 「どの行も下線の無い字にして押せないことを見せる」「押せない形は、§6 に加える『答えた選択肢』の形で、知識クイズで答えたあとの形と同じになる」。診断で押した行は下線を持ったままの「実行のさいちゅう」で、答えた選択肢ではない。

案の比べと採る扱いの見出しに前の置き方が残ると、4-2 と5章を読む前にそこを読んだ builder とレビューが、押した行の下線を外して実装・確認しうる。

直すこと: 3箇所を、いまの押した形（診断は押した行だけが下線を持ったまま、ほかの行は答えた選択肢。知識クイズはどの行も答えた選択肢で、正誤の字を名前の下に添える）で書き直す。

### 5. 7章 T5a-5 の `Button.module.css` の説明に、下線の共有が無い

4-4 の「下線も共有する」は、`.variantDefault` の下線の3つの宣言を1つの規則にまとめ、プライマリでない `Button` と押した行の字の両方が使う、とする。7章 T5a-5 の触るファイルの `src/components/Button/Button.module.css` の説明は「面の箱の規則を答えたあとの字と共有する形にまとめる」だけで、下線の規則を切り出すことが入っていない。T5a-5 の担当が表から作業を読むと落とし、押した行の下線を字の側で写すと、4-4 がそれを避けるために決めた、値の写しが生まれる。第8回の指摘6（globals の説明）と同じ類である。

直すこと: 説明に「`.variantDefault` の下線の宣言を、押した行の字と共有する規則にまとめる」を足す（指摘2 でボタンの要素のまま残す形を選べば、この項ごと要らなくなる）。
