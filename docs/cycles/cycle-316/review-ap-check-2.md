## 指摘（重い順）

### 重い1 「iOS の Safari の実機で確かめる」に実行する者も手段も無いまま、WebKit の確かめの受け皿にしている（AP-WF09・AP-WF23 の先送り、AP-WF02）

- しかし、この環境にも builder にも iPhone の実機は無く、Owner は作業をしない。このサイクルのレビュー自身がそれを指摘している（review-slider-spec.md の Major-1「builder もこの環境も iPhone の実機を持たないので、「実機で確かめる」は実行できない確認です。確かめられないまま…出荷されえます。SKILL.md の文も、今後のどの作業にも同じ実行できない確認を求め続けます」）。スライダーではそれを受けて「実機で確かめ、駄目なら処理を足す」を「処理を必ず足す」に改めたが、同じ判断がほかの項目とスキルに広げられていない。
- 来訪者への効き方: character-personality の結果に着く回数の約66%は WebKit である（t5a-design.md 22 行）。T9 に着いた時点で確かめる手段が無ければ、(a) 確かめないまま出荷するか、(b) 「確かめた」と書いて先へ進む（AP-WF23）かのどちらかになる。後続の約20のサイクルが、近似できない差を見つけるたびにこの受け皿へ送り続ける。
- 直すこと（PM が決め、planner が文書を直し、スキルは builder）: (1) T9 の「実機」の各項目を、実行できる形のどれかに振り分けて carryover.md の T9 と decisions.md の該当の行に書く。振り分け先は、(i) 端末の振る舞いに頼らない作りにして確かめを要らなくする（スライダーの例。`touch-action: manipulation` を必ず掛ける、など）、(ii) コンテナで決まりに反せずに確かめられる近似に置き換える、(iii) 確かめられない危険として受け入れ、出荷のあとに GA のブラウザ別の数（離脱・完走・共有）で見張る項目と撤退の線を T10 の ADR009 に書く、のいずれか。実機を使える手段（外部のサービスなど）を得られるなら、その手段と誰が使うかを書く。(2) `frontend-design` スキルの4を、(i)〜(iii) の振り分けを求める文に直す。(3) decisions.md 125 行の「近似できない所は T9 が実機で確かめる」を、(1) の結論に合わせる。

### 中1 incident-1 の再発防止が、セッションをまたいで残らない（前回の重い2と同じ型）

- incident-1 は、原因に「`stop-cycle-guard.sh` の差し戻しの文面は「作業が残っているなら、続けてください」で、サブエージェントを待っている状態をどう扱うかは書かれていない」を挙げる。hook の文面はいまも同じで、「何が正しかったか」（何も出さずにターンを終える・完了は通知で届く）は cycle-316 の文書の中にしか無い。オーナーの規則のとおり AP には書けない（待った時点で害が出ている）ので、担保は hook か手順書にしかない。

- incident-1 に「再発防止」の節を足し、担保した先（hook・knowledge）を指す。「待機のコマンドは数十回になった（本セッションの記録で確かめられる）」は、後から読む者が確かめられないので、数を書けないなら「記録はリポジトリに残っていない」と添える。
