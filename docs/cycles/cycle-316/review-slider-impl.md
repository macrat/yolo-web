## 指摘

### Critical

なし。

### Major-1: 溝のほかの幅の見積もりが、数字でない半角の字と一部の仮名で小さすぎ、T5 で道具に使うと、溝が 5rem に届かないまま1行で組まれ、Web フォントを読んだあとに溝と − 値 ＋ が動く

**しくみ**: `textEm` は、U+0000〜U+024F の字をどれも 0.6em、ほかを 1em と見積もる。一方、値の列の幅は `min-width: var(--slider-value)` で、実際の字がそれより広ければ、列は実際の字の幅まで広がる。

- イロドリの数字だけの値（0.6em の等幅の数字）では、見積もりと実際が一致する。1行の組みの溝の長さが、入れ物の幅（コンテナクエリが問う幅）とちょうど等しかった（89.38 と 89.39）。
- 数字でない字では、見積もりが実際より小さい。次の値は、17px の本文の字で測ったものである（`glyph.cjs`）。

| 字                   | 見積もり | Web フォントを読んだあと | 読む前（代わりの書体） |
| -------------------- | -------- | ------------------------ | ---------------------- |
| 「%」                | 0.6em    | 0.927em                  | 0.89em                 |
| 「100%」             | 2.4em    | 2.727em                  | 2.558em                |
| 「パスワードの長さ」 | 8em      | 8.141em                  | 8.141em                |

**来訪者に起きること**: 画像のリサイズの品質（ラベル「品質」、値 10〜100%、刻み 5）を部品が組むときの値で、イロドリのページに当てて測った（`pct.cjs`）。

- 322〜326px の幅では、コンテナクエリは溝を 81〜85px と見て1行で組む。しかし実際の溝は 75.63〜79.63px で、5rem（80px）に届かない。§6 の「1行の組みで溝が 5rem に届かないときは、並び全体を2行の組みにする」に反する。
- Web フォントを止めたときの溝は 78.5〜82.5px で、読んだあとより 2.9px 長い。フォントの差し替えのあとで溝が縮み、− と値と ＋ が約 3px 動く。200% では差が約 6px になる。「組みは最初の描画から決め、開いた直後に替えない」と、値の場所を固定して「指の下でつまみがずれない」ようにした狙いが、「%」を持つ値で崩れる。
- コードの注記もこれと合わない。`NARROW_CHAR_EM` の「半角の字（数字・記号・欧字）… 0.6em」と、`.value` の「Web フォントを読む前も後も変わらない」は、「%」では成り立たない。
- 画像のリサイズの品質は、T5 でこの部品にする所として index.md に書いてある。パスワードの生成の値（「128」）は数字だけで、この問題に当たらない。ラベル（「文字数」「品質」）は短く、長いラベルで大きく誤ることは無かった。ただ、仮名の多いラベルでは 1〜2% 小さく見積もる。

**直し方の向き**: 溝のほかの幅を、どの書体でも実際より小さくならない見積もりにする。そのうえで、ラベルと値の列を、その見積もりの幅に固定する（値の列は `min-width` でなく幅で持つ）。こうすると、1行の組みの溝の長さが、どの字でもどのフォントでも、入れ物の幅と等しくなる。

- 等幅の数字だけを 0.6em にする。
- ほかの半角の字は、字ごとの上限（例: 「%」や大文字の欧字は 1em）で数える。
- 仮名は、1em を超えうる分を見込む（または、ラベルの列だけは実際の幅で取り、閾値にその上限の差を足す）。
- `textEm` と `--slider-fixed` に単体のテストを足す（数字・「100%」・「1.5 MB」・仮名のラベル）。Playwright で、「%」を持つ値の閾値の前後を、フォントを止めたときと読んだときの両方で確かめる。

### Minor

**Minor-1: 値の字が、− と ＋ の押せる範囲に接していて、hover の線・無効の破線の枠・フォーカスのリングが数字に触れる**

- 375・1280px の「100」の右端は、無効の ＋ の破線の枠に接している。1280px で hover した ＋ の枠も、「291」の「1」に接する（`shots/sl-375-16-light.png`・`sl-1280-32-dark.png`・`hover-inc-1280.png`）。
- §6 は「溝の押せる範囲・−・値・＋ は接して並べる」とする。一方で、§5 はラベルを「コントロールでないので 8px あける」としている。値もコントロールでない字なので、同じ考えなら、値と − ＋ の押せる範囲のあいだを 8px あけることになる。
- DESIGN.md の文を planner が見直し、値の左右に 8px を取るかを決める。取るなら、見積もりの 112px も 128px に変える。

**Minor-2: − と ＋ が、刻みの格子に値を揃えない**

- `step` は `item.value ± step` を min と max で挟むだけである。刻みの格子から外れた値（刻み 5 で 82）では、＋ が 87 にする。ネイティブの矢印のキーは 85 にするので、− ＋ とキーで行き先が食い違う。
- 小数の刻みでは、0.1 + 0.2 のように浮動小数の誤差を持つ値を使う側に渡す。
- いまの使い手（1刻みと、10 から 5 刻み）では起きない。ただ、共有の部品なので、ネイティブと同じく `min + round((v − min) / step) * step` に揃え、テストを足す。

**Minor-3: `trackPositionPx` は、本番のコードで使われていない**

- `index.tsx` から書き出されているが、使うのはテストだけである。
- テストは `trackPosition` の文字列と `trackGradient` で足りる。もし px の対応を残すなら、本番の関数がそれを使う形にする。

**Minor-4: index.md の T5 の行の、画像のリサイズのボタンの位置は、読み込んだ画像で変わるのに、その画像が書かれていない**

- パスワードの生成は、320px で 773.4→801.4、375px で 685.4→713.4 だった。書かれた数（773→801・685→713）と一致する。
- 画像のリサイズは、320×667 の PNG を読み込み、JPEG を選んで測ると、320px で 1529.2→1547.3、375px で 1350.0→1368.1 だった。書かれた数（1413→1431・1275→1293）とは違うが、下がる量（+18）は一致する。
- 数を読んだ T5 の担当が同じ数を再現できるよう、読み込んだ画像の大きさを書き添えるか、「約 18px 下がる」と差で書く。
- どの条件でも 667px の最初の画面の外にあることは、書かれたとおりである。
- 画像のリサイズの値「80%」は、320px ではスライダーの下の行に折れる。これは親でも同じで、この変更で起きたものではない。T5 の組み直しで消える。

**Minor-5: builder が決めて記録することになっていた3つが、サイクルの文書に無い**

t4-design.md の builder の項目3が、次の3つを「決め、記録する」としている。

- − と ＋ で変えた値を、使う側の処理を直に呼んで渡すこと
- スライダーにフォーカスがあるときは知らせないこと
- 1行と2行の切り替えを、入れ物の幅を「並びの幅 − 見積もり」にしたコンテナクエリで組むこと

どれも部品の頭の注記には書いてあるが、t4-design.md（スライダーの定めの節）には無い。(a)〜(k) の結果もどこにも残っていない。Major-1 を直すときに、見積もりの考え方と合わせて、t4-design.md の節に書き足す。

**Minor-6: この確かめの環境で確かめられないもの**

- 今回の測りは Chromium だけである。Firefox の `::-moz-range-*` と WebKit（iOS Safari）で、溝の線・つまみの中心の対応（§6）・2行の組みが同じになるかは、このコンテナでは確かめられない。t4-design.md も、Firefox は実装のレビューで確かめるとしていたが、使えるブラウザが無かった。確かめられていないことを、t4-design.md に残しておく。
- 知らせを出さない条件は `document.activeElement === input` である。読み上げの仮想カーソルが DOM のフォーカスを動かさない読み上げ（NVDA のブラウズモードの既定など）では、フォーカスがスライダーに残ったまま − を押すことがある。そのとき新しい値が読まれるかは、実機でないと分からない。これも、確かめていないこととして記録に残す。
