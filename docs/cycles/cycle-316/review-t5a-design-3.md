## 指摘

### 1. §4 に足す「コントロールの面の字」の行が、範囲も理由も既存のものと合わない

grep の結果（`src` の CSS の `line-height: 1.4`。1.4x を除く）は8か所で、4-4 の数と合う。しかし中身は「コントロールの面の字」ではない。

| ------------------------------------- | ------------------------------------ | ---------------------------------------------------------------- |
| `Button.module.css:18`                | ボタン                               | はい                                                             |
| `CopyButton.module.css:50`            | ボタンの面の字の場所を取る見えない箱 | はい（ボタンと同じ組み）                                         |
| `ResultPageShell.module.css:69`       | `.tryButton`（反転の誘い）           | はい                                                             |

したがって、4-4 の「すでにある8か所の `line-height: 1.4`（`Button` など）を後から書き起こすもので、見た目は変わらない」は事実と違う。書き起こすのは3か所である。残る5か所のうち見出しの2か所は、むしろ §4 の「見出しは行間 1.25 以下」から外れている。

行の文そのものにも3つの問題がある。

- **(a) 語が既存の語と重なる。** §4 はすでに「**コントロールの名前**（ボタンの面の字と、入力欄・ラジオボタン・チェックボックス・スライダー・アコーディオンのラベル）」を定義している（HEAD の 115行）。新しい「コントロールの面の字」は、その語と「ボタンの面の字」のあいだに3つ目の語を作る。読み手は、アコーディオンのラベルも入るのかを決められない。
- **(b) 括弧の「ボタン・問に答える選択肢」は、選択肢をボタンの外に置く。** §6 に足す箇条と 4-1 は、選択肢を「押すと回答が決まるボタン」と決めている。並べると、選択肢がボタンでないように読める。
- **(c) 理由が、この行の外のコントロールにも当たる。** 理由は「面の字は1〜3行の名前で、本文の行間では2行に折れた面の行どうしが離れて2つの名前に見え」る、である。しかし `ListControls` の並び順の開閉と `DisclosureRow` の開閉の行は、どちらも `<button>` で、1〜3行に折れる名前を本文の行間 1.85（`--leading-body`）で組んでいる。目次のリンクも「2行に折れた項目が続いても境目が分かるよう、項目の中の行間を詰め」ると、同じ理由で 1.4 にしている。この理由を §4 に書くと、アコーディオンの行が §4 に反するように読める。反さないのなら、理由がボタンに固有でない。どちらにしても `DESIGN.md` が自分と食い違う。

直すこと:

- 行の語と範囲を、既存の語に合わせて決める。例: 「**ボタンの面の字**（問に答える選択肢も、押すと回答が決まるボタンなのでこれに従う）」。
- 理由を、その範囲に固有のものにする。例: ボタンは面の上下に 8px をあけて縁や地の中に字を置くので、行間を開くと、1つの面の中の行のあいだと面どうしのあいだが近づく。アコーディオンの行などのほかのコントロールも同じ理由で詰めるべきだと判断するなら、範囲を「コントロールの名前」に広げ、1.85 で組んでいる `ListControls`・`DisclosureRow` を直す行を T5a か backlog に起こす。どちらを採るかと、その理由を 4-4 に書くこと。
- 4-4 の「8か所」の文を、書き起こす3か所（`Button`・`CopyButton` の場所を取る箱・`ResultPageShell` の `.tryButton`）の事実に直すこと。見出しの2か所が 1.25 を超えていることは、この設計の範囲の外なので、PM に渡すか backlog の行にすること。

### 2. タイマーで起きる切り替わりでは、見出しへのフォーカスと結果への送りが塗ったあとに走りうる

R2 で、診断の答えから次の問（と、最後の答えから結果）への切り替わりは、150ms のタイマーの中で起きる（4-3）。クリックの中では起きなくなる。React の文書は `useEffect` について、「クリックのような操作で起きたのでない Effect は、ふつう、ブラウザに更新した画面を先に塗らせてから走らせる」と書いている（react.dev の `useEffect` の文書）。いまのコードの2つの処理は、どちらも `useEffect` にある。

- **問の見出しへのフォーカス**: `QuestionCard` がマウントのときに `useEffect` で移す。4-7 は「どれもいまのコードと同じ動き（`QuestionCard` がマウントのときに見出しへ移す）」と書いている。診断では、見せているあいだフォーカスは押した行（`li`）にある。次の問の描画で行が外れると、フォーカスは `body` に落ちる。見出しに移るのは、塗ったあとになりうる。6章 条件5 の「`BODY` だったフレームが 0」を、書いたとおりに作ると満たさない。条件で見つかるにしても、設計が「いまと同じ」と言ったまま builder に直させるのは筋が違う。
- **結果への送りとフォーカス**: いまは `QuizContainer` の `useEffect`（77〜83行）にある。4-9 の結果の行は送りの量を決めているが、いつ送るかを決めていない。タイマーで結果に移ると、結果の画面がもとの送りの位置で1フレーム塗られ、そのあと跳ぶことがありうる。§11「1つの操作に応える動きは1つだけ」から外れ、来訪者にはちらつきとして見える。いまのコードでは、診断の最後の答えはクリックの中で結果に移るので、この問題は T5a が持ち込むものである。

4-5 は、問のまとまりの送りを「塗る前（`useLayoutEffect`）」と決めている。同じ決まりを、切り替わりのあとのフォーカスと送りのすべてに広げること。範囲は、問の見出しへのフォーカス（3つの切り替わり）、結果への送りと着地とフォーカス、「もう一度挑戦する」のあとの送りとフォーカスである。あわせて、誰がそれを持つか（`QuestionCard` のマウントか、`QuizContainer` の送りのすぐあとか。4-7 の「送りを先に、フォーカスをあとに」との順も）を決め、4-7 の「いまのコードと同じ動き」を直すこと。試験には、偽の時計で 150ms 進めた切り替わりのあと、塗る前（同じ task の中）に `document.activeElement` が見出しであること、結果の送りが済んでいることを入れること。これは React の挙動についての知見なので、T5a-7 で `docs/knowledge/` に書くことも勧める。

### 3. 結果の名前が見えることを、見せる範囲の決め方に入れる

4-9 と §8 に書く文は、結果のボックスの上端を 8px 〜 画面の高さの 1/3 にある範囲で選ぶ。§8 の文は「上端を 1/3 までに置けば、結果の名札と名前は画面の上のほうに残り」と言い切っている。一方で 4-9 は、200% と 740×360 では確かめていない（推論）と書いている。結果の名前が見えるかは、条件7 で測って確かめるだけである。

8章は「結果の名前が画面から外れるとき」を PM の道の入口に挙げている。しかし4つの道のどれも、この件には効かない。

- 見せる範囲を広げると、名前はもっと下へ行く。
- 組みを直すのは、2打目が落ちた押せるものについての道である。
- 第2の組を外すのは、次の問の選択肢についての道である。
- 件を受け入れるのは、開閉するものに限っている。

名前が見えることは、測って祈るものではなく、決め方で守れる。見せる範囲の結果の行を「ボックスの上端が画面の上端から 8px 以上で、画面の高さの 1/3 以下、かつ**結果の名前（見出し）の下端が画面の下端から 8px 上より上にある**送り」とすること。4-9 の表、4-9 の結果の範囲の箇条、§8 に書く文、条件7 をそろえ、§8 の文の言い切りをこの決め方に合わせること。範囲が空になる場合（名前だけで画面より高いとき）は s0（上端 8px）にする、と書くこと。

### 4. §8 の着地の箇条の頭が、診断の答えを落としている

§8 に足す着地の箇条は、頭で操作を「「はじめる」・知識クイズの答えと「次へ」・最後の答え・「もう一度挑戦する」」と挙げる。この並びは、最後でない診断の答えを含まない。ところが同じ箇条は、あとで「診断で答えて次の問へ移るときは、次の問の選択肢を避けない」と書く。4-9 の冒頭と表も、診断の答えを押した点の下が入れ替わる操作に入れ、送るときには距離で FAQ などから遠ざける。

頭の並びを「「はじめる」・答え（知識クイズでは「次へ」も）・「もう一度挑戦する」」のように、診断の答えを含む形に直すこと。スキルの文には操作の並びが無いので、直さなくてよい。

### 5. 知識の文書の新しい冒頭の段落が、読み手には自分と食い違って見える

5章が示す `input-events-and-guards.md` の第2段落は、次の順で書かれている。

1. 「cycle-301 で試した修正（**状態更新の冪等化**・時間ガード・`pointer-events` の窓・retry 後の intro へのスクロールとフォーカス）は、正味で来訪者のためにならないとして取り消された」
2. 「いまのコードは…次の形で2打目を扱う。**状態の更新の冪等化**…」「「もう一度挑戦する」のあとは開始の画面を頭から見せ、フォーカスを「はじめる」に移す」

読み手には、「来訪者のためにならない」とされたものが、そのまま戻っているように読める。

cycle-301 の index.md「サイクルの結末」によれば、正味でマイナスとされたのは変更の全体である。増えた害として挙がっているのは、600ms の無言棄却と、retry の2打目が X の投稿画面へ落ちることの2つだった。冪等化そのものは害として挙がっていない。一文目は、取り消されたことの理由を、冪等化にも掛かる形で言っている。

次のように書き直すこと。

- cycle-301 の変更はまとめて取り消されたこと。
- 増えた害は、時間ガードの無言棄却と、retry のあとの送りで2打目が X の投稿へ落ちたことだったこと。
- いまのコードは冪等化を持ち直した。押した形を見せ、時間の窓で捨てない。retry のあとの送りは、着地の選び方で押した点の真下を避ける。この2つが、cycle-301 と違う所であること。

### 6. 「送るとき」に第1の組を避けられないときの括弧書きが、手順と合わない

4-9 の手順5 の後ろの文は、「範囲の中に真下の第1の組を避ける送りが無ければ、s0 のままにする（送るときは、第1の組からいちばん離れる送り）」と書く。しかし d1 は「点が矩形の上なら 0」と決めている。どの送りでも点が第1の組の上にあるなら、d1 はどれも 0 で、「いちばん離れる」は決まらない。手順5 の比べる順どおりなら、選ばれるのは d2 が大きく、s0 に近い送りである。

括弧書きを、手順5 が実際に選ぶもの（「d2 と s0 への近さで選ぶ」）に直すこと。第1の組の中での位置（縁への近さなど）で選び分けたいなら、その量を定義すること。
