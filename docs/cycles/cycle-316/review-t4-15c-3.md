### `keydown` の受け手

- ページを開いたとき、検証の結果（`kind` を持たないボックス）を出したとき、誤りを出したときは0個。整形・圧縮の結果を出すと1個。整形から検証に替えると0個に戻り、整形を押し直して箱を出し直しても1個のまま。`kind` の箱が無いページには受け手を置かず、外すときに漏れない。
- 設計は妥当と判断する。Chromium はフォーカスの知らせより先に着いた所を画面に入れる送りを済ませるので、送る前の位置を知る手は Tab の `keydown` しかない。`focus({ preventScroll })` はブラウザが動かすフォーカスには使えない。受け手は `kind` の箱があるあいだだけ捕獲の段で1つ置き、時刻で古い記録を捨てるので、ほかの面の Tab の扱いに触れない。これより簡単で正しい方法は見当たらない。

## 走査の確かめ

`findJsonErrorPosition` を、乱数で作った正しい JSON（入れ子・空白・タブ字下げ・逃がし・絵文字・対の無いサロゲート・前後の空白）と、それを1〜2か所変えたもの（字を挿す・消す・途中で切る。挿す字は `,` `}` `'` `T` `/` `\u0000` ` ` NBSP・BOM など）で 30,000 組試した。

- 正しい JSON 30,000件: どれも `null`（食い違い0件）。
- 変えても正しいままの 6,529件: どれも `null`（0件）。
- 正しくない 23,471件: どれも位置を返し、V8 が位置を言う誤りでは、返した位置が V8 の位置より後ろになるものは0件。
- 7.5MB（60万行）の正しい JSON は 162ms、終わりの近くに `True` を入れた誤りは 349ms（`JSON.parse` は 53ms）。押してから一度だけ走るので、来訪者に問題になる長さではない。
- 例外: 入れ子の深さ（Minor 1）。

## Major

### M1. §8 と PM の決定の「後ろから戻ったときは、ページを動かさない」が、見本の実装と違い、文のとおりに作るとフォーカスが画面の外に出る

- 作業ツリーの `DESIGN.md` §8 は「リングの上の辺がもう画面にあるときと、後ろから（Shift+Tab で）戻ったときは、ページを動かさない」と書く。`t4-design.md` の PM の決定も同じ文である。
- 実装（`revealFocusedFrame` の `arrivedFromAfter` の枝）は、後ろから戻ったときも、リングの下の辺が着く前に画面の外なら、下の辺を画面の下端から 8px 上に来るまで送る。上の表の5条件では実際に送っている。
- 実装が正しい。FAQ の開閉から Shift+Tab で戻るとき、戻る前の画面ではボックスの下端が画面の上の外（320 で −308px）にある。文のとおり「動かさない」（着く前の位置に戻す）と、フォーカスのある区画が丸ごと画面の外に残り、キーボードの来訪者はフォーカスを見失う（WCAG 2.4.7）。
- **来訪者に起きること:** T5 の builder・レビュアーは `DESIGN.md` を正として `ResultBox` とそのテストを読む。文と振る舞いが違えば、文に合わせて「直す」か、同じ食い違いを別の面で持ち込む。規定が見本と食い違ったまま T5 に渡ると、2巡目 M1 で直そうとしたこと（見本の振る舞いを規定から導けること）が果たせない。
- **直し方の方向:** planner が §8 の文を、前と後ろを同じ形で言うように直す。例:「キーボードで結果の中の送る区画に着いたときは、着いた向きの側のリングの辺を見せる。前から着いたら上の辺、後ろから戻ったら下の辺で、その辺が着く前から画面にあればページを動かさない。無ければ、その辺が画面の端から 8px の所に来るまで送る。」PM の決定の記録も同じに直す。

## Minor

### m1. 深い入れ子で、走査が落ちて前の結果が残る

- 走査は再帰で読むので、入れ子が深いとスタックが尽きる。Node で 20,000段、ブラウザ（375 の Chromium）で 30,000段の `[` の、閉じ括弧が1つ足りない JSON を整形すると、`RangeError: Maximum call stack size exceeded` がページの外へ投げられ、誤りの文は出ない。**直前に整形した結果が、そのまま画面に残る。** 来訪者は新しい入力が整形できたと取り違える。
- 正しい JSON でも、`JSON.stringify` が深さで落ちる（Node で 5,000段）と、`catch` に入り、走査が `null` を返して「JSONの形式が正しくありません。」と、正しい JSON を正しくないと言う（ブラウザの 3,000段では整形できた）。
- 手で書く JSON では起きないので Minor とする。走査を配列のスタックで回すか、`RangeError` を受けて「入れ子が深すぎて扱えません」と言い、前の結果を消す。どちらでも、`runOperation` が例外の種類を見分けて、正しくない JSON と扱えない JSON を別の文で言う。

### m2. 道具の説明の文が、出す内容と合わない

- `meta.ts` の `howItWorks` は「JSON構文エラーがある場合はエラー内容を表示します」と書く。道具が出すのは、形式が正しくないことと、その行と字だけで、誤りの内容（何が違うか）は言わない。2巡目 M3 でも挙げたが直っていない。
- 「JSON構文エラーがある場合は、最初に誤った所の行と字を表示します」のように、実際に出すものに合わせる（constitution の 4）。

### m3. テストの届いていない所

- `revealFocusedFrame` の、Tab の記録が 1,000ms より古いときにいまの位置を着く前の位置とする道を試していない（`TAB_TO_FOCUS_LIMIT`）。
- `ResultBox` のテストは `trackScrollBeforeTab` を空の関数に差し替えており、`kind` のある箱だけが受け手を置き、外したときに外すことを試していない。本レビューでは本番のビルドで確かめたが、回帰を防ぐテストが無い。
- m1 の深い入れ子の扱いを決めたら、それも試す。

### m4. `SKILL.md` の送りの項が、まだ無いものをあるように書く

- 未コミットの `SKILL.md` は「ゲームの次に使うコントロールを見せる送りも同じファイルに置く」と書く。いまは `src/play/games/shared/_lib/revealControl.ts` にあり、`reveal.ts` には無い（移しは `index.md` 275行の片付けのタスク）。
- 読んだ builder が `reveal.ts` にゲームの送りを探して見つからないか、2つ目を書く。移しを終えるまでは今の置き場所を書くか、移しと同じコミットでこの文を入れる。
