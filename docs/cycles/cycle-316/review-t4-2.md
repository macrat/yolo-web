### 依存

- `budoux` 0.9.2 は公開から10日で、`.npmrc` の `min-release-age=7` を満たす。
- `dev` の印が外れた `agent-base`・`debug`・`htmlparser2` などは、budoux が本番の依存として持つ `google-artifactregistry-auth` を通して、本番の依存の木に入ったもの。`@img/sharp-*` と `@emnapi/runtime` に `dev` が付いたのは、budoux を足す前の HEAD の lock で `npm install --package-lock-only` を実行し直しても同じ差分になる。つまり npm（10.9.7）がいまの lock の印を計算し直したもので、budoux を足したこととは関係しない。`sharp` は devDependencies にあり、`next/image` はどこでも使われていない。CI（`npm ci`）も Vercel も dev の依存を入れるので、来訪者への影響は無い。
- worktree で `npm install budoux@^0.9.2 --package-lock-only` を実行し直すと、コミットされた lock とバイト単位で同じになった。

### 区切りの関数の後処理

- 禁則の字の前・開き括弧の後ろ・数字の後ろ・最後の1字の4つの処理は、どれも設計の 2-3 のとおり。`柔和温順（に|ゅうわおんじ|ゅん）` のように、BudouX が小書きの仮名の前で割る所も、この後処理で塞がっている。
- 文節の境界の判定は、つないだあとの前の文節の末尾を見るので、何度つないでも正しく続く。最後の1字は書記素（`Intl.Segmenter`）で数えている。
- ツギハギや経緯のコメントは無い。コメントは、いまの仕組みとその理由だけを書いている。

## 指摘

### Major-1: 「サーバーだけで使う」を守る仕組みがコメントだけで、クライアントから読み込んでもビルドが黙って通り、約250KB の JS が来訪者に配られる

- **どこで**: `src/lib/phrase-breaks.ts`。サーバーだけで使うという約束は、ファイルの頭のコメントにしか書かれていない。
- **何が起きるか**: worktree で、`"use client"` の部品から `splitIntoPhrases` を読み込んで本番のビルドをすると、エラーも警告も出ずにビルドが通った。そして、BudouX のモデル・`linkedom`・`htmlparser2` を含む 251,458 バイト（gzip で 103,571 バイト）のチャンクが `.next/static/chunks/` に入った。
  - これを止める仕組みがほかに無い。CI（`deploy.yml`）は `npm test` を `npm run build` より先に実行するので、`.next` の無い CI では bundle-budget のテストがまるごと飛ばされる。大きいチャンクのしきい値（300KB）も下回っている。
  - 設計では、次の T4-5 で `ResultCard`（クライアントの部品）がこの区切りを使い、T5 はサイトの見出しに広く使う。部品を書く人が `ResultCard` の中で `splitIntoPhrases` を呼べば、約104KB（gzip）が性格診断のページの JS に黙って足される。
- **来訪者にどう効くか**: 来訪者の多くはモバイルで、結果の画面に着くまでの JS が約104KB（gzip）増える。読み込みと操作できるまでが遅くなる（AP-I03）。しかも、レビューで `.next/static` を探さない限り気づけない。
- **直し方**: `phrase-breaks.ts` の頭に `import "server-only";` を置く。Next.js はパッケージを入れなくてもこの import を扱う（公式の「Preventing environment poisoning」）。worktree で次を確かめた。
  - これを置いてクライアントから読み込むと、ビルドが失敗する。
  - サーバーのページから使うだけならビルドが通る。
  - vitest では `Failed to resolve import "server-only"` でテストが落ちる。`vitest.config.mts` の `resolve.alias` で `server-only` を `next/dist/compiled/server-only/empty.js` に向けるなどして、テストを通す。
  - 注意: 失敗のときの Turbopack のメッセージは `end byte index 93 is not a char boundary; it is inside 'ダ'` という panic（`Panic in async function`）だった。コードの抜き出しを色付けするときに、和文の所で落ちたもの。ビルドは止まるので守りにはなるが、原因は読み取りにくい。builder はこの現れ方を確かめ、`docs/knowledge/nextjs.md` の11項（`server-only` を勧めている項）に書き足す。
  - `src/lib/zen-antique-charset.ts` も同じくコメントだけで守っている。同じ直しを当てるかどうかは PM が決める（T4-2 の受け持ちの外）。

### Minor-1: 読み仮名の括弧の中と、1つの文節しかない長い名前が、既定の文字サイズでも変な所で折れる（T4-2 の条件の外。当てる先のタスクの条件にも入っていない）

- **どこで**: クイズの見出しの全144件を、主見出しの段（321px・266px）の既定の文字サイズで組んだとき。
  - word-sense-personality の結果の名前の読み仮名が、語の途中で割れる。321px（375px の画面）で「理路整然（りろせい／ぜん）タイプ」「疾風迅雷／（しっぷうじんらい／）タイプ」（閉じ括弧が行頭に来る）「柔和温順／（にゅうわおんじゅ／ん）タイプ」。266px で「和顔愛語／（わがんあい／ご）タイプ」「奇想天外／（きそうてんが／い）タイプ」。BudouX は仮名だけの並びを語で分けられず、括弧の中にも区切りを置くため。
  - science-thinking の結果の名前は、BudouX が1つの文節として返すため、1行に入らないと `anywhere` で割れる。321px で「チューリング型思考／者」（1字だけの行）、266px で5タイプが「〜型思考／者」。kotowaza-level の結果の名前は、266px で「ことわざビギナ／ー」（長音符が1字で行頭に来る）。
- **いまと比べると**: 同じ見出しを、いまの組み方（Chromium の `auto-phrase`、WebKit の近似の `normal`）で測った。どれも同じか近い割れ方をしていて、T4-2 で悪くなったわけではない。ただし、§4 の「見出しは文節で折る」が約束する見え方にもなっていない。
- **来訪者にどう効くか**: T4-7 で結果のページの h1 をこの部品に替えると、375px の既定の文字サイズでも、診断の結果の名前が「（りろせい／ぜん）」「思考／者」のように読みにくく出る。いまの T4-7 の完了の条件は、24のタイプ名と「ほかの診断から1本ずつ」のスクリーンショットしか見ないので、この割れ方を拾わない。
- **求めること**: PM が次のどちらかを決め、設計の T4-7（と T5 に渡す事項）に書く。
  - (a) 後処理を足す。例: 括弧で囲まれた読みの中では区切らない。ただし、これにも損がある。「（かちょうふうげつ）」は10字で 321px の1行に入らず、`anywhere` で割れて閉じ括弧が行頭に来る。いまの「（かちょう／ふうげつ）」は語の切れ目で折れているので、このタイプでは悪くなる。試作で数を比べてから決める。
  - (b) 限界として受け入れる。そのうえで、T4-7 の条件に「クイズの見出しの全件を主見出しの段で測り、既定の文字サイズでの1字だけの行と禁則の破れを記録する」を足し、来訪者の目で許せるかを判断する。

### Minor-2: `budoux` が、使わない `google-artifactregistry-auth` を本番の依存として引き込み、`npm audit` の指摘が2件増える

- **どこで**: `budoux` 0.8.x 以降の `package.json` は、`google-artifactregistry-auth`（npm を Artifact Registry に認証させる道具）を `dependencies` に持つ。0.7.0 には無い。budoux のコード（`dist/`）はこれを読み込まない。
  - これを通して `google-auth-library`・`gaxios`・`gtoken`・古い `uuid` など約20のパッケージが本番の依存の木に入る。
  - `npm audit --omit=dev` の数は、7件（moderate 3）から9件（moderate 5）に増える。増えたのは `uuid <11.1.1`（GHSA-w5hq-g745-h8pq）と `gaxios`。install のスクリプトは持たない。
- **来訪者にどう効くか**: 実行の時に読まれないので、来訪者への直接の害は無い。ただし、サプライチェーンの面が広がり、audit の雑音が増える。
- **求めること**: この事実と、それでも 0.9.2 を採る理由（例: 0.7.0 ではモデルが古い）を、サイクルのドキュメントに残す。`overrides` などで外せるかも調べ、外せないなら上流への報告を検討する。

### Minor-3: 単体テストが「許される区切りを残すこと」を見ていない

- **どこで**: `src/lib/__tests__/phrase-breaks.test.ts`。いまのテストは、区切ってはいけない所で区切らないこと（つなぐと元の文になる・数字・禁則・最後の1字）を検査している。区切るべき所で区切ることは、「タイプ名は2つ以上の文節に分かれる」と「3秒後」「10年」の2件しか見ていない。
- **何が起きうるか**: 例えば、後処理の正規表現を広げすぎて区切りを多く外しても、見出しごとに1つでも区切りが残れば、テストは通る。区切りが減った見出しは、`anywhere` による文節の中の折れが増える。
- **求めること**: 性質のテストを1つ足す。例:「出力の境目は、どれも BudouX の境目の中にある」「BudouX の境目のうち外すのは、禁則・開き括弧・数字・最後の1字の所だけ」。BudouX の出力を実行のたびに作って関係を見るので、出力の写しにはならない。

### Minor-4（軽微）: `PhrasedTag` が、使い手の無い `p`・`span` を持つ

- `PhrasedText` の `as` は `p` と `span` を受け付ける。しかし、設計（2-3）とコメント・CSS のコメントは見出しだけを対象にしていて、T4 の中で `p`・`span` の使い道は決まっていない。
- 使う予定が無いなら `h1`〜`h6` に絞る。使うなら、その対象をコメントと設計に書く。

## そのほか（指摘ではない）

- 見出しの中にある要素は `<wbr>` だけで、`span` は無い。サーバーの HTML でも `「よし行くぞ！」と<wbr/>叫んで<wbr/>3秒後に…` の形で出ている。
- `.phrased`（クラス）は `globals.css` の `h1`〜`h6` の `word-break: auto-phrase` より詳細度が高い。実測でも、計算値はどの見出しも `keep-all` だった。
- 依頼では「まだコミットしていない」とされていたが、レビューのあいだにコミットされた。完了はこのレビューの後なので手順の違反ではないが、直しは別のコミットになる。

**改善指示。** 完了の条件（24タイプの折り方・読み上げの名前・クライアントの JS に budoux が入らないこと・単体テスト）は満たしている。しかし、Major-1（クライアントから読み込んでも黙って通り、約104KB（gzip）が来訪者に配られうること）を、T4-5 がこの関数を使い始める前に塞ぐ必要がある。Minor-1〜4 もあわせて対応する。
