### 記事の外の表（外側の余白0）

外側の縁の余白を0にする CSS を当てて、storybook の結果のボックスの表（d05dbe0）と、ContrarianFortuneContent の指標の表（T4-6 の作業中の版）を 375px と 1280px、ライトとダークで撮った。どちらも字の左端が置かれた幅の左端（結果のボックスでは内側の余白の内側、読みものでは本文の左端）にそろい（前は 8px 右）、崩れは無かった。

### そのほか

- React 19.2.7 の開発のビルドは、水和のときに `dangerouslySetInnerHTML` を持つ要素の `innerHTML` と `__html` を比べ、違えば食い違いを報告する（`diffHydratedProperties`）。サイトに CSP は無い（`next.config.ts`・`vercel.json`・`middleware.ts`）。
- 枠の判定（枠を外した組み方の表の幅と枠の外形の幅を比べる）は、表が `width: 100%` なので、枠の中の表の幅は「最小の幅と内側の幅の大きいほう」になる。最小の幅がコンテンツ幅以下なら枠を付けても外しても外す側に、超えるならどちらでも付ける側に落ち着き、行ったり来たりしない。T5 でコンテンツ幅が変わっても同じ。

## 指摘

### Major-1: いちばん大事な得失を、測らずに決めている。この設計の数は 136 でなく 165、1280px では 1 から 12 になる（AP-P01・AP-P07）

5-2 は「横に送る表は語の切れ目で折る組み方より増えます（T4-17 で数を記録する）」とし、planner の対応は「T4-17 の実測では…136表、T4-17 の前は 77表」を挙げている。136 は T4-17 の版（語の切れ目）の数で、この設計の数ではない。見積もりでは **375px で 165表（84%）、1280px で 12表（T4-17 の前は 1）**。丸括弧の中で折らない規則と、最初の文節にしか語の切れ目を足さない規則は見出しのためのもので、表のセルでは長く割れない塊を作る（「大（ページ数分のファイル作成）」「対応（日・曜日で必須）」「C: サーバーコンポーネント直接インポート」「AIカラーパレットジェネレーター」）。

GA では、記事の読者は9割がデスクトップ、表の多い早見表の読者はほぼデスクトップだけである。だから:

- **モバイルの得失（77→165）は受け入れてよい。** 375px のコンテンツ幅（273px）では、列の多い表はどの組み方でも横に送るか字の所で割れるかのどちらかで、`anywhere` の組み方は文節の中の折れが数十倍になる。記事を読むモバイルの来訪者は28日で7回で、語が1行で読めることのほうが価値が大きい。
- **デスクトップの 1→12 は、主な読者の見え方を悪くする。** 1280px で新たに枠が付くものには、はみ出しが 1px（nextjs-global-not-found-for-multiple-root-layouts）・3px（http-status-code-guide-for-rest-api）・16px（clickable-list-row-stretched-link）・33px（game-dictionary-layout-unification）のものがある。枠を付けると内側の余白と線で表を置く幅が 38px 狭まるので、ほぼ収まっていた表の字が 39〜71px 隠れ、デスクトップの読者はスクロールバー付きの箱を送って読むことになる。cron-cheatsheet・git-command-cheatsheet・nextjs-directory-architecture など、読まれている早見表・解説の表も入る。

直し方（planner が 5-2 を直す）:

1. 数を測ってから決める。この設計の組み方で、6つの条件の横に送る表の数と、1280px（と T5 のあとの幅）で横に送る表の一覧・はみ出しの px・原因の塊を、5-2 の判断の根拠として書く。「T4-17 で記録する」への先送りをやめる。
2. **表のセルでの区切りの規則を、見出しの規則から表に合うものへ分ける比較**を、案の表（AP-P17）で行う。少なくとも次を並べ、375px と 1280px の横に送る表の数と文節の中の折れの数で比べる。
   - A. この設計（見出しと同じ区切り）: 375px 165・1280px 12。
   - B. 丸括弧の中でも文節で折る（開き括弧の後ろと閉じ括弧の前では折らない禁則は残す）: 375px 162・1280px 8。見出しで丸括弧の中を折らない理由（読み仮名・添えた数）は、説明を括弧に入れる表のセルには当たらない。
   - C. B に加え、長い文節（例: 8字以上）を字の種類の変わり目でも折る: 375px 160・1280px 8。
   - D. 長い片仮名の複合語（「サーバーコンポーネント」）の中の語の切れ目を、長いときだけ区切りに足す、など、残る 1280px の表の原因の塊を個別に見て効く規則。
   - E. `anywhere`（とセルの最小の幅）: 横に送る表は減るが、文節の中の折れが数十倍になるので採らない、と数で書く。
3. 完了の条件（10章の (4)）の「増えるのは受け入れる」を、上で決めた数（例: 1280px の既定で横に送る表は、列の数か割れない字の並び（コード・URL）のために収まらないものだけで、一覧にして報告する）に置き換える。デスクトップの読者が主なので、1280px の条件を上限つきにする。

### Major-2: 本文の直後の同期のスクリプトは、開発のビルドで水和の食い違いを必ず出し、遅い回線では最初の描画に間に合わない（5-2「枠は最初の描画から付け」）

- React 19.2 の開発のビルドは、`dangerouslySetInnerHTML` の要素の `innerHTML` を `__html` と比べる。スクリプトが中の枠に `data-scrolls`・`tabindex`・`role`・`aria-label` を付ければ、組み方の上で食い違いが報告される。5-2 は「警告が出ないことを確かめます」とするが、確かめれば必ず落ちる条件で、builder がその場の判断で `suppressHydrationWarning` を付けるか、別の形に変えることになる。**設計で決める**: `Prose` の要素に `suppressHydrationWarning` を付けてよいか（その要素の属性と中の HTML の比べだけが消え、中身はサーバーの HTML のまま変わらない）、それとも印を中の HTML の外（例: 本文の要素の属性に、枠を付ける表の番号を持たせ CSS で当てる）に置くか。
- 記事の HTML は長く、回線が遅いと本文の途中までが届いた所でブラウザが描くことがある。スクリプトは本文の後ろなので、そのときは枠が描いたあとに付き、表とその下が動く（枠の付いた表は上下に余白と線の分だけ高くなる）。10章の (6) の CLS は、手元の速いサーバーで測るので、これを捉えない。完了の条件に、回線を遅くした測り（CDP の回線の絞り）での CLS を足すか、スクリプトを表ごとに表の直後に置くなど、届いた所から描く場合にも間に合う置き方を決める。
- React が描く `<script>` は、クライアントでの移動（一覧から `Link` で記事へ）では実行されない。そのときは `Prose` の layout effect が描く前に印を付けるので問題は無いが、5-2 はこの経路に触れていない。「最初の読み込みはスクリプト、クライアントでの移動は layout effect」と書き、10章の (6) に一覧から記事へ移ったときの CLS を足す。
- 「スクリプトの印の付け方は `scroll-frame.ts` から作り」は、関数の文字列化で作るなら、その関数が外の名前（読み込んだ関数・定数）を使わない形でなければ本番のビルドで壊れる。確かめる条件（本番のビルドで、スクリプトが例外なく動き、印が付いている）を (6) に明記する。
- CSP はサイトに無いので、いまは問題にならない。JavaScript が無いときの扱い（枠なしで横に送れる）は妥当。

### Minor-1: 「自前の余白を持つ表は変わりません」で、keigo-reference の表が新しい §5 と食い違ったまま残る

8章の §5 の表の項に「表の外側の縁では、セルは余白を持たない。表の字の左端は本文の字の左端とそろう」を書くのに、5-2 は keigo-reference の表（`KeigoReferenceTile.module.css` の `.table th, .table td` が左右 8px を持つ）を「変わりません」とし、T4-17 の受け持ちにも10章の (9) にも入れていない。規定に反する表を1つ残すことになる。keigo の表の外側の縁がどうなっているか（先頭の列は開閉のボタンで余白0、最後の列の右は 8px）を確かめ、§5 に合わせるか、合わない理由があるなら規定の側を書き分ける。色の辞典のカラーコードの表は、左0・値の列の左右0で、すでに合っている。

### Minor-2: 設計（docs）から `tmp/` のファイルを指している

10章の測り方と T4-17 の行が `tmp/cycle-316/rv-t4-17/metrics.mjs`・`slugs.txt` を指し、5-2 も `small.mjs` を挙げている。`tmp/` はコミットされず残る保証が無い（`.claude/rules/tmp-directory.md`「他のディレクトリにあるファイルから `./tmp/` に保存したファイルについて言及またはリンクする」は Don't）。測る対象は「draft を除く公開記事のすべて」と書けば足り、手順は10章の文で足りる。`tmp/` への参照を外す。

### Minor-3: 5-2 の「表の右端は最後の列のいちばん長い字の右端」は、はみ出すときだけ正しい

表は `width: 100%` なので、収まる表の右端はコンテンツ幅の右端である。文は判定の理由（はみ出すなら字が隠れる）として使っているので、「コンテンツ幅を超える表では、右端は最後の列のいちばん長い字の右端になる」と書く。

## 見てほしい点への答え

1. **得失**: モバイルで横に送る表が増えること（字を1行で読める代わりに送る）は、記事のモバイルの読者が1割に満たず、`anywhere` の代わりの組み方は文節の中の折れを数十倍に増やすので、受け入れてよい。ただし数は 136 でなく 165 で、デスクトップで 1→12 になることが測られていない。代わりの組み方は Major-1 の B〜D。
2. **外側の余白0の既定**: 結果のボックスの表と ContrarianFortuneContent の指標の表は、撮った限り崩れず、字の左端がそろって良くなる。keigo-reference の表は Minor-1。
3. **枠の判定**: T5 のあとも成り立ち、付け外しは行ったり来たりしない（上の「そのほか」）。比べる幅は、丸めた整数の `scrollWidth` でなく小数の幅で、付けるときと外すときに同じ値を使うよう、`scroll-frame.ts` に書く。
4. **同期のスクリプト**: 考え方は妥当だが、水和の食い違い・遅い回線・クライアントでの移動・関数の文字列化を設計で決める（Major-2）。CSP は無く、JS 無しの扱いは妥当。
5. **フォーカスのリングの規則**: 筋は通っている。§6 の「内側に出す」の理由（並んだコントロールや詰めた行に食い込まない）が横に送るボックスには当たらないことと、外端 6px がコンテナの内側の余白 8px とコンポーネントのあいだ 16px に収まることを、規則の理由として書けている。「横に送るボックス」は、横に送れるときだけフォーカスを受けるので、一般の規則として過不足が無い。
6. **完了の条件**: 来訪者に見える結果（折れ・枠・字の左端・CLS・リングの撮影）を測れる形になっている。足りないのは、1280px の横に送る表の上限（Major-1）、遅い回線とクライアントでの移動の CLS（Major-2）、keigo の表（Minor-1）。
