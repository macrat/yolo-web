## 指摘

### 指摘1（planner）: 括弧の中の欧文の空白で折れることを見落としており、375px・200% で §4 が受け入れない折れが出る

9-b は「アクセス解析（Google Analytics）の全体は約 264px で、1行に収まるか、始め括弧の前で2行に折れます」と書き、200% については「（Google Analytics）」の 320・375px と「（Google AdSense）」の 320px の3つを、括弧の一続きが1行に収まらないので中で折れてよいものとして挙げる。実際の組み方では次のようになる（上の実測）。

1. **1行に収まらないとき、折れるのは始め括弧の前ではなく、括弧の中の空白である。** 括弧の中の「Google」と「Analytics」のあいだの空白は `PhrasedText` でも折り所のまま残り、ブラウザは行に入るいちばん後ろの折り所で折るので、始め括弧の前の `<wbr>` より空白が先に使われる。320px の既定では 263.28px が 266px に 2.7px の余りで収まるので実害は出ないが、「始め括弧の前で2行に折れます」は事実と違う。収まらなければ「アクセス解析（Google ／Analytics）」になり、§4 の既定の文字サイズで作らない「丸括弧の一続きの中の折れ」になる。
2. **375px・200% の「広告（Google AdSense）」が、括弧の一続きが1行に収まるのに、その中で折れる。** 「（Google AdSense）」は 34px で 318.08px、375px のコンテンツ幅 321px に収まる。それでも1行目に「広告（Google 」まで入るので、ブラウザは空白で折り、「広告（Google ／AdSense）」になる。§4 の 200% の項が受け入れるのは「1行に収まらない文節の中の折れから出た」ものだけで、これはどちらにも当たらない。9-b が挙げた受け入れる3つにも入っておらず、builder は完了の条件（「1行に収まらない文節か丸括弧の一続きの中の折れから出たものだけ」を受け入れる）に照らして受け入れられないが、直し方は行にも 9-b にも無い。

直し方の候補には、どれも損がある（決めるのは planner）。

- 括弧の中の空白を折れない空白（U+00A0。Zen Antique の字の表にあり、`joinDashes` が見出しで先に使っている）にする: 375px・200% の「広告／（Google AdSense）」は正しくなるが、1行に収まらない 320px・200% では「（Google Analyti／cs）」「（Google AdSens／e）」、375px・200% では「（Google Analytics／）」と語の中や閉じ括弧だけの行で折れ、§4 が受け入れる範囲ではあっても、今の空白での折れより読みにくい。
- 括弧の中に空白を持たない言い方にする、あるいはサービスの名前を括弧に入れない言い方にする: 指摘の3つの条件（和文を含む・前のほうの字で見分けられる・本文より強く言わない）と、名前で探す来訪者への手がかりを保てるかを、もう一度比べる必要がある。
- 括弧の一続きを、1行に入るときは丸ごと次の行へ送り、入らないときだけ中の空白で折る組み方を `PhrasedText` に足す: 仕組みとしては正しい形だが、`PhrasedText` は「要素の中は文の字と `<wbr>` だけにする」と決めており、T5-21 の範囲を越える部品の変更になる。

どれを採るにしても、9-b には次を書く。

- 採った形で、320・375・1280px の既定と、320・375px の 200% のそれぞれで、第三者サービスの章の h3 の2つがどう折れるか（今回のように実測できるので、見積もりでなく数で）。
- 200% で受け入れる折れの名指しに、実際に出る h3 の折れを、どの一続きが1行に収まらないことから出たかと合わせて入れる。
- 9-b の「1行に収まるか、始め括弧の前で2行に折れます」を、仕組みに合った記述に直す。320px の既定の余りが 2.7px しかないことも書き、builder が実測で1行に収まることを確かめる条件にする。

T5-21 の行の完了の条件も、それに合わせて「受け入れる折れ」の名指しを直す。

### 指摘2（planner）: 案 D を捨てる理由の後半が事実と合わず、前半は来訪者にとっての損でない

案 D の判断は「変える見出しが3つになり、第三者サービスの章の2つは B と同じく頭が欧文で、同じ章の中で和文の見出しと欧文の見出しの頭がそろわない」と書く。

- D では第三者サービスの章の h3 は2つとも欧文で始まり、「収集する情報」の章の h3 は3つとも和文で始まるので、「同じ章の中で」頭がそろわない所は無い。ずれるのは章をまたいだページ全体である。
- 「変える見出しが3つになる」は作る側の手間で、来訪者の得失ではない（CLAUDE.md の判断の原則）。

D を捨てる来訪者の側の理由は、B と同じく見出しの頭が欧文で、§3 により本文と同じ IBM Plex Sans で組まれ、`45rem` 未満では頭の字が本文と大きさも形も同じになる（条件1が頭の部分で弱い）ことのはずである。理由をその形に書き直す。判断（C を採る）は変わらない。

## 見たが指摘にしないこと

- **§4 の「丸括弧で囲んだ一続き」の例は読み仮名・添えた数で、サービスの名前は例に無い。** ただ、`phrase-breaks.ts` は丸括弧の中身を問わず1つのまとまりとして扱っており、中で折らない理由（中は1つのまとまりとして読まれる）もサービスの名前にそのまま当てはまるので、9-b がこの規則を当てるのは妥当。
- **h3 の区切りの並びが 9-b に書かれていない。** 「アクセス解析｜（Google Analytics）」「広告｜（Google AdSense）」は `followsPhraseRules` で builder が確かめられ、行の「見出しの区切り」の項で受け持ちも決まっている。ただし指摘1の直し方によっては並び自体が変わるので、直すときに書いておくと builder が迷わない。
- **45rem 以上 64rem 未満（タブレット）の h3（`1.49rem`）** は、「アクセス解析（Google Analytics）」が約 392px で、この幅の段のコンテンツ幅に余裕で収まる。測る幅を増やす必要は無い。
- **1280px の 200%** は、本物の 200%（既定の文字サイズを 32px にする）では `45rem` 未満の段になるので、私の近似（ルートの文字サイズだけを変える）では測れない。9-b の表の値（h3 34px）と、幅が広いので括弧の一続き（約 323px）がどの行にも収まることから、問題は出ない。
- **GA の閲覧の数**は、前回と同じくこの環境に GA の道具が無いので確かめていない。結論は数の多少に左右されない。
