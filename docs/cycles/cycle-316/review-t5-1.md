### M-1 留めた目次が、ボックスであること・幅・地を持たない（§5）

§5 の「目次」の項は「閉じたアコーディオン（§6）で置き、…画面の上端に留める」としか書いていません。§5 のボックスの項（「コンテンツ幅に置くもの（結果・表・コード・一覧・横に送る図）」）と幅の表にも、目次がありません。

直し方の例: 目次の項を「**目次**は、記事の頭のあと・本文の前に、ボックス（§5）に入れた閉じたアコーディオン（§6）で置き、…」にします。留めるときはボックスの地が `--paper` で、下を送られる本文を隠すことを1文で言います。ボックスの項の「コンテンツ幅に置くもの」に目次を足します。`##` の全幅の罫線は、留まった目次の左右（コンテンツ幅の外）では見えたまま下を通ります。これを受け入れるかは、T5-15 のスクリーンショットで確かめる項目にします。

### M-2 `line-break: strict` の項の「この禁則はかからない」が、既定の文字サイズの項と食い違って読める（§4）

見出しの下位の項の最後に、「文節が1行に収まらずにその中で折れる所では、字を欠かさないことが先で、この禁則はかからない」とあります。2つ上の項は「既定の文字サイズでは、見出しに…禁則の破れ…を作らない。組み方で避けられないときは…文を直す」です。「かからない」を「その折れでは禁則の破れを許す」と読むと、既定の文字サイズでも破れを受け入れることになり、2つ上の項と食い違います。9章の「食い違わない理由」が言う意味（strict は、いまの規定を組み方で守る手段）は、「CSS の禁則では防げない」です。

直し方の例: 「…その中で折れる所は、字を欠かさないことが先で、CSS の禁則では防げない。そこで出た禁則の破れの扱いは、上の既定の文字サイズと 200% の項に従う。」

### m-3 書いた Markdown のプレビューの見出しの段と大きさが、「折り方」の箇条の中にある（§4）

builder が `#`→`h2`・`##`→`h3` と書き、大きさを役割の名前（セクションの見出し・セクションの中の小見出し）と「見出しの5段をさらに1段ずつ下げて、本文の大きさで止める」で書いたのは妥当です。9章の「2段目・3段目」は、§4 の大きさの「5段」と取り違えうる語でした。`h2` と書けば取り違えません。4-k の「B の損」（`45rem` 未満で `##` から下が本文の大きさにそろう）とも合います。

ただ、この文は見出しの要素の段と大きさを決める規則で、折り方の規則ではありません。見出しの大きさを組む人は、§4 の見出しの項と段の表を読み、「折り方」の中のプレビューの項までは読みません。段の表の下（「階層は相対で…」の表のあと）に、独立した1文として移してください。プレビューの項には「通常の禁則処理で折る」とその理由だけを残します。

### m-4 日時の文字列が、§8 の結果の表のどの形にあたるかが決まらない（§8）

§4 に日時の文字列の折り方が入りました。一方、§8 の表の「1続きの文字列（符号にした文字列など）」は「全体を1語として字のあいだのどこでも折る」です。空白を持たない ISO 8601 の文字列（「2024-01-01T00:00:00.000Z」）は「1続きの文字列」とも読め、そう読むと §4 の日時の規則と食い違います。§8 の表で、日時の文字列が「数字・短い語」なのか、ほかの形なのかを言い、折り方は §4 の日時の文字列に従うと書いてください。どの形にするかは 0-10 の測り（本文の大きさで日付と時刻の塊が 200% の 320px に入る）と合わせて決めます。これは T5-18 の unix-timestamp が迷わないために要ります。

### m-5 スキルの書き足しの取りこぼし

1. 節の名前「見出しの折り方を測る」と、数える項目の「文節の中で折れた見出し」「語の中で折れた見出し」が、測る対象を広げたあとも「見出し」のままです（直前の文は「要素ごとに次を数える」）。機械で確かめる表の行（「見出しとコントロールの名前の折り方」）と合わせて、節の名前を「見出しとコントロールの名前の折り方を測る」に、項目を「文節の中で折れた要素」などにしてください。冒頭の「測るのは、見出しと、…コントロールの名前と名前に括弧で数を添えたもの（見出し・アコーディオンのラベル・索引の語）」は「見出し」が2度出て範囲が読みにくいので、あわせて整えてください。
2. 手順2の終わりの「行の切れ目を決めるのは `<wbr>` と Web フォントの字の幅なので、これを WebKit の近似とする」は、見出しにしか当たりません。コントロールの名前の和文は本文の書体（端末の書体）で組むので、字の幅は Web フォントで決まりません。手順4に「端末の書体…の字の幅」を回したのは妥当です。そのうえで、近似が成り立つ根拠を1文で書いてください。コンテナの Chromium で本文の並びを組むと、和文は WenQuanYi Zen Hei に落ち、仮名は 16px で 16.4px、漢字と約物は 16.0px でした（このレビューで `chromium-1194` で測った値）。iOS のヒラギノも和文をほぼ全角で組むので字の幅は近く、コンテナのほうがわずかに広いので、折れを多めに数える側の近似になります。
3. 手順1は、見出しの Zen Antique だけを待ちます。コントロールの名前にも数や英字（「（10）」「HEXをコピー」）があり、その字の幅は Web フォントの IBM Plex Sans が決めます。Plex の分割ファイルも同じく `document.fonts.load` で待つ、と足してください（見出しの欧文にも当たります）。
4. スキルは「手順の詳しい書き方は `docs/knowledge/playwright-mcp.md` の『WebKit の折り方を Chromium で近似して測る』」と案内しています。ところがその節は見出しだけの手順のままです（`line-break: strict` の確かめも、名前に括弧で数を添えたものの数え方も、本文の書体の前提も無い）。同じ手順が2か所で食い違うので、knowledge の節を同じ範囲に書き直してください。重複を減らして knowledge を書き方の要点だけにする形でもかまいません。
5. 実装の技術の「見出しの折り所は、サーバーで HTML に入れる」の手順7は、`line-break: strict` を見出しの要素にしか持たせていません。§4 はコントロールの名前にも同じ禁則をかけます。区切りを受けて組む部品（`PhrasedText`・`Accordion` の `summary`）も同じ3つの指定（`keep-all`・`overflow-wrap: anywhere`・`line-break: strict`）で組むことを、スキルの同じ所か `PhrasedText` の項に書いてください。手順1の確かめはコントロールの名前の `strict` を求めているのに、作り方の側にそれが無い状態です。
