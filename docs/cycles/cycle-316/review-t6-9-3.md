## 指摘

### 指摘1（動きとコメント）: `loadFonts` が、描かない書体のファイルを読み込み、そのあいだ保存を待たせる

`share.ts` 404〜430行の `loadFonts` は、コメントで「並びの書体を1つずつ、**その書体で組む字**を渡して読み込み」と言っている。ところがコードは、同じ組み方（役割・太さ・大きさ）の字を**全部**つないで、並びのどの書体にも渡している。

```ts
families[font.role].all
  .split(",")
  .map((family) => document.fonts.load(cssFont(font, family.trim()), text)),
```

見出しの並び（`--font-heading`）は `plexSans, "IBM Plex Sans Fallback", "Zen Antique", …` なので、合計点の「27点」は Zen Antique にも「27」を含んだまま渡る。Zen Antique は字の範囲ごとに分けたファイルで、`U+0-FF` を持つファイル（`c938a31bc0b7eb0b…woff2`、16,032 バイト）がある。

Chromium で確かめた:

- 結果の画面が出て書体を読み終えた時点では、このファイルは取得されていない。画面では、数字は IBM Plex Sans（`unicode-range: U+0-7F`）が組むので、ブラウザは Zen Antique の欧文のファイルを要らないとしている。
- 「画像を保存」を押すと、書体のファイルが**1つだけ**取得された。それがこの `U+0-FF` のファイルだった。ほかの字（「点」・表の字・補助情報）の書体は、画面が読み込み済みだった。
- 画像の中でも、数字は Plex で描かれる（`drawText` は `all` の並びで描き、先頭の Plex が U+0000-007F を組む）。読み込んだこのファイルは、画像にも画面にも使われない。

来訪者から見ると、最初の保存で、使わない 16KB を取りに行く。`loadFonts` はどの読み込みも終わるまで待つので、画像が落ちるのも、その取得が終わるまで遅れる。今回の測りでは保存のときに取得された書体のファイルはこれだけなので、t6-log.md の「ページで最初の1枚は書体の読み込みを含めて約 120ms」の「書体の読み込み」は、この取得だと考えられる（時間は自分では測っていない）。回線の遅い携帯では、押してから落ちるまでの間が、この分だけ長くなる。T6-9 が保存を計測し始める面で、押しても反応が遅い体験は避けたい。

コメントの「その書体で組む字を渡して」は、正しい設計（書体ごとに、その書体が組む字だけを渡す）を言っている。直すのはコードの方である。

直し方:

- 書体ごとに、その書体が組む字だけを渡す。字の分け方は `drawText` と同じ（U+0000-007F は `all` の並びのうち和文の並び（`ja`）より前の書体、それ以外の字は `ja` の並び）。2か所が別々の分け方を持たないよう、分け方を1つの関数にして両方が使うのがよい。
- どの書体にどの字を渡すかを、純粋な関数として単体テストで確かめる（例: 見出しの「72点」で、Zen Antique に渡る字に「7」「2」が無い。Plex に渡る字に「点」が無い）。
- Chromium で、結果が出て書体を読み終えたあとに「画像を保存」を押し、書体のファイルの取得が0であることを確かめ、記録に残す。書体を止めたとき・遅らせたときに、第2回と同じく1枚・1回で落ち、書体を止めたときの見出しの字が `--font-ja-heading-fallback` の並びで描かれることも、もう一度確かめる。

### 指摘2（コードとコメント）: 表の行の高さの `Math.max` が、起こらない場合のための分岐で、コメントと合わない

`share.ts` 184行:

```ts
const rowHeight = Math.max(swatchSize, TEXT_LINE_HEIGHT);
```

`layoutResultImage` のコメント（149行）は「表の行の高さは見本の1辺」と言い、ファイルの頭のコメント（6〜7行）は「見本の1辺は問の数から決めるので、どの問も画像の中に入る」と言う。

- 問は常に5つ（`ROUNDS_PER_GAME = 5`。盤は `colors` から作り、端末の記録も `colors` に当てて作り直す）。見本の1辺は (422 − 50 − 18×5) ÷ 5 の切り捨てで 56、行の字の高さは 50 なので、`Math.max` はいつも見本の1辺を返す。333行の `(rowHeight - swatchSize) / 2` もいつも 0 である。
- `Math.max` が効くのは、問が6つ以上のときだけ。そのときは、行の高さが見本より大きくなり、表の高さは中身の枠（422px）を超える（6問で 50 + 6×68 = 458px）。つまり、この分岐が効く唯一の場合に、頭のコメントの「どの問も画像の中に入る」が成り立たない。また、見本の縦の位置が半画素になりうるので、187行のコメントの「見本と罫線を画素の境に置く」も成り立たなくなる。

起こらない場合のための分岐で、しかもその場合には3つのコメントと食い違う。読む人は「行の高さが見本と違うことがあるのか」を調べることになる（CLAUDE.md「ツギハギ禁止」の、例外と特別な場合を残さない、に当たる）。

直し方: 行の高さを見本の1辺そのものにする（`Math.max` と、見本の縦の中央揃えの `(rowHeight - swatchSize) / 2` を外す）。コメントはそのままで合う。問が5つの4例の画像は、画素単位で変わらないはずなので、単体テストが通ることと、1例を描いて前と同じ PNG であることを確かめる。
