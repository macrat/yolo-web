### 2. 指摘

**major-1 転送量の線（110%）が、DESIGN.md §3 の本文書体でほぼ確実に越えられ、しかも越えたときの行き先が無い**

- どこ: index.md:94 の「越えたら、T1 の Web フォントの配り方に差し戻す」と T1 の書き方。
- なぜ:
  - 本文は、変更前はシステムゴシックです（`src/lib/fonts.ts` は Noto Serif JP 600 と Zilla Slab だけ）。変更後は BIZ UDPGothic 400/700 を Web フォントとして読み込みます。
  - Google Fonts の CSS API の実際の応答で見積もりました。ブログ記事 `/blog/sql-cheatsheet` の原稿（`src/blog/content/2026-06-15-sql-cheatsheet.md`）には ASCII 以外の字が386種あり、BIZ UDPGothic の分割ファイルのうち各ウェイト37本が要ります。**400 だけで約 362KiB**、700 も同じ量です。next/font も同じ unicode-range の分割を配ります（facts-external §3）。
  - 変更前 575KiB の 110% は 632KiB なので、増やせるのは 57KiB だけです。Noto Serif JP の 278KiB がまるごと消えても、本文の 400 だけで +84KiB になり、線を越えます。Zen Antique・IBM Plex Sans・700 を足す前の時点でです。
  - 「字からサブセットを作る」案もサイト全体の字（辞典は数千字）が対象なので、かえって大きくなります。
  - 5巡目の前には「それでも越えるなら DESIGN.md §3 が来訪者にとって誤りでないかを判断する」という終点がありました。今回の変更でそれが消え、差し戻しがいつまでも終わらない形になっています。
  - 判定が T9、つまり全ページを作り終えたあとにあるため、差し戻しはすべての作り直しを意味します。
  - 110% という値も、捨てる Noto Serif JP の重さで予算が決まる基準で、来訪者の害から導かれていません。
- どう直すか:
  1. T1 の中で、5ページについて新しい書体の転送量を試作して測り（またはページの字と分割表から見積もり）、土台を作る前に判定する。
  2. 越えるときの終点を書き戻す。「配り方を変えても越えるなら、`DESIGN.md` を変えるときの手順で §3 の本文書体の規定を判断する」。
  3. 線の値を来訪者の側から決め直す。たとえば、1ページで去る 83.7% のセッションがモバイル回線で払う量として何 KiB まで許すか。
  4. 「display: swap のもとでは害は LCP より転送量に出る」は未検証です。Lighthouse の模擬の減速では、LCP より前のフォントの取得が帯域を奪い合うので、実験室の LCP にも出えます。仮説と書くか、確かめてください。
