## Minor

1. **移したときに名指すのが「移した先」だけだと、移す元の削除が段に残る（10章の頭の最初の項目）**
   - **事実**: 使い捨てのリポジトリで、`git rm other.txt`（ほかのタスクの段に載せた削除の代わり）のあと `git mv d/a.txt e.txt` → `git commit -- e.txt` とすると、コミットには `e.txt` の追加だけが入り、`d/a.txt` の削除は段に載ったまま残った（`git status` が `D d/a.txt`）。コミットの時点のリポジトリには、移す元と移した先の両方が入る。`git commit -- d/a.txt e.txt` と両方を名指すと、コミットは `d/a.txt => e.txt` の移動になり、ほかの削除（`other.txt`）は持っていかない。ディレクトリ（`git mv app/new/x app/x` → `git commit -- app/new/x app/x`）でも同じく通ることを確かめた。
   - **読み違いのおそれ**: いまの文は「新しく作ったファイルと移した先は……先に `git add <パス>` で載せてから名指しでコミットする」で、名指すものとして「移した先」だけを挙げている。T5-9（`src/dictionary/_components/new/` の移動）と T5-20a（ゲームの `new/` 2つの移動）の builder がこのとおりにすると、(a) そのコミットの時点で `new/` と移した先の両方がリポジトリに残り（T5-20a の条件「`_components/new` が無い」は作業ツリーでは満たされるので気づきにくい）、(b) 段に残った `new/` の削除を、あとでほかのタスク（T6 など）のコミットが持っていきうる。(b) は、この決まりを足した理由（3回目で見つけた、T6-2 の段に載せた削除を T5 のコミットが持っていった件）と同じ形である。
   - **求めること**: 括弧の中を「移すときは `git mv` を使い、移す元と移した先の両方を名指してコミットする」のように直す。
