### 1-2. いまの組み方と、ずれの原因

`applyTableLayout` は各列のいちばん長い文節の幅（mins）を測り、`planColumns` で次の3つに分ける。

- 収まる: 幅を指定しない。表は `width: 100%` の自動の組みになる。
- 細くする: `table-layout: fixed` にし、全部の列に幅を指定する。
- 送る: 下限の幅のまま、枠の中で横に送る。

収まる表では、ブラウザが CSS Tables 3 の配り方（3.9.3 Distribution algorithm）で幅を配る。

- 表の幅が全部の列の max-content の和より広いとき（余りがあるとき）は、どの列も max-content を取り、余りを max-content に比例して足す。
- 余りが無いときは、各列が min-content と max-content のあいだで分け合う。

漢字カナールの2つの表は、どちらも「収まる」に当たる。

- 「読みと意味」は値の列が長いので、余りのほとんどが値の列に行く。
- 「これまでの成績」は値が「12日」のように短いので、見出しの列が余りの半分ほどを取る。

こうして見出しの列の幅が表ごとに違ってくる。review-t5-20d.md の実測では、320 の既定で 66 と 131px、1280 の既定で 239 と 476px だった。この「余りを中身に比例して足す」ことは、行の見出しを持つどの表でも、広い画面で見出しと値のあいだに空きを開ける。

**(a)+(b) を採る。** 理由は次のとおりである。

- ずれの原因は、余りを中身に比例して足すことにある。(a) はその原因を、行の見出しを持つすべての表で取り除く。
- (a) だけでは、見出しの字数の違う表が縦に並ぶと1字ぶんのずれが残る。(b) で1つの区画の中の表をそろえ、ずれそのものを無くす。
- (b) だけでは、幅の出どころが読み取れない。(c) は §5 と食い違い、ボックスの中の罫線の長さを崩す。(d) は後退を残す。(e) は呼ぶ側ごとの回避になる。

(a) で見出しの列に上限を掛けるのは、余りがあるときだけにした。いつも掛ける形と比べた結果である。

- **いつも掛ける（捨てる）。** 見出しの列に幅を指定すると、CSS Tables 3 の配り方では、幅を指定した列が先に max-content を受け取り、そのあいだ指定の無い列は min-content に留まる。そのため余りの無い狭い画面では、見出しが1行に伸び、値が文節1つずつ縦に並ぶ。実測では、見出し「丁寧語に／言い換えた／ときの／形」と、7文節の値の表で、299px の値が3行から8行になった。ラベルより値を読みに来た来訪者には逆である。
- **余りがあるときだけ掛ける（採る）。** 余りがあるときは、どの列ももともと max-content 以上を取っている。見出しの列を max-content に留めても、値の列は max-content 以上のままで、値の行は増えない。余りが無いときは幅を指定しないので、今と同じ組みになる。見出しの列が max-content を超えないという (a) の中身は、どの幅でも保たれる。

(b) の組の決め方は、次の2つを比べた。

- **(b1) 呼ぶ側が組の部品 `DataTableGroup` で囲む（採る）。** どの表が1つの組かは、来訪者に続けて読ませる単位で、書く人が決めるものである。サーバーで描いた組も、組の最後で1度だけ組める。変わるのは、組を持つ面（いまは漢字カナールの1面）だけである。
- **(b2) `ResultBox` の中の表を自動で組にする（捨てる）。** 変更が `ResultBox` を使うすべての面に及ぶ。irodori の問ごとの点数（列の見出しを持つ表）のように、そろえると困る表を外す例外の規則も要る。サーバーで描いたボックスには、表の有る無しに関わらず、ボックスの終わりに組むスクリプトを置くことになる。

## 3. 採る案の中身

### 3-1. 行の見出しの列の幅（`src/lib/scroll-frame.ts`）

`applyTableLayout` に、行の見出しの列の扱いを足す。

- **行の見出しの列を持つ表**: `tbody` のいずれかの行の最初のセルが `th[scope="row"]` である表。記事の Markdown の表は当たらないので、組み方は変わらない。
- **収まる表（`planColumns` が送らず、どの列も細くしない）**: 次の手順で組む。
  1. 幅を指定しない今の組みのまま、最初の行の最初のセルの幅 w を読む。
  2. 行の見出しの列の max-content の幅 m を測る。表の幅を `max-content` にして、最初の行の最初のセルの `getBoundingClientRect().width` を取る。これは余白と罫線の半分を含む外の幅で、サイトの `border-box` の `width` と同じ数え方である（今の細くする道の `columns.outer` と同じ）。このとき開いた行（`[data-detail]` を持つ行）は隠して測る。表の幅いっぱいのセルの長い文が、列の max-content に混ざらないようにするためである。測ったあとは元に戻す。
  3. w が m より広いとき（表に余りがあるとき）だけ、m を最初の行の最初のセルの `style.width` にする。余りは、幅を指定しない値の列にすべて行く。
  4. w が m 以下のとき（余りが無いとき）は、何も指定しない。今の組みのままである。
- **細くする表と送る表**: いまのまま変えない。
- **コピーのボタンの列を持つ表**: 値のセルの幅が「値＋あき＋ボタン」になるだけで、手順は同じである。ボタンを値の次の行に送る判断（`data-copy-below`）は、今のとおり手順1より前に済ませる。

### 3-2. 組（`DataTableGroup`）

`src/components/DataTable` に組の部品 `DataTableGroup` を置き、`index.tsx` から名前付きで書き出す。

- **DOM**: 部品は `<div data-table-group>` を描く。
  - div には `display: contents` のクラスを付け、親の flex や grid の並びとあき（漢字カナールの `.resultBody` の `gap`）に影を落とさない。
  - 組は入れ子にしない。
  - 部品は React の context で、中の `DataTable` に組の中であることを伝える。
- **組と `inBox` は一緒に使えない**:
  - `inBox` の表は、結果のボックス（`kind="table"`）の直接の子として、ボックスの幅で組み（`placedWidth`）、ボックスの大きさの変化を見る（ResizeObserver）。ボックスは子の幅で横に送るかを決める（`markContentFrame`）。
  - 組の div は `display: contents` で箱を持たず、幅が0に測られる（レビューの試作で確かめた）。枠と箱のあいだに入ると、この3つがどれも組の div を測ってしまう。
  - そもそも `kind="table"` の結果のボックスは、1つの表の箱である（§8「コード・表・一覧が結果であるときは、結果のボックスがそのコンポーネントのボックスである」）。小見出しを挟んで表を並べる組は、そのボックスの中身の形ではない。
  - そこで、組の中の `DataTable` に `inBox` を渡すと、部品は描くときに Error を投げる。部品の JSDoc と SKILL の項にもそう書く。
- **そろえる幅**: 組の中の表のうち、行の見出しの列を持ち、「収まる」に当たるものを、そろえる表とする。
  1. そろえる表をそれぞれ 3-1 で組み、組まれた見出しの列の外の幅 h を読む。
  2. そのいちばん広い幅を G とする。
  3. そろえる表のうち h が G より狭いものごとに、G ＋ 値の列の外の最小の幅（`measureColumns` の `outer`）の和 ≦ 表の幅 であるかを確かめる。当たるときだけ、最初の行の最初のセルの `style.width` を G にする。当たらない表は、自分の組みのまま残す。
  4. 細くする表と送る表は、G を決めるのにも数えず、G も受けない。送る表は太い線と内側の余白を持つ自分のボックスに入るので、字の左端がもともと罫線の分だけずれていて、そろえる意味が無い。
- **そろえるために値の列が譲る幅**: 手順3で G を受けた表では、見出しの列が h から G に広がる。その分（G − h）だけ値の列が細くなり、値の行が増えることがある。値の文節は入る（手順3の条件）。G は組の中のどれかの表の見出しの列の幅なので、譲る幅は組の中の見出しの列の幅の差で決まる。漢字カナールでは、「音読み」「訓読み」（3字）と「最長連続」（4字）の差の1字である。
  - 実測（この planner。冒頭の CSS。字「一」と成績「12日」など）: 299px・32px で G は 138px、「読みと意味」の h は 105.3px で、値の列は 32.7px 細くなった。値の行は4行の合計で 8 から 10 に増えた。244px・32px では値の列に文節が入らなくなるので、そろえなかった。
  - 値の行を1行も増やさないときだけそろえる形も試した（4-1 の数え）。既定の文字サイズの 320 で、全2136字のうち 489字がそろわなくなる。遊び終えた来訪者の多くが見る既定の大きさで罫線が跳ぶので、採らない。
- **組むときの流れ**: どれも `createFrameLayout` の中に書き、文字列にしても動くように外の名前を使わない。
  - `layoutGroup(group)` を足す。組の中の枠（`.table-phrased`）をすべて組み、そろえ、各枠に組んだ印（`data-layout-key`）を付ける。組そのものにも組んだ印を付け、組んだときの枠の数を覚えさせる。
  - `layoutTable(frame, contentChanged)` は、枠が `[data-table-group]` の中にあれば `layoutGroup` に任せる。組み直さずに済むのは、次の3つがどれも成り立つときだけである。どれかが崩れたら、組の全部を組み直す。
    - どの枠の印も、今の幅・字の大きさ・Web フォントの状態と同じである。
    - 枠の数も同じである。
    - 中身が変わっていない（contentChanged でない）。

### 3-3. 組の最初の描画

組は、組の最後で全部の表を1度に組む。組み終えるまでは、組の中身の全体（表と、表のあいだの小見出しなど）を描かない。表だけを隠すと、表のあいだの中身が先に描かれる。そのあとで上の表を組むと表の高さが変わり、描かれた中身が動く（§5「描いたあとに組み直して表とその下を動かさない」に反する）。

サーバーで描く組を、今は持たないと決める形とも比べた。

- 今は、サーバーで描く組を使う面が無い。

- **ブラウザで描いた組**:

`scroll-frame.test.ts` と `DataTable.test.tsx` の作り物の組み（jsdom の `getBoundingClientRect` の決まり）に、次を足す。

- 組の2つの表の見出しの列に、同じ幅（広いほう）が指定されること。
- G ＋ 値の列の外の最小の幅の和が表の幅を超える表には、G を指定しないこと。
- 送る表と細くする表が、G を決めるのにも数えず、G も受けないこと。
- 組の1つの枠に `layoutTable` を呼ぶと、組の全部の枠と組そのものが組まれて印が付くこと。

- `LAYOUT_PREVIOUS_GROUP` が組の全部を組むこと。失敗したら組と組の全部の枠に `data-layout-failed` を付けて投げること。
