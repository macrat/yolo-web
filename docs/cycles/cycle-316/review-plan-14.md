### 2. 指摘

**minor-1 変更前に無い URL の増分が定義されていない（除外をやめたことで生じた）**

- どこ: index.md:94 の境界のページの定義。
- なぜ:
  - DESIGN.md:260（§7）は「1画面に収まらないときはページ送り」と定めています。このため T3 では、いまページ送りの無い一覧に新しいページが生まれます。たとえば facts-speed-before.md にある `/dictionary/kanji/grade/7` は、ページ送りが無く1,110件を全件描いています。
  - 13巡目までは「ページ送りが入る一覧は除く」がこれを覆っていました。除外をやめたいま、変更前に存在しない URL（2ページ目以降）が「全ページ」に入ってしまいます。そうしたページの「変更後と変更前の差」は定義されていません。
  - 文字どおりに変更前を0と読むと、そうしたページは増分がページの総量そのものになります。すると必ず最大として選ばれ、合否の線（変更後が変更前を超えない）を必ず落とします。T1a と T9 の作業者がこう読む余地があります。
- どう直すか: どちらかを1文で書いてください。
  - (a) 「変更前に無い URL は、変更前に同じ項目を描いていたページと比べる」。来訪者が同じものを見るために変更前に払っていた量と比べることになり、線の根拠と向きが揃います。こちらを推奨します。
  - (b) 「変更前に無い URL は候補に入れない」とし、その理由を書く。

**minor-2 越えたときの帰結に、中身（HTML・データ）が原因の場合が無い**

- どこ: index.md:96「フォント以外（CSS・JS・画像）が原因なら、この作業の中で減らしてから出荷する」。
- なぜ:
  - 13巡目の対応で、index.md:94 は「中身の変化で増えた分も含めて上限に掛ける」と定めました。
  - ところが帰結の括弧は CSS・JS・画像しか挙げていません。中身の変化で増えるのは、主に HTML と Next.js の RSC ペイロード（文言・データ）です。
  - 括弧を「原因の列挙」として読むと、HTML が原因で越えたときに何をするかが計画に無いことになります。その場合、作業者は「減らす」のか「中身の価値との比較で判断する」のかを自分で決めてしまいます。後者はこの計画が禁じていることです（「得との比較で上限を覆すことはしない」options.md:73）。
- どう直すか: 括弧を「フォント以外（HTML・データ・CSS・JS・画像）」にしてください。そうすれば、中身が原因のときも同じく作業の中で減らしてから出荷する、と読めます。
