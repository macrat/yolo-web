## 指摘

### Major-1: WebKit の確かめ方が、このコンテナの決まりで使えない手段（`playwright install`）に立っている

- 所: 0章の2つ目の事実、10章「確かめ方の共通の決まり」の1つ目、8章の末尾（`frontend-design` スキルに「Playwright の WebKit を入れて」と書く）、T4-2・T4-5・T4-7 の完了の条件（「Chromium と WebKit のどちらでも」）。
- 食い違い: `docs/knowledge/playwright-mcp.md` は「コンテナの決まりにより `playwright install` でブラウザを足すこともできない」と書く。設計は「`npx playwright install webkit` で、このコンテナにも入る」と書き、それを全タスクの共通の確かめ方にし、スキルにまで書き込もうとしている。0章の WebKit の事実もこの手段で得たもので、「Safari 26.5 相当」も裏付けが無い。
- 来訪者への効き方: このまま進むと、builder は決まりに反する操作をするか、完了の条件を満たせずに止まる。スキルに書けば、以後のサイクルにも広がる。結果に着いた回数の66%が WebKit なので、ここは確かめを省けない所でもある。
- 直し方（決まりの中での確かめ方）:
  1. 新しい組み方が使うのは `<wbr>`・`word-break: keep-all`（Safari 9〜）・`overflow-wrap: anywhere`（Safari 15.4〜）だけで、`auto-phrase` のような Chromium だけの機能を使わない。0章の WebKit の事実は、この外部仕様（caniuse）で書き直す。
  2. Chromium で測るときは、見出しの要素とその中の計算値が `word-break: keep-all` で、`globals.css` の `auto-phrase` が効いていないことを先に確かめる。そのうえで、字を1字ずつ Range で測り、行の切れ目が `<wbr>` の所か、文節が1行に収まらない所だけにあることを見る（設計の「文節の中で折れない」の測り方）。このとき、行の切れ目を決めるのは `<wbr>` と Zen Antique（Web フォントで両方のエンジンに同じもの）の字幅だけなので、Chromium の結果を WebKit の近似として扱える。
  3. まだ `auto-phrase` に頼る見出し（T5 が直すまでのもの）の WebKit の見え方は、棚卸し 2-5 と同じく Chromium で `word-break: normal` を当てた近似で測る。
  4. 近似で拾えない差（約物の禁則、`overflow-wrap: anywhere` の非常の折り、括弧と「！」が続く所）は、T9 の実機の iOS Safari の確かめに、具体の見出し（下の Minor-2 の型）を渡す。
  5. 10章の共通の決まり・各完了の条件の「Chromium と WebKit」・8章のスキルの文を、上の形に書き直す。この確かめ方は `docs/knowledge/playwright-mcp.md` にも足す（CLAUDE.md の knowledge の決まり）。

### Major-2: 判定の示し方が、盤に収まらず、一目でも読めない形になっている（kanji-kanaru の語・yoji-kimeru の「・」・共有の文）

- 所: 3-1・3-6・T4-11〜T4-13 の完了の条件。
- kanji-kanaru の盤は、字の列 2.5rem と判定の6列（`grid-template-columns: 2.5rem repeat(6, 1fr)`・間 0.25rem）で組む。3-1 は「いまの語（一致・近い・不一致）を残し」「語と印は `0.875rem` 以上」とする。計算すると、判定のマスの字の幅は 375px で約37px、320px で約27px しか無い。「不一致」は 14px で 42px、学年の矢印を添えた「不一致↑」は 56px で、どちらも1行に入らず、語の途中で折れる（§4）か、盤がはみ出す（§12 幅）。列の見出し（「音読み」「訓読み」42px）も同じ。設計は T4-11 に「盤がコンテンツ幅の中に収まる」を置くが、この2つの条件を同時に満たす組み方を決めていない。
- 一目で伝わるか: 6列×最大6行の盤で、判定が同じ字の色・同じ大きさの2〜3字の語だけで並ぶと、来訪者はマスを1つずつ読むことになる。いまの色の盤は、見渡しただけで「どの列が合っているか」が分かる。3-1 の B の欄は「緑と黄に慣れた来訪者の見分けは速くなる」とその得を認めながら、捨てる理由を「`DESIGN.md` の規定が誤りだと示す材料が無い」としている。これは来訪者にとっての価値を比べた判断ではなく、材料を集める手順も書かれていない。完了の条件の「グレースケールで読み分けられる」は、色に頼らないことは確かめるが、一目で読めることは確かめない。
- yoji-kimeru の「含まれない ・」: 日本語で見慣れた組は ○・△・× で、「・」は小さく弱い。同じ設計の中で「・」は irodori の共有の点数の区切りにも使われ、設計の本文の「（○・△・・）」自体が読めなくなっている。
- 共有の文の食い違い: 3-6 は「共有の文は盤と同じものでないと、画面で見た盤と人に見せた盤が別の形になる」と理由を書くが、kanji-kanaru は盤が語、共有が印で、その理由に自分で反している。
- 直し方: (1) 判定は1字の印（○・△・×。読み上げは語）で、盤のマスでも凡例でも共有でも同じにする。kanji-kanaru もマスは印にし、学年の向きは印に添える。これで 320px にも収まる。(2) 印の大きさと太さを「一目で」読める形にする（例: マスの字を本文より大きい段にする）。(3) T4-11・T4-12 の完了の条件に、いまの色の盤と新しい盤を 375px で並べて撮り、判定の分布が一目で読めるかを来訪者の目で比べる項目を足す。新しい盤が明らかに劣るなら、index.md の「`DESIGN.md` を変えるとき」の手順で §2 の判定の扱いを問い直す、と書いておく。(4) 列の見出しが 320px・375px で語の途中で折れない組み方（略さない短い語・2行の見出しの許容など）を決める。

### Major-3: ゲームの初めての来訪者が、遊び方を自動で見られなくなる

- 所: 2-6 の2つ目の箇条・11章の3つ目。
- いま kanji-kanaru などは、初めての来訪者に遊び方のダイアログを自動で開く（`GameContainer.tsx:165-166`）。設計はアコーディオンを閉じて置き、理由を「読み込みのあとに開くと盤が動く（CLS）」とする。しかし 2-6 の3つ目の箇条では、アコーディオンを盤と結果の下に置く場合もある。盤より下（最初の画面の外）で開けば盤は動かず、画面の外の移動は CLS に数えられない。また、サーバーで「開いた状態」を既定にすれば、端末の記録を待たずに開いたまま描ける。

- 直し方: 「初めての来訪者に遊び方をどう見せるか」を、閉じたまま・サーバーで開いたまま・盤の下で記録により開く、の3案以上で比べ（AP-P17）、B-621（盤と入力欄が最初の画面に入る）と CLS の両方で測って決める。
