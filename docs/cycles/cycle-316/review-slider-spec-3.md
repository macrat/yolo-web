## Major

### Major-1: 溝の色とつまみの値の一致を、(e) の幅では確かめられない。溝の枠がつまみの動く幅を縮めることも抜けている

§6 は「溝の各点は、つまみの中心をそこに置いたときの値を指す。つまみの中心は、溝の両端からつまみの幅の半分だけ内側までしか動かない」と定めています。確かめの (e) は、その一致を「色相で 1 以内」で見るとしています。

試作で、次の3つが分かりました。

1. **Chromium は、つまみを溝の枠の内側で動かす。** 溝の細い線を `border: 1px` で引くと、つまみの中心は 9〜84px の範囲で動いた（動く幅 75px）。§6 の文のとおりなら 8〜85px（77px）になる。線を内側の `box-shadow` で引くと、8〜85px になった。WebKit も同じ作り（つまみは溝の要素の中身の箱の中で動く）なので、同じになるはずである（実行環境が無く、確かめていない）。Firefox は確かめていない。
   - いまの HslSliders は溝の線を `border` で引いている。builder の項目 1 も「溝: 高さ 16px、細い線の枠」と書くだけである。このまま組むと、対応の関数が 8〜85px に止まりを置き、エンジンのつまみは 9〜84px を動く。
   - 93px の溝では 1px が色相約 4.7 にあたる。端（色相 0・360）で、つまみの下の溝の色が、つまみの値の色から色相約 5 ずれる。試作の画素で、色相 0 は 7.1 と読めた（彩度 100・明度 50）。
   - 1巡目の Major-2（最大 16 のずれ）を直すための定めが、端では 1/3 ほど残ることになる。
2. **Chromium は、つまみを整数の px に置く。** 93px の溝では、色相 180・181・182 のつまみが、どれも同じ画素（47px）に描かれた。
   - 1px は色相約 4.7 なので、正しく組んでも、つまみの中心の画素の色は、つまみの値から色相で最大 2〜3 ほど離れる。試作では、止まりの位置を正しく置いた組み方でも、色相 30 の所が 30.4、300 の所が 301.6 と読めた。
3. **彩度 20・明度 25 の色では、画素の色から色相を 1 の細かさで読めない。** この色では、色相 1 の違いが RGB で 0.42 段にしかならない。RGB の1段が色相約 2.4 にあたる。試作では、色相 0 が 6.9、300 が 295.4 と読めた。

つまり、(e) の「色相で 1 以内」は、正しく組んだ部品でも通らず、どんな組み方にも同じ値を出します。builder はこの確かめを通せないか、幅を勝手に緩めることになります。

**来訪者が受けること**: 端の色（赤の近く）を狙う人が、溝の色を頼りにつまみを置くと、つまみの値と溝の色が色相で約 5 食い違います。(e) がそれを見分けないので、食い違ったまま出荷されえます。

**直し方の向き**:

- builder の項目 1 と SKILL.md の見た目の1行に、次を書く。
  - 「溝の細い線は、つまみの動く幅を変えない形で引く」（例: 内側の `box-shadow`。WebKit・Chromium は、溝の要素の枠の内側でつまみを動かす）。
  - または、対応の関数に線の太さを入れて、エンジンのつまみの動く幅に合わせる。
  - どちらにするかは builder に任せてよい。ただし、Firefox でもつまみの動く幅が同じになることを確かめる。
- (e) を、画素の色でなく位置で確かめる形に改める。
  - エンジンが描いたつまみの中心の x と、対応の関数が値に与える x の差が 1px 以内であること。値 0・最大・真ん中と、いくつかの値で見る。
  - 止まりの色が、その値の色と RGB で各 1〜2 段以内であること（彩度 20・明度 25 を含む）。
  - 色の読み方を書くなら、「つまみを隠して、つまみの中心の x の溝の色を読み、その x が指す値の色と比べる」とする。つまみが溝の色を覆うので、つまみを隠す手順も書く。

## Minor

### Minor-1: 決定で引き受けた代価のうち、ページを送るときに値が変わることが t4-design に書かれていない

t4-design の「指・マウス・キーボードでの動き」は、iPhone ではつまみのまわりでしか動かないこと、掴んだ位置のずれを保って引けることを書いています。しかし、2巡目のレビューで試作が示した、ページを送る指で値が変わる代価が書かれていません。

- **Android の Chrome**: 溝に触れた瞬間に、触れた位置の値に変わる。そのまま縦に払うとページは送られ、値は変わったまま残る（2巡目の試作 A で、180 から 66）。
- **iPhone**: つまみのまわり（約 41×57px）から縦に払うと、ページは送られず、指の横のぶれだけ値が変わる。

イロドリの3行は、320px で高さ 132px の帯です。遊び方を読もうとページを送る指がこの帯に触れると、作っている色が変わります。見本の色が変わるので気づけますが、それでも来訪者が受ける代価です。決定はこの代価を受け入れたものと読めます。それなら、そう書くのが AP-P02 の「採った案の代価も数える」です。

**直し方の向き**: t4-design の「指・マウス・キーボードでの動き」に、上の2つを「引き受けた代価」として書く。VoiceOver のなぞる探索を保つことと比べて引き受けた、という理由も添える。

### Minor-2: 無効になった − ＋ にフォーカスがあるときの見え方が決まっていない

§6 は「無効になっても、その形にあったフォーカスは失われない」と定め、SKILL.md は `aria-disabled` を例に挙げます。無効でフォーカスを受けるものは、このサイトではこれが初めてです。

- `Button.module.css` の無効の形は、「無効のボタンはフォーカスを受けないので、outline をリングと取り合わない」として、破線の枠を `outline` で描いている。− ＋ で同じ描き方をすると、破線の枠とフォーカスのリングが同じ `outline` を取り合い、どちらか一方しか出ない。
- §6 の表では、無効は「太い破線の枠」、フォーカスは「押せる範囲の内側に密着した二重リング」である。どちらも押せる範囲の縁に出るので、重なったときにどう見えるかが決まっていない。
- 無効の形の線の色も決まっていない。§6 の無効は「文字は `--ink-2`」だが、− ＋ は字でなく太い線で描く形である。

フォーカスが − ＋ に乗るのは、読み上げの操作（NVDA のブラウズモードで押す、など）のときです。弱視で読み上げと画面を併せて使う来訪者は、それを目でも見ます。

**直し方の向き**: 無効の − ＋ にフォーカスがあるとき、二重リングと破線の枠がどう並ぶか（例: リングを先にし、破線は線の色で補う）と、無効の形の線の色を、§6 か builder の項目に書く。確かめ (g) に、そのときの画面を撮ることを足す。§6 の「押してもフォーカスをいまの場所から動かさず」と「その形にあったフォーカス」が並ぶと、形にフォーカスが乗る場面が読み取りにくいので、「読み上げの操作で形にフォーカスがあるとき」のように場面を添えるとよい。

### Minor-3: 「新しい値を読み上げで1度言う」が、スライダーにフォーカスがあるときに2度になりうる

§6 は、マウスで − ＋ を押してもフォーカスを動かさないと定めます。スライダーにフォーカスがあるまま − ＋ を押すと、次の2つが両方起こりえます。

- NVDA や JAWS は、フォーカスのあるスライダーの値が変わると、その値を読む。
- 部品の知らせも、新しい値を言う。

また、知らせを「値が変わるたび」に出す組み方をすると、矢印のキーや引く操作でも知らせが出て、引いているあいだ値を読み続けます。§6 は「押したあとは」と書いているので、意図は − ＋ だけです。しかし、builder の項目と確かめ (g) は「押すたびに新しい値が知らせに入る」だけを見ています。

**直し方の向き**: 確かめ (g) に、「矢印のキーと引く操作では知らせに入らない」「無効の形を押しても値も知らせも変わらない」を足す。スライダーにフォーカスがあるときの2度の読み上げは、builder が組み方を決めて記録する項目にする（例: そのときは知らせを出さない）。

### Minor-4: 長押しで続けて動かさない理由のうち、2つが事実と合わない

長押しを持たない決め自体は、来訪者にとってよいと判断しました（下の「問い 3」）。ただし、t4-design の理由のうち2つが事実と合いません。

- 「長押しを受けるには、iOS の長押しの既定の処理（呼び出しの表示）を部品で抑えることになり」: 長押しの呼び出し（callout）は、リンクや画像の情報を出すもので、CSS の `-webkit-touch-callout` で止められる（MDN）。線で描いた形だけのボタンには、もともと出ない。出来事を部品で抑える必要は無い。
- 「指の受け方をエンジンに任せる決めとも食い違う」: その決めは `input type="range"` の指の受け方についてのものである。− ＋ は、もともと部品が押された出来事を受け、マウスで押したときのフォーカスも部品が止める。長押しを受けても、スライダーの指の受け方には触れない。

正しい理由は、1つ目の「要る回数が1つのスライダーで 10 回ほどまでで、続けて動く速さを決めると行き過ぎが起きる」だけで足ります。iOS の標準の UIStepper は長押しで続けて動くのが既定なので、捨てる理由は、回数の小ささと行き過ぎで言うのが正確です。

**直し方の向き**: t4-design の長押しの項から、事実と合わない2つの理由を外す。「1〜2px のずれ」は測った値でなく仮定なので、ずれが大きいときは引き直してから − ＋ で詰めることになる、と添える。

### Minor-5: 確かめが約束を証明しない所

- **(g) の「画面が拡大しない（Chromium のタッチのエミュレーション）」**: Chromium は、`width=device-width` のページでは速い2度の押しで拡大しない。この確かめは、`touch-action` を掛けなくても通る。確かめるなら、− ＋ の `touch-action` の計算値が `manipulation` であることを見る。
- **(h) の「Web フォントを読む前と後で組みが替わらない」**: 320px・375px の既定では、溝が閾値を 13px 上回る。Web フォントの差し替えで `ch` が変わっても、組みは替わらない。この確かめは、閾値の近くの幅（1行の組みの溝が 5rem ちょうどになる幅の前後数 px）を見ないと、約束を証明しない。
- **§6 の「値の場所は、とりうるいちばん長い値の幅をいつも取る」**: 確かめが無い。値の桁が変わる所（色相 9→10→100、品質 95→100）で、溝の長さとつまみの位置が変わらないことを (a) か部品のテストに足す。
- **§6 の「並べたスライダーは、どの行も溝の始まりと長さを同じにする」**: (a) は左端だけを見ている。長さも見る。

### Minor-6: §5 と §6 で、− ＋ の形の置き方が食い違う

§5 は、縁が見えないもの（その並びに「スライダー」がある）について、「最初の字か形を揃え、その左右に 8px を足した字の箱を押せる範囲にする。字の箱が 44px に届かなければ、右へ広げる」と定めます。§6 の冒頭は、スライダーが − ＋ を含むとしています。そのため、字どおりに読むと、− ＋ の形は 44px の箱の左から 8px の所に置かれます。一方、§6 は「44px 四方の押せる範囲の中央に置く」と定めています。

中央に置く §6 のほうが、値を挟む形として来訪者に正しいと判断します。ただし、DESIGN.md の中で2つの文が食い違わないようにする必要があります。

**直し方の向き**: §5 の文を、並びの左端に置くものの揃え方として読めるようにする。または、§6 の − ＋ の文に、中央に置く理由（値を左右から挟む）を一言添え、§5 の「右へ広げる」が並びの左端に揃えるものの決まりだと読めるようにする。例外の注記を足す形にはしない。

### Minor-7: 1行の組みの列のあいだの間隔が決まっていない

§5 の量の帯は、「1行の組みでは列のあいだと行のあいだを 8px にする」と定めています。スライダーの1行の組みは、ラベルと溝、溝と −、− と値、値と ＋ のあいだの間隔を定めていません。溝の押せる範囲は左右に 8px 張り出すので、張り出しがラベルや − の押せる範囲とどう接するかで、溝の長さも変わります。2行の組みでも、1行目（ラベル・− ・値・＋）と溝の押せる範囲のあいだが決まっていません。§5 の「縁の見えないコントロールどうしは押せる範囲を接して並べてよい」から導けるものもありますが、ラベルはコントロールではありません。

**直し方の向き**: §6 の1行の組みと2行の組みの文に、列のあいだと行のあいだの間隔を書く。5rem の閾値の計算も、それに合わせる。

### Minor-8: 言い回しと、同じファイルに残る古い文

- `src/test/design-gate.test.ts` の頭のコメント（23 行）は、「§5 角丸は 0px。影・グロー・半透明ぼかし・グラデーションを持たない」のままである。同じファイルの WARN の文言は §5 の新しい文（「グラデーションは、移り変わりの各点を、その位置が表す値から作った色で塗るときだけ描く」）に合わせたので、ファイルの中で食い違う。CLAUDE.md のツギハギ禁止に当たる。コメントも §5 に合わせる。
- t4-design の項目 3 の「指・マウス・キーボードの出来事を部品で受けない」と、SKILL.md の「指の出来事を部品で受けない」は、字どおりに読むと − ＋ の押す出来事やマウスのフォーカス止めも含む。「`input` の上の」のように、どこの出来事かを書く。
- §5 の幅の表の「横に置くラベルと − ・値・＋ の残りいっぱい」は、ほかの所の「− と値と ＋」と言い方が揃っていない。

## 問いへの答え

1. **前の指摘**: 上の表のとおり、すべて直ったか、決定で問う必要が無くなった。部品で作る指の動きの約束は、DESIGN.md・SKILL.md・builder の項目・確かめのどこにも残っていない。(k) の下の「指での動きはエンジンに任せ、定めの確かめに含めない」も、決定と合う。引き受けた代価の記録が足りない（Minor-1）。
2. **− と ＋ の細部**
   - 名前: 刻みと単位を含む（「品質を5%下げる」）。刻みが 1 でない画像のリサイズでも誤らない。正しい。
   - 1度言う: − ＋ で押したときについては正しい。スライダーにフォーカスがあるときと、矢印・引く操作で知らせを出さないことが抜けている（Minor-3）。
   - マウスでフォーカスを奪わない: 正しい。Chromium は `tabindex="-1"` のボタンでもマウスで押すとフォーカスを移すので、要る決めである。
   - 端で無効になってもフォーカスを落とさない（`aria-disabled`）: 正しい。`globals.css` の hover の規則は、もともと `[aria-disabled="true"]` を外しているので、hover の線は出ない。無効とフォーカスが重なったときの見え方が決まっていない（Minor-2）。
   - `touch-action: manipulation`: 正しい。ただし (g) の確かめ方では、掛けたかどうかを見分けられない（Minor-5）。
   - 44px 四方に 16px の形: 正しい。内側に出るリング（6px）と形のあいだに 8px あく。§5 の「右へ広げる」とは食い違う（Minor-6）。
3. **押す回数と長押し**
   - 数は合っている。つまみの動く幅 77px で、1px は色相 4.68・彩度と明度 1.30 にあたる。1〜2px のずれは、色相で 4.7〜9.4（5〜9 回）、彩度と明度で 1.3〜2.6（1〜3 回ずつ）になり、合わせて 7〜15 回になる。
   - 長押しを持たない決めは、来訪者にとってよいと判断した。1つのスライダーで 5〜9 回押す時間は、長押しの待ち（0.5 秒ほど）と続けて動く時間と大差なく、長押しには行き過ぎの危険がある。押すたびに1刻みずつ確かに動き、見本を見ながら止められる。
   - ただし、理由の2つが事実と合わず、1〜2px が仮定であることも書かれていない（Minor-4）。
4. **§5 のラベルの文と「溝を置く列の左端」**: どちらの組みでも正しく読める。1行の組みでは、ラベルの後ろの列の左端に溝が始まり、ラベルは溝の横にある。2行の組みでは、列は並びの幅いっぱいで、溝は並びの左端から始まり、ラベルはその上の行にある。
5. **DESIGN.md と SKILL.md**: DESIGN.md は1つのいまの状態として読める。経緯の文は無く、「イロドリ」「色相」も 0 件である。§6 のスライダーの8項は、どれも理由を持ち、長すぎない。食い違いは §5 の「右へ広げる」だけ（Minor-6）。SKILL.md は DESIGN.md と揃っている。ただし、溝の線とつまみの動く幅（Major-1）と、出来事の範囲の言い方（Minor-8）を直す。
6. **builder の項目と確かめ**: 大筋は揃っていて、確かめられる形である。ただし、(e) は通らない幅を持ち（Major-1）、(g) の拡大と (h) の Web フォントは約束を証明せず（Minor-5）、値の幅と溝の長さの確かめが無い（Minor-5）。
