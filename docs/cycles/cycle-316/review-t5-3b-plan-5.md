## 指摘

### 1. 共通の完了の条件「触った `.tsx` で数が0」が、ほかのタスクの受け持ちの名前が残るファイルを触るタスクで満たせない【planner】

10章の頭（と t6-design 4章の頭、index.md の (1)）は「T5-3b のあとに終わるタスクは、触った `.tsx` で 4-g の数え方の数が0」を完了の条件にした。しかし次のタスクは、T5-3b のあとに、あとのタスクが受け持つ名前の残るファイルを必ず触る。

- **T5-3a**（T5-3b を待つ）: `BlogListView.tsx`・`KanjiListView.tsx`・`YojiListView.tsx`・`ColorListView.tsx` を触る。4つとも探す欄の名前（「題名・説明・分類・タグ・連載名で探す」「字・読み・熟語で探す」など）が2文節以上で、T5-7 の受け持ち（T5-3a → T5-7）。`StorybookContent.tsx` も触り、そこには T5-24 の受け持ちの 19 がある。
- **T5-3c**（T5-3b を待つ）: `StorybookContent.tsx` を触る（19 は T5-24 の受け持ち）。
- **T5-5b**（T5-3b より後に終わる見込み）: `ResultCard.tsx` の「もう一度挑戦する」（T5-3d の受け持ち）と `StorybookContent.tsx` を触る。T5-5a も、T5-3b のあとに終わるなら `InviteFriendButton.tsx`（T5-3d）で同じになる。

`npm run check:phrased-names` は「数が0でなければ失敗する」ので、字どおりに読めば、これらのタスクはほかのタスクの受け持ちを先取りするか、完了の条件を満たせない。括弧書き（「名前やボタンの面を新しく書くか書き換えたときに、区切りの並びで渡す」）が意図だが、条件の文はそれより広い。

直し方: 条件を「触った `.tsx` で、そのタスクが書いたか書き換えた名前と面の数が0。ほかのタスクが受け持つもの（10-5 の行）は残してよく、数え方の出力をタスクの記録に残す」のように、タスクが直すものに絞る。10章の頭・t6-design 4章の頭・index.md の (1) を同じ文にそろえる。走らせ方が「0でなければ失敗」なら、記録のために失敗させずに出す使い方（または変更の前との差を見る使い方）も 4-g に書く。

### 2. 値で渡す2文節以上の名前の列挙に漏れがあり、数え方の props の名指しが実際の型と合わない所がある【planner】

4-g は「値で渡す2文節以上の名前は、道具で 26（6本）と、…である」と列挙し、値で渡すものは「受け持ちのタスクの行に名前と出どころと出る状態を書き、その状態を 200% で測って確かめる」としている。関数は値を拾わないので、この列挙が値の名前を見つける唯一の手段だが、手元で値の出どころをたどると次が漏れている（どれも `splitIntoPhrases` が2つ以上に分ける）。

一覧の組のラジオボタンは閉じた開閉の中にあり、cron-parser のビルダーは選ばないと出ないので、既定の状態を撮る T5-26 の 68 ページの測りにも写らない。さらに一覧の選択肢の `label`（`list-browse.ts` の `BrowseChoice`・`BrowseSort`）は、並びの鍵（`TOOL_KINDS.map((choice) => choice.label)` など）と開閉のラベルの文にも使われているので、区切りの並びを渡すなら型をどこでどう広げるか（T5-3b の `ListControls` か T5-7 の `list-browse.ts` か）を決める必要がある。短いもの（7字まで）が 320px の 200% で1行に収まると測って区切りを渡さないと決めるなら、それも規則として書く必要がある。

あわせて、4-g の props の名指しに実際の型と合わない所がある。`Slider` は `label` を持たず（`items` だけ。名前は要素の `label`）、`BrowsableList` は `filterGroups`・`sortGroup` を持たず、並び順は `sorts` で受ける。builder が字どおりに関数とその単体テストを作ると、無い props を探し、`BrowsableList` の `sorts` を見ない。また T5-3b の完了の条件の単体テストの列は枝を「三項演算子と `&&`」とだけ書き、4-g の `||`・`??` が抜けている。

直し方: 手で列挙し直すのでなく、関数が名指した props に値で渡している所も「値で渡す（出る状態を 200% で測る）」として位置ごとに出す（失敗には数えない）ようにし、各タスクはその一覧を見て出どころと出る状態を行に書く形にすると、列挙の漏れが構造的に起きない。そのうえで上の表の名前を 10-3 の regex-tester・keigo-reference・yoji-search・cron-parser の行と T5-7・T5-24 の行に入れ、一覧の選択肢に区切りを渡すかと、渡すならどのタスクが `BrowseChoice`・`BrowseSort` の型をどう広げるかを決める。4-g の props を `Slider` の `items`、`BrowsableList` の `kindGroup`・`sorts` に直し、単体テストの枝に `||`・`??` を入れる。4-g と 10-3 の「26 か所・6本」も数え直す。

### 3. yoji-kimeru の入力欄の名前が JSX の断片と `nowrap` の `span` で組まれていることが書かれていない【planner】

T5-3b の行の差し込みの名前の並びの例（「`${難しさ}の`」「漢字を」「1字」「入力」「`（あと${残り}回）`」）は kanji-kanaru の文字列（`GameContainer.tsx:467` のテンプレート文字列）に当たる。yoji-kimeru は `GameContainer.tsx:494-499` で、`{difficultyNames[difficulty]}の四字熟語を入力` と `<span className={styles.remaining}>（あと{…}回）</span>` の断片を `label` に渡し、`.remaining`（`YojiKimeru.module.css:145`）は `white-space: nowrap` だけの規則である。これは括弧の数を1つの文節にするための自前の組み方で、区切りの並びに替えると `.remaining` の規則が使われずに残る。完了の条件の「`<wbr>` を組む所が `PhrasedText` のほかに増えない」ではこの残りは見つからない。

直し方: T5-3b の行に、yoji-kimeru の名前も並び（「`${難しさ}の`」「四字熟語を」「入力」「`（あと${残り}回）`」）で渡し、断片の `span` と `.remaining` の規則を消すことを書く。全組の `followsPhraseRules` のテストに yoji-kimeru の並びも入れる。

## 実装で確かめれば足りること（指摘にしない）

- `npm run check:phrased-names -- <パス>…` を vitest の上で走らせるとき、vitest の位置引数は試験のファイルの絞り込みとして読まれるので、パスは環境変数か、vitest を呼ぶ小さな台本で渡すことになる。ふだんの `npm test` でこの走らせ方が何も数えずに通ることも、実装で確かめればよい。
- 手元の数（294 / 117）と計画の数（293 / 116）の差の1つは拾い方の細部の違いの範囲で、T5-3b が関数を作ったときの数を記録すれば足りる。
- 関数のファイル名（`unphrased-names.ts`）と試験・走らせ方の名（`phrased-names`）の不ぞろいは、読み違えを生むほどではない。
