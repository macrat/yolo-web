## 指摘

### 1. `BrowsableList` の `searchLabel` の型を変えるタスクが無い【planner】

一覧の探す欄の7つ（`BlogListView`・`KanjiListView`・`YojiListView`・`ColorListView`・`HumorListView`・`PlayListView`・`ToolListView`）は、`searchLabel` を `ListControls` に直接渡しておらず、`src/components/BrowsableList/index.tsx` に渡している。`BrowsableList` の `searchLabel` は `string` 型（34行目）なので、区切りの並びは渡せない。

- T5-3b の行は `ListControls` が区切りの並びを受け取ることは書いているが、`BrowsableList` には触れていない。
- T5-7 の行も7つの一覧の部品しか挙げていない。
- 10-4 の受け持ちの表にも `BrowsableList` が無い。
- `BrowsableList` の名前が出てくるのは T5-26 のテストの部品の列だけである。

このままだと、T5-7 の builder は受け持ちの外の共有の部品を触ることになる。触らなければ、T5-26 のテストが最後に落ちる。直し方: `BrowsableList` の型の変更を T5-3b（部品の props を足す）か T5-7（使う側と同じコミット）のどちらかの行に書き、10-4 の表に行を足す。

### 2. T5a に、選択肢の区切りの完了の条件が無い【planner】

選択肢の面（`QuestionCard`）は §4 の名前の折り方で組み、区切りはサーバーで作って渡す、と 5-a の受け持ちの表と 10-5 に書かれた。しかし index.md の T5a の行にも t5-design にも、それを確かめる完了の条件が無い。

- 選択肢は値で渡すので、T5-26 のテスト（字で渡すもの）では見つからない。
- T5-26 の測り（68ページの 320px の 200%）は棚卸し 12章の手順でページを開いたときの状態を撮るので、「はじめる」を押したあとの選択肢は写らない。
- 4-g の「値で渡すものは、面ごとのタスクと T5-26 が 200% で測って確かめる」の約束が、選択肢については果たされない。

来訪者の 81% が来るのはプレイ面で、選択肢はそこでいちばん長く読まれる字である。直し方: T5a の完了の条件に、たとえば「15本の診断の全部の設問の選択肢を 320・375px の既定と 200% で数え、語の中の折れが0（1行に収まらない文節の中のものは記録する）」と、「選択肢に渡す区切りが `splitIntoPhrases` の結果であることの単体テスト」を入れる。書く場所は index.md の T5a の行か、5-a の表の T5a の欄。

### 3. 字で渡す名前と面を見つける検査が最後の T5-26 にしか無く、途中のタスクが自分の受け持ちを0にしたかを確かめられない【planner】

2文節以上の名前と面を拾う数え方は、4-g に「構文木から拾い」と書かれているだけで、リポジトリには無い。それを行う `src/test/phrased-names.test.ts` は、最後の T5-26 が置く。そのため次のことが起きる。

- T5-18 の36本の builder は、自分の道具のどれが「54 か所」「値で渡す 9 か所」に当たるかを、同じ方法で知ることができない（10-3 は合計しか書いていない）。
- T5-18 の完了の条件の 200% の測りは、見えている状態しか数えない。「コピー済み」「送信中」、エラーのとき、無効のとき、三項演算子のもう一方の枝の面は漏れる。
- T5-24 の完了の条件（「棚卸し 9章の数がどれも0」）には、区切りの項目が1つも無い。見本の20と `Button` の `phrases` の見本を足したかは、測れない。
- 漏れが最後の T5-26 でまとめて見つかると、終わったはずのタスクへ戻ることになる。

直し方の例:

- 数え方を T5-3b が関数として置く（ファイルかディレクトリを渡すと、字で渡す2文節以上を返す）。
- T5-7・T5-15・T5-18・T5-24・T5-3b 自身の完了の条件に「受け持ちのファイルでこの数が0」を入れる。
- T5-26 はそれを `src/` の全体に当てるテストにする。

あわせて、テストが拾う範囲を行に書く。

- 字の子と字の props のほか、三項演算子と `&&` の枝の字も拾う。
- 同じファイルに書いた `options`・`items` の `label` も拾う（line-break-remover の「改行をスペースに置換」は、同じファイルの `MODE_OPTIONS` にある）。
- 手で書いた区切りの並びが `followsPhraseRules` を満たすことも確かめる（4-g の B が「テストを置く」としているが、どのタスクが置くかが書かれていない）。

### 4. `ShareButtons` の面の列挙から「X でシェア」「LINE でシェア」が抜けている【planner】

T5-3b の行は `ShareButtons` と `src/lib/share-labels.ts` の面として「この結果をシェア」「はてブに追加」「URLをコピー」「結果をコピー」を挙げている。`share-labels.ts` の `SHARE_LABELS.x.text`「X でシェア」と `line.text`「LINE でシェア」も、`splitIntoPhrases` では `["X で","シェア"]`・`["LINE で","シェア"]` の2文節になる。これらは値で渡すので、T5-26 のテストでは見つからない。Web Share の無い環境では、診断・ゲーム・辞典・ブログのすべての共有の区画に出る面である。直し方: 列挙に足すか、「`share-labels.ts` と `ShareButtons` の面のすべて」と書く。

### 5. `Button` の `phrases` と `children` の関係が決まっていない【planner】

4-g と T5-3b の行は「`Button` は面の区切りの並びを `phrases` で受け取り、`children` の字は1つの文節として組む」とだけ書いている。どちらか一方だけを渡すのか、両方を渡したらどうなるのかが書かれていない。いまの `children` は必須の型である。T5-18 の36本と T5-24 がこの形で書くので、T5-3b の builder が決めて、あとで変えることになると使う側が崩れる。直し方: 形を行に書く。たとえば「`phrases` を渡すときは `children` を渡さない（型で排他にする）」。

### 6. 4-g の案 A を捨てる理由が量で書かれていない【planner】

「BudouX の分け方の表は大きく（`src/lib/phrase-breaks.ts` はクライアントに入れない）」は、量が無い。括弧の中は、決めたことを理由に挙げていて循環している。手元では、`budoux` 0.9.2 の日本語のモデルが 23,753 バイト（gzip で 9,209 バイト）で、これに分ける関数と `phrase-breaks.ts` の禁則の規則が加わる。判断は変わらない。ただ、転送量の「増分0」にこだわった事故（incident-2）の後なので、量を書いたうえで、主な理由を「BudouX は語を割るので書き手の直しがどのみち要り、B の手間は A でも減らない。そのうえで配るものが増える」の順にしておくと、後で読む人が判断を追える（AP-P01）。

### 7. T5-3b の行が大きくなり、あとに続くタスクの多くが T5-5a の終わりを待つようになった【planner・PM】

改訂で T5-3b に、道具の外の使う側への区切り（10ファイル・14か所）が加わった。このうち `InviteFriendButton`・`ResultCard` は「T5-5a のあと」に触ることになっているので、T5-3b は T5-5a（いまレビューの直しの巡目）が終わるまで完了できない。

T5-3b の部品の変更は、T5-3a・T5-3c・T5-7・T5-8・T5-15・T5-16・T5-24・T5a の8つを待たせている。いま T5-3b は1つのタスクなので、部品の変更と関わらない1つの画面の順番待ちが、この8つをまとめて止める。

直し方: 部品の変更（`PhrasedText`・名前を受け取る部品・`Button` の `phrases`・`CopyButton`・`GuessInput` と unit-converter の字・決定 (6)）と、道具の外の使う側に区切りを渡す作業を、別のタスクに分ける。後者は、部品の変更と T5-5a のあと、T5-5b・T5-20e・T6-6 の前に置く。10-1・10-4・t6-design の順序と受け持ちを、分けた名前に合わせる。「Keep task smaller」にも合う。
