### 1-4. 解き終えた画面にあとから差し込まれるもの

解き終えた画面では、character-fortune・science-thinking・japanese-culture の追加の読みもの（`ResultExtraLoader` が `next/dynamic` で読み込む）が、結果の画面が描かれたあとに「このタイプについて」の最後へ差し込まれる。差し込みは、そこから下のものを押し下げる。

**実測**（この設計の planner。HEAD 12d53461 の本番ビルドを Chromium で、GA を止めて測った。各問の最初の行を押して解き終え、結果が描かれたあとに `MutationObserver` で差し込まれた要素を拾い、結果のボックスの上端を画面の上端から 8px に置いたときの位置に直した。選択肢の並びが毎回変わるので、2回の測りで結果が違うことがある。既定の文字の大きさは2回測った小さいほう、200% は1回の値）:

- 差し込まれた位置は、どれも画面の下端より下だった。最も近いのは 1280×800 の japanese-culture で、下端から 20px 下である。
- 差し込まれたのは、結果が描かれてから 236〜325ms 後だった（既定の文字の大きさの5つの画面。手元のサーバー。来訪者の回線ではもっと遅い）。二度打ちの2打目の間隔（90〜500ms）と重なる。
- 測ったのは各本で結果1つずつである。ほかの結果では「このタイプについて」が短く、差し込みが上に来うる。T5a-7 の二度打ちの測り（6章 条件7）で、この3本の全結果について差し込みの位置を記録する。

## 2. 決めること

1. 選択肢を §6 のどの種類で組むか（押すと進むボタンか、ラジオボタンか）
2. 回答中に選択肢がすべて画面に入る組み方と送り（どちら向きに外れていても）。知識クイズでは、答えたあとの正誤・解説・「次へ」が同時に入ること
3. 押した選択肢を、§11 の操作フィードバックの長さで選択済みとして見せる形と、添える字の文言
4. 選択を見せているあいだの、同じ問への再入力の扱いと、それをどこで守るか（状態・タイマー・後始末）
5. 答えたあとのフォーカスの置き場（B-624）
6. 「もう一度挑戦する」のあと、開始の画面（「はじめる」）を見せる送り
7. 押した点の下が入れ替わる操作の2打目（T5-5b からの kanji-level 375×800 を含む）
8. 選択肢と問の見出しの区切り（4-g。`splitIntoPhrases` をサーバーで）
9. `QuestionCard.module.css` の片付け

## 4. 案1 の中身

### 4-1. 選択肢の種類（§6）

選択肢は、押すと回答が決まる**ボタン**（§6「そのページで何かが実行されるもの」）で、1行に1つずつ、行の区切りの罫線で分けて並べる。いまの組み方の種類は変えない。ラジオボタンにしない理由は2つある。

- ラジオボタンは、選ぶ操作と確かめの操作を分けないと組めない。
- 選んだだけで進める組み方は、矢印のキーで選ぶ所を動かしただけで答えが決まる。WCAG 3.2.2（入力で文脈を変えない）にも当たる。

`DESIGN.md` にこの決まりは無いので、5章の文を書く（T5a-1）。

### 4-2. 押した形・添える字・再入力

**押した形**: 押すと、その問のどの選択肢もボタンから字に替わる。字はボタンの面と同じ箱で組むので、替わっても名前の字の位置と折り返しは変わらない（4-4）。診断と知識クイズで、押したものの示し方を分ける。

- **診断**: 押したものは、次の問か結果が出るまでの 150ms（§11 の操作フィードバックの上限）、押す前と同じ下線を持ったままでいる。§6 の「実行のさいちゅう」のもの（5章）で、押したリンクが次のページが出るまで下線を持っているのと同じ種類である。その答えで次の問か結果へ進む操作が、まだ終わっていない。ほかの選択肢は下線を外し、§6 の「押しても何も起こらないもの」の答えた選択肢になる（5章。現在地・無効に並ぶ3つ目）。字は添えない。見せるのは止まった形で動きではないので、`prefers-reduced-motion` でも長さを変えない。
  - **字を添えない理由**: 150ms では字は読めず、見分けるのは形である。下線が1本だけ残る形は、行の高さも字の位置も変えずに押したものを示せるので、押しても何も動かない。字を添えると、名前の箱が2行以上なら字は必ず名前の下の行に落ち（review-t5a-design-7.md の実測: 320 で押した回の 69%、375 で 62%）、押した行が伸びて下の行が下がる。
  - **hover**: 押したあとも持ったままでいるのは下線だけである。hover は押す前と同じように応える。ポインタが押した行の上にあれば押す前と同じ線が出て、外にあれば出ない。ポインタの形も同じで、押した行の字の `span` は `cursor: pointer` を持ち、150ms のあいだにポインタが矢印に替わって戻るちらつきを起こさない（答えた選択肢は持たず、矢印になる）。そのため、字の `span` にも押す前と同じ `data-hit-area="after"` と `::after`（押せる範囲を行へ広げる指定）を持たせ、`globals.css` の行の hover の線が同じ範囲に出るようにする。マウスでは、押す前の像とピクセル単位で同じ形になる（review-t5a-design-9.md の実測）。タッチでは、tap のあとブラウザが押したボタンに hover を移して線が出ることがあるが、要素が `span` に替わると、ポインタが動くまで hover にならず、線は消える（同じ実測）。タッチの hover はブラウザが指の位置に置く名残で、来訪者が狙って出す手応えではない。押したものの印は下線で、それはタッチでも残るので受け入れる。iOS の Safari のふるまいは T9 の実機で見る。
  - **押し直し**: 見せているあいだに押した行をまた押しても、同じ答えなので何も替わらない（4-3 の reducer も受け付けない）。ほかの行は下線を外し、押しても何も起きないことが見える（R2）。
  - **読み上げ**: 押した行へのフォーカス（4-7）は、押したボタンが字に替わってもフォーカスを `body` に落とさず、キーボードの来訪者にリングを見せ続けるためのものである。読み上げの来訪者に答えが入ったことを伝えるのは、150ms のあとに次の問の見出しが読まれることである。押したのは来訪者自身なので、それで足りる。押した行の読みは、フォーカスが見出しへ移ると切られるので、押した行で何かを読ませることには頼らない（推論。支援技術はフォーカスが移るとそれまでの読みを止める）。T9 で VoiceOver の実機で診断の流れを聞く（8章）。
- **知識クイズ**: どの行も下線を外して答えた選択肢になり、正誤を字で添え、解説と「次へ」を出す（4-6）。正誤は答えたあとも残り、来訪者が読み返すものなので、形だけでなく字で言う（WCAG 1.4.1）。
  - **添えた字は、いつも名前の下の自分の行に置く。** 名前の右には置かない。どの行でも同じ置き方になり、名前の長さで並び方が変わらない。字を添えた行（押した行と正解の行）はその分だけ伸び、下の行が下がる。この形は解説と「次へ」を出す形そのもので、画面はどのみち変わり、どの行ももう押せない。2打目は 4-9 の着地の選び方が扱う。名前の字の位置と折り返しは変わらない。組みは 4-4 の「行の並び」。
- 押した名前は太字にしない。太字は字幅が広く（欧文と数字を組む IBM Plex Sans で、17px の「BGii」が 31.42 から 33.30。review-t5a-design-6.md の実測）、行の終わりの近い名前が押した瞬間に1行増えて動く。
- 添えた字も太字にしない（太さ 400）。§4 は太字を一段落に一箇所までとしており、知識クイズでは押した行と正解の行の2か所に出る。いまの `.feedbackTag` の `font-weight: 700` を外す。

**添える字**（T5a が書く文言なので、ここで決める）:

| 行                                     | 添える字             |
| -------------------------------------- | -------------------- |
| 知識クイズの押した行（正解だったとき） | あなたの回答は正解   |
| 知識クイズの押した行（誤りだったとき） | あなたの回答は不正解 |
| 知識クイズの押していない正解の行       | 正解                 |

- 1つの行には字を1つだけ添える。「あなたの回答」と「正解」を2つの字として並べると、あいだに区切りの約物か空きが要り、読み上げでは2語が区切りなしに続く（「あなたの回答正解」）。文にすれば、目でも読み上げでも1つの文として読める。
- どの字も約物を持たないので、T5-27（約物）には何も渡さない。
- 知識クイズの添える字は、§4 の補助情報の大きさで、`--ink` で組む。§7 の「来訪者の項目」の字（補助情報の位置で `--ink-2`）と違い、正誤は来訪者の操作への応えの中身そのもので、前に出ない字ではないからである。
- いまのコード（押した行が正解なら「正解」だけ）は、押したことを言わない。押した行が正解のとき、来訪者はどれを押したかを字で確かめられない。

**押しても動かないもの**: 診断では、押しても、どの行の上端・高さも、どの名前の字の位置と折り返しも変わらない。知識クイズでは、名前の字の位置と折り返しは変わらず、字を添えた行が添えた字の行の分だけ伸び、その下が下がる。起きた行と量を測って記録し、撮って目で見る（6章 条件1・3・11）。

**再入力**の扱いは次の3つを比べた。

| 扱い                                                                                        | 判断                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1 見せているあいだは受け付け、押し直した選択肢に替える                                     | 捨てる。二度打ちの2打目が指のずれで隣の行に落ちると、**来訪者の知らないうちに答えが隣に替わる**。選び直せる得も小さい。押した形を見て、違うと気づいて、隣を押し直すまでを 150ms で終えるのは難しい（推論。単純な反応時間はおよそ 200ms と言われるが、出典は確かめていない）。捨てる理由は前の文（答えが黙って替わる）で、この数には依らない |
| **R2 見せているあいだは受け付けず、押さなかった行を下線の無い字にして押せないことを見せる** | **採る。** 答えを黙って替えない。押さなかった行は §6 に加える「答えた選択肢」の形になり、知識クイズで答えたあとの形と同じである。押した行は実行のさいちゅうとして下線を持ったままで、押し直しても同じ答えなので、見せる相手が無い                                                                                                           |
| R3 次の問が出てから一定の時間は押しても捨てる                                               | 捨てる。cycle-301 で正味マイナスだった形（押せる形のまま黙って捨てる）                                                                                                                                                                                                                                                                      |

R2 は時間の窓ではない。「1つの問に答えは1つ」という不変条件で、次の 4-3 で状態の更新そのものに持たせる。

### 4-3. 状態の持ち方と、150ms のタイマー

`input-events-and-guards.md` §1 のとおり、二度打ちの2打目は別の task で届き、部品のマウントごとの ref では止められない。関数で状態を更新する形にしただけでも、2回呼ばれれば答えが2件足される。そこで、**不変条件を状態の更新そのものに持たせる**。

- 解く進み（段階・いまの問の番号・答えの並び）を、`QuizContainer` が1つの値として持ち、純粋な関数（reducer）で更新する。置き場は `src/play/quiz/quizProgress.ts`（新規）で、描画から切り離して単体で試す。
- 更新の種類と、受け付ける条件は次のとおり。条件に合わない更新は、状態を変えずに捨てる。捨てるのは、画面に見えている形がすでに「押せない」「もう移った」ことを言っている入力だけである。

| 更新                             | 受け付ける条件                                                         | 変えること                            |
| -------------------------------- | ---------------------------------------------------------------------- | ------------------------------------- |
| 始める（「はじめる」）           | 段階が開始                                                             | 段階を回答へ、番号を 0 へ、答えを空へ |
| 答える（問の id・選択肢の id）   | 段階が回答で、**名指した問がいま出ている問で、その問の答えがまだ無い** | 答えを1件足す                         |
| 進む（問の id）                  | 段階が回答で、名指した問がいま出ている問で、その問の答えがある         | 次の問へ。最後の問なら段階を結果へ    |
| やり直す（「もう一度挑戦する」） | 段階が結果                                                             | 段階を開始へ、番号を 0 へ、答えを空へ |

- **答えを記録するのは押した時**である。押した形は、記録した答えから描く（`QuestionCard` は、いまの問に記録した答えを props で受け取り、自分では選んだものを持たない）。記録と見え方が1つの値から出るので、見え方だけが先に替わったり、見えない所で答えが替わったりしない。
- **150ms のタイマーは `QuizContainer` が持つ。** 診断で、いまの問に答えが記録されたら、その問の id を閉じ込めたタイマーを掛け、150ms 後に「進む（その問の id）」を送る。知識クイズでは、「次へ」が「進む（その問の id）」を送る。進む更新も問の id を名指すので、タイマーと「次へ」の2打目が重なっても、進むのは1問だけである。
- タイマーは、答えが記録された状態を見る effect の中で掛け、effect の後始末で止める。見せているあいだにアンマウントされたとき（上端のリンクで別のページへ移るなど）も止まり、アンマウントのあとに状態を更新しない（AP-I11）。
- 結果に着いたことの計測（`trackContentEnd`）は、段階が結果に変わったときに1度だけ送る（段階を見る effect）。開始の計測（`trackContentStart`）も、段階が開始から回答に変わったときに1度だけ送る。「はじめる」の二度押しで2回送らない。
- 最後の問でも、150ms 見せてから結果へ移る。

**試験**（jsdom と偽の時計。`input-events-and-guards.md` §2 の3経路）:

1. 同じ描画の中の2回の click（1つの `act` の中で、押した行と別の行を続けて押す）→ 答えは1件、最初に押したもの。
2. 見せている 150ms のあいだに、別の task で届く click（時計を 50ms・100ms 進めてから別の行を押す）→ 答えは変わらず、最初に押した行だけが下線を持ったまま、ほかの行は下線を持たない。
3. キーボードの Enter の連打（押した行にフォーカスが残る。4-7）→ 答えは1件。
4. 検査が空振りでないことの対: 次の問が出た直後（0・50・100・200ms）に押した選択肢は、次の問の答えとして受け付けられる。
5. 見せているあいだにアンマウントし、時計を 200ms 進めても、状態の更新とエラーが無い。
6. reducer の単体: いま出ていない問への答え、答えのある問への答え、答えの無い問の進む、開始でない段階の始める、結果でない段階のやり直すを、どれも捨てる。

### 4-4. 選択肢が画面に入る組み

どれも §4・§5 に合わせる直しで、それが塊を短くもする。1-3 の「案1 の近似」はこの組みを差し込んで測ったものである。

- **問の見出し**（h2）は、§4 の「セクションの中の小見出し」の段（`--text-heading-sub`。`45rem` 未満で 1.0625rem）と見出しの行間（`--leading-heading`）にする。問は最初のセクションの中の見出しで、セクションの見出しではない。見出しの要素は h2 のまま（最初のセクションに h2 がほかに無いので、段を飛ばさない）。セクションの見出しの段（`45rem` 未満で 1.49rem）も比べたが、320px で1行 11字ほどになり、いまと同じ高さ（2〜3行×30）になるので採らない。
- **見出しの上の細い罫線**: §5 は、セクションの中の小見出しに上の細い罫線を引き、すぐ上が見出し・ラベル・ボックスの太い枠なら引かない、と決めている。問の見出しのすぐ上は進み具合の帯で、太い線で囲まれ、「3 / 12」の字を添えている。そこがすでに切れ目なので、線を引かない。§5 の文を、太い線で囲んだもの（ボックス・進み具合の帯）と言う形に書き直す（5章）。
- **余白**: 見出しの下は 16px（8 の倍数）。選択肢の行（`li`）は上下の余白と最小の高さを持たず、行の上下 8px と 44px の高さは `Button` の面が持つ（下の箇条）。行の余白を面の余白に重ねない。
- **選択肢の面は、サイトのボタンの面（`Button`）をそのまま使う。** 選択肢は §6 のボタン（押すと回答が決まる）なので、`QuestionCard` は各選択肢を `Button`（プライマリでない種類）で描き、面の大きさ・行間・上下の余白・下線・44px の高さを `Button` に任せる。`QuestionCard.module.css` が持つのは、押せる範囲を行の全体へ広げる指定（`data-hit-area="after"` と `::after`）だけで、面の字の組みを自分で持たない。選択肢はサイトのほかのボタンと同じ見え方になり、選択肢のためだけの行間や余白の決まりを `DESIGN.md` に足さずに済む。`Button` は区切りの並び（`phrases`）を受けるので、4-10 の区切りもそのまま渡せる。
  - **答えたあとの字は、ボタンの面と同じ箱で組む。** 押すと、その問の選択肢はどれもボタンから字に替わる（4-2）。字の箱を `Button` の面と同じにすれば、押して変わるのは下線が消えることと添えた字だけで、行の上端・高さと名前の字の位置と折り返しは変わらない。字の組みを決めないと、字は `body` の行間 1.85 を継ぎ、1行の選択肢では字が約 6px 上へ跳び、3行の選択肢では行が約 7px 伸びる（review-t5a-design-5.md の算術）。押した形を見せるほかに字と行が動き、§11「1つの操作に応える動きは1つだけ」から外れ、知識クイズでは解説と「次へ」も動く。
    - **共有する規則**: `.button` の箱の宣言をすべて1つの規則にまとめ、`Button` と答えたあとの字の両方が使う。`display: inline-flex`・`align-items: center`・`min-width: 44px`・`min-height: 44px`・`padding-block: 8px`・`flex-shrink: 0`・`max-width: 100%`・`line-height: 1.4` である。答えたあとの字も `data-text-box="inline"` を持ち、左右の余白と左への張り出しを `Button` と同じ `globals.css` の規則から得る。
    - **下線も共有する**: 診断で押した行の字は、押す前と同じ下線を持ったままでいる（hover は押す前と同じように応える。4-2）。`Button.module.css` の `.variantDefault` の下線の宣言（`text-decoration: underline`・`text-decoration-thickness: var(--rule-w-hair)`・`text-underline-offset: 0.15em`）を1つの規則にまとめ、プライマリでない `Button` と押した行の字の両方が使う。値を写さないので、押しても下線の太さと位置が変わらない。
    - **行の並び**: `.choice`（`li`）は `display: flex; flex-direction: column; align-items: flex-start` にする。名前の箱が上に、知識クイズの添えた字がその下に、どちらも左に寄って並ぶ。診断の行は名前の箱1つだけで、押す前も押したあとも同じ並びである。並びの向きを縦にしないと、2行以上の名前の箱は行の幅を使い切るので、添えた字は右の幅 0 に縮み、1字ずつの縦の列になる（review-t5a-design-8.md の実測: 3行の名前の行が 88.39 から 216.94 に伸びた）。
    - **添えた字の要素**: `span`（縦の並びの子なので箱として並ぶ）。字の大きさは §4 の補助情報（`--text-small`）、色は `--ink`、太さ 400、行間 1.4、下の余白 8px（名前の箱の下の余白 8px のあとに続き、罫線までに 8px をあける）。`data-text-box` は持たない。縦の並びでは `li` の内側の余白から始まり、名前の字（名前の箱は左へ張り出し、同じ幅の余白を持つ）と左の端がそろう。添えた字はフォーカスを受けず押せもしないので、字の箱もリングの変数も要らない。行は 1行の添えた字につき約 27.6（14 × 1.4 ＋ 8。review-t5a-design-8.md の実測 27.59）伸びる。
    - **入れ子も `Button` と同じにする**: 箱の規則と `data-text-box` を掛けるのは、`PhrasedText` の `span` を中に入れる箱の要素（`Button` の `button` にあたる `span`）である。`PhrasedText` の `span` にじかに `display: inline-flex` を掛けない。Firefox は flex の入れ物の子の `<wbr>` を flex の要素にするので（Bugzilla 1499348。未解決）、区切りのあいだの字がそれぞれ別の要素になり、折り返さない1列に縮んで並ぶ（review-t5a-design-7.md が Chromium で再現）。`Button` の入れ子なら `<wbr>` は flex の入れ物の子にならない。
    - WebKit の `button` は中に名前の無い箱を1つ持って組むので、押す前の `button` と押したあとの `span` の字が同じ所に来るかは、Chromium の測りでは確かめきれない。T9 の iOS の Safari の実機で確かめる（8章）。字の大きさは規則に書かず、どちらも本文の大きさを継ぐ（書けば、本文と違う大きさの中に置いた `Button` の字が変わる）。
    - 列挙が1つでも欠けると、字の幅が `Button` と違って押した瞬間に折り返しが変わる。review-t5a-design-6.md の実測（行の中の幅 272px）では、`max-width` と `data-text-box` を欠いた箱で、`Button` では2行の選択肢が1行になり、行が 19.6 縮んだ。`.button` の箱の宣言をすべて写し `data-text-box` を足した箱だけが、`Button` と同じ2行・同じ高さになった。
  - **高さの算術**: `li` が上下の余白を持たないので、行の高さは面（`Button`、答えたあとは同じ箱の字）と区切りの罫線 1 で決まる。1-3 の近似（review-t5a-design-1.md）とは次の3つが違う。
    - 1行の選択肢は、近似の 44（`li` の `min-height: 44px`。罫線を含む）から 45（面 44＋罫線 1）へ、行ごとに 1 高くなる（算術）。
    - **選択肢の字の幅が 16px 狭い。** `Button` の面は行の中の幅 W を超えず（`max-width: 100%`）、左右に 8px ずつ余白を持つので、字の幅は W − 16 になる。近似はいまの `.choiceButton`（余白 0）の幅 W で組んでいた。320 の画面では W は 250（コンテンツ幅 266 − 行の左右の余白 16）、字の幅は 234 で、16px は本文の字でほぼ1字にあたる。行の終わりの近い選択肢は1行増え、1行で約 24 伸びる。
    - **問の見出しの字の幅が 8px 狭い。** 見出しは字の箱（`data-text-box="inline"`。4-7）を持ち、左へ 8 張り出して左右に 8 ずつ余白を持つので、字の幅はコンテンツ幅 − 8（320 で 266 − 8 = 258）になる。見出しが1行増えれば約 21 伸びる。
    - review-t5a-design-6.md が、この環境の書体で character-personality Q1 の4つの選択肢を組んだところ、幅 250 では 2・3・3・3 行、234 では 3・3・3・3 行だった（参考。来訪者の端末の書体とは違う）。1行増えれば余り 50 のおよそ半分を使う。**余りは減ることがあり、どれだけ残るかは T5a-2 で測るまで分からない。** T5a-2 は `Button` の面の左右の余白と `max-width`、見出しの字の箱（余白と張り出し）を差し込んで近似して測り、`DESIGN.md` に書く文はその値に頼る。入らない問が出たら 8章の選択を先にする。
  - **§7 の行の一覧（`ItemList`。上下 16px・本文の行間）の形にしない**のは、それが別のページへ進む名前と説明を読ませて選ぶ一覧で、働きが違うからである（§12「同じ働きのコンポーネントは同じ形」は、ここではボタンとの一致を求める）。本文の行間 1.85 と上下 16px で組むと、320 の character-personality の最も高い問で約 +92（行間）と +64（余白）伸び、534 を超える（算術。1-3 の近似の 484 から）。
  - **範囲の外で見つけたもの**: 選択肢の面を確かめるときに `src` の CSS の `line-height: 1.4` を洗い、見出しを 1.4 で組む2か所（`YojiDetail` の h1・`ErrorBoundary` の見出し）が §4「見出しは行間 1.25 以下」から外れていることを見つけた。T5a の範囲の外なので、PM がそれぞれの面のタスク（T5-11・T5-17）に渡す（8章）。
- **帯の下の 24px** は `ProgressBar` が持つ。irodori と共有で、T4-14 が 180 通りを確かめた部品なので変えない。
- **押す範囲**は行全体のまま（44px 以上）。
- **`touch-action: manipulation`**: iOS の Safari は、速い2度の押しを拡大の操作に取りうる（推論。T9 の実機で確かめる）。画面を切り替える押す所を二度押しすると、切り替わった先の画面が拡大されて、来訪者が位置を見失う。`touch-action` は祖先の値と重なって効くので、開始の画面（`.intro`）と問の区画（`.stage`）に掛け、「はじめる」・選択肢・「次へ」をまとめて覆う。`manipulation` は指でつまむ拡大を残す（§12 の拡大を妨げない）。解き終えた画面（「もう一度挑戦する」・保存・共有）は `ResultCard.tsx` にあり、T5a は触らない。すぐ後に同じ画面を組み直す T6-6 に渡す（8章）。

### 4-5. 問のまとまりを見せる送り

**見せるもの**: 問のまとまり（進み具合の帯の上端から、最後の選択肢の行の下端まで）。

**いつ**: 「はじめる」を押したときと、次の問が出たとき（診断の答えのあと・知識クイズの「次へ」のあと）。送りとフォーカスをいつ・誰が行うかは 4-7 の「切り替わりのあとの送りとフォーカス」で決める（塗る前、`QuizContainer` が送ってからフォーカス）。

**どれだけ**: まとまりが画面（`visualViewport` の範囲）に丸ごと入っていれば送らない。入っていなければ、**まとまりを丸ごと入れる、いちばん小さい送り**にする。

- 下に外れているとき（「はじめる」のあとなど）は、最後の行の下端が画面の下端から 8px 上に来るまで送る。
- 上に外れているとき（知識クイズで答えたあとに下へ送り、「次へ」を押したときや、来訪者が上へ送ったあとに答えたとき）は、帯が画面の上端から 8px に来るまで上へ送る。
- まとまりが画面より高い（上下の 8px を除いた高さを超える）ときは、どちら向きでも、帯を画面の上端から 8px に置く。問の頭から読ませ、選択肢の残りは来訪者が送る（200% など）。

`revealResult` の決め方（操作の行を上端へ置く量と、結果の下端を下端へ合わせる量の少ないほう）は、見せるものが画面の下にある場合のものである。上に外れているときに当てると、下端を合わせる量のほうが大きく負になり、まとまりを画面の下端に寄せて、上に前の問の頭の残りを並べる（review-t5a-design-1.md 指摘2 の例: 帯の上端 −60・高さ 400 で、帯を上へ置く量 −68 に対し、下端を合わせる量 −202 が選ばれる）。そこで、上下どちらにも使える関数を `reveal.ts` に足す（4-9 の着地の選び方と同じ T5a-3）。単体試験に、下に外れる・上に外れる・画面より高い・入っている、の4つを入れる。

**Web フォントの読み込みで高さが変わったとき**: 問を出したあと、その問が出ているあいだに字の読み込みが終わり（`document.fonts` の `loadingdone`）、まとまりが画面から外れたら、同じ決め方で送り直す。送り直すのは、その問を出してから来訪者が自分で送っていないときだけにする。来訪者の送りと取り合わない。

**頭**: 上端（サイト名とナビ）とパンくず・h1 は、送った来訪者には画面の上の外にある。上へ送れば見える。消してはいない（3-2）。

**問の区画を低くしない**:

- 1回解くあいだ、問の区画（`.stage`）の最小の高さを、それまでに描いた区画のいちばん高いもの（知識クイズの答えたあとの形を含む）に保つ。短い問に移っても、下のよくある質問が持ち上がらない。
- これで、前の問を押した点は、次の問でも区画の中に残る（4-9 の「答えて次の問へ」の算術）。**B-623 の直しになる**。
- 「はじめる」と「もう一度挑戦する」でやり直したとき、画面の幅か文字の大きさが変わったときは、そのときの高さからやり直す。
- `min-height` なので中身は欠けない（§4「高さを固定した領域を持たない」に触れない）。
- 高い問のあとの短い問では、選択肢の下が空く。知識クイズで答えたあとの形がいちばん高いと、空きは大きい。この形を撮って来訪者の目で見る（6章 条件11）。

### 4-6. 知識クイズの答えたあと

- 解説は結果でなく、操作への応え（§8「推測への判定は操作への応えで、結果ではない」と同じ位置づけ）なので、ボックスに入れない。地（`--paper-2`）と角丸を外し、本文の大きさ・行間・`--ink` で、本文の幅（`--measure`）で組む。
- 見せるもの: 押した行と正解の行の上のほうから、「次へ」の下端まで。4-5 と同じ決め方で見せる。
  - 入っていれば送らない。押した点は押した行（押せない字）の上に残り、真下に押せるものが来ないので、4-9 の着地の選び方でもずらさない。
  - 下に外れていれば、「次へ」の下端が画面の下端から 8px 上に来るまで送る。まとまりが入る大きさなので、上のほうの行は画面の上端から 8px 以上下に残る。
  - 画面より高ければ、上のほうの行を画面の上端から 8px に置く。正誤の字を先に見せ、「次へ」は続きを読んだ先にする（200% など）。
  - 帯と問の見出しは画面の上に出てよい。index.md の条件は「正誤・解説・次へ」で、正誤は行の添えが言う。
- **高さの見込み**: 320×550 の近似の実測（1-3）では、最初の行から「次へ」の下端まで 378〜441 だった。この近似は、添えた字を名前の横に置き（いまの `.choiceText` が縮んで字の横に並ぶ）、字の幅も狭くなっていない。この設計の組みでは、添えた字の行が、押した行が誤りなら2行（押した行と正解の行）、正解なら1行加わり、約 27.6 ずつ伸びる（4-2）。加えて、1行の選択肢は行ごとに 1 高くなる（4-4。kotowaza の選択肢は1行なので 4行で +4）。最も高い kotowaza の 441 は、2行加われば約 500（441 ＋ 55.2 ＋ 4）で、534 まで約 34 残る（算術）。字の幅が狭くなって名前が1行増えれば、さらに約 24 ずつ伸びる（4-4）。条件は 375×550 で、T5a-2 が近似に添えた字の行と字の幅を入れて、375 と 320 で測る。
- 入らない問が出たら、帯と見出しを外に出しても入らない分は解説の文の長さにあたる。PM が、解説の文を短くするか（T7 と相談）を決める。

### 4-7. 答えたあとのフォーカス（B-624）

| 置き場                               | 判断                                                                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| F1 「次へ」（いま）                  | 捨てる。読み上げが正誤と解説を飛ばす。送らないので画面の外で隠れる                                                             |
| F2 解説と正誤の区画（`tabIndex=-1`） | 捨てる。区画が大きく、リングが画面より大きくなりうる。押した所から目が離れる                                                   |
| **F3 押した行（`li`）に移す**        | **採る。** B-624 の「見える場所に残る」そのまま。知識クイズでは、読み上げは行の名前と添えた字を読む。次の Tab で「次へ」に着く |

- **フォーカスを受けるのは行（`li`）で、名前の `span` ではない。** 行は `tabIndex=-1` で、プログラムからだけフォーカスを受ける。名前だけにフォーカスを置くと、名前の外にある知識クイズの添えた字（「あなたの回答は不正解」）が読まれない。診断では、押した行のフォーカスはリングを見せ続け `body` に落とさないためのもので、答えが入ったことは次の問の見出しの読み上げで伝わる（4-2）。行は押せる範囲だったのと同じ箱で、区切りの罫線が縁として見えるので、二重リングは行の全体の内側に密着して出る（§6 の「一覧の行のように視覚の単位全体が…リングも行全体に出る」と同じ位置）。globals.css の、リングを内側に置く対象の並びに、行の一覧の行（`[data-text-box="rows"] > li`）を加える。
- **知識クイズでは、押した行が解説を指す `aria-describedby` を持つ。** フォーカスが着いたときに、名前と添えの字に続けて解説が読まれ、B-624 の「解説へ進める」を1度の着地で満たす。押していない行には付けない（解説を何度も読ませない）。付けない案と比べると、付ける案は読み上げで解説まで届くのに操作が要らず、目で読む来訪者には何も変わらない。付けない案の得は、解説を2度聞かないこと（読み進めると同じ文にまた会う）だけである。付ける案を採る。VoiceOver が `tabIndex=-1` の行の説明を読むかは T9 の実機で確かめる。
- **次の問が出たときは、どの操作のあとでも、フォーカスを問の見出しへ移す。** 「はじめる」のあと・診断の答えのあと（見せる 150ms のあいだは押した行に置き、次の問が出たら移す）・知識クイズの「次へ」のあと、の3つである。いまのコードは `QuestionCard` がマウントのときに `useEffect` で移しているが、この形は下の「切り替わりのあとの送りとフォーカス」の形に改める。6章 条件5 で3つとも確かめる。見出しに着けば、読み上げは新しい問を読み、キーボードでは次の Tab で最初の選択肢に着く。「次へ」を押したボタンは消えるので、ここで移さなければフォーカスは `body` に落ちる（B-624 の続き）。
- **問の見出しのリングは、見出しの字の箱（§5）に出す。** 見出しは押せないがフォーカスを受けるもので、件数の行（`ListStatus`）と同じく `data-text-box="inline"` を持ち、ブロックの箱に字の左右の余白を足した範囲がリングの範囲になる。`outline: none` を外し、共通の二重リングに任せる。
- 行（`li`）と見出しのリングの違い: 行は区切りの罫線という縁が見えるので行の全体、見出しは縁が見えないので字の箱である（§5「縁が見えなければ字の箱を持つ」）。
- **切り替わりのあとの送りとフォーカス（持ち主・時・順）**:
  - **時**: 切り替わりのあとの送りとフォーカスは、どれも新しい画面を描いた直後、塗る前（`useLayoutEffect`）に行う。診断の答えから次の問と結果への切り替わりは、150ms のタイマーの中で起き、クリックの中では起きない。React は、クリックのような操作で起きたのでない更新の `useEffect` を、ふつう画面を塗ってから走らせる。クリックで起きた更新でも、塗る前に走ることがある、というだけで保証はしない（react.dev の `useEffect` の文書は may と書く）。`useEffect` のままでは、次の問が出た画面がフォーカスを `body` に落としたまま1フレーム塗られ、結果の画面はもとの送りの位置で1フレーム塗られてから跳ぶ（§11「1つの操作に応える動きは1つだけ」から外れ、ちらつきに見える）。いまのコードでは診断の最後の答えはクリックの中で結果に移るので、この1フレームは目立ちにくい。T5a のタイマーはそれを持ち込み、目立たせるので、T5a で防ぐ。
  - **範囲**: 問の見出しへのフォーカス（「はじめる」・診断の答え・知識クイズの「次へ」のあと）、診断で答えたあとの押した行へのフォーカス（見せる 150ms のあいだ。送らない）、知識クイズで答えたあとの送りと押した行へのフォーカス、問のまとまりの送り（4-5）、結果への送り・着地とフォーカス、「もう一度挑戦する」のあとの送りとフォーカス。
  - **マウントのときは何もしない**: この `useLayoutEffect` は、来訪者の操作（始める・答える・進む・やり直す）で画面が切り替わったあとにだけ働く。マウント（ページを開いた直後と、サイトの中の遷移で離れて戻ったときや bfcache に載らなかった戻りで部品が作り直されたとき）は、番号がマウントのときから変わらないので、送りもフォーカスも行わない。bfcache から戻ったときは、ページが離れたときの状態のまま戻り、React は描き直さず effect も走らないので、何も起きない（そのための処理は要らない）。やり直したあとの状態（段階＝開始・番号 0・答えが空）はページを開いた直後と同じ値なので、状態の値では見分けられない。そこで、reducer が受け付けた更新ごとに1つ増える数（切り替わりの番号）を状態に持ち、マウントのときの番号から変わったときだけ働く。マウントで送ったりフォーカスを動かしたりすると、ページの途中へのリンク（`#faq` など）で着いた来訪者と、戻る操作で位置を復元した来訪者の位置を壊し、読み上げは開いた直後にページの頭でなく「はじめる」を読む。
  - **持ち主**: どれも `QuizContainer` が1つの `useLayoutEffect` で行う。画面（段階・いまの問・その問の答えの有無）が変わったときに、(1) 基準の送りと着地を決めて送り（4-5・4-6・4-9・4-8）、(2) そのあとにフォーカスを `preventScroll` で移す。送りを先にするのは、フォーカスの置き場がまだ画面の外にあるときに、ブラウザがフォーカスのために勝手に送らないためである。`QuestionCard` は問の見出しと押した行の要素を `QuizContainer` から受けた ref で渡すだけにし、自分ではフォーカスを動かさない（マウントのときの `useEffect` を外す）。1か所に集めるので、送りとフォーカスの順が画面ごとに食い違わない。
  - **試験**: マウントのとき（`scrollY` を 0 以外にした状態と、`location.hash` を付けた状態で描く）に、送りの関数が呼ばれず、`document.activeElement` が `body` のままであること。やり直したあと（同じ状態の値）には送りとフォーカスが起きること。jsdom は塗りを持たないので、「塗る前」を jsdom では見分けられない（`act` は `useEffect` も流してしまう。`input-events-and-guards.md` §2 の「発見はできない」の類）。jsdom の試験は、偽の時計で 150ms 進めた切り替わりのあと、`document.activeElement` が次の問の見出しであること、結果への切り替わりのあと送りの関数が結果の着地の量で呼ばれ、フォーカスが結果のボックスにあることを確かめる。塗る前であることは実ブラウザで確かめる（6章 条件5・7 の毎フレームの記録）。
  - この React の挙動（クリックの外の更新の `useEffect` は、ふつう塗ったあとに走る）は、T5a-7 で `docs/knowledge/` に書く（5章）。
- ポインタで押したあとのプログラムからのフォーカスは `:focus-visible` にならないので、リングは出ない（ブラウザの決まりどおり）。キーボードで操作していれば出る。
- 押したボタンが字に替わると、押したボタンは文書から外れる。行へのフォーカスは同じ描画の `useLayoutEffect`（上の持ち主）で移すので、フォーカスが `body` にある状態は塗られない。測り方は 6章 条件5。

### 4-8. 「もう一度挑戦する」のあと

- 開始の画面をページの頭から見せる（`scrollY = 0`）。既定の文字の大きさでは、550 の画面で「はじめる」の下端は 533 まで（T5-4）なので入る。
- 入らないとき（200% など）は、「はじめる」の下端が画面の下端から 8px 上に来るまで送る。
- フォーカスは「はじめる」に移す（`preventScroll`。送りとあわせて 4-7 の持ち主が塗る前に行う）。
- 送りは即時（§11）。cycle-301 で、滑らかな送りの約 800ms が座標の不安定な窓になったため。
- 4-9 の着地の選び方を当てる。

### 4-9. 押した点の下が入れ替わる操作の2打目

押した点の下が入れ替わる操作は、「はじめる」（開始→問）、答え（問→問。知識クイズでは答え→答えたあと、「次へ」→問）、最後の答えか最後の「次へ」（問→結果）、「もう一度挑戦する」（結果→開始）である。知識クイズの答えは画面を切り替えないが、答えたあとの形を見せるために下へ送る（4-6）ので、押した点の下に「次へ」や解説が来うる。

| 手当て                                                        | 判断                                                                                             |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| D1 切り替わってから一定の時間、押しても捨てる                 | 捨てる。押せる形のまま黙って捨てる（cycle-301 の失敗）                                           |
| D2 click の `detail ≥ 2`（ブラウザが数える連続押し）を捨てる  | 捨てる。黙って捨てる点は同じ。iOS の Safari が2打目に 2 を付けるかも未確かめ                     |
| D3 何もしない                                                 | 捨てる。T5-5b の測りで、kanji-level の 375×800 の最後の「次へ」の2打目がおすすめのリンクに当たる |
| **D4 押した点に押せるものが来ない送りを選ぶ（着地の選び方）** | **採る**                                                                                         |

D4 は時間の窓ではなく、押せる形のまま黙って捨てることもしない。送りの量を選ぶだけなので、options.md の制約（時間の窓で回答を黙って捨てない）に触れない。来訪者の手間を何も足さずに、2打目が意図しない所へ連れていくことを減らす。

#### 着地の選び方

切り替わったあとの送りを、次の手順で選ぶ。

1. **基準の送り** s0: 操作ごとに下の表のとおり。
2. **見せる範囲** [smin, smax]: 見せるものが、決めた形で画面に入っている送りの範囲。ページが送れる範囲（0 〜 `scrollHeight − innerHeight`）で打ち切る。範囲が空なら s0 だけにする。
3. **押した点** p: 1打目の click の座標。`QuizContainer` が、捕捉の段階の `click` の受け手（`window`）で覚える。キーボードで押したとき（click の `detail === 0`）は点が無いので、s0 のまま。
4. **避けるもの**: 切り替わったあとの画面の押せるもの（`a[href]`・`button`・`summary`・`input`・`select`・`textarea`・`label`・`[role=button]`・`[role=link]`）の矩形。2つの組に分ける。
   - 第1の組: 別のページへ移るもの・開閉するもの・ボタン。操作ごとの除外は下の表。
   - 第2の組: 次の問の選択肢（「はじめる」と「次へ」のあとだけ）。
5. **選ぶ**: 基準の送りが「送らない」（s0 がいまの位置）ときと、送るときで比べ方を分ける。
   - **送らないとき**: s0 で押した点の真下に第1の組も第2の組も来なければ、送らない。来るときだけ、範囲の中を 1px 刻みで調べ、真下に第1の組が来ない送り、そのなかで第2の組も来ない送りのうち、s0 にいちばん近いものを選ぶ。点から押せるものまでの距離は見ない。
   - **送るとき**: 範囲の中の送りを 1px 刻みで調べ、押した点から第1の組・第2の組のいちばん近い矩形までの距離 d1・d2（点が矩形の上なら 0。100 で頭打ち）を求め、次の順で比べていちばん良いものを選ぶ。
     1. d1 が 0 でない（押した点そのものに第1の組が来ない）
     2. d2 が 0 でない
     3. d1 が大きい
     4. d2 が大きい
     5. s0 に近い

   分ける理由: 基準がすでにページを送るときは、来訪者はどのみち送られた先で見るものを探し直すので、見せる範囲の中で着地を選んでも、見えるものの動きは増えない。基準が送らないときは、来訪者は動かないまとまりを見ており、ずらせばそれだけで余計な動きになる。そこで、2打目が真下のものを実際に押してしまうときだけずらし、距離を空けるためには動かさない。

   範囲の中に真下の第1の組を避ける送りが無いとき、送らないときは s0 のままにする。送るときは、d1 がどの送りでも 0 なので手順5 の1・3 は差をつけず、2・4・5 で選ぶ（次の問の選択肢を真下から外し、遠ざけ、s0 に近いもの）。第1の組の矩形の中での位置（縁への近さなど）では選び分けない。その件は 6章 条件7 の合否に掛かり、8章で PM が扱いを決める。

**100 の出自**: Android は、2度の押しの距離が 100dp 以内なら二度押しとみなす（`android.view.ViewConfiguration` の `DOUBLE_TAP_SLOP = 100`。Android のソース）。Android の Chrome では CSS の 1px が 1dp にあたるので、100px を「同じ二度押しの2打目が落ちうる距離」の上限とする。iOS の Safari の同じ値は公開されていない（推論。T9 で、実機の二度押しの2打目のずれを記録する）。100 は上限なので、送るときも、押した点そのものに来ないことを先にし（手順5 の1・2）、そのうえで遠ざける。送らないときは距離を見ない（手順5）。

**操作ごとの当て方**:

- **知識クイズの答えのあとは「次へ」を避ける**: 答えたあとの形が画面に入っていれば送らず、押した点は押した行（押せない字）の上に残るので、手順5 のとおりずらさない。下へ送るときは、押した点に「次へ」が来ると、2打目が解説を読ませずに次の問へ進める。見せる範囲の中で「次へ」を真下から外し、100 まで遠ざける。
- **「はじめる」と知識クイズの「次へ」のあとは、次の問の選択肢も避ける**（第2の組）: 2打目がまだ読んでいない問に答えを入れるからである。320×550 の science-thinking（「はじめる」の下端 533・帯 368・高さ約 415）では、基準の送り 241 で「はじめる」の点が1問目の最後の選択肢に来る（review-t5a-design-1.md の算術）。見せる範囲にはまだ余り（534−415＝119）があり、点を選択肢の下へ出せる見込みがある。「次へ」は解説の下にあるので、その点は多くの問で次の問の選択肢より下（区画の空き）に来る。基準が送らないときにずらすのは、点の真下に選択肢が来る問だけで、ずらさずにおけば知識クイズの点数が、読んでいない問への答えで変わる。
- **診断の答えのあとは、次の問の選択肢を避けない**（第2の組を持たない）。診断では、押した点は前の問の選択肢の行の上にあり、次の問の選択肢も同じ所に並ぶ。点の真下に次の問の選択肢が来るのはほぼ毎問で、避ければ PV の78%が集まる面のすべての来訪者が、問ごとに選択肢の位置が動いて探し直すことになる。知識クイズの「次へ」と違うのはこの頻度である。第1の組は、問の区画を低くしない（4-5）ので点の真下に来ない。
  - 送らないとき、区画はその場にあり、点は区画の中にある。
  - 下へ送るとき、送ったあとの帯は前より上に、まとまりの下端は画面の下端から 8px 上にある。点は前の問の選択肢の上にあったので、帯より下、まとまりの下端より上に来る（算術）。
  - 上へ送るとき、点の文書の上の位置は前より上に動くが、帯の下に残る（帯は画面の上端から 8px に来て、点はそれより下にある）。区画は前のいちばん高い形の下端まで伸びているので、点は区画の中にある（算術）。
  - したがって、同じ点の2打目は区画の外（FAQ・関連・フッタ）に落ちず、送らないときの診断の答えのあとは、手順5 によりずれることが無い。基準がもともと送るとき（次の問が画面から外れるとき）は、手順5 の距離で FAQ などから遠ざけることがある。落ちうるのは次の問の選択肢で、それは B-620 の類である。見せている 150ms のあいだの2打目は押せない行に落ちる（4-2）。150ms より後の2打目が次の問に落ちる数は T9 と 6章 条件7 で記録し、B-620 の材料にする。
- **結果の範囲は、ボックスの上端の位置で決める。** 診断の結果のボックスは画面より高いことが多く、「丸ごと入る」では範囲が空になる。上端を 8px から画面の高さの 1/3 までにするのは、結果の頭（名札と結果の名前）を画面の上のほうに残し、下の約 2/3 に説明の書き出しを見せながら、押した点を押せるものから外せる幅を取るためである（550 の画面で上端約 183、下に約 367）。review-t5a-design-2.md が、いまの組みでこの幅を測った（HEAD 326a75df。15本を解き、最後に押した点について、上端を 8px から 1/3 まで 1px ずつ動かした）。診断12本は、どの画面でも上端 8px で押せるものから 100 以上離れ、ずれない。知識クイズ3本は結果のボックス（高さ 305〜346）が画面に丸ごと入り、上端 8px では押せるものから 13〜69 しか離れず、1280×800 の kotowaza では上端 8px の点が「X でシェア」（ほかのサイトへ移る）に落ちた。上端を 109 まで下げると 100 離れる。1/3 はこの件を避けられる幅で、ボックスは丸ごと見えたまま、上にページの頭が見えて何の結果かが分かる。200% と 740×360 では 1/3 の下に残る高さが小さく（200% では名前が大きく、740×360 では 1/3 が 120）、上端を 1/3 まで下げると名前が画面から外れうる（推論）。そこで、**結果の名前の下端が画面の下端から 8px 上より上にあることを、見せる範囲の条件に入れる**。名前が見えることを測って確かめるのでなく、決め方で守る。範囲が空になるのは、ボックスの上端から結果の名前の下端まで（名札を含む）が、画面の高さから上下の 8px を除いた高さを超えるときだけである。そのときは s0（上端 8px）にし、そのまま受け入れる。上端 8px は名前をいちばん多く見せる置き方で、それより良い送りは無く、PM が選べる道も無いからである。名前の残りは来訪者が送って読む。6章 条件7 は、範囲が空だった回の数と値を記録する（合否には入れない）。
- **「もう一度挑戦する」のあとの「はじめる」は避けない。** 2打目が「はじめる」を押すと、開始の画面を経ずに1問目が出る。来訪者がしようとしたこと（もう一度解く）のとおりで、答えも計測も壊れない（始める更新は開始の段階でだけ受け付け、1回だけ計測を送る。4-3）。避けると、2打目の点を開始の画面の説明の字へ出すために頭を送り上げることになり、「ページの頭から見せる」を崩す。`input-events-and-guards.md` §4 はこれを「意図しないプレイ開始」と書いているので、この判断に合わせて書き直す（T5a-7。5章）。
- **着地が s0 と違った回数と量**を、T5a-7 で操作ごと・画面ごとに記録する。送らないときにずらした回が多ければ、PM がその操作の第2の組を外すかを決める（8章）。
- **あとから差し込まれるもの**: 解き終えた画面の追加の読みもの（1-4）は、測った範囲ではどれも画面の下端より下に差し込まれ、画面の中の点の下を変えない。着地は、切り替わった直後の組みで選ぶ。条件7 で、extra を持つ3本の全結果について差し込みの位置を記録する。画面の中に差し込まれる結果が1つでもあれば、`ResultExtraLoader` の読み込みを「はじめる」のときに始め、結果と同じ描画で差し込む形にする（T5a-6 の中で直す）。Web フォントによる見出しの組み替えは、4-5 の送り直しが受け持ち、条件7 はフォントの読み込みを済ませていない新しいブラウザの文脈で測る。

選び方は描画から切り離した純粋な関数（`src/lib/reveal.ts`）にして、単体で試す。DOM から矩形を集めて送る薄い関数を別に置く。

**`docs/knowledge/` に足す React の知見**（T5a-7。React の描画の知見を置く文書があればそこに、無ければ `input-events-and-guards.md` の新しい節に）:

> **クリックの外で起きた更新の `useEffect` は、ふつう画面を塗ったあとに走る。** タイマーなどから起きた更新の `useEffect` は、ふつうブラウザに新しい画面を先に塗らせてから走る。クリックのような操作の中で起きた更新の `useEffect` は、塗る前に走ることがあるが、保証はされない（react.dev の `useEffect` の文書は may と書き、操作で起きた Effect でも塗ってから処理することがあると断っている）。画面を切り替えたあとのフォーカスと送りを `useEffect` に置くと、切り替えがクリックの中で起きていたあいだは問題が見えにくく、タイマーのあとに切り替えるようにした途端に、フォーカスが `body` にあるフレームや、送る前の位置のフレームが塗られる。切り替わりのあとのフォーカスと送りは `useLayoutEffect` に置く。jsdom は塗りを持たず `act` が `useEffect` も流すので、この違いは実ブラウザで毎フレーム `document.activeElement` と `scrollY` を記録して見つける。根拠: T5a-7 の実測（値を書く）。
