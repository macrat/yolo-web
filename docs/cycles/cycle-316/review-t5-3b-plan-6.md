## 指摘

### 1. T5-3b の行の `||` が表のセルを割り、完了の条件の大半が表示されない【planner】

10-2 の T5-3b の行（t5-design.md:815）の完了の条件に「三項演算子・`&&`・`||`・`??` の枝」を書いたが、GFM の表ではコードの中の `|` もセルの区切りになる（エスケープ `\|` が要る。同じファイルの T5-22b の行は `\|` で書いている）。このため行のセルが見出しの3つより多い5つに割れ、描いた表では完了の条件が「…三項演算子・`&&`・`」で切れ、そのあとの数え方の関数のテストの残り、`npm run check:phrased-names` の数、値で渡すものの測り、200% の測り、`CopyButton` の升、入力の行の測り、`.remaining` が無いこと、`line-break`が`strict`、`<wbr>` の所が増えないこと、がどれも表示されない（余ったセルは捨てられる）。prettier もこれを別の列とみなして整え、そのあとのコードの前後の空白を詰めている（「`Slider`の`items`」「`<wbr>`を組む所が`PhrasedText`」など）。

直し方: `\|\|` と書き、詰められたコードの前後の空白を戻す。prettier をかけたあと、この行のセルが3つであることを確かめる。

### 2. 値で渡す名前を書いたか書き換えたタスクに、それを 200% で測る条件が無い。T5-26 のあとの T7 では網も無い【planner】

10章の頭・t6-design 4章の頭・index.md の (1) の共通の条件は「そのタスクが書いたか書き換えた名前と面で、数え方の数が0」で、数え方の数は「字で渡すもの」だけを数える。値で渡す名前（`.ts` のデータ・`.map`・差し込み・字と式を含む要素）は、4-g で「その位置の受け持ちのタスクが測る」としたが、受け持ちは 4-g の 49 の内訳と 10-2・10-3 の行に書いた所だけで決まっている。そのため次の道が残る。

- T5-3b のあとに、行に値の測りを持たないタスク（T6-6・T6-9 の面、T5-4・T5-5b・T5-6・T5-19・T5-20e など）が、値で渡す名前や面を新しく書くか書き換える（例: `{saving ? "保存しています" : label}` のような面、`logic.ts` の名前）。共通の条件は通り、誰も 200% で測らない。T5-26 は「出た位置ごとに受け持ちのタスクの測りの記録がある」ことを確かめるので、そこで初めて記録の無い位置として見つかり、受け持ちのタスクはもう閉じている。
- T7（UI の文言。T5 と T5-26 のあと）は、`share-labels.ts`・道具の `logic.ts`・一覧の選択肢のような `.ts` の名前を書き換える。字で渡すものは `phrased-names.test.ts` が止めるが、値で渡すものは T5-26 の網のあとなので、200% で語の中で折れる名前がそのまま出荷に残る。index.md の (1) は「T6 を含む」と書くが、T7 には触れていない。

直し方: 共通の条件（3か所）に「そのタスクが書いたか書き換えた名前と面のうち、数え方が値で渡す所として出す位置は、名前が出る状態を開いて 320px の既定と 200% で測り、語の中の折れが0（1行に収まらない文節の中のものは記録する）。位置と状態と測った値を記録に残す」を足す。4-g の「受け持ちのタスクの行には、その状態を書く」はこの条件の一部として読めるようにし、49 の内訳は「いまある位置の受け持ち」とする。index.md の (1) に T7 も同じ条件を負うことを書く（T7 の計画はまだ無いので、ここが T7 に届く唯一の場所になる）。

### 3. `.ts` に手で書く区切りの並びが禁則で確かめられず、一覧の選択肢の `phrases` は `label` とずれうる【planner】

4-g の関数は `.tsx` の位置だけを見て、手で書いた並びの `followsPhraseRules` を確かめる。しかしこの計画で並びを書く所の多くは `.ts` のデータで、関数からは「値で渡すもの」としか見えない: 一覧の選択肢の `phrases`（`tool-list.ts`・`play-list.ts`・`blog-list.ts`・`humor-list.ts`・`src/dictionary/_lib/*-list.ts`・keigo-reference と yoji-search の `logic.ts`・`palette-list.ts`・storybook の `samples.ts`）、`share-labels.ts` の面、business-email の欄の名前 15 など。T5-3b の行が `followsPhraseRules` のテストを求めるのは `GuessInput` の2本の並びだけで、T5-7・T5-18・T5-24 の行にはこのテストが無い。200% の測りは、折れ目がたまたまその区切りに来たときしか禁則の破れ（行頭の「、」、最後の1字の行、括弧の中の区切り）を見つけない。

さらに一覧の選択肢は、`label`（並びの鍵・開閉のラベルの文・読み上げの名前に使う）と `phrases`（画面の名前）を別の欄に持つ。`phrases.join("")` が `label` と同じであることを型も関数も確かめないので、誰か（T7 の文言の見直しを含む）が片方だけ直すと、ラジオボタンの見える名前と、開閉のラベル「種別: …」や読み上げの名前が別の文になる。

直し方: 一覧の選択肢は、並びから `label` を作る形（例: 並びを受けて `label` と `phrases` をそろえて返す関数で選択肢を作る）にするなど、ずれが起きない組み方を T5-3b が決める。それが無理なら、T5-3b が「一覧の選択肢の `phrases` は `join` が `label` と同じで `followsPhraseRules` を満たす」ことを、`list-browse.ts` の型を使う全ての定義に当てるテストを置く。あわせて 4-g に「`.ts` に書く区切りの並びは、書いたタスクが `followsPhraseRules` のテストを置く」を書き、T5-3b（`share-labels.ts`）・T5-7・T5-18・T5-24 の行の完了の条件に入れる。

### 4. 値で渡す所の受け持ちの行に、測りが書かれていないものと、どこにも受け持ちの無い位置がある【planner】

4-g は値で渡す所を「受け持ちのタスクが名前の出る状態を 200% で測る」とし、T5-26 は位置ごとにその記録を確かめる。しかし受け持ちの行の条件がこれと合わない所がある。

- **T5-3a**（`IndexAccordion` の2か所）: 完了の条件に `npm run check:phrased-names` も値で渡す所の測りも無い。200% の測りは `/blog` と `/dictionary/kanji` だけで、同じ `IndexAccordion` を持つ `/dictionary/yoji`・`/dictionary/colors` の一覧を測らない。
- **受け持ちの無い位置**: 関数の「素の `button` の子」を見る規則は、`src/tools/_components/DisclosureRow/index.tsx:63-66`（yoji-search と keigo-reference の行の頭の `name`・`description`）も値で渡す所として出す。このファイルは 10-4 のどの行にも無く、49 の内訳にも入っていない。行の一覧の中身なので除くなら、4-g の「どちらにも出さない」に名指しで入れる。`ListControls` の開閉のボタンの `{label}`（T5-7 の `controlsLabel`）と nakamawake の `WordGrid.tsx` の語（T5-20e）も関数から出るが、49 の内訳に無い。受け持ちの行（T5-7・T5-20e）はその名前を測るので、内訳に入れれば足りる。

直し方: T5-3c の条件を「FAQ を持つ4つの器のそれぞれ（道具36本のほか、ゲーム・診断・辞典の代表のページ）で、320px の既定と 200% の語の中の折れが0（1行に収まらない文節の中のものは記録する）」にする。T5-3a の条件に `npm run check:phrased-names` と、`IndexAccordion` を持つ4つの一覧の 320px の既定と 200% の測りを入れる。`DisclosureRow` を除くか受け持たせるかを決め、`ListControls` の開閉・`WordGrid` を内訳に入れ、49 を数え直す。
