## blocker

### B-1. クライアント側の遷移で、段落・見出しの中で字ごとに書体が混ざる（§3「一つの見出しの中で和文の書体が混ざらない」、憲法4）

**どこが**: 次の3か所です。

- 「差し替えのずれ」の最後: 「本文はほぼ端末のゴシックになり、見出しは swap で差し替わる見込み（確かめていない）。ずれは起きない。」
- 「確かめられなかったこと」の「クライアント側の遷移」を「T1 の最初に確かめる」に回している。
- 「preload は HTML にだけ置き、RSC には入れない」という条件。

**なぜ**: 試作の中継（`proxyS.mjs` をそのまま 3301 番で起動）で、Next.js の Link による遷移を実際に確かめました。

- **ツールからツール**（`/tools/char-count` → `/tools/text-diff`・`/json-formatter`・`/line-break-remover`）: 本文の段落とリストに、BIZ UDPGothic と IPAGothic が**同じ要素の中で**混ざった（例: BIZ UDPGothic 231字＋IPAGothic 49字、混ざった要素が2つ）。
- **診断の結果面から結果面**（blazing-strategist → careful-scholar）: h1 の中で、Zen Antique 85字と端末の書体 15字が混ざった。画像 `softnav-h1.png` で、「を」「やってから」などだけがアンティーク体になっていることが目で見て分かります。
- **原因**: `<head>` の `@font-face`（家族名 "P Zen"／"P BIZ" は全ページ共通、`unicode-range` は前のページの字）が遷移のあとも残る。そのため、前のページにあった字だけが Web フォントで描かれる。
- 「HTML にだけ置く」という条件を守るかぎり、本番でも同じことが起きる。

問題はもう1つあります。PV の78%が集まる `/play/character-personality` は**リクエストごとに描くページ**です（`.next/prerender-manifest.json` に無く、`Cache-Control: private, no-store`）。「2回目のビルドで各ページの `<head>` に書く」「ビルド後の HTML に書き込む」という方法は、このページには当てはまりません。React で書けば RSC に入り、RSC に入れれば先読みでフォントが読まれる（文書自身が 36件中25件で確かめた）。つまり「HTML にだけ置く」「遷移で正しく切り替わる」「リクエストごとに描くページでも使える」の3つを同時に満たす方法が示されていません。

これは T1 の最初に確かめればよい細部ではありません。配り方の構造（家族名をページごとにするか、どこで宣言するか、preload をどの経路で出すか）を決める問題です。2ページ目以降を見る来訪者（options.md では 16.3% のセッション）の全員に影響します。

**どう直すか**:

1. 遷移のあとにページのフォントをどう扱うかを決めて、試作で確かめる。例:
   - ページごとに固有の家族名にし、その宣言をページの RSC の `<style>` で運ぶ。こうすれば、前のページの面が遷移先の字を拾わない。
   - preload は、`proxy.ts`（Next.js 16 の middleware）で文書の要求にだけ HTTP の `Link` ヘッダで付ける（`RSC`／`Next-Router-Prefetch` の要求には付けない）。
   - 遷移先の本文（optional）と見出し（swap）がどう見えるかを決める。
2. 確かめ方: ツール→ツール、結果面→結果面、辞典→辞典、ブログ→ブログの遷移で、`CSS.getPlatformFontsForNode` を使い、1つの要素に Web フォントと代わりの書体（和文）が同居しないこと。あわせて、遷移先のフォントの転送量を測る。変更前の2ページ目は Noto の分割ファイルが一部キャッシュに残るので、それと比べる。
3. リクエストごとに描くページ（プレイ面・結果面）で、この経路が成り立つことを、同じ試作で確かめる。
4. GA で、2ページ目以降の PV が全体に占める割合を確かめ、影響の大きさとして書く。

## major

### M-1. §3 への書き加え1（本文を optional にする）が「必要だ」と示されていない。代わりの手段を見落としている

**どこが**: 「差し替えのずれ」の「判断」、特に次の記述。

- 「§3 はこのままでは成り立たない」
- 「どの配り方でも最初の描画に間に合うことは保証できない」
- 「本文の書体を BIZ UDGothic に替える案は…検討から外した」
- 「HTML への埋め込み…採らない」

**なぜ**: 5つあります。

1. **HTML への埋め込み＋swap を試していない。** 埋め込みを試したのは optional のもとだけで、18回すべて失敗し、原因は調べていません。私は試作の `INLINE=1` を swap で起動し（3305番）、遅い 4G で4ページを開きました。FCP の直後に `document.fonts` を見ると、ページの層の面はすべて `loaded` でした。
   - ずれ（CLS）は、email 0.0101、palette 0.0001、プレイ面 0。
   - ブログ記事の 0.1235 は、ネットワークで遅れて届く欧文のファイルによるもので、変更前にも 0.115 ある。

   フォントが HTML と一緒に届くので、「間に合うことは保証できない」は少なくとも静的なページには当てはまりません。この案を外した理由（「RSC に入って二重になる見込み」）は確かめていない推測です。リクエストごとに描くページでの制約は B-1 と同じ構造の問題なので、あわせて検討すべきです。

2. **BIZ UDGothic を外した理由が成り立たない。** 外した理由は「欧文のずれが残る」です。しかし欧文は和文と別に扱えます。たとえば次の組み合わせは比べていません。
   - 和文は仮名が全角の UDGothic を swap にする（Zen Antique で0だったのと同じ原理）。
   - 欧文は optional にするか、メトリクスを合わせた代わりの書体（size-adjust・ascent-override。欧文では業界の標準的な手法）にする。
3. **block は「測っていない。推定」のまま外している。**
4. **「間に合った割合」は試作の条件に左右されている。**
   - 速めの 4G の結果面で、フォントの読み終わり（698ms）が FCP（744ms）より前なのに、本文が Web フォントになった回は 0/3。ブログ記事も 681 < 844 で 1/3。
   - 中継は HTML をまとめて返す（ストリーミングしない）。
   - 「表示の半分以上で端末のゴシック」は、本番を代表する値として根拠が弱い。
5. **options.md の手順との対応が書かれていない。** options.md は、示し方を規定の種類で分けています。「転送量や速さに効く規定」は、上限を越えることを T1a で示す。今回は上限を越えていない。書き加えの根拠は §3 と §12 の食い違いで、その結果、来訪者が最初に見る画面の半分以上で本文の書体が変わります。これは見た目の変更なので、手順では「変更前と変更後を来訪者の目で比べる（T9）」に当たります。ところが文書は、T1 で §3 を書き換えると決めています。

**来訪者の側での優先順位の判断**（本当に両立しないなら §12 を優先する）には同意します。§1 は本文の仕事を読みやすさとしていて、読んでいる段落が動くことは実害だからです。問題は、「両立しない」ことがまだ示されていない点です。

**どう直すか**:

- 埋め込み＋swap（静的なページと、リクエストごとに描くページの両方で）、UDGothic の swap と欧文の扱いの組み合わせ、block を、同じ矩形の比較と probe で測る。
- 1つでも §3 と §12 を両立できるなら、それを採って §3 は変えない。
- どれも両立しないときだけ書き加えを提案する。その場合、どの示し方に当たるかと、T9 の目視で来訪者に害があると分かったときの扱いを明記する。
- 「間に合った割合」は、中継がまとめて返す影響を除いた条件で取り直す。

### M-2. サイト名「yolos.net」と見出しの欧文が、代わりの明朝体（serif）で出る

**どこが**: 内訳の表の欧文 700 の「—」、64行目の「700 は本文で太字の欧文を描くページだけ」、「欧文は optional」の判断。

**なぜ**:

- 上端のロゴは、全ページで欧文の 700 です（巡回データの `plex700` = `.elnosty`）。
- 試作の表（manifest）の `bold_ascii` は、7ページのうち4ページで false になっていて、preload されていない。
- ロゴと見出しは明朝の書体の並び（`--font-mincho`）で組まれているので、欧文が間に合わないと、端末の serif（Times 系）で出ます。画像 `q1page-fast.png` で、ロゴが serif の太字になっていることが見えます。埋め込みの probe でも、h1 に `Liberation Serif` が出ています。
- §3 は「欧文は見出しも IBM Plex Sans。サイト名も favicon も欧文で、Zen Antique の欧文は細く…保たない」と定めています。代わりの serif は、まさにその理由で避けたい書体です。
- サイト名は §1 の「デザインだけで yolos.net だと分かること」の要でもあります。

**どう直すか**:

- 表と本文を直す（700 は全ページで要る）。
- 700 を全ページで preload する。
- ロゴと見出しの欧文を読み込む前の代わりの書体を、serif ではなくゴシックにする（`unicode-range` を欧文に絞り、`src: local()` で端末のゴシックを指す `@font-face` を、並びの2番目に置く、など）。
- ロゴの表示のしかた（swap にしてずれを測るか、SVG の字形にするか）を決める。

### M-3. ビルドの成り立ちは、今の段階で安く確かめられるのに回している（AP-P01・AP-WF12）

**どこが**: 「確かめられなかったこと」のビルド時間、Chromium、197MB、ビルドの機械。

**なぜ**: 4つあります。

1. **プランと機械の種類を確かめていない。** 同じ Vercel の API で直近のデプロイは取得しているので、確かめるのは容易です。
2. **ビルド時間が 45 分を越える恐れがある。** この機械（4コア、`nproc`=4）で、巡回が6並列で約20分、切り出しが4プロセスで約3.5分でした。Basic（2 vCPU）ならその倍前後かかり、2回のビルドを足すと 45 分に近いか越える見込みです。ビルドのキャッシュは最初のビルドには効きません。
3. **代わりの道にも上限がある。** GitHub Actions でビルドして `vercel deploy --prebuilt` で配る道は、Vercel「Limits」の「Static File uploads」（CLI で配るとき Hobby 100MB／Pro 1GB）と「Files」（CLI で 15,000 ファイル）に掛かりうる。197MB・数千ファイルです。「CLI deployment limits removed」の changelog と食い違うので、確かめが要ります。
4. **Chromium が起動しない既知の原因がある。** Vercel のビルドの環境（Amazon Linux 2023）には NSS が無く、Playwright の Chromium が起動しない。`installCommand` で `dnf install -y nss` を入れて解決した実例があります。そのとき、失敗しても黙ってビルドを通してしまい、中身の無いページが公開された事故例もあります。

加えて、`vercel.json` は main 以外の git デプロイを止めています。T9 の「プレビューのデプロイで MISS／HIT を測る」は CLI で配る必要があります。

**どう直すか**:

- プランと機械の種類を今確かめ、その機械でのビルド時間を見積もる。
- どの経路で配るのを標準にするかを、T1 の前に決める。
- T1 の条件に次を加える。
  - Chromium を動かす手段（`dnf install -y nss`）
  - 字の収集か切り出しが失敗したら**ビルドを失敗させる**こと
  - T9 のプレビューを CLI で配ること

T1 の最初でよいのは、Chromium の実地の起動の確認、197MB の出力、preload の具体的な実装です。ただし preload の実装は、B-1 の構造が決まってからにしてください。

- **4. 確かめられなかったこと**:
