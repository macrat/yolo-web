## 指摘事項

### 1. 閉じた目次のまま縦のスマホを横に回すと、記事の頭へ引き戻され、読んでいた所を失う（重い）

スマホの形で、目次を1度も開かずに（または開いて閉じたあとに）本文を読み進め、縦から横に回すと、ページが記事の頭（目次の元の位置）へ飛ぶ。2記事 × 3つの端末の大きさで、y=5000 から回した結果:

| 回し方            | 記事                                 | そのまま（目次を留める） | 対照（目次の `position` を `relative` にする） |
| ----------------- | ------------------------------------ | ------------------------ | ---------------------------------------------- |
| 375×667 → 667×375 | `character-counting-guide`           | 418（「はじめに」の所）  | 3103（読んでいた段落の近く）                   |
| 390×844 → 844×390 | `character-counting-guide`           | 415                      | 3292（読んでいた段落が上端）                   |
| 412×915 → 915×412 | `character-counting-guide`           | 415                      | 3332（読んでいた段落が上端）                   |
| 375×667 → 667×375 | `javascript-date-pitfalls-and-fixes` | 418（記事の最初の段落）  | 3673（読んでいた段落が上端）                   |
| 390×844 → 844×390 | `javascript-date-pitfalls-and-fixes` | 474                      | 4016（読んでいた段落が上端）                   |
| 412×915 → 915×412 | `javascript-date-pitfalls-and-fixes` | 415                      | 3958（読んでいた段落が上端）                   |

横から縦に戻しても元の所へは戻らない（418 のまま）。タブレット（768×1024 ⇄ 1024×768）は回す前も後も目次を留めるので起きず、そのままと対照の差は 12px 以内。デスクトップの形（`isMobile` なし）で幅と高さを変えても起きない（6000 のまま、または対照と同じ所）。

**原因**: スマホの形で画面の幅が変わる（回す）とき、Chromium は「回す前に画面の上の真ん中にあった要素」を拠り所にして、回したあとも同じ要素が画面の上に来るようにページを送る（Blink の `RotationViewportAnchor`。画面の中の点で当たりを取り、その要素の位置で回したあとの位置を決める）。縦の画面では、その点にあるのは上端に留まった目次なので、目次が拠り所になる。横の画面（高さ 500px 未満）では目次は留まらず、記事の頭の元の位置へ戻るので、Chromium はそこへページを送る。ルートに `overflow-anchor: none` を掛けても、目次に掛けても、結果は同じだった（CSS の送りの拠り所（scroll anchoring）とは別の仕組み）。目次を留めない対照では、拠り所は読んでいた段落になり、読んでいた所が保たれる。

**来訪者への害**: 技術記事の横に長い表やコードを見るためにスマホを横に回すのは、ありふれた操作である。そのたびに記事の頭へ戻され、読んでいた所を探し直すことになる。これは目次の設計の要（「来訪者が気づかないまま読んでいた所を失わない」、DESIGN.md の目次の段・JSDoc・知見の2章）と正面から食い違う。HEAD（目次を留めない形）では起きないので、T5-15 が持ち込んだ後退である。Android の Chrome は同じ Blink の仕組みで回すので、実機でも起きると考える（実機では確かめていない。iOS の Safari が同じことをするかは分からない）。

**直し方の方向**（どう直すかは builder が比べて決める）:

- 画面の条件が変わって目次が留まらなくなったとき、目次が閉じていれば、読んでいた所へ戻す。例: 閉じているあいだも留める条件の `change` を受け（開いているときは今の形のまま上端へ送る）、条件をまたぐ前の、目次の下に見えていた本文の要素と画面の中の位置を覚えておき、またいだあとにその要素を同じ位置へ送る。回す前に覚えるには、送りや幅の変わる前の時点の値が要るので、`scroll` のたびに軽く覚える形か、`resize` の前に取れる値で足りるかを測って決める。
- 拠り所の当たりが目次に来ない形（留めた目次の当たりを外す等）は、目次を押せなくなるので採れない。
- 直したあと、上の表の6通りに加え、開いたまま回す形（11回目の測り: 目次が上端へ送られる）、横から縦へ回す形、タブレットの回し方、デスクトップの窓の高さの変更と拡大で 500px をまたぐ形で、読んでいた所が保たれるか（開いていれば目次が上端に来るか）を、目次を留めない対照と並べて測る。試験には、閉じたまま条件をまたいだときに読んでいた要素へ戻す単体の試験を足す。
- `DESIGN.md` の目次の段に、閉じたまま画面の大きさが変わって留めるかどうかが変わっても、読んでいた所は動かないことを書く。知見のファイル（`browser-layout-and-scrolling.md`）に、スマホの形で幅が変わるときの Blink の拠り所が留めた要素を選ぶことと、対照の測りを、実測として足す。index.md の T9 の行に、Android の Chrome と iOS の Safari の実機で、閉じた目次のまま本文の途中で縦から横に回し、読んでいた所が保たれるかを確かめる項目を足すよう PM に依頼する。

### 2. 新しい2件の試験が、名前の合わない `describe` の中にある（軽い）

「開いて閉じたあとは、…受け手が残らず…」と「問い合わせる画面の条件は、CSS の目次を留める規則の条件と同じ」は、`describe("開くとき、目次が画面の上端にないと、目次が上端に来るまでページを送る")` の中に置かれている。前者は受け手の後始末、後者は条件の文字の一致を見る試験で、この `describe` の名前が言う振る舞いではない（11回目に足された「開いたまま条件をまたぐと…」「閉じているあいだは…」も同じ）。試験の一覧を読む人が、何を確かめている群かを取り違える。画面の高さの条件の受け手を見る4件（指摘1の直しで足すものを含む）を、それを言う名前の `describe`（例: 「画面の高さが目次を留める条件をまたいだとき」）にまとめる。`scrollBy` の代わりを置く `beforeEach` と `placeToc` は、両方の群が使えるよう外へ出す。
