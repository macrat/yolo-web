## 見てほしいと言われた点への答え

- **量の帯と、§2・§6・§8・§11 の書き足し**: 語と参照は5つの節で揃っている（§2 の地と塗り、§5 の線の表と幅の表、§6 の太い線の読み分け、§8 の成績の分布、§11 のボックスの中の部分）。
  - **進み具合の帯との読み分け**は、目で見る人には「3 / 10」と値の違いで伝わる。読み上げの人には、進み具合として読ませず値を言う規定で伝わる。
  - ただし、量の帯を何本も並べたときの長さの揃え方と、分布の上限が書かれていない。これは Major-1。
- **図をコンテンツ幅にしたこと**: 妥当。PC の来訪者ほど得をし、モバイルでは何も変わらない。表・コード・画像と同じ扱いになり、§5 の中で説明が1つで済む。§6 の細い線の読み分けとの関係だけが残る（Minor-1）。
- **本文の区切りの幅**: 妥当。本文の幅に引くので、全幅の罫線や、コンテンツ幅いっぱいの一覧の行の区切りと取り違えない。
- **注記の種類の語を1行目に単独で置く**: 妥当。100件のうち5件ある「最初の段落がすでに太字を持つ注記」でも、太字が並ばない。
- **§11 の reduced-motion**: 妥当。設計 6-2・T4-11 の条件と、いまの `DisclosureTriangle`・`ProgressBar` の実装を1文で覆っている。
- **経緯とツギハギ**: `DESIGN.md` に経緯の語は無い。書き足した文は、どれも来訪者にとっての理由を持ち、節の流れに収まっている。スキルに1か所、移り変わりの途中を前提にした語がある（Minor-8）。

## 指摘

### Major-1 量の帯を並べたとき、帯どうしの長さを比べられることが保証されていない。分布の上限も書かれていない

- **どこが**:
  - §5 の幅の表の「進み具合の帯・量の帯 → 添える字の残りのコンテンツ幅いっぱい」（DESIGN.md:169）。
  - §5 の量の帯の「上限に対する量（統計の分布の回数・診断の軸のスコア）」「量の名前と値を字で添え、値の字は帯の外に置く」「今回のように字で示し」（DESIGN.md:193）。
  - 設計 3-1 の「今回の行は、帯の横に『今回』と字で添えて示し」。
- **何と食い違うか**:
  - 量の帯は、並べて長さを比べるための部品である。統計の分布は回数ごとの帯の長さで分布の形を見せる。スコアの帯は軸どうしの強弱を見せる。
  - ところが幅の表は、帯の枠の長さを「その帯に添える字の残り」で決める。行ごとに添える字の幅は違う。名前（「1回」と「失敗」、「論理」と「直観的」）も、値（「3」と「12」）も違い、「今回」はその回の行にしか付かない。
  - 文のとおりに組むと、枠の始まりと長さが行ごとに違う。同じ割合でも塗りの長さが変わるので、帯の右端は分布の形を表さない。とくに「今回」を持つ行は、ほかの行より枠が短くなる。
  - 「上限」は、分布ではいちばん多い回数とも、遊んだ回数の合計とも読める。いまの実装は前者で、いちばん多い行が枠いっぱいに塗られる。どちらを採るかで見え方が大きく変わるのに、`DESIGN.md` はどちらとも言っていない。
  - 値の字を帯の右と左のどちらに置くか、どの大きさで組むかも書かれていない。進み具合の帯は「左に」「補助情報の大きさで」と決めている。スコアの値を「72 / 100」のように組むと、「添えた字で読み分ける」（進み具合は「3 / 10」、量は値）が崩れるが、それを防ぐ文も無い。
- **来訪者にどう効くか**: 解き終えた来訪者は、分布の形を一目で見たくて統計を見る。診断の来訪者は、軸どうしのどれが強いかを帯の長さで見る。枠の長さが行ごとにずれると、短い行が少なく見え、「今回」の行はいつも少なめに見える。前回の Major-1 で守ろうとした「分布の形が一目で見える」が、組み方によってはまた失われる。T4-6・T4-11・T4-12・T4-13 の builder は、これを `DESIGN.md` だけから組む。
- **直し方**（量の帯の項と幅の表を書き足す）:
  - 並べた量の帯は、どれも同じ位置から始まり、同じ長さの枠を持つ。名前・値・「今回」は、行をまたいで揃えた列に置く。
  - 幅の表は、「並べた帯では、どの行でも添える字の列を除いた同じ幅」と分かる形にする。
  - 上限を書く。統計の分布なら「いちばん多い回数」か「遊んだ回数の合計」のどちらか。診断の軸なら、その軸の満点。
  - 値の字の置き場所（帯の右）と大きさを書く。値は「n / N」の形にしないことも書く（進み具合と読み分けるため）。

### Minor-1 図の中の箱が、§6 の細い線の読み分けでは hover になる

§5 は、図の箱を「箱の地は `--paper-2`、線は `--rule-2`」で描くと決めた。これは細い線で囲まれたものである。一方、§6 の細い線の読み分け（DESIGN.md:247）は、「どれでもなければ hover」とし、読み分けに掛からないものとして「一覧の行の区切り・表の内部の線・本文の区切り・引用の左の線」だけを挙げる。

来訪者が図の箱を hover と取り違えることはまず無い。それでも文のとおりに読むと、図は §6 に反し、ほかの builder やレビューが判断に迷う。除く線の列挙に「図の中の線」を足し、「コンポーネントを囲むのではなく、コンテンツの中身として描かれる線」と一緒に言う。

### Minor-2 注記の定義「1つ以上の段落」から、箇条書きを持つ注記が外れる

ブログの注記100件のうち4件は、中に箇条書きを持つ（上の「確かめたこと」）。定義が段落だけなので、T4-17 の builder は、これらを注記の組み方で組んでよいのかを `DESIGN.md` から決められない。「本文の中で補足や注意として分けて読ませるひとまとまり（段落・箇条書き）」のように書く。

### Minor-3 §11 の「表示が自動で書き換わり続けるもの」の理由が、読み上げだけになっている

DESIGN.md:416 の理由は「読み上げでは書き換わるたびに読まれうるからである」だけである。しかし、書き換わり続ける表示は、目で見る来訪者の注意も引き続ける。WCAG 2.2.2 が自動更新を動きと同じ扱いにするのも、読み上げより、注意をそらされる来訪者のためである。

いまの文では、builder が「`aria-live` を付けなければ止める手段は要らない」と読みうる。unix-timestamp（T4-16）に止めるボタンを添える理由も弱くなる。「目で読んでいる来訪者の注意を引き続け、読み上げでも書き換わるたびに読まれうる」のように、両方を書く。

### Minor-4 「動きを2つ同時に走らせない」を一般の規定にするかの判断が、まだどこにも無い

前回、次のどちらかを求めた。

- 設計 6-2 の「最後の推測では行に動きを持たせず、結果のボックスの登場だけにする（動きを2つ同時に走らせない）」を、§11 の一般の規定として書く。
- 書かないなら、その理由を設計に残す。

PM の決定にも設計にも、この判断が無い。§11 のスクロールの項は「結果の登場と重なると動きが2つになる」を理由にしており、この考え方は §11 の中ですでに前提になっている。一般の規定として無いので、最後の推測の盤の動き（T4-11〜T4-13）が `DESIGN.md` のどの規定にも拠らない。

§11 に「UI の動きは同時に2つ走らせない。結果が出る操作では、結果の登場だけが動く」と書けば、スクロールの項と判定の動きが同じ規定から出る。書かないなら、その理由を設計に残す。

### Minor-5 「字の形を見せる字」と「字の形そのものが中身である字」の2つの言い方がある

§3 の書き出しと表と82行目は「字の形を見せる字」、76行目は「字の形そのものが中身である字」と言う。同じものを指すが、語が2つあるので、読み手は別のものかと迷う。単一情報源なので、builder が語で検索したときに片方を見落としうる。どちらかにそろえる。76行目で定義し、ほかはその語を使う。

### Minor-6 §4 の折り方の導入文「名前を割らないよう」が、書き直した見出しの項に合わない

DESIGN.md:103 は「次の2つは、名前を割らないよう折る所を限り」と言う。1つ目の項は、名前ではない見出し一般を文節で折る規定になった。導入文の「名前」は2つ目の項（名前に括弧で数を添えたもの）にしか当たらない。§4 を書き直したのに、導入文だけが古い項の言い方で残っている。「意味のまとまりを割らないよう」のように、2つの項の両方に掛かる語にする。

### Minor-7 「1字だけの行を作らない」が、スキルにだけあって `DESIGN.md` に無い

スキルの「実装の技術」（SKILL.md:74）は、「最後の文節が1字なら、その前の文節につなぎ、1字だけの行を作らない」とする。測り方の手順 2 も「1字だけの行」を数える。これは来訪者に見える組み方の規定なのに、`DESIGN.md` §4 に無い。

§4 の見出しの項に「見出しの最後の行を1字だけにしない」を足し、スキルはその作り方（前の文節につなぐ）だけを持つ。

### Minor-8 スキルの手順 3 の「まだ `auto-phrase` に頼る見出し」が、移り変わりの途中を前提にしている
