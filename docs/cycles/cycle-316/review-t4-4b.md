## 指摘

### Major-1: OGP 画像と共有の文から読みが外れていて、決定と食い違い、その扱いも記録されていない

決定（「T4-1 の3巡目の対応と T4-2 の2巡目のレビューを受けた PM の決定」の1つ目の項）は、読みを添える所を「解き終えた画面・結果のページ・OGP・共有の文」と挙げている。実装は前の2つだけで、後の2つは `result.title` のままなので読みが消えた。

- OGP 画像（`src/app/play/[slug]/result/[resultId]/opengraph-image.tsx`）は「柔和温順タイプ」だけになった（本番ビルドの画像で確認）。SNS でこの札を見る人の多くはまだ診断を遊んでいない人で、「柔和温順」「和顔愛語」「抱腹絶倒」は読めない人が少なくない。この診断は四字熟語そのものが面白さの芯で、読めない名前の札は押す気を削ぐ。OGP は見出しの折れの問題を持たない（画像の幅は十分で、`createOgpImageResponse` にはタイトルの下に字を置く場所がすでにある）。
- 共有の文（`ResultCard.tsx` の `shareText`、結果のページの `page.tsx` の `shareText`）は「…の結果は「柔和温順タイプ」でした！」になった。共有の文はただの文なので折れの問題は無く、これまで来訪者が共有してきた「柔和温順（にゅうわおんじゅん）タイプ」の形のままにしても何も壊れない。読みを外す理由が無い。
- ページの題・og:title・twitter:title も「和顔愛語タイプ | あなたの言葉センス診断の結果」になった。これは決定が明示していないが、検索結果とリンクのカードに出る題で、前は読みを含んでいた。読みで探す人（「わがんあいご」）に当たらなくなる。

builder の報告は「読みが外れるだけ」と書き、決定との食い違いとして扱っていない。決めた所に届かない実装を、判断を仰がずに済ませるのは作業の進め方の逸脱でもある（`workflow.md` の AP-WF02・AP-WF09 の趣旨）。

直し方: OGP 画像はタイトルの下に読みを補助の大きさで添える（`createOgpImageResponse` に読みを渡せるようにするか、同じ場所に置く）。共有の文は「和顔愛語（わがんあいご）タイプ」の形で読みを含める（タイトルと読みから組む1つの関数にし、解き終えた画面と結果のページで同じ文にする）。ページの題に読みを含めるかは、題の幅の上限（全角30字相当）とあわせて PM が決め、決めたことをサイクルの記録に残す。どれかを添えないと決めるなら、その理由を PM の決定として t4-design.md に残してから閉じる。

### Minor-1: 変えたデータを例に引くコメントとテストが、もう無い文のまま残った

- `src/lib/phrase-breaks.ts` の `OPEN_PAREN` のコメントの例「和顔愛語（わがんあいご）」と、`splitFirstPhraseAtWords` のコメントの例「ムササビ -- 座布団／サイズで」。

### Minor-2: OGP 画像で「——」の2つのダッシュのあいだが切れて見える

animal-personality・japanese-culture の OGP 画像（`ogp-image.tsx` の明朝の書体で組む）では、「ムササビ——座布団…」の2つのダッシュのあいだに隙間があり、「—　—」のように2本の短い線に見える（本番ビルドの画像を拡大して確認）。画面の Zen Antique ではつながっている。和文のダッシュを2つ続けるのは1本の長い線に見せるためなので、切れて見えると記号の意図が伝わらない。このタスクが OGP に持ち込んだ見え方なので、ここで直す（OGP の組みでダッシュの字間を詰めるなど）か、OGP を受け持つ T6 に、見え方と例の画像を添えて渡すことを記録する。
