## 確かめたこと

- **4-9 の受け付けの決め方と React 19 の事象の順**: 本物の2度押しは `mousedown(1)`→`mouseup`→`click(1)`→…→`mousedown(2)` と、別々の task で届く。
  1. `mousedown(1)` の時点では、`window` の捕捉の受け手が番号 N を覚える。React は `mousedown` を回答に使わないので、何も更新されていない。
  2. `click(1)` では、`window` の捕捉の受け手が先に走り、そのあと React の根の受け手が `onClick` を呼び、reducer への送りが起きる。click は React の離散の事象で、その更新は同期の優先度になる。React 19 は同期の更新を、その事象の処理の終わりか直後のマイクロタスクで描いて確定させる。離散の事象から来た描画の passive effect も、確定の終わりに同期で流す。
  3. `mousedown(2)` は次の task なので、その前に更新は確定し、番号は N+1 以上になっている。受け手が確定した番号を読める形（4-7 の `useLayoutEffect` で写す ref、または番号を依存に持って付け直す受け手）なら、比べは正しく働く。
  4. 閉じ込めた古い番号を読む形で組むと守りは働かないが、417行の jsdom の試験（答えのあとの `detail: 2` で `defaultPrevented` が真）が落ちるので気づける。

  番号は診断の 150ms のタイマーの「進む」でも増えるので、1打目が操作を起こしていなくても、その 150ms の窓の中で `detail` 1 の押し下げを始めた連続の押しは止まりうる。ただ、答えから 150ms の内で同じ所を押せばそれ自体が `detail` 2 になるので、この形に当たるのは、答えた直後に離れた所で新しく始めた連続の押しだけである。来訪者が損をする場面は見当たらず、指摘にしない。

- **守りが来訪者に効く所**: 止めるのは `detail >= 2` の `mousedown` の既定の動き（語の選択と押し下げでのフォーカスの移り）だけで、2打目の click は届く。条件7 の落ちた先の記録と着地の選び方は変わらない。

## 指摘

### 1. 条件7 の「2 でない回は数えない」がタッチの回にも掛かると読め、タッチの 500ms の回が合否から落ちる

553行は「入力: タッチ…とマウス。同じ座標を2度押す。マウスの2打目は…で送る。1打目は `clickCount: 1` で送る。2打目の `mousedown` の `detail` を捕捉の段階の受け手で記録し、2 であることを確かめる（2 でない回は測りが空振りなので数えない）」と書く。最後の文の主語が、マウスの回だけか、タッチの回も含むかが読み分けられない。

- 上の測りのとおり、マウスは `clickCount: 2` で送れば間隔によらず 2 になるので、この前提が外れる回はタッチでしか起きない。タッチの2度の tap は、500ms の間隔で2打目が `1` になる。
- タッチの回にこの文を当てると、「はじめる」と結果への切り替わりの 500ms の回が、落ちた先の記録と第1の組の合否（564行）から外れる。落ちた先の記録と合否は `detail` と関係が無い。それなのに、来訪者の大半（1-1 の WebKit 66%）が使うタッチの、しかも間隔の長い回が抜ける。
- 「数えない」も、何を数えないのか（語の選択の検査だけか、その回の全体か）が書かれていない。

直すこと: `detail` が 2 であることを前提にするのは、マウスの回の語の選択の検査（561行）だけだと書く。タッチの回は `detail` を記録するだけにして、どの間隔も落ちた先の記録と合否に数える。あわせて 561行の「2打目が落ちた先に、『もう一度挑戦する』のあとの開始の画面の字も入る。」を、直前の括弧の並び（「答えたあとの行・解説の字・次の問の見出し・結果の字」）に入れて1つの並びにする。いまは並びのあとに1文を継ぎ足した形で、並びが閉じたあとに項目が増えるので読み返しが要る。

### 2. 4-7・4-11・7章が `globals.css` に足させる `[data-text-box="rows"] > li` は、いまの継承で既に効いており、4-11 の説明の文も事実と合わない

- 315行は「globals.css の、リングを内側に置く対象の並びに、行の一覧の行（`[data-text-box="rows"] > li`）を加える」と書き、7章 T5a-5（583行）の触るファイルにも「リングを内側に置く対象に行の一覧の行を加え」とある。
- いまの `globals.css` の377〜389行の並びは `[data-text-box]` を持ち、`ul[data-text-box="rows"]` に `--focus-ring-offset`・`--focus-ring-fill` を掛けている。カスタムプロパティは子に継ぐので、`li` は何も足さなくても内側の二重リングを持つ。上の測りでも、いまのままで `outline-offset: -3px`・`… 6px inset` が出た。規則の上の説明（381〜384行）も「値は子孫に継ぐので、押せる範囲を ::after に広げた一覧の行にも同じリングが出る」と、継承に頼る形をすでに書いている。
- 足せば、同じことを2か所で言う選択子が1つ増え、継承に頼ると書いた規則の上の説明とも食い違う。
- 434行（4-11 の `data-hit-area` の説明の書き直し）の「リングは `[data-text-box="rows"] > li` の規則が行に出す」も事実と合わない。その選択子の規則（428〜430行）が持つのは `padding-inline` だけである。リングを出すのは `:focus-visible` の規則で、内側に置く値は `ul` の `[data-text-box]` から継いでいる。このまま書けば、コードの説明が誤りになる。

直すこと: 315行と 583行の「加える」を外し、`li` のリングは `ul`（`data-text-box="rows"`）から内側に置く値を継いで行の内側に出る、と事実を書く。434行の説明の中身も、「フォーカスを受けるのは `li` で、リングは共通の `:focus-visible` の規則が、`ul` の `[data-text-box]` から継いだ内側の値で行に出す」の類に直す。条件5 の知識クイズの箇条（546行）には、押した行のリングが行の内側に出ること（`outline-offset` が負）を見る1項を足すと、継承に頼る形が崩れたときに気づける。
