## 指摘

### 指摘1（保存の計測）: 押し続けると、落ちる画像と `save` の数が重なる

`handleSaveImage` は、書体の読み込みを待つ非同期の処理になった。ところが、処理のあいだにもう1度押されるのを止めていない。Chromium で「画像を保存」を2度続けて押すと、同じ画像が2枚落ち、`trackSave("irodori", …)` が2回送られた。

- 来訪者から見ると、同じファイルが2つ保存される（`irodori-222 (1).png` など）。
- 計測から見ると、1人の1回の保存が2回に数えられる。T6-9 の目的は「保存を計測する」ことで、この画像の保存はまだ28日で0回の面である（2-2）。最初の数から水増しされる。
- 同じ役目の `FudaActions` は、`runExclusively`（`busyRef`）で処理中の押下を捨てている。irodori だけがそれを持たない。

直し方: 画像を作って落とすあいだ、次の押下を受けないようにする（`FudaActions` と同じく ref で守る）。単体テストに「処理のあいだに2度押しても、`downloadImage` と `trackSave` は1回」を足す。`generateResultImage` が例外を投げたときに押せないままにならないよう、`finally` で守りを外す。

### 指摘2（ツギハギ）: `share.test.ts` の中で、前からある試験と足した試験の書き方が食い違う

`share.ts` は、`イ…` の逃がし字を実の字に書き直し、コメントも日本語に直した。ところが、同じファイルを試す `share.test.ts` の `generateShareText` の試験は、前のまま残っている。

- 試験の名前は英語（"includes puzzle number" など）。
- 期待値は `ランク`・`#イロドリ #yolosnet` の逃がし字（68・73・85行）。

足した `layoutResultImage`・`rankPhrases` の試験は、日本語の名前と実の字で書かれている。このため、1つのファイルの中で、どこから足したかが見える。

また、"ends with the hashtags …"（73行）と "includes hashtags"（85行）は、同じハッシュタグの行を2度試している。

直し方: `generateShareText` の試験を、足した試験と同じく日本語の名前と実の字に書き直し、重なる1件を消す（CLAUDE.md「ツギハギ禁止」）。

### 指摘3（記録）: `ShareSurface` の食い違いを、T6-6 への引き継ぎとして記録に残す

判断3のとおり、`analytics.ts` を触らないのは正しい。ただ、コミットの時点から HEAD のコメントが実際と食い違う。t6-log.md の T6-9 の記録に、次の3つを書くこと。

- 食い違う2つの文（`"fuda"` の説明と「ゲームなどは `surface` を省く」）
- それを T6-6 が 3-1 の文に書き換えること
- irodori の `save` が `surface="fuda"` を持って送られ始めること

あわせて、T6-9 の完了の条件の記録（前と後の PNG、見本の座標、字の高さ、枠の一致、実際の操作の `save`）も、同じ所に残すこと。
