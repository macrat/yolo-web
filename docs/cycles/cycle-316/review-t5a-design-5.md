## 確かめたこと

- **`Button` が設計の求めるものを持つか**:
  - プライマリでない種類と `phrases`: `ButtonFace` が `phrases` と `children` を排他で受け、`PhrasedText as="span"` で組む。既定の種類は `data-text-box="inline"` を持ち、下線を持つ。
  - `data-hit-area="after"` と `::after`: `Button` は `{...rest}` を最後に広げるので `data-hit-area` を渡せ、`className` も足せる（TSX は `data-*` の属性を props の型で拒まない）。`globals.css` の hover の規則は `[data-hit-area]` を除き、`[data-hit-area="after"]:hover::after` と `:focus-visible::after` が線とリングを `::after` に出す。行の `--hover-line`（`[data-text-box="rows"]` の左右だけの線）はボタンに継がれる。`.button` は `position` を持たないので、`::after` の `inset: 0` は `position: relative` の `li` に掛かる。字の左端は、ボタンの `margin-inline-start: −8px` と `padding-inline: 8px` で、行の `padding-inline: 8px` の位置のまま変わらない。**行の全体を押せる範囲にする決まりは `Button` と両立する。**
  - 答えたあとの押せない形: `Button` は押せない形を「無効」（破線の枠）しか持たず、設計はそれを使わずにボタンを字（`PhrasedText as="span"`）に替えるので、`Button` に足すものは無い。替えたあとの字の組みは設計に無い（指摘1）。
  - `li` へのフォーカス・`touch-action`: どちらも `Button` の外（`li` の `tabIndex=-1` と `globals.css` の並びへの追加、`.intro`・`.stage` への指定）で、`Button` の支えを要らない。`touch-action` は祖先の値と重ねて効くので、`.intro`（`QuizContainer.module.css` 25行）と `.stage`（16行）に掛ければ中のボタンを覆う。
- **切り替わりの番号と StrictMode**: 開発時の StrictMode は effect を「走らせる→後始末→走らせる」と2度走らせるが、状態（番号）は保たれ、2度とも同じ番号で走る。「マウントのときの番号から変わったときだけ働く」は、マウントのときの番号を ref に取っても、前に扱った番号を ref に取っても、2度とも働かない。reducer が開発時に2度呼ばれても純粋なので番号は1つだけ増える。やり直しは番号を変えるので働く。考え方は正しい。
- **constitution**: 違反は無い。

## 指摘

### 1. 行（`li`）の上下の余白と、答えたあとの字の組みが決まっておらず、押した瞬間に行と字が動く

4-4 は「選択肢の面は…`Button` の面…上下の余白…を `Button` に任せる」「`QuestionCard.module.css` が持つのは、押せる範囲を行の全体へ広げる指定…だけ」と書く一方で、同じ 4-4 の「余白」の箇条に「選択肢の行の上下は 8px」を残し、4-11 は「`.questionText`・`.choice`・添える字を 4-2・4-4 の値にする」とする。`.choice` は `li` なので、書いてあるとおりに組むと `li` の `padding-block: 8px` に `Button` の `padding-block: 8px` が重なり、行ごとに 16px 伸びる。character-personality の最も高い問（余り 50）は、選択肢が4つなら約 +64 で 534 を超える（算術）。

もう1つの抜けのほうが来訪者に見える。押すと、その問の選択肢はどれもボタンから字（`PhrasedText as="span"`）に替わる（4-2・4-10）。ボタンの面は上下 8px・行間 1.4・最小の高さ 44px で字を上下の中央に置くが、字のほうは組みが書かれていないので、`body` の行間 1.85 を継ぎ、上下の余白を持たない。17px の字で（`li` の上下の余白 0、`min-height: 44px` を残す場合の算術）:

| 選択肢 | ボタンの行（面＋罫線） | 字の行（1.85）      | 押した瞬間の差             |
| ------ | ---------------------- | ------------------- | -------------------------- |
| 1行    | 45、字の上端 約 13.5   | 44、字の上端 約 7.2 | 行 −1、字が約 6px 上へ跳ぶ |
| 2行    | 64.6                   | 63.9                | −0.7                       |
| 3行    | 88.4                   | 95.4                | +7                         |

- 押した行の字が上に跳び、上の行の高さが変われば押した行そのものも上下する。4-2 の「押した行は動かず、下がるのは押せない行なので」は、この組みでは成り立たない。押した形を見せることのほかに字と行が跳ぶ動きが加わり、§11「1つの操作に応える動きは1つだけ」から外れる。
- 知識クイズでは行の高さの変わりが解説と「次へ」の位置を動かし、4-9 の「入っていれば送らない。押した点は押した行の上に残る」の前提も崩れる。
- 4-4 の「高さの算術」も前提が違う。1-3 の近似（review-t5a-design-1.md）は `li` の `min-height: 44px` を外していない（`box-sizing: border-box` なので罫線を含んで 44）ので、1行の行はすでに 44 だった。`Button` にすると 45 になり、差は「約 3」でなく 1 である（`li` の上下の余白を 0 にした場合。8 を残せば 17）。

直すこと:

- 4-4 の「余白」の箇条と 4-11 で、`li` は上下の余白を持たず（`min-height` も `Button` の 44px に任せるか、持つならその理由）、行の上下 8px は `Button` の面の余白であることを1つの書き方にする。「高さの算術」を直す。
- 答えたあとの字を、ボタンの面と同じ箱で組むと決める（字の大きさ・行間 1.4・上下 8px・最小の高さ 44px と上下の中央・左右の余白）。押して変わるのは下線が消えることと、押した行の太字と添えた字だけにする。4-11 の片付けの対象に、いま `.choiceText`（1rem・行間 1.6）があることも書く。
- 5章の §6 の「答えた選択肢」の行に、ボタンの面と同じ位置と大きさの字であること（押しても動かないこと）を入れるかを決める。入れれば、ほかの面で同じ形を作るときにも守られる。
- 6章 条件3 に、押す前と押したあと（50ms 前後）で、各行の上端と名前の字の位置が変わらないこと（添えた字が名前の下に落ちた行より下の行が下がることは除く）を加える。

### 2. bfcache から戻ったときを「マウント」と書いている

4-7 の「マウントのときは何もしない」は「ページを開いた直後と bfcache から戻ったとき（マウント）」と書く。bfcache から戻ったページは、JavaScript の状態ごと凍結から戻るだけで、React は描き直さず、effect も走らない。つまり番号の仕組みが何もしなくても、送りもフォーカスも起きない（3-2 の「離れたときの状態と位置のまま戻り」はこれと合う）。いっぽう、戻る操作で実際にマウントが起きるのは、サイトの中のリンクで別のページへ移って戻ったとき（App Router のクライアントの遷移で、クイズの部品が作り直される）と、bfcache に載らなかったときである。

いまの書き方のままでは、bfcache で守りが要ると読め、`pageshow` を扱う処理を足すなど、要らない実装を誘う。条件5 の「ほかのページから戻る操作で途中の位置に戻ったとき」も、どちらの戻り方かで起きることが違うのに分けていない。

直すこと: 4-7 を、「マウント（ページを開いた直後と、サイトの中の遷移や bfcache に載らない戻りで作り直されたとき）は、番号が変わらないので何もしない。bfcache から戻ったときは React が描き直さないので、何も起きない」の形に直す。条件5 の戻る操作を、サイトの中のページから戻る場合と、ほかのサイトから戻る場合（bfcache。`pageshow` の `persisted` を記録する）の2つに分ける。
