## 指摘

### Minor-1: 件数の行の並び順の語と0件の文が、まだ語の途中で折れる

**どこで何が起きているか**: `statusPhrases`（`src/lib/list-browse.ts`）は、並び順の語（`・${sortLabel}`）と0件の文（`条件に合う${unitNoun(unit)}はありません`）を `keep: false` にして、通常の禁則処理に任せている。文字サイズ 200% では、ここが語の途中で折れる。

| 画面             | ページ                                   | 折れ方                                            |
| ---------------- | ---------------------------------------- | ------------------------------------------------- |
| 320px・200%      | `/dictionary/colors/category/achromatic` | 「全10色・明るい」「順」                          |
| 320px・200%      | `/dictionary/humor`                      | 「全30語・五十音」「順」                          |
| 360・375px・200% | `/dictionary/kanji/stroke/21`〜`23`      | 「全6字・読みの五十」「音順」                     |
| 414px・200%      | 同上                                     | 「全6字・読みの五十音」「順」                     |
| 360px・200%      | `/dictionary/kanji?q=zzzz`               | 「条件に合う字はあ」「りません」「（全2,136字）」 |
| 375px・200%      | `/blog?q=zzzz`                           | 「条件に合うものはあ」「りません」「（全86件）」  |
| 480px・200%      | `/blog?q=zzzz`                           | 「条件に合うものはありませ」「ん（全86件）」      |

無彩色の 320px・200%（light）、23画と0件の 375px・200%（dark）を撮り、画面でも同じ折れ方を確かめた。

**来訪者にどう効くか**: 文字を大きくして読む来訪者が、「順」「ん」の1字だけの行や「あ／りません」を読むことになる。前回の Minor-3 で直した「字／目」と同じ種類の読みにくさで、直ったのは数と単位の部分だけである。並び順の語は、10件以下の一覧（部首・画数の多くと無彩色）と、並び順を1つしか持たない一覧（ユーモア辞典・学年が1つの画数）で必ず出る。0件の文は、名前の欄に打って当たらなかった来訪者が、次に何をするか決めるときに読む文である。PM の依頼の条件「320px と文字サイズ 200% で語の切れ目でしか折れない」も満たしていない。

**直し方**: 並び順の語と0件の文も、`keep` の語に分けて組む。

- 並び順の語は「・」を前の語に付け（「・」は行頭に置かない約物）、ラベルは文節で分ける（「読みの」「五十音順」、「明るい順」「五十音順」「学年順」はそれぞれ1語）。ラベルを文節で分けた形は、並び順の定義の側（`BrowseSort`）で持つか、`statusPhrases` が決まった区切りで分けるかを builder が決める。
- 0件の文は「条件に合う」「字は」（「ものは」）「ありません」のように文節で分ける。
- ListStatus のテストに、並び順の語と0件の文の分け方を足す。直したあと、320・360・375・414・480px の 200% と 320px の既定で、上の表のページの行を測り直す。

### Minor-2: 句を `inline-block` にしたことで、件数の行の読み上げの木が変わったのに、その確かめが無い

**どこで何が起きているか**: `ListStatus.module.css` の `.phrase { display: inline-block }` により、Chromium の読み上げの木は、変更前の `paragraph` → `StaticText` 1つから、`paragraph` → `generic` 2つ → `StaticText` 4つ（「全1,110字」「のうち」「1,101〜」「1,110字目」）になった（CDP の `Accessibility.getFullAXTree`）。設計 2-4 が確かめ方に挙げる Playwright の `ariaSnapshot` は、`paragraph: 全1,110字のうち 1,101〜1,110字目` と句のあいだに空白を入れて返すようになった。

**来訪者にどう効くか**: この行は、ページを送ったあとにフォーカスが移り、キーボードと読み上げの来訪者が最初に聞く行である。iOS の VoiceOver は、要素の境目で文を別々のスワイプに分けて読むことが知られている（[Axess Lab「Text Splitting Causes Screen Reader Problems」](https://axesslab.com/text-splitting/)、[WebAIM のスレッド](https://webaim.org/discussion/mail_thread?thread=7882)）。「全1,110字」「のうち」「1,101〜」「1,110字目」を4回に分けて聞かされると、範囲の文として聞き取りにくい。この環境では読み上げソフトを動かせないので実害は確かめられないが、設計 2-4 の確かめ方で結果が変わったことを、builder もテストも記録していない。
あわせて、320px・200% では句をまとめて送るために「のうち」が1行を占め、学年7の12ページ目の件数の行が4行（約 237px）になる。句でなく語だけで折れば「全1,110字」「のうち1,101〜」「1,110字目」の3行で済む。

**直し方**: 次のどちらかを選び、選んだ理由を cycle-316 の文書に残す。

1. 句の `inline-block` をやめ、`nowrap` の語（インラインの `span`）だけで折る。読み上げの木に `generic` が挟まらず、200% の行も短くなる。失うのは、320px・既定の「全1,110字のうち」「1,101〜1,110字目」という句ごとの折り方である。
2. `inline-block` を残すなら、T3-11 の読み上げソフトでの確かめ（NVDA か VoiceOver）の項目に、ページを送ったあとの件数の行が1つの文として読まれることを足す。

どちらでも、設計 2-4 の「確かめ方」の `ariaSnapshot` の結果を、いまの形に合わせて測り直して記録する。

### Minor-3: 381d2d9 と 3b6111a は、そのコミットだけでは型の検査を通らない。381d2d9 の説明が、別のコミットの成果を言っている

**どこで何が起きているか**: 381d2d9 は `BrowseItem` から `sortKeys`・`matchNames`・`reading` を外し、`BrowseSort.keys` を必須にした。しかし、使う側の `kanji-list.ts`・`kanji-list.test.ts`・`BlogListView.tsx` は a123792 まで、`play-list.ts` は 3b6111a まで古い形のままである。381d2d9 を取り出して `tsc --noEmit` を通すと、`kanji-list.ts` 5件・`BlogListView.tsx` 3件・`play-list.ts` 3件・`kanji-list.test.ts` 2件の型のエラーが出る（`BrowseSort` に `keys` が無い、`BrowseItem` に `sortKeys` が無い など）。3b6111a も `kanji-list.ts`・`BlogListView.tsx` が同じ理由で通らない。また、381d2d9 の説明の「漢字のトップの HTML を 891KB から 564KB に減らす」は、`kanji-list.ts` を変えた a123792（T3-8 のコミット）で初めて起きることである。PM の依頼文の「3b6111a・a123792 に入った kanji-list.ts」も、実際は a123792 だけである。

**来訪者にどう効くか**: 直接は効かない。ただし、出荷のあとに一覧で不具合が出て 381d2d9 か 3b6111a へ戻す・二分探索で原因を探すとき、そのコミットはビルドできず、戻す単位として使えない（AP-I09「依存される側 → 依存する側の順」）。Minor-1 の直しがどのコミットにあるかを、履歴から追えない。

**直し方**: push 済みの履歴は書き換えない。cycle-316 の index.md の補足事項（221行目の並行作業の記録）に、T3-7 の Minor-1 の直しが 381d2d9・3b6111a・a123792 にまたがり、381d2d9 と 3b6111a は単独ではビルドできないことを書き足す。AP-I09 がありながら起きた理由（型を変える builder と使う側を組む builder を並行させ、それぞれが自分の分だけをコミットした）も同じ所に残し、以後、共有の型を変える直しは使う側の変更と同じコミットに入れるよう、builder への指示で求める。

### Minor-4: 学年・部首・画数のページの説明の「意味」は、字のページでは英語の語である

**どこで何が起きているか**: `kanjiListDescription` の「熟語や意味は字のページで確かめられます」は、検索結果と SNS のカードに出る。字のページ（`KanjiDetail.tsx`）の意味は `kanji.meanings.join(", ")` で、「水」なら「water」のような英語の語だけである。辞典のトップの説明（`DICTIONARY_DESCRIPTION`）の「各漢字の読み方・意味・…」も同じ。

**来訪者にどう効くか**: 日本語で「漢字 意味」と調べて説明を読んだ来訪者は、日本語の意味の説明を期待して字のページを開き、英語の語を見る。前回の Minor-2 は「行に無いものを約束している」ことを直したが、約束する先の字のページとも合っている必要がある。

**直し方**: 説明の「意味」を、字のページにあるものに合わせる。たとえば「熟語の使用例と英語の意味は字のページで確かめられます」。辞典のトップの説明も同じ言い方にそろえる（トップの説明は `DICTIONARY_DESCRIPTION` で、学年・部首・画数と同じファイルにある）。字のページに日本語の意味を足すほうが来訪者の役に立つが、データの無いものを足す大きな作業なので、この直しではなくバックログで検討する。

## 範囲の外で見つけたこと（この変更の合否には数えない。T3-8 のレビューに渡すことを勧める）

- **伝統色の名前の欄で、仮名の読みで探せない**: 行の読みはローマ字（「ikkonzome」）だけで、「あか」と打つと0件（「条件に合う色はありません（全250色）」）になる。欄のラベルは「色名・読み・カラーコードで探す」、導入の文は「色名の読みとカラーコードを引けます。」で、仮名で探せると読める。ローマ字の読みから仮名を作って探す字に足すか、ラベルを「色名・ローマ字・カラーコード」にするかを決める必要がある。
- **伝統色のトップの説明が、一覧でできないことを言う**: 「色名・ローマ字・カラーコード（HEX/RGB/HSL）をカテゴリ別に検索できます」とあるが、一覧で探せるのは HEX だけで、カテゴリ別の検索は索引から分類のページへ移る形である。
- **漢字のトップの操作の応答**: CPU を4倍に落とすと、並び順の切り替えが 376ms、名前の欄の1字が 272ms かかった。計算は 30ms 前後で、残りは100行の描き替えである。INP の「要改善」（200〜500ms）に入る。この変更で増えたものではないが、B-758 の測り直しのときに一覧の操作も測ることを勧める。

## 合否

**改善指示**。Minor-1〜4 を直す。並び順・絞り込み・ページ送りはすべての一覧で正しく、HTML には行が入り、読み込み前に打った字も残り、漢字のトップの HTML は 891KB から 564KB に減った。一覧のデータの直しとしての目的は果たしている。ただし、前回の Minor-3 の直しは数と単位の部分だけで、文字を大きくして読む来訪者には、並び順の語と0件の文が語の途中で折れて見える。件数の行の読み上げの木の変化も確かめられていない。
