## 指摘

### 1. （小）`clipboard-and-copy.md` の 2 に、測った値と合わない文が3つある

本番のビルドを Chromium の本体（`/opt/pw-browsers/chromium`、141.0.7390.37）で開いた。記事 `nextjs-global-not-found-for-multiple-root-layouts` を 1280×900 で表示し、h1（語結合子 4 個）を3度押して選んで写した。そのときの値と文書を並べる。

- **「`MutationObserver` には届く（見出しを写すたびに 10 件）」**: `document.body` を `childList`・`characterData`・`attributes`・`subtree` で見ると、1回の写しで記録は 38 件だった（`childList` 28、`characterData` 10）。受け手が呼ばれたのは 2 回。組み方の第1の場面・第2の場面・Ctrl+A でも、どれも 38 件だった。「10 件」は `characterData` だけの数と一致するが、文書にはそう書かれていない。読んだ人は、DOM の変更が 10 件だと受け取る。
- **「次の `requestAnimationFrame`（描かないタブのために `setTimeout` も）で……戻す」**: 同じ写しで、受け手の後に登録した `setTimeout(0)` は 2.3ms 後に走り、`requestAnimationFrame` は 13.6ms 後に走った。どちらの時点でも span は 0 個で、戻したのは受け手の `setTimeout` のほうである。描く画面では、ふつう `setTimeout` が先に戻す。文書の書き方では、`setTimeout` は描かないタブのための予備としか読めない。コードの説明（「次の requestAnimationFrame か、それより先に来れば setTimeout で」）は正しい。
- **「`getSelection()` の範囲は仕様どおり動いて見えるが、写す範囲は古い数のまま途中で切れる」**: 受け手を止めて、端を置き直さずに span に入れる受け手を代わりに置いた。そのうえで h1 を `selectNodeContents` で選んで写すと、コピーの出来事の中で `focusOffset` は 17 に増えていた（子は 9 → 17）。しかし `Selection.toString()` も 38 字（「…not-⁠found.tsx が」まで）で、クリップボード（37 字）と同じ所で切れていた。仕様どおりに見えるのは端の数だけで、`toString()` は写す範囲と同じく切れる。後の作業者が `toString()` で確かめれば、ずれに気付けるのに、この文はそこを読み違えさせる。

直すこと: 3つを測った値のとおりに書き直す。1つ目は、何を数えたか（記録の種類と、見た範囲）を書く。2つ目は、どちらが先に走るかを書く。3つ目は、`toString()` も切れることを書く。書き足した跡が残らない形にする。

### 2. （小）「字の位置も変わらない」は、1/64px の単位で成り立たない

`hideJoiners` の説明は「字そのものは文書に残るので、行の組みも字の位置も変わらない」と書く。知見の文書の 2 も「span を足しても組みが変わらないのは……」と書く。

これを字ごとの矩形で測った。語結合子を持つ要素の中で、語結合子を除く字ごとの `Range.getBoundingClientRect()` と、要素の矩形を取り、写す前とコピーの出来事の中（受け手の後）で比べた。測ったのは、語結合子を持つ本番のページの全体（下の 41 ページ）である。その結果、行（y と高さ）はどの幅でも変わらなかった。一方、語結合子の隣の字の x と幅は 0.016px（1/64px）動いた。組みの幅で大きさが決まる箱は、幅が 0.016px 増えた。password-generator の「小文字 (a-z)」の `span` は 89.813 → 89.828px、wifi の h1 は 1280px で 72.83 → 72.84px だった。

`user-select` を付けない素の span に入れても、同じ値になった。取り除いて `normalize()` すると元の値に戻った。つまり、span の境で字の組み（シェーピング）が分かれることによる。layout-shift は、41 ページ × 4 幅のどれでも 0 件だった（Chromium は 3px に満たない動きを数えない）。いま来訪者に害は無い。

しかし、この説明を読んだ後の作業者は「組みは一切変わらない」と受け取る。そうすると、語結合子を、縮めて組む箱（inline-block や flex の項目）の中に、容器の端いっぱいで置くことがありうる。そのとき、この 1/64px で折り返しが変わりうることを知らないまま進める。

直すこと: コードの説明と知見の文書の 2 を、「行は変わらない。字の x と幅は span の境で 1/64px ほど動き、組みの幅で大きさが決まる箱はその分だけ広がる（layout-shift の数には入らない）」と、測ったとおりに書く。知見の文書の「親が flex や grid の容器だと……」の項に、この限りも並べる。

### 3. （小）Chromium の外で効くかを確かめる手立てが無い

この組み方は、ブラウザがコピーのときに `user-select: none` の字を除くことに頼っている。WebKit は長くこの字をクリップボードに入れていた（[WebKit bug 80159](https://bugs.webkit.org/show_bug.cgi?id=80159)。直ったのは 2022年12月の 257749@main）。知見の文書の 1 の根拠は「Firefox と Safari は測っていない」と書く。それでも、2 の組み方の根拠と決定 (9) は、Chromium での測りだけで決まっている。iOS の Safari の来訪者が見出しを長押しして写すと、語結合子が除かれるかは誰も確かめていない。また、古い iOS では除かれないはずである。T9 の実機の項目にも、写しの確かめは入っていない（T9 にあるのは、json-formatter の誤りの文の VoiceOver の聞き取りだけ）。

直すこと:

- PM が、T9 の実機の確かめに次の項目を足す。iOS の Safari（と、使えれば macOS の Safari・Firefox）で記事の h1（例 `nextjs-global-not-found-for-multiple-root-layouts`）を選んで写し、語結合子が残るかを見る。確かめ方は、たとえば json-formatter の入力欄に貼り、字数が h1 の見える字数と同じかを見る。あわせて、iOS の版を記録する。残ると分かったときにどうするかも、決定 (7) の近くに書く。
- `clipboard-and-copy.md` の 2 で、この組み方が効くのは、ブラウザが `user-select: none` の字を写さないときだと書く。Chromium の外では測っていないことも書く。WebKit が直した時期を根拠に添える。
