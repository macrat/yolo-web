## 2. 結果の組み方（論点 1〜6）

### 2-1. 結果のボックスが囲むもの

**ボックスは結果と、結果を写すコピーのボタンだけを囲み、入力と、結果を生む操作は囲みません。** 結果のボックスは `ResultBox`（`src/components/ResultBox/`）の1つの部品にし、診断・占い・道具・ゲームのどの結果もこれで組みます。

| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. いまの形（道具は入力と結果を同じ `Panel` に入れる）    | 太い枠が道具全体を囲み、結果は枠の中のどこか。結果の区画はカードや細い枠で道具ごとに違う                 | 捨てる。太い枠が「道具」と「結果」のどちらを指すかが面で違い、結果を一目で探せない。コード・表・一覧の結果が道具の枠の中で自分の枠を持ち、ボーダーが二重になる（§8）                      |
| B. 道具の枠の中で、結果の区画を小見出しと細い罫線で分ける | 太い枠が道具全体を囲み、結果は枠の中の小見出しの下                                                       | 捨てる。二重のボーダーは消えるが、コードの結果を `--paper-2` の地のボックス（§5）にできない。診断の結果（ボックス）と道具の結果（区画）で、結果の見え方が2つになる（§12 位置の一定）      |

コピーのボタンは結果のボックスの頭に置きます（2-5）。コピーは、写して使う道具の結果でいちばん使う操作で、結果の長さに関わらず、結果が出たその位置ですぐ押せる必要があるからです。

`ResultBox` が持つもの（形の見本。名前と細部は実装で決めます）:

- §5 のボックス（太い線・内側の余白・コンテンツ幅いっぱい）。中身がコード・表・一覧のときは、そのコンポーネントの形（コードなら `--paper-2` の地）をボックス自身が持ち、中に枠を重ねない。
- 頭の行: 結果の見出し（あれば）と、コピーのボタン（写して使う結果のとき）。
- 結果の登場の動き（§11。1回・250〜400ms。`prefers-reduced-motion` で即時）。結果の登場の動きは、この部品だけが持つ（6章）。

- 結果に着いたときにフォーカスを受ける場合の `tabindex="-1"`。

### 2-2. 性格診断の解き終えた画面（論点1・2）

**組み方**（上から）:

1. **結果のボックス**
   1. 補助情報の1行「{診断名}の結果」（例「あなたに似たキャラ診断の結果」。`0.875rem`・`--ink-2`）。

   4. キャッチコピー（本文の大きさ・`--ink`）。
   5. 説明（`result.description`。本文の大きさ・本文の幅）。
2. **持ち帰る・共有する**の区画（ボックスの外、すぐ下）。character-personality の札の画像の保存と共有（`FudaActions`）と、共有のボタン（7-3 で1つにした `ShareButtons`）を1か所にまとめます。

**VoiceOver の読み上げと禁則の破れの天秤**: iOS の VoiceOver は、見出しやリンクの中のインラインの要素（`span` など）で文を切り、スワイプごとに別々に読むことが報告されています（[Axess Lab「Text Splitting Causes Screen Reader Problems」](https://axesslab.com/text-splitting/)、[WebAIM のメーリングリスト「Spans inside headings pauses VoiceOver on iOS」](https://webaim.org/discussion/mail_thread?thread=7882)）。回避に使われてきた `role="text"` は、iOS 17.2 から効かないという報告があります（[AppleVis](https://www.applevis.com/forum/app-development-programming/voiceover-aria-roletext-support-no-longer-supported-ios-v172)）。`white-space` だけの `span` でも切れるかは、このコンテナでは確かめられません。

- 切れたときに失うもの: スクリーンリーダーの来訪者が、自分の結果の名前を「先頭を走りながら「全員」「来てるか！」と」……と切れ切れに聞き、見出しとして1回で読めない。結果の中身そのものが伝わりにくくなる。
- 禁則を破ったときに失うもの: 文字を 200% にした来訪者が、24のうち 2〜6タイプで、閉じ括弧や小書きの仮名で始まる行を見る。字は全部読め、意味も変わらない。既定の文字サイズでは、320px の1タイプ（「これ普通じゃないよね」と」）だけ。

結果の名前がそのまま伝わることを先に取り、`span` を持たない H2n を採ります。T9 の iOS の VoiceOver の聞き取りで、`white-space` だけの `span` で読み上げが切れないと分かったら、禁則の字のまとまりを足す（H2 にする）ことを、T9 の結果で決め直します。

組み方（H2n）:

- 文節と文節のあいだに `<wbr>` を置きます。最後の文節が1字なら、その前の文節につなぎます（1字だけの行を作らない）。
- 文節の中の語の切れ目（次の語が漢字・片仮名・開き括弧で始まり、前の語が数字で終わらない所）に、2つ目の `<wbr>` を置き、ふだんは `display: none` で効かせず、見出しの1行に入る字が約8字より少ない幅のとき（コンテナクエリ。Safari 16 から効く）だけ効かせます。既定の文字サイズでは文節の切れ目でだけ折れ、文字を大きくしたときだけ、文節の中の語の切れ目でも折れます。
- 要素は `word-break: keep-all` と `overflow-wrap: anywhere` を自分で持ち、`globals.css` の見出しの規則には触りません。語の切れ目でも入らない語だけが、`anywhere` で語の中で折れます。
- 区切りを作る関数（`src/lib/phrase-breaks.ts` などの、サーバーだけで動くもの）と、区切りを受けて組む部品（`PhrasedText` など）を T4 が作ります。
- クライアントの部品が描く、データから作る見出し（解き終えた画面のタイプ名・占いの運勢の名）は、サーバーの `page.tsx` が区切りを作って props で渡します。日付で選ぶ占いのように、描くまでどれになるか決まらないものは、候補の全件の区切りを渡します。
- `<wbr>` は、Chromium の読み上げの名前に空白を足しません（0章）。VoiceOver での読み上げは確かめていないので、T9 に渡します。

**§4 の文を書き直します**（8章）。いまの §4 は「語の中で折るのは、一語が1行に収まらないときだけ」とします。200% の 320px の見出しの1行は約5字で、語の切れ目を持たない仮名の続き（「調べてから」「確認しながら、」）は、1行に入る長さでも語の切れ目で折れず、`anywhere` で割れます。これを無くすには語を細かく分ける解析をサーバーに持つことになり、それでも「言って」「気づいたら」のような仮名の続きの中は分けられません（ICU の語の分け方は「言|って」「気|づ|い|たら」と割りすぎる）。そこで §4 の文を、この組み方が実際に守れることに合わせます: 「見出しは意味の切れ目（文節）で折る。文節が1行に収まらないときは、文節の中の語の切れ目で折る。それでも収まらないときだけ、語の中で折る」。書き直しは、index.md の「`DESIGN.md` を変えるとき」の手順で、この判断と数をレビューに通してから行います（T4-1）。

**確かめ方の共通の決まり**

- ブラウザは `/opt/pw-browsers/chromium` の Playwright です。`playwright install` でほかのブラウザを足しません。
- **WebKit の近似の測り方**（見出しの折り方）:
  1. 測る見出しの字の Web フォントの分割ファイルが読み込まれるのを待つ（`document.fonts.load` に見出しの書体の名前（`"Zen Antique"`）と見出しの字を渡して待ち、`document.fonts.check` が真になってから測る）。見出しの要素とその中の計算値の `word-break` が `keep-all` で、`globals.css` の `auto-phrase` が効いていないことを確かめる。
  2. 見出しの字を1字ずつ Range で行の位置を取り、行に分ける。次を数える: 文節の中で折れたタイプ、語の中で折れたタイプ（文節の切れ目でも、文節の中の語の切れ目でもない所で折れた）、1字だけの行、行頭に置かない字（閉じ括弧・句読点・！？・…・小書きの仮名・長音符）で始まる行か開き括弧で終わる行（禁則の破れ）、見出しの幅からのはみ出し。行の切れ目を決めるのは `<wbr>` と Web フォントの字の幅なので、これを WebKit の近似とする（0章）。
  3. まだ `auto-phrase` に頼る見出し（T5 が直すまでのもの）の WebKit の見え方は、棚卸し 2-5 と同じく、Chromium でその見出しに `word-break: normal` を当てた近似で測る。
  4. 近似で拾えない差は、2-3 の末尾の型にして T9 に渡す。
- 「200%」は、CDP の `Page.setFontSizes` で既定の文字サイズを 32px にした状態です。
- **見出しの折り方の条件**は、24のタイプ名で、2 の数が 0章の表の H2n の数以下で、既定の文字サイズでは 375px の語の中の折れ・1字だけの行・禁則の破れがどれも0、どの幅でもはみ出しが0であることです。
- 本番のビルド（`npm run build` のあと `next start`）で、自分の worktree と、ほかと重ならないポートで測ります。

## 11. 決めきれない所と、確かめれば決まること

どれも PM が確かめて決めます。

- **ボックスの中の間隔**（補助情報とタイプ名のあいだが 8px か 16px か、など）: T4-5 で2つ組んで 375px で撮り比べ、タイプ名が補助情報の続きに見えないほうを採ります。試作（0章）は 8px で測りました。
- **横に送る表の枠の描き方**（5-2）: 場所を取らない線で描くか、場所をはじめから取っておくかを、T4-17 で表の字の左端がほかの本文とそろうほうに決めます。
- **札の保存の区画を残すか**: T6 が決めます（7-2）。T4 は、残る前提で置き場所を決めています（2-2）。
- **見出しの中に禁則の字の `span` を足すか**（2-3）: T9 の iOS の VoiceOver の聞き取りで、`white-space` だけの `span` で読み上げが切れないと分かったら、H2（禁則の破れ0）に切り替えます。切れるなら H2n のままにします。

判定の印（3-1 の A）と、ゲームの頭の組み方（2-6 の V7）は、設計の時点で決めました。
