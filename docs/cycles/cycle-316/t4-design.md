## 0. 前提の事実（棚卸しに足したもの）

- **BudouX は、character-personality の24のタイプ名を、どれも語の途中で割らずに文節に分ける。** `budoux` 0.9.2 の既定の日本語の分け方（`loadDefaultJapaneseParser`）で24件を分けると、数字と助数詞は1つの文節に残り（「3秒後に」「10年経っていた」「1000回繰り返す美の」）、括弧と助詞も文節の中に入った（「来てるか！」と」「解釈だと…」と」）。文節の最長は「これ普通じゃないよね」と」の12字。
- **新しい折り方が使うのは、どのエンジンでも同じに効く機能だけである。** `<wbr>`、`word-break: keep-all`（Safari・iOS Safari 9 から。https://caniuse.com/mdn-css_properties_word-break_keep-all ）、`overflow-wrap: anywhere`（Safari・iOS Safari 15.4 から。https://caniuse.com/mdn-css_properties_overflow-wrap_anywhere ）。Chromium でしか効かない `word-break: auto-phrase` を使わない。行の切れ目を決めるのは `<wbr>` の位置と、見出しの書体（Zen Antique。Web フォントなのでどちらのエンジンにも同じもの）の字の幅なので、Chromium で `auto-phrase` が効いていないことを確かめて測れば、WebKit の近似として扱える。サイトの索引とアコーディオンのラベル（`LinkIndex`・`IndexAccordion`）は、すでに `keep-all`・`<wbr>`・`overflow-wrap: anywhere` で組まれている。

### 2-3. 見出しの折り方（論点1 の折り方）

**タイプ名のように、データから作る見出しにも、BudouX の文節の区切りをサーバーで入れます。見出しは文節で折り、文節が1行に収まらないときだけ、その文節の中で折れます。仕組みは T4 が作り、T5 はそれをページの見出しに使います。**

**区切りをどこで作るか**

| 案                                                            | WebKit（結果に着いた回数の66%）                                         | 判断                                                                                                                                                    |
| ------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. いまの `word-break: auto-phrase` のまま                    | 効かない。375px の結果の画面で24のうち15タイプが語の途中で折れる（0章） | 捨てる。いちばん多い来訪者に §4 を守れない                                                                                                              |
| B. データに折り所を手で書く（タイプ名ごとに区切りを持たせる） | 効く                                                                    | 捨てる。診断・占いのタイトルだけで190件あり、タイトルを直すたびに区切りも直す必要があり、書き忘れた所は黙って語の途中で折れる                           |
| C. BudouX をブラウザで動かして区切りを入れる                  | 効く                                                                    | 捨てる。分け方の表（`budoux` 0.9.2 の日本語のモデルで約23KB）と処理をすべての来訪者に配り、区切りが入るまでのあいだ、見出しが違う所で折れてから組み直る |
| **D. BudouX をサーバーで動かし、区切りを HTML に入れる**      | 効く                                                                    | **採る。** 来訪者に配る JS が増えず、最初の描画から区切りが入っている                                                                                   |

**区切りをどう組むか**

組み方は、BudouX 自身の出力と同じ形（要素に `word-break: keep-all`・`overflow-wrap: anywhere`、文節のあいだに折り所。0章）にします。使う機能はどれも Safari・iOS Safari 15.4 から効きます（0章）。そのうえで、次を決めました。

- **最後の文節が1字なら、その前の文節につなぎます**（Eg）。1字だけの行が、375px の既定で1タイプ（「備えの／王」）から0になります（0章）。
- **丸括弧で囲んだ一続き（読み仮名・添えた数）の中には、折り所を置きません。** 中は1つのまとまりとして読まれ、「（りろせい／ぜん）」のように割れると、読み仮名が途中で切れるからです。鉤括弧は文を引き、中にも文節があるので含めません。
- **最初の文節の、最初の空白より前にだけ、字の種類が変わって漢字か片仮名の語が始まる所の折り所を足します**（「チューリング|型思考者」「ことわざ|ビギナー」）。置くのは、前後がどちらも同じ字の種類の2字以上の続きで、前が漢字か仮名で、丸括弧の中でも禁則の字の所でもない所です。
  - この部分は行の頭から始まるので、この折り所は、そこが1行に収まらないときにしか使われません。その折れを、「型思考／者」「ビギナ／ー」のような字の所から語の切れ目に移すだけです。
  - 2つ目からの文節と空白の後ろは行の途中から始まりうるので、中に折り所を置くと、次の行に丸ごと入る語まで割ります。そのため置きません。BudouX は空白をまたいで1つの文節を返すことがあるので（「ムササビ -- 座布団サイズで」「JSON 整形ツール」）、最初の文節の中でも、空白の後ろには置きません。
  - 解析で分けられない仮名の続き（「調べてから」は ICU でも「調べ|て|から」と細かく割れます）も、字の種類だけでは切れ目を決められないので分けません。
- **閉じ括弧の直後の折れは止めません**（「「来てるか！」／と」）。Unicode の改行の規則が折り所とし、`keep-all` でも止まらない所で、日本語の組版でも普通の折り所です。止めるには、下の F か Z が要ります。
- **禁則の字をまとめる `span` も持ちません**（下の読み上げの比べ）。

組み方（Eg）:

- 文節と文節のあいだと、最初の文節の、最初の空白より前の語の切れ目に `<wbr>` を置きます（丸括弧の一続きの中を除く）。最後の文節が1字なら、その前の文節につなぎます。
- 要素は `word-break: keep-all` と `overflow-wrap: anywhere` を自分で持ち、`globals.css` の見出しの規則には触りません。
- 区切りを作る関数（`src/lib/phrase-breaks.ts` などの、サーバーだけで動くもの）と、区切りを受けて組む部品（`PhrasedText` など）を T4 が作ります。区切りの印（`<wbr>` か、ゼロ幅スペースか）は、この部品の1か所で決まるようにします。
- クライアントの部品が描く、データから作る見出し（解き終えた画面のタイプ名・占いの運勢の名）は、サーバーの `page.tsx` が区切りを作って props で渡します。日付で選ぶ占いのように、描くまでどれになるか決まらないものは、候補の全件の区切りを渡します。
- `line-break: strict` は、`anywhere` の非常の折りに効かないことを確かめました（0章）。T5 が §4 に `line-break: strict` を書くとき、それで見出しの禁則の破れが消えるわけではないことを、T5 に渡します。

**§4 の文を書き直します。** いまの §4 は「見出しは意味の切れ目で折る。語の途中で折らない」「語の中で折るのは、どちらも一語が1行に収まらないときだけ」とします。書き直す文は「見出しは文節で折る。文節が1行に収まらないときだけ、その文節の中で折る」です。これに、次の6つを添えます（8章の §4 の行）。

- 閉じ括弧の直後で折ってよいこと。
- 丸括弧の一続きの中で折らないこと。
- 最初の文節の、最初の空白より前の語の切れ目で折ること。
- 最後の1字の文節をつなぐこと。
- 既定の文字サイズで、1字だけの行・禁則の破れ（行頭の閉じ括弧・句読点・！？・…・中点とコロン類・小書きの仮名・長音符・繰り返し記号（々・ゝ・ヽ など）、行末の開き括弧）・丸括弧の中の折れを作らないこと。文字サイズ 200% では、1字だけの行と禁則の破れは、1行に収まらない文節の中の折れから出たものに限って受け入れる。
- 来訪者にすでに渡した結果の名前（診断のタイプ名など）は、見出しの折れのためには変えないこと。組み方で避けられない折れは、その名前に限って受け入れる。

来訪者にとっての理由は次の2つです。

- **この折り方で、WebKit の来訪者が見る語の途中の折れが大きく減ります。** いまの見出しは Chromium でしか効かない `auto-phrase` に頼っていて、結果に着いた回数の66%を占める WebKit の来訪者は、375px の解き終えた画面で24のうち15タイプ、結果のページの h1 で20タイプのタイプ名を、語の途中で割られて読んでいます。この折り方では、それぞれ0と4になります（0章）。
- **仕組みを重ねても、文節が1行に入らないときの割れは無くせません。** 文節の中をさらに分ける仕組みを重ねても、解析で分けられない仮名の続き（「調べてから」「確認しながら、」）は語の途中で割れて残りました。いまの文の「語の途中で折らない」は、文字を大きくした来訪者の画面では守られない約束で、守られない約束を規定に置くと、見出しを作るたびに作り手が満たせない条件を追うことになります。書き直した文は、来訪者がどの画面でも実際に見る折れ方（ふだんは文節で折れ、文節が入らない幅でだけ文節の中で折れる）をそのまま言います。

いまの2つ目の項（名前に括弧で数を添えたもの）は、「名前の中の語の切れ目と、始め括弧の前でだけ折る。語の中で折るのは、一語が1行に収まらないときだけ」と、この項だけの文にして残します（いまの「どちらも」を外す）。索引の語とアコーディオンのラベルは短い名前で、いまの組み方で語の中の折れが出ていないからです（T3 の完了の判定）。書き直しは、[options.md](./options.md) の「`DESIGN.md` を変えるとき」の手順に乗せます。変更前と変更後の来訪者の見え方の比べ（上の数と、T4-5 と T4-7 で撮る変更前と変更後の画面）を添えて、判断をこの設計のレビューに通してから、T4-1 で書き換えます。

**T9 に渡す、実機で確かめる項目**（Chromium の測りで近似できない所）:

- **iOS の VoiceOver で、タイプ名の見出しを1回で読むか。** 記録すること: iOS の版と端末。見出しへの移り方の3つ（1本指の左右のスワイプ・ローターを「見出し」にして上下のスワイプ・2本指の上スワイプで全体を読む）のそれぞれで、見出しの全体を1回で読むか、`<wbr>` の所で切れるか。聞く見出しは、解き終えた画面のタイプ名（blazing-warden・contrarian-professor・creative-disruptor・guardian-charger）と、結果のページの h1（同じ4タイプ）。比べのために、同じ文で `<wbr>` を持たない見出しの見本と、ゼロ幅スペースで区切った見出しの見本も聞く（見本は T4-3 が storybook に置く）。
- **320px と 200% の作り方**: 320px は、幅 320pt の端末（iPhone SE（第1世代）など）があれば見る。無ければ 375px の端末で見て、320px は Chromium の近似の数で代える。200% は、Safari の「aA」のページの拡大を 200% にして見る。これはページ全体の拡大で、Chromium で既定の文字サイズを 32px にした組み方と同じにはならないので、記録にそう書く。iOS の設定の「文字サイズを大きく」は Web の既定の文字サイズを変えないので使わない。
- 閉じ括弧と「！」「?」が続く文節（「来てるか！」と」「理由ある?」と」）、三点リーダの後の閉じ括弧（「解釈だと…」と」）、数字と助数詞と小書きの仮名（「10年経っていた」）が、375px の既定で文節の切れ目で折れているか。

- **文字盤を開いた状態の送り方**（2-6）: iPhone で推測を3回続けて送り、そのたびに入力欄と送信のボタンが文字盤の上に見えているか。

**聞いたあとの分かれ道**（11章にも書く）:

- 実機の VoiceOver を使える機会が無いときは、この形（`<wbr>`）を保ちます。見出しの中に字を分ける要素を持たない形で、出典の報告（`span`・`<br>`）にあたらないからです。聞けなかったことは T9 の記録に残します。

- 一覧の件数の行が切れると分かったときも、同じ直しのタスクで、件数の行を1つの文字の並びにする組み方（語ごとの `span` をやめ、語の切れ目をゼロ幅スペースか `<wbr>` で持つ）に替えます。

- **共通の決まり**: 操作のあと、次に使うコントロールが画面の外に出たら、それが画面に入るまで即時に送ります（滑らかに送らない。§11）。「画面」は `visualViewport` の範囲（下端は `visualViewport.offsetTop + visualViewport.height`。`visualViewport` が無い環境では `innerHeight`）で測ります。iOS の Safari は文字盤（ソフトウェアキーボード）を開いても `innerHeight` を変えず、`visualViewport` だけが縮むので、これで文字盤を開いていてもいなくても同じ決まりで働きます。この送り方の関数は、T4-10 が `src/play/games/shared/_lib/` に1つ作り、T4-11〜T4-13 はそれを呼びます。`DESIGN.md` §8 と §11 にも書きます（8章）。

- nakamawake: **4つ目の語を選んだ時点から数えます**。4つ目の語を選んだとき、チェックのボタンと、選んだ4語を含む行が画面に入るように送ります。両方が入らないときは、チェックのボタンが入ることを先にします。送ったあと、来訪者は画面を送らずに、選んだ4語を見直してチェックを押せます。送るボタンを格子の上に移す組み方は、320px で格子の最初の行が画面の下端に掛かったので捨てました（0章）。

## 3. 色（論点 7〜13）

`DESIGN.md` §2 は、色を使うのは「その色がコンテンツそのものであるときだけ」とし、区別・強調・気分のための色を、コンテンツであっても認めません。棚卸し 4-2 の「色の性質」の列で、和色はどれも区別・強調・気分の色にあたります。この章は、§2 のとおりにする形で決めます。

### 3-1. 判定の示し方（論点7）

対象は kanji-kanaru・yoji-kimeru の判定のマスと凡例、nakamawake のグループの難易度、4本のゲームの統計の分布です。

- ゲームの共有の文の絵文字（🟩🟨⬜ など）は、盤と同じ印の並びに替えます（論点12。3-6）。

**統計の分布**（4本のゲームの結果のボックスの中。2-6）は、§5 の量の帯を区分ごとに並べて組みます。

- **行**は、いまのデータの区分のままです（各ゲームの `GameContainer.tsx` の統計の更新）。kanji-kanaru・yoji-kimeru は当てた回数（1〜6回。当てた回だけを数える）、nakamawake はミスの数（0〜4。負けた回も数える）、irodori は合計の点数の10の区分です。
- **名前の列**は、区分を単位の付いた字で言います（「1回目」「0ミス」「90〜100点」など）。**値**は、その区分に入った回数を数字だけで言い、何を数えた数かは分布の見出しの字で一度だけ言います。文言は各ゲームのタスクで決め、T7 に渡します。
- **帯の上限は、並んだ行のうちいちばん多い回数にします**（いまの `StatsModal.tsx` の `Math.max(...guessDistribution, 1)` と同じ）。

  | 上限                        | 来訪者に見えること                                                                                                                     | 判断                                                                                                                                                                                                                                     |
  | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | **A. いちばん多い行の回数** | いちばん多い行が枠いっぱいに塗られ、ほかの行はそれに対する長さになる。どの回数で当てることが多いかが、枠の長さを目いっぱい使って見える | **採る。** 来訪者が分布で見たいのは、自分がどの回数で当てることが多いかという形で、A はその形の差をいちばん大きく見せる。何回ずつかは、どの行も値の字で読める                                                                            |
  | B. 遊んだ回数の合計         | 行の長さが全体に対する割合になる。当てた回数が散らばるほど、いちばん多い行でも枠の一部しか塗られず、形が枠の左に詰まる                 | 捨てる。320px の1行の組みで枠は約 139px（下の概算）なので、行どうしの差が数 px になる。kanji-kanaru・yoji-kimeru の分布は当てた回だけを数え、行の合計が遊んだ回数にならないので、上限が遊んだ回数か当てた回数かで、同じ帯が2通りに読める |

- **値が0の行は塗りません。** いまの実装は、0の行に枠の4%、1以上の行に最低8%を塗り、塗りの中に回数を置いています。最低の長さを足すと、0の行が塗られて見え、少ない行どうしの長さの比も崩れるので、塗りは割合のままにします。どの行も0のとき（最初の回を当てられなかったとき）は、どの帯も塗りません。
- **今回の行**は、「今回」の列（下の組み方）に「今回」と字で置きます。色・塗りの違い・太字では示しません。今回の結果が分布のどの行にも入らないとき（kanji-kanaru・yoji-kimeru で当てられなかった回）は、「今回」を置きません。

**量の帯を並べる組み方**（統計の分布と、3-3 のスコアの帯に共通。§5 に書く。8章）

量の帯は、並べた帯どうしの長さを比べて読むものです。帯の始まりか枠の長さが行ごとに違うと、同じ割合でも塗りの長さが変わり、帯の右端が量を表さなくなります。とくに、「今回」を持つ行だけ枠が短いと、今回の行がいつも少なめに見えます。そこで、並べた帯はどの行も同じ位置から始まり、同じ長さの枠を持つように組みます。部品は1つにし（T4-3。§12 位置の一定）、統計の分布とスコアの帯はそれを使います。

1. **並びは、本文の幅（`min(--measure, 置かれるコンテンツ幅)`）いっぱいに置きます。** 結果のボックスの中では、ボックスの内側の幅が置かれるコンテンツ幅です。
   - 中身の幅に縮めません。縮めると、枠の長さが字の列の残りでなく帯の最小の幅で決まり、1行の組みか2行の組みかの判定（下の 4）も成り立たないからです。
   - 本文の幅より広げないのは、1280px で結果のボックスの中の幅いっぱいにすると、名前から値まで目で横に追う距離が延びるからです（2-6 の入力欄と盤と同じ考え方）。
   - `45rem` 未満の画面では、本文の幅はコンテンツ幅と同じです。
2. **1行の組み**: 1行に、名前の列・帯・値の列・「今回」の列をこの順に並べます。各列の幅は、並んだ行のうちいちばん広い字で決まり、どの行も同じです。「今回」の列は、並びに「今回」を持つ行が1つでもあれば、どの行にも同じ幅を取ります。こうすると、どの行の帯も同じ位置から始まり、同じ長さの枠を持ちます。
   - 名前の列は左揃えにします。
   - 帯は、進み具合の帯と同じ形と高さ（`--rule-w` の `--rule` で囲んだ `--paper-2` の地、高さ `--space-16`）で、左から量の割合だけ `--ink` で塗ります。
   - 値の列は帯の右に置き、右揃えにします。IBM Plex Sans の数字は桁が揃う（§3）ので、行をまたいで一の位が揃います。
   - 「今回」の列は値の列の右に置きます。統計の分布だけが持ちます。
   - 列のあいだと、行どうしのあいだは 8px です。
3. **字の大きさと色**: 名前・値・「今回」は、どれも補助情報の大きさ（`0.875rem`）で、`--ink` で組みます。比べるのは帯の長さで、字は帯に名前と値を添えるものです。進み具合の帯の数と同じ大きさで、本文の大きさにすると字の列が広がって枠が短くなります。`--ink-2` にしないのは、名前と値が結果の中身で、前に出ない文字ではないからです。
4. **2行の組み**: 1行の組みで枠が並びの幅の半分に届かないときは、並び全体を2行の組みにします。各項目の1行目に名前を置き、同じ行の右端に値と「今回」を置き（値と「今回」の列は、1行の組みと同じく、どの行も同じ幅を取ります。値は行をまたいで右揃えになり、桁が揃います）、そのすぐ下に並びの幅いっぱいの枠を置きます。項目どうしのあいだは 16px にし、字がどちらの帯のものかを取り違えないようにします。2行の組みでも、どの帯も並びの左端から始まり、同じ長さの枠を持ちます。
   - 切り替えは並び全体で一度に行い、行ごとには替えません。行ごとに替えると、1行の組みの帯と2行の組みの帯で枠の長さが違ってしまいます。
   - 字の列の幅は字の大きさに比例するので、文字を大きくした画面でも同じ決まりで切り替わります。切り替えの仕組み（コンテナクエリの `em` の幅か、描く前に測るか）は T4-3 が決めます。どちらでも、最初の描画から組みを決めておき、ページを開いた直後に組みが替わって下が動くことはしません。来訪者が幅や文字の大きさを変えたとき（端末の回転・ブラウザの拡大）は、新しい幅で組み直します。組み直さないと、たとえば 200% にしても1行の組みのまま枠が並びの幅の2割ほどに縮み、分布の形が読めなくなるからです。
   - 概算（和字 1em・半角 0.6em で見積もり、列のあいだ 8px。結果のボックスの中の幅は 375px で 299px、320px で 244px（0章）。T4-3 で測る）:

     | ------------------------------------------------------------------------------------------------- | ----------------------- | ---------------------------------- | ------------------------------ | -------------------------------------------- |
     | 統計の分布（名前「1回目」・値2桁・「今回」あり。字の列は約 105px、200% で約 186px）               | 1行・枠 約 194px（65%） | 1行・枠 約 139px（57%）            | 2行（1行なら枠 約 113px・38%） | 2行（1行なら枠 約 58px・24%）                |

5. **値の形**: 値は量だけを言い、「n / N」の形にしません。§5 の進み具合の帯は「3 / 10」で「10問のうち3問目」を言います。量の帯に「38 / 51」と書くと、同じ形の帯が同じ形の字を持ち、2つを見分ける手がかりが無くなるからです。

7. **動き**: 結果のボックスと一緒に出て、塗りが伸びる動きを持ちません（§11。6-1）。

- **配色**: 図を、mermaid の `base` のテーマに UI のトークンの値を渡した無彩にします。割り当ては、地が `--paper`、箱の地が `--paper-2`、線と箱の枠が `--rule-2`、字が `--ink` です（§5 の図）。ダークでは同じ割り当てのダークの値を渡します（いまの `MermaidRenderer.tsx` は、端末のテーマが替わると図を描き直す）。

- **WebKit の近似の測り方**（見出しの折り方）:
  1. 測る見出しの字の Web フォントの分割ファイルが読み込まれるのを待つ（`document.fonts.load` に見出しの書体の名前（`"Zen Antique"`）と見出しの字を渡して待ち、`document.fonts.check` が真になってから測る）。見出しの要素とその中の計算値の `word-break` が `keep-all` で、`globals.css` の `auto-phrase` が効いていないことを確かめる。
  2. 見出しの字を1字ずつ（サロゲートペアの字も1字として、コードポイントごとに）Range で行の位置を取り、行に分ける。行の切れ目を、次の3つに分ける。
     - **折り所での折れ**: 見出しの中の `<wbr>` の所（区切りの関数が置く、文節の切れ目と、最初の文節の、最初の空白より前の語の切れ目）か、閉じ括弧の直後。
     - **文節の中の語の切れ目での折れ**: 折り所でなく、`Intl.Segmenter("ja", { granularity: "word" })` の語の切れ目のうち、次の語が漢字・片仮名・開き括弧で始まり、前の語が数字で終わらない所。
     - **語の中の折れ**: どちらでもない所。

     そのうえで、見出しごとに次を数える。
     - 文節の中で折れた見出し（折り所でない所で折れたもの。あとの2つを合わせる）
     - 語の中で折れた見出し
     - 1字だけの行（字が1つだけの行。その字がどの文節の字かは問わない）
     - 禁則の破れ（行頭に置かない字（閉じ括弧・句読点・！？・…・中点とコロン類・小書きの仮名・長音符・繰り返し記号（々・ゝ・ヽ など））で始まる行か、開き括弧で終わる行）
     - 丸括弧の中の折れ（丸括弧で囲んだ一続きの中で折れたもの）
     - 見出しの幅からのはみ出し

     行の切れ目を決めるのは `<wbr>` と Web フォントの字の幅なので、これを WebKit の近似とする（0章）。

  3. まだ `auto-phrase` に頼る見出し（T5 が直すまでのもの）の WebKit の見え方は、棚卸し 2-5 と同じく、Chromium でその見出しに `word-break: normal` を当てた近似で測る。
  4. 近似で拾えない差は、2-3 の末尾の型にして T9 に渡す。
- 「200%」は、CDP の `Page.setFontSizes` で既定の文字サイズを 32px にした状態です。
- **見出しの折り方の条件**は、測る見出しのそれぞれで、次を満たすことです（数え方は上の 2）。
  - どの幅と文字の大きさでも、はみ出しが0。行の切れ目は、折り所か、1行に収まらない文節の中か、1行に収まらない丸括弧の一続きの中にだけある。
  - 既定の文字サイズ（320px・375px・1280px）では、1字だけの行・禁則の破れ・丸括弧の中の折れが、どれも0。
  - 200% では、1字だけの行と禁則の破れは、1行に収まらない文節の中の折れから出たものに限って受け入れ、数を記録する（§4）。
  - character-personality の24タイプでは、既定の文字サイズで語の中で折れたタイプが、0章の表の Eg の数以下。
- 本番のビルド（`npm run build` のあと `next start`）で、自分の worktree と、ほかと重ならないポートで測ります。

## 11. 決めきれない所と、確かめれば決まること

どれも PM が確かめて決めます。

- **ボックスの中の間隔**（補助情報とタイプ名のあいだが 8px か 16px か、など）: T4-5 で2つ組んで 375px で撮り比べ、タイプ名が補助情報の続きに見えないほうを採ります。試作（0章）は 8px で測りました。
- **横に送る表の枠の描き方**（5-2）: 場所を取らない線で描くか、場所をはじめから取っておくかを、T4-17 で表の字の左端がほかの本文とそろうほうに決めます。
- **札の保存の区画を残すか**: T6 が決めます（7-2）。T4 は、残る前提で置き場所を決めています（2-2）。
- **見出しの区切りの印（`<wbr>` のままか、ゼロ幅スペースに替えるか）**（2-3）: T9 の iOS の VoiceOver の聞き取りで決めます。実機を使える機会が無いときは `<wbr>` を保ち、聞けなかったことを T9 の記録に残します。`<wbr>` の所で読み上げが切れると分かったときは、PM が T9 の中に直しのタスクを立て、区切りの印を決める部品（`PhrasedText`）と、一覧の件数の行（`ListStatus`）を、1つの文字の並びの組み方に替えます。

判定の印（3-1 の A）と、ゲームの頭の組み方（2-6 の V7）は、設計の時点で決めました。

**Minor-1（括弧の中・1字の行・行頭の長音符）**:
