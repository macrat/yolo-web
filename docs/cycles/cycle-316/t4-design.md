## 0. 前提の事実（棚卸しに足したもの）

画面の数は、本番のビルドを `next start` で配信し、`/opt/pw-browsers/chromium` の Playwright で測りました。**このコンテナには Chromium しか無く、決まりにより `playwright install` でブラウザを足しません**（`docs/knowledge/playwright-mcp.md`）。WebKit での見え方は、下の外部の仕様と、10章の確かめ方で扱います。

- **BudouX は、character-personality の24のタイプ名を、どれも語の途中で割らずに文節に分ける。** `budoux` 0.9.2 の既定の日本語の分け方（`loadDefaultJapaneseParser`）で24件を分けると、数字と助数詞は1つの文節に残り（「3秒後に」「10年経っていた」「1000回繰り返す美の」）、括弧と助詞も文節の中に入った（「来てるか！」と」「解釈だと…」と」）。文節の最長は「これ普通じゃないよね」と」の12字。
- **新しい折り方が使うのは、どのエンジンでも同じに効く機能だけである。** `<wbr>`、`word-break: keep-all`（Safari・iOS Safari 9 から。https://caniuse.com/mdn-css_properties_word-break_keep-all ）、`overflow-wrap: anywhere`（Safari・iOS Safari 15.4 から。https://caniuse.com/mdn-css_properties_overflow-wrap_anywhere ）、`white-space: nowrap`。Chromium でしか効かない `word-break: auto-phrase` を使わない。行の切れ目を決めるのは `<wbr>` の位置と、見出しの書体（Zen Antique。Web フォントなのでどちらのエンジンにも同じもの）の字の幅なので、Chromium で `auto-phrase` が効いていないことを確かめて測れば、WebKit の近似として扱える。サイトの索引とアコーディオンのラベル（`LinkIndex`・`IndexAccordion`）は、すでに `keep-all`・`<wbr>`・`overflow-wrap: anywhere` で組まれている。
- **文節の区切りだけでは、文節が1行に収まらないときに禁則が破れる。** 24のタイプ名を `keep-all`・`<wbr>`・`overflow-wrap: anywhere` で、セクションの見出しの段・幅 244px（320px の画面のボックスの中身の幅）に組むと、既定の文字サイズで1タイプ、200% で7タイプが、閉じ括弧を行頭に置いた（「来てるか！／」と」「大丈夫?／」と」）。`anywhere` の非常の折りは禁則を見ないためである。行頭に置かない字（閉じ括弧・句読点・！？・…・小書きの仮名・長音符）をその前の1字と、行末に置かない字（開き括弧）をその次の1字と、`white-space: nowrap` の字のまとまりにすると、既定でも 200% でも禁則の破れは0タイプになり、はみ出しも0で、見出しの読み上げの名前は元の文と同じだった。文節ごとに `display: inline-block` で包む組み方は、禁則は守るが、200% で19タイプが見出しの幅からはみ出し、読み上げの名前に文節ごとの空白が入った（「普段は 後方で 全員の …」）。
- **解き終えた画面の試作の実測**（`/play/character-personality` を解いたあと、包みを結果のボックスに差し替え、§5 の幅（375px でボックスの x=27・幅 321px）にして、24タイプのタイプ名・キャッチコピー・説明を流し込んだ。375×667・Chromium・`keep-all`・`<wbr>`）:

## 2. 結果の組み方（論点 1〜6）

### 2-1. 結果のボックスが囲むもの

**ボックスは結果と、結果を写すコピーのボタンだけを囲み、入力と、結果を生む操作は囲みません。** 結果のボックスは `ResultBox`（`src/components/ResultBox/`）の1つの部品にし、診断・占い・道具・ゲームのどの結果もこれで組みます。

| 案                                                        | 来訪者に見えること                                                                                       | 捨てた理由・採った理由                                                                                                                                                                    |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. いまの形（道具は入力と結果を同じ `Panel` に入れる）    | 太い枠が道具全体を囲み、結果は枠の中のどこか。結果の区画はカードや細い枠で道具ごとに違う                 | 捨てる。太い枠が「道具」と「結果」のどちらを指すかが面で違い、結果を一目で探せない。コード・表・一覧の結果が道具の枠の中で自分の枠を持ち、ボーダーが二重になる（§8）                      |
| B. 道具の枠の中で、結果の区画を小見出しと細い罫線で分ける | 太い枠が道具全体を囲み、結果は枠の中の小見出しの下                                                       | 捨てる。二重のボーダーは消えるが、コードの結果を `--paper-2` の地のボックス（§5）にできない。診断の結果（ボックス）と道具の結果（区画）で、結果の見え方が2つになる（§12 位置の一定）      |
| **C. 入力は囲まず、結果を結果のボックスに入れる**         | どの面でも、太い枠の中にあるものがその操作の結果。入力欄は細い枠とラベル（§8）で、結果は太い枠で見分ける | **採る。** 診断・道具・ゲームの結果が同じ形になり、来訪者はどの面でも太い枠を見れば答えに着く。コード・表・一覧の結果は、結果のボックスがそのままそのコンポーネントのボックスになる（§8） |

コピーのボタンは結果のボックスの頭に置きます（2-5）。コピーは、写して使う道具の結果でいちばん使う操作で、結果の長さに関わらず、結果が出たその位置ですぐ押せる必要があるからです。

`ResultBox` が持つもの（形の見本。名前と細部は実装で決めます）:

- §5 のボックス（太い線・内側の余白・コンテンツ幅いっぱい）。中身がコード・表・一覧のときは、そのコンポーネントの形（コードなら `--paper-2` の地）をボックス自身が持ち、中に枠を重ねない。
- 頭の行: 結果の見出し（あれば）と、コピーのボタン（写して使う結果のとき）。
- 結果の登場の動き（§11。1回・250〜400ms。`prefers-reduced-motion` で即時）。結果の登場の動きは、この部品だけが持つ（6章）。
- 結果に着いたときにフォーカスを受ける場合の `tabindex="-1"` と、読み上げの名前（結果の見出しを指す）。

### 2-2. 性格診断の解き終えた画面（論点1・2）

**組み方**（上から）:

1. **結果のボックス**
   1. 補助情報の1行「{診断名}の結果」（例「あなたに似たキャラ診断の結果」。`0.875rem`・`--ink-2`）。
   2. **タイプ名**を結果の見出し（`h2`）として、§4 のセクションの見出しの段（`45rem` 未満で `1.49rem`）で、見出しの書体で組みます。文節の区切りで折ります（2-3）。
   3. 伝統色診断だけ、タイプ名の下に結果の色の色見本（`result.color`。細い枠・文字を載せない。§2）。
   4. キャッチコピー（本文の大きさ・`--ink`）。
   5. 説明（`result.description`。本文の大きさ・本文の幅）。
2. **持ち帰る・共有する**の区画（ボックスの外、すぐ下）。character-personality の札の画像の保存と共有（`FudaActions`）と、共有のボタン（7-3 で1つにした `ShareButtons`）を1か所にまとめます。
3. **詳しい読みもの**（成り立ち・日常・メッセージなど、診断ごとの詳細）。セクションの中の小見出し（上に細い罫線。§5）で分け、文は段落、あるあるは箇条書きで組みます。`--paper-2` の地のカードと細い枠の行（`.behaviorsItem` など）は持ちません。
4. 相性（友だちの結果から来たとき）と招待。
5. すべてのタイプ（`OtherTypesNav`。T3 で組んだもの）。
6. 「もう一度挑戦する」。

**ページの共有**（`QuizPlayPageLayout` の「この診断が楽しかったらシェア」）は、診断のプレイ面から外します。解き終えた画面では結果の共有と2か所になり（§8 に書く「結果を持ち出す操作は1か所」に反する）、解く前の来訪者が診断を共有した回数は直近28日で0回です（0章）。

## 3. 色（論点 7〜13）

`DESIGN.md` §2 は、色を使うのは「その色がコンテンツそのものであるときだけ」とし、区別・強調・気分のための色を、コンテンツであっても認めません。棚卸し 4-2 の「色の性質」の列で、和色はどれも区別・強調・気分の色にあたります。この章は、§2 のとおりにする形で決めます。

### 3-1. 判定の示し方（論点7）

対象は kanji-kanaru・yoji-kimeru の判定のマスと凡例、nakamawake のグループの難易度、統計の分布の強調です。

### 5-4. `hr` と引用（論点18）

- `hr` は細い線（`--rule-2`・`--rule-w-hair`）で、本文の幅に引きます。本文の中の話の区切りは、セクションの切れ目（全幅の太い罫線）より弱い区切りで、§5 で細い線が受け持つ「小見出しの上の区切り」と同じ強さです。太い線にすると、全幅の罫線と取り違えます。
- 引用は、左に細い線（`--rule-2`）を引いて字下げし、字は `--ink` で組みます。引用した文は記事の中身で、「前に出ない文字」（`--ink-2`）ではありません。2px の線（§5 の2種のどちらでもない）はやめます。
- §5 の線の表の「細い」の使う場所に、「本文の区切り（`hr`）・引用の左」を足します（8章）。左だけの線は何かを囲まないので、§6 の囲みの読み分けに掛かりません。

### 5-5. mermaid（論点19）

- 図の配色を、mermaid の `base` のテーマに UI のトークンの値（`--paper`・`--paper-2`・`--ink`・`--rule-2`）を渡した無彩にします。ダークでも同じ値の組のダーク版を渡します。図の中の区別は、mermaid がもともと持つ形（箱・菱形・線種）と字で読みます。gantt の `crit` は「テスト失敗」の字で言われている（棚卸し 4-3）ので、色を外しても情報は減りません。
- **図は縮めすぎず、本文の幅に収まらないときはボックスの中で横に送ります。** 図の中の字が §4 の補助情報の下限（`0.875rem`）より小さくなるまでは縮め、それより小さくなる図は、その大きさで描いて横に送ります（表・コードと同じ扱い）。いまは 375px で 0.18倍に縮めて字が読めません（棚卸し 4-3）。狭い画面で mermaid の記事を見た来訪者は28日で0回ですが、記事は検索から着く面で、見る来訪者が現れたときに読めない図を出さないためです。

### 5-6. 絵文字

本文の絵文字（2本・5行）は、どれも絵文字の数え方を説明する題材の字です（棚卸し 4-3）。これは中身なので残します。§5「絵文字は、どこにも置かない」と食い違うので、§5 に「その字そのものが話題であるときは、本文の字として置く」を書き足します（8章）。§2 の中身の色・§5 の中身の画像と同じ考え方です。

**確かめ方の共通の決まり**

- ブラウザは `/opt/pw-browsers/chromium` の Playwright です。`playwright install` でほかのブラウザを足しません。
- **WebKit の近似の測り方**（見出しの折り方）:
  1. 測る見出しの要素とその中の計算値の `word-break` が `keep-all` で、`globals.css` の `auto-phrase` が効いていないことを先に確かめる。
  2. 見出しの字を1字ずつ Range で行の位置を取り、行に分ける。行の切れ目が、`<wbr>` の所か、文節が1行に収まらない所（§4 の例外）だけにあること、どの行頭にも行頭に置かない字（閉じ括弧・句読点・！？・…・小書きの仮名・長音符）が無く、どの行末にも開き括弧が無いこと、見出しの幅からはみ出さないことを見る。行の切れ目を決めるのは `<wbr>` と Web フォントの字の幅なので、これを WebKit の近似とする（0章）。
  3. まだ `auto-phrase` に頼る見出し（T5 が直すまでのもの）の WebKit の見え方は、棚卸し 2-5 と同じく、Chromium でその見出しに `word-break: normal` を当てた近似で測る。
  4. 近似で拾えない差は、2-3 の末尾の型にして T9 に渡す。
- 「200%」は、CDP の `Page.setFontSizes` で既定の文字サイズを 32px にした状態です。
- 本番のビルド（`npm run build` のあと `next start`）で、自分の worktree と、ほかと重ならないポートで測ります。

## 11. 決めきれない所と、確かめれば決まること

どれも PM が確かめて決めます。

- **判定の色の扱い**（3-1）: 設計は A（印だけ・無彩）を採りました。撮った盤（いま・A・B・C。375px と 320px、A はダークも）を PM が見て、A が明らかに読みにくければ、index.md の「`DESIGN.md` を変えるとき」の手順で B を問い直します。
- **ボックスの中の間隔**（補助情報とタイプ名のあいだが 8px か 16px か、など）: T4-5 で2つ組んで 375px で撮り比べ、タイプ名が補助情報の続きに見えないほうを採ります。試作（0章）は 8px で測りました。
- **ゲームの頭が最初の画面に入らないときの手当て**（2-6）: T4-10 で測り、要約を1行に縮めるか、盤の空の行の高さを詰めるかを撮り比べて決めます。
- **横に送る表の枠の描き方**（5-2）: 場所を取らない線で描くか、場所をはじめから取っておくかを、T4-17 で表の字の左端がほかの本文とそろうほうに決めます。
- **札の保存の区画を残すか**: T6 が決めます（7-2）。T4 は、残る前提で置き場所を決めています（2-2）。
