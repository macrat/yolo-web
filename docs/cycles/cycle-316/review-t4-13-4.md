## 指摘

### Major-1: 200% でキーボードでチェックすると、フォーカスが画面の外の語に移る

`handleCheck` のあと、次の3つが起きる。

- `revealControl(statusRef, context)` が、status の下端を画面の下に合わせる。
- 当てた組と格子の最初の行と status が画面に収まらないときは、status を入れることが先になる。
- そのうえで、`firstWord.focus({ preventScroll: true })` がフォーカスを格子の最初の語へ移す。

320/375 × 200% では格子が2列の縦長になるので、フォーカスを受け取った語が画面のまったく外に出る。

| 画面       | 1回目のチェック（当たり）のあとのフォーカス（viewport 667） |
| ---------- | ----------------------------------------------------------- |
| 320 × 32px | 語のマスが top -221〜bottom -136（全体が画面の上の外）      |
| 375 × 32px | -159〜-74（全体が外）                                       |
| 375 × 24px | 4〜80（入る）                                               |
| 320 × 16px | 293〜360（入る）                                            |

2回目と3回目も、320 × 32px では -95〜-10、-35〜50 だった（kb.mjs）。

- **来訪者に起きること**: 文字を大きくして使う弱視の人がキーボードで遊ぶと、チェックのあとフォーカスのリングがどこにも見えない。そのまま Space を押すと、見えていない語が選ばれる。WCAG 2.4.7（Focus Visible）と、2.4.11（Focus Not Obscured）の考え方に反する。既定の大きさでは起きないので、これまでの確かめからは漏れていた。
- **直すこと**: フォーカスを格子へ移すとき（`focusGrid`）は、フォーカスを受け取る語が画面に入ることを先にして送る。status は `role="status"` なので読み上げられ、目で見る分は語の格子のすぐ下にある。たとえば、送る先の control を最初の語にし、status は入るときだけ入れる。または、フォーカスを移す先を「画面に入っているいちばん上の語」にする。直したら、320/375 × 200% でキーボードの1局を通して、どのチェックのあともフォーカスした要素が画面の中にあることを示す。

### Minor-1: `grid-auto-rows: 1fr` で、長い語のある日は 1280×800 の最初の画面からチェックが出る

`1fr` にすると、並べ替えても格子の高さが変わらず、開き直しの場所取りと合う。この考え方は正しく、既定の大きさの見た目も受け入れられる。どのマスも同じ高さの札になり、四角の位置が行ごとにそろう（shots/grid-fish-320-16.png・375-16.png）。

ただし、2行に折れる語が1つあると、4行すべてが高くなる。2巡目と同じ魚の組を入れて 1280×800 で測った。

- `1fr` のとき、格子は 323〜717、チェックは 781〜825 で、最初の画面の外に出る。
- `auto` のときはチェックが 717〜761 で、前回のレビューの値と同じく画面に入る。
- 375×667 では格子が 346〜780 になり、`auto` の 710 より 70px 高い。

今日の問題（語は3字まで）では 696〜740 で、画面に入る。9字以上の語（「リュウグウノツカイ」、ことわざ）を持つ問題は、50問のうち数問である。4つ目の語を選べばチェックまで送られるので、遊べなくはない。

- **直すこと**: 2つのどちらかを取る。1つは、マスの縦の余白を減らすなどして、1280×800 でもチェックが最初の画面に入るようにすること。もう1つは、PM が受け入れを決めて t4-design.md に書き残すこと。

### Minor-2: 語のマスで、行頭の長音符と語の中の折れが出る（受け入れた「4字の語」の外）

`overflow-wrap: anywhere` と `text-wrap: balance` の組み合わせで、次のように折れる。

- 行頭の長音符: 320 既定・375 200%・320 26〜32px の「サラリ／ーマン」、375 18〜20px の「シャ／ープペ／ンシル」。
- 語の中の折れ: 1280 の既定と 20〜32px で「風が吹けば桶／屋が儲かる」。広い画面の既定の大きさで「桶屋」が割れる。

どちらも受け入れた「320 既定で4字の語が折れる」の外にある。DESIGN.md §4 の「通常の禁則処理」でも、行頭の長音符は避けたい。

- DOM で `line-break: strict` を足して測った。「サラリー／マン」「サラ／リー／マン」になり、行頭の長音符は消え、1字の行もできない（grid2.mjs）。`word-break: auto-phrase` は「アンコ／ウ」「テーブ／ル」と1字の行を作るので、使わない。
- ことわざの問題（#34 などの語）は、`splitIntoPhrases` で文節の切れ目に `<wbr>` を置き、`keep-all` にすると「風が吹けば／桶屋が儲かる」と折れる。組の語の並びと同じ考え方である。
- **直すこと**: `.wordButton` に `line-break: strict` を足す。ことわざのように文節を持つ語は、文節で折る。直したら、上の3つの語の組で、320/375/1280 × 16〜32px を測り直す。

### Minor-3: 解き終えた日の場所取りの高さが、回転・拡大のあとも残る（共有の部品）

ナカマワケは `releaseSavedLayout` を一度も呼ばない。解き終えた日は `min-height` の値を「外さない」ので、画面の向きや字の大きさを変えたあとも、前の高さが残る。

- 375×667 で開き直したあと 667×375 に回すと、区画は 1880px のまま、中身は 1764px になり、結果の下に 116px の空白ができる（rot.mjs、shots/rot-375-667-16.png）。
- 320 から 1280 に広げると、23px の空白が残る。
- ページから離れても、`<head>` の `<style>` がサイトの中の移動のあいだずっと残る。漢字カナールと四字キメルは、外したときに `useEffect(() => () => releaseSavedLayout(...))` で外している。ナカマワケだけがこれを持たない。
- **直すこと**: 結果の区画を描き終えたら（ReservedResultArea が高さを覚えたら）、取っておいた高さを外す。または、ResizeObserver で幅か字の大きさが変わったと分かったときに外す。これを共有の部品の側で決める。ナカマワケにも、外したときの片付けを入れる。

### Minor-4: `savedLayoutScript` が JSON を `<script>` にそのまま埋める

`JSON.stringify(options)` は `<` を逃がさない。いまの設定は開発者が書く定数なので、実際の害は無い。ただ、どのゲームからも使う共有の関数としては、渡す値に `</script>` が入ると壊れる。すでにある `safeJsonLdStringify` と同じ逃がし方（`<` を `<` にする）を使い、テストを1つ足す。
