  - 短い結果は、下端が画面の下端から 8px 上に入る所で止める。
  - 結果が収まっていれば送らない。
  - キーボードで中身の区画に着いたら、ボックスの上端とリングの上の辺から見せる。

- `src/lib/reveal.ts` の頭の注釈は「（DESIGN.md §8・§11）」と規定を指すが、指した先に `revealResult` の決め方は書かれていない。

- **直し方の方向:** planner が §8 の送りの規定を、コントロールを見せる送り（ゲーム）と結果を見せる送り（道具）の両方を1つの考えから導く文に書き直す。上の4つ（短い結果の止め方を含む）とその理由を書き、2-5 にも当てはめを書く。そのうえで、`reveal.ts` の注釈がその文を指すようにする。

### M2. キーボードで着いたときの直しが道具の中にあり、逆向きに着くとボックスの上端まで跳ぶ

- `JsonFormatterTile.tsx` の `handleResultFocus`（`onFocus` と `:focus-visible` の判定）が、`revealFocusedFrame` を呼ぶ。
- ところが、これが扱うのは `ResultBox` の中身の区画のフォーカスと、`ResultBox` が描くリングである。`ResultBox` で `kind="code"`・`kind="table"` を使う面は、どれも同じ直しが要る。いま `kind="table"` の年齢計算はこれを持たない。
- 1巡目は「消えないなら、`ResultBox`（共有の部品）で扱う必要がある」とした。実際、ブラウザの送りは消えていない。Tab で区画に着くと、Chromium はまず区画の上端を画面の上端に合わせて送り、次の描画の前に `revealFocusedFrame` が戻している。
- 見本の道具の中に置くと、T5 の道具が1本ずつ `handleResultFocus` を写すことになる（AP-I02）。
- 測った動き（375×667、499行を整形したあと）は次のとおり。
  - **順に進むとき:** コピー → 区画で `scrollY` が 692 → 788 動く（320 で 156px、320・200% で 318px、375・200% で 239px、1280・200% で 159px）。Tab を押す前から、ボックスの上端（上から 110px）とリングの上の辺は画面にあった。それでもブラウザの送りのあとで直すので、操作の行が画面の外へ出る。
  - **逆向きに着くとき:** 区画から Tab で FAQ の開閉（`summary`）へ進むと、`scrollY` は 13,677 になる。そこで Shift+Tab で区画に戻ると、`scrollY` は **788 へ 12,889px 戻り**、ボックスの上端が画面の上に来る。結果の終わりを読んでいたキーボードの来訪者は、戻った瞬間に 499行の頭へ連れていかれる。
  - **コピーのボタンでも動く:** `handleResultFocus` は中身の区画だけでなく、コピーのボタンにキーボードで着いたときにも `revealFocusedFrame` を呼ぶ。注釈の「コードの区画に着いたら」と合わない。いまはコピーのボタンが頭の行にあるので害は小さい。
- **直し方の方向:** この直しは `ResultBox` が中身の区画に持たせ、道具は何も渡さないようにする。直す条件は、1巡目の M2（リングの上下の辺がどちらも画面に無い）に絞る。フォーカスの知らせの時点（ブラウザが送る前）の位置を覚え、そのときリングの辺が画面にあったなら、その位置に戻す。そうすれば、順に進むときは動かず、逆向きに着くときは終わりの側が見えたままになる。どう振る舞わせるかは planner が M1 の §8 の文と合わせて決める。

### M3. 誤りの位置は、Chrome でもよくある誤りの種類で出ない

- PM の決定は「Safari の `JSON.parse` は誤りの位置を言わないので、その場合は行と列を出さない」だった。
- ところが、V8（Chrome・Edge、Node 22.22 で確かめた）も、「Unexpected token」の種類では位置を言わない。
  - `{"a": True}` は「Unexpected token 'T', "{"a": True}" is not valid JSON」になる。
  - `None`・`undefined`・`NaN`、`// コメント`、`tru` のような打ち誤り、引用符の無い値（`{"a": abc}`）も同じである。
  - 一方、末尾のカンマ・引用符の無い鍵・単引用符・閉じ忘れは「at position 7 (line 1 column 8)」の形で位置を言う。
- **来訪者に起きること:** Python の `dict` を貼った（`True`・`None`）、コメントを残した、値を引用符で囲み忘れた、という開発者にありふれた誤りでは、いちばん多い Chrome の来訪者にも「JSONの形式が正しくありません。」だけが出る。500行の JSON のどこを直せばよいか分からない。
- 一方で、道具の説明は来訪者にこう約束している。`meta.ts` の `description` は「インデント幅の設定やエラー位置の表示に対応」、`howItWorks` は「JSON構文エラーがある場合はエラー内容を表示します」である（いまはエラーの内容は出さず、位置も出ないことがある）。
- 決定の前提（Safari だけの制約）が事実と違うので、PM が決め直す。
  - **位置を自分で求める:** 誤りの最初の字を走査して見つければ、どのブラウザでも同じ行と列が出る。道具のいちばん役に立つ情報をそろえられる。
  - **受け入れる:** 説明の文を、実際に言えることに合わせて直す。
  - いずれでも、説明の文は実際の振る舞いと一致させる（constitution の 4、品質）。

### m2. §5 の書き足しが、規則と例外の形に読める

いまの文は次のとおりである。

> コードは `--paper-2` の背景のボックスに置き、折り返さずその中で横に送る。タブは2字の幅にする。行を持たない1続きのコード（圧縮した JSON など）は、横に送ると終わりまで読めないので、ボックスの幅で折り返し、どこで折れてもよい。

- 「横に送ると終わりまで読めない」は正しくない。送れば読める。1巡目で測ったとおり、1行が 86,000px になって見渡せないのが理由である。
- タブを2字にする理由が §5 に無い。理由は `globals.css` の注釈（深い字下げも狭い画面に収まる）にだけある。
- 例: 「コードは `--paper-2` の背景のボックスに置く。行を持つコードは、行と字下げが構造を見せるので折り返さず、ボックスの中で横に送る。タブは2字の幅にし、深い字下げも狭い画面に収める。行を持たない1続きのコード（圧縮した JSON など）は、1行が画面の何十倍にも伸びて見渡せないので、ボックスの幅でどの字のあいだでも折り返す。」。M1 の §8 の書き直しと一緒に、planner が文を決める。

### m4. ゲームの `revealControl` を移すことが、タスクの一覧に無い

- `DESIGN.md` はコードの行間を決めていない。記事のコードにも効くサイト全体のことなので、この道具の直しの範囲ではない。PM が扱い（§3・§5 で決めるか、バックログに積むか）を決めて記録する。

### m7. 欄に貼ったタブは 8字、結果は 2字の幅になる

- 入力の欄（`Textarea` の `variant="mono"`）は `tab-size` が既定の 8 のままである。タブで字下げした JSON を貼ると、欄では1段が8字、整形した結果では2字になり、同じ JSON の見た目が欄と結果で4倍違う。
- 等幅の欄はコードを書く所なので、§5 のタブの幅を当てるかを PM が決める。当てるなら `Textarea` の共有の部品の変更になるので、AP-I14 のとおり、使う面をすべて撮り比べる。

## 3. `src/lib/reveal.ts` について

- **サイト全体の1つの部品になっている。** 道具にもゲームにも依らない名前と引数で、`visibleRange`・`isInside`・`revealResult`・`revealFocusedFrame` を持つ。送りはどれも `behavior: "instant"` で、送る量が0なら送らない。
- **`visualViewport` と `offsetTop` の扱いは正しい。**
  - `getBoundingClientRect` はレイアウトのビューポートの座標である。`visualViewport.offsetTop` は、見えている範囲のレイアウトのビューポートからの位置である。したがって、見えている範囲を `[offsetTop, offsetTop + height]` とするのは同じ座標で比べている。
  - テストの期待値を手で計算し直し、どれも合っていた。たとえば `offsetTop 200・height 300`・操作の行の上端 450 では、450 − (200 + 8) = 242 になる。
  - ボタンを押したとき、iOS では文字盤が閉じる途中で測ることがある。それでも送り先は見えている範囲の上端で決まるので、閉じたあとも操作の行は上に残る。
- **ゲームの `revealControl` は、振る舞いを変えずにここへ移せる**（m4）。
- `revealFocusedFrame` の置き場所と条件は M2 のとおりである。

## 4. §5 の書き足しと `tab-size` の影響（AP-I14）

- 文の形は m2 のとおりである。
- `:where(pre)` の `tab-size: 2` が効くのは、タブの字を持つ `pre` だけである。サイトの中を洗った。
  - **記事（87本）:** 本文の Markdown にタブの字は1つも無い（`\t` の字の並びは正規表現の説明の中の文字列で、タブの字ではない）。記事のコードの見た目は変わらない。
  - **テキスト差分（text-diff）:** 来訪者の文を `pre`（`pre-wrap`）で組む。タブで字下げしたコードと、タブで区切った表を差分にして撮った。字下げは2字の幅でそろい、「−」「＋」の印のあとも崩れず、ページは横に伸びない（375 で `scrollWidth` 375）。害は無い。
  - `pre` を持つほかの所は、この道具と storybook だけである。regex-tester は `pre` を持たない。

## 5. 見た目（ライト・ダーク・はみ出し・リング）

- **ライトとダーク:** 375・1280 の既定、320 の 200% で撮った。コードのボックスは `--paper-2` の地（ダークで `oklch(0.24 0 0)`）に字が `--ink` で、どちらもはっきり読める。「整形」は反転、「圧縮」「検証」「コピー」は下線で、ダークでも同じ見え方になる。圧縮した JSON の折り返しも、ダークで同じに読める。
- **はみ出し:** どの条件でも、ページは横に伸びない。整形した JSON の長い行は、ボックスの中だけで横に送る（375 で区画の中身 728px・見える幅 299px、`tabindex="0"`・名前「コード（横にスクロールできます）」）。1280 の既定ははみ出さず、区画はフォーカスを取らない。
- **リング:** 区画に着くと、ボックスの太い線の外に、内の `--paper` の輪と外の `--ink` の輪（`solid 3px`）が密着して出る。上の辺も画面の上端から 8〜9px に見える（§6）。
- **頭の行（42d853a）:** 320・375・1280 の既定と 1280 の 200% では、名前とコピーのボタンが1行に並ぶ（44px・64px）。320・375 の 200% では、ボタンが次の行の右端に移り、名前は削られない（§6）。`ResultBox` でコピーのボタンを渡すのはこの道具と base64（と storybook）だけで、見出しを持つボックスは渡していないので、ほかの面の見た目は変わらない。
- **気づいたこと:** 誤りのとき（整形のボタンを画面の下端から 8px に置いて押す）、知らせの文が欄の下に入るぶん、整形のボタンは画面の下へ押し出される（320 で下端 631/568）。次にすることは欄を直すことで、知らせ（405〜468px）と欄は見えているので、§8 のとおりである。
