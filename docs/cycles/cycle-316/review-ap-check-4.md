## 指摘（重い順）

### 中1 手順3 のとおりに打つと、main から AP-WF29・30・38・39・41 が消える（AP-WF41・AP-WF12）

- split-plan.md 2 は手順のコミットの `candidates.md` を「cycle-316 の完了のコミットのものと同じにする（AP-WF42 候補と AP-WF43 候補が入る）」とし、6 の手順3 は「Edit で同じ変更を当てる（…`candidates.md` の AP-WF42 候補と AP-WF43 候補の2節）」と書いたあと、`git diff claude/cycle-kickoff-rv3l21 -- <その3つのパス>` が何も出さないことを確かめさせる。
- 完了のコミットの candidates.md は、AP-WF42・43 の2節を足すだけでなく、workflow.md へ昇格した AP-WF29・30・38・39・41 の5節を消し、AP-WF17 候補の扱いを書き換えている。そのため、2節だけを当てると確かめの `git diff` が空にならず PM はそこで止まり、確かめが空になるまで当てると、main の candidates.md から5節が消える。手順のコミットには workflow.md が入らないので、main にはこの5項目が本体にも候補にも無くなる。
- main はこれから約20サイクルのあいだ、急ぎの不具合を直すサイクルが使い、各サイクルのセッションが始まる所でもある。この期間、main で動くサイクルは、このサイクルが昇格させた点検（自分のツールの結果を読む・評価で対応範囲を縮めない・品質レビューを打ち切らない・改稿で同型の欠陥を入れない）を持たない。2節だけを足す読みと「同じにする」読みが同じ手順の中で食い違っていること自体も、PM が上から打てない原因になる。
- 直すこと（PM が決め、planner が書く）: 手順のコミットのアンチパターン集を一貫した形にする。例えば `docs/anti-patterns/` の4ファイル（workflow.md・planning.md・implementation.md・candidates.md）をすべて完了のコミットと同じにし、2 の一覧、手順3 の `git diff` と `git add` のパス、`git diff --stat origin/main` が示すべきパスの数、手順5 の「衝突しない」ものの一覧をそれに合わせる（どれも来訪者に見える変更を含まず、両方の側で同じ中身なので手順5 のマージで衝突しない）。あわせて、incident-1・2 の再発防止の担保である `block-process-kill-and-browser-install.sh`（と `settings.json` の登録・`lib/`）を main にも入れるかを決め、入れないならその理由を decisions.md に書く。入れなければ、main で立てる急ぎのサイクルには `pkill` や `playwright install` を止める仕組みが無い。

### 中2 昇格した AP-WF38 が、AP-WF01・完了のチェックリスト・レビュアーの定義と両立する道を持たない（ツギハギの規則に反する食い違い）

- AP-WF38 は「実体が正されたあとも、記述の精度の指摘のためにレビューの巡を重ねていないか」と問う。一方、同じ workflow.md の AP-WF01 は「最後の修正のあと、それがどんな修正であったとしてもレビューを実施したか？ すべての指摘事項に対応したか？」と問い、完了のチェックリストは「すべての変更がレビューされ、残存する指摘事項が無くなっている」を求め、レビュアーの定義（`.claude/agents/reviewer.md`）は「ごく小さな問題でも、どんな問題も見逃さずに指摘」し、指摘が1つでもあれば直させてもう一度レビューさせるよう PM に指示する。
- 精度の指摘だけが残った巡で PM が取れる道は、直して次の巡を頼む（AP-WF38 に反する）、直して次の巡を頼まない（AP-WF01 の前半に反する）、直さずに閉じる（AP-WF01 の後半と完了のチェックリストに反する）のどれかで、どれを取っても拘束するチェックリストのどれかに反する。候補のあいだは拘束しなかったが、本体に置いた今は、点検のたびにこの食い違いが現れる。この完了の処理そのものがその場面にある（4巡目の点検は内部記録が対象である）。
- decisions.md の昇格の理由は、オーナーの規則（気づけるか）だけを確かめ、ほかの拘束する規則と両立するかを確かめていない。「気づけるか」には当たる（次の巡を頼む時に気づける）ので、オーナーの規則には反しない。問題は気づいたあとに取れる正しい行動が規則の中に無いことである。
- 直すこと（PM が決め、planner が書く）: AP-WF38 の本文を、AP-WF01・チェックリスト・レビュアーの定義と食い違わずに守れる形にするか、それができるまで候補に戻すかを決め、decisions.md に理由を書く。本文を直すなら、たとえば「内部記録のレビューを頼むときに、見る観点を実体の誤りと虚偽の記録に限って渡しているか」のように、レビューを頼む側の行為を問う形にすると、レビュアーが指摘しても PM が閉じられない、という食い違いを生まない（観点を渡すことは AP-WF02 とも合う）。

### 軽1 手順1 が確かめさせる `git status` の中身に、hook・`settings.json`・take-screenshot のスキルが無い（AP-WF12）

- 6 の前書きは作業ツリーの完了のものを「文書・スキル・backlog・candidates.md」とし、手順1 は `git status --short` と `git diff --stat` に「`docs/` の変更と未追跡の文書・`cycle-kickoff` と `cycle-completion` のスキル・`docs/backlog.md`・`docs/anti-patterns/candidates.md`」だけが出ることを確かめさせる。実際に出るのは、それに加えて `.claude/hooks/pre-commit-check.sh`・`stop-cycle-guard.sh`・未追跡の `block-process-kill-and-browser-install.sh` と `lib/`・`.claude/settings.json`・`.claude/skills/take-screenshot/` の2ファイルである。
- 書かれたとおりに照らした PM は、期待にないものが出たとして止まるか、これらを完了のコミットから外す方へ動きうる。外せば、incident の再発防止の担保が完了のコミットに入らない。

### 軽2 このサイクルで足した AP-WF42・AP-WF43 候補が、手順を書いている（`.claude/rules/anti-patterns-directory.md` の Don't）

- AP-WF42 候補の「対症療法案」は `git commit -- <パス>` と `git diff --cached --stat` の手順を、AP-WF43 候補の「対症療法案」は比べる表の列の作り方を書く。`.claude/rules/anti-patterns-directory.md` は `docs/anti-patterns/**.md` に「どのような手順でやるべきか」を書くことを禁じ、8ca36da7 はまさにこの理由で cycle-312 の旧 AP-WF42 候補を消した。今回その 312 を発生に数えたので、同じ候補の中で、消された理由と同じ形が残っていることになる（AP-WF41 の「過去に指摘された型を新しく入れる」）。
