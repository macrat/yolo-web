# T5 面ごとの適用の設計

対象は index.md の T5 の行と、[t5-inventory.md](./t5-inventory.md)（以下「棚卸し」）の「決めること」41問（1-a〜10-e）です。ここで1問ずつ答え、実装をタスクに分けます。

- 事実は棚卸しの節番号で引きます（例「棚卸し 4-1」）。棚卸しに無い事実で、この設計のために測ったものは 0章に書きます。
- どの問いも3つ以上の案を来訪者の側から比べ、画面の組み方で答えが変わる問いは試作して測りました。重みは棚卸し 0章の GA（診断・クイズのプレイ面 81.01%、一覧 7.85%、辞典の詳細 3.02%、トップ 2.13%、ブログの記事 1.90%、ツール 1.75%、結果のページ 1.07%、ゲーム 0.86%）です。
- `DESIGN.md` を変える答えは、書く文を 9章にまとめます。`DESIGN.md` そのものは T5-1 で書き換えます（`frontend-design` スキル「`DESIGN.md` に無いコンポーネントを足したくなったら、先に `DESIGN.md` へ書く」）。

## 1. 優先の付け方

**直す順は、その面に来る来訪者の数の順にする。** 診断のプレイ面が PV の 81.01%（`/play/character-personality` だけで 74.87%）を占めるので、面のタスクの最初はプレイ面の頭と開始（T5-4）と、解き終えた画面（T5-5a・T5-5b）です。どの面も使う規則（`DESIGN.md` の書き足し・ページの頭の位置）は面より先に置き、共有の部品（文節の区切り・表）は、それを使う面のタスクより先に置きます。面ごとに同じ補いを書くと、面によって見え方がずれるからです（§12 位置の一定）。出す順は 10-1 に書きます。

一覧（7.85%）は §4・§5 がすでにそろっていて、残りは見出しの区切りだけなので、仕事は小さく、プレイ面の次に置きます。道具は PV が 1.75% と小さい一方、仕事の量がいちばん多い（36本・棚卸し 11章）ので、頭の組み方（`ToolPageLayout`）を1つのタスクにし、道具ごとの直しを1本ずつのタスクにします。

## 10. 実装の分け方

どのタスクも、レビューを受けてから完了とします。**どのタスクも、終わった時点で `npm run build`・型の検査・lint・テストが通ることを完了の条件に含めます**（途中のコミットでもビルドを壊さない）。**スクリーンショット**は、どのタスクも変更の前と後を、320px・375px・1280px の既定と、320px の 200% で、ライトで撮って並べ、面の見た目を変えるタスクはダークも1枚撮ります（`take-screenshot` スキル）。変更の前は、タスクを始めるときのコミットのビルドです。**測る手順**は、ことわりの無いものは棚卸し 12章の手順で、測った値を棚卸しの値と並べてタスクの記録に残します。**横のはみ出し**は、どのタスクも棚卸し 12章の「はみ出し（4-2・4-3）」の手順（`main` の中の見える要素の矩形が画面の左右の端を越えるか。横に送れる祖先の中のものと、祖先がすでに越えているものを除く）で、既定と 200% の 320px で数えます。コンテナの `overflow-x: clip` が切って隠すので、`scrollWidth` だけでは見つかりません。

**受け持ちの決まり**（index.md 補足事項の、381d2d9 と 3b6111a の型の不一致と、同じファイルの並行の教訓）:

- 並行する作業があるあいだは、どのタスクも自分の受け持ちのファイルだけをパスで名指ししてコミットする（`git commit -- <パス>…`）。新しく作ったファイルと移した先は git がまだ知らないので、先に `git add <パス>` で載せてから名指しでコミットする（移すときは `git mv` を使い、移す元と移した先の両方を名指してコミットする）。`git add -A` や `git commit -a` で作業ツリーをまとめて載せない。同じ作業ツリーでほかのタスク（T5・T5a・T6・T7）が書きかけたファイルや、段に載せた削除を持っていかないためである。
- 共有の部品の型や props を変えるタスクは、それを使う側のファイルを同じタスク（同じコミット）に入れる。そのタスクが終わるまで、使う側のファイルに触るタスクを並行させない。
- `src/app/storybook/StorybookContent.tsx` は、部品の見本を持つので、部品の型を変えるタスク（T5-5a・T5-5b・T5-3a・T5-3c）がその見本も同じコミットで直す。この4つと T5-24 は、`StorybookContent.tsx` を T5-5a → T5-5b → T5-3a → T5-3c → T5-24 の順に触る。T5-3b と T5-8 は、部品の props を足すだけで既存の見本を壊さないので、`StorybookContent.tsx` を触らない（見本は T5-24 が足す）。
- ページのディレクトリ（`src/app/**/`）で T5 が受け持つのは、ページの `page.tsx`・`page.module.css` と、そのディレクトリの `__tests__` のうちページの試験だけである。画像のルート（`opengraph-image.tsx`・`twitter-image.tsx`・`fuda-image/`）とその試験は T6 の受け持ちで、T5 は触らない。

- **解き終えた画面と結果のページの距離**（5-c）: 「約 1,590」「約 2,020」は棚卸しの値からの見込み。T5-5b・T5-6 で測り直した値を T9 に渡す。

- **410 から置き換え先へ送るか**（1-b）: T5 の範囲の外。GA を載せたあとの数を材料に、PM が backlog に起票するかを決める。
- **目次が使われているか**（8-a〜8-c）: **決定（PM）**: 計測を入れる。T5-15 が、目次を開いたこと（`toc_open`）と、目次から章へ移ったこと（`toc_jump`）を GA に送るイベントを足す。どちらも `src/lib/analytics.ts` のいまの書き方（`sendGaEvent` を包む `track…` の関数・`content_type` と `content_id` を持つ形）に合わせ、`content_type: "blog"`・`content_id` は記事の slug（ページの共有の計測の `contentId` と同じ値）とし、`toc_jump` は移った先の章を `section_id`（見出しの `id`）と `section_level`（見出しの段の数。目次はどの深さの見出しも載せるので、いまの記事では 2〜4）で言う。出荷の日から数え始めるので、ADR009 の前後の読みでは新しいイベントとして扱う（PM が T10 の行に書き足す）。数は、E の目次を来訪者が使っているか（開いた回に対して章へ移った回）を読み、次にブログの目次の置き方を変えるときの材料にする。
- **回答中の画面の送り方**（5-a）: 帯を画面の上端に送るかどうかと、375×550・320×550（B-614 の条件）で入るかは T5a の設計が決める。0-3 の塊の高さ（最大 550）は、550 の画面では帯を上端から 8px に置いても 8px 足りない値で、T5a が比べる材料になる。
