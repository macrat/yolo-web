## Major

### Major-1: 指の操作の3つの約束を、エンジンの既定の処理とどう両立させるかが決まっていない

§6・t4-design・SKILL.md は、次の 3 つを同時に約束しています。

- ネイティブの `input type="range"` を残す（VoiceOver で値を動かすため）。
- 縦に払った指は、ページを送るだけで値を変えない。
- 動かさずに離したら、離した位置の値にする。

そのうえで「ネイティブのつまみの引き方に任せない」と書いています。しかし、ネイティブの `input` に指が当たる限り、どちらのエンジンでも既定の処理が先に動きます。

- **Chromium（Android の Chrome）**: 試作 A では、溝に触れた瞬間に値が 180 から 66 に変わった。そのまま縦に払っても、ページは送られ、値は 66 のまま残った。`pointerdown` で `preventDefault` しても（試作 C）、触れた瞬間に 66 になった。止めるには `touchstart` の `preventDefault` が要るが、それをするとページも送られなくなる。
- **WebKit（iPhone のすべてのブラウザ）**: `SliderThumbElement::handleTouchStart` は、つまみのまわり（16×32px を 12.5px ずつ広げた約 41×57px）に触れると、すぐに引き始めて `touchEvent.setDefaultHandled()` する。`handleTouchMove` は、指の向きにかかわらず、指の x 座標に値を合わせ続ける。つまり、つまみの近くから縦に払うと、ページは送られず、指の横のぶれだけ値が変わる。イロドリの 3 行は 320px で高さ 132px の帯で、そのうち 3 つのつまみのまわりが、この挙動の範囲になる。
- **既定の処理を止める素直な方法の代価**: `input` を指の当たり先から外す方法がある（試作 B。`pointer-events: none` にして、外側の箱が `touch-action: pan-y pinch-zoom` で指を受ける）。Chromium では 3 つの約束がすべて成り立った。押すだけなら離したときに 65、縦に払うとページが送られて値は 180 のまま、横に引くと付いて動いた。読み上げの木にも `slider "B wrapped": "180"` が残り、矢印キーでも動いた。ところが WebKit では、VoiceOver の指でなぞる探索が使う当たり判定が、`pointer-events: none` の要素を飛ばす。当たり判定の要求は `AccessibilityHitTest` で、`IgnoreCSSPointerEventsProperty` を持たない。`RenderElement::visibleToHitTesting` は、その印がない限り `usedPointerEvents() != None` を条件にする。そのため VoiceOver の利用者は、画面をなぞってスライダーを見つけられなくなる。左右に払って順に移る操作と、上下に払って値を動かす操作は残る。
- **確かめ方の穴**: 項目 6 の (g) と (m) は、Chromium のタッチのエミュレーションと読み上げの木で確かめる。上の WebKit の 2 つの挙動（つまみのまわりで縦に払うと値が変わる、なぞる探索で見つからない）は、どちらもこの確かめ方では出ない。そのため builder が素直に組むと、Chromium ではすべて通り、iPhone でだけ約束が破れたまま出荷されうる。

**来訪者が受けること**: iPhone でイロドリを遊ぶ人がスライダーの帯の上からページを送ろうとして、たまたまつまみの近くに触れると、ページは送られず、作っている色が黙って変わります。§6 がいちばん防ぎたかったことです。それを避けようと `pointer-events: none` にすると、画面をなぞって使う VoiceOver の利用者がスライダーを見つけられなくなります。

**直し方の向き**: 3 つの約束のどれをどのエンジンで優先するかを、planner が来訪者の比べで決め、t4-design に書く。SKILL.md の組み方の 1 行もそれに合わせる。

- 比べる案の例:
  - (1) 試作 B の組み方で、VoiceOver のなぞる探索で見つからない代価を受ける。なぞったときに外側の箱かラベルがスライダーの名前を言うなど、代価を小さくする手を添える。
  - (2) `input` を当たり先に残し、WebKit ではつまみのまわりの既定の引き方を受け入れる。§6 の「縦に払っても値を変えない」は、つまみのまわりを除いて約束する形に書き直す。
  - (3) ほかの組み方。
- どの案でも、指の受け方は `touch-action: pan-y pinch-zoom` にすることを守ることに書く。縦に送る判定をブラウザに任せ、`pointercancel` で「縦と分かった」を受ける。ピンチで拡大する操作も奪わない。
- 確かめに、Chromium で出ない挙動への備えを足す。例: `elementFromPoint` で当たり先を確かめる構造のテスト。選んだ案で iPhone に残る代価を、t4-design に記録する。

### Major-2: つまみそのものを押しても押した位置へ移るので、合わせた値が崩れる

§6 は「押せる範囲のどこを押しても、つまみはその位置へ移る」とし、指について「横に動かしたと分かってからは、つまみが指に付いて動く」と書いています。t4-design は「横と分かったら、その時点の指の位置へ移し」と書いています。つまみの上を押したときの例外がありません。

- 試作 B で、つまみの中心から 5.3px 右を押して離すと、値は 180 から 188 になった（溝 266px）。
- イロドリの 320px の 1行の組みでは、溝は約 93px（下の Minor-4）で、つまみの動く幅は約 77px になる。つまみの幅 16px の中のどこを押すかで、値が最大で ±8px ぶんずれる。色相で ±37、彩度と明度で ±10 にあたる。
- つまみを掴んで引き始めるときも、「横と分かった時点で指の位置へ移す」ので、掴んだ位置とつまみの中心のずれ（最大 8px）だけ、つまみが跳ぶ。
- ネイティブのスライダーは、つまみを掴んだときにずれを保って動かす。WebKit のつまみの引き方、Chromium のマウス、iOS の UISlider がそうである。

**来訪者が受けること**: − と ＋ で色相を 1 ずつ合わせたあと、少しだけ引こうとしてつまみに触れると、それだけで色相が数十ずれます。細かく合わせるための − と ＋ の仕事が、次の一押しで消えます。PC でも、マウスでつまみを押すだけで値が跳ぶと定めているので、ネイティブの振る舞いより悪くなります。

**直し方の向き**: §6 に「つまみの上を押したときは移らず、引けば指（マウス）の動いた分だけ動く」を足す。それ以外の所を押したときに移す定めは残す。t4-design の Major-1 の決めと項目 3、SKILL.md の 1 行、確かめの (f)(g) に、つまみの上を押すだけで値が変わらないことと、掴んで引くと跳ばないことを入れる。「つまみの上」をどこまでにするかは builder に任せてよい。例としては、指ではつまみの幅に左右数 px を足す。

## Minor

### Minor-1: 指の操作の端の場合が決まっていない

- **2本目の指**: 横に引いている最中にピンチが始まったとき（`pointercancel`）、引いて変えた値を残すのか、戻すのかが無い。どちらでもよいが、決めないとテストに書けない。
- **縦から横へ曲がる指**: 試作 B では、縦と判定したあとに横へ曲げても値は変わらなかった（`mode v|cancel v`）。これが意図どおりなら、§6 か t4-design に「一度縦と分かった指は、離すまでページを送るだけ」と一言書く。
- **判定までの跳び**: 目安の 10px 動くまでは、つまみが止まっている。判定したところで、指の位置へ 10px 跳ぶ。93px の溝では色相で約 47 にあたる。判定の距離を builder に任せること自体はよい（問い 6 の 2 つ目）。ただし、その距離は「縦に送るかどうかをブラウザが決めるまで」と揃えるのが筋で、10px を固定の目安にする理由は無い。「小さいほど跳びが小さい」ことを、決めるときの材料として書く。

### Minor-2: − と ＋ の細部

- **速く2度押すと拡大しうる**: iPhone の Safari は、2 度の素早い押しを拡大の操作に取りうる。ボタンの上には `touch-action: manipulation` を掛ける（WebKit のブログ「More Responsive Tapping on iOS」）。「＋を続けて押して、どれも1刻みになる」を確かめ (i) に足す。
- **フォーカスを奪う**: Chromium は、`tabindex="-1"` のボタンでもマウスで押すとフォーカスを移す。そのあと矢印のキーを押しても値は動かない。端で無効になった瞬間には、フォーカスが `body` に落ちる。押してもフォーカスをいまの場所から動かさないことを守ることに書く。
- **読み上げに新しい値が届かない**: VoiceOver で「色相を1減らす」を押しても、読み上げられるのはボタンの名前だけで、変わった値は聞こえない。ボタンを読み上げの木に残す以上、押したあとに新しい値を1度言う決めが要る。
- **刻みが 1 でないスライダー**: 画像のリサイズの品質は 5 刻みで、単位も付く。名前の例（「色相を1減らす」）に倣うと「品質を1減らす」と誤って名付けうる。名前は刻みと単位を含む（「品質を5%下げる」など）と書く。
- **形の大きさ**: − と ＋ の線の長さが決まっていない。§6 のほかの形は大きさを持つ（円と四角は 20px、つまみは 16×32px）。

Tab の順から外すこと自体は正しいと判断しました（問い 2 の 4 つ目）。キーボードでは矢印が同じ働きをします（WCAG 2.1.1 を満たす）。読み上げの木に残るので、VoiceOver の左右の払いと、音声での操作（名前で押す）で届きます。3 行で Tab の止まりが 9 になるのを避ける利もあります。無効の − と、隣に字で出る端の値の組み合わせも、「理由を文字で添える」を満たすと判断しました（問い 6 の 1 つ目）。端の値が見え、それより下へ行けないことが字で分かるからです。

### Minor-5: builder の項目の補い

- **(e)**: 色相の溝の確かめが、彩度・明度を決めていない。Major-3 の直しを確かめるには、彩度 20・明度 25 のような低い値で、色相の溝の各点がその彩度・明度の色になることを見る必要がある。彩度と明度の溝の、つまみの中心の色の一致も見る。
- **(g)**: つまみのまわりから縦に払う、縦から横へ曲げる、2本目の指、つまみの上を押すだけの 4 つを足す（Major-1・Major-2・Minor-1）。
- **項目 3 の「入力の `input` の出来事を起こし、使う側の `onChange` が動くようにする」**: 書き方を決めすぎている（AP-P20）。React は `value` を代入しただけでは `onChange` を呼ばない（値の追跡を持つため）。この書き方どおりに組むと、落とし穴に当たる。守ることは「使う側に新しい値が届く」で足りる。
- **組みの決め方**: 最初の描画から正しい組みで描けることは確かめた。コンテナクエリで `calc(2em + 8px + 16px + 88px + 3ch + 5rem)` の条件を書いた CSS だけの試作を、JavaScript を止め、Web フォントも読まない状態で描いた。320px の既定では 1行の組み（溝 93px・帯 132px）、ルート 18px と 32px では2行の組みで描けた。builder に任せてよい。ただし、閾値の近くでは、Web フォントの差し替えで `ch` の幅が変わり、組みが替わりうる。その場合を確かめに入れる。
- **SKILL.md が、まだ無い `src/components/Slider` を名指ししていること**: `CopyButton` と同じく、部品の名と置き場所を先に決める書き方として成り立つ。ただし、builder がその名や置き場所を変えると SKILL.md が嘘になる。項目 3 に「名とパスは SKILL.md のとおりにする。変えるなら SKILL.md も同じコミットで直す」と書く。
- **イロドリの決定のボタン（663/667）と道具の 2 つの AP-I14 の確かめ**: (k) と項目 7 に入っていて、足りている。

## 問いへの答え

1. **1巡目の指摘**: 上の表のとおり、10 件が正しく直った。Major-1 は、部品が必ず指を受けるところまでは直った。その受け方とエンジンの既定の処理とのぶつかりが残る（このレビューの Major-1）。
2. **− と ＋ への転換**
   - 点数の数は再計算で一致した。
   - 溝が約 188px から約 93〜97px に縮む代価と比べても、よい選択と判断した。理由は 4 つ。溝の色で向きは読める。スマートフォンで見えている違いを詰める手段が − と ＋ のほかに無い。1行の組みを保つので、決定のボタンが最初の画面に残る。2行の組みにすると帯が 132px から 296px に伸び、ボタンが画面から出る。
   - §6 の語彙には合っている。「その場で状態を変える」ので形で示し、太い線で描く。下線を持たない。押せる範囲は 44px 四方で、hover の線と無効の枠はほかのコントロールと同じである。
   - Tab の順から外して名前を付けることも正しい。細部は Minor-2。
3. **指の操作**: 押すだけ・横・縦の 3 つの分け方は、Chromium の試作 B で意図どおりに動いた。ただし、ネイティブの `input` を残して VoiceOver を保つこととの両立は決まっていない（Major-1）。つまみの上を押したときの扱い（Major-2）と、2本目の指・縦から横への曲がり（Minor-1）も抜けている。
4. **2行の組み**: 閾値は妥当。CSS だけで最初の描画から決められ、CLS は出ない（Minor-4・Minor-5）。
5. **グラデーション**: 締まった。抜け道は無い。
6. **planner の問い**: 無効の端のボタンと端の値の組み合わせは、理由を字で言う形として認める。判定の距離を builder に任せることも認める。ただし、ブラウザの判定と揃える条件を添える（Minor-1）。
7. **一貫性**: DESIGN.md は、§5 のラベルの文（Minor-3）のほかは、1 つの今の状態として読める。SKILL.md は DESIGN.md と揃っている。ただし、Major-1 の決めに合わせて組み方の 1 行を直す必要がある。
8. **builder の項目**: 大筋は揃っていて、確かめられる形になっている。Major-1・Major-2 と Minor-5 の補いが要る。
