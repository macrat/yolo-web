## 結論

**改善指示**（Blocker 0・Major 3・Minor 14）

設計の骨格はよい。とくに次の点は来訪者の役に立つ。

- 行の部品を1つにして、読み上げの名前を名前だけにする（B-574）。
- `/blog` の一覧を HTML に入れる。
- 1,110件を1ページに出す面をやめる。
- 狭い画面で絞り込みを畳む。

技術の前提も、下で確かめたとおり Next.js 16.3 で成り立つ。

直すべき点は次の3つが中心である。

- 「`DESIGN.md` を変えない」という主張が、いくつかの点で成り立っていない。
- 辞典のトップで、部首・画数・カテゴリの入口が一覧の約1万px下に沈む。
- ブログの一覧から、タグで辿る道が消える。

## 確かめたこと

### Next.js 16.3 で成り立つか

入っている版は `next` 16.3.0 で、同梱の文書を読んだ。

- **`Suspense` の fallback を静的な HTML に入れること**: 成り立つ。`use-search-params.md`「Prerendering」によると、`useSearchParams` を読むと、いちばん近い `Suspense` までの木がクライアントで描かれ、fallback が最初の HTML に入る。そのうえで「When the value is available during React hydration the fallback will be replaced」とある。つまり fallback の DOM は、ハイドレーションのときに子の DOM へ**置き換わる**（Minor-7 に続く）。
- **`pushState`・`replaceState` と `useSearchParams` の同期**: 成り立つ。`04-linking-and-navigating.md`「Native History API」に「`pushState` and `replaceState` calls integrate into the Next.js Router, allowing you to sync with `usePathname` and `useSearchParams`」とあり、並べ替えを `pushState` で行う例も載っている。
- **`page` のパスの区切りの優先**: 静的な区切りは、同じ階層の動的な区切り（`[char]`・`[yoji]`・`[slug]`）より優先される。`src/app/blog/page/[page]` と `src/app/blog/[slug]` は、すでにこの形で並んでいる。データも確かめた。伝統色の slug・四字熟語・ユーモア辞典の slug に `page` は無い。漢字はどれも1字である。
- **静的生成の数**: 下の Minor-2 のとおり、データからいま正確に数えられる。

## Major

### Major-1 「`DESIGN.md` を変えない」（9章）が成り立たない。§7 から外れる決定を、`DESIGN.md` を直す手順を経ずに入れている

外れる決定そのものは、多くが来訪者にとって妥当である。問題は、それを「§7 を満たす」と書いて、options.md「`DESIGN.md` を変えるとき」と frontend-design スキルの「`DESIGN.md` に無いコンポーネントは先に `DESIGN.md` へ書く」を通していないことである。

このまま実装すると、次の2つが起きる。

- T8 の機械の検査と T11 の全体のレビューで、`DESIGN.md` と実装が食い違う。
- 次の一覧を作る人は、`DESIGN.md` を読んでもこの設計の規則を知れない。

外れている点は次のとおり。

1. **§7 の備えが要る条件**
   - §7 は「1画面に収まらなくなった時点で」備えを求める。設計の 2-2 は、これを「10件を超えるとき」に置き換えている。
   - inventory 1-2 では、5件の `japanese-culture` でも 375 と 1280 の両方で1画面に収まらない。
   - 2-2 の理由の文も食い違っている。「10件までは…1回のスクロールで見渡せ」とある一方で、同じ節で「375×667 に入る行は…3〜5件」と書いている。
   - 3-2 は、短い一覧（最多24件）を備えの外に置く。理由は「§7 の備えは1画面に収まらなくなったときのもの…これらは多くても24件」である。しかし24件は 375px で 1,447px ある（inventory 1-2）。
2. **行が種別を持たない一覧**
   - §7 は「行は名前・説明・種別を持つ」と定める。
   - 種別を持たない一覧: ユーモア辞典・ブログの分類のページ・学年のページ・四字熟語と伝統色のカテゴリのページ・連載・他のタイプ・同じカテゴリの伝統色。
   - 説明を持たない一覧: 伝統色。
   - 漢字の説明は、「何であるかを一文で言う」ものでなく音訓になる。
3. **種別で絞り込めない一覧**
   - 1画面に収まらないのに、種別の絞り込みを持たない一覧がある。学年7（1,110）・カテゴリのページ・ユーモア辞典（30）である。
4. **`LinkIndex`**
   - 同じ部首の漢字（117件）は項目の一覧で、§7 のとおりなら1行1項目のボックスになる。
   - 9章は `LinkIndex` を「§6 のリンクを §5 の規則で並べたもの」とする。しかし実際には、§7 に無い「一覧の形」を1つ足している。

**求めること**: 上の各点について、次のどちらかを選ぶ。

- (a) 設計を §7 に合わせる。
- (b) §7 が来訪者にとって誤りである（または足りない）と示して、`DESIGN.md` §7 を書き直す。この場合は単独でレビューを受ける。

(b) の例を挙げる。

- 「種別は、一覧の中で値が分かれるときに持つ」
- 「名前だけで何か分かる短い語の索引は、折り返して並べる」
- 「絞り込みと並び順を持つのは、ページの主な中身である一覧」

9章は、選んだ結果に合わせて書き直す。

### Major-2 辞典のトップで、部首・画数・カテゴリから探す入口が、一覧の約1万px下に沈む

3-1 では、漢字のトップの「部首から探す」（198）と「画数から探す」（24）を一覧の下の `LinkIndex` に移す。1ページは100行で、設計の見積もりでは 375px でおよそ1万px になる。

**失われるもの**

- 部首と画数は、字を知らない来訪者が漢字辞典を引くときの主な入口である。いまは 375px の最初の画面のすぐ下（y=777 から）にある。変更後は、100行を送り切った先にしか無い。
- 設計は「部首の198リンクが一覧の前に 1,452px を取る」という押し出しの害だけを量り、入口が見つからなくなる害を量っていない。
- 四字熟語と伝統色のトップでは、いまのカテゴリ・色みの一覧が消える。代わりに何で分類のページへ行けるのかが書かれていない。3-1 で下に `LinkIndex` を置くと書いたのは、漢字の部首と画数、ブログの分類のページの「ほかの分類」だけである。
- 分類のページは、検索から着く面でもある（`/dictionary/yoji/category/society` は28日で12 PV、全体の15位）。

**求めること**: 入口を、一覧を押し出さず、しかも見つかる位置に置く。案を比べて決める（AP-P17）。

- 一覧の上に、閉じたアコーディオン「部首・画数から探す」（1行 44px）を置く。
- `ListControls` の中に、「分類のページへ」の組を置く。
- 件数の行の近くに、索引へ飛ぶリンクを置く。

四字熟語と伝統色のトップで分類のページへの道をどう残すかも、明記する。

### Major-3 ブログの一覧から、タグで辿る道が消える。GA を確かめずに決めている

3-1 では、行の中のタグのリンクと `/blog` の「タグで探す」の両方を外す。タグのページ（29）への道は、記事の中の `TagList` だけになる。

理由の「行の中にリンクを重ねると押せる範囲が入れ子になる」は、§7 の要求ではない。§7 は「行の中に別のリンクを置くときは、それだけを独立に押せる」と、行の中のリンクを認めている。一覧の上から外すことには理由がある（375px で y=571〜763 を占め、一覧を押し出す）。しかし、下にも置かない理由は書かれていない。

CLAUDE.md は「来訪者の体験や流入に効く判断の前に GA を確かめる」と定めている。この設計が挙げる GA の数値は、検索の表示回数の割合だけである。次の数値を確かめていない。

- タグのページ・分類のページ・`/blog` の PV
- `/blog` からタグのページへ移った数

同じことは、次の決定にも言える。

- ツールと遊びの棚をやめること
- 「← ユーモア辞典一覧へ」を外すこと

**求めること**

- `/blog` の一覧の下に、タグの `LinkIndex`（件数つき）を置く。分類のページの「ほかの分類」と同じ形になる。置かないなら、GA の数値で理由を示す。
- 外すもの・変えるものの判断に、確かめた GA の数値を書き添える。いまの一覧のページの PV は小さい（`/play` 20・`/tools` 18・`/blog` 15）。この数値自体が、変更の害が小さいという根拠にもなりうる。

## Minor

### Minor-1 範囲外のページの扱いが、事実とも検索の扱いとも合わない（2-7）

- 「いまの `/tools/page/[page]` と同じ扱い」は事実と違う。いまの `route.ts` は `dynamicParams = false` で、`generateStaticParams` は `page: "2"` だけを返す（36÷24）。308 で送るのは `/tools/page/2` だけで、`/tools/page/9` は 404 になる。`/blog/page/[page]` も `dynamicParams = false` で、範囲外は 404 である。
- 任意の番号（`/blog/page/999`・`/page/abc`・`/page/0`）を1ページ目へ 308 で送ると、Google はソフト 404 として扱う。308 で送るのは、**かつて存在したページ**（ブログの3〜8ページ目、分類とタグの旧2ページ目から）だけにして、ほかは 404 のままにするほうが正確である。
- 新しい経路の `/page/1`（`/dictionary/kanji/page/1` など）を basePath へ送るかどうかが書かれていない。いまは `next.config.ts` の redirects で扱っている。

### Minor-2 いま数えられる値を「見積もり」「数件」にしている。部首の数は誤っている（3-1・4-3）

- 部首で100字を超えるのは「水」118 と「人」102 の2つである。3-1 の「1〜2（「水」が2）」と 4-3 の「部首 … 1」は、「水・人」「2」に直す。
- 画数の2ページ目からは、10画を超える画数ごとに数えて 14 である（6画 114・7画 153・8〜13画・14画 116・15画 120）。「48以下（T3-7 で数えて記録する）」でなく、14 と書ける。
- 四字熟語のカテゴリの2ページ目からは 1（life 58）。タグの2ページ目からも、データから数えられる。
- 行の高さ（「約200px」「約100px」）と「およそ1万px」は、実測でなく見積もりである。見積もりと明記するか、inventory の方法で測る。

### Minor-3 ツールの種別の語が定まっていない。種別の中の並びに意味が無い

- 3-1 の表は「分類（文章・計算・生成・パスワード・ハッシュ・開発・エンコード）」と7語を並べる一方で、「すべて＋5」としている。データの分類は5つ（text・generator・security・developer・encoding）である。いまの棚の名前は「計算・生成の道具」「パスワードとハッシュの道具」で、そのままでは「一語」（§7）にならない。5つの種別の語を決めて書く。
- 既定の「種別順」では、同じ種別の中がデータの順（英字の slug 順）になる。来訪者には意味の無い順である。同じ種別の中の順（新しい順など）を決める。なお、36本のうち30本は公開日が 2026-02-13〜14 で、新しい順の多くは同じ日付に並ぶ。

### Minor-4 並び順に使う値が見えていない一覧がある（2-6 の自分の規則に反する）

- 伝統色のカテゴリのページでは、種別が「—」なのに、既定が「色み順」である（同じ色みの中の色相の順）。色相は行に見えない。「明るい順」の明度も数値では見えない（見えるのは色見本だけ）。色見本で足りるとするなら、そう書く。
- 漢字の「読みの五十音順」は、どの読みで並べるか（先頭の音読みか、訓読みか）が決まっていない。
- ユーモア辞典の「五十音の逆順」は、「並び順を2つ以上」を満たすためだけの順に見える。来訪者に得が無いなら、Major-1 の (b) の中で、並び順が1つしかない一覧の扱いとして決める。

### Minor-5 漢字の音訓の表示と探し方

- `kanji-data.json` の訓読みには、重複がある字が 119 字ある（例「生」: うまれる×2・うまれ×2・なま×2）。そのまま行の説明にすると「なま・なま」と出て、壊れて見える。表示の前に重複を除く。
- 欄のラベル「字・読み・意味で探す」の「意味」は、データでは英語である。「さかな」のような日本語の意味で探す来訪者は、意味では当たらない。「water」で当たった行には、当たった理由が見えない。ラベルを実態に合わせる（例「字・読み・英語の意味で探す」）か、英語を探す対象から外す。

### Minor-6 `/page/n` のパスで既定でない状態に入ったときの食い違い

`/blog/page/2` で並び順を「古い順」にすると、見出しは「（2ページ目）」、canonical は `/blog/page/2` のままになる。一方で中身は、古い順の1ページ目になる。パスが言うページと中身が食い違うので、どちらかを選んで書く。

- 既定でない状態に入るときに、パスを basePath に置き換える。
- 食い違いを受け入れる理由を書く。

### Minor-7 fallback が置き換わることの影響と、道具での扱い

- fallback の DOM はハイドレーションで置き換わる。そのため、読み込みの途中で欄に打った字や、開いた操作の枠が消えうる。受け入れるのか、防ぐのかを書く。
- T3-9 の3つの道具は `useSearchParams` を使うことになるが、2-8 の fallback の組み方が掛かるかが書かれていない。yoji-search は 90日で 40 PV の上位の面である。いまの HTML にある結果を失わないようにする。
- yoji-search の難易度と出典はクエリに持たない（7章は `q`・`kind`・`sort`・`page` だけ）。詳細から戻ると、この2つが消える。

### Minor-8 `ItemList` の型が、使い方の説明と合わない

- 1-1 には「結果のボックスや `Panel` の中では、ボックスを持たない形で描く」とあるが、`ItemListProps` にそれを選ぶ手段が無い。
- `CrossCategoryBanner`・`NextGameBanner` の「今日は遊んだ」は、種別（何の仲間か）でなく補助情報である。

### Minor-9 完了の条件が 375×667 だけを見ている

- §7 の「一覧を画面の外へ押し出さない」は、どの幅にも掛かる。45rem 以上では操作の枠がいつも開くので、1280×800 でも最初の行が画面に入ることを、T3-5〜T3-9 の条件に足す。漢字のトップでは、学年8つ・並び順3つ・名前の欄が並ぶ。
- 10件以下の一覧のページ（site-updates 10 など）で、件数の行を出すかどうかが書かれていない（§7「全体の件数は…見える」）。

### Minor-10 T3-1 に、後で作り直す箇所の置き換えが入っている。並行の条件も正確でない

- T3-1 は、`/tools`・`/play`・辞典のトップ・`DictionarySearch` の結果を `ItemList` に替える。しかしこれらは、T3-6〜T3-8 で `BrowsableList` に作り直され、`DictionarySearch` は消える。2度手間になる。T3-1 は残る呼び出し（トップ・`/dictionary`・`/about`・404・`RelatedArticles`）に絞る。「`Shinagaki`・`DictionaryEntryList` の参照0件」の条件は、T3-8 の完了のあとに置く。
- 「T3-5〜T3-9 は触るファイルが分かれている」は正確でない。次の2つが重なる。
  - `next.config.ts` の redirects は、T3-5・T3-7・T3-8 で触る。
  - 「遊ぶ」から「遊び」へのパンくずの変更（T3-6）は、`QuizPlayPageLayout`・`GameLayout` など、T3-2b と近い面に掛かる。

  共有するファイルを誰がいつ触るかを決める。

### Minor-11 パスでページを分ける理由の一部が事実と合わない。URL の組み方の比較が無い

- 2-7 の「辞典の全項目が一覧の HTML から辿れることにもなり」は、いまでも成り立っている。学年のページが 2,136字、四字熟語のカテゴリのページが 400語、伝統色の色みのページが 250色を、すべて HTML の行で出している。パスでページを分ける本当の理由は、JS を待たずに読めること・リンクとして開けること・共有と戻るで同じページが出ることである。そう書き直す。
- パス（既定の状態）とクエリ（既定でない状態）の二本立ては、この設計でいちばん複雑な部分である。ほかの案を並べて比べていない（AP-P17）。比べる相手は、クエリだけの案や、既定でない状態でパスを basePath に寄せる案（Minor-6）など。短い比較の表で足りる。

### Minor-12 アコーディオンの `summary` に付ける `aria-labelledby` が、どの環境で効くかを確かめる

`summary` には、対応する ARIA のロールが無い。Chromium 以外（Safari と VoiceOver）で `aria-labelledby` が名前に使われるかは、確かでない。T3-9 の完了の条件に、Safari での確かめを足す。効かないなら、別の組み方を選ぶ。

### Minor-13 部品の型の全文は、builder を縛らない書き方にする（AP-WF03・AP-P20）

1-1・2-1 の TypeScript のインターフェースは、決定（行が何を持つか、操作が何を持つか）を伝える見本としては役に立つ。しかし builder への指示として全文を渡すと、実装の判断を先に固めてしまう。「形の見本で、名前と細部は実装で決める」と添えるか、持つものの箇条書きに絞る。

### Minor-14 そのほか

- **読了時間を外すこと（3-1）**: 「一覧で比べて選ぶのに要るのは分類と公開日」は、裏付けの無い断定である。読了時間は、時間の限られた来訪者が記事を選ぶ材料になる。補助情報に1つ足しても、行を目で追う速さはほとんど落ちない。残すか、外す根拠を示す。
- **件数の行に `role="status"` を付けること（2-4）**: ページを送るたびにフォーカスを移すことと、ライブリージョンの読み上げが二重にならないかを、実装のレビューで確かめるよう書き添える。
- **T3-11 のビルドの時間の記録（4-3）**: 増えるのは実数で約60ページで、来訪者には効かない。incident-2 の教訓（目的に釣り合わない計測を足さない）に照らし、ビルドの時間の記録は外してよい。静的生成の数の記録で足りる。
- **1ページ約1万px のとき、ページ送りが下端にしか無い（2-7・3-1）**: 3ページ目へ行きたい来訪者は、1万px を送り切る必要がある。件数の行の近くにもページ送りを置くかを決めて書く。
