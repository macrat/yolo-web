### M-2. 「仮名と約物が全角なので、差し替えても字幅が変わらない」は、この機械の代わりの書体でしか確かめていない。全角でない字が残る（§12）

**どこが**: 「差し替えのずれ」の「事実」の1点目、置き換える §3 の文「端末のゴシックから差し替わっても行の折り返しが変わらない（§12）」、スキルへの提案2。

**なぜ**:

- 16ページで集めた字（1,102字）のうち、BIZ UDGothic の送り幅が全角でない字は5つあった（`adv3.cjs`）: `©`・`↗`・`▶`・`−`（U+2212）・`—`（U+2014）。すべて 1024/2048。
- サイト全体では、Latin-1 の文字（é など。§3 で和文の書体が組む）などが加わる見込み。
- 差し替えの前は、代わりの書体で描く。
  - iOS・macOS のヒラギノ、Windows の游ゴシック、Android の Noto Sans CJK JP では、U+2014 は 1em（全角）なのが通例です。▶ も多くは全角。
  - この機械の代わりの書体（WenQuanYi・IPAGothic）では、たまたま変わらなかったか、その字を含む行で折り返しが変わらなかったので、「7ページで0」になったと考えられる。
- 「——」を含む段落は、実機では差し替えで折り返しが変わりうる。文書は、字幅そのものは機械に依らないと書いているが、この部分はそうではない。

**どう直すか**:

- ビルドの時に、集めた字のうち本文の書体で全角でない字を列挙する。M-1 の処置（字形を当て直す）で全角に揃えるか、揃えない字を明記する。
- §3 とスキルの文は「全角でない字は切り出しのときに揃える」と条件つきにする。
- T9 の実機の確認で、「——」「▶」を含む行を必ず見る。

### M-3. ページの書体の変数を `:root` に書いているので、「前のページの `<style>` が DOM から消える」ことに依存している。Next.js 16 の `cacheComponents` を有効にすると B-1 に戻る（問い4の「将来の版で壊れやすくないか」）

**どこが**: 試作の `src/components/PageFonts.tsx`（`:root{--font-mincho:…;--font-gothic:…}`）、結論の1「ページを離れると消える」。

**なぜ**:

- Next.js 16.3.0 同梱の `cacheComponents.md`「Navigation with Activity」は次のように書いている。
  - 「Rather than unmounting the previous route when you navigate away, Next.js sets the Activity mode to "hidden"」
  - 「Next.js uses heuristics to keep a few recently visited routes "hidden"」
- 隠れた経路の `<style>` は DOM に残って効き続ける（`display:none` は `<style>` の効果を止めない）。そのため、`:root` の規則が複数並び、DOM の順で後にあるものが勝つ。前のページの家族名がそのまま使われ、字ごとの混ざり（B-1）が起きる。
- 今の `next.config.ts` は `cacheComponents` を使っていない。しかし `cacheComponents` は Next.js 16 の中心の機能で、将来有効にされうる。そのとき壊れても、文書にもコードにもその前提が書かれていない。

**どう直すか**:

- 変数を当てる先を、ページ自身が描く要素にする。例: ページの外枠に `data-pf="pf3062…"` を付け、`[data-pf="…"]{--font-…}` とする。
- こうすれば、隠れたページの `<style>` が残っても、今のページには効かない。家族名はページ固有なので `@font-face` が残っても害は無い。
- 遷移の試験に「戻る・進む」を足す。

- **m-3. 層を持つページの `<style>` の大きさ。**
  - プレイ面の HTML は gzip で 36.4 → 45.7KiB（+9.3KiB）。`unicode-range` を字ごとに `U+XXXX` で並べていて、HTML と RSC の二重に入るためである。
  - 「1ページあたり gzip で約 0.3KB」は層の無いページの値なので、そう限定して書く。
  - 連続する範囲にまとめて小さくする（`U+3042-3093` など）。診断のページは一覧やトップから先読みされるので、先読みの分も見積もる。
- **m-4.** 「見出しに palt を掛けない」を、「見出しの書体を当てるすべての要素（属性で宣言した要素を含む）」にする。試作は h1〜h6 だけを戻している。今のコードでは `Tsutsumi`・`Shinagaki`・`In` がクラスで `palt` を掛けている。
- **m-5.** 「書体の役割はタグと属性だけで決まる」の守り方。
  - CI の Chromium で確かめるのは代表のページだけで、外れたページは見逃す。
  - コード全体に掛かる静的な検査（stylelint で、`font-family`・`font-weight` を許した選択子にしか書けない規則）を条件に足す。
- **m-6.** 自己点検を、2回目のビルドの出力にも掛ける。「2回目で変わるのは `<style>` と preload だけ」は、ビルドの時刻や乱数で中身が変わるページでは保証されない。あわせて、すべての HTML にそのページの `<style>` があること（部品を入れ忘れたページが無いこと）を確かめる。
- **m-7.** 遅い回線では、遷移のたびに `main` の本文全体が端末のゴシックから UDGothic に替わって見える（字の位置は動かない）。変更前は本文が端末の書体のままで、この切り替わりは無かった。遷移の代償として書き、T9 の目視の観点に入れる。
- **m-8.** `main` の中で、遷移しても残る部分（入れ子のレイアウト）の字は、ページの家族で描かれるので、遷移のたびに切り替わる。今は `kanji-kanaru/layout.tsx` だけだが、T2〜T7 で入れ子のレイアウトを作るときの条件として書く（上端・下端と同じ共通の家族にするなど）。

## 3. 問いへの答え（要約）

- **2. 採った形は来訪者にとって正しいか**: 配り方（ページ固有の家族名、ページが描く `<style>`、上端・下端は共通、静的なファイル）は正しいと考えます。数字もすべて確かです。遷移1回あたりの増分（平均 +52KiB）は、着地で減る量とセッションあたり 1.29 PV から見て、許せる代償です。ただし、字の集め方（B-1）と `:root` の範囲（M-3）を直す必要があります。
- **3. §3 の変更**:
  - 「UDPGothic は §12 と両立しない」という示し方は、§12 が「どのページでも必ず成り立つこと」なので、来訪者にとっての誤りを示すものとして成り立ちます。
  - 入力由来の和文を端末のゴシックで組む書き加えは、手順に沿っています。ただし、範囲は B-1 のとおり絞るべきです。
  - 替える先の UDGothic の見た目の比較は、今やるべきです（M-1）。
  - 見出しに `palt` を掛けないのは妥当です（Zen Antique に `palt` が無いことを確かめた。m-4 の範囲だけ直す）。
  - 本文の `text-spacing-trim: space-all` は、§12 の側では筋が通っています。Chrome は `halt`／`chws` の無いフォントでは詰めない。しかし §4 と食い違います（M-1）。
- **4. 生の HTML の preload**:
  - 仕組みとして正しく働く。`pre.mjs` で見ると、フォントは約40ms に parser の起点で High の優先度で要求された。辞典の詳細で先読みされた RSC 37件のあいだにフォントの要求は0だった。
  - React は `dangerouslySetInnerHTML` の中を見ないので、`:HL` は出ない。これは React の安定した約束事です。
  - 壊れやすさは、preload ではなく `:root` の範囲にある（M-3）。
  - HTML の妥当性は m-2 のとおり。
- **5. ビルドの経路**:
  - 2回のビルド、キャッシュ、失敗したらビルドを失敗させること、Basic で約16分の見積もりは成り立ちます。
  - 「役割をタグと属性で決める」という T1 への条件は妥当です。ただし、守り方は静的な検査にする（m-5）。
  - 字の集め方には、操作と日付で現れる字が欠けている（B-1）。
- **6. ライセンス**:
  - OFL.txt の冒頭3件は、2026-09-24 に取得し直して一致した。FAQ の 1.1.1・1.10・2.5・2.6・5.3 の引用も一致した。1.1 はロゴを作る用途を明示している。
  - 派生の name テーブルと STAT が無いことは、ファイルで確かめた。
  - ロゴの SVG を OFL FAQ 1.1.1 で扱うことは正しい。
