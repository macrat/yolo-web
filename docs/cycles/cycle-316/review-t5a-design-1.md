## 指摘

### 1. cycle-301 が「送り」の案を退けた理由に答えていない（AP-P12）

cycle-301 の design.md 案2（「回答フェーズに入った時点でスクロール位置を設問へ移す」）は、次の3点を理由に退けられている。

- `scrollY>0` の状態は、スクロールの復元・スクロールアンカリング・iOS のツールバーの伸び縮み・戻る操作で崩れ、崩れると元の欠陥（4択が見えない）に静かに戻る。
- 上へ一度送ると、答えるのに使わない頭が現れる。
- 送ったあとの座標で測ると、合格に見える。

案1 は同じ方向の手当てである。それなのに t5a-design.md は、この退け方に触れていない。案1 には違いがある。問ごとに入るかを見直して送り直すので、崩れても次の問で戻る。「はじめる」を `scrollY=0` から押して測る（6章）。5-a で頭を消さないと決めている。こうした違いを3章に書き、「今回は何が違うか」を示すこと。4-4 の知識クイズの送りも、cycle-301 の (ii) と同じ危険を持つ。cycle-301 は「正誤の添えが画面から出ていかないこと」をその危険とした。案1 がそれをどう満たすかも同じ所で言うこと。

### 2. 帯が画面の上の外にあるときの送りが決まっていない

4-3 と §8 の文は、「帯を上端から 8px に置く送り」と「下端を下端から 8px 上に入れる送り」の**少ないほう**で送る、と決めている。`revealResult` と同じ決め方である。しかしこの決め方は、見せるものが画面の下にあることを前提にしている。

知識クイズで答えると、4-4 の送りで帯と見出しは画面の上の外に出てよい。そのあと「次へ」を押すと、次の問の帯は上の外にある。例として、帯の上端が −60、まとまりの高さが 400 のとき（画面は 550）を考える。帯を上端へ置く量は −68、下端を合わせる量は 340−542 = −202 である。`Math.min` は −202 を選ぶ。まとまりは画面の下端に寄せられ、上に前の頭の残りが並ぶ。来訪者が上へ送ったあとに答えた場合も同じである。

§8 の文と T5a-3 の関数に、次を書くこと。上に外れているときは帯を上端から 8px に置く。つまり、どちらの向きでも、まとまりを丸ごと入れるいちばん小さい送りにする。単体テストに上向きの場合を入れる。

### 3. 着地の選び方（D4）の文に誤りと抜けがある

- **(a) 逆に書かれている**: 4-7 の末尾に「どの送りを選んでも押せるものが来ないときは、決まりの送りのまま」とある。正しくは「来る**とき**は」である。完了の条件（「測りで0件」）の意味もこの一文で決まるので、直すこと。
- **(b) 「見せるものが画面に入る範囲」が決まらない**: 結果のボックスは多くの本で画面より高い。そのため、ボックスが「画面に入る」送りの範囲は空になる。どこまでずらしてよいかを、ボックスの上端の位置で決めること（例: 画面の上端から 8px 〜 画面の高さの何割か）。ページが送れる範囲（0 〜 `scrollHeight − innerHeight`）で打ち切ることも書くこと。
- **(c) 8px の広げ幅に出自が無い**: 「指のずれとして上下左右に 8px 広げて見る」は、実測でも算術でもなく、推論の印も無い。冒頭の決まり（数の出自を書く）に反する。参考として、Android は2打の距離が 100dp 以内なら二度押しとみなす（`ViewConfiguration` の `DOUBLE_TAP_SLOP = 100`）。2打目のずれは 8px を越えうる。推論と書き、T5a-2 の測りか T9 の実機で確かめるか、出典のある値にすること。
- **(d) 「区画の外に落ちない」は、送りが動く操作では成り立たない**: 4-7 は「はじめる・問→問: 区画を低くしないので、区画の外に落ちない」とする。しかし「はじめる」のあとは、まとまりを入れるために送るので、押した点の下に来るものが変わる。表の値で計算すると、320×550 の science-thinking（はじめる 533・帯 368・高さ約 415）では 241 送る。すると「はじめる」の点は1問目の選択肢の上に来る。japanese-culture・yoji-personality・traditional-color・character-personality でも同じく、1問目の選択肢に落ちる見込みである（算術）。本や位置によっては区画の外（下の罫線の先の FAQ）に落ちうる。知識クイズの「次へ」のあとも、上向きに送るので同じことが起きる。

  「はじめる」と「次へ」にも D4 を当て、少なくとも `a[href]`・`summary`・区画の外のボタンを避けること。次の問の選択肢も避けられる送りがあるなら選ぶか、選ばないならその理由を書くこと。D4 は時間の窓ではない。押せる形のまま黙って捨てることもしない。だから options.md の制約には触れない。まだ読んでいない問に答えが入るのを、誰にも手間を足さずに減らせる。

- **(e) `DESIGN.md` の文と 4-7 が食い違う**: 5章の §8 の最後の箇条は「押した点に、別のページへ移るもの・開閉するもの・ボタンが来ない量」と書く。次の問の選択肢もボタンなので、この文では避ける対象に入る。4-7 は選択肢を避けない。(d) で決めた範囲に、どちらかをそろえること。
- **(f) 知識の記録と食い違う**: `input-events-and-guards.md` §4 は、retry の2打目が「はじめる」を叩くことを「意図しないプレイ開始」と書いている。4-7 は「意図に沿うので避けない」とする。どちらを取るか、理由とともに書き、採るほうに記録を合わせること。
- **(g) あとから来る組み替え**: 解き終えた画面では、`ResultExtraLoader` が `next/dynamic` で読みものを遅れて差し込む。Web フォントの読み込みでも組みが変わる。どちらも、D4 が選んだあとで押した点の下を変えうる。完了の条件7に、extra を持つ3本（character-fortune・science-thinking・japanese-culture）を入れること。

### 4. 再入力の不変条件を、どこで守るかが書かれていない

4-2 は「1つの問に答えは1つ」を不変条件とし、「`handleAnswer` を前の状態から作る形にする」と書く。しかし関数で状態を更新する形にしただけでは、2回呼ばれれば答えが2件足される。`input-events-and-guards.md` §1 の (a) のとおり、**状態を更新する所そのもの**で、その問の id の答えがすでにあれば足さない、と決めること。マウントごとの ref では、別の task で届く2打目を止められない。次の3つを試験に入れること。

- 同じ描画の中の2回の click
- 見せている 150ms のあいだに別の task で届く click
- キーボードの Enter の連打

150ms のタイマーについても決めること。

- どちらが持つか（`QuestionCard` か `QuizContainer` か）
- 答えをいつ記録するか（押した時か、150ms のあとか）
- 見せているあいだにアンマウントされたとき（上端のリンクで移るなど）の後始末（AP-I11）

### 5. F3（押した行にフォーカス）の組み方と、`DESIGN.md` の既存の文との食い違い

- フォーカスを受ける要素を**行（`li`）**にすること。4-5 は「読み上げは行の名前と添えを読む」とする。名前の `span` だけにフォーカスを置くと、隣の要素の添え（「あなたの回答」「不正解」）は読まれない。行には字の箱の余白（`[data-text-box="rows"] > li`）があるので、リングを内側に密着させる指定（§6）と合う。これを 4-5 に書くこと。
- `DESIGN.md` §6 の「二重リングは…押せないがフォーカスを受けるもの（ページを送ったあとの件数の行、§7）では字の箱」は、押せないのにフォーカスを受けるものを列挙している。5章の箇条を足すなら、この列挙に答えたあとの行も入れること。そうしないと、足した箇条と既存の文が食い違う（ツギハギ）。
- §6 の冒頭は「押しても何も起こらないもの」を、現在地と無効の2つとして定めている。答えたあとの選択肢はどちらでもない。「押したあとはコントロールでない字になる」と冒頭の定義の中で位置づけるか、足す表の行でそう言うこと。
- 問の見出し（ブロックの `h2`）にフォーカスがあるとき、リングを字の箱に出すのか、見出しの箱に出すのか。4-5 の「行の字の箱に出す」がどちらを指すのか読めないので、分けて書くこと。
- 完了の条件5の「`BODY` になる瞬間が無い」を、どう測るかを書くこと（例: `focusout` の `relatedTarget` が `null` になった数）。押したボタンが字に替わる描画で、フォーカスは一度 `body` に落ちうる。
