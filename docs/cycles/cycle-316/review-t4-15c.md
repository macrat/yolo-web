## Major

### M1. 整形したあと、整形した JSON が1行も見えない

来訪者が画面を送って「整形」のボタンが見える所まで来て押す、という普通の使い方を再現した（ボタンの下端を画面の下端から 8px 上に置いて押す）。

| 条件           | 送った量 | コピーのボタンの下端 / 画面の高さ | コードの始まり | 見えるコード |
| -------------- | -------- | --------------------------------- | -------------- | ------------ |
| 375×667        | 64px     | 666 / 667                         | 682            | 0px          |
| 320×568        | 63px     | 568 / 568                         | 584            | 0px          |
| 1280×800       | 49px     | 799 / 800                         | 815            | 0px          |
| 375×667・200%  | 83px     | 667 / 667                         | 783            | 0px          |
| 1280×800・200% | 83px     | 800 / 800                         | 816            | 0px          |

- **来訪者に見えること:** 押すと画面が少し（50〜80px）動き、画面の下端に灰色の帯と「整形した JSON」「コピー」だけが出る。整形できたか、どう整形されたかは、自分で送らないと1行も見えない。1280 では 49px しか動かないので、結果が出たことにも気づきにくい。コピーのボタンは下端に接していて、ボックスの内側の余白も線も画面の外にある。
- **前との比べ:** 前の 1280×800 は入力と出力が左右に並び、押したその場で整形した JSON が 12行見えていた（出力欄の上端 397px・下端 790px）。PC の来訪者にとっては、結果を見るために送る手間が1つ増えた。
- **原因:** 送り先が「コピーのボタンの下端 = 画面の下端」の最小の送りである（`JsonFormatterTile.tsx` の `useEffect`）。§8 の「次に使うコントロールが画面に入るまで送る」は満たすが、道具の結果では、来訪者が次にすることは「結果を見て、写す」で、結果そのものが見えることが要る。
- **直し方の方向:** 送り先を「操作の行（整形・圧縮・検証）を画面の上のほうに残し、その下に結果をできるだけ多く見せる」位置にする（結果がそれより短ければ、結果の下端が入るまで）。375×667 なら、操作の行を上端近くに置けば、頭の行の下に約 20行のコードが入り、操作の行も見えたままになる。これは道具の結果の見本（T5 の31本が倣う）なので、送り先の決め方は planner が 2-5 と `DESIGN.md` §8 に決めてから実装する。コントロールだけでなく結果の中身も見せる送り方は、§8 の「次に使うコントロール」の文だけでは導けない。
- 結果の送りそのものは、出しゃばりではない。コピーのボタンが画面の中にあれば送らず（375 で 20字の JSON を整形したとき 0px）、送るときも即時で、登場の動きと重ならない。問題は送る量が足りないことである。

### M2. キーボードでコードの区画に着くと、PC では結果の真ん中へ飛ぶ

- 1280×800 で、整形のボタンで Enter → Tab を3回（圧縮 → 検証 → コピー → コードの区画）押した。コピーまではページが動かない（`scrollY` 49）。コードの区画に着いた瞬間に `scrollY` が **49 → 8,302** になり、区画の上端は画面の 7,438px 上にある。画面には 55件のうち 26〜28件目が出る。リングは左右の縦の線しか見えず、上と下の辺は画面の外にある。
- 375×667 では区画の上端に合わせて送られた（`scrollY` 431 → 873）。
- **来訪者に見えること:** キーボードで整形した JSON を読み始めようとすると、始まりではなく真ん中に連れていかれ、どこに着いたかも分からない。始まりに戻るには自分で数千 px 戻る必要がある。
- **原因:** M1 の送りのあと、区画が画面の外に丸ごとあり、Chromium はフォーカスを受けた画面より高い要素を画面の真ん中に寄せる。375 では区画の上端が画面の中にあったので、上端に合わせて送られた。M1 で結果の中身が画面に入るように直せば、この飛びも消える見込みが高い。直したあとに、1280・375・320 の既定と 200% で、Tab でコードに着いたときの `scrollY` と区画の上端の位置を測って確かめる。消えないなら、`ResultBox`（共有の部品）で扱う必要がある。

### M3. 圧縮した JSON が 86,000px の1行になり、終わりが見えない

- 500行ぶんの JSON を圧縮すると、中身の幅が 85,979px の1行になる。375 で見えるのは `{"items":[{"id":0,"name":"item-0'` の約 35字、1280 で約 100字だけである。終わりまで見るには 86,000px を横に送る。
- **来訪者に見えること:** 圧縮できたか、最後まで入っているかを目で確かめられない。前は出力欄（textarea）の中で折り返し、欄の中を縦に送れば全体を見られた。
- **原因:** 2-5 の表は「整形したコード → コードのボックス（折り返さない）」「1続きの文字列 → 本文の幅で折り返す」と分けているが、**圧縮した JSON がどちらか**を決めていない。圧縮した JSON は改行を持たない1続きの文字列で、読む形は Base64 の結果に近い。
- **直し方の方向:** planner が 2-5 で圧縮の結果の組み方を決める（例: 圧縮の結果はコードのボックスのまま、`pre` を折り返す組みにする。§3 の「等幅はコードだけ」は守れる）。§5 の「コードは折り返さない」の例外になるので、`DESIGN.md` の文も合わせて決める。SQL・CSS などの圧縮を持つ道具も T5 でこれに倣う。

### M4. 画面に入れる送りを、共有の部品を使わずに道具の中にもう1つ書いている

- `src/play/games/shared/_lib/revealControl.ts` に、同じ §8 の規定（操作のあと、次に使うコントロールが画面の外にあれば、`visualViewport` で測って即時に送る）の実装が 11119f8 の時点ですでにあり、ゲーム3本が使っている。
- この道具は `useEffect` の中に別の実装を書いた。2つは振る舞いが違う。ゲームはコントロールの下端を画面の下端から 8px 上に置き、道具は下端にぴったり付ける（M1 の表でコピーのボタンの下端が 666/667・800/800）。画面の上端の側（`visualViewport.offsetTop`）も、ゲームは測り、道具は測らない。
- **来訪者に見えること:** ゲームでは送ったあとにボタンの下に少し余白があり、道具では画面の端に接する。同じサイトの「操作のあとに送る」が面ごとに違う。
- 道具の結果の見本なので、このままでは T5 の31本に同じ関数の写しが増える（AP-I02）。送りの関数を `src/lib` などサイト全体の場所に1つ置き、ゲームと道具の両方がそれを使う形にする。M1 で送り先の決め方を変えるなら、その関数に入れる。

## Minor

### m1. Safari では誤りの位置が出ない

- `toJapaneseJsonError` は、エンジンのエラーの文から「line N column M」か「position N」を拾う。Chrome（V8）と Firefox は位置を書くが、Safari（JavaScriptCore）は「JSON Parse error: Unexpected identifier "invalid"」のように位置を書かない（[PerryTS/perry#10882](https://github.com/PerryTS/perry/issues/10882)、[DEV Community](https://dev.to/helloashish99/jsonparse-errors-what-each-message-actually-means-20io)）。
- **来訪者に見えること:** iPhone と Mac の Safari では、どの JSON でも「JSONの形式が正しくありません。」だけになり、何行目を直せばよいか分からない。
- 前からある制約だが、この道具のいちばん役に立つ情報の1つである。位置をエンジンの文に頼らず自分で求めるか、B 番号でバックログに積むかを PM が決める。

### m2. 同じ誤りのまま押し直すと、何も起きていないように見える

- 誤った JSON で整形を2回押すと、`role="alert"` の要素は同じもの（同じ文）のまま残る（1回目の要素に付けた印が2回目も残っていた）。文が変わらないので読み上げは言い直さず、画面も変わらない。
- 成功の知らせは `key={run}` で押すたびに入れ直している（2回目に要素が入れ替わることを確かめた）ので、誤りも同じく押すたびに入れ直すと、「押したが、まだ誤っている」ことが目でも耳でも伝わる。

### m3. 誤りの文が「3行／目」で折れる

- 375 で「JSONの形式が正しくありません。（3行目、3文字目付近）」が「（3行」と「目、3文字目付近）」に折れた。§4 と §8 の「数字と単位を離さない」に当たる。
- 決まった形の文なので、「3行目」「3文字目」が割れないように組む（折り所を手で決める、など）。

### m4. 「整形した JSON」の半角の空白

- 結果の見出しとコピーの名前は「整形した JSON」「圧縮した JSON」「整形した JSONをコピー」で、和文と欧文のあいだに半角の空白がある。同じ道具のほかの文（欄のラベル「JSON」、「JSONを入力してください。」「JSONの形式が正しくありません。」「正しいJSONです。」、ページの説明）は空白を入れていない。
- 読み上げの名前も「整形した JSONをコピー」と、空白のある所と無い所が混ざる。「整形したJSON」にそろえる（`docs/japanese-ai-slop.md` の「不要な半角スペース」）。

### m5. 使われていないコードが残っている（AP-I13）

- `variant="format-only"` は、11119f8 の `src/` と `scripts/` のどこからも使われていない（呼ぶのはこの道具のテストだけ。ページは `variant="full"`）。このコミットで型の説明を書き直し、テストを2件保っている。
- `logic.ts` の `JsonValidationResult.position` と、それを拾う正規表現は、本体からもテストからも読まれていない。
- 道具ごとの `variant` はほかの道具にもあり、この道具だけの判断で消せないなら、PM が扱いを決めて記録する。`position` はこの道具の中だけのものなので消せる。

### m6. テストが届いていない振る舞い

- 送りのテストは `visualViewport` を `undefined` にして `innerHeight` の道だけを試している。文字盤が開いたときの `visualViewport.offsetTop + height` の道は試していない。
- 検証の結果（コピーのボタンが無い）でボックスを送る先にする道も試していない。
- M1・M4 で送りを直すときに、この2つも含めて試す。

### m7. タブで字下げすると、1段が 8字になる

- インデントに「タブ」を選ぶと、`pre` の `tab-size` が既定の 8 のままで、375 では3段目が 24字ぶん右から始まる。狭い画面では数段で横に送る所に入る。
- コードのボックスのタブの幅は `DESIGN.md` §5 に定めが無い（AP-I08）。記事のコードも同じボックスで組むので、決めるなら §5 に書いてから `globals.css` の既定に入れる。

## 来訪者の目で見た全体

- 入力が枠から出て、太い枠の中が結果だけになったので、どこに答えが出たかは一目で分かる。コードのボックスは灰の地で、JSON が等幅で読みやすく、ダークでも同じように読める。コピーのボタンが結果の頭にあるので、554行の結果でも送らずに写せる。検証・誤り・空の入力の知らせも、日本語で、欄の直下に、読み上げにも届く形になった。
- 惜しいのは、整形したあとに見えるのが結果の頭の帯だけで、JSON そのものは送らないと見えないこと（M1）。PC では前より一手増えた。ここを直せば、PC でもスマホでも「押す → 見る → 写す」が1画面で済む。
