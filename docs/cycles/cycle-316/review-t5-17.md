## 指摘

### 1. email-validator の h1 が、既定の文字サイズの 375px で語の中で折れる（「メールアドレスバリ／データー」）

全36本の h1 の折れを 320・375・1280・320 200% で取った。既定の文字サイズでは、email-validator だけが 375px で「メールアドレスバリ／データー」と、1行に収まる語「バリデーター」の中で折れる（320px では「メールアドレス／バリデーター」と正しく折れるので、幅しだいで割れ方が変わる）。前は h1 が 20px で1行に収まっていたので、T5-17 で h1 を §4 の大きさにしたことで表に出た崩れである。375px は来訪者のいちばん多い幅で、h1 は道具の名前として最初に読まれる字なので、「バリ」と「データー」が別の語に見える。

原因は `src/lib/phrase-breaks.ts` の `wordStartsOf`。`Intl.Segmenter` が「メールアドレス|バリ|デー|ター」と刻み、片仮名の続きの中に3字未満の切れ端（「バリ」「デー」「ター」）があるので、続きの中の語の頭をすべて捨てる。そのため `<wbr>` が1つも無く、`word-break: keep-all` と `overflow-wrap: anywhere` が、行の埋まった所で割る。§4 は「いちばん狭い画面の1行より長い文節は、中の語と語の切れ目に折り所を持つ」「語の中で折れるのは、語が1行に入らないときだけ」と定めているので、この名前は「メールアドレス|バリデーター」に折り所を持つべきである。

名前を1本だけ別に書く（ハードコード）のではなく（AP-I02）、片仮名の続きの中で短い切れ端をとなりと合わせてから語の頭を決めるなど、区切りの側で直すことを勧める。直したら、全36本の h1 と、同じ関数を使うほかの見出し（一覧の名前・画像の名前）の折れを取り直す。`phrase-breaks.ts` は T5-17 の受け持ちの外なので、どのタスクで直すかは PM が決め、決めた内容を index.md に書く。T5-17 の完了の条件として、375px の既定の文字サイズでこの h1 が語の中で折れないことを確かめる。

### 2. 短い説明を「h1 の下」に置く前提の注記が2か所に残っている（ツギハギ）

T5-17 で短い説明を頭から「このツールについて」の最初の段落へ移したが、次の注記は前の置き場所のまま書かれている。

- `src/tools/_lib/share-image-content.ts` の5行目: 「副題に h1 の下の短い説明を添える」。いまの画面では h1 の下に短い説明は無い。
- `src/tools/types.ts` の9行目と19行目: `shortDescription` は「~50 chars for cards」、`howItWorks` は「ゾーン3「このツールについて」セクションに表示する」。短い説明がいまは「このツールについて」の最初の段落にもなっていることが書かれておらず、「ゾーン3」はもう無い組み方の言い方である。

CLAUDE.md のツギハギ禁止に従い、どちらもいまの組み方を最初から書いたように書き直す（短い説明が、一覧の行の説明・画像の副題・「このツールについて」の最初の段落の3か所に出ることが、型の注記から分かるようにする）。

### 3. 「このツールについて」の中身が同じことを繰り返す道具が、PM の決定の6本より多い（T5-18 への申し送り）

T5-17 の組みは正しい。ただ、段落を並べて読むと、次の点で来訪者は同じことを2度読むことになる。

- **短い説明と仕組みの重複**: PM の決定は6本（sql-formatter・unit-converter・line-break-remover・yoji-search・color-converter・text-replace）を挙げている。しかし char-count（「文字数・バイト数・行数をカウント」のすぐ後に「文字数・バイト数（UTF-8）・単語数・行数を同時にカウントします」）、byte-counter、kana-converter なども、最初の段落が次の段落の頭をそのまま縮めた文になっている。
- **仕組みとプライバシーの注記の重複**: 12本（age-calculator・base64・business-email・char-count・hash-generator・image-resizer・json-formatter・line-break-remover・password-generator・percent-calculator・text-diff・yaml-formatter）は、仕組みの文に「入力データはサーバーに送信されません」の趣旨を持ち、そのすぐ下の注記が同じことを言う。
- **段落として読めない文**: 短い説明は、一覧の行や見出しの下に添える体言止めの句（「テキストとBase64の相互変換」）として書かれていて、句点を持たない。本文の段落に置くと、見出しの切れ端のように見える。json-formatter（「…整形します。構文チェックや圧縮にも対応」）と yaml-formatter は、途中に句点があるのに終わりに句点が無い（§9 自然な日本語）。

どれも `meta.ts` の中身で、T5-18 の道具ごとの行の受け持ちである。PM は、T5-18 の各行で「このツールについて」の3つの段落を通して読み、重複を除くことと、短い説明を段落として読める文にするかどうか（一覧の行と画像の副題にも出る）を決めることを、6本に限らず36本の条件として index.md に書く。

### 4. 試験の名前に前の組み方の語が残っている

`ToolPageLayout.test.tsx` の「パンくず→h1→children→howItWorks の順序で DOM に出現する」と、その中の変数 `howItWorksIdx`・注記「パンくず → h1 → ツール本体 → howItWorks の順」は、いまは「このツールについて」のセクション（`aria-labelledby='about-tool-heading'`）を指している。「children が null でも howItWorks 以降が描画される」も同じ。試験が確かめているもの（セクション）の名前に合わせる。

### 5. ErrorBoundary の代わりの組みを確かめる試験が無い

`ErrorBoundary` の代わりの組み（`role="alert"`・h2 の見出し・本文）は、このタスクで組み方を変えたのに、単体の試験が1本も無い。子が投げたときに `role="alert"` の中に h2「ツールの読み込みでエラーが発生しました」と本文が出ること、枠やクラスの見た目を持たないことを確かめる試験を足す（`src/tools/_components/__tests__/` など）。今回は本番のページで落とせないので、見た目は差し替えて測るしかなかった。

### 6. ErrorBoundary を持たない道具が4本ある（申し送り）

bmi-calculator・number-base-converter・percent-calculator・unix-timestamp の `page.tsx` は `ToolErrorBoundary` で道具を包んでいない。この4本では、道具の本体が描けなかったときに T5-17 が組んだ知らせが出ず、ページ全体のエラーになる。T5-17 の前からのことで、`page.tsx` は T5-17 の受け持ちの外なので、PM が T5-18 のそれぞれの道具の行に入れる。
