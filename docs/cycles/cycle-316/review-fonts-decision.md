# レビュー: Web フォントの配り方と表示の速さの条件（fonts-decision.md）

レビュー日: 2026-09-25
対象: [fonts-decision.md](./fonts-decision.md)（新規）、index.md・options.md の未コミットの変更

## 結論: 改善指示

判断の方向（本文の和文は端末のゴシック、見出しは Zen Antique、欧文は IBM Plex Sans、専用の配信の仕組みは作らない）は、来訪者にとって釣り合っていると評価する。本文を BIZ UDPGothic で配ると、PV の78%が集まるプレイ面で +527.9KiB、辞典の詳細を除く4ページで総転送量が約1.9〜2.7倍になる。これは出典（487e5fc の t1a-fonts.md の方式 A の実測）と合っていた。一方で `DESIGN.md` §1 は本文の仕事を読みやすさとし、個性は罫線・見出し・コントロールに担わせている。この比較で本文の Web フォントを外す判断は妥当である。

ただし、採った配り方（Plex を `next/font/google` で配る）が、来訪者の読む日本語の約物を壊す事実が検討されていない（Major 1）。また、options.md に取り下げた上限の名残が残っている（Major 2）ほか、Major が計4件ある。

## Major

### 1. `next/font/google` の IBM Plex Sans は、和文の約物（——・……・“”）まで Plex で組む

- `next/font/google` の `latin` サブセットの `unicode-range` を、Google Fonts の CSS API で確かめた（2026-09-25）。値は `U+0000-00FF, U+0131, U+0152-0153, U+02BB-02BC, U+02C6, U+02DA, U+02DC, U+0304, U+0308, U+0329, U+2000-206F, U+20AC, U+2122, U+2191, U+2193, U+2212, U+2215, U+FEFF, U+FFFD` である。一般の約物（U+2000-206F）を含む。
- 本文も見出しも「欧文（Plex）, 和文」の並びで組むので、和文の中の `—`（U+2014）・`…`（U+2026）・`“”‘’`・`×`・`¥` は Plex で描かれる。この配信ファイルの字幅を fontTools で測ると、`—` は 0.78em、`…` は 0.803em（ベースラインに乗る欧文の三点）、`“` は 0.475em だった。「——」は全角2つの続いた線にならず、「……」も和文の中央の三点リーダではなく、ベースラインに乗った欧文の点になる。
- `—` は `src/` の 355 ファイルに現れる（ブログ・辞典・ツールの本文）。変更前の本文は端末のゴシックだけなので、全角で組まれている。**変更後に、来訪者が読む和文の組みが目に見えて崩れる。**
- これは `DESIGN.md` §3 と食い違う。§3 は、Plex の範囲を「見出しを含む `U+0000-007F` の全体」とし、「この範囲の外の字（アクセント付きラテン・欧文約物）は和文の書体が組む」と定めている。§4 の「三点リーダは『……』」とも食い違う。487e5fc の t1a-fonts.md の最初の版は、Plex を `U+0000-007F` に絞った自前のファイルで配っており、この問題を避けていた。fonts-decision.md の「いまのサイトと同じ `next/font/google` で配る」は、この差を落としている。
- `next/font/google` には `unicode-range` を上書きする手段が無い。`next/font/local` には `declarations` があり、`unicode-range` を指定できる（`node_modules/next/dist/compiled/@next/font/dist/local/index.d.ts` で確かめた）。Plex だけ `next/font/local`＋`unicode-range: U+0000-007F` で配れば、専用の配信の仕組みは要らない。ほかに、§3 を改めて欧文約物を Plex で組むことを受け入れる道もある。その場合は、得と失うもの（和文の中のダッシュ・三点リーダの見た目）を来訪者の側で比べて示す必要がある。**どちらを採るかを決め、fonts-decision.md の表・転送量の見込み（Plex の `latin` は1ファイル 45.7KB、`U+0020-007E` なら 13KB）・「`DESIGN.md` の変更」に反映すること。**

### 2. options.md に、取り下げた上限と、決定と食い違う記述が残っている

options.md 66行目「**Web フォントが増える。**」の段落に、次の2点が残っている。

- 「和文2書体（BIZ UDPGothic は2ウェイトで各124分割、Zen Antique は118分割）を読み込むことになる」。決定では本文の和文は配らない。和文の Web フォントは Noto Serif JP が Zen Antique に替わるだけで、書体の数は増えない。
- 「**そこで、刷新でページの総転送量を増やさないという上限を計画で先に決め（index「表示の速さ」）、土台を作る前（T1a）に越えるかを確かめる。越えれば §3 を改める。**」。取り下げた増分0の上限そのもので、index「表示の速さ」にはもうこの上限が無い。リンク先とも食い違う。

この段落は、決定（fonts-decision.md）に合わせて書き直す必要がある。関連して、index.md 135行目の A の代償「和文の Web フォントが増える」も、決定のあとでは実態と合わない。「見出しの書体が Zen Antique に替わり、Web フォントの転送量が数十 KiB 増える」のような、決定に合った表現に揃えること。

### 3. Zen Antique に無い字の規定を、データから描く見出しで確かめないと、index の完了の条件と食い違う

- fonts-decision.md は、この規定を「コードに書かれた見出しを Zen Antique の字の表と照らす試験で確かめる。データや入力から描く見出しまで網羅する仕組みは作らない」としている。
- しかし、この規定が実際に掛かる見出しはデータから描く見出しである。facts-design-gap.md §12-2 によれば、`src/data/kanji-data.json` の漢字辞典の見出しの「𠮟」がそれにあたる。t1a-fonts.md の最新版は、ほかに 剝・塡・頰 なども挙げている。index.md 72行目は、完了の条件の境界の値に「**見出し書体に無い字を含む見出し**（漢字辞典の「𠮟」）」を必ず含めると定めている。いまの書き方では、試験は通るのに T9 でこのページが落ちる。来訪者は、1つの見出しの中で書体が混ざったページを見ることになる。
- 入力から描く見出しを外すのはよい。ただし、**ビルドの時に決まるデータ（辞典のデータ）の見出しは、同じ字の表との照合の対象に含める**と書くこと。これはデータを読む試験で済み、配信の仕組みではない。

### 4. frontend-design スキルが、取り下げた道（自前のサブセット）を指示したままになっている

`.claude/skills/frontend-design/SKILL.md` 56行目に「**書体を変えたら、サブセットを作り直す。** 収録する字種は、サイトで実際に使う字から決める。」とある。T1 の builder がこのスキルに従うと、今回取り下げた自前のサブセット作りに戻る。incident-2 の再発の入口になるので、決定（`next/font` で配る。Plex の範囲は Major 1 の結論に従う）に合わせて書き直すこと（CLAUDE.md「Improve work and process」）。

## Minor

1. **A2 の数字の出どころ。** 「同じ試作で、見出しの Zen Antique と IBM Plex Sans だけを配った場合、Web フォントの増分は7ページで +6〜+85KiB だった」とあるが、出典（487e5fc の「A2」）は、この値が Lighthouse の試作の実測か計算による見積もりかを書いていない。全ページの計算値（3,318 ページで増える）と並んでいるので、見積もりと読むのが自然である。「同じ試作で」ではなく、出典どおり「同じ見積もりで」と書くこと。また、この文書の他の箇所は「代表の5ページ」なのに、ここだけ「7ページ」になっている。取り下げた境界の2ページを含むことを書き添えること。
2. **「転送量がほぼ倍になる」。** 表の比は 1.37倍（辞典の詳細）〜2.68倍（結果面）で、2倍を大きく超えるページが2つある。「1.4〜2.7倍になる」と書くほうが正確である。
3. **単位と丸め。** 「2秒あまり」は 527.9÷200＝約2.6秒なので、「約2.6秒」と書くこと。「0.5〜0.9MB」は、表の KiB に揃えて「460〜916KiB」とすること。
4. **増分の理由の説明が不足している。** 「いまの見出しの明朝の分割ファイルが、Zen Antique の分割ファイルに置き換わるだけだからである」とあるが、置き換わるだけなら増分は0に近いはずである。出典によれば、+6〜+85KiB が出るのは Zen Antique の字形が重い（1字あたり平均約 355B）ためで、あわせて Zilla Slab が Plex に替わる。この2点を書くこと。
5. **変更前の値の出どころ。** 表の「変更前」（554.9KiB など）は 487e5fc で測り直した値で、facts-speed-before.md の値（558KiB など）より 3.8〜6.5KiB 小さい。「変更前の値は facts-speed-before.md」と書いてある index と並べて読むと、数字が合わないように見える。表の出どころ（487e5fc の同日の再計測）を一言添えること。
6. **「端末のゴシック（`system-ui` の和文）」という書き換えの案。** いまのサイトの本文は `system-ui` ではなく、書体の名前を並べた指定（`"Hiragino Kaku Gothic ProN", "Yu Gothic Medium", "Noto Sans JP", sans-serif`。`src/app/globals.css`）で組んでいる。Windows の `system-ui` は Segoe UI → Yu Gothic UI（UI 向けの字幅の狭い書体）に解決され、OS の言語によっては中国語の字形が出ることが知られている。「いまのサイトの本文もこれで組んでいる」「Windows の游ゴシック・メイリオ」という本文の記述とも食い違う。`DESIGN.md` の書き換えは、いまの書体の並びに合う表現にすること。
7. **CLS と LCP の条件の書き方。** fonts-decision.md の CLS は「比べる」だけで、悪化したときにどうするかが無い。index.md は「ずれないことを確かめる」と書いており、両者が合っていない。どちらかに揃えること。LCP の「揺れの範囲を越える」は定義が無い。変更前の5回の幅は 722〜1,980ms あるので、各5回では 10% の悪化はほぼ判定に掛からない。測り方を細かくする必要は無いが、「大きな悪化を見逃さないための確認である」と、条件の実際の強さを正直に書くこと。
8. **「1ファイルのうち使う字は数字にとどまる」。** 「数字（すうじ）」と読めてしまうので、「数文字」と書くこと。

## 確かめたこと

- 表の5ページの値（変更前・方式 A・差）、BIZ UDPGothic の各124分割・1ファイル平均約 23KB、フォントの CSS が gzip で約 4KB 減ること、+6〜+85KiB は、487e5fc の t1a-fonts.md と一致した。
- 83.7%・PV の78%・約 200KiB/秒（1,638.4Kbps）は、facts-ga と index の記述と一致した。
- Zen Antique（400）と IBM Plex Sans（400・700 を含む）が、Next.js 16.3.0 の `font-data.json` にあることを確かめた。
- `src/lib/fonts.ts` は、Noto Serif JP 600 と Zilla Slab 500 を `next/font/google`・`display: swap` で配っている。fonts-decision.md の記述と一致した。
- index.md の「表示の速さ」から、増分0・境界のページ・T1a への差し戻しの記述は除かれていた。t1a-closure.md への参照も index から消えていた。options.md 73行目の書き換えも決定と合っていた（残っている名残は Major 2 の66行目）。
