## 指摘

### Minor-1: §4「和欧混植」が、§3 で近似とした字面の大きさを「揃える」と言っている

§4 の新しい文:

> 和文と欧文は別の書体で、行の高さ・字面の大きさ・ベースラインは §3 の規定で揃える。

§3 の最後の箇条は、字面の大きさを「端末の和文の書体による近似とする」と定め、揃えることを約束していない。§4 だけを読むと、字面の大きさも揃える規定に見える。実装する人が size-adjust で揃えようとすれば、§3 と逆の実装になる。

直し方の例: 「和文と欧文は別の書体で、その切り替わりの扱いは §3 に従う」のように、§3 を指すだけにする。または「行の高さとベースラインは揃え、字面の大きさは近似とする（§3）」と、§3 と同じ区別を書く。

### Minor-2: 「字ごとに分割して配っても」は、分割配信の仕組みと合わない

§3 の新しい箇条:

> 本文の字はページに散らばるので、字ごとに分割して配っても1ページで数百 KiB を読ませることになり

分割配信は、字の範囲ごとのファイル（BIZ UDPGothic では 400・700 の各124分割、1ファイル平均約 23KB）に分けて配るもので、1字ずつ分けるものではない。重くなる理由も、散らばった字のために数十のファイルに触れ、各ファイルでは数文字しか使わないことにある（fonts-decision.md「なぜこの形か」）。「字ごと」と書くと、必要な字だけを配っても重いと読めてしまい、仕組みと理由が正しく伝わらない。

直し方の例: 「字の範囲ごとに分割して配っても、散らばった字のために1ページで数十のファイルを読むことになり、数百 KiB を待たせる」。

### Minor-3: `system-ui` の箇条で、「Yu Gothic UI に解決される」ことの何が来訪者に困るのかが書かれていない

> **本文の並びに `system-ui` を使わない。** Windows では Yu Gothic UI に解決され、OS の言語によっては中国語の字形が出る。

後半の「中国語の字形が出る」は、来訪者に起きる害として読める。前半の「Yu Gothic UI に解決され」は、起きることを書いているだけで、それがなぜ困るのかが無い。§3 のほかの箇条（「小さいサイズで保たない」「痩せない」など）は、規定のあとに来訪者に起きることを書いている。この箇条だけ書き方が揃っていない。

Yu Gothic UI には、Windows の日本語環境で欧文の字形が崩れる不具合の報告がある（[tailwindcss PR #20318](https://github.com/tailwindlabs/tailwindcss/pull/20318)。Tailwind はこれを理由に既定の並びから `system-ui` を外した）。また、Yu Gothic UI は約物をあらかじめ詰めた UI 用の書体で、`text-spacing-trim` を掛けると詰めすぎになることが CSSWG で議論されている（[csswg-drafts #11074](https://lists.w3.org/Archives/Public/public-css-archive/2024Oct/0867.html)）。

直し方の例: どちらの害を理由にするかを出典（fonts-decision.md が引く出典か一次資料）で確かめ、そのうえで「Windows では UI 用の Yu Gothic UI に解決され、〈来訪者に起きること〉。OS の言語によっては中国語の字形が出る」と書く。出典で裏づけられないなら、前半を「中国語の字形が出る」ことの前提として書き直し、理由を1つにまとめる。

### Minor-4: §3 の最後の箇条は、見出しに当てはまらない言い方で、size-adjust を掛けない理由も書かれていない

> IBM Plex Sans は `size-adjust` を掛けずに組み、和文との字面の大きさの揃いは端末の和文の書体による近似とする。

見出しでは、和文は Web フォントの Zen Antique で、端末の書体ではない。「端末の和文の書体による近似」は本文にしか当てはまらないが、§3 は同じ箇条の先で「欧文は見出しも IBM Plex Sans」と定めている。この文では、見出しの Zen Antique と Plex の字面の関係がどうなるのかが読み取れない。

また、`size-adjust` を掛けない理由が無い。理由は、本文の和文の書体が端末ごとに違い、一つの倍率では揃えられないことである（fonts-decision.md「捨てるもの」）。この理由を書けば、「近似とする」が妥協ではなく必然だと読める。

直し方の例: 「IBM Plex Sans は `size-adjust` を掛けずに組む。本文の和文の書体は端末ごとに違い、一つの倍率では揃わないためで、字面の大きさは近似で揃う。行の高さとベースラインは和文と欧文で揃える。」見出しについては、Zen Antique と Plex の字面の関係をどう扱うかを決定の範囲で書く（決定が見出しを区別していないなら、本文と見出しの両方に当てはまる言い方にする）。

## T1 への申し送り（今回の差分の指摘ではない）

- §4「強調」の「和文も欧文もウェイト 700 を持つ（合成太字を作らない）」は、端末の書体に任せたことで、すべての端末では保証できなくなった。とくに `"Yu Gothic Medium"` は、ファミリー名で 700 を当てると合成太字になる例が広く知られている。fonts-decision.md「T1 で確かめること」の1項目めで確かめ、守れないなら §4 をどうするかを決定として記録してから書き換える。
- 並びの `"Noto Sans JP"` は、Android では選ばれない（システムのファミリー名は Noto Sans CJK JP で、末尾の `sans-serif` から選ばれる）。どの端末でこの名前が効くのかを、決定の文書が説明していない。決定の範囲の問いで、`DESIGN.md` の差分は決定を忠実に写している。
