## blocker

### 新 B-1. 入力を映す表示の印の付け忘れを、ビルドは本文の役割では検出しない。境界のページ `keigo-reference` で、実際に混ざりが残っている

**どこが**

- 「入力と、入力で選ばれる表示」の表の「付け忘れは、辿れない式としてビルドが止め」
- 字の集め方の2の3
- 4巡目 B-1 への対応の「全36ツールで…0になった」
- 境界のページの「操作のあとの同居も0」

**なぜ**

- r5h で `keigo-reference` の入力欄に「鬱蒼とした森で麒麟を見た。ｶﾀｶﾅとＡＢＣも。」を入れた。「「…」に一致する動詞が見つかりませんでした」の `div` 1つに、BIZ UDGothic と端末の書体が同居した（`keigo.png`）。4巡目の B-1 と同じ種類の混ざりが、閉じたページで出ている。
- 文書の試験で見つからなかった理由は2つある。
  - `scen5` の keigo の手順は「存在しない動詞」を打っている。この字はページの層にある。
  - `sweep5` は、入れたあとにボタンを押すので、結果の状態が変わってしまう。
- 構造の原因は、辿れない式の検出が、見出しと太字の役割の要素の中の式だけに掛かることである。`roles5.mjs` の `resolve` は、役割が `zen` と `biz700` のときしか呼ばれない。本文の役割で入力を映す式は解析されない。閉じたページの本文に何が入るかは「届くテキスト」で決まり、入力の値はそこに入らないので、ビルドは通ってしまう。
- 文書が柱にしている「漏れる方向の失敗を、ビルドか CI で見える失敗に変える」は、本文の役割（入力を映す表示の大半）では、CI の手順が偶然その状態を踏んだときにしか成り立たない。

**どう直すか**

- 閉じたページでは、**役割を問わず、すべての JSX のテキストの式**を辿る。値が入力に由来するなど辿れない式があれば、ビルドを失敗させる。規則として書き、試作で `keigo-reference` のこの式が報告されることを示す。
- keigo の結果なしのメッセージに `data-input-view` を付ける（または、入力の値を描かない文言にする）。
- CI の手順は「結果の無い入力」「層に無い字の入力」のあと、**ボタンを押す前の状態で**検査する形にする。全36ツールで確かめ直す。

## major

### M-1. CI の検査は「1つの要素の中の同居」しか見ない。要素がまるごと端末の書体に落ちたときは、見つけられない（「測り方」の CI・「落ち着いた後に混ざらない」の主張）

- 実例1: r5h の `email-validator` に `a..b@-exa mple`（B-1 の再現手順）を入れると、「無効」のバッジが丸ごと IPAGothic で描かれる（`email.png`）。
  - 原因: バッジは `font-weight: 600` で 700 の面が選ばれるが、その面に「無効」が無く、閉じたページなので予備も無い。
  - `CSS.getPlatformFontsForNode` の結果は IPAGothic 2字だけで、同居ではないので、文書は「同居0」と報告している。
- 実例2: `/dictionary/kanji` の部首のリンク「疒」「辵」「黃」「彐」も、要素ごと端末の書体で描かれる。
- 本番では、stylelint がクラスでのウェイト指定を禁じるので、実例1はそこで塞がる見込みはある。しかし、「CI が混ざりとして見つける」という安全網は、要素がまるごと落ちる型を原理的に検出できない。
- **直し方**: CI の検査を次の形に改める。「ページの家族を書体の並びに持つ要素（`data-input-view`・コードの中を除く）で、端末の和文の書体で描いた字が0（書体に無い字として列挙した字を除く）」。あわせて、ウェイトと役割の対応（600 以上は 700 の層）をビルドが検査するか、stylelint で保証すると書く。

### M-2. Zen Antique に無い字の数え方が誤っている。辞典の詳細の見出しの中で、書体が混ざる（§3「Zen Antique に無い字を含む見出しは、その和文を丸ごと本文書体で組む」・「予備の組み方」の「見出しの字で Zen Antique に無いのは14字（絵文字・記号）」）

- fontTools で調べた。Zen Antique に無い漢字は、常用漢字の 𠮟・剝・塡・頰（漢字辞典の詳細の h1）、部首の 疒・辵・黃・彐（部首のページの h1 と一覧のリンク）、伝統色の 纁 だった。
- r5h で `/dictionary/kanji/剝`・`/頰`・`/radical/疒`・`/radical/彐` を開いた。落ち着いた後の h1 が「WenQuanYi Zen Hei:1, Zen Antique:4」のように、**1つの見出しの中で書体が混ざった**。
  - 変更前は Noto Serif JP がすべての字を持っていたので、混ざらなかった。字形が主題の面（options.md）での退行である。
  - 疒・辵・黃は BIZ UDGothic にあるので、§3 の規則どおり見出しを丸ごと本文書体で組めば揃う。
- 文書のビルドの工程（字の集め方・ビルドの経路・スキルへの提案）には、§3 のこの規則を実装する手順が無い。CI の開いたページの対象（代表のページ）にも、これらのページが入っていない。
- **直し方**:
  1. 見出しの役割のテキストに Zen Antique に無い字があれば、その要素を本文書体で組む（その字を本文の層に入れる）手順を、ビルドの工程に書く。
  2. 無い字の一覧とページ数を正しく数え直す。
  3. 対象のページを CI に入れる。
  4. スキルへの提案にも入れる。

### M-3. 閉じたページが API から受け取って描く文字列の扱いが決まっていない。PV の78%が集まる面に関わる（「辿れない式」の閉じたページの2箇所のうち `label`）

- `CharacterPersonalityContent`（`ResultCard` から `next/dynamic` で読み込む。閉じたプレイ面）は、紹介者の型があるとき、`/api/quiz/compatibility?typeA=<自分の結果>&typeB=…` を取得して相性の `label`・`description` を描く。
- 「届くテキスト」は HTML・RSC・JS チャンクと定義されていて、API の応答は含まれない。そのため、この区画は層から漏れ、閉じたページなので予備も無い。文書は「T1 で式か解析器を直す」としているが、実行時のデータなので、式や解析器では直せない。配り方の判断が要る。
  - 例: API の元のデータ（`character-personality-compat-*.ts`。字の種類は各 430〜660）を結果の層に入れる、など。
- あわせて、この経路では、答えから決まる結果が API に送られている。「閉じたページ＝内容をサーバーに送らない」という定義と、どう整合させるかを書く必要がある。
- **直し方**:
  1. 「同じオリジンの API の応答で描く文字列は、その元のデータを層に入れる」などの規則を、T1a で決める。
  2. 結果の層がどれだけ増えるかを見積もる（流れ全体の余裕は 70〜97KiB）。
  3. 紹介者のある流れを、試作か計算で確かめる。
  4. `axisId` のほうは、T1 の条件（解析器を直す）でよい。
