## 指摘

### Major-1: 部首の索引の見出しの大きさが区切りの見出しより小さく（45rem 未満）、広い画面でも区切りの見出しと同じ形で並ぶ。そのため「画数（24）」が部首の区切りの続きに見える

**どこで何が起きているか**: 「学年・部首・画数から探す」を開いたとき、索引の見出し `h2`（`KanjiListView.module.css` の `.indexHeading`、`--text-heading-sub`）と部首の区切りの見出し `h3`（`LinkIndex`、`max(--text-heading-sub, 1.49rem)`）の大きさは、次のとおりだった。

| 画面          | 「部首（198）」 | 「1画」 |
| ------------- | --------------- | ------- |
| 320・375px    | 17px            | 23.84px |
| 800px         | 23.84px         | 23.84px |
| 1280px        | 33.28px         | 33.28px |
| 200% の 320px | 34px            | 47.68px |

**来訪者にどう効くか**: 狭い画面では、親の「部首（198）」が子の「1画」より小さく、「1画」〜「15画」が見出しに、「部首（198）」がその前の添え書きに見える。広い画面でも、部首の索引の最後の「15画」のあとに、同じ大きさ・同じ細い罫線で「画数（24）」が並ぶ。中身のリンクも「1画」「2画」…なので、画数から引きたい来訪者が部首の区切りを画数の索引と取り違える。そのまま部首のページへ入ってしまう（撮った `top_375_light_index.png`・`mizu_1280_light_index.png` で、「画数（24）」が「15画」の次の区切りに見える）。部首のページは辞典の主な入口（12週 476 PV）で、このアコーディオンはそこで毎回使われる。

**DESIGN.md に照らして**: §4 の階層は見出しの段が大きさと罫線で作る。§7 は、漢字1字の索引の区切りの見出しを字より小さく組まないとしたうえで、「親子は大きさでなく罫線が見せる」と決めている。親が子より小さくなる組み方は、どこにも認められていない。§7 が想定する親は、全幅の罫線を持つセクションの見出しかアコーディオンのラベルである。このページでは、そのあいだに索引の見出しが1段挟まり、しかもその見出しは細い罫線しか持たないので、罫線でも親子が見えない。

**直し方**（どれも欠かせない）:

1. **DESIGN.md §7 に書く**（frontend-design の「文書に無いものを実装に置かない」）。§7「索引」の区切りの見出しの項に、次を足す。区切りを持つ索引をほかの索引と同じアコーディオンに並べるとき、索引の見出しは区切りの見出しより小さく組まず、並ぶ索引の見出しはどれも同じ大きさにする。区切りを持つ索引はアコーディオンの最後に置き、区切りの見出しの後ろに別の索引の見出しが続かないようにする。

3. **並び**: 索引を「学年 → 画数 → 部首」の順にし、ラベルを「学年・画数・部首から探す」にする。区切りの見出し「N画」の後ろに「画数（24）」が来なくなる。「部首（198）」の直下の「1画」は線を持たないので、見出しと最初の区切りが1組に見える。学年（1行）と画数（2〜4行）は短いので、部首へ届くまでに増える高さは小さい。
4. 設計書 t3-design.md 3-1 の漢字の行（「学年（7）」「部首（198）」「画数（24）」の順）も同じ順に直す。T3-8 で索引のアコーディオンの中身を共有の部品にするときは、この規則を部品が持つようにする。T3-8 で同じ組み方を写すと、同じ逆転が四字熟語・伝統色にも起きうる。

直したあと、320・375・800・1280px と 200% で、索引の見出しが区切りの見出し以上の大きさであること、部首の索引の後ろに別の見出しが無いことを撮って確かめる。

### Minor-1: トップの HTML の 80% が、行に見えている値から作り直せるデータで膨らんでいる

**事実**: トップの HTML は 890,947 バイト。変更前（6578b66）の 738,059 バイトより大きいが、転送量は gzip で 183,793 → 133,524、brotli で 128,507 → 95,813 と減っている。いま来訪者が待たされる量は増えていない。ただし、HTML の中の一覧のデータ（2,136件）は、エスケープ込みで約 710KB ある。その中身は次のとおり（JSON の値の大きさ）。

| 項目                   | バイト  |
| ---------------------- | ------- |
| `sortKeys`             | 113,229 |
| `matchNames`           | 86,285  |
| `reading`              | 69,196  |
| `searchTexts`          | 58,568  |
| `facts`                | 39,707  |
| `kind`                 | 29,989  |

`matchNames` は字と `reading` を「・」で分けたものと同じで、`sortKeys` は学年・画数・最初の読みの組み替えで、`slug` は字そのものから作れる。

**来訪者にどう効くか**: 転送量よりも、端末が 891KB の HTML を解析し、約 600KB の JSON を読んで保持する時間とメモリに効く。とくに低い性能のスマートフォンで効く。学年7のページ（531KB）も同じ形である。

**直し方**: 行が見せる値（字・音訓・学年・画数・熟語）だけを小さな形で渡し、`matchNames`・`sortKeys`・href をクライアントで組む。漢字の一覧をクライアント側の小さなラッパーで包むか、`BrowsableList` が `matchNames` の既定を名前と読みから作るようにする。この環境で見積もると、`matchNames`・`sortKeys` を渡さず `slug` を字のままにするだけで、一覧のデータは約 710KB → 403KB（gzip 113KB → 70KB）になり、配列の形にすれば 219KB（gzip 58KB）になる。設計の 2-8「行のデータは表示と絞り込みに要るものだけにし…小さくします」にも沿う。

### Minor-2: 学年・部首・画数のページの説明が、一覧に無い「意味」を約束している

`kanjiListDescription` の「読み方・意味・部首情報を確認できます」「読み方・意味・画数情報を確認できます」は、検索結果と SNS のカードにそのまま出る。一方、一覧の行は、この変更で意味（英語の語）を持たなくなった。検索から来た来訪者は、一覧で意味を探しても見つけられない。行が見せるもの（読み・学年・画数）に合わせ、たとえば「部首「水」を持つ常用漢字の一覧。読み方と画数を見て、字の詳しい意味や使用例へ進めます。」のように直す。

### Minor-3: 320px で件数の行が「1,110字 / 目」と単位の途中で折れる

`/dictionary/kanji/grade/7/page/12` の 320px で、件数の行が「全1,110字のうち1,101〜1,110字」と「目」の2行に折れる（`g7p12_320_light_full.png`）。「字目」の途中で折れると、数え方の語が切れて読みにくい。これは `ListStatus`（T3-4 の部品）の組み方なので、`ListStatus` で範囲の「1,101〜1,110字目」をひとまとまりにし（`white-space: nowrap` の span か `word-break: keep-all`）、「のうち」の後ろで折れるようにする。ブログや四字熟語の一覧でも、桁が増えれば同じことが起きる。

### Minor-4: 漢字が使わなくなった部品のコメントが、まだ漢字を使い手として書いている

`src/dictionary/_components/DictionarySearch/index.tsx`（「各辞典（kanji/yoji/colors）が」）、`DictionaryEntryList/index.tsx`（同じ）、`FacetIndex/index.tsx`（例「/dictionary/kanji/grade」）は、この変更で漢字から使われなくなった。それなのに、コメントが漢字を使い手や例に挙げている。3つとも T3-8 で消す予定の部品だが、それまでのあいだ、事実と違うコメントが残る（CLAUDE.md のツギハギの規則）。いまの使い手（四字熟語・伝統色）に合わせて直す。

### Minor-5: builder の文字サイズ 200% の確かめが、§12 の条件を測っていない

`tmp/cycle-316/t3-7/interact.mjs` は `html{font-size:32px !important}` を足して 200% としている。この方法では、`rem` で書いたメディアクエリ（`45rem`・`64rem`）が動かず、ブラウザの既定を大きくした来訪者の画面にならない（frontend-design の「ブラウザの既定の文字サイズを 32px にして描く」）。このレビューで `Page.setFontSizes` を使って測り直し、ページも要素も横に伸びないことを確かめたので、実装を直す必要は無い。Major-1 を直したあとの確かめでは、既定の文字サイズを変える方法で測る。
