# cycle-300 事故報告書2：アンチパターン集への記録方法がルールに反した（＋同種事故の全数調査）

本報告は、incident-1.md の整備の中で私が行った「アンチパターン集への発生記録の追記方法」がルールに反していた事実を記録し、是正し、**過去に同じ違反をしたサイクルを全数調査して集約する**。判断基準は constitution とルール群のみ。

## ルール上の定義

`.claude/rules/anti-patterns-directory.md`:

> **Do**: 同じアンチパターンを繰り返してしまった場合は `（cycle-XXX, XXXで実際に発生）` という部分に**サイクル番号のみを追記**する。このとき、詳細はサイクルドキュメントに記録する。
> **Don't**: 特定の状況に特化した具体的な事例を記録する。（具体的な事例はサイクルドキュメントに記録し、サイクル番号だけを書くのが正しい）
> **Do**: 一般化した説明として広く捉えられるように記録する。

## cycle-300 での該当（記録が示す事実）

incident-1.md の整備として、私は planning.md の AP-P31・AP-P34 の発生一覧に、番号だけでなく**その回の具体的な事例説明を本文へ書き込んだ**（AP-P31 へ「cycle-300 は時間軸前後比較を効果読みに使い…」、AP-P34 へ「cycle-300 は rebuild-plan §1(a) の…引用・増幅した＝『引く側』違反…」）。これは「サイクル番号のみを追記」に反し、「特定の状況に特化した具体的な事例を記録する」を禁じた Don't に真っ向から反する。既存の同項目はすべて番号のみで、逸脱は私の追記だけだった。→ **是正済み（下記）**。

## なぜルール上の失敗か（一般化された害）

アンチパターン集は「広く捉えられる一般化された説明」であることに価値がある（Do）。個別サイクルの事例説明を発生一覧に混ぜると、(1) チェックリストが具体事例で膨れて一般性が薄まり、次以降の PM が一項目ずつ声に出して確認する運用（CLAUDE.md）を妨げる、(2) 同じ事実がアンチパターン集とサイクルドキュメントに二重管理され、更新時に片方が陳腐化する。だからこそルールは「番号のみ・詳細はサイクル文書」と定めている。

## 是正（本セッションで実施）

1. planning.md の AP-P31・AP-P34 の発生一覧を、**サイクル番号のみ（`, 300`）**へ戻した。事例の詳細は incident-1.md に既に記録済みで、サイクル番号から辿れる（情報は失われない）。
2. 新しいアンチパターンやルールは新設しない——ルール（anti-patterns-directory.md）は既に存在し、違反は私の不遵守であって規約の不足ではない。守れていないルールを別ルールで上塗りするのは candidates.md が禁じる「帳尻合わせ」（類型C）に当たるため行わない。
3. **B-540 の優先度を P1 へ引き上げ**、スコープに再発防止の enforcement を加えた。ただし当初 incident-2 で私が挙げた「発生記録の丸括弧にサイクル番号以外の散文が混じっていないかを機械検査する」という具体案は**撤回する**——実ファイルに当てずに言い切った過剰主張だった。実測すると:
   - **過剰**: planning.md の丸括弧 102 個中、発生記録（「で実際に発生」）は 34 個で、残り ~68 個は正当な散文の括弧（`（例: …）`・`（→理由）`・`（調査のヒント）` 等）。「括弧＝番号のみ」の検査はこれらを全部弾き、**丸括弧を書けなくする**。
   - **過小**: 私の cycle-300 の違反は「…で実際に発生**。**cycle-300 は…」と発生記録の**外（後ろ）**に付けた。同じ位置には AP-WF23/24 の**正当なポインタ**（「うち … は docs/research/… 」）が入り、構文上は事例ナラティブと区別できない。さらに AP-P04 本文には既に事例参照 `（cycle-299: …）` が埋め込まれている。**一般化説明・例示・事例ナラティブの境界は意味の判断であり、正規表現の hard block では過不足なく強制できない。**
   - よって enforcement の設計は**未解決の設計課題**として B-540 に委ねる。方向性の候補は (i) 発生記録を機械可読な構造（AP→サイクル番号の配列）へ分離し、その構造だけを厳密検査する（自由文は意味層に残す）、(ii) 差分が `docs/anti-patterns/` に散文を追加したときに**警告（ブロックでなく）**を出し人手レビューを促す、(iii) AP 集を触る差分に限定した必須レビュー観点。どれで過不足なく止められるかは B-540 で設計・検証する（本報告では結論を出さない）。実際のクリーンアップと enforcement の設計・実装は教訓喪失を避け **B-540 の独立サイクルで計画＋レビューを通す**（cycle-257 方針踏襲）。

## 残る宿題

- **B-540（P1・次サイクル最優先候補）**: (a) `docs/anti-patterns/` 全体の規約違反（類型A〜D）を「手順→knowledge・具体事例→cycle-doc・発生記録→番号のみ」で是正、(b) 再発防止の enforcement を**設計から**行う（構造化検査／警告／レビュー観点のいずれが過不足なく効くかの設計・検証を含む。ナイーブな「括弧＝番号のみ」の hard block は上記の理由で不採用）。本報告の全数調査表を着手材料とする。
