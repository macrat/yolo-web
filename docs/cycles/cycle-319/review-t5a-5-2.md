## 指摘

### 1.（中）キーボードで問に着いたとき、問の見出しのリングが見出しの1行目の字の上端に重なる

問が替わると見出し（h2）がフォーカスを受け、`:focus-visible` で二重リングが出る（`outline` 3px・`outline-offset` −3px・内側の `box-shadow` 6px）。リングは箱の縁から内側 3px を占める。見出しは `data-text-box="inline"` で左右に 8px の余白を持つが、上下の余白を持たず、行間は `--leading-heading`（1.25）なので、字の箱の上端と字の上端のあいだがほとんど無い。

実測（本番ビルド、キーボードで「はじめる」を押した直後、`deviceScaleFactor: 3` で撮った）:

| 画面                    | 字の大きさ | 箱の上端から字の墨の上端まで（canvas の `actualBoundingBoxAscent` から算出） | リングの内側の端 |
| ----------------------- | ---------- | ---------------------------------------------------------------------------- | ---------------- |
| 320×550・375×550 の既定 | 17px       | 約 1px                                                                       | 3px              |
| 1280×800 の既定         | 33.28px    | 約 4〜5px                                                                    | 3px              |

- モバイル（17px）では、リングが字の上端の約 2px を覆う。320 のライトの character-personality Q2（「ネットで気になるアイテムを…」）では「気」の上の画がリングに食われて見え、375 のダークの kanji-level Q1（「「挨拶」の読みは？」）でも「挨」「拶」の上端がリングに接している。1280 でも「休」「覚」の上端がリングに触れ、あいだに地が無い。
- DESIGN.md §5 は、押せないがフォーカスを受ける見出しが字の箱を持つ理由を「フォーカスのリングが、並んだコントロールのリングと同じ位置に出る」としている。並んだ選択肢（`Button`）は上下に 8px の余白を持つのでリングと字のあいだに地が残るが、見出しには残らない。リングが字を覆うと、キーボードの来訪者が問ごとに最初に読む文が欠けて見え、「どこに着いたか」を示すはずのリングが読みを妨げる（§12 のフォーカスの見え方の趣旨からも外れる）。
- 来訪者の87%が mobile の面で、問が替わるたびに出る。キーボードで解く来訪者には毎問見える。
- 第1回の指摘1 の前（張り出しの無い形）でも上下は同じだったので、第1回で見落としていた。jsdom の試験は箱の形を見分けず、6章の条件5 も「リングが見出しの字の箱に出て、画面の中にある」だけを見るので、T5a-7 の測りでも拾われない（AP-I07。撮った像を拡大して見ないと出ない点は AP-WF05）。

直し方の案（確かめた形だけ）:

- 見出しの箱を、行の位置を変えずに上下へも広げる。たとえば `.questionText` に `padding-block: var(--space-8)` と `margin-block: calc(-1 * var(--space-8)) var(--space-8)` を持たせると、字・帯・一覧の位置と問のまとまりの高さ（t5a-measure.md の余り）は変わらず、リングの範囲だけが上下に 8px 広がって、並んだ選択肢のリングと同じく字とのあいだに地が残る。上に広がる 8px は帯の下の 24px に、下に広がる 8px は見出しの下の 16px に収まる。左右と同じ考え（余白と負の margin）を上下にも使う形になる。
- これは §5 の「字の箱」の定義（左右に 8px を足す）に上下を足すことになるので、PM が DESIGN.md §5 の文を直すか、問の見出しのリングの置き方として決めてから builder に渡す。ListStatus の件数の行（本文の行間 1.85）は字とリングのあいだに地があるので、同じ扱いにするかもそのとき決める。
- 直したあと、本番ビルドで 375・320・1280 の既定と 200% について、(a) h1・帯・見出し・一覧の左端と、帯の下端から一覧の上の罫線までの距離が直す前と同じであること、(b) 箱の上端・下端から字の墨までがリングの 3px より十分に大きいこと（数を記録）を測り、キーボードで着いた見出しを `deviceScaleFactor: 3` で撮って、ライトとダークで字とリングのあいだに地があることを目で確かめる。

### 2.（軽）SKILL.md に足した左端の項目が、§5 と食い違う所を持つ

足した項目「一覧の罫線・ボックスの線・プライマリボタンの地の縁が、同じ縦の線に並び、**一覧の行の字だけが**その内側 8px から始まるか」は、DESIGN.md §5 の「縁に地や線が見えるもの（プライマリボタン・入力欄・一覧の行の区切り）はその縁を揃え、中身は縁の内側 8px から始まる」と合わない。

- プライマリボタンの字も、入力欄の書いた字も、縁の内側 8px から始まる（`Button.module.css` の `.variantPrimary` の説明も「字は縁の内側 8px から始める」）。「一覧の行の字だけ」と書くと、この項目で見る人が、正しく組まれたプライマリボタンや入力欄の字を外れとして拾う。
- 入力欄が縁の見えるものの並びから落ちている。ボックスの中身は内側の余白（16px、45rem 未満で 8px）から始まるので、8px と一括りにもできない。
- 原因の文「`margin` の一括指定を書くと」は、左の余白を 0 にする指定（`margin-inline`・`margin-left` など）のどれでも同じことが起きるので、一括指定に限ると読み違える。

文の置き場（「目で確かめる」の1項目）と、確かめ方（字の Range の矩形と箱の左端を測る）は依頼の趣旨に合い、経緯の残りも無い。

直し方の案: §5 の言い方に揃え、たとえば「主見出し・小見出し・縁の見えないコントロールの最初の字と、縁の見えるもの（プライマリボタン・入力欄・一覧の行の区切り）の縁とボックスの線が同じ縦の線に並び、縁の見えるものの中身が縁の内側 8px から始まるか。字の箱を持つ要素に部品のクラスが左の margin を 0 にする指定（`margin` の一括指定を含む）を書くと、…」のように書き直す。
