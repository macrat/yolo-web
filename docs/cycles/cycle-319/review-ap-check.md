## 2. 補足事項にない外れ

補足事項の3件は、記録と合う。

- `sed -i` を `/dev/null` に向けた件: 03:31:25 の呼び出しで、置き換えの型はレビューの表の計画の行に当たり、出力は「sed: couldn't edit /dev/null: not a regular file」。回数は直後の Edit で直した。書いたとおり。
- T5a-6 の完了の条件の2度押しの件: review-t5a-6.md 指摘1・2 と合う。
- T5a-5 の像の見落とし: 見落としたこと自体は記録と合う。知覚と判断の書き方は上の AP-WF27。

ほかに、記録で裏付く次の外れが補足事項に無い。

1. 計画の初版の外部仕様と GA の数（AP-WF12・AP-WF09・planning.md の AP-P01）。上の表のとおり。計画のレビューが5回になった最初の原因で、次のサイクルの計画で同じ形（道具1つの失敗で「読めない」と書き、確かめていない前提でタスクを立てる）を避ける材料になる。
2. PM の通読が本体のコードに限られ、試験の差分を読まずにレビューへ回し、取り込んだ（AP-WF11）。計画に自分で書いた手順を守っていない。
3. 結果を見る前に、Edit とコミット、マージと木の削除と push を同じバッチに繋いだ（AP-WF29）。
4. PM がレビュー結果の要約に書いた「0」が、記録の限定（第1の組）を落とした（AP-WF09）。全体のレビュー第1回が捕まえ、直った。
5. 全体のレビュー第3回の直しの取り込み（7cf23c0e）は、担当の枝 57c2b3e2 の親が主の木の HEAD 79f078f5 そのもので fast-forward できたのに、`git merge --no-ff` でマージのコミットを作った（`.claude/rules/delegation.md` の「進められるなら fast-forward」）。ほかの3回（74e66341・728c8bd5・7ae55aa4）は主の木に PM のコミットが先にあり、どちらでもマージのコミットになる。T5a-5 の取り込みは `--no-edit` のマージのあと `git commit --amend` で題を付け替えた。review-final-4.md は 7cf23c0e を「PM の記録のコミット 79f078f5 が先にあるので、マージのコミットになる」と書くが、79f078f5 は担当の起点で、事実と合わない。害は余分なマージのコミット1つで、push 済みなので履歴は直さない。

確かめて、外れが無かったもの:

- 担当を起こす前のコミットと HEAD: 5人の builder のどれも、直前に `git status --short`（出力は空）と `git rev-parse HEAD` を別々の呼び出しで打ち、出た HEAD を依頼に写した。起こす前のコミットの終了の値（`rc=0`）も見ている。コミットが hook（backlog の行の長さ）に止められた2回は、結果を見て直してからコミットし直した。
- push の終了の値: この点検を頼むまでの19回の push はどれも `git push … 2>&1 | tail -n; echo "push_rc=${PIPESTATUS[0]}"` で、パイプの前の push の値を読み、すべて `push_rc=0` だった。
- 取り込みの後片付け: `git worktree remove` と `git branch -d` の終了の値を読み、`--force` 類は使っていない。いま `git worktree list` は主の木だけ、`worktree-*` の枝は0。
- キックオフ: `git merge origin/main` は浅い clone のため「unrelated histories」で止まったが、PM は `--unshallow` で取り直し、`git log HEAD..origin/main` が空であること（main に取り込むものが無い）を確かめた。
- 補足事項の3つ目の段落の事実: main への手順のコミットを作らない理由（このサイクルが `.claude/` で変えたのは `frontend-design` のスキル1つ）、ADR009 の次回確認日（`docs/ADR/open/2026-10-23-…`）は合う。

## 4. 候補と発生の一覧の案

足すかは PM が決める。

発生の一覧に 319 を足す案:

- workflow.md: AP-WF03・AP-WF05・AP-WF09・AP-WF11・AP-WF12・AP-WF27・AP-WF29・AP-WF41
- planning.md: AP-P01（確かめていない外部仕様の前提の上に、実機に頼る振り分けのタスクと危険の重みを置いた）
- implementation.md: AP-I01（builder の像にずれが出ていたが評価で拾わなかった）・AP-I07（補足事項の3つ目。jsdom の点の無い `click()` で着地の欠陥が見分けられなかった）
- candidates.md の AP-WF54 候補: 補足事項の1件目を発生に数えるなら N=3（cycle-316・318・319）。ファイルは変わらなかったが、置き換えの型はコミットに入るファイルの行に向けて組まれていた。N≥3 なので、`.claude/rules/anti-patterns-directory.md` のとおり本体に置くか、機械で止める（B-790 の hook）かを決める。止められる型なので、hook を先に決めるのが規則に合う

新しい候補の案:

- **道具が中身を返さなかったことを、資料そのものが読めないことと取り違えていないか。** 計画の初版は、WebFetch が bug の頁のログインの画面しか返さなかった1回で「入らないと読めない」と書き、別の取り方（`curl`・頁の裏の API）を試さずに、確かめていない前提でタスクを立てた。レビュアーは `curl -sS "https://issues.chromium.org/action/issues/41453122"` で本文を、`chromium.googlesource.com/…?format=TEXT` でソースを読めた。AP-P19・AP-WF12 は一次資料に当たることを求めるが、当たろうとして道具が失敗した所で止まる形を名指さない（N=1、cycle-319）。対症の案は、機械で止める形が無いので、取り方を `docs/knowledge/` に置くこと（issues.chromium.org と googlesource の読み方）と、「読めない」と書く前に2つ目の取り方を試すこと。

## 指摘と直し方の案

1. **（中）補足事項に、記録で裏付く外れが5つ欠けている**（上の2の1〜5）。直し方: 補足事項の「手順を外れたこと」に、それぞれ1〜2文で足す（何が・どのアンチパターンに当たり・どこで捕まり・害が何だったか）。レビュー記録の誤り（review-final-4.md の取り込みの理由）は、レビューの記録なので書き換えず、補足事項の5の文で正しい事実を書く。
2. **（軽〜中）補足事項の2つ目が、記録に無い知覚と判断を事実として書く（AP-WF27）**。直し方: 例えば「T5a-5 の取り込みの前に PM が見た像（1280 の知識クイズの答えたあとほか）に、問の見出しの字が 8px 右にずれた形が出ていたが、PM はそれを拾わずにレビューへ回した（当時の記録にはずれへの言及が無い）」とし、かぎ括弧の空きと判じた件は書かないか、「レビューを受けたあとの報告でそう述べた（当時の記録では裏付かない）」と地位を添える。教訓の文（違和感は計算値で確かめる）は、記録が支える形「像は左端の揃いを測って見る」などに合わせる。
3. **（中）AP-WF29 の再発**。直し方: 記録には上の1で足す。進め方として、Edit・Write・マージの呼び出しと、それを前提にするコミット・push・木の削除を同じバッチに入れない。cycle-318 に続く再発なので、`.claude/rules/anti-patterns-directory.md` のとおり機械で止められるか（例: PostToolUse の失敗のあとの同じバッチを見分けるのは難しいので、まず手で守るのか）を PM が決めて記録する。
4. **（中）AP-WF11 の通読が試験に届いていない**。直し方: 記録には上の1で足す。このサイクルの成果物は、T5a-6 の試験の欠けがレビューで直ったので、作り直しは要らない。次の取り込みから、計画に書いた「差分の全文」を試験を含めて読む。
5. **（軽）fast-forward できる取り込みを `--no-ff` にした**。直し方: 記録には上の1で足す。履歴は push 済みなので直さない。`-m` は fast-forward のときは使われないだけなので、`--no-ff` を付けずに `git merge <担当の枝> -m "…"` とすれば規則どおりになる。
6. **（軽）完了の処理の順**: `cycle-completion` の手順1（チェックリストの確かめと `completed_at`）より先に手順3・5へ進んでいる。チェックリストはまだチェックされておらず偽りは無いが、ゲートの項目は最後に走らせたのが全体のレビュー第4回（HEAD 7cf23c0e、reviewer）である。直し方: この点検の直しのあと、手順1を最初からやり直し、ゲートの5つを PM が主の木で自分で走らせて exit 0 を見てからチェックする（AP-WF23）。
7. **（軽）AP-WF03**。直し方: 記録は発生の一覧に 319 を足すかの判断だけでよい。次から、レビュアーの確かめた形を渡すときは、何を満たすか（字とリングのあいだに地を残す・行の位置と高さを変えない）を渡し、宣言の値とコメントの文は案として添えるに留める。
