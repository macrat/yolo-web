## 指摘と直し方の案

1. **（中）第1回の点検の完了の通知を待たずに進んだ（AP-WF04 の再発）が、補足事項に無い。** 直し方: 補足事項の「手順を外れたこと」に、記録の時刻で裏付く形で足す（ファイルが変わらなくなるのを待つループで進む時を決め、reviewer の完了の報告の前に途中の版の記録をコミットし builder を起こし報告した。reviewer はそのあと数を2か所直して完了した。害は数の2か所で、builder の成果には響いていない）。workflow.md の AP-WF04 の発生の一覧に 319 を足す（builder に担当の木で頼む）。次から、reviewer と担当の作業は完了の報告（SubagentHandback か task-notification）を受けてから次へ進み、ファイルの変わり方で代えない。届いた完了の報告は読んでから次の操作を決める。
2. **（中）「hook では組めない」が確かめていない断言で、機械で止めるかの判断を閉じている（AP-WF12・AP-WF27）。** 直し方: 補足事項の AP-WF29 の行を、記録で言えることに書き直す（例: 「hook で止められるか（`PostToolUseFailure` で失敗の印を書き、コミット・push・木の削除の `PreToolUse` で止める形など）はまだ確かめていない。確かめるまで手で守る」）。そのうえで、backlog に「AP-WF29 を hook で止められるか確かめ、組めるなら組む」項目を足す（B-790 と同じく hook の仕事で、7度目の再発なので急ぎの度合いを B-790 と並べて決める）。確かめた結果組めないと分かったなら、その根拠（資料の文・試した結果）を補足事項に書く。
3. **（軽）knowledge の googlesource の取り方に、ときどき 503 が返る落とし穴が無い。** 直し方: builder に担当の木で、googlesource の項目に「HTTP の状態を見て（`curl -w "%{http_code}"` など）、503 なら少し待って取り直す。そのまま `base64 -d` に流すと invalid input で空になる」を足させ、根拠に cycle-319 の第2回の点検で6回中2回 503 だったことを書く。
