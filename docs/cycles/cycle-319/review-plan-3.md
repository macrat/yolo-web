## 指摘

### 1. T5a-5 が直さないと通らない既存の試験と、T5a-6 が前提にする切り替わりの番号が、どちらのタスクにも書かれていない（中）

計画の T5a-5 の完了の条件は「既存の試験・型・lint・`format:check`・build が通る」で、触るファイルは t5a-design.md 7章の T5a-5 の行に従う。確かめると、次の2つが受け持ちの隙間に落ちる。

1. **`QuizContainer.reveal.test.tsx` は T5a-5 のタイマーで落ちるが、7章ではこのファイルは T5a-6 のものである。** この試験の `playToLevelEnd`（171〜192行）は、診断の最後の選択肢を押した直後に `level_end` が送られていることを確かめ、偽の時計を使わない。T5a-5 は最後の問でも 150ms 見せてから結果へ移す（4-3）ので、この試験の5つ（結果のボックスへの送りとフォーカス・登場の動き・ページの頭・追加の読みもの）は T5a-5 で落ちる。T5a-5 の builder は、T5a-6 のファイルを触ってよいかが分からないまま、試験を直すか、T5a-6 の受け持ち（結果への送りとフォーカス）を先に組み替えるかを迫られる（AP-WF13 の型）。あわせて、計画は結果への送りとフォーカスを T5a-6 に置いたが、T5a-5 の時点で今の `useEffect`（`QuizContainer.tsx` 77〜83行の `scrollIntoView` とフォーカス）を残すのか、`useLayoutEffect` に移すのかを書いていない。7章の T5a-5 の行は「切り替わりのあとのフォーカスを `useLayoutEffect` に集める形」と書くので、どちらにも読める。同じく、`Button.test.tsx`（96〜101行。`.button { … }` の塊に `min-height: 44px` があること）と `src/app/blog/[slug]/__tests__/page.test.tsx`（154〜160行）は `Button.module.css` の文字を読むので、箱の宣言の切り出し方によっては落ちる。どちらも7章の触るファイルに無い。
2. **切り替わりの番号を、どちらが入れるかが書かれていない。** 4-7 は、reducer が受け付けた更新ごとに1つ増える数を状態に持ち、マウントとやり直しを見分けると決める。4-9 の「2打目で語を選ばない」守りもこの番号を使う。reducer（`quizProgress.ts`）は T5a-5 のファイルで、T5a-6 の触るファイルに無い。一方、T5a-5 の完了の条件の「マウントのとき `body` のまま」は、番号が無くても段階（開始）を見るだけで通る。番号を入れずに T5a-5 が通ると、T5a-6 のやり直しの試験と secondPress の試験は、T5a-6 の触るファイルの外の `quizProgress.ts` とその試験を直すことになる。4-3 の試験6 も番号を試さない。

直し方の案（7章の分けを崩さない形）:

- T5a-5 の完了の条件に「reducer が、受け付けた更新ごとに1つ増える切り替わりの番号を持ち、捨てた更新では増えないことを `quizProgress.test.ts` で確かめる（4-7。T5a-6 のやり直しと 4-9 の守りが使う）」を足す。
- T5a-5 の項に「T5a-5 は結果への送りとフォーカスの今の形（`useEffect`）を変えない。150ms のタイマーで落ちる既存の試験（`QuizContainer.reveal.test.tsx` の `playToLevelEnd` など）は、偽の時計で 150ms 進める直しだけをし、確かめる中身は変えない。`Button.module.css` の文字を読む試験（`Button.test.tsx`・`blog/[slug]/__tests__/page.test.tsx`）が切り出しで落ちるなら、同じく確かめる中身を保って直す」と書く。逆に、結果への送りとフォーカスも T5a-5 で `useLayoutEffect` に移す形を採るなら、それを T5a-5 の受け持ちとして書き、T5a-6 の項から外す。どちらを採っても、7章の触るファイルの表から外れるファイルを計画に名指す。

### 2. 診断で答えたあと 150ms のあいだのフォーカス（押した行）を、どの試験も確かめない（軽い）

T5a-5 の完了の条件は「問のあいだのフォーカス」を3つ挙げる（マウントのとき `body`・次の問の見出し・知識クイズで答えたあと押した行）。4-7 の「範囲」にある「診断で答えたあとの押した行へのフォーカス（見せる 150ms のあいだ）」が入っていない。これは、押したボタンが字に替わって文書から外れたとき、フォーカスを `body` に落とさない仕組みそのもの（B-624 の「`body` に落ちない」の診断の側）である。4-3 の試験3（Enter の連打で答えが1件）は、フォーカスが `body` に落ちても Enter が何も起こさず答えは1件のままなので、空振りでも通り、この仕組みを確かめない。実ブラウザでは T5a-7 の条件5 が見るが、そこで見つかると T5a-5 に戻ることになる。PV の8割が集まる診断の、毎問のフォーカスである。

直し方の案: T5a-5 の列挙に「診断で答えたあと、150ms 進める前の `document.activeElement` が押した行（`li`）」を足す。列挙が4-7 の範囲のうち T5a-5 のものを尽くすように並べる。

### 3. B-624 の行に、Done へ移す条件が無い（軽い）

B-614 は「T5a-7の測りで確かめてDoneへ」、B-623 は「T5a-7の二度打ちの測りで0を確かめてDoneへ」と書くが、B-624 は「T5a-5(t5a-design.md 4-7)で入る」で止まり、いつ Done にするかが無い。T5a-5 の取り込みで Done にするのか、T5a-7 の条件5（キーボードで15本を解き切り、`BODY` のフレームが0）で確かめてからかが、次のサイクルの PM に分からない。また、B-624 の題の「読み上げが正誤と解説を飛ばす」を直すのは、押した行へのフォーカスと `aria-describedby`（T5a-5）だが、「次へ」が画面の下にあるときに見えるようにするのは知識クイズの答えたあとの送り（4-6。T5a-6）でもある。

直し方の案: B-624 の Notes を「T5a-5・T5a-6(t5a-design.md 4-6・4-7)で入り、T5a-7の条件5で確かめてDoneへ」のように、ほかの2行と同じ形にする。

### 4. 6章 条件9 の `grep` の範囲が書かれておらず、条件の「目で確かめる」が落ちている（軽い）

計画は条件9 を「`fadeIn` の規則と `@keyframes` が0」を `grep` で確かめる、と書く。いま `src/components/ResultBox/ResultBox.module.css` と `DataTable.module.css` も `@keyframes` を持つ（結果のボックスの登場の動きは解き終えた画面のもので、回答の画面ではない）。範囲を書かないと、`src/` や `src/components/` を洗った builder は0にできず、範囲を狭めた builder は理由を書かない。また、t5a-design.md 6章 条件9 は「目で確かめる」を含むが、計画の文から落ちている。

直し方の案: 「回答の画面の CSS（`QuestionCard.module.css`・`QuizContainer.module.css`）に `fadeIn` と `@keyframes` が0。撮った像で、帯の伸びのほかに動きが無いことを目で確かめる」と書く。

### 5. T5a が split-plan.md 7 の見込み「1〜2サイクル」を超えて3つ目のサイクルに入ることが、計画にも申し送りの行にも無い（軽い）

split-plan.md 7 の表の2行目は T5a の見込みを「1〜2」とし、各サイクルのキックオフで見積もり直すと書く。T5a は cycle-318・319 に続き、T5a-4・T5a-7 で3つ目のサイクルに入る。計画は分ける理由を書いているが、見込みを超えることと、表の後ろの行（T5-30・T5-25c・T6-6 など T5a を待つもの）の始まりが1サイクルずつ遅れることを書いていない。次のサイクルのキックオフが見積もり直すときの材料になる。

直し方の案: 「検討した他の選択肢」の1つ目の終わりか、申し送りの行に「T5a は見込みの1〜2を超えて3サイクルになる。T5a を待つ行（split-plan.md 7 の後ろの依存）は1サイクルずつ後ろへずれる」と書く。
