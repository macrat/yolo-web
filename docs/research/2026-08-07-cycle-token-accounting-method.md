# サイクル別トークン・時間集計の数え方

このディレクトリのスクリプトが「何を、どう数えているか」を書き下したもの。
**同じ数字を後から誰でも再現できること**が目的。恣意的な選択をした箇所は「判断」と明記した。

## ファイル構成

| ファイル       | 役割                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| `common.py`    | 共通処理。サイクル定義の読み込み、JSONL 走査、サイクル割り当て、稼働時間計算                            |
| `build_map.py` | セッション → サイクル の対応表を作る。`out/session_cycle_map.json` と `out/session_cycle_map.md` を出力 |
| `aggregate.py` | 対応表を使ってサイクル別に集計。`out/cycle_stats.json` を出力し、標準出力に表を出す                     |
| `verify.py`    | 独立経路での検算（ファイル本数・行数・割り当て・重複排除の効果・usage 欠落率）                          |

実行順:

```bash
python3 scripts/cycle-stats/build_map.py      # 全ログを走査（約 470MB / 数分かからず終わる）
python3 scripts/cycle-stats/aggregate.py cycle-301 cycle-302
python3 scripts/cycle-stats/verify.py
```

`aggregate.py` は引数なしで全サイクル、`--json` で JSON 出力。

## 入力データ

- メインセッション: `/home/node/.claude/projects/-mnt-data-yolo-web/*.jsonl`（**33本**）
- サブエージェント: `/home/node/.claude/projects/-mnt-data-yolo-web/<session-id>/subagents/*.jsonl`（**577本**）
  - 親セッションのディレクトリ配下にあるので、親の `.jsonl` からディレクトリ名を導いて辿る。
  - 孤児（親の `.jsonl` が無いサブエージェント）は **0本**（`verify.py` の項目2で確認）。
- サイクル期間: `docs/cycles/cycle-*/index.md`（古いサイクルは `docs/cycles/cycle-*.md`）の
  frontmatter `started_at` / `completed_at`。**ハードコードせず毎回ここから読む**ので、
  新しいサイクルが増えても自動的に対象になる。

## 規則

### R1. タイムゾーン

セッションログの `timestamp` は UTC（末尾 `Z`）、サイクル frontmatter は `+0900`。
**両方を UTC epoch 秒に変換してから比較する。** 表示は JST（+09:00）。

### R2. レコードの単位

JSONL の 1行 = 1レコード。空行は数えない。JSON パースに失敗した行は `parse_failures` に
計上する（実測では **0件**）。

### R3. サイクルへの割り当て（レコード単位）

各レコードを、その `timestamp` によって次の3つのいずれかに振り分ける。

1. `started_at <= timestamp <= completed_at` を満たすサイクルがあれば、そのサイクル（**閉区間**）
2. どのサイクル期間にも入らなければ `__UNASSIGNED__`（＝サイクル間の作業）
3. `timestamp` フィールドを持たなければ `__NO_TIMESTAMP__`

**セッション単位ではなくレコード単位で振り分ける**ので、1セッションが複数サイクルに跨っても
正しく分かれる。**サブエージェントのレコードも同じ規則で、それ自身の timestamp によって
振り分ける**（親セッションの所属を機械的に継承させると、親が跨いだ場合に誤る）。
対応表には親セッション ID も記録してある。

> **判断 (a)**: 区間は**閉区間**（両端を含む）とした。境界ぴったりのレコードは1件あるかないかで、
> どちらに倒しても結果はほぼ変わらない。
>
> **判断 (b)**: サイクル期間が重なる場合は **`started_at` がより遅いサイクル**を採用する。
> 実測で重なっていたのは `cycle-12`/`cycle-13` と `cycle-194`/`cycle-195` の2組のみで、
> いずれも 2026-02〜05 のもの。セッションログは 2026-07-03 以降しか無いので影響はない。
>
> **判断 (c)**: `completed_at < started_at` の壊れた frontmatter（実測で `cycle-19` の1件のみ）は
> 割り当て対象から除外する。これも 2026-02 のものでログ範囲外。

### R4. トークンの合計 ★最重要

**Claude Code は、1回の API 応答を content ブロックごとに複数の assistant レコードとして
書き出す。それらは同じ `message.id` を持ち、`usage` オブジェクトはどのレコードにも
まったく同じ値が繰り返し書かれている。**

例（実測、`7c702374` セッション）:

```
id msg_011CdHwcXSLc54tMc8ds5GiG  レコード4件
  ts 23:12:13  out 354  in 2  cc 29509  cr 0  blocks [thinking]
  ts 23:12:14  out 354  in 2  cc 29509  cr 0  blocks [text]
  ts 23:12:16  out 354  in 2  cc 29509  cr 0  blocks [tool_use Bash]
  ts 23:12:16  out 354  in 2  cc 29509  cr 0  blocks [tool_use Read]
```

したがって **`usage` は `message.id` 単位で1回だけ加算する**（同一ファイル内で id を記録し、
2回目以降はスキップ）。レコード単位で素朴に足すと **2.2〜3.5倍** に膨れる
（`verify.py` の項目5で実測値を出している）。

そのサイクル配分は、**その `message.id` を最初に見たレコードの timestamp** で決まる
（同一 API 応答のレコードは数秒以内なので、サイクル境界を跨ぐことは事実上ない）。

集計する4フィールドは**それぞれ別に合計し、決して足し合わせない**:

- `input_tokens`
- `output_tokens`
- `cache_creation_input_tokens`
- `cache_read_input_tokens`

`server_tool_use` / `cache_creation`（内訳）/ `service_tier` などは無視している。

重複排除のスコープは**ファイル単位**。メインセッション同士、およびメインとサブエージェントの
間で `message.id` が重複することは無い（実測で確認: main↔main の重複 0件、
サブエージェント 18,615 個の id と親メインの id の重複 0件）ので、二重計上は起きない。

### R5. メッセージ数

- `user_messages`: `type == "user"` のレコード数（**重複排除しない**。
  ツール結果も `type: "user"` として記録されるので、これは「ユーザーの発言数」ではなく
  「user ロールのレコード数」である点に注意）。
- `assistant_responses`: **`message.id` で重複排除した assistant 応答の数**。
  「何回 API を呼んだか」に相当する。トークンの加算単位と一致する。
- `assistant_records`: 重複排除前の assistant レコード数（参考値）。

> **判断 (d)**: 「メッセージ数」として代表させるなら `assistant_responses` を使うのが妥当。
> `user_messages` はツール結果を含むので実態より大きい。

### R6. ツール呼び出し数

assistant レコードの `message.content` にある `type == "tool_use"` ブロックを数える。
同じ API 応答が複数レコードに分かれていても、各レコードが持つブロックは**異なる**ので、
すべてのレコードを走査する。ただし念のためブロックの `id` で重複排除している。

### R7. サブエージェント起動数

`tool_use` のうち `name` が `Agent` または `Task` のものを数える。

検算: cycle-301 は起動 62回 / サブエージェントファイル 62本、
cycle-302 は起動 69回（メイン 46 + サブエージェントからの孫起動 23）/ ファイル 69本 で一致する。

### R8. 経過時間

2種類を別々に出す。

1. **実時間 (`wall_clock_seconds`)**: frontmatter の `completed_at` − `started_at`。
   休憩も夜間も含んだ、カレンダー上の経過。

2. **稼働時間 (`active_seconds_*`)**: そのサイクルに属するレコードの timestamp を
   昇順に並べ、**隣り合うレコードの間隔が `IDLE_GAP_SEC` 以下ならその間隔を加算し、
   超えたら 0 として加算しない**（＝無活動の空白とみなして切る）。

   > **判断 (e)**: `IDLE_GAP_SEC = 300 秒（5分）` とした。根拠は
   > 「LLM の1ターンが5分以上かかることは稀で、5分以上空いていれば
   > 人間の待ち・中断とみなしてよい」という経験則であって、実測から導いた値ではない。
   > `common.py` の定数を変えれば追随する。**この値を変えると稼働時間は大きく変わるので、
   > 数字を引用するときは必ず閾値を併記すること。**

   2つの数え方を出している:
   - `active_seconds_merged`: **メイン + サブエージェントのレコードを1本のタイムラインに
     合流させて**から計算。サブエージェントは並列に走るので、単純に足すと実時間を超える。
     合流させることで二重計上を避け、「システム全体が動いていた時間」の目安になる。
   - `active_seconds_main_only`: メインセッションのレコードだけで計算。
     「PM 本体が動いていた時間」の目安。サブエージェント待ちの間はメインのレコードが
     空くので、`merged` より必ず小さくなる。

   > **判断 (f)**: 「実際に動いていた時間」の代表値としては `active_seconds_merged` を推す。

### R9. 取りこぼしの検算

`aggregate.py` は毎回次の恒等式を確認して `一致: OK / NG` を出す。

```
サイクルに割り当てられたレコード
  + どのサイクルにも属さないレコード (__UNASSIGNED__)
  + timestamp を持たないレコード (__NO_TIMESTAMP__)
  = 全ファイルの全レコード数
```

### R10. `usage` の欠落

`usage` を持つのは `type == "assistant"` のレコードだけ。
実測（全 110,007 レコード）:

| type                  |   件数 | usage 有 |   割合 |
| --------------------- | -----: | -------: | -----: |
| assistant             | 58,389 |   58,389 | 53.08% |
| user                  | 31,545 |        0 | 28.68% |
| attachment            | 12,148 |        0 | 11.04% |
| last-prompt           |  2,673 |        0 |  2.43% |
| queue-operation       |  1,887 |        0 |  1.72% |
| bridge-session        |    704 |        0 |  0.64% |
| mode                  |    696 |        0 |  0.63% |
| permission-mode       |    696 |        0 |  0.63% |
| ai-title              |    674 |        0 |  0.61% |
| system                |    409 |        0 |  0.37% |
| file-history-snapshot |    167 |        0 |  0.15% |
| file-history-delta    |     18 |        0 |  0.02% |
| progress              |      1 |        0 |  0.00% |

**`usage` を持たないレコード: 51,618 / 110,007 = 46.92%**。
**assistant レコードで `usage` を欠くものは 0件**（つまり取りこぼしは無い）。

`timestamp` を持たないのは `last-prompt` 型のみ（実測 5,610件、全体の約 5.1%）。
これは UI 用のキャッシュレコードで `usage` も持たないため、トークン集計には影響しない。

## 既知の注意点

- **ログは追記中**。現在アクティブなセッション（`a0ac882e`）は実行のたびに行数が増える。
  完了済みサイクル（`completed_at` が過去）の数字は安定しているが、
  「全レコード数」は実行タイミングで数行ずれる。
- **`docs/cycles` の frontmatter を正とする**。セッションログ側に「このサイクルの作業だ」と
  書かれた印は無いので、時刻でしか紐づけられない。参考として
  「セッション内に `cycle-XXX` という文字列が何回出るか」も対応表に記録してあるが、
  過去サイクルへの言及が大量に混ざるため（例: あるセッションで `cycle-284` が 1,199回）、
  **単独では所属判定に使えない**。時刻ベースの判定の裏取りとしてのみ見ること。
