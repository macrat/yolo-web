- 起票日 / 出荷日: 2026-09-14 ／ **未出荷**（cycle-313 の作業ブランチ `claude/amazing-goodall-2ttqs7` にある。`main` には無い）
- 決定・仮説:
  - **決定**: ブログ一覧6ルート（`/blog`・`/blog/page/*`・`/blog/category/*`・同ページ送り・`/blog/tag/*`・同ページ送り）の記事リストを、静的HTMLに載る形に戻す。一覧全体を包んでいた fallback 無しの `<Suspense>` をやめ、`useSearchParams` の読み取りを葉まで下ろし、キーワードの無い一覧はサーバーで確定させる（`src/blog/_components/BlogListView.tsx` の Suspense には、同じ `BlogListPanel` を `keyword=""` で描いた fallback を渡す）。
  - **来訪者価値の仮説**: 一覧がHTMLに載れば、(1) JS が無効・失敗・到着前の来訪者にも記事が見える、(2) **クローラが一覧面から記事へたどれる経路が戻り、記事の発見と再クロールが増える**。
  - **賭けの中身は「直すかどうか」ではない**。欠陥の是正に異論の余地は無い。賭けているのは **(2) の効き幅**である——この4か月、`sitemap.xml` は公開86記事の全URLを載せ続けており（実測）、記事ページ自身も関連記事リンクを静的HTMLに持っていた（実測で4本）。つまり切れていたのは**冗長経路の一本**であって、発見経路が全滅していたわけではない。**内部リンクが sitemap の上にどれだけ積み増すのかは、まだ誰も測っていない。**
- 根拠:
  - 欠陥の実測と起点: [cycle-313/measurements.md §8](../../../cycles/cycle-313/measurements.md#8-ブログ一覧が静的htmlに載らなくなった起点)——本番 `/blog` の `<a>` は25個すべてがヘッダとフッタで、記事リンクは**0本**。起点は `d790b08f`（2026-05-07・cycle-183 の一覧移行でキーワード検索を足した際）で、測定日まで**4か月と1週間**。欠陥は一覧6ルートに限られ、`/tools`（36本）・`/dictionary`（4本）は健全。
  - 原因と是正方針: [cycle-313/index.md T7](../../../cycles/cycle-313/index.md#t7-ブログ一覧を静的htmlに載せる)。prerender されたルートで `useSearchParams` を呼ぶと、最も近い `Suspense` 境界までがクライアント描画へ退避する（Next.js 公式仕様）。境界が一覧全体を包み fallback が空だったため、静的HTMLには何も入らなかった。
  - 是正の確認: [cycle-313/measurements.md §10](../../../cycles/cycle-313/measurements.md#10-実ビルドでの復旧の確認)——`/blog` の記事リンクは 0本 → **12本**。記事リンクが0件の一覧ページは**0件**——全数走査したのは T7 完了時点の**59枚**で、タグページ追加後の67枚は回帰テストが毎ビルド検査する（総数の内訳は §8）。見た目の前後比較は [§9](../../../cycles/cycle-313/measurements.md#9-見た目の確認)。
  - 出荷の経路: [cycle-313/measurements.md §13](../../../cycles/cycle-313/measurements.md#13-出荷の経路)——`deploy.yml` は名前に反してデプロイせず、公開はホスティング側のリポジトリ連携で行われる。**届くかどうかは `main` にマージされたかだけで決まる。**
  - 再発の歯止め: `src/__tests__/blog-list-static-html.test.ts`（ビルド生成物を読み、一覧系の全ページに記事リンクがあることを毎ビルド検査する）。
- 観測手段と評価窓 / 撤退基準:
  - **起点は出荷日**（`main` マージ日）であり、起票日ではない。**未出荷のまま窓を数え始めないこと。**
  - **計器: Search Console**（BigQuery `searchconsole.searchdata_url_impression`）。数値の基準を置ける唯一の外部母集団で、反応は約3ヶ月遅れる（`docs/ADR/README.md`「観測の規律」）。
  - **主指標**: 表示が発生した**記事URLの異なり数**（週次）。一覧面の増減に引きずられず、「何本の記事が検索に出ているか」を直接見る。副指標: 一覧系URLの表示・クリック（一覧自身が中身を持った効果）、ブログ全体の表示・クリック・平均順位（`SUM(sum_position)/SUM(impressions) + 1`）。
  - **基線**: 出荷直前28日。**凍結値ではなく、出荷後と同じ日に同じ成熟度で取り直して比較する**（SC はバックフィル漂流があり、凍結値と再集計値がずれる——ADR001 の +2週の読みで実証済み）。
  - **窓**: 読み始め＝出荷+2週（方向のみ）、結論＝出荷+3ヶ月。時間軸の前後は方向読みに留め、因果を断定しない（双方向ガード）。
  - **交絡（同時に出荷される）**: 同サイクルは frontmatter の復元（タグ8記事・関連ツール4記事）と、全タグへのタグページ追加（8種・一覧系ルート59→67枚）を同時に出す。ただし**新設8タグはいずれも掲載2本以下で `noindex` のため `sitemap.xml` のタグURLは23件で不変**（[§14](../../../cycles/cycle-313/measurements.md#14-タグページを持たないタグが読者から隠れていた)）。**記事URLの増減は無い**（執筆した2本は取り下げた）ので、主指標を記事URLの異なり数に置けば交絡は母数の変化を伴わない。**タグ面の増減をこの ADR の効果に数えないこと。**
  - **GA4**: organic のブログ着地は補助に留め、単独の根拠にしない（小n・計測欠落）。
  - **撤退基準は置かない。** これは仮説の検証ではなく既知の欠陥の是正であり、「効かなければ戻す」という選択肢が存在しない——JS 無効の来訪者に一覧が空で届くこと自体が欠陥だからである。代わりに**逆行トリップワイヤ**を置く: 出荷+4週で、記事URLの異なり数または一覧系URLの表示が基線の50%を割ったら、是正が別の退行（`robots` / `canonical` / ページ送りリンク）を連れてきていないかを生成HTMLで検分する。
  - **この記録を閉じる条件**: 出荷+3ヶ月の窓を読んだ時点で「結果・学び」を書き、**adopted へ移す**（負けでも撤回対象が無いため expired にはならない）。
- **結果がどちらに転んでも使い道がある**（これが残す理由である）:
  - **上がった場合**——sitemap が全記事を載せていてもなお内部リンクが効くことの実測になる。トップページが記事へ直リンクを持たない（実測: `/` からの `/blog/<slug>` リンクは0本。`/blog` と5カテゴリ一覧へのリンクだけ）現状は、次に投資すべき面がそこにあることを意味する。
  - **動かなかった場合**——この規模のサイトでは sitemap だけで発見は足りており、**「内部リンクを増やす」施策を検索の利得として見積もってはならない**、という値付けの根拠になる。同時に、この欠陥が4か月与えた損害は検索ではなく**JS 無しの来訪者が空の一覧を見ていたこと**に確定し、同種の欠陥の優先度は UX の側で判断することになる。
  - **どちらでもない中間（読み取り不能）でも使い道がある**——出荷日が確定して記録に残るので、以降 SC を読む他の観測（ADR001 など）は「一覧6ルートの中身が空→12件へ変わった段差」を交絡として織り込める。**この段差を知らずに読むと、ブログ面の変化を無関係な原因に帰属させる。**

  3. **出荷済みだったら**、この3つを順にやる:
     - **出荷日を確定して経過記録に書く**: `git fetch origin && git log --date=iso --format='%ad %h %s' --ancestry-path 54ad8abb..origin/main | tail -1`（`54ad8abb` が T7 の是正コミット。これを `main` に取り込んだ最初のコミットの日付が出荷日）。本番の反映はその後なので、`curl` で確認した日も併記する。
     - **基線を取る**: 出荷日の前日から遡る28日で、下のクエリを走らせて結果を経過記録に貼る。出荷後の読みでも**同じクエリを同じ日に**走らせて突き合わせる（凍結値と比べない）。
     - **ディレクトリを「出荷日+2週」へリネームする**（読み始め）。結論は出荷日+3ヶ月。
  4. **基線・観測の共通クエリ**（`npx tsx .claude/skills/analyze-bigquery/scripts/query.ts "<SQL>"` で実行。`<開始>` `<終了>` は `YYYY-MM-DD`）:

     ```sql
     SELECT
       CASE
         WHEN REGEXP_CONTAINS(url, r'/blog/(page|tag|category)/') OR REGEXP_CONTAINS(url, r'/blog/?$')
           THEN 'listing'
         ELSE 'article'
       END AS surface,
       COUNT(DISTINCT url) AS urls,
       SUM(impressions) AS impressions,
       SUM(clicks) AS clicks,
       ROUND(SUM(sum_position) / SUM(impressions) + 1, 2) AS avg_position
     FROM `searchconsole.searchdata_url_impression`
     WHERE data_date BETWEEN '<開始>' AND '<終了>'
       AND REGEXP_CONTAINS(url, r'/blog')
     GROUP BY surface
     ```

     `surface = 'article'` の `urls` が主指標。**出荷時点の公開記事は88本**なので、この値を88で割れば「検索に出ている記事の割合」になる。平均順位の `+ 1` を落とさないこと（`docs/knowledge/search-console-bigquery.md`）。

## 失効理由（2026-09-14・PM の全責任における無効判定）

**1. 賭けになっていない。** 本文が「撤退基準は置かない」と明記しており、結果に懸かる判断が存在しない。
`docs/ADR/README.md` は ADR を「重大な意思決定」と「賭けて観測するもの」の記録と定めている。
本件はそのどちらでもなく、**既知のバグの修正**である。バグの修正に賭けの要素は無い。

**2. 主指標が読めない。** 効き幅を測ると称したが、`sitemap.xml` は4か月にわたり公開全記事の URL を載せ続け、
記事ページ自身も関連記事リンクを静的HTMLに持っていた（いずれも実測）。切れていたのは**冗長経路の一本**である。
そこへ同サイクルのタグページ8種の追加が同時に乗り、Search Console の反応は約3ヶ月遅れる。
この設計で内部リンクの寄与を分離して読み取ることはできない。

**3. 判断の中身は既に別の場所にある。** 是正の設計・一次資料の引用・検討した他の選択肢は

`docs/ADR/README.md` の「結果がどう出ても使い道のない記録は残さない（記録は目的でなく手段）」に該当する。
