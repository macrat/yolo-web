# サイクル完了手順

サイクルの全タスクが完了したら、以下の手順を順番に実行してください。

## 1. 実装完了確認

サイクルドキュメントに記載されたチェックリストがすべて完了していることを確認してください。
1つでも未完了の項目がある場合は、サイクルを完了させてはいけません。すべての項目を完了させてから完了手続きをやりなおしてください。

あわせて、サイクルドキュメントの「## レビュー結果」セクションが、各レビュー（計画・各タスク・ブログ）の指摘内容と対応で埋まっていることを確認してください（テンプレートのプレースホルダのままにしないこと）。後から「すべての指摘に対応したか」を検証できるトレーサビリティのために必須です。

サイクルドキュメントに `<!-- pause-cycle: ... -->` マーカー（中断記録）が残っている場合は、中断理由が解消されていることを確認したうえでマーカーを削除してください。理由が解消されていないなら、サイクルを完了させてはいけません。

問題なければ、 `completed_at` を !`date +"%Y-%m-%dT%H:%M:%S%z"` で更新してください。

## 2. ブログ記事確認

以下の条件に該当する場合、新しいブログ記事が作成されていることを確認してください。

1. サイトの来訪者（読者）が興味を持ちそうな変更を行った場合（新しいコンテンツの追加や既存コンテンツの変更など。想定読者はその都度推論する——ターゲット定義の仕組みは cycle-278 で廃止）
2. このサイクル内で調査または実装した内容が、ターゲットユーザーのいずれかにとって有益な情報である場合（SEO・サイト製作・マーケティングに関する調査や複雑な実装を行った場合など）

まだ作成されていなければ、blog-writerエージェントにテーマを渡して執筆させ、レビューしてください。
このとき、読者は誰で、どんな情報を求めているか、どんな情報には興味がないかをよく検討してください。
完了したら、この手順を最初からやりなおしてください。

ブログはターゲットユーザーにとって有益な情報になっている必要があります。
もし読者にとって分かりにくかったり、価値が薄い内容になってしまっているなら、全面的な書き直しも辞さない覚悟で記事を修正してください。
修正を行った場合はこの手順を最初からやりなおしてください。

また、「今後の展望」を書いた場合は、同じ内容が backlog.md にも記載されていることを確認してください。
もし記載されていないものがあれば、必ず記載してください。

## 3. キャリーオーバー項目の整理

サイクルドキュメントにキャリーオーバー項目がある場合は、内容を整理して /docs/backlog.md に登録してください。

## 4. ADRの記録と更新

`docs/ADR/README.md` の運用に従い、以下を確認してください。

1. **記録漏れの確認**: このサイクルで (a) 重大な意思決定（コンセプト・アーキテクチャ・戦略・大きな方針転換）、(b) 出荷した賭け（新コンテンツ・実験枠・効果を観測すべき変更）があったのに ADR に記録されていないものはありませんか？ あれば `docs/ADR/open/` に起票してください（次回確認日を先頭に付ける・「次回確認時にやること」を必ず書く）。
2. **既存 ADR の更新**: このサイクルで観測・進展があった ADR には経過を追記し、ディレクトリ名を次の確認日へリネームしてください。決着したものは結果・学びを記入して `docs/ADR/adopted/`（確定）または `docs/ADR/expired/`（失効）へ移動してください。
3. **失効の処理**: このサイクルの決定が過去の ADR を覆した場合は、旧 ADR を `docs/ADR/expired/` へ移し、双方の index.md に相互参照（「ADR◯◯◯により失効」／「ADR◯◯◯を覆す」）を書いてください。

## 5. ワークフローのアンチパターンチェック

今回のサイクルディレクトリ全体（`index.md` と補助ファイル）と `docs/anti-patterns/workflow.md` をreviewerに読ませ、アンチパターンに該当する問題がなかったかをチェックさせてください。

reviewerが問題を指摘した場合は、関連する作業をやりなおしてください。このとき、ドキュメントだけを書き換えて帳尻を合わせるのではなく、アンチパターンによって引き起こされたプロダクトの問題が存在しないかを入念に調べて解消するようにしてください。
すべての問題が解消されたら、この完了手続きを最初からやりなおしてください。

## 6. 最後のフォーマット

コミット前に、最終のフォーマットを行ってください。

```bash
npm run format
```

## 7. コミットとプッシュ

コミットの前に、担当の木が片付いていることを確かめてください。動いている担当が無いこと、取り込むと決めた担当の枝がすべて作業ブランチにマージされていること、`git worktree list` に主の木しか出ないことを確かめます。担当の木が残っていれば、`.claude/rules/delegation.md` のとおり、取り込む枝は `git merge` で取り込んでから、取り込まない枝はそのまま、`git worktree remove` で木を消します。担当の木は `.gitignore` で外れているので、このあとの `git add .` は主の木の変更だけを載せます。

主の木のすべての変更を、そのサイクルが進むブランチにコミットしてプッシュしてください。プッシュするのは作業ブランチだけで、担当の枝はプッシュしません。

- **main**: プッシュすると、サイクルの成果が本番にデプロイされます。
- **統合のブランチ**（来訪者に途中の状態を見せられない変更を、複数のサイクルに分けて進めるブランチ）: 本番は main だけからデプロイされるので、プッシュしても出荷されません。CI は、`.github/workflows/deploy.yml` の `on.push.branches` に統合のブランチの名前を入れておくことで、プッシュのたびに走ります。
  - 変更を統合のブランチで続けると決めたサイクルは、完了のコミットで `/docs/backlog.md` のその項目を Active から Queued に戻し、統合のブランチの名前とそこで続けていることを書いて、統合のブランチの名前でプッシュします。続けて、`origin/main` の上に手順のコミットを作って main にプッシュし、main を統合のブランチにマージしてプッシュします。手順のコミットに入れるのは、main から始まる次のセッションに要るものだけです。1つは、そのセッションが main から統合のブランチへたどり着き、そこで CI が走るのに要るもので、`/docs/backlog.md` はその項目の行だけを完了のコミットと同じ行にし、`deploy.yml` の `on.push.branches` に統合のブランチの名前を足し、統合のブランチを扱う手順を書いた `cycle-kickoff`・`cycle-completion` のスキルを完了のコミットと同じ中身にします。もう1つは、セッションの初めに読み込まれるもの（`paths` の無い `.claude/rules/` の規則・CLAUDE.md など）のうち、そのサイクルが変えたものです。これらはセッションを始めた木から読み込まれ、統合のブランチに移るのはセッションが始まったあとなので、main に無いと、統合のブランチで進むサイクルにも読み込まれません。これらも完了のコミットと同じ中身にします。完了のコミットと同じ中身にするものは、main の木でも正しい（統合のブランチにしか無い hook・ファイル・文書の節を前提にしない）ことを、`git show origin/main:<パス>` と `git cat-file -e origin/main:<パス>` で確かめてから入れます。手順のコミットに入れるのはここに挙げたものだけで、ほかの道具と `/docs/anti-patterns/`・`/docs/knowledge/` は入れません（一部だけを入れると、案内が main に無い節を指す、候補から消した項目が本体に無い、といった食い違いが出ます）。main は古い道具とアンチパターンと知見の一貫した形のまま保たれ、新しいものは最後のサイクルのマージでまとめて入ります。そのあいだ main の上で動く本番の急ぎの不具合を直すサイクルは、`cycle-kickoff` の手順1のとおり、統合のブランチの新しい道具とアンチパターンと知見を読んでから進み、レビューと手順5のチェックも統合のブランチのアンチパターン集で行います。手順のコミットを作るときは、main にあるファイルは Edit で変更を当て、main に無いファイル（そのサイクルが新しく作った規則など）は Write で完了のコミットと同じ中身に作り、入れると決めたパスだけを `git add -- <パス>` で名指して載せ（`git add .` は使いません）、`git diff <完了のコミット> -- <完了のコミットと同じ中身にしたパス>` が何も出さないことを確かめます。コミットしたら、push の前に、`git status --short` が何も出さないことと、`git diff --name-only origin/main` に出るパスが手順のコミットに入れると決めたものだけであることを確かめます。依存を入れ直したときの `package-lock.json` の書き換えのように、決めていないものが混ざったまま main にプッシュすると、来訪者に見える変更を含まないはずの手順のコミットが本番を変えます。完了のコミットの `deploy.yml` にはまだ統合のブランチの名前が無いので、統合のブランチの CI はこのマージのコミットで初めて走ります。手順8では、main と統合のブランチの両方で CI を確かめます。次のサイクルは main から始まり、`cycle-kickoff` の手順1でそのブランチに移ります。
  - そのあいだのサイクル（`cycle-kickoff` の手順1で統合のブランチに移り、手順4でその項目を Queued から Active に移して始めたサイクル）は、完了のコミットでその項目を Queued の同じ行に戻し、統合のブランチの名前でプッシュします。main の行と統合のブランチの行が同じまま保たれ、次のキックオフも手順4で Queued から選べます。main への手順のコミットは、そのサイクルがセッションの初めに読み込まれるものか、統合のブランチを扱う2つのスキルを変えたときにだけ作ります。変えたものを上と同じ確かめをして完了のコミットと同じ中身にし、上と同じく push の前にコミットに入ったパスを確かめて main にプッシュしてから、main を統合のブランチにマージしてプッシュし、手順8で両方の CI を確かめます。
  - その変更の最後のサイクルは、`deploy.yml` の `on.push.branches` と `/docs/backlog.md` の項目から統合のブランチの名前を外して完了のコミットを作り、`git fetch origin main` と `git merge origin/main` で main を統合のブランチにマージしてから、`git push origin HEAD:main` で main にプッシュして出荷します。手順8で出荷の CI を確かめたあと、`git push origin --delete <統合のブランチ>` で統合のブランチを消します（残すと、後のセッションがブランチの一覧から、使い終えたものか進行中のものかを見分けられません）。

必ずすべてのファイルをコミットしてワークスペースをクリーンな状態にしてからプッシュしてください。
ただし、作業中の一時ファイルや誤って作成されたでファイルがあれば削除してからコミットしてください。

```bash
git add .
git commit -m "<サイクルの成果>"
git push origin HEAD:<そのサイクルが進むブランチ>
```

push時にはフック（`.claude/hooks/pre-push-check.sh`）がフルスイート（format:check / lint / typecheck / test / build）を自動で再実行します。数分かかりますが、失敗した場合は必ず修正してから再度pushしてください。フックはいまの作業ツリーと `node_modules`・`.next` で検査するので、別のブランチへ移ってプッシュするとき（統合のブランチの手順のコミットなど）は、移った直後に `rm -rf .next` で前のブランチの build の結果を消し、`npm ci` で依存をその木に合わせてください。依存は、その木の `package-lock.json` を書き換えずに入れます。lock は CI と同じ npm 11 で書かれていることがあり、そのときは作業のコンテナの npm 10 の `npm ci` が、CI では通る lock を欠けとして（`Missing: <パッケージ> from lock file`）止まります。止まったときは、npm の案内する `npm install` を打たず（lock が書き換わり、コミットに紛れ込みます）、CI と同じ npm 11 の `npx -y npm@11 ci` で入れてください。

## 8. CIの成功確認

push後、GitHub ActionsのCIが成功したことを確認してください。

```bash
bash scripts/wait-for-ci.sh
```

CIが失敗した場合は、原因を修正して再度コミット・プッシュし、CIが緑になるまでこのステップを繰り返してください。「環境起因」「今回の変更と無関係」を理由にCI未成功のまま完了させることはできません。CIの成功を確認するまで、サイクルを完了として報告してはいけません。

## 9. 成果の報告

サイクルの成果をownerに報告してください。
何を目的として何をやったのか、次に予定している作業は何かを簡潔に伝えてください。
