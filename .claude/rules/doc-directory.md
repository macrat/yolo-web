# ドキュメントディレクトリのガイド

`./docs/` ディレクトリはドキュメントを保存するための場所です。
以下のようなディレクトリがあります。

- `./docs/ADR/` - ADR 兼実験記録（仮説→賭け→観測→記録）。1件=1ディレクトリで、`open/`（実験中・先頭日付=次回確認日）・`adopted/`（確定）・`expired/`（失効）に分かれます。書式・運用は `./docs/ADR/README.md` を参照してください。
- `./docs/archive/` - もはや利用しなくなったが、将来参照する価値がある知見が含まれているドキュメント。
- `./docs/cycles/` - サイクルごとのドキュメント。1サイクル=1ディレクトリ（`cycle-XXX/`）で、`index.md` が正本です。`index.md` には計画・チェックリスト・完了サマリだけを書き、長くなる内容（レビューの経過ログ・事故報告の詳細・調査メモなど）は同じディレクトリ内の別ファイル（例: `review-log.md`・`incident-1.md`）に分割して `index.md` からリンクしてください。`index.md` の肥大化はレビューの全文通読を不可能にします（cycle-214/215 で実際に発生）。単一ファイル形式（`cycle-XXX.md`）は cycle-283 以前の旧形式で、参照のみ・新規作成はしません。サイクルドキュメント以外は保存しないでください。
- `./docs/research/` - 調査や分析の結果。計画や提案などは保存しないでください。
- `./docs/anti-patterns/` - 過去の失敗から抽出したアンチパターンのチェックリスト。将来再発しそうな失敗を記録する。
- `./docs/knowledge/` - 技術的な知見の蓄積（フレームワーク固有の挙動、LLMの実証的知見など）。
- `./docs/`直下 - 上記以外のドキュメント。古くなったドキュメントは削除するかarchiveに移動してください。

## 注意

- ドキュメントは将来も参照されることを前提に、内容が古くなったものは削除するか `./docs/archive/` に移動してください。誤解を生む可能性があるものや間違っているものは、内容を更新するか削除してください。
- 新しいドキュメントを作成するときは、既存のファイルと重複していないか確認してください。重複している場合は既存のドキュメントを更新するか、古いドキュメントを削除またはarchiveに移動してください。
- ソースコードを読めば分かることはドキュメントにしないでください。代わりに、ソースコード内のコメントを充実させてください。
- ある作業の途中で一時的に必要なドキュメントやファイルは `./tmp/` ディレクトリに保存してください。 `./docs/` に保存するものは、次以降のサイクルでも参照されることを前提にしてください。

## 無ツギハギ原則（生きた参照ドキュメントは常に「最新の coherent 状態のみ」）

**生きた参照ドキュメント**（＝将来の作業への現在の権威ある指針を述べるもの。本ファイルは `paths: docs/**` にスコープされるので、ここでの対象は `docs/` 配下のもの: `docs/site-concept.md`・`docs/knowledge/`・`docs/` 直下の指針類・`docs/backlog.md`）は、**単一の coherent な現在状態だけ**を述べます。**経緯・撤回された旧判断・「以前はこう書いたが是正した」といった追記の痕跡を残してはいけません。**

> ⚠ この原則は `docs/` の外にある top-level の生きた参照ドキュメント（`DESIGN.md`・`CLAUDE.md` 等・repo 直下）にも本来適用されるべきですが、本ファイルの `paths: docs/**` スコープはそれらに届きません。top-level docs に効かせるには常時読込の `CLAUDE.md`（またはグローバル scope の rule）へ同原則を置く必要があり、これは B-583 の再導出の第一ステップで行います（cycle-310/redo-decision.md）。

- 内容が変わったら、古い記述を**その場で書き換え／除去**して、あたかも最初からその形だったかのように読める完璧な状態にする。⚠注記・「cycle-XX で是正」等の**後貼りパッチを積み重ねない**。
- 変更の**経緯・理由・撤回の記録**は、その時のサイクルドキュメント（`docs/cycles/`）に書く。生きた参照ドキュメントは「なぜ今こうなっているか」でなく「今どうなっているか」だけを述べる。
- **理由**: 追記だらけのドキュメントは容易に自己矛盾を生み（本文と後貼り注記が食い違う）、それを読む者に矛盾した判断をさせ、無益な失敗を連鎖させる。矛盾に混乱した書き手はさらに矛盾を書き足す。これを断つため、生きた参照ドキュメントは常にツギハギの跡が一切ない完璧な形を保つ。
- **偽になった現在状態記述の除去は「追記」ではなく、この原則が要求する当のもの**（除去・是正は歓迎。禁じるのは矛盾する追記の積み重ね）。

**本質的に記録型のドキュメント**（時系列の記録そのものが目的のもの: `docs/cycles/`＝経緯／`docs/ADR/`＝仮説→観測→確定のライフサイクル記録／`docs/anti-patterns/` の「発生 cycle」列）は、それぞれの既存の構造化規約に従い、本原則の対象外です。
